# 개발 지침

이 디렉터리는 여러 변경에 걸쳐 유효한 저장소별 개발 지침을 보관한다. 기여자가 현재 규칙과 승인된 기술 결정을 찾을 수 있도록 안내한다. 테스트, 도구, 공식 프레임워크 문서나 개별 설계 문서를 대신하지 않는다.

## 구조와 수록 조건

```text
docs/dev/
  README.md
  <topic>/
    <guidance>.md
```

저장소의 실제 책임과 용어로 주제를 정한다. 다른 저장소의 분류를 복사하거나 빈 디렉터리를 만들지 않는다. 이 예시에 맞추려고 기존 지침을 재구성하지 않는다. 이름과 링크만으로 적합한 파일을 찾기 어려워질 때만 주제별 README를 추가한다.

다음 조건을 모두 충족할 때만 지침을 추가한다.

- 둘 이상의 변경에 적용된다.
- 이후 기여자가 코드, 생성물, 표준 도구나 공식 문서만으로 신뢰성 있게 추론하기 어렵다.
- 현재 저장소 근거나 승인된 결정이 뒷받침한다.
- 자동 검사나 명시한 검토 방법으로 확인할 수 있다.

개별 요구사항, 조사, 결정과 플랜은 `docs/designs/`에 둔다. 일반적인 프레임워크 설명, 사용하지 않는 기술의 가상 규칙, 생성물에서 알 수 있는 사실이나 기존 도구로 강제할 수 있는 규칙을 글로만 적어 두지 않는다.

## 모든 지침 문서의 규칙

작성 전에 적용할 저장소 영역, 대상 기여자와 지침이 돕는 행동 또는 판단을 확인한다. 작성, 구현, 검토와 승인 책임이 다르면 역할을 구분해 명시한다. 책임 역할을 확인할 근거가 없으면 임의 배정하지 말고 `needs human input`으로 보고한다.

지침은 산문 중심이며 고정 템플릿이 없다. 내용을 설명하는 제목 하나, 논리적인 제목 계층과 규칙을 가장 잘 설명하는 순서를 사용한다. 배경보다 규칙이나 결론을 먼저 쓴다. 표를 쓰지 않는다. 실제 도구가 사용하지 않는 ID와 메타데이터를 추가하지 않는다.

저장소 근거, 외부 권고, 제안, 승인된 결정, 예외와 미해결 불확실성을 구분한다. 요청 프롬프트, 에이전트 지침, 요청한 형식, 도구 조건, 진행 보고, 검토 문구와 추적하지 않는 메모는 조사 단서로 취급한다. 저장소 관행의 근거로 보지 않는다.

대상 기여자에게 자연스러운 언어를 사용한다. 추적하는 지침에 자격 증명, 개인 위치, 비공개 URL, 비공개 프로젝트 식별자와 불필요한 내부 위치를 넣지 않는다. 독자에게 파일 위치가 필요하면 확인된 저장소 상대 위치를 쓴다.

### 필수 정보

- 지침이 적용되는 일과 저장소 영역
- 지침을 뒷받침하는 현재 저장소 근거
- 기여자가 이해해야 할 규칙, 권고나 한계
- 적용을 바꾸는 조건과 예외
- 자동 검사 또는 담당 검토자에게 지정한 명확한 검토 방법
- 외부 주장이 규칙에 중요한 영향을 주면 외부 출처와 정확한 버전
- `current`, `proposed`, `deprecated` 중 지침의 상태

저장소별 규칙을 분명하게 할 때만 코드 예시를 사용한다. 문서의 기술 구성과 일치시키고 예시가 설명하는 근거를 밝힌다.

### 금지 내용

- 공식 문서에서 복사한 일반 프레임워크 지침
- 현재 저장소 관행처럼 제시한 제안
- 현재 코드, 설정, 테스트나 생성물과 대조하지 않은 저장소 주장
- 다른 관리 문서에서 복사한 규칙
- 행동과 검증 방법을 밝히지 않은 모호한 지시
- 지침으로 제시한 요청 문구, 진행 보고, 도구 지시나 검토 문구
- 기여자에게 불필요한 비공개 환경 정보, 식별자나 위치

## 상태와 관리 책임

- `current`: 현재 저장소 근거나 승인된 결정이 있고 지금 적용한다.
- `proposed`: 조사했지만 승인되거나 채택되지 않았다.
- `deprecated`: 더는 적용하지 않으며 대체 지침이나 폐기 이유를 밝힌다.

각 규칙을 관리하는 문서는 하나로 정한다. 다른 문서는 링크로 연결한다. 독자와 목적이 같을 때만 합치거나 관리 문서를 선택한다. 프로젝트 전체 선택은 결정 책임자가 승인한 뒤에만 현재 규칙으로 기록한다.

## 지침 탐색과 적용

주제를 정하기 전에 기존 `docs/dev` 파일을 확인한다. 명시된 적용 조건이 현재 요청과 맞는 문서만 읽는다. 이 README보다 먼저 작성됐거나 구조가 달라도 필요한 기존 지침을 사용한다. 오래된 주장, 모순, 불분명한 책임과 빠진 근거를 보고한다. 읽기 전용 조사 중에는 문서를 재구성하거나 고쳐 쓰지 않는다.

적용 전에 지침을 현재 매니페스트, lockfile, 설정, 스크립트, CI, 테스트, 생성물, 코드, 승인된 결정, 의존성 버전과 관찰 가능한 동작에 대조한다. 기존 코드와 글은 낡을 수 있으며 패턴이 권장된다는 증거가 아니다.

새 애플리케이션 코드를 쓰기 전에 설치 버전의 최신 공식 지침을 검토한다. 빌드 또는 문법, 타입 또는 스키마, 필요한 정적 분석, 의존성과 보안 및 관찰 가능한 동작을 확인할 기존 검사 중 비용이 가장 적은 기본 검사를 정한다. 코드 작성 전에 필요한 기존 기본 검사를 실행한다. 필수 검사가 통과하거나 결정 책임자가 미해결 판단을 수용하기 전에는 그 검사에 의존하는 코드 변경을 진행하지 않는다. 저장소에서 정한 명령을 사용한다. 추정한 명령은 제안으로 제시하고 실행 전에 승인받는다.

동작을 바꾸기 전에 사용자가 보는 동작, 외부 API, 저장 데이터, 오류 처리, 영향을 받는 호출자와 연결 지점 중 요청에서 변경을 허용하지 않은 것을 확인한다. 주변 코드를 복사하지 말고 최신 공식 지침, 적용할 저장소 지침과 검사 결과로 새 패턴을 선택한다.

지침 사용, 조사나 검토만으로 코드, 의존성, 설정, 도구나 문서 변경이 허용되지 않는다. 명시적으로 요청한 범위의 변경만 적용한다. 승인된 결정, 문서의 관리 책임이나 저장소 전체 규칙을 바꾸기 전에 결정 책임자에게 묻는다.

## 패턴과 안티패턴 조사

현재 기술 구성과 요청에서 실제로 발생할 수 있는 사례만 조사한다. 코드 모양만으로 분류하거나 가능한 모든 안티패턴을 열거하지 않는다. 현재 저장소는 기술, 버전, 동작과 연결 지점을 확인하는 데 사용한다. 안티패턴이나 권장 코드 예시의 출처로 쓰지 않는다.

패턴 판단은 최신 공식 자료와 고정 리비전의 공개 오픈 소스 애플리케이션을 근거로 한다. 관찰한 실패나 변경 이유는 이슈, pull request, 변경 커밋, 실패 보고나 유지보수자 설명으로 확인한다. 공개 저장소의 현재 코드만으로는 충분하지 않다.

안티패턴과 그에 대응하는 권고마다 다음을 기록한다.

- 막을 실패, 영향 범위와 관찰 가능한 결과
- 공개 소스의 리비전과 확인된 실패 또는 변경 이유
- 최신 공식 지침과 적용 버전
- 최소 안티패턴 코드 예시
- 같은 동작을 구현하는 최소 권장 패턴 코드 예시
- 권장 패턴이 실패를 피하는 이유
- 적용 조건, 예외와 장단점
- 위반을 정확히 찾을 규칙이 있으면 적용 가능한 lint 설정 예시
- lint가 판단할 수 없는 사항과 대신 사용하는 타입, 스키마, 테스트, 실행 중 검사, 브라우저 검사나 담당 검토자의 판단 근거

다른 도구를 제안하기 전에 기존 컴파일러, 타입, 스키마, lint, 테스트와 CI 기능을 재사용한다. 의도한 위반을 허용 가능한 정확도로 찾고, 위반 사례와 정상 사례 또는 동등한 실행 근거가 있으며 실행과 유지보수 비용이 적절할 때만 정적 규칙을 추가하거나 강화한다. 적합한 lint 규칙이 없으면 부정확한 대리 규칙을 쓰지 말고 없다고 밝힌다. 코드 예시는 규칙을 설명하거나 검사기를 실행하는 자료이며 저장소 준수를 입증하지는 않는다.

외부 권고, 현재 저장소 관행, 제안과 승인된 결정을 구분한다. 저장소별 조사 결과, 선택 규칙, 명령, 예외와 근거는 이 최상위 README가 아니라 해당 주제 문서나 도구 설정에 둔다.

## 의존성 변경

외부 의존성을 고르거나 바꾸기 전에 목적, 정확한 버전, 공식 연동 구조와 적용할 디자인 패턴을 확인한다. 해석된 그래프의 모든 직접 및 전이 의존성을 조사한다. 이름, 해석된 버전, 제공 능력, 가능한 문제와 적용 패턴을 기록한다. 적용할 패턴이 없으면 근거 사실과 함께 `not applicable`로 기록한다. 패턴 이름을 지어내지 않는다.

설치된 의존성, 플랫폼 기능과 내부 구현을 비교한다. 필요한 경우 런타임과 peer 호환성, 유지보수, 보안과 라이선스를 확인한다. 조사만으로 의존성이나 설정 변경이 허용되지는 않는다.

허용된 변경 뒤에는 매니페스트, lockfile과 해석된 그래프 자료의 실제 추가, 제거와 갱신을 확인한다. 예상하지 못한 전이 변경을 조사한다. 이어서 영향받는 설정, 타입, 생성물, 테스트, import와 외부 API를 확인하고 필요한 검사를 실행한다.

## 검증

각 속성을 신뢰성 있게 판단할 수 있는 방법 중 비용이 가장 적은 것을 사용한다.

- 정적 분석은 문법, import, 의존 방향, 이름과 검출 가능한 코드 형태를 확인한다.
- 타입 또는 스키마 검사는 데이터 형태, 인터페이스와 호환성을 확인한다.
- 자동 테스트는 관찰 가능한 동작, 실패 처리와 연동을 확인한다.
- 실행 중 검사나 브라우저 검사는 사용 절차, 렌더링, 성능과 운영 신호를 확인한다.
- 담당 검토자는 의도한 동작, 사용성, 시각 품질과 장단점을 판단한다. 승인 책임자는 결정을 승인한다.

해당 검사가 있으면 저장소 도구로 문서 위치, 빈 파일, 미해결 임시 표시와 저장소 상대 링크를 검사한다. AI는 필수 정보, 근거의 뒷받침, 모순, 적용 가능성과 가독성을 확인한다.

적용할 기준마다 `pass`, `needs revision`, `needs human input`, `not applicable` 중 하나로 보고하고 짧은 인용이나 파일 위치를 근거로 제시한다. 현재 규칙을 만들어내지 말고 근거가 없으면 없다고 밝힌다. 검토와 재작성은 별도 행위다.

변경한 지침마다 이후 기여자의 관점에서 최종본을 읽는다. 각 규칙을 저장소 근거, 승인된 결정이나 필요한 외부 출처로 추적한다. 비공개 정보를 검사한다. 제목, 예시와 본문이 작성 요청이 아니라 저장소 규칙을 설명하는지 확인한다.

문서는 규칙을 설명한다. 변경이 규칙을 따르는지는 도구, 실행 근거와 담당 검토자의 판단으로 결정한다.

## 지침 갱신과 유지

지침 갱신이 허용되면 현재 근거를 확인한다. 발견 사항이 현재 규칙, 제안, 폐기 대상 또는 해당 요청에만 필요한 정보인지 판단한다. 중요한 외부 주장은 최신 공식 출처와 저장소 버전에 대조한다. 규칙의 관리 문서를 하나로 정하고 신뢰할 수 있는 검사에 연결한다. 복사한 프레임워크 자료, 내부 요청 문구, 비공개 세부 정보, 임시 표시, 중복 규칙과 오래된 주장을 제거한다.

의존성, 아키텍처, 관찰 가능한 동작이나 뒷받침 근거가 바뀌면 지침을 다시 확인한다. 자주 위반되고 기계적으로 찾을 수 있는 규칙은 도구로 옮긴다. 저장소별 의미를 더하지 않고 코드나 공식 문서만 반복하는 지침은 삭제한다.
