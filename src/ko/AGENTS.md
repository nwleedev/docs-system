# AGENTS.md

## 언어

- **모든 답변과 문서는 결론부터 작성한다.** 결론부터 작성하면 안 되는 경우에는 파일 형식이 주석을 허용할 때 한 줄로 이유를 설명한다.
- 코드와 파일명은 영어를 사용한다.
- 커밋 메시지는 이 문서의 「Git 커밋」 지침을 따른다.
- 저장소가 다른 언어를 지정하지 않았다면 설계 문서, 수행할 절차나 변경 내용에 대한 설명, 코드 주석은 한국어로 작성한다.
- 사용자와 한국어로 소통한다.

## 기본 원칙

**답변**

- 일반 산문에서는 U+00B7을 사용하지 않는다. 인용문, 승인된 이름, 코드, 정규식, 문자 검사, 코드 포인트 설명 또는 평가 입력에 정확한 문자가 필요할 때만 보존한다. 예를 들어 `설계·구현·검증 결과를 기록합니다`는 `설계, 구현과 검증 결과를 기록합니다`로 고친다.
- `계약`, `경로`, `공개`, `좁히다`, `박다`, `제품`, `포화`, `경계`, `소유`, `작은`, `표면화` 등의 표현은 문맥에서 뜻을 확인한다. 전문 분야에서 정확한 용어이면 유지한다. 뜻이 모호하면 문장이 가리키는 규칙이나 행동을 명시한다. 의도를 확인할 수 없으면 사용자에게 질문한다. 목록에 없는 표현에도 같은 기준을 적용한다.

**문서와 커밋의 서술**

- 문서와 커밋 메시지에는 실제 변경 내용, 결정 사항과 확인된 이유를 기록한다. AI가 대화에서 요청이나 지시를 받은 경위는 생략한다.
- 대화에 참여했다는 사실만으로 요청자, 결정자 또는 기여자를 구분하지 않는다. 지침의 역할 이름만으로 실제 인물 관계나 기여를 추정하지 않는다.
- 누가 무엇을 수행하거나 승인할 수 있는지 설명할 때는 기록에서 확인한 역할을 유지한다. 대화 경위를 생략하면서 확인되지 않은 변경 이유나 기여를 추가하지 않는다.

**컨텍스트 압축**

- 컨텍스트 압축 후에는 `AGENTS.md`의 지침, 특히 **기본 원칙**을 다시 확인한 뒤 진행한다.
- 컨텍스트 압축 후에도 어떤 변경을 완료했는지 확인할 수 있도록 변경 목적에 따라 커밋을 구성한다. 재개 시에는 먼저 Git 이력을 확인한다.

**금지 사항**

- 코드 구현을 명시적으로 요청하지 않았다면 코드를 구현하지 않는다.
- 테스트 코드 작성을 명시적으로 요청하지 않았다면 테스트 코드를 작성하지 않는다.
- TDD를 명시적으로 요청하지 않았다면 TDD를 수행하지 않는다.
- 사용자가 요청한 범위를 임의로 변경하지 않는다.
- 이모지를 사용하지 않는다.
- 사용자 승인 없이 변경사항을 제거하거나 덮어쓰는 등 되돌리기 어려운 명령을 실행하지 않는다.
- 각 부분의 역할을 코드에서 이해할 수 있도록 작성하고 불필요한 주석은 생략한다.
- 코드를 작성한 뒤 유사한 구현과 비교한다. 같은 동작을 수행하고 같은 조건을 검증하는 코드인지 비교한 뒤 하나의 구현으로 통합할지 판단한다.
- 오류를 해결하기 위해 타입 검사를 비활성화하지 않는다.
- 설계에 명시된 요구사항이나 기능을 임의로 비활성화하지 않는다.
- 테스트 실패를 숨기기 위해 테스트를 삭제하거나 약화하지 않는다.
- 문서에는 이 저장소의 독자가 알아야 할 내용과 실제 결정 사항을 명시한다. 어느 프로젝트에나 적용될 상투적인 설명은 생략한다.
- 의미를 더하지 않는 상투적 표현과 과장된 수식어는 생략한다.
- 소제목별 문단 길이나 항목 수를 일률적으로 맞추지 않는다. 내용상 구분할 이유가 없는데도 세 항목으로 분류하거나, 문단마다 같은 연결 표현을 반복하지 않는다.
- 영어 문장이 가리키는 대상, 행동, 조건과 책임 주체를 확인한 뒤 한국어로 작성한다. 영어 단어를 하나씩 대응시키는 직역은 피한다.
- 영어 기술 용어를 한국어 한 단어로 일괄 치환하지 않는다. 분야에서 정확한 용어이면 유지하고 뜻이 모호하면 실제 행동이나 조건을 명시한다.

**기존 기능과 코드 작성**

- 사용자가 기능 변경이나 제거를 요청하지 않았다면 기존 기능을 없애거나 약화하지 않는다. 사용자에게 보이는 결과, 외부에서 사용하는 API, 저장되는 데이터, 오류 처리, 현재 테스트와 실행 결과를 확인해 유지할 기능을 정한다.
- 기존 코드는 현재 동작을 확인하는 자료로 사용한다. 여러 파일에서 반복되거나 수정할 코드 주변에서 사용된다는 이유만으로 같은 구현 방식을 채택하지 않는다.
- 코드를 작성하기 전에 사용 중인 기술과 버전에 해당하는 공식 문서, 저장소의 개발 지침, 설정과 검사 결과를 확인한다. 이를 바탕으로 요구사항을 충족할 구현 방식을 선택하고 기존 코드에서 발견한 안티패턴은 반복하지 않는다.
- 선택한 방식으로 구현하되 기존 기능, 외부에서 사용하는 API, 데이터 형식과 필요한 호환성을 유지한다. 값이나 형식을 변환해야 한다면 기존 코드와 데이터를 주고받는 부분에서만 변환한다. 다른 부분까지 이전 구현 방식에 맞춰 수정하지 않는다.
- 선택한 방식을 적용하려면 기존 기능이나 저장소 전체 구조를 변경해야 하는 경우, 유지할 기능과 예상 영향을 사용자에게 설명하고 승인을 받은 후에 진행한다.
- 테스트는 사용자가 확인할 수 있는 동작과 승인된 호환 조건이 유지되는지 검증한다. 이전 코드와 구현 구조가 같은지만 비교해서는 이 조건을 검증할 수 없다.

**리서치**

- 모든 요청에 대해 여러 방법으로 인터넷 자료를 검색하고 출처 간 내용을 대조해 사실과 최신 여부를 확인한다.
- 블로그나 큐레이션 글보다 공식 문서, 표준 문서, 최초 발표 자료, 실제 소스 코드 등 1차 자료를 우선한다. 1차 자료를 최소 다섯 개 확보하도록 시도한다.
- 현재 시점의 최신 정보를 먼저 확인하고 모든 답변에 신뢰도 높은 출처를 제시한다.
- 시각 분야의 조사와 교차 검증에는 MCP를 사용한다.
- GitHub 저장소 파일과 이슈를 조사할 때에는 `gh` CLI를 사용한다.
- 소스 코드는 개인 저장소보다 공식 저장소를 우선한다.
- 사용자가 조사 내용을 검증할 수 있도록 답변에 출처를 표시하고, 인용이 허용되는 범위에서 관련 문구를 짧게 인용한다.
- 조사 기준은 조사 과정과 사용자에게 전달하는 답변에 적용한다. 조사 출처, 메모, 권고 사항, 인용 문구를 대상 파일에 포함하려면 사용자가 그 파일에 출처 표기를 요청했고 독자에게도 그 정보가 필요해야 한다.
- 저장소에 라이선스, 정책, 검사 도구, 문서 또는 결정 사항이 없으면 사용자에게 별도로 보고한다. 누락을 이유로 이를 임의로 추가하거나 대상 문서에 임시 문구, 경고, 관리자용 지시를 작성하지 않는다. 이를 보완하면서 요청받은 결과물이 달라진다면 먼저 승인을 받는다.

## 진행 순서와 요구사항 변경

- 답에 따라 요구 동작이 달라지는 질문은 계획을 확정하기 전에 해결한다. 검토가 끝난 계획에 따라 구현한다.
- 두 단계가 같은 파일이나 공유 상태를 변경하면 한 번에 한 단계씩 실행한다. 다음 단계에 앞 단계의 실행 결과가 필요하면 앞 단계를 완료한 뒤 다음 단계를 시작한다. 검토에서 확인한 수정 사항은 검토를 마친 후 반영한다.
- 구현과 검토를 별도 세션에서 진행하면 검토 세션에서는 요청에 명시된 Git 리비전과 저장소 규칙으로 검토 대상을 식별한다. 필요한 리비전이 누락됐거나 저장소 상태와 일치하지 않으면 그 리비전에 관한 검토는 보류한다.
- 요구사항이 변경되면 그 요구사항에 의존하는 다음 단계를 시작하기 전에 진행 중인 절차에 미치는 영향을 확인한다.
- 영향을 받지 않는 절차는 계속한다. 영향을 받은 절차는 중단하거나 변경된 요구사항에 맞는지 다시 검증한다.
- 영향 여부를 판단할 수 없거나 여러 단계가 공유하는 전제와 완료 조건이 바뀌면, 영향을 받을 수 있는 절차를 모두 중단하고 요구사항 작성자에게 확인한다.

## 스킬 사용 조건과 문서 위치

필요한 스킬이나 필수 참고 자료의 내용을 확인할 수 없으면 진행을 중단한다. 어떤 자료를 확인할 수 없는지 보고하고 대체 규칙을 추정하지 않는다.

- `docs/designs/README.md`가 없으면 `$flexible`에 따라 기존 문서 관리 규칙을 먼저 확인한다. 규칙이 없고 설계 문서 안내가 필요하면 이 파일의 생성을 제안한다. 사용자가 동의한 후에만 생성한다.
- `docs/dev/README.md`가 없고 조사 내용을 기록해야 한다면 `$programming`과 저장소 지침에 따라 기록할 위치를 제안한다. 이 README는 사용자가 동의한 후에만 생성한다.

### 인수인계 정보

- 재사용할 문서, 코드 등을 작성하거나 수정할 때는 표현을 검토하기 전에 `$handover`를 사용한다. 다음 에이전트에게 필요한 정보를 지정한 인수인계 파일에 기록한다. 기존 문서나 코드에서는 이관한 메모를 삭제한다. 인수인계 기록과 수정한 파일은 함께 공유한다. 이관하거나 갱신할 정보가 없으면 기록을 추가하지 않는다.
- 인수인계 기록에서 프로젝트의 현재 상태를 확인하거나 기록을 갱신할 때도 `$handover`를 사용한다. 열람만 요청받으면 파일을 수정하지 않는다.
- 기본 인수인계 파일은 저장소 최상위의 `HANDOFF.md`다. 사용자 요청이나 저장소 지침에서 파일 이름과 위치를 별도로 지정할 수 있다. 일반 대화나 진행 상황 보고만으로 `$handover`를 실행하지 않는다.

### 글과 문구

- 재사용할 글이나 이름을 작성하기 전에 언어와 관계없이 `$terms`로 프로젝트의 표현 규칙과 공식 명칭을 확인한다. 요구되는 행동은 요구사항에서, 승인 여부는 승인 기록에서, 실제 수행 내용은 실행 기록에서 확인한다. 한국어가 포함된 부분에는 스킬 본문의 한국어 기준을 적용한다.
- 저장하거나 공유하기 직전에 `$terms`로 이번 요청에서 작성하거나 수정한 각 파일의 텍스트 전체를 검토한다. 파일명, 화면 문구, 커밋 메시지 등 함께 저장하거나 공유할 텍스트도 같은 검토에 포함한다. 작성이나 수정을 요청받으면 문맥과 자료에서 뜻을 확인한 표현을 교정한다. 검토만 요청받으면 지정한 파일이나 문구의 수정안을 답변에 제시한다.
- 확립된 용어나 정확한 명칭을 유지하면 그 이유를 설명한다. 의도한 뜻, 책임 주체 또는 승인 여부를 알아야 표현을 교체할 수 있다면 사용자에게 확인한다.
- 사용자가 특정 문구나 공개할 결과물을 지정해 검토를 요청하면, 파일 변경 여부와 관계없이 지정한 내용 전체를 검토한다.
- 일반 대화나 진행 상황 보고만으로 `$terms`를 실행하지 않는다.

### 리서치, 교차 검증, 설계와 문서화

- 요구사항을 구체화하거나 실행 계획을 작성할 때, 또는 계획의 실행을 요청받았을 때 `$flexible`을 사용한다. `docs/designs/**`의 문서를 조사, 작성, 검토하거나 작성 계획을 세울 때, 내용을 검증하거나 문서에 따라 구현할 때도 사용한다.
- 요구사항을 작성하거나 검토할 때는 실제 목표와 사용 상황을 확인한다. 프로젝트 이름만으로 기능을 추정하지 않는다. 별도 요청을 기다리지 말고 착수 조건을 조사하고 새로 확인한 사실이 계획을 바꾸는지 판단한다. 조사 내용을 처음 보고할 때는 어느 단계부터 시작할 수 있는지와 그 이유를 설명한다. 정보가 부족하면 무엇을 확인해야 하는지, 충분하면 어떻게 판단했는지 밝힌다. 필요한 변경과 그 이유, 완료 여부를 확인할 방법도 제시한다. 빈 파일 생성이나 문서 재배치 요청은 지정된 범위에서 수행한다.
- 요구사항과 승인된 결정은 AI의 조사 결과나 제안과 구분한다.
- 저장소에 `docs/designs/README.md`가 있으면 설계 문서의 구조, 기록 위치와 검사 기준은 그 문서를 따른다.

### 개발 지침, 기술 스택과 검사 설정

- 소스 코드, 테스트, CLI, 라이브러리, 스크립트, 빌드, CI 또는 설정 변경을 계획, 구현, 검토, 리팩터링, 테스트 또는 문서화할 때와 의존성이나 검사 설정을 변경할 때에는 `$programming`을 실행한다.
- 저장소에 `docs/dev/README.md`가 있으면 개발 방법, 기술별 규칙, 실행 명령과 검증 절차는 그 문서와 거기서 지정한 주제별 지침을 따른다.

### 구현 방법 비교와 예시

- 프로젝트에 적용할 컴퓨터 과학 원리, 디자인 패턴, 파일과 디렉터리를 포함한 모듈 구성 또는 시스템 아키텍처를 조사할 때도 `$programming`을 사용한다. 적용 이유와 배경, 프로젝트에서 그 방식을 선택한 이력을 예시와 함께 설명하거나 기록해 달라는 요청도 포함한다.
- 구현 전이라도 어떤 조건에서 문제가 발생하고 어떤 원리로 설명되는지 조사한다. 조사 내용을 처음 보고할 때는 구현 대안, 구체적으로 변경할 부분과 이유, 예상 위험을 제시하고 다음 결정을 위해 무엇을 확인해야 하는지 설명한다. 요구사항이나 계획에 관한 판단과 구현 방법에 관한 판단을 구분해 각각 필요한 스킬을 선택한다.
- 구현 방법을 조사한 내용을 기록할 파일을 사용자가 지정하면 그 파일에 작성한다. 지정하지 않았으면 파일을 수정하지 않고 적합한 위치를 제안하며 대화에서 조사 내용을 설명한다. 소스 코드나 테스트를 변경하려면 구현 또는 개발을 명시적으로 요청받아야 한다.

## 환경변수 및 민감정보

- 개인 민감정보, 보안 키, 내부 URL, 토큰과 자격 증명은 Git에 커밋하지 않는다. 개인 PC 계정이 포함될 수 있는 절대 경로도 Git에 커밋하지 않는다.
- Git에 커밋해서는 안 되는 값은 `.env` 같은 환경변수 파일로 관리한다.
- 테스트에 필요한 민감한 값을 코드에 직접 작성하지 않는다. 테스트 전용 환경변수를 사용하거나 테스트에서 fixture를 생성한다.
- 커밋하기 전에 환경변수 파일, 인증정보, 토큰, 개인정보, 내부 URL, 비공개 저장소 참조와 개인 계정이 드러나는 절대 경로가 포함되지 않았는지 확인한다.

## 임시 파일

- 임시 파일을 `/tmp` 같은 시스템 디렉터리에 저장하지 않는다.
- 임시 파일은 프로젝트 최상위 `temps/<scope>-<nonce>/` 아래에 저장한다.
- `scope`에는 임시 파일의 용도를 식별할 이름을, `nonce`에는 이름 충돌을 방지할 짧은 식별자를 사용한다.
- MCP로 생성한 스크린샷도 같은 임시 디렉터리에 저장한다.
- AI 에이전트가 생성한 임시 파일은 사용이 끝나면 제거한다.

## Gitignore

- `.gitignore`에 등록된 파일을 커밋하지 않는다.
- 커밋 전에 민감정보나 자격 증명이 포함되지 않았는지 확인한다.
- 커밋할 파일을 이 문서의 「환경변수 및 민감정보」 기준으로 확인한다.

## Git 브랜치

- 요청을 수행하기 전에 현재 Git 브랜치를 확인한다.
- 별도 워크트리 브랜치는 사용자가 생성을 명시적으로 요청한 경우에만 생성한다. 요청을 받으면 현재 브랜치와 저장소 규칙을 확인한다. 수동으로 생성하는 워크트리는 저장소 최상위의 `.worktrees/` 아래에 배치한다.
- 사용이 끝난 워크트리 브랜치의 제거를 제안하기 전에 그 브랜치에만 있는 커밋과 워크트리의 미커밋 변경이 있는지 확인한다.
- 사용자는 기존 워크트리 브랜치에서 계속 진행하거나 별도 워크트리 브랜치 생성을 요청할 수 있다.
- 설계와 구현은 같은 브랜치에서 진행한다. 브랜치 `type`은 변경 목적에 따라 선택하고 `docs`를 기본값으로 사용하지 않는다.
- 현재 브랜치가 `main`, `master`, `develop`, `dev`, `release/*`이면 변경 전에 별도 브랜치를 생성한다.
- `.codex`, `.claude` 폴더 안의 에이전트 환경 설정은 브랜치를 변경하지 않고 진행할 수 있다.
- 브랜치 이름은 `<type>/<short-description>` 형식으로 지정한다. 워크트리 디렉터리 이름도 브랜치 이름에 맞춰 `.worktrees/<type>/<short-description>`로 지정한다.

허용되는 `<type>`은 `feature`, `fix`, `hotfix`(긴급 수정에만 사용), `refactor`, `test`, `docs`, `chore`다.

## Git 커밋

- 현재 변경사항을 하나의 목적으로 설명할 수 있는지 검토하고, 커밋이 필요하면 그 단위로 커밋한다.
- 커밋 제목, 본문과 footer에는 실제로 변경한 내용과 변경 이유를 설명한다. 사용자 프롬프트, 에이전트 지침, 내부 진행 지시, 검토 기준, 비공개 자료, 에이전트의 수행 과정은 포함하지 않는다.
- 커밋 형식은 제목, 본문과 footer로 구성한다.
- 제목 형식은 `<type>(<scope>): <subject>`를 사용한다.
- 제목의 `type`은 `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `perf`, `ci`, `build` 중 하나를 사용한다.
- 제목의 `scope`에는 변경 대상 모듈이나 컴포넌트의 이름을 영어로 표기한다.
- 제목의 `subject`는 영어 명령형으로 작성하고 마침표를 찍지 않는다. `subject`는 영어 소문자로 시작한다.
- 본문에는 변경한 이유를 영어로 먼저 작성한 뒤 같은 내용을 한국어 명사형으로 작성한다. 구체적인 변경 내용은 Git diff에서 확인할 수 있다.
- 필요하면 `BREAKING CHANGE:`, `Fixes #N`, `Closes #N` footer를 사용한다.
