# AGENTS.md

## 언어

- 코드 작성과 파일명은 영어를 사용한다.
- Git 커밋의 `type`과 `scope`는 영어를 사용하고, 제목의 `subject`와 본문은 한국어를 사용한다.
- 사용자와 의사소통할 때에는 한국어를 사용한다.
- 설계 문서, 작업 설명, 코드 설명용 주석은 한국어를 사용한다.

## 기본 원칙

**컨텍스트 압축**

컨텍스트가 압축되면 AGENTS.md, 특히 **기본 원칙**을 숙지하여 작업에 반영합니다.

**올바른 작업 진행**

- "코드 구현을 수행해라"라는 지시가 없으면 코드 구현을 하지 않습니다.
- "테스트 코드 작성을 수행해라"라는 지시가 없으면 테스트 코드 작성을 하지 않습니다.
- "TDD 작업을 수행해라"라는 지시가 없으면 TDD 작업을 하지 않습니다.
- 작은 변경을 하지 않는다.
- 작업의 범위를 임의로 변형시키지 않는다.
- 안전한 작업을 하지 않는다. 올바른 작업을 한다.
- 사용자는 다양한 분야의 작업을 동시에 안정적으로 진행하기 위해 워크트리 브랜치의 생성을 요구할 수 있다.
- 이모지를 사용하지 않는다.
- 주석을 사용하게 되면 주석의 설명과 코드의 동작이 일치하지 않을 수 있다. 코드가 각각 어떤 역할을 할 수 있을지 이해할 수 있을 정도로 작성한다.
- 코드를 한번 작성하고 나서 끝내지 않는다. 유사한 코드가 있는지 확인하고 모듈화를 할 수 있는지 검토한다.
- 에러를 해결하기 위해 타입 검사를 비활성화하지 않는다.
- 설계에 명시된 요구사항이나 기능을 임의로 비활성화하지 않는다.
- 테스트 실패를 숨기기 위해 테스트를 삭제하거나 약화하지 않는다.

**올바른 글쓰기**

- 다른 프로젝트에 그대로 붙여 넣을 수 있는 상투적인 글을 쓰지 않는다. 현재 독자, 저장소, 결정 사항을 구체적으로 반영한다.
- 각 문장에는 근거, 결정, 해야 할 일 또는 이해에 필요한 배경 중 하나가 있어야 한다. 앞 문장을 되풀이하는 소개, 맺음말, 요약과 연결 문장은 지운다.
- 뜻을 보태지 않는 상투적 표현과 과장된 수식어를 쓰지 않는다.
- 소제목마다 같은 길이의 문단을 만들거나, 근거 없이 세 항목으로 나누거나, 같은 연결 표현을 되풀이하지 않는다. 내용에 맞춰 글의 짜임을 정한다.
- 영어를 낱말 단위로 옮기지 않는다. 원문이 가리키는 대상, 행동, 조건과 책임 주체를 확인한 뒤 자연스러운 한국어 문장을 새로 쓴다.
- 영어 기술 용어를 정해진 한국어 한 단어로 자동 변환하지 않는다. 해당 분야에서 뜻이 정확한 용어는 유지하고, 그렇지 않으면 실제 행동이나 조건을 드러낸다.
- 문장마다 지칭 대상, 행동 주체, 행동, 조건과 결과를 구분할 수 있는지 따로 확인한다. 표현이 자연스러워도 여러 생각을 압축해 그 관계를 알 수 없다면 다시 쓴다.
- 문장을 각각 고친 뒤 문단과 문서 전체를 다시 읽는다. 역할 이름, 지칭 대상, 가정, 결정과 앞 단계의 결과가 다음 내용까지 이어지는지 확인한다.
- 글을 내보내기 전에 소리 내어 읽는다고 생각하며 한 번 검토한다. 한국어 화자가 같은 상황에서 쓰지 않을 표현, 지나치게 반듯하지만 정보가 없는 문장, 영어 원문이 떠오르는 직역 문장은 다시 쓴다.

**레거시 코드**

- 레포에 존재하는 모든 코드, 문서는 레거시일 가능성이 있다고 생각한다. 항상 의심한다.
- 기존에 존재하는 기능의 경우 "제거하라", "대체하라"와 같은 명시적인 지시가 없으면 제거하지 않습니다.
- 코드를 작성할 때마다 작성할 코드와 관련된 베스트 패턴, 아키텍처, 디자인 패턴을 지속적으로 리서치+교차검증한다.
- 베스트 패턴 기반으로 작성할 때에도 최소한 "기존 레거시 코드"와 호환될 수 있도록 작성합니다.
- 테스트는 코드가 레거시인지에 대한 여부 관계없이 관찰 가능한 동작을 검증해야 한다.

**리서치**

- 모든 프롬프트에 대해서는 다양한 방법으로 인터넷 자료를 조사해 교차 검증하여 정확성이나 최신성을 확보한다.
- 블로그, 큐레이션 글 대신 공식 문서, 표준 문서, 원문, 실제 존재하는 소스 코드와 1차 자료(공식문서)를 최소 5개 이상 찾아서 교차검증한다.
- 현재 시점 기준 최신 정보를 먼저 확인하고, 모든 답변에는 신뢰도 높은 출처를 함께 제시한다.
- 시각적인 분야에 대한 리서치, 교차검증이 필요할 때에는 MCP를 사용합니다.
- Github에 있는 레포 파일 및 이슈를 리서치할 때에는 gh cli를 사용한다.
- 소스 코드는 공식 레포를 우선하고 개인 사용자 레포를 우선하지 않는다.
- 리서치한 자료는 사용자가 진위 여부를 확인할 수 있게 출처와 허용 가능한 한도의 짧은 인용을 남긴다.
- 리서치 규칙은 에이전트의 조사 과정과 사용자에게 전달하는 답변에 적용한다. 사용자가 대상 파일에 출처를 요구했고 그 파일의 독자에게 필요한 경우가 아니면 조사 출처, 조사 메모, 권고 사항이나 원문 표현을 대상 파일에 옮기지 않는다.
- 저장소에 라이선스, 정책, 검사 수단, 문서 또는 결정 사항이 없다는 사실을 발견해도 이를 추가할 권한이 생기지는 않는다. 대상 문서에 임시 문구, 경고 또는 관리자용 작업을 넣지 말고 발견한 문제를 사용자에게 별도로 알린다. 요청한 결과가 달라진다면 승인받기 전까지 수정하지 않는다.

**애플리케이션 검증**

- 브라우저를 사용해서 실제로 애플리케이션이 어떻게 작동하는지 확인하세요.
- 명령어를 임의로 지어내지 않습니다. 프로젝트에 정의된 명령어로 애플리케이션을 실행시킨다.
- 만약 명령어가 없다면 프로젝트의 컨벤션과 맞는 명령어를 추론하고 이를 답변에 포함시킵니다.
- E2E 테스트를 진행하거나 실제 애플리케이션 동작을 확인할 때에는 개발 서버를 직접 실행하고 사용이 끝나면 종료한다.

## 서브에이전트 사용

- 단순한 작업, 하나의 문맥에서 끝나는 작업, 작업 분할 비용이 예상 절감 시간보다 큰 작업에는 서브에이전트를 사용하지 않는다.
- 작업을 둘 이상의 독립적인 단위로 나눌 수 있고 예상 절감 시간이 작업 분배와 결과 종합 비용보다 크면, 메인 에이전트는 해당 작업을 서브에이전트에 분배한다.
- 각 서브에이전트에는 적용할 요구사항 기준, 정확한 작업, 확인할 경로, 파일 변경 허용 범위, 중단 조건과 반환할 결과를 전달한다.
- 사용자가 특정 Skill을 지정했거나 현재 실행 중인 Skill이 서브에이전트 사용 방법을 정의하면 해당 Skill의 절차를 따른다. 같은 역할을 중복 호출하거나 Skill 바깥에서 별도 검토 단계를 추가하지 않는다.
- 메인 에이전트는 요구사항 기준, 작업 분배, 의존 관계, 결과 종합, 충돌 해결, 중단 판단과 최종 검증을 담당한다.
- 서브에이전트의 작업 보고를 완료 증거로 간주하지 않는다. 메인 에이전트가 실제 파일, 변경사항과 검사 결과를 확인한다.

### 병렬 실행

- 서로 다른 질문을 조사하는 리서치, 서로 다른 관점의 읽기 전용 검토, 독립적인 로그 및 테스트 결과 분석은 병렬로 실행할 수 있다.
- 구현 작업은 수정 파일뿐 아니라 공용 인터페이스, 스키마, 생성 파일, 잠금 파일, 설정, 개발 서버, 데이터베이스와 테스트 데이터가 겹치지 않을 때만 병렬로 실행한다.
- 작업 결과가 다른 작업의 입력이 되거나 영향 범위를 확신할 수 없으면 병렬로 실행하지 않는다.
- 실행 환경의 동시 실행 한도를 넘기지 않고, 남은 작업은 대기시켰다가 자리가 생기면 실행한다.

### 순차 실행

- 요구사항의 동작을 바꿀 질문을 해결한 뒤 계획을 확정하고, 검토된 계획을 기준으로 구현을 시작한다.
- 같은 파일이나 공용 상태를 변경하는 작업과 앞 작업의 결과에 의존하는 작업은 순차적으로 실행한다.
- 검토 결과에 따른 수정과 재검토는 기존 검토가 끝난 뒤 순차적으로 실행한다.
- 독립된 작업 단위의 구현이 완료되어 안정된 변경사항이나 커밋이 생겼다면, 다음 독립 작업의 구현과 해당 단위의 읽기 전용 검토를 겹쳐 실행할 수 있다.

### 요구사항 변경

- 요구사항이 변경되면 새로운 작업 분배를 잠시 멈추고 진행 중인 작업에 미치는 영향을 확인한다.
- 영향을 받지 않는 작업만 계속하고, 영향을 받은 작업은 중단하거나 변경된 요구사항을 기준으로 다시 검증한다.
- 영향 여부를 확신할 수 없거나 공통 전제와 성공 조건이 바뀌면 전체 관련 작업을 멈추고 요구사항 작성자에게 확인한다.

### 글과 문구 검토

- 한국어 공개 문구, 이름 또는 사용자에게 보낼 답변을 작성하거나 고치는 작업을 시작할 때 설치된 `use-words-review` 스킬의 `references/korean.md`의 내용을 불러온다. 화면과 접근성 문구, 코드 주석, 커밋과 풀 리퀘스트 문구, 이슈 문구, 릴리스 안내와 재사용할 문구도 포함한다. 이 자료는 한국어 부분에만 적용한다.
- 모든 한국어 답변을 보내기 전에 사용자에게 보일 초안을 문장별로 점검하고, 위반한 문장을 고친 뒤 수정한 답변만 보낸다. 짧은 진행 알림과 확인 답변에도 자체 점검을 적용하되, 참조 자료를 다시 읽거나 서브에이전트를 매번 호출하지 않는다.
- 일반 산문에서는 U+00B7을 사용하지 않는다. 인용문, 승인된 이름, 코드, 정규식, 문자 검사, 코드 포인트 설명 또는 평가 입력에 정확한 문자가 필요할 때만 보존한다. 예를 들어 `설계·구현·검증 결과를 기록합니다`는 `설계, 구현과 검증 결과를 기록합니다`로 고친다.
- 영어 용어를 정해진 한국어 한 단어로 자동 변환하지 않는다. `계약`, `경로`, `공개`, `좁히다`, `박다`는 고정된 단어 목록이 아니라 예시다. 해당 분야에서 확립된 용어이며 지칭 대상, 행동, 조건과 결과가 분명할 때만 유지한다. 그 밖의 경우 실제 규칙이나 행동을 적고, 근거로 뜻을 정할 수 없으면 `needs human input`으로 판정한다.
- 번역체와 정형화된 AI 문체를 지운다. `본질적으로`, `다양한 측면에서`, `강력한`, `원활한`처럼 사실을 더하지 않는 표현을 다시 쓴다. 답변을 되풀이하는 도입과 결론, 근거 없이 만든 세 항목, 같은 문단 구조의 반복을 만들지 않는다.
- 커밋하거나 공유할 글 또는 이름을 만들거나 바꾼 뒤에는 커밋하거나 공유하기 전에 설치된 `use-words-review` 스킬로 검토한다. 문구나 공개 결과물 검토를 요청받았을 때도 실행한다.
- 요구사항, 결정, 정책, 보안, 개인정보, 라이선스, 소유권 또는 재사용할 문구를 담은 한국어 답변은 먼저 초안을 만들고, 범용 서브에이전트를 사용할 수 있으면 보내기 전에 `use-words-review`를 실행한다.
- 같은 커밋이나 공유 단위에 속한 변경은 한 번에 검토한다. 변경된 결과물과 이름, 독자와 독자가 해야 할 일, 문장에 나온 역할, 적용할 저장소 규칙, 후보 커밋 또는 게시 문구를 전달한다.
- 스킬이 서브에이전트를 사용할 수 있는 환경이라면 1개의 범용 서브에이전트에게 읽기 전용 의미 검토를 맡기게 한다. 서브에이전트가 없으면 스킬의 주 에이전트 대체 절차를 따른다. 사용자가 검토 결과를 요청했을 때는 독립 검토를 수행하지 못했다고 밝히고, 답변을 보내기 전 검토에는 이 내부 상태를 덧붙이지 않는다.
- 사용자가 검토 결과 자체를 요청했을 때는 적용되는 항목마다 `pass`, `needs revision`, `needs human input`, `not applicable` 중 하나를 보고한다. 통과하지 못한 결과에는 위치와 이유를 함께 적는다. 답변을 보내기 전 검토에서는 지적 사항을 반영한 답변만 보내고, 사용자가 요청하지 않은 내부 검토 보고를 덧붙이지 않는다.
- 검토와 수정을 분리한다. 결과를 실제 변경과 대조하고 검토 중 파일이 바뀌지 않았는지 확인하며, 별도로 승인받은 작업에서만 수정한다.

### 설계 문서

- `docs/designs/**`의 문서를 작성, 검토, 계획, 구현 또는 검증에 사용하기 전에 `docs/designs/README.md`를 읽는다.
- 해당 작업의 `requirements.md`가 있으면 전체 확인하고, 현재 질문에 필요한 참고 자료, 결정사항, 계획과 저장소 근거만 추가로 읽는다.
- 설계 문서 묶음이 필요하지만 `requirements.md`가 없으면, AI는 현재 요청에 명시된 결과, 조건, 완료 증거와 사용자가 직접 밝힌 질문만으로 수정하기 쉬운 최소 초안을 만들 수 있다. 명시되지 않은 내용을 추론해서 채우거나 빈 소제목과 임시 문구를 추가하지 않는다.
- 요구사항 작성자는 `requirements.md`의 문구와 순서를 정한다. 최소 초안을 만든 뒤에는 요구사항 작성자가 변경을 요청하거나 정확한 문구를 승인했을 때만 AI가 수정하며, 승인되지 않은 추론을 요구사항이나 결정사항으로 기록하지 않는다.
- 설계 문서 묶음을 만들 필요가 없는 대화 안의 검토나 조사에서는 현재 요청을 작업 기준으로 사용할 수 있으며, `requirements.md`가 없다는 이유만으로 작업을 중단하거나 문서 묶음을 만들지 않는다.
- 파생 문서는 고정 템플릿을 따르지 않는다. 대신 `docs/designs/README.md`에 정의된 필수 정보, 금지 사항, 검사 방법과 가독성 기준을 충족해야 한다.
- 요구사항 원문과 해당 소제목을 인용해 참고 자료, 결정사항, 작업 단위와 검증 결과를 연결한다.
- 작업이 끝나면 `docs/designs/README.md`의 검사 기준으로 문서와 실제 결과를 다시 확인한다.

### 개발 지침

- 애플리케이션 변경을 계획, 구현, 검토, 리팩터링, 테스트 또는 문서화하기 전에 `docs/dev/README.md`를 읽는다.
- 전체 `docs/dev`를 읽지 않고 현재 작업에 필요한 지침만 선택하며, 계획이나 이에 준하는 실행 입력에 선택한 파일을 기록한다. 계획을 커밋한 뒤에는 계획을 마지막으로 변경한 커밋에 포함된 각 지침 파일을 검토 기준으로 삼는다. 이후 지침이 바뀌면 영향을 받은 작업을 계속하기 전에 기준 내용과 비교한다.
- 개발 지침은 고정 템플릿을 따르지 않는다. 대신 `docs/dev/README.md`에 정의된 포함 조건, 필수 정보, 금지 사항, 검사 방법과 가독성 기준을 충족해야 한다.
- 현재 코드, 설정, 테스트, 생성 산출물, 승인된 결정과 의존성 버전을 확인한 뒤 기존 지침을 현재 규칙으로 사용한다.
- 자동으로 확인할 수 있는 규칙은 린트, 타입 또는 스키마 검사, 테스트, 훅, CI나 실행 결과로 확인한다. 제품 의미는 담당 검수자가 확인하고 승인 여부는 승인 책임자가 결정한다.
- 작업이 끝나면 선택한 개발 지침과 실제 변경사항이 일치하는지 다시 확인한다.

### 검사 원칙

- 문서의 제목과 구성은 내용에 맞게 선택할 수 있지만, 필수 정보가 실제로 존재하는지는 근거 위치와 함께 항목별로 검사한다.
- AI는 검사 결과를 `pass`, `needs revision`, `needs human input`, `not applicable`로 구분하고, 근거를 찾지 못하면 추정하지 않는다.
- 문서 검사와 문서 수정은 별도 작업으로 진행한다. 검사를 수행하면서 요구사항, 결정사항 또는 현재 지침을 자동으로 다시 작성하지 않는다.
- 문서만으로 구현 준수를 증명하지 않는다. 저장소 검사와 담당 검수자의 명시적인 검토를 함께 사용한다.
- 조사하거나 검토하면서 발견한 문제를 대상 문서를 수정해도 된다는 뜻으로 해석하지 않는다. 새로운 결정, 정책, 소제목 또는 작업 범위 변경이 필요하면 별도로 보고하고 승인받은 뒤 수정한다.

## 환경변수 및 민감정보

- 개인 민감정보, 보안 키, 내부 URL, 토큰, 크레덴셜은 Git에 커밋하지 않는다. 개인 PC 계정이 포함될 수 있는 절대 경로도 Git에 커밋하지 않는다.
- Git에 커밋하면 안 되는 데이터는 `.env` 같은 환경변수 파일로 관리한다.
- 테스트 코드도 민감한 목업 값을 직접 하드코딩하지 않고 테스트 전용 환경변수나 테스트 코드 내 fixture 작성 방식을 사용한다.
- 커밋하기 전에 환경변수 파일, 인증정보, 토큰, 개인정보, 내부 URL, 비공개 저장소 참조와 개인 계정이 드러나는 절대 경로가 포함되지 않았는지 확인한다.

## 임시 파일

- PC 루트 위치의 `/tmp` 같은 폴더를 사용하지 않는다.
- 임시 파일은 프로젝트 최상위 `temps/<scope>-<nonce>/` 아래에 저장한다.
- `scope`는 작업 범위, `nonce`는 충돌 방지용 짧은 식별자다.
- Playwright MCP나 Chrome devtools MCP가 생성하는 스크린샷의 위치도 이 파일 규칙을 준수해야 한다.

## 기록하거나 공유하는 글과 문구

- 저장소가 다르게 정하지 않았다면 커밋하거나 공유하는 파일명과 디렉터리명, README, 문서, 소스 코드와 주석, Git 커밋과 PR 문구, Issue 문구, 릴리스 안내, 사용자에게 보이거나 스크린리더가 읽는 문구를 작성자 외의 독자에게 전달되는 내용으로 다룬다.
- 저장소에 기록하거나 공유할 문구나 이름을 쓰기 전에 독자, 독자가 알아야 하거나 해야 할 일, 문구에 나온 행위 주체, 검수자와 승인 책임자를 확인한다. 역할을 구분해야 할 때에는 `사람`처럼 넓은 표현 대신 저장소 근거로 확인한 역할을 쓰거나 행동을 직접 설명한다. 역할을 확인할 근거가 없으면 임의로 정하지 않고 확인이 필요한 역할로 보고한다.
- 독자에게 전달할 각 문장은 확인된 저장소 근거, 승인된 결정 또는 사용을 승인받은 문구를 토대로 작성한다. 사용자 프롬프트, 에이전트 지침, 내부 작업 설명, 작업 메모, 검토 기준, 평가표, 출력 형식과 작업 과정 설명을 독자에게 전달할 문구의 출처로 사용하지 않는다.
- 내부 문구를 독자에게 전달할 내용에 인용하거나 그대로 옮기거나 일부 표현만 바꿔 쓰지 않는다. 해당 정보가 독자에게 필요하면 확인된 제품 동작, 사용 안내 또는 승인된 정책으로 새로 쓴다. 독자에게 제시할 수 있는 근거가 없으면 문구에서 빼고 작업 지시자에게 별도로 알린다.
- 내부 식별자, 비공개 문서 참조, 구현에서만 쓰는 이름, 관리자 메모, 미해결 결정, 검토 메모와 커밋하거나 공유하기 전 확인 목록을 독자에게 전달할 내용에 넣지 않는다. 해당 상태 자체가 독자에게 필요하고 승인 책임자가 문구를 승인한 경우가 아니면 `TODO`, `TBD`, `추후 결정` 같은 임시 문구를 넣지 않는다.
- 소유권, 지원 범위, 보안, 호환성, 개인정보 처리, 기여 조건 또는 라이선스가 결정되지 않았으면 추정해서 쓰지 않는다. 필요한 결정은 별도로 보고하고, 승인된 근거가 생긴 뒤 독자에게 전달할 내용을 수정한다.
- Git 커밋 메시지는 실제 변경사항과 변경 이유를 토대로 작성한다. 사용자에게 보이거나 스크린리더가 읽는 문구는 사용자가 하려는 일, 요소의 목적과 알아야 할 상태를 설명한다.
- 독자에게 전달할 내용의 수정과 저장소 관리 작업을 분리한다. 사용자가 명시적으로 허용하지 않으면 이슈, 계획 항목, 정책 파일 또는 커뮤니티 파일을 만들지 않는다.

### 커밋하거나 공유하기 전 검사

1. 변경한 파일명과 디렉터리명, 글과 문구, 커밋 메시지 초안을 모두 확인한다.
2. 추가한 각 문장과 문자열이 저장소 근거, 승인된 결정 또는 사용을 승인받은 문구에서 나온 것인지 확인한다.
3. 프롬프트, 내부 작업, 검토 기준, 출력 형식 또는 작업 과정에서 나온 문구는 제외한다.
4. 변경한 결과물에서 내부 식별자, 비공개 경로, 프롬프트의 특징적인 문구, HTML 주석과 `TODO`, `TBD`, `FIXME` 같은 미해결 표시를 검색한다.
5. 라이선스, 지원 범위, 보안, 호환성, 소유권과 제품 동작에 관한 문장을 승인된 근거와 대조한다.
6. 독자에게 전달될 최종 형태로 다시 읽고 행위 주체, 검수자와 승인 책임자가 저장소 근거로 확인되는 역할인지 점검한다. 프로젝트가 아니라 에이전트의 작업을 설명하는 내용이 남아 있으면 공유하거나 커밋하지 않는다.

## 의존성

- 의존성을 리서치할 때 의존성의 이름 뿐만 아니라 제공하는 기능, 버전, 잠재적 이슈까지 같이 리서치해야 한다.
- 의존성 리서치 또한 작업 설계 단계에서 진행되어야 한다.
- 외부 의존성과 내부 구현 중에서 장단점을 구체적으로 비교하고 더 근본적인 선택지를 선택한다.
- 외부 의존성을 도입한다면 의존성에 대해서 사용할 수 있는 정적 검사 도구, 베스트 패턴/아키텍처 + 디자인 패턴을 리서치하여 설계+하네스 문서에 반영해야 한다.

## 주석

- 프로젝트의 기술스택에 대해서 주석 컨벤션을 리서치하여 설계에 반영한다.
- 애플리케이션 코드의 함수, 메서드와 exported symbol 주석은 `/** ... */` JSDoc/TSDoc 문서 주석으로 작성하고, 구현 내부 사유는 `//` line comment로 분리한다.
- 문서 주석은 코드를 처음 보는 개발자도 호출 방법과 제약을 이해할 수 있도록 작성한다. 함수의 경우 요약 설명, `@param`, `@returns`를 기본으로 포함하고, 부수 효과, 서버 렌더링 코드와 클라이언트 코드의 구분, 보안 제약, 예외 전달 방식처럼 호출자가 알아야 하는 내용은 `@remarks` 또는 `@throws`로 보강한다.
- TypeScript 코드에서는 이미 타입 시그니처가 제공하는 타입 이름을 `@param {Type}`처럼 반복하지 않는다. 대신 값의 의미, 허용 범위, 기본값, 단위, 정규화 규칙, 반환값의 도메인 의미를 설명한다.
- 이름과 타입만으로 의미가 충분한 private/local helper에는 불필요한 문서 주석을 추가하지 않는다. 단, public API, shared utility, Route Handler/BFF helper, chart/URL/parser/threshold 정책 함수에는 문서 주석을 작성한다.
- "코드의 각 표현식마다 주석을 작성해라"라는 명시적인 요청이 있으면 **코드를 처음 보는 개발자도 이해할 수 있을 정도의 주석을 각 표현식,선언문마다 1-2줄로 작성한다.**

## Git 브랜치

- 작업을 시작하기 전에 현재 Git 브랜치를 확인한다.
- 여러 터미널을 사용할 수 있도록 워크트리 브랜치를 사용한다. 워크트리 브랜치 위치는 우리 레포 최상위에서 .worktrees 폴더 내 있어야 한다.
- 작업이 더 이상 진행되지 않는 워크트리 브랜치에 대해서는 제거가 가능한지 교차검증하고 제안한다.
- 사용자는 기존 워크트리 브랜치에서 계속 작업을 이어나가거나, 새로운 워크트리 브랜치 생성을 요구할 수 있다.
- 워크트리 브랜치가 양산되는 것을 방지하기 위해 설계 작업과 구현 작업 모두 동일한 브랜치에서 진행한다. 이 때 docs 브랜치보다는 작업 성격에 맞는 type을 선택한다.
- 현재 브랜치가 `main`, `master`, `develop`, `dev`, `release/*`이면 직접 수정하지 않고 새 작업 브랜치를 만든다.
- `.codex`, `.claude` 폴더 내 에이전트 환경 설정은 브랜치를 변경하지 않고 진행할 수 있다.
- 브랜치 이름은 `<type>/<short-description>` 형식을 사용한다.

허용되는 `<type>`:

- `feature`
- `fix`
- `hotfix`
  - 수정 작업이 아니라 핫픽스 작업일 때 사용
- `refactor`
- `test`
- `docs`
- `chore`

## Git 커밋

- 작업 단위가 커밋할 가치가 있는지 검토하고, 필요하면 커밋한다.
- 커밋 제목, 본문과 푸터에도 이 절의 규칙을 적용한다. 저장소에서 실제로 바뀐 내용과 변경 이유를 설명하고, 사용자 프롬프트, 에이전트 지침, 내부 작업 문구, 검토 기준, 비공개 자료 또는 에이전트의 작업 과정은 적지 않는다.
- 커밋 형식은 제목, 본문, 푸터로 구성한다.
- 제목 형식은 `<type>(<scope>): <subject>`를 사용한다.
- 제목의 `type`은 `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `perf`, `ci`, `build` 중 하나를 사용한다.
- 제목의 `scope`는 변경 대상 모듈이나 컴포넌트를 영어로 쓴다.
- 제목의 `subject`는 한국어 명사형 요약으로 작성하고 마침표를 찍지 않는다.
- 영어 커밋 제목은 Git 권장 관례에 따라 imperative mood를 사용할 수 있지만, 한국어 제목에는 `추가하라`, `수정하라` 같은 직접 명령형을 쓰지 않는다.
- 본문은 WHY 중심으로 한국어로 작성하고, 무엇을 했는지는 diff에 맡긴다.
- 필요 시 `BREAKING CHANGE:`, `Fixes #N`, `Closes #N`, `Co-Authored-By:` 푸터를 사용한다.

## 금지 사항

- 사용자 승인 없이 변경사항을 제거하거나, 덮어씌우는 것과 같은 "돌이킬 수 없는 명령"을 실행하지 않는다.
- 사용자가 만든 변경을 임의로 되돌리지 않는다.
