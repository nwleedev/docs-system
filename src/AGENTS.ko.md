# AGENTS.md

## 언어

- **모든 답변과 문서는 결론부터 작성한다.** 결론부터 작성하면 안 되는 경우에는 파일 형식이 주석을 허용할 때 한 줄로 이유를 설명한다.
- 코드와 파일명은 영어를 사용한다.
- Git 커밋은 아래의 Git 관련 지침을 따른다.
- 저장소가 다른 언어를 정하지 않았다면 설계 문서, 작업 설명과 코드 설명용 주석은 한국어로 작성한다.
- 사용자와 한국어로 소통한다.

## 기본 원칙

**답변**

- 일반 산문에서는 U+00B7을 사용하지 않는다. 인용문, 승인된 이름, 코드, 정규식, 문자 검사, 코드 포인트 설명 또는 평가 입력에 정확한 문자가 필요할 때만 보존한다. 예를 들어 `설계·구현·검증 결과를 기록합니다`는 `설계, 구현과 검증 결과를 기록합니다`로 고친다.
- `계약`, `경로`, `공개`, `좁히다`, `박다`, `제품`, `포화`, `경계`, `소유`, `작은`, `표면화`는 금칙어가 아니라 문맥을 확인할 신호다. 목록 밖의 표현도 같은 기준으로 살핀다. 해당 분야에서 뜻이 정확하면 유지하고, 그렇지 않으면 실제 규칙이나 행동을 적으며, 근거가 부족하면 사용자에게 묻는다.

**컨텍스트 압축**

- 컨텍스트가 압축되면 AGENTS.md, 특히 **기본 원칙**을 다시 읽고 작업에 적용한다.
- Git 커밋을 적절하게 관리해 컨텍스트 압축에 대비한다. 컨텍스트가 압축되면 먼저 Git 기록을 확인한다.

**금지 사항**

- 코드 구현을 명시적으로 요청하지 않았다면 코드를 구현하지 않는다.
- 테스트 코드 작성을 명시적으로 요청하지 않았다면 테스트 코드를 작성하지 않는다.
- TDD를 명시적으로 요청하지 않았다면 TDD를 수행하지 않는다.
- 작업 범위를 임의로 바꾸지 않는다.
- 이모지를 사용하지 않는다.
- 사용자 승인 없이 변경사항을 제거하거나 덮어쓰는 등 되돌리기 어려운 명령을 실행하지 않는다.
- 가급적 주석을 사용하지 않는다. 코드만으로 각 부분의 역할을 이해할 수 있게 작성한다.
- 코드를 작성한 뒤 유사한 코드가 있는지 확인하고 공통화할 책임과 검증이 실제로 같은지 검토한다.
- 오류를 해결하기 위해 타입 검사를 비활성화하지 않는다.
- 설계에 명시된 요구사항이나 기능을 임의로 비활성화하지 않는다.
- 테스트 실패를 숨기기 위해 테스트를 삭제하거나 약화하지 않는다.
- 다른 프로젝트에 그대로 붙여 넣을 수 있는 상투적인 글을 쓰지 않는다. 현재 독자, 저장소와 결정 사항을 구체적으로 반영한다.
- 뜻을 보태지 않는 상투적 표현과 과장된 수식어를 쓰지 않는다.
- 소제목마다 같은 길이의 문단을 만들거나, 근거 없이 세 항목으로 나누거나, 같은 연결 표현을 되풀이하지 않는다. 내용에 맞춰 글의 짜임을 정한다.
- 영어를 낱말 단위로 옮기지 않는다. 원문이 가리키는 대상, 행동, 조건과 책임 주체를 확인한 뒤 자연스러운 한국어 문장을 새로 쓴다.
- 영어 기술 용어를 정해진 한국어 한 단어로 자동 변환하지 않는다. 해당 분야에서 뜻이 정확한 용어는 유지하고, 그렇지 않으면 실제 행동이나 조건을 드러낸다.

**기존 기능과 코드 작성**

- 사용자가 기능 변경이나 제거를 요청하지 않았다면 기존 기능을 없애거나 약화하지 않는다. 사용자에게 보이는 결과, 외부에서 사용하는 API, 저장되는 데이터, 오류 처리, 현재 테스트와 실행 결과를 확인해 유지할 기능을 정한다.
- 기존 코드는 현재 기능을 파악하는 자료로만 사용한다. 같은 작성 방식이 여러 파일에 있거나 수정할 코드와 가깝다는 이유만으로 새 코드에 가져오지 않는다.
- 새 코드를 작성하기 전에 현재 기술과 버전의 공식 문서, 이 저장소에 적용할 개발 지침, 설정과 검사 결과를 확인한다. 확인한 근거에 따라 현재 작업에 알맞은 작성 방식을 고르고, 기존 코드에서 발견한 안티패턴을 되풀이하지 않는다.
- 새 코드는 확인한 작성 방식으로 구현하면서 기존 기능, 외부에서 사용하는 API, 데이터 형식과 필요한 호환성을 유지한다. 기존 코드와 연결할 때 변환이 필요하면 연결 부분에서 처리하고, 이전 작성 방식을 새 코드 전체에 퍼뜨리지 않는다.
- 확인한 작성 방식을 적용하려면 기존 기능을 바꾸거나 저장소 전체 구조를 고쳐야 하는 경우 임의로 진행하지 않는다. 유지할 기능과 예상되는 영향을 사용자에게 설명하고 승인을 받는다.
- 테스트는 새 코드가 이전 구현과 같은 모양인지가 아니라 사용자가 확인할 수 있는 동작과 승인된 호환 조건이 유지되는지 검사한다.

**리서치**

- 모든 프롬프트는 다양한 방법으로 인터넷 자료를 조사하고 교차 검증해 정확성과 최신성을 확보한다.
- 블로그와 큐레이션 글보다 공식 문서, 표준 문서, 원문, 실제 소스 코드와 같은 1차 자료를 최소 다섯 개 찾으려고 시도한다.
- 현재 시점의 최신 정보를 먼저 확인하고 모든 답변에 신뢰도 높은 출처를 제시한다.
- 시각 분야의 조사와 교차 검증에는 MCP를 사용한다.
- GitHub 저장소 파일과 이슈를 조사할 때에는 `gh` CLI를 사용한다.
- 소스 코드는 개인 저장소보다 공식 저장소를 우선한다.
- 사용자가 조사 결과의 진위를 확인할 수 있도록 출처와 허용 범위 안의 짧은 인용을 남긴다.
- 리서치 규칙은 에이전트의 조사 과정과 사용자에게 전달하는 답변에 적용한다. 사용자가 대상 파일에 출처를 요구했고 그 파일의 독자에게 필요한 경우가 아니면 조사 출처, 조사 메모, 권고 사항이나 원문 표현을 대상 파일에 옮기지 않는다.
- 저장소에 라이선스, 정책, 검사 수단, 문서 또는 결정 사항이 없다는 사실을 발견해도 이를 추가할 권한이 생기지는 않는다. 대상 문서에 임시 문구, 경고 또는 관리자용 작업을 넣지 말고 발견한 문제를 사용자에게 별도로 알린다. 요청한 결과가 달라진다면 승인받기 전까지 수정하지 않는다.

## 서브에이전트 사용

- 단순한 작업, 하나의 문맥에서 끝나는 작업, 작업 분할 비용이 예상 절감 시간보다 큰 작업에는 서브에이전트를 사용하지 않는다.
- 작업을 둘 이상의 독립적인 단위로 나눌 수 있고 예상 절감 시간이 작업 분배와 결과 종합 비용보다 크면, 메인 에이전트는 해당 작업을 서브에이전트에 분배한다.
- 각 서브에이전트에는 적용할 요구사항 기준, 정확한 작업, 확인할 경로, 파일 변경 허용 범위, 중단 조건과 반환할 결과를 전달한다.
- 사용자가 특정 Skill을 지정했거나 현재 실행 중인 Skill이 서브에이전트 사용 방법을 정의하면 해당 Skill의 절차를 따른다. 같은 역할을 중복 호출하거나 Skill 바깥에서 별도 검토 단계를 추가하지 않는다.
- 메인 에이전트는 요구사항 기준, 작업 분배, 의존 관계, 결과 종합, 충돌 해결, 중단 판단과 최종 검증을 담당한다.
- 서브에이전트의 작업 보고를 완료 증거로 간주하지 않는다. 메인 에이전트가 실제 파일, 변경사항과 검사 결과를 확인한다.

### 병렬 실행

- 서로 다른 질문을 조사하는 리서치, 서로 다른 관점의 읽기 전용 검토, 독립적인 로그 및 테스트 결과 분석은 병렬로 실행할 수 있다.
- 구현 작업은 수정 파일뿐 아니라 공용 인터페이스, 스키마, 생성 파일, 잠금 파일, 설정, 개발 서버, 데이터베이스와 테스트 데이터가 겹치지 않을 때만 병렬로 실행한다.
- 작업 결과가 다른 작업의 입력이 되거나 영향 범위를 확신할 수 없으면 병렬로 실행하지 않는다.
- 실행 환경의 동시 실행 한도를 넘기지 않고 남은 작업은 대기시켰다가 자리가 생기면 실행한다.

### 순차 실행

- 요구사항의 동작을 바꿀 질문을 해결한 뒤 계획을 확정하고, 검토된 계획을 기준으로 구현을 시작한다.
- 같은 파일이나 공용 상태를 변경하는 작업과 앞 작업의 결과에 의존하는 작업은 순차적으로 실행한다.
- 검토 결과에 따른 수정과 재검토는 기존 검토가 끝난 뒤 순차적으로 실행한다.
- 독립된 작업 단위의 구현이 완료되어 안정된 변경사항이나 커밋이 생겼다면, 다음 독립 작업의 구현과 해당 단위의 읽기 전용 검토를 겹쳐 실행할 수 있다.

### 요구사항 변경

- 요구사항이 변경되면 새로운 작업 분배를 잠시 멈추고 진행 중인 작업에 미치는 영향을 확인한다.
- 영향을 받지 않는 작업만 계속하고, 영향을 받은 작업은 중단하거나 변경된 요구사항을 기준으로 다시 검증한다.
- 영향 여부를 확신할 수 없거나 공통 전제와 성공 조건이 바뀌면 전체 관련 작업을 멈추고 요구사항 작성자에게 확인한다.

### 글과 문구

- 저장, 커밋, 게시하거나 대화 밖에서 공유할 한국어 글과 이름을 작성하거나 고칠 때에는 `$use-words-review`가 요구하는 작성 전 참고 자료를 읽는다.
- 모든 언어의 글과 이름은 같은 공유 단위로 묶어 저장하거나 공유하기 직전에 `$use-words-review`로 한 번 검토한다.
- 사용자가 특정 문구나 공개 결과물의 검토를 요청하면 파일 변경이 없어도 지정한 문구 전체를 한 단위로 검토한다.
- 일반 채팅과 진행 알림만을 이유로 `$use-words-review`를 실행하지 않는다.
- 독자에게 제공할 각 문장은 확인된 저장소 근거, 승인된 결정 또는 사용을 승인받은 문구를 토대로 작성한다. 사용자 프롬프트, 에이전트 지침, 내부 작업 설명, 작업 메모, 검토 기준, 평가표, 출력 형식과 작업 과정 설명을 독자에게 전달할 문구의 출처로 사용하지 않는다.
- 내부 식별자, 비공개 문서 참조, 구현에서만 쓰는 이름, 관리자 메모, 미해결 결정, 검토 메모와 커밋하거나 공유하기 전 확인 목록을 독자에게 전달할 내용에 넣지 않는다. 해당 상태 자체가 독자에게 필요하고 승인 책임자가 문구를 승인한 경우가 아니면 `TODO`, `TBD`, `추후 결정` 같은 임시 문구를 넣지 않는다.

### 리서치, 교차 검증, 설계와 문서화

- 요구사항을 구체화하거나 `docs/designs/**`를 조사, 작성, 검토, 계획 또는 검증할 때에는 `$use-design-docs`를 실행한다.
- 요구사항과 승인된 결정은 AI의 조사 결과나 제안과 구분한다.
- 설계 문서의 구조, 기록 위치와 검사 기준은 저장소의 `docs/designs/README.md`가 관리한다.

### 개발 지침, 기술 스택과 검사 설정

- 애플리케이션 변경을 계획, 구현, 검토, 리팩터링, 테스트 또는 문서화하거나 의존성과 검사 설정을 변경할 때에는 `$use-dev-guidance`를 실행한다.
- 개발 방법, 기술 스택별 규칙, 실행 명령과 검증 방법은 저장소의 `docs/dev/README.md`와 그 문서가 선택한 주제별 지침을 따른다.
- 외부 의존성을 선택, 추가, 교체, 제거하거나 버전을 변경하기 전에 공식 권장 통합 구조와 적용 가능한 디자인 패턴을 조사한다.
- 직접 의존성과 전이 의존성을 포함한 모든 외부 의존성을 조사하고, 의존성마다 이름, 버전, 기능, 잠재적 문제와 적용할 디자인 패턴을 확인한다.
- 외부 의존성과 이미 설치된 의존성, 플랫폼 기능 및 내부 구현을 비교한다.
- 의존성 조사 결과를 적용하려면 사용자의 변경 요청과 저장소의 승인 절차를 별도로 확인한다.

## 환경변수 및 민감정보

- 개인 민감정보, 보안 키, 내부 URL, 토큰과 자격 증명은 Git에 커밋하지 않는다. 개인 PC 계정이 포함될 수 있는 절대 경로도 Git에 커밋하지 않는다.
- Git에 커밋하면 안 되는 데이터는 `.env` 같은 환경변수 파일로 관리한다.
- 테스트 코드도 민감한 목업 값을 직접 하드코딩하지 않고 테스트 전용 환경변수나 테스트 코드 안의 fixture 작성 방식을 사용한다.
- 커밋하기 전에 환경변수 파일, 인증정보, 토큰, 개인정보, 내부 URL, 비공개 저장소 참조와 개인 계정이 드러나는 절대 경로가 포함되지 않았는지 확인한다.

## 임시 파일

- PC 루트 위치의 `/tmp` 같은 폴더를 사용하지 않는다.
- 임시 파일은 프로젝트 최상위 `temps/<scope>-<nonce>/` 아래에 저장한다.
- `scope`는 작업 범위, `nonce`는 충돌 방지용 짧은 식별자다.
- MCP가 생성하는 스크린샷도 이 파일 규칙에 맞는 위치에 저장한다.

## Gitignore

- `.gitignore`에 등록된 파일을 커밋하지 않는다.
- 커밋 전에 민감정보나 자격 증명이 포함되지 않았는지 확인한다.
- AGENTS.md의 "환경변수 및 민감정보" 절에 적용할 규칙이 있는지 다시 확인한다.

## Git 브랜치

- 작업을 시작하기 전에 현재 Git 브랜치를 확인한다.
- 여러 터미널을 사용할 수 있도록 worktree 브랜치를 사용한다. 수동으로 만든 worktree는 저장소 최상위의 `.worktrees/` 아래에 둔다.
- 더 이상 진행하지 않는 worktree 브랜치를 제거해도 되는지 교차 검증하고 제안한다.
- 사용자는 기존 worktree 브랜치에서 작업을 이어가거나 새 worktree 브랜치 생성을 요구할 수 있다.
- worktree 브랜치가 불필요하게 늘어나지 않도록 설계와 구현 작업은 같은 브랜치에서 진행한다. `docs`를 기본값으로 사용하지 말고 작업 성격에 맞는 type을 선택한다.
- 현재 브랜치가 `main`, `master`, `develop`, `dev`, `release/*`이면 직접 수정하지 않고 새 작업 브랜치를 만든다.
- `.codex`, `.claude` 폴더 안의 에이전트 환경 설정은 브랜치를 변경하지 않고 진행할 수 있다.
- 브랜치 이름은 `<type>/<short-description>` 형식을 사용한다. worktree 폴더 이름도 브랜치 이름을 반영해 `.worktrees/<type>/<short-description>`로 정한다.

허용되는 `<type>`: `feature`, `fix`, `hotfix`(실제 핫픽스 작업에만 사용), `refactor`, `test`, `docs`, `chore`

## Git 커밋

- 작업 단위가 커밋할 가치가 있는지 검토하고 필요하면 커밋한다.
- 커밋 제목, 본문과 footer에도 이 절의 규칙을 적용한다. 저장소에서 실제로 바뀐 내용과 변경 이유를 설명하고, 사용자 프롬프트, 에이전트 지침, 내부 작업 문구, 검토 기준, 비공개 자료 또는 에이전트의 작업 과정은 적지 않는다.
- 커밋 형식은 제목, 본문과 footer로 구성한다.
- 제목 형식은 `<type>(<scope>): <subject>`를 사용한다.
- 제목의 `type`은 `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `perf`, `ci`, `build` 중 하나를 사용한다.
- 제목의 `scope`는 변경 대상 모듈이나 컴포넌트를 영어로 쓴다.
- 제목의 `subject`는 영어 명령형으로 작성하고 마침표를 찍지 않는다. `subject`는 영어 소문자로 시작한다.
- 본문은 변경 이유를 영어로 먼저 작성한 뒤 같은 내용을 한국어 명사형으로 작성한다. 무엇을 바꿨는지는 diff에서 확인할 수 있게 둔다.
- 필요하면 `BREAKING CHANGE:`, `Fixes #N`, `Closes #N` footer를 사용한다.
