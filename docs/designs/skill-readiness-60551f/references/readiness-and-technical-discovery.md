# 스킬의 첫 응답에서 요구사항과 구현 준비 상태를 판단하는 방법

두 스킬의 개선에는 조사 분야를 더 나열하기보다 첫 응답에서 무엇을 판단하고 어떤 근거를 제시할지 정하는 방식이 적합하다. 현재 목표를 만족하는 데 필요한 정보와 향후 기능을 구분하고, 착수 판단을 수정할 파일, 작성 방식과 확인 방법까지 연결하는 방안을 제안한다.

이 자료는 [개선 요구사항](../requirements.md)에 대한 조사다. 스킬을 고칠 사람이 적용 방법을 선택하도록 작성했다. 외부 사례의 동작 설명, 저장소에서 확인한 사실과 아래 개선 제안은 서로 구분한다. 자료 확인일은 2026-11-01이다. 외부 도구를 설치하거나 실제 에이전트의 변경 전후 답변을 비교한 결과는 아니다.

## 현재 지침에서 확인한 점

### 이름 변경과 호출 변경은 구분해야 한다

설계 스킬의 폴더와 frontmatter는 이미 `use-flexible-design`다. 표시 제목과 UI 이름도 여기에 맞춰 단수형 `Use Flexible Design`으로 통일한다. 과거 설계 폴더 이름이나 조사 당시의 이전 이름은 실행할 스킬 이름과 목적이 다르므로 일괄 치환할 대상이 아니다.

두 언어의 `src/AGENTS.*.md`에서 설계 호출은 현재 이름을 사용한다. 개발 변경을 `use-dev-guidance`로 안내하던 항목은 `use-flexible-coding`으로 맞춘다.

기존 스킬 파일까지 삭제할 이유는 없다. [기존 코딩 스킬 요구사항](../../task-pattern-guidance-4ffad1/requirements.md#스킬-이름과-변경-권한)은 두 스킬의 병존을 정했다. 호출 안내를 교체하는 것과 과거 요구사항 및 구현 기록을 다시 쓰는 것은 다르다.

### 조사 의무가 없어서 생긴 문제로 단정할 수 없다

[설계 스킬](../../../../skills/use-flexible-design/SKILL.md#select-the-work)은 조사 질문과 선택의 구분, 요구사항 검토와 계획을 지시한다. [설계 요구사항](../../flexible-designs-4f8c/requirements.md#내용-작성과-구조-정리)에는 착수와 개발에 부족한 조건의 조사 및 제안도 있다. 다만 첫 응답에 착수 판단과 누락 분석을 반드시 포함하게 하는 지시는 분명하지 않다. 요청을 문서 작성으로만 분류하면 조사 자체가 선택되지 않을 여지가 있다.

[코딩 스킬](../../../../skills/use-flexible-coding/SKILL.md#research-each-task)은 실패 가능성에서 질문을 도출하고, 원리와 대안, 실제 파일과 타입, 변경할 코드를 설명하도록 이미 지시한다. [기존 조사](../../task-pattern-guidance-4ffad1/references/cs-research-workflow.md)도 같은 문제를 조사했다. 따라서 같은 조사 목록을 더 추가하는 것만으로 개선된다고 볼 근거가 없다. 첫 응답에 필요한 설명을 정하고 그 설명이 빠졌을 때 발견할 방법을 마련하는 일이 우선이라는 분석이다.

이 자료에는 실패한 전체 대화, 실행 모델과 도구 사용 기록이 없다. 실제 실행에서 두 스킬을 읽지 않았는지, 상위 지침과 충돌했는지, 읽고도 응답에 반영하지 않았는지는 판별할 수 없다. 본문의 원인 설명은 지침을 읽고 찾은 가능성이며 관측된 모델 내부 원인이 아니다.

## 추가 프롬프트 없이 필요한 내용을 찾는 사례

### Cucumber: 규칙과 예시로 질문을 발견하고 새 기능은 분리한다

[Cucumber Example Mapping](https://cucumber.io/docs/bdd/example-mapping/)은 하나의 사용자 이야기에서 규칙, 구체적인 예시, 답하지 못한 질문을 나누고 새로 발견한 이야기는 범위 밖으로 미루는 방식을 설명한다. 원문은 “sliced and deferred out of scope”다. 필요한 설명을 찾는 일과 기능을 추가하는 일을 구분하는 직접적인 사례다. 해당 페이지의 표시 갱신일은 2026-10-27이다.

이를 설계 스킬에 적용하면 목표를 만족하는 대표 상황과 실제로 가능한 실패 상황을 먼저 대입하고, 그 결과가 기존 요구사항으로 결정되는지 살필 수 있다. 결정되지 않는 부분을 질문으로 제시하되 요구사항 본문에 답을 추정해 넣지 않는다. 모든 상태에 새 화면이나 새 기능이 필요하다고 가정하지 않는다. 예시를 이용하는 절차만 참고하며 Cucumber 설치, Gherkin 작성과 테스트 코드 생성을 함께 요구하지 않는다.

### GitHub Spec Kit: 영향 있는 질문을 우선하고 실제 파일 구성을 선택한다

[Spec Kit의 clarify 지침](https://github.com/github/spec-kit/blob/7370e592f3cd9c06e5b698983957e227c75b30e2/templates/commands/clarify.md)은 누락을 조사한 뒤 구현과 확인 방법에 영향을 주지 않는 질문을 제외하고, 재작업 위험이 큰 질문을 우선한다. [계획 지침](https://github.com/github/spec-kit/blob/7370e592f3cd9c06e5b698983957e227c75b30e2/templates/commands/plan.md)은 기술적 미확인 사항, 의존성과 연동을 조사 과제로 만든다.

[계획 템플릿](https://github.com/github/spec-kit/blob/7370e592f3cd9c06e5b698983957e227c75b30e2/templates/plan-template.md)은 일반적인 폴더 선택지를 그대로 제출하지 않고 실제 디렉터리를 반영한 구성을 선택하게 한다. 원문은 “Replace the placeholder tree”다. 세 파일은 위 링크의 동일 revision을 `gh`로 확인했다.

적용할 점은 기술로 확인할 사실은 먼저 조사하고 사람의 판단이 필요한 질문만 남기는 순서, 실제 파일을 명시하는 작성 방식이다. 질문 수 상한, 별도 명령 실행, 여러 문서의 자동 생성과 조사 담당 에이전트 호출은 이 저장소에 그대로 적용하지 않는다. 외부 지침의 존재만으로 그 도구가 실제 사용에서 추가 질문을 줄였다고 주장할 수는 없다.

## 지금 필요하지 않은 기능을 요구사항으로 만들지 않는 방법

현재 목표를 달성할 수 없게 만드는 누락인지 먼저 설명하고, 설명할 수 없는 추가 기능은 이번 필수 작업으로 올리지 않는 방안을 제안한다. 현재 범위에 필요한 조건도 답을 새로 만들어 확정하지 않고 조사 결과나 결정할 질문으로 남긴다.

[Martin Fowler의 Yagni](https://martinfowler.com/bliki/Yagni.html)는 미래에 필요할 것으로 예상하는 기능을 미리 구현하면 개발 비용뿐 아니라 지연과 복잡성 유지 비용이 생긴다고 설명한다. 원문은 “should not be built now”다. 원 글은 2015-05-26 작성됐으며, 최신 기능의 성능 자료가 아니라 미래 기능을 판단하는 원칙으로 사용한다. 글은 변경을 쉽게 하는 코드 개선까지 금지하는 원칙으로 설명하지 않는다.

아래는 출처를 이 저장소에 적용한 분류 제안이다.

- **현재 결과에 필수인 조건:** 없으면 이미 정한 동작이나 보존할 데이터가 달라진다. 어떤 동작을 결정하지 못하는지 적고, 사실 조사와 사람의 선택을 구분한다.
- **현재 구현에 필요한 기술 선택:** 파일 배치, 처리 순서와 오류 전달 방식처럼 구현을 위해 정할 내용이다. 기술 근거로 추천할 수 있지만 새로운 사용자 기능으로 요구사항에 추가하지 않는다.
- **현재 작업과 연결된 위험:** 발생 조건과 영향이 있는 우려다. 예방이나 확인 방법을 제안하며 모든 위험을 별도 기능 개발로 바꾸지 않는다.
- **향후 기능:** 현재 동작이 성립하는 데 필요하지 않다. 현재 요구사항과 실행 계획에서 제외하고, 기록할 가치가 있을 때에만 다시 검토할 조건을 조사 자료에 남긴다.

예를 들어 이 저장소의 빈 요구사항 생성에는 새 폴더와 빈 파일의 생성, 기존 파일 보존이 필요하다. 편집 이력 서버나 다중 사용자 승인 화면은 그 동작에 필수라는 근거가 없다. 반면 생성에 실패하면 무엇이 남는지는 현재 파일 보존 조건과 직접 관련되므로 조사할 가치가 있다. 이 예는 범위 판단을 설명하며 새 기능 추가 제안이 아니다.

## 구현 착수 여부와 위험을 함께 설명하는 방법

착수 여부는 문서가 있는지보다 현재 요구사항을 구현할 선택과 확인 방법이 마련됐는지로 판단하는 방안을 제안한다. 기술적으로 시작할 수 있다는 판단과 실제 구현 권한도 따로 밝혀야 한다.

[NASA 요구사항 작성 지침](https://www.nasa.gov/reference/appendix-c-how-to-write-a-good-requirement/)은 필요한 결과와 구현 방법의 구분, 명료성, 일관성, 기술적 실현 가능성과 확인 가능성을 살핀다. 원문은 “Are the requirements technically feasible?”다. 요구사항 확인 항목은 참고하되 NASA의 전체 문서 절차, 식별자와 미완성 항목 형식을 도입하는 근거로 사용하지 않는다.

[OpenSpec 기본 schema](https://github.com/Fission-AI/OpenSpec/blob/27c0515724decc633818c735ee596481eec78a8b/schemas/spec-driven/schema.yaml)의 design과 tasks 지침은 구현 내용이나 접근 방식 및 작업 분해를 바꿀 질문을 먼저 해결하고, 작업마다 완료 확인 방법을 연결한다. 원문은 “resolve them with the user first”다. `gh`로 확인한 위 revision에서는 미뤄도 되는 질문과 지금 답해야 하는 질문을 구분한다. 자체 문서 구조와 작업 파싱 형식은 가져오지 않는다.

이 두 자료를 비교하면 미확인 사항이 하나라도 있다는 이유로 전체 착수를 막을 필요도, 문서가 완성됐다는 이유로 착수 가능하다고 할 근거도 없다. 다음과 같이 작업 단위별로 설명할 수 있다.

- **착수 가능:** 목표와 완료 증거가 정해졌고, 구현 방식과 필요한 기술의 근거가 있으며, 해당 작업을 바꿀 미해결 질문이 없다. 남은 위험과 검사하지 않은 조건을 함께 적는다.
- **일부 착수 가능:** 특정 질문에 의존하지 않는 작업이 실제로 있다. 시작할 파일과 작업, 멈출 작업과 그 이유를 구분한다.
- **착수 보류:** 미해결 질문의 답에 따라 동작, 데이터나 구현 방식이 달라진다. 필요한 답, 추천안과 근거, 답을 얻었을 때 다시 판단할 내용을 적는다.

이는 준비 상태를 설명하는 제안이며 저장소가 쓰는 `pass`, `needs revision`, `needs human input`, `not applicable` 검토 상태를 대체하지 않는다. 구현 권한이 없으면 준비 상태가 충분해도 조사와 제안까지만 수행한다. 이 자료의 사례를 실제로 실행하기 전에는 결과를 확인한 것으로 적지 않는다.

[arc42 위험 설명](https://docs.arc42.org/section-11/)은 확인한 기술 위험을 우선순위로 정리하고 줄이거나 피할 방법을 연결하도록 안내한다. 이를 적용한 위험 설명에는 발생 조건, 영향을 받는 동작과 파일, 확인된 근거 또는 가정, 대응 방법, 확인 방법과 착수에 미치는 영향을 담는 방안을 제안한다. 확률 수치나 위험 없음이라는 결론을 근거 없이 만들지 않는다. 가능성은 있으나 관련 사용 조건이 확인되지 않았다면 그 조건부터 조사한다.

## 기술 이슈에서 실제 파일과 작성 방법까지 조사하는 방법

현재 스킬의 조사 의무는 유지하되, 하나의 이슈에서 입력을 받은 뒤 처리하고 반환하거나 저장하는 순서를 따라가며 설명을 구체화하는 방안을 제안한다. 원리 이름을 나열한 답변은 수정할 코드에 대한 판단으로 충분하지 않다.

[arc42 Building Block View](https://docs.arc42.org/section-5/)는 구성요소의 역할과 연결, 코드 위치를 설명하고, 중요하거나 위험한 부분을 선택해 상세화하도록 한다. 원문은 “prefer relevance over completeness”다. 전체 디렉터리를 문서화하거나 특정 아키텍처를 일괄 도입하는 지침이 아니다.

이 방식을 코딩 스킬에 적용할 때에는 현재 이슈의 구현 판단에 필요한 설명을 다음 항목에서 선택해 연결한다. 모든 작업에서 각 항목을 별도 제목으로 채울 필요는 없다.

- 실제 입력이 들어오는 파일과 함수, 처리 순서, 값이 저장되거나 반환되는 지점 및 그 함수를 호출하는 코드
- 유지할 동작, 데이터 형식과 오류 처리의 근거, 현재 구현에서 바꿀 수 있는 부분
- 적용할 컴퓨터 공학 원리, 그 원리가 필요한 실패 조건과 비용, 원리가 성립하는 가정
- 변경할 기존 파일과 신설할 파일, 함수 또는 타입의 역할, 의존 방향과 파일을 나누거나 유지할 이유
- 처리 순서와 코드 작성 예시, 사용하는 기술 버전 및 기존 타입과 연결되는 방법
- 부분 수정과 처리 방식 변경의 실질적인 대안, 선택 이유와 제외 근거, 미확인 사항
- 관찰할 성공 및 실패 결과, 사용할 기존 검사와 실행하지 못한 확인

자료구조, 정규화, 캐시와 동시성 같은 분야명은 조사 시작을 돕는 단서다. 실제 저장 방식, 호출 횟수, 같은 값을 바꾸는 작업이나 외부 입력에서 문제가 생기는 조건을 찾아 관련 원리를 선택한다. 현재 저장소에 없는 데이터베이스나 서비스 계층을 예시 편의를 위해 추가하지 않는다. 새 코드 예시는 기술 근거를 설명할 필요가 있을 때 문서 안에서 제시하며 실제 소스 수정과 실행 확인으로 간주하지 않는다.

### 저장소 사례: 빈 요구사항 생성기의 기존 파일 보존

이 사례에서는 새 모듈을 추가하기보다 이미 선택한 배타적 파일 생성 방식과 실패 후 상태를 설명하는 것으로 판단을 구체화할 수 있다. [생성 스크립트](../../../../skills/use-flexible-design/scripts/requirements/create.mjs)의 `main`은 인수 해석, 저장 위치 확인, 이름 결정과 생성을 연결한다. `createEmptyRequirements`는 먼저 `mkdir`을 호출하고 다음과 같이 파일을 연다.

```mjs
const file = await open(paths.file, "wx");
await file.close();
```

위 두 줄은 현재 소스의 발췌이며 새 구현안이 아니다. 배포 기준은 Node.js 22.0.0 이상이다. [Node.js 22.x 파일 시스템 설명](https://nodejs.org/docs/latest-v22.x/api/fs.html#file-system-flags)은 `x`가 대상이 이미 있을 때 실패하도록 하는 플래그임을 설명하며 네트워크 파일 시스템에서는 동작이 제한될 수 있다고 밝힌다. 같은 문서의 [access 설명](https://nodejs.org/docs/latest-v22.x/api/fs.html#fspromisesaccesspath-mode)은 존재를 미리 확인한 뒤 여는 방식에 경쟁 상태가 생기는 이유를 설명한다. 확인한 문서 표시는 v22.23.4다.

여기서 필요한 지식은 파일의 존재 확인과 생성 사이에 다른 프로세스가 개입할 수 있다는 동시성 원리다. `access` 후 일반 쓰기 방식으로 바꾸는 제안보다 생성 연산에서 충돌을 처리하는 현재 방식을 유지할 근거가 있다. 이는 마지막 파일의 덮어쓰기 방지에 관한 판단이며 상위 디렉터리의 악의적인 동시 교체까지 막는 보장은 아니다.

파일과 폴더 구성도 실제 역할로 설명할 수 있다. CLI의 인수 해석과 물리적 생성은 기존 `scripts/requirements/create.mjs`에, 작성 의도와 대상 문서 선택은 [requirements workflow](../../../../skills/use-flexible-design/references/requirements/workflow.md)에 둔다. 현재 이 사례만으로 별도 파일 시스템 서비스나 공용 저장 모듈이 필요한 이유는 없다. 재사용할 독립적인 책임이 확인되기 전에는 파일 분할을 제안할 근거가 부족하다.

보존할 결과는 충돌한 기존 파일을 바꾸지 않는 것과 실패를 성공으로 보고하지 않는 것이다. 코드에서 확인한 사실은 생성 실패 시 `InputError`로 처리하고 종료 상태의 기본값을 `2`로 두며 새 폴더가 남을 수 있음을 알린다는 점이다. 실행으로 확인할 항목은 충돌 시 기존 내용 보존, 반환 상태와 실패 후 남은 파일이다. 이 자료에서는 해당 상황을 실행하지 않았다. 실제 지원 환경에 네트워크 파일 시스템이 포함되는지, 위협 모델에 악의적인 동시 교체가 포함되는지는 추가 근거 없이는 확정할 수 없다.

이 정도 설명이면 파일 보존에 관련된 원리, 실제 함수와 API, 유지할 작성 방식, 별도 파일을 만들지 않는 이유와 남은 위험을 알 수 있다. 관련 없는 캐시, 정규화나 분산 잠금의 조사로 확대할 이유는 없다.

## 두 스킬에 적용할 구성 제안

두 스킬의 첫 응답에 현재 작업 대상, 부족한 정보와 착수 판단을 포함하고, 구현 방법의 구체화는 코딩 스킬에서 담당하는 방안을 우선한다. 스킬을 여러 개 더 만들거나 별도 관리 서버를 추가할 근거는 확인하지 못했다.

설계 스킬의 `Select the work`에서는 준비만 하는 요청과 내용 판단이 필요한 요청을 구분할 수 있다. 후자에서는 목표, 현재 범위에서 성립해야 할 상황, 부족한 사실과 결정, 착수 판단을 먼저 제공하게 하는 보완을 제안한다. 요구사항은 승인된 내용을 유지하고 새 기술안과 기능 제안은 조사 자료 또는 대화에서 분리한다. 빈 파일 준비 요청에는 전체 구현 분석을 강제하지 않는다.

코딩 스킬의 `Research each task`와 `Explain changes and examples`에는 앞 절의 처리 순서 조사 방식과 응답에 필요한 설명을 연결하는 보완을 제안한다. 분리된 장문 체크리스트를 새로 읽게 하기보다 기존 의무를 실제 파일, 처리 방식, 선택 이유와 확인 방법으로 이어지게 한다. 파일이 지정되지 않았을 때에는 기록 후보를 제안하는 기존 조건을 지키면서 대화에서 기술 설명을 제공할 수 있다. 파일 지정 대기를 조사 중단 조건으로 만들 필요는 없다.

`use-dev-guidance`의 호출 교체만으로 그 스킬의 모든 기능이 코딩 스킬에 이관되지는 않는다. 기존 코딩 스킬에는 기준 README의 승인 후 생성 절차나 의존성 전체 조사와 검사 선택 절차가 동일하게 들어 있지 않다. 현재 `AGENTS.*.md`는 `docs/dev/README.md`와 해당 지침을 직접 따르게 하므로 그 의무를 유지할 수 있다. 개발 README가 없는 경우에는 코딩 스킬에 없는 생성 절차가 있다고 안내하지 않고 기록 후보 제안과 기존 지침 확인으로 설명해야 한다. 이후 통합을 추진할 때에도 옛 스킬 전체 복사 대신 필요한 동작과 빠질 수 있는 의무를 비교해야 한다.

이번 조사만으로 후속 스킬 동작을 확정하거나 실행 계획을 완료한 것으로 보지 않는다. 위 보완안은 현재 동작을 개선할 후보이며, 채택하면 기존 두 설계 묶음의 요구사항 및 계획에 영향을 반영한 뒤 실제 스킬 수정 범위를 정할 수 있다.

## 효과를 확인할 방법과 남은 한계

스킬 문장의 존재나 형식 검사로 효용을 입증할 수 없다. 동일한 요청과 저장소 자료로 기존 스킬과 보완한 스킬을 실행해 첫 응답이 달라지는지 비교하는 방안을 제안한다.

[Agent Skills의 품질 평가 안내](https://agentskills.io/skill-creation/evaluating-skills)는 실제적인 요청과 입력을 마련하고 기존 버전 또는 스킬이 없는 실행을 기준으로 비교하도록 한다. 원문은 “once with the skill and once without it”이다. 각각 새 문맥에서 실행하며 결과 품질과 소요 시간 및 토큰을 함께 비교한다. 평가용 파일 형식과 추가 도구는 이 조사에서 도입하지 않는다.

비교할 사례는 증상별로 선택할 수 있다. 요구사항이 충분한 경우에는 추가 질문 없이 착수 근거와 다음 작업이 나와야 한다. 필요한 동작이 미정인 경우에는 그 답에 의존하는 작업만 멈춰야 한다. 미래 기능을 섞은 경우에는 현재 필수 작업에서 제외해야 한다. 기술 이슈에서는 저장소의 실제 파일과 원리, 코드 작성 방식 및 남은 위험이 연결돼야 한다. 동일한 요청을 다른 말로 전달해도 불필요한 기능을 추가하지 않는지도 비교할 수 있다.

관찰할 값은 필요한 설명을 얻기까지 입력한 추가 프롬프트 수, 근거 없이 추가한 기능, 착수 판단의 근거 누락, 실제 파일 및 코드 설명 누락, 근거로 확인할 수 없는 주장과 사용 비용이다. 수치 목표는 실제 기준 실행 없이 만들지 않는다. 문서 길이나 항목 수만으로 품질을 판정하지 않는다.

이 자료는 공식 절차와 실제 지침 파일을 비교한 조사이며 성공적인 도입을 재현한 실험 보고는 아니다. 따라서 개선 가능성은 설명할 수 있지만 개선 폭이나 모든 위험의 발견을 보장할 수 없다. 실제 실행 비교는 후속 확인으로 남는다.

## 구현 가능성 검토와 대안 비교

현재 요구사항은 기존 스킬의 조사 절차와 답변 기준을 보완하는 방식으로 구현에 착수할 수 있다. 새로운 실행 프로그램이나 외부 패키지가 필요한 조건은 확인되지 않았다. 다만 지침의 구현 가능성과 실제 모델의 개선 효과는 별개의 판단이다. 이 절은 2026-11-01에 현재 스킬 및 기존 요구사항을 비교한 분석이며, 실행 실험의 결론이 아니다.

### 지침을 추가하는 방식

기존 본문의 끝에 착수 판단과 구체적인 설명을 요구하는 문장을 붙이는 방법은 수정할 부분이 적다. 하지만 코딩 스킬에는 이미 원리 조사, 실제 파일 선택과 변경 설명 의무가 있다. 비슷한 문장을 더 붙이면 어느 단계에서 무엇을 해야 하는지가 여전히 모호하고, 반복해서 읽는 비용만 늘 수 있다. 이번 문제에 대한 우선안으로는 부적합하다는 판단이다.

### 조사 순서와 답변 기준을 연결하는 방식

요청의 목표에서 실제 파일과 처리 순서를 찾고, 필요한 원리를 조사한 뒤 변경 방법과 착수 여부를 함께 설명하게 하는 방식을 우선한다. 설계 스킬은 요구사항의 누락과 현재 작업 대상을, 코딩 스킬은 구현 방법과 기술적 실현 가능성을 담당한다. 둘을 항상 연달아 실행하게 만들지는 않는다.

[Agent Skills 작성 지침](https://agentskills.io/skill-creation/best-practices)은 선언보다 절차를 사용하고, 기본 방법을 제시하며, 필요한 상세 정보만 읽게 하는 방식을 설명한다. 원문은 “Favor procedures over declarations”다. 이 근거와 현재 코딩 스킬에 조사 의무가 이미 있다는 사실을 함께 보면, 기존 문단을 실행 가능한 순서로 보완하는 편이 조사 주제를 추가하는 것보다 문제에 직접 연결된다. 이 방식의 우위는 실제 비교로 확인해야 한다.

기존 파일 구성을 유지할 수 있다. 설계 스킬 본문에는 작업 판단과 착수 설명을, 기존 requirements workflow에는 요구사항을 바꾸지 않고 누락을 조사하는 절차를 둔다. 코딩 스킬은 현재 두 파일 안에서 조사와 설명을 연결한다. 기술별 교재나 조사 자료를 스킬의 필수 입력으로 복사할 이유는 없다.

### 별도 판정 도구를 만드는 방식

정해진 필드를 검사하는 프로그램은 필드 누락을 찾기 쉽다. 그러나 현재 문제는 불필요한 기능을 필수로 올리는 판단과 기술 설명의 구체성이다. 제목이나 항목의 존재만으로 그 의미를 판정할 수 없고, 별도 프로그램은 배포 및 유지할 대상을 늘린다. 기계적으로 반복 확인할 필요가 입증되지 않아 이번 계획에는 포함하지 않는다.

## 착수 판단에서 해소할 오해와 남은 위험

첫 응답은 도구 사용 전의 진행 알림이 아니라 필요한 조사를 마친 뒤 처음 제공하는 실질적인 답변으로 해석한다. 조사 전에 결론을 단정하게 하면 확인되지 않은 사실을 채워 넣을 수 있다. 조사 시간이 길면 확인된 내용과 아직 모르는 내용을 진행 알림으로 설명할 수 있다.

추가 질문을 줄이는 목표는 질문 자체를 금지하는 조건이 아니다. 자료로 확인할 사실은 먼저 조사하고, 동작이나 보존할 정보를 바꾸는 선택만 사람에게 묻는다. 답을 모르는 채 착수 가능으로 처리하거나 관련 없는 작업까지 전부 보류하는 방식은 모두 피해야 한다.

스킬을 실행했다고 항상 전체 구현 계획을 작성할 필요는 없다. 빈 파일 준비, 이름 변경과 읽기 전용 정리에는 요청한 결과를 제공하고 필요한 제약만 설명한다. 요구사항 작성과 보완 또는 기술 이슈처럼 내용 판단이 필요한 요청에서는 별도 보완 요청을 기다리지 않고 누락 조사와 착수 판단을 수행한다. 긴 고정 서식으로 모든 답변을 늘리는 것은 목표와 맞지 않는다.

기술 위험을 조사하는 행위와 새 기능을 요구하는 행위도 구분한다. 위험을 기록할 때는 현재 작업에서 발생할 조건과 영향을 설명하고, 조사나 기존 검사로 확인할 수 있는지 먼저 판단한다. 가능한 모든 보안, 성능과 운영 항목을 필수 개발 작업으로 바꾸지 않는다.

개발 스킬 호출을 바꾼 뒤에도 저장소 지침을 따라야 한다. 개발 README가 있으면 적용할 내용을 읽지만, 없는 README를 새 필수 파일로 요구하지 않는다. 기존 코딩 스킬의 고정 문서 체계를 전제하지 않는 조건과 양립하는 보완이다. 예전 스킬의 자동 실행, 삭제와 전체 내용 이관도 필요하지 않다.

지침이 길어지면 추가 요구가 기존 보존 조건을 가릴 수 있다. 현재 본문은 설계 스킬 427단어, 코딩 스킬 1,292단어다. 이는 현재 파일의 공백 기준 집계이며 토큰 수나 성능 측정값이 아니다. 구현 시 중복 문장을 대체하고 추가 이유가 없는 절과 참고 파일을 만들지 않는 방안을 적용한다. 특정 단어 수를 품질 목표로 정하지 않는다.

## 계획 수립 가능성과 효과 확인의 조건

요구사항을 바꾸어야 할 미해결 선택은 현재 검토에서 발견하지 못했다. 조사 방법과 기록 위치는 기존 지침으로 선택할 수 있으므로 [후속 계획](../plan.md)을 작성할 수 있다. 이 판단은 이후 새로운 충돌이나 확인할 수 없는 필수 자료가 발견됐을 때 다시 검토한다.

효과 확인에는 같은 요청과 같은 저장소 자료를 사용한 이전 버전과의 비교가 필요하다. [Agent Skills 평가 지침](https://agentskills.io/skill-creation/evaluating-skills)은 비교 실행과 새 문맥을 사용하고 답변 품질 및 사용 비용을 함께 살피도록 한다. 원문은 “a baseline to compare against”다. 이번 계획은 기존 사례 설명을 이용하며 별도 평가 프로그램이나 가짜 애플리케이션을 만들지 않는다.

비교 실행을 할 수 없어도 지침과 형식의 반영 여부는 확인할 수 있다. 이 경우에는 지침 반영 완료와 효과 미확인을 함께 남겨야 한다. 모든 잠재 위험의 발견, 추가 질문의 완전한 제거와 항상 정확한 착수 판정을 완료 조건으로 만들 수는 없다.
