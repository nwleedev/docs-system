# 요구사항 조사와 구현 착수 판단을 연결하는 스킬 보완 계획

기존 스킬의 조사 순서와 답변 기준을 보완하는 작업에 착수할 수 있다. 설계 스킬은 현재 요구사항의 누락과 작업 대상을, 코딩 스킬은 실제 파일과 작성 방법 및 기술적 위험을 설명하도록 연결한다. 지침 반영과 실제 사용 효과는 따로 확인한다.

## 기준과 유지할 동작

이번 계획의 기준은 [요구사항](./requirements.md)의 「이름과 호출 안내」, 「개선할 동작」, 「이번 조사의 완료 조건」과 「구현 가능성 판단과 계획」이다. [구현 가능성 검토](./references/readiness-and-technical-discovery.md#구현-가능성-검토와-대안-비교)에서 비교한 방법 중 기존 절차와 답변 기준을 연결하는 방식을 사용한다. 계획에서 선택한 작성 방법을 별도의 승인된 요구사항으로 취급하지 않는다.

다음 기존 요구사항도 적용하며, 같은 뜻의 조건을 여러 파일에 복제하지 않는다.

- [설계 스킬 요구사항 전체](../flexible-designs-4f8c/requirements.md): 최소 작성, 빈 문서 준비, 기존 문서 재사용, 의미 보존과 제안 분리 및 결정과 계획 연결을 유지한다.
- [코딩 스킬 요구사항 전체](../task-pattern-guidance-4ffad1/requirements.md): 지정 파일 기록, 파일 미지정 시 후보 제안, 구현 및 측정 권한 구분, 원리와 대안 조사, 판단에 맞는 예시, 근거가 있는 이력 설명과 재개 절차를 유지한다.
- [개발 지침](../../dev/README.md): 요청에 맞는 조사와 확인 방법을 선택한다. 실행 프로그램과 의존성을 바꾸지 않으므로 MJS 개발 지침은 이번 스킬 문구 보완에 적용하지 않는다.

계획의 첫 커밋 전에는 검토한 현재 파일을 임시 기준으로 삼는다. 이후에는 이 계획을 마지막으로 수정한 커밋의 요구사항과 적용 지침을 기준으로 변경 영향을 비교한다. 구현 시작 전에 아직 커밋하지 않은 선행 변경과 이 계획을 구분해 확인한다.

## 변경할 파일과 이유

스킬 본문과 호출 정보는 영어로 유지한다. 아래 파일을 보완하고 새 실행 프로그램이나 스킬을 추가하지 않는다.

- `skills/use-flexible-design/SKILL.md`: 내용 판단이 필요한 요청에서 누락 조사와 착수 판단을 작업 선택에 포함하고, 첫 실질 답변에 담을 판단을 정한다.
- `skills/use-flexible-design/references/requirements/workflow.md`: 요구사항 보존 및 비교 단계에 누락 조사를 연결한다. 조사 제안은 작성 권한과 별개임을 유지한다.
- `skills/use-flexible-coding/SKILL.md`: 조사 대상을 발견하는 순서와 실제 파일, 원리, 작성 방법 및 착수 판단의 연결을 보완한다. 기존 문단을 대체해 같은 의무를 중복 추가하지 않는다.
- 두 스킬의 `agents/openai.yaml`: 본문의 실제 역할에 맞춰 설명과 기본 호출문을 고친다. 기존 필드와 호출 이름은 보존한다.
- `src/AGENTS.en.md`, `src/AGENTS.ko.md`: 두 스킬을 선택할 조건과 독립적인 사용, 개발 지침 적용 및 구현 권한 구분을 같은 의미로 맞춘다.
- `README.md`, `README.ko.md`: 첫 실질 답변에서 제공할 판단과 두 스킬의 차이를 소개한다. 기존 개발 지침 스킬의 파일과 독립 사용 가능성은 유지하되 현재 AGENTS 호출과 혼동되는 설명을 고친다.
- 이 설계 묶음의 조사 자료와 계획: 실제 선택과 미해결 사항이 바뀔 때 갱신한다. 과거 두 계획의 완료 기록은 변경하지 않고 후속 계획을 연결한다.

이름과 이전 호출 참조의 수정은 현재 작업 파일에 이미 반영돼 있다. 구현 단계에서는 이름과 호출 수정을 보존하고 실제 수정 차이를 기준으로 남은 내용을 반영한다. 사용자 환경에 설치된 스킬 사본은 자동으로 바꾸지 않는다.

## 실행 기록

- 착수 조건과 보존 기준: 확인 완료. 현재 변경은 이 설계 묶음의 조사와 계획, 후속 계획 연결 및 이름과 호출 안내 정리다. 기존 요구사항과 실제 구현 권한은 유지하며 추가로 결정할 동작은 발견하지 못했다.
- 설계 스킬 보완: 본문과 requirements workflow에 반영. 현재 목표와 대화의 의도 확인, 후속 요청 없이 누락 조사, 제안 분리와 근거가 있는 착수 판단을 연결했다. 빈 파일 및 구조 정리의 예외는 유지한다. 최종 사례 대조와 형식 확인은 마지막 단계에서 수행한다.
- 코딩 스킬 보완: 미착수.
- 호출 정보와 안내 일치: 미착수.
- 마지막 확인과 효과 비교: 미착수. 문서 및 형식 확인과 실제 답변 비교를 구분한다.

수정 전 기준은 이 실행 기록과 함께 저장하는 현재 파일이다. 실제 비교를 수행할 때는 Git에 저장한 이전 스킬을 읽어 사용하며, 필요한 임시 사본만 계획에서 정한 위치에 둔다.

## 작업 순서와 단계별 확인

### 착수 조건과 보존 기준 확인

구현을 시작할 때 위 기준 요구사항, 최종 조사 자료와 수정 대상 파일을 읽고 선행 변경을 확인한다. 이름 및 호출 변경을 중복 수행하거나 다른 작업의 변경을 덮어쓰지 않는다. 현재 설계 스킬과 코딩 스킬은 서로를 필수 실행 조건으로 요구하지 않는다.

동작과 작성 권한을 바꾸는 미해결 질문이 없는지 확인한다. 보완이 기존 최소 작성이나 지정 파일 규칙을 바꿔야만 가능한 경우에는 영향을 받는 작업을 멈춘다. 기존 조건을 유지하는 본 계획대로 진행할 수 있으면 다음 단계로 간다.

완료 근거는 현재 파일과 계획의 일치, 보존할 조건의 확인과 새로 발견한 차이의 기록이다. 실제 답변 비교를 수행할 예정이면 수정 전 스킬과 그 참고 파일을 `temps/skill-readiness-<nonce>/` 안에 복사해 비교 기준을 남긴다. 이 사본을 커밋하거나 배포하지 않는다.

### 설계 스킬에 현재 목표 중심의 누락 조사 연결

`Select the work`와 `Finish`를 보완한다. 요구사항 작성과 보완을 포함해 내용이나 구현 준비 상태를 판단하는 요청이면 현재 목표, 대표적인 사용 상황과 가능한 실패 상황을 먼저 파악하고, 그 상황의 동작이 기존 요구사항으로 결정되는지 조사한다. 별도로 부족한 점을 묻는 후속 요청을 기다리지 않는다. 빈 파일 준비와 단순 정리에는 전체 구현 분석을 강제하지 않는다.

부족한 항목은 현재 목표에 필요한 조건인지 이유를 설명한다. 자료로 답할 사실은 조사하고, 사람의 선택이 필요한 질문과 향후 기능은 구분한다. 필요한 선택을 답하지 못한 채 확정 요구사항으로 넣지 않는다. 요청에 따라 작성할 요구사항은 명시된 목표와 조건만 반영한다.

requirements workflow의 비교 단계에는 이 판단을 연결하되 최소 작성 규칙을 유지한다. 새 기능, 성능 목표나 운영 절차를 예시에서 추정해 넣지 않는다. 기존 내용이 충분하면 변경 없이 그 근거와 다음 작업을 설명할 수 있어야 한다.

첫 실질 답변은 필요한 조사를 마친 뒤 제공하는 답변이다. 현재 목표, 부족한 정보 또는 충분하다는 근거, 착수 가능 여부와 남은 위험 및 다음 작업을 요청에 필요한 분량으로 설명한다. 고정 제목, 항목 수와 장문 서식을 요구하지 않는다. 실행할 코드의 구체화가 필요한 부분은 기술 조사 대상으로 연결하되 코딩 스킬 실행을 모든 요청에 강제하지 않는다.

완료 여부는 아래 「대표 사례와 관찰할 행동」의 충분한 요구사항, 미해결 질문, 미래 기능과 빈 파일 준비 사례를 최종 지침에 대조해 판단한다. 의미 보존과 조사 제안 분리도 함께 확인한다.

### 코딩 스킬에 실제 처리와 작성 방법 연결

`Establish the task and destination`에서는 기록할 파일의 미지정이나 기록 불가가 조사 자체의 중단을 뜻하지 않도록 설명한다. 파일을 바꾸지 않고 대화에서 기술 조사와 기록 후보를 제시하는 기존 권한을 유지한다. 개발 README가 있으면 적용할 지침을 읽고, 없으면 기존 지침과 기록 대상 확인 절차를 따른다. 새 README 생성이나 옛 개발 스킬의 실행을 필수로 만들지 않는다.

`Research each task`는 조사할 질문을 실제 입력, 호출 함수, 처리 순서, 저장 또는 반환 및 실패 처리에서 찾도록 구체화한다. 목적과 버전, 보호할 동작, 실제 파일 및 타입을 먼저 확인하고 아직 읽지 못한 내용을 밝힌다. 요구사항, 현재 구현 방식과 변경 가능한 부분을 구분하는 기존 절차를 유지한다.

각 질문에는 어떤 원리가 필요한지, 현재 작업에서 왜 문제가 되는지, 원리가 성립하는 조건과 대안 및 확인할 증거를 연결한다. 데이터 모델, 반복 작업과 동시성 등은 질문을 찾는 단서로 사용하며 분야명이나 대안 수를 채우지 않는다. 처리 방식을 바꾸는 대안도 조사하되 현재 동작을 바꿀 권한으로 해석하지 않는다.

`Explain changes and examples`에서는 추가, 수정, 분리하거나 유지할 실제 파일과 함수 및 타입, 그 역할과 의존 방향을 제시한다. 구현 방법을 판단하는 요청에서는 코드 예시를 따로 요구하지 않아도 처리 순서와 사용하는 버전 및 기존 타입에 맞는 예시를 포함한다. 파일과 폴더 구성은 실제 위치와 역할로 설명하며 무조건 계층을 새로 만들지 않는다. 변경하지 않는 판단도 이유를 설명한다.

완료 시 착수 판단을 제시하도록 짧은 절을 추가하거나 기존 미확인 사항 처리 절과 연결한다. 구현에 필요한 선택과 확인 방법이 있으면 착수 가능, 독립적인 작업만 시작할 수 있으면 일부 가능, 답에 따라 동작이나 구현이 달라지면 보류로 설명한다. 영향을 받는 작업과 다음 행동을 명시하며 저장소의 검토 상태 명칭과 혼용하지 않는다. 준비 상태와 실제 수정 권한도 구분한다.

이력, 재개, 예시의 실행 여부와 테스트 대상 및 필요성 판단, 시각 표현 조건은 유지한다. 테스트 코드 작성이나 부하 측정을 자동으로 실행하게 만들지 않는다. 완료 여부는 아래 기술 설명과 부분 착수 사례에서 실제 파일, 원리, 작성 방법과 확인 방법을 연결하도록 지시하는지로 확인한다.

### 호출 정보와 안내 일치

두 스킬의 본문을 먼저 확정한 뒤 YAML과 두 언어 AGENTS 및 README를 맞춘다. 기본 호출문에 본문 전체를 복제하지 않고 현재 목표에 필요한 조사와 구현 준비 상태 설명을 요청하는 문장을 둔다.

이전 이름으로 실행하라는 안내가 남지 않아야 한다. 보존하는 옛 스킬의 소개, 과거 조사 기록과 실제 호출 안내는 구분한다. 설계 스킬의 내용을 판단하는 요청과 코딩 스킬의 기술 판단 요청을 같은 문구로 합치지 않으며, 둘을 항상 연속 실행하도록 만들지 않는다.

완료 근거는 YAML과 본문의 역할 일치, 이름 및 디렉터리 일치, 두 언어의 의미 일치와 문서 연결이다. 메타데이터를 고쳤다는 이유로 실제 스킬 동작이 확인됐다고 판단하지 않는다.

### 마지막 확인과 효과 비교

모든 수정 뒤 대표 사례 대조와 문서 및 형식 확인을 한 번 수행한다. 필요한 지침이 본문 여러 절에 반복되지 않는지, 새로운 스킬 또는 실행 도구가 추가되지 않았는지, 기존 요구사항의 보호 조건이 빠지지 않았는지 읽는다. 문서 연결, YAML, 변경 대상과 민감정보 및 표현을 같은 단위로 확인한다.

기본 스킬 검사기를 실행할 수 없으면 사용 가능한 YAML 파서로 확인한 항목과 확인하지 못한 항목을 구분한다. 문서만 바뀌는 작업의 검사 범위를 넘어 의존성을 임의로 추가하지 않는다. 구문이나 실행 로직 변경이 생기면 기존 계획을 그대로 적용하지 않고 적용할 개발 지침과 검사를 다시 정한다.

실제 효과는 새 문맥에서 동일한 요청, 자료, 모델과 도구 조건으로 수정 전후 답변을 비교해 확인한다. 이 단계는 문서 검토를 반복하는 절차가 아니라 관찰된 행동의 비교다. 각 실행에서는 정답이나 예상 개선점을 미리 제공하지 않는다. 아래 사례의 필요한 설명이 첫 실질 답변에 있는지, 근거 없는 기능이 추가되는지, 사실 질문을 사람에게 떠넘기는지와 추가 프롬프트 수를 기록한다. 제공되는 경우 시간과 토큰도 비교하며 예상치를 측정값처럼 적지 않는다.

비교 환경을 확보하지 못하면 지침 반영 여부까지만 완료로 기록하고 효과는 미확인으로 남긴다. 실제 실행을 하지 않았는데 입력 사례를 문서에 대입한 결과로 대체하지 않는다. 별도 평가 프로그램, 테스트 코드나 가짜 프로젝트를 만들지 않으며, 임시 사본과 실행 자료는 사용이 끝나면 정리한다.

## 대표 사례와 관찰할 행동

아래 사례는 변경 지침을 확인하고 후속 비교 실행을 설계하기 위한 입력이다. 현재 실행 결과나 새 기능 요구사항이 아니다. 사례마다 현재 자료로 확인할 사실과 사람의 선택이 필요한 조건을 구분한다.

### 충분한 요구사항

현재 설계 스킬의 빈 문서 준비 요구사항과 생성 스크립트를 제시하고 착수 가능 여부 및 보완할 내용을 묻는다. 기존 파일 보존, 생성 결과와 실패 후 상태를 근거로 설명하고, 충분한 조건을 다시 질문하거나 편집 이력 서버 같은 새 기능을 필수 작업에 넣지 않아야 한다.

### 동작을 바꿀 답이 없는 상황

기존 문서에 덧붙일지 새 문서를 만들지 결정되지 않은 입력에 대해 요구사항 정리와 착수 판단을 요청한다. 실제로 같은 목적의 후보가 둘 이상 남을 때에만 차이와 선택할 질문을 제시해야 한다. 그 선택에 의존하는 작성은 멈추되, 영향을 받지 않는 자료 조사까지 일괄 중단하지 않아야 한다.

### 미래 기능이 섞인 상황

빈 요구사항 생성에는 현재 새 폴더 및 빈 파일과 기존 파일 보존이 필요하고, 여러 사용자의 승인 처리는 나중에 검토한다고 명시한 입력을 사용한다. 후자의 기능을 현재 필수 요구사항이나 실행 작업으로 올리지 않아야 한다. 현재 실패 처리 조사까지 미래 기능으로 간주해 생략해서도 안 된다.

### 구체적인 기술 설명과 파일 미지정

이 저장소의 생성기가 기존 파일을 바꾸지 않는 이유, 코드를 어떻게 작성할지와 파일을 나눌 필요가 있는지 설명해 달라고 요청한다. 기록 파일은 지정하지 않는다. 현재 `create.mjs`의 함수, `open`의 `wx`, 동시성 원리와 파일 역할을 조사하고 대화에서 작성 방향을 설명해야 한다. 저장할 후보는 제안하되 파일을 만들지 않으며, 실행하지 않은 예시를 검증 완료라고 표현하지 않아야 한다.

### 조사하지 않은 조건과 부분 착수

배포할 파일 시스템의 종류가 확인되지 않았을 때 기존 생성 방식의 적용 가능성을 묻는다. 로컬 파일 생성에서 확인한 사항과 네트워크 파일 시스템에서 확인할 사항을 구분하고, 그 차이에 의존하지 않는 문서 정리 등의 작업이 있을 때만 일부 착수 가능으로 판단해야 한다. 모든 환경에서 안전하다고 단정하거나 분산 잠금을 자동으로 추가하지 않아야 한다.

### 과도한 분석을 하지 않아야 하는 요청

빈 파일만 준비하는 요청과 스킬 표시 이름만 바꾸는 요청을 사용한다. 요청한 결과와 필요한 제약을 설명하되 전체 아키텍처 조사나 코드 예시, 새 기능 목록을 강제하지 않아야 한다. 최소 작성과 읽기 전용 요청의 권한도 유지해야 한다.

## 중단 조건과 완료 판단

현재 검토에서 스킬 지침 보완을 막는 기술적 조건은 발견하지 못했다. 실제 모델 효과와 모든 위험의 발견은 아직 확인되지 않았다. 다음 조건이 새로 확인되면 영향을 받는 작업을 멈춘다.

- 필수 스킬 또는 참고 자료를 읽을 수 없다.
- 기존 요구사항의 의미, 작성 권한, 데이터 보존이나 지정 파일 조건을 바꿔야 한다.
- 새 실행 도구, 의존성 또는 설치된 스킬 사본 변경이 필요해진다.
- 사람의 선택 없이는 구현할 동작이나 실제 수정 대상을 결정할 수 없다.

완료 보고에서는 지침의 내용 확인, 파일 및 형식 확인, 실제 답변 비교를 구분한다. 지침과 형식을 반영했지만 비교 실행을 못했다면 그 사실을 함께 기록한다. 구현이 끝나지 않은 작업을 문서 작성만으로 완료 처리하지 않는다.
