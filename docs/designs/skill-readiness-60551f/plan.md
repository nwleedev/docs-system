# 요구사항 조사와 구현 착수 판단을 연결하는 스킬 보완 계획

## 추가 요구사항의 후속 실행 계획

기존 두 스킬의 조사 절차와 문서 규칙을 보완하는 작업에 착수할 수 있다. 새로 추가한 목표 확인과 이슈 처리, 기술 조사 깊이 요구사항은 아래 후속 계획을 따른다. 이전 계획의 완료 기록은 추가 전 요구사항에 대한 것이며 이 후속 작업의 완료를 뜻하지 않는다.

### 기준 요구사항과 유지할 조건

기준은 [요구사항](./requirements.md)의 「목표 확인과 이슈 처리 및 완료 판단」과 「기술 이슈의 원리와 설계 대안 심층 조사」다. 기존 「이름과 호출 안내」, 「개선할 동작」, 「이번 조사의 완료 조건」과 「구현 가능성 판단과 계획」도 유지한다. 이름 변경과 기존 구현을 다시 수행하지 않고, 추가 조건에 필요한 차이만 보완한다.

- [설계 스킬의 기존 요구사항](../flexible-designs-4f8c/requirements.md)은 최소 작성, 기존 문서 재사용, 의미 보존과 승인된 내용의 기록 조건에 적용한다.
- [코딩 스킬의 기존 요구사항](../task-pattern-guidance-4ffad1/requirements.md)은 지정 파일 기록, 원리와 대안 조사, 판단에 맞는 예시, 재개와 실제 변경 권한에 적용한다.
- [설계 문서 규칙](../README.md)의 계획 기준과 변경 영향 분석을 따른다. 후속 계획을 처음 저장하는 커밋까지는 검토한 현재 요구사항을 임시 기준으로 삼고, 이후에는 이 계획을 마지막으로 수정한 커밋의 요구사항과 적용 지침을 기준으로 삼는다.
- [개발 지침](../../dev/README.md)은 실제 스킬과 설정 및 검사 변경을 판단할 때 적용한다. 실행 코드를 바꾸지 않으므로 현재 MJS 개발 지침에 따른 새 구현이나 테스트는 필요하지 않다.

스킬 본문과 호출 정보는 영어로 유지한다. 두 스킬의 독립적인 선택, 기록할 파일이 없어도 대화에서 조사를 이어가는 동작, 빈 문서 준비와 단순 정리의 예외를 보존한다. 요구사항의 작성 권한이나 실제 구현 및 측정 권한도 바꾸지 않는다.

### 구현 방법과 선택 이유

[기존 대안 비교](./references/readiness-and-technical-discovery.md#구현-가능성-검토와-대안-비교)의 조사 순서와 답변 기준을 연결하는 방법을 이어간다. 현재 본문에도 조사 분야와 원리, 가정 및 대안 설명이 있어 분야 목록이나 마지막 확인 문장만 더 붙이는 방법은 중복을 만든다. 기존 절에서 판단이 필요한 시점과 그때 사용할 근거를 연결하는 방법을 선택한다.

스킬별 판단 절차는 각 본문에 두고, 요구사항 기록과 계획 갱신의 공통 규칙은 설계 README에 둔다. 코딩 스킬이 특정 문서 체계를 필수로 요구하지 않는 조건은 유지한다. 새 판정 도구는 요구사항의 의미와 설명의 깊이를 판정할 필요가 입증되지 않아 추가하지 않는다. 기술별 교재나 별도 필수 참고 파일도 만들지 않는다.

### 현재 지침과 추가 요구사항의 차이

설계 스킬의 「Investigate what the current goal needs」에는 필요한 조건과 제안을 구분하는 지침이 있다. 프로젝트 이름에서 동작을 확정하지 않는 기준, 신규 이슈의 분류와 근거 설명을 이 조사 순서에 보완한다. 기존 requirements workflow에는 조사와 기록 사이에서 승인 상태를 확인하는 절차를 연결한다.

코딩 스킬의 「Research each task」와 「Explain principles and decision history」에는 원리의 작동 방식과 가정 및 대안 조사가 있다. 구현 전 질문 도출, 실제 문제와 원리의 인과관계, 대안 선택을 바꾸는 조건까지 설명하도록 구체화한다. 깊이가 부족한 답변의 원인을 기존 지침 누락으로 단정하지 않는다.

현재 설계 README의 「Requirement Changes During Work」는 요구사항이 달라졌을 때의 갱신 절차를 정한다. 요구사항이 그대로여도 기술적 전제와 작업량이 달라지면 전체 계획을 재판단하는 절차가 필요하다. 두 README의 기존 「plan.md」와 변경 영향 절에 이 조건을 보완하고, 일반 요구사항 변경과 같은 절차를 다시 복제하지 않는다.

### 설계 스킬의 목표 확인과 이슈 분석 보완

대상은 `skills/use-flexible-design/SKILL.md`의 「Select the work」, 「Investigate what the current goal needs」, 「Keep the work connected」와 「Finish」다. `skills/use-flexible-design/references/requirements/workflow.md`의 기존 자료 비교와 작성 단계도 함께 보완한다.

목표와 사용 상황에서 기대 동작을 찾고, 기존 자료로 확인한 의미와 아직 결정할 수 없는 의미를 구분하도록 한다. 이슈가 발견되면 사실과 추정을 구분하고 결함, 해석 차이, 기술적 제약과 추가 기능 중 어떤 성격인지 설명하도록 연결한다. 모든 이슈를 새 요구사항으로 기록하는 절차는 만들지 않는다.

추가 조건이 없으면 실패하는 사용 상황과 현재 목표의 관계를 설명하게 한다. 유사 서비스의 기능이라는 사실만으로 필요성을 확정하지 않고, 기존 동작에 필요한 처리를 부가 기능으로 잘못 제외하지 않게 한다. 다르게 해석할 때 실제 동작이 달라지는 부분은 구체적으로 설명하되, 구현 방법의 선택까지 모두 모호한 요구사항으로 처리하지 않는다.

조사로 확인할 사실은 먼저 확인하고, 선호나 우선순위 및 요구한 동작을 바꾸는 선택만 그 영향을 설명해 묻도록 한다. 기존 workflow의 의미 보존과 최소 작성 조건을 유지하며, 조사와 권장안을 승인된 요구사항으로 자동 기록하지 않게 한다.

완료 증거는 이름만 제시된 요청, 충분한 요구사항과 부가 기능 후보가 섞인 요청에서 목표와 근거를 설명하도록 최종 지침이 연결되는지다. 실제 답변의 개선은 뒤의 행동 비교에서 별도로 확인한다.

### 코딩 스킬의 심층 조사와 구현 설명 보완

대상은 `skills/use-flexible-coding/SKILL.md`의 「Establish the task and destination」, 「Start and resume」, 「Research each task」, 「Explain principles and decision history」, 「Explain changes and examples」와 「Return an actionable assessment」다.

구현 전에는 목표와 사용 조건, 기존 코드가 있으면 실제 입력과 처리 및 저장 또는 반환에서 조사 질문을 찾도록 한다. 코드가 없다는 이유로 기술 조사를 중단하거나, 제안한 구조를 이미 존재하는 구현처럼 설명하지 않게 한다.

현재 문제를 일으키거나 예방하는 원리를 찾고, 작동 방식과 성립 조건을 설명한 뒤 대안의 차이에 연결한다. 코드 디자인 패턴, 모듈 구조, 시스템 아키텍처와 컴퓨터 공학 지식은 질문에 필요한 만큼 조사한다. 모든 질문에서 같은 분야와 대안 수를 채우는 방식은 사용하지 않는다.

설명에는 판단에 필요한 처리 순서와 자료 구성, 의존 관계와 자원 비용을 연결한다. 원리의 정의나 일반적인 장단점으로 끝내지 않고, 적용 조건이 바뀌면 어떤 결론이 달라지는지와 아직 확인할 사실을 제시하도록 한다. 실제 조건에 맞는 예시와 근거를 사용하고, 추정 효과를 측정값으로 표현하지 않게 한다.

요구사항을 구현하기 위한 작업과 파일, 필요한 이유 및 완료 증거를 연결한다. 선행 조건은 그 조건이 없을 때 다음 작업에서 수행하거나 확인하지 못하는 동작으로 설명하게 한다. 최종 완료 기준을 모든 기능의 착수 조건으로 삼지 않고 독립적인 작업은 구분하도록 한다.

조사의 종료 여부는 다음 판단에 필요한 근거와 남은 불확실성으로 설명하도록 한다. 조사 분량이나 출처 수를 심층 조사의 완료 근거로 삼지 않는다. 기존 재개 절차에도 새 사실로 판단 근거가 바뀌었는지 확인하는 내용을 연결한다.

완료 증거는 현재 문제와 원리, 대안의 차이, 구체적인 변경 및 확인 방법을 최종 지침에서 따라갈 수 있는지다. 기술의 이름만 추천하거나 모든 기술 주제를 나열해도 완료로 보지 않는 기준을 포함한다.

### 문서 규칙에 재계획 조건 반영

대상은 `docs/designs/README.md`와 `skills/use-flexible-design/references/_README.md`의 「plan.md」 및 「Requirement Changes During Work」다. 후속 구현에서 두 문서에 같은 공통 의미를 반영하되 각 문서의 다른 내용을 덮어쓰지 않는다.

새로 확인한 기술 제약, 예상 작업량이나 확인한 사실이 기존 전제와 다르면 영향을 받는 작업, 유지되는 완료 근거와 전체 완료 예상의 변화를 비교하게 한다. 요구사항이 그대로라면 요구사항 문서를 억지로 고치지 않고 영향을 받는 계획과 판단 근거를 갱신하도록 한다. 기한과 자원 제한은 정해져 있을 때 반영하며, 요구한 동작과 조건을 바꿔야 하는 선택은 확정 전에 영향을 설명하도록 한다.

계획에는 각 작업에서 확보할 근거나 산출물, 선행 이유와 관찰할 증거를 연결하고 개별 작업 완료와 전체 목표의 달성을 구분하도록 한다. 이미 계획이 있는 경우 그 계획을 갱신하며 모든 작업에 새 계획 문서를 만들도록 요구하지 않는다. 다른 저장소의 README를 자동 비교하거나 동기화하는 동작도 추가하지 않는다.

완료 증거는 요구사항 변경 없이 전제만 달라진 경우에도 기존 변경 관리와 충돌 없이 재판단할 수 있는 규칙이다. 설계 스킬은 이 규칙을 참조하고, 코딩 스킬은 문서 체계가 없는 작업에서도 영향과 다음 판단을 대화로 설명할 수 있어야 한다.

### 호출 안내와 소개의 일치

본문과 문서 규칙을 정한 뒤 두 스킬의 `agents/openai.yaml`, `src/AGENTS.en.md`, `src/AGENTS.ko.md`, `README.md`와 `README.ko.md`를 대조한다. 목표 확인과 이슈 분석, 근거를 갖춘 기술 설명의 역할이 기존 안내로 충분하면 유지하고, 차이가 생긴 설명과 기본 호출문만 수정한다.

상세 판단 절차는 본문에 남기고 호출 안내에 반복하지 않는다. 두 스킬을 언제나 연속 실행하는 조건이나 이름 변경, 설치된 사본의 자동 갱신은 추가하지 않는다. 완료 증거는 본문과 호출 정보의 역할 및 두 언어의 의미가 일치하는지다.

### 실행 순서와 의존 관계

1. 최신 요구사항과 현재 본문을 대조해 유지할 지침과 대체할 문장을 확정한다. 이 계획을 마지막으로 저장한 커밋과 그 뒤의 요구사항 차이를 확인하며 이전 완료 기록을 새 작업에 합산하지 않는다.
2. 설계 스킬과 requirements workflow, 문서 규칙의 공통 의미를 맞춘다. 이슈 분석, 요구사항 기록과 계획 갱신이 다른 승인 상태를 가정하지 않도록 함께 정리한다.
3. 코딩 스킬의 조사와 설명 및 재개 절차를 보완한다. 기술적 분석은 독립적으로 작성할 수 있지만, 계획 갱신과 사용자 선택의 의미는 앞 단계와 일치시킨다.
4. 본문을 기준으로 호출 정보와 소개를 맞춘다. 이 단계는 역할 설명이 정해진 뒤 수행해야 안내가 실제 동작을 과장하지 않는다.
5. 변경된 문서와 형식을 한 번 대조하고, 실제 행동 비교를 수행한다. 지침 반영과 효과 확인은 각각의 증거로 완료 상태를 구분한다.

요구사항을 더 구체화해야 하는 질문이 없다면 위 순서로 지침을 보완할 수 있다. 현재 계획은 기존 Markdown과 YAML의 설명을 수정하는 작업이며 실행 코드, 생성기, 의존성이나 테스트 코드를 추가하지 않는다.

### 대표 상황과 관찰할 증거

아래 상황은 후속 구현을 확인할 입력과 판단 기준이다. 별도 애플리케이션이나 평가 프로그램을 만들지 않고 이 저장소의 기존 문서와 생성기를 사용한다.

- 이름만 제시된 작업: 이름에서 연상되는 부가 기능을 확정하지 않고 기존 대화와 문서에서 실제 목표를 찾는지 확인한다. 부족한 의미를 묻는 경우에는 선택에 따라 달라지는 동작을 설명해야 한다.
- 부가 기능 제외와 필수 처리 유지: 빈 요구사항 파일 생성에서 향후 승인 처리는 제외하되 기존 파일 보존과 실패 후 상태 설명은 유지하는지 확인한다. 요구하지 않은 자동 정리나 복구 기능을 필수로 올리지 않아야 한다.
- 의미와 구현 선택 구분: 문서의 뜻이 달라지는 해석은 근거를 설명하고, 같은 뜻을 보존하는 여러 파일 구성 방법은 기술적 선택으로 비교하는지 확인한다. 확인할 사실을 사용자에게 대신 조사하도록 요구하지 않아야 한다.
- 요구사항 변경 없는 새 사실: 생성기의 동작 요구는 유지하면서 적용할 파일 시스템의 조건이 새로 확인된 상황을 제시한다. 기존 근거의 적용 여부와 영향을 받는 작업 및 완료 예상을 재판단하고, 영향을 받지 않는 작업은 유지하는지 확인한다. 완료 시점의 근거가 없으면 날짜를 만들지 않아야 한다.
- 기존 코드의 기술적 질문: `create.mjs`의 `mkdir`와 `open`의 `wx`가 기존 파일 보존에서 각각 어떤 역할을 하는지 묻는다. 사전 존재 확인과 실제 생성 사이의 동시성 문제, 각 호출이 덮어쓰기를 막는 조건과 적용 환경의 한계를 설명하고 대안을 비교하는지 확인한다. 실행하지 않은 환경에서의 안전성을 확정하지 않아야 한다.
- 코드가 없는 설계 질문: 기존 두 스킬과 문서 규칙의 역할을 어떻게 나눌지 묻는다. 기술 이름이나 폴더 목록만 제시하지 않고 규칙 중복, 수정 영향과 의존 관계를 근거로 대안을 설명하는지 확인한다. 가상의 구현이나 새 서비스를 만들지 않아야 한다.
- 실제 동작의 완료 판단: 생성기의 코드와 사용법만 제시하고 파일 생성 동작까지 확인됐다고 말할 수 있는지 묻는다. 소스 대조와 실제 실행 증거를 구분하고, 확인할 입력과 생성 파일 및 실패 후 상태를 설명하는지 확인한다.
- 충분한 근거와 단순 요청: 기존 명령의 사용법이나 빈 파일 준비만 필요한 요청에서 전체 아키텍처 조사와 불필요한 질문을 추가하지 않는지 확인한다. 추가 조사가 현재 결정을 바꿀 수 있는 경우와 이미 근거가 충분한 경우를 구분해야 한다.

### 마지막 확인과 효과 비교 방법

문서 확인은 최종 변경을 요구사항의 열 항목과 심층 조사 조건에 한 번 대조한다. 중복 의무, 모순된 승인 상태, 원하지 않는 기능 축소와 조사 확대를 함께 확인한다. 상대 링크와 절 연결, YAML 형식, 두 언어의 의미와 `git diff --check`를 확인하고, 한국어 변경 문구는 기존 표현 검사로 확인한다.

YAML은 저장소에서 사용한 Ruby 표준 파서로 필드와 형식을 확인할 수 있다. 전용 스킬 검사기를 사용할 수 없으면 확인한 항목과 미확인 항목을 구분하며 새 의존성을 설치하지 않는다. 실행 코드와 검사 설정을 변경하지 않는 동안에는 MJS 테스트와 lint 실행을 지침 효과의 증거로 사용하지 않는다.

행동 비교에서는 수정 전후 스킬을 같은 요청과 자료, 모델 및 도구 조건의 서로 독립된 새 문맥에 제공한다. 한 사례의 대화가 다른 사례의 답을 알려주지 않도록 분리한다. 입력에는 작업에 필요한 사실만 제공하고 위 관찰 기준과 기대 답안은 평가에만 사용한다. 응답과 확인한 근거, 불필요한 추가 기능이나 질문, 실제로 추가 설명이 필요했던 부분을 함께 기록한다.

기술 조사의 깊이는 설명 길이보다 원리가 현재 문제와 대안 선택을 설명하는지, 성립 조건과 결론을 바꿀 사실을 제시하는지로 비교한다. 실제 도구 호출과 읽은 자료도 살펴 답변에 없는 조사를 했다고 추정하지 않는다. 제공되는 실행 시간과 토큰을 함께 기록하되 수집하지 못한 수치는 미확인으로 남긴다.

비교 환경과 호출 한도가 확인되지 않으면 실제 모델 실행만 보류하고 지침 반영과 문서 확인은 진행한다. 모델 실행의 별도 권한이 필요한 경우에는 확보한 뒤 수행한다. 임시 사본이 필요하면 `temps/skill-readiness-<nonce>/` 아래에 두며 민감정보와 다른 저장소 자료는 포함하지 않는다. 실제 비교를 하지 못하면 지침 반영 완료와 효과 미확인을 구분해 남긴다.

### 중단 조건과 전체 완료 판단

기존 요구사항의 의미나 기록 권한을 바꿔야 하거나 새 실행 도구와 의존성이 필요해지면 영향을 받는 작업을 멈추고 이유를 설명한다. 새로운 사실이 후속 계획의 전제를 바꾸면 필요한 작업과 완료 예상을 다시 판단한다. 비교 실행만 불가능한 경우에는 그와 독립적인 문서 보완까지 중단하지 않는다.

전체 지침 반영 완료는 요구사항이 실제 본문과 기록 규칙 및 호출 안내에 연결되고 마지막 문서 확인의 근거가 있을 때 판단한다. 실제 답변에서의 효과는 비교한 사례와 조건 안에서만 설명한다. 일부 사례의 개선만으로 모든 프로젝트에서 정확하게 판단하거나 일정을 준수한다고 단정하지 않는다.

## 추가 전 계획과 완료 기록

아래는 추가 요구사항 이전의 계획과 완료 근거다. 현재 후속 실행 순서와 추가 조건의 완료 판단은 위 「추가 요구사항의 후속 실행 계획」을 따른다.

기존 스킬의 조사 순서와 답변 기준을 보완하는 작업에 착수할 수 있다. 설계 스킬은 현재 요구사항의 누락과 작업 대상을, 코딩 스킬은 실제 파일과 작성 방법 및 기술적 위험을 설명하도록 연결한다. 지침 반영과 실제 사용 효과는 따로 확인한다.

## 기준과 유지할 동작

이번 계획의 기준은 [요구사항](./requirements.md)의 「이름과 호출 안내」, 「개선할 동작」, 「이번 조사의 완료 조건」과 「구현 가능성 판단과 계획」이다. [구현 가능성 검토](./references/readiness-and-technical-discovery.md#구현-가능성-검토와-대안-비교)에서 비교한 방법 중 기존 절차와 답변 기준을 연결하는 방식을 사용한다. 계획에서 선택한 작성 방법을 별도의 승인된 요구사항으로 취급하지 않는다.

다음 기존 요구사항도 적용하며, 같은 뜻의 조건을 여러 파일에 복제하지 않는다.

- [설계 스킬 요구사항 전체](../flexible-designs-4f8c/requirements.md): 최소 작성, 빈 문서 준비, 기존 문서 재사용, 의미 보존과 제안 분리 및 결정과 계획 연결을 유지한다.
- [코딩 스킬 요구사항 전체](../task-pattern-guidance-4ffad1/requirements.md): 지정 파일 기록, 파일 미지정 시 후보 제안, 구현 및 측정 권한 구분, 원리와 대안 조사, 판단에 맞는 예시, 근거가 있는 이력 설명과 재개 절차를 유지한다.
- [개발 지침](../../dev/README.md): 요청에 맞는 조사와 확인 방법을 선택한다. 실행 프로그램과 의존성을 바꾸지 않으므로 MJS 개발 지침은 이번 스킬 문구 보완에 적용하지 않는다.

계획의 첫 커밋 전에는 검토한 현재 파일을 임시 기준으로 삼는다. 이후에는 이 계획을 마지막으로 수정한 커밋의 요구사항과 적용 지침을 기준으로 변경 영향을 비교한다. 구현 시작 전에 아직 커밋하지 않은 선행 변경과 이 계획을 구분해 확인한다.

## 변경할 파일과 이유

스킬 본문과 호출 정보는 영어로 유지한다. 아래 파일을 보완하고 새 실행 프로그램이나 스킬을 추가하지 않는다.

- `skills/use-flexible-design/SKILL.md`: 내용 판단이 필요한 요청에서 누락 조사와 착수 판단을 작업 선택에 포함하고, 첫 실질 답변에 담을 판단을 정한다.
- `skills/use-flexible-design/references/requirements/workflow.md`: 요구사항 보존 및 비교 단계에 누락 조사를 연결한다. 조사 제안은 작성 권한과 별개임을 유지한다.
- `skills/use-flexible-coding/SKILL.md`: 조사 대상을 발견하는 순서와 실제 파일, 원리, 작성 방법 및 착수 판단의 연결을 보완한다. 기존 문단을 대체해 같은 의무를 중복 추가하지 않는다.
- 두 스킬의 `agents/openai.yaml`: 본문의 실제 역할에 맞춰 설명과 기본 호출문을 고친다. 기존 필드와 호출 이름은 보존한다.
- `src/AGENTS.en.md`, `src/AGENTS.ko.md`: 두 스킬을 선택할 조건과 독립적인 사용, 개발 지침 적용 및 구현 권한 구분을 같은 의미로 맞춘다.
- `README.md`, `README.ko.md`: 첫 실질 답변에서 제공할 판단과 두 스킬의 차이를 소개한다. 기존 개발 지침 스킬의 파일과 독립 사용 가능성은 유지하되 현재 AGENTS 호출과 혼동되는 설명을 고친다.
- 이 설계 묶음의 조사 자료와 계획: 실제 선택과 미해결 사항이 바뀔 때 갱신한다. 과거 두 계획의 완료 기록은 변경하지 않고 후속 계획을 연결한다.

이름과 이전 호출 참조의 수정은 현재 작업 파일에 이미 반영돼 있다. 구현 단계에서는 이름과 호출 수정을 보존하고 실제 수정 차이를 기준으로 남은 내용을 반영한다. 사용자 환경에 설치된 스킬 사본은 자동으로 바꾸지 않는다.

## 실행 기록

- 착수 조건과 보존 기준: 확인 완료. 현재 변경은 이 설계 묶음의 조사와 계획, 후속 계획 연결 및 이름과 호출 안내 정리다. 기존 요구사항과 실제 구현 권한은 유지하며 추가로 결정할 동작은 발견하지 못했다.
- 설계 스킬 보완: 반영 및 최종 확인 완료. 현재 목표와 대화의 의도 확인, 후속 요청 없이 누락 조사, 제안 분리와 근거가 있는 착수 판단을 연결했다. 빈 파일 및 구조 정리의 예외는 유지한다.
- 코딩 스킬 보완: 반영 및 최종 확인 완료. 실제 입력부터 호출, 처리와 저장 또는 반환을 따라 질문을 찾고 원리, 대안과 파일별 작성 방법 및 착수 판단을 연결했다. 기록 파일이 없어도 대화에서 조사와 설명을 계속하며, 기존 권한과 예시 및 재개 조건은 유지한다.
- 호출 정보와 안내 일치: 반영 및 최종 확인 완료. 두 YAML, 두 언어 AGENTS와 README에 현재 목표와 첫 실질 답변의 판단, 독립적인 스킬 선택, 기록 미지정 시 대화 조사와 구현 권한 구분을 맞췄다. 옛 개발 스킬의 파일과 독립 사용은 유지한다.
- 마지막 확인과 효과 비교: 완료. 문서 및 형식 확인과 수정 전후 6개 요청씩의 답변 비교를 수행했다. 아래 확인 기록과 비교의 한계는 구분해 적용한다.

수정 전 기준은 이 실행 기록과 함께 저장하는 현재 파일이다. 실제 비교를 수행할 때는 Git에 저장한 이전 스킬을 읽어 사용하며, 필요한 임시 사본만 계획에서 정한 위치에 둔다.

### 마지막 확인 기록

현재 요구사항과 최종 본문을 대표 사례에 한 번 대조했다. 아래 내용 확인은 실제 답변 비교와 구분한다.

- `pass`: 설계 스킬의 「Investigate what the current goal needs」와 「Finish」는 현재 목표의 누락 조사, 제안과 확정 요구사항 분리, 근거를 밝힌 착수 판단 및 단순 요청의 예외를 연결한다. requirements workflow는 최소 작성과 의미 보존을 유지한다.
- `pass`: 코딩 스킬의 「Research each task」, 「Explain changes and examples」와 「Return an actionable assessment」는 실제 처리 순서와 파일, 필요한 원리와 대안, 작성 방법과 예시 및 위험을 연결한다. 기존 재개, 이력과 구현 및 측정 권한, 예시와 테스트 판단 조건도 유지한다.
- `pass`: 두 스킬의 YAML을 Ruby 표준 파서로 읽고 이름, 설명과 기본 호출문 및 UI 필드 조건을 확인했다. 두 언어의 안내는 역할과 기록 권한을 같은 의미로 설명한다. AGENTS의 현재 호출에는 이전 이름이 없다.

`Explain changes and examples`에서는 추가, 수정, 분리하거나 유지할 실제 파일과 함수 및 타입, 그 역할과 의존 방향을 제시한다. 구현 방법을 판단하는 요청에서는 코드 예시를 따로 요구하지 않아도 처리 순서와 사용하는 버전 및 기존 타입에 맞는 예시를 포함한다. 파일과 폴더 구성은 실제 위치와 역할로 설명하며 무조건 계층을 새로 만들지 않는다. 변경하지 않는 판단도 이유를 설명한다.

아래 사례는 변경 지침을 확인하고 후속 비교 실행을 설계하기 위한 입력이다. 현재 실행 결과나 새 기능 요구사항이 아니다. 사례마다 현재 자료로 확인할 사실과 사람의 선택이 필요한 조건을 구분한다.

### 충분한 요구사항

현재 설계 스킬의 빈 문서 준비 요구사항과 생성 스크립트를 제시하고 착수 가능 여부 및 보완할 내용을 묻는다. 기존 파일 보존, 생성 결과와 실패 후 상태를 근거로 설명하고, 충분한 조건을 다시 질문하거나 편집 이력 서버 같은 새 기능을 필수 작업에 넣지 않아야 한다.

### 동작을 바꿀 답이 없는 상황

기존 문서에 덧붙일지 새 문서를 만들지 결정되지 않은 입력에 대해 요구사항 정리와 착수 판단을 요청한다. 실제로 같은 목적의 후보가 둘 이상 남을 때에만 차이와 선택할 질문을 제시해야 한다. 그 선택에 의존하는 작성은 멈추되, 영향을 받지 않는 자료 조사까지 일괄 중단하지 않아야 한다.

### 미래 기능이 섞인 상황

빈 요구사항 생성에는 현재 새 폴더 및 빈 파일과 기존 파일 보존이 필요하고, 여러 사용자의 승인 처리는 나중에 검토한다고 명시한 입력을 사용한다. 후자의 기능을 현재 필수 요구사항이나 실행 작업으로 올리지 않아야 한다. 현재 실패 처리 조사까지 미래 기능으로 간주해 생략해서도 안 된다.

### 구체적인 기술 설명과 파일 미지정

이 저장소의 생성기가 기존 파일을 바꾸지 않는 이유, 코드를 어떻게 작성할지와 파일을 나눌 필요가 있는지 설명해 달라고 요청한다. 기록 파일은 지정하지 않는다. 현재 `create.mjs`의 함수, `open`의 `wx`, 동시성 원리와 파일 역할을 조사하고 대화에서 작성 방향을 설명해야 한다. 저장할 후보는 제안하되 파일을 만들지 않으며, 실행하지 않은 예시를 검증 완료라고 표현하지 않아야 한다.

### 조사하지 않은 조건과 부분 착수

배포할 파일 시스템의 종류가 확인되지 않았을 때 기존 생성 방식의 적용 가능성을 묻는다. 로컬 파일 생성에서 확인한 사항과 네트워크 파일 시스템에서 확인할 사항을 구분하고, 그 차이에 의존하지 않는 문서 정리 등의 작업이 있을 때만 일부 착수 가능으로 판단해야 한다. 모든 환경에서 안전하다고 단정하거나 분산 잠금을 자동으로 추가하지 않아야 한다.

### 과도한 분석을 하지 않아야 하는 요청

빈 파일만 준비하는 요청과 스킬 표시 이름만 바꾸는 요청을 사용한다. 요청한 결과와 필요한 제약을 설명하되 전체 아키텍처 조사나 코드 예시, 새 기능 목록을 강제하지 않아야 한다. 최소 작성과 읽기 전용 요청의 권한도 유지해야 한다.

## 중단 조건과 완료 판단

현재 검토에서 스킬 지침 보완을 막는 기술적 조건은 발견하지 못했다. 실제 모델 효과와 모든 위험의 발견은 아직 확인되지 않았다. 다음 조건이 새로 확인되면 영향을 받는 작업을 멈춘다.

- 필수 스킬 또는 참고 자료를 읽을 수 없다.
- 기존 요구사항의 의미, 작성 권한, 데이터 보존이나 지정 파일 조건을 바꿔야 한다.
- 새 실행 도구, 의존성 또는 설치된 스킬 사본 변경이 필요해진다.
- 사람의 선택 없이는 구현할 동작이나 실제 수정 대상을 결정할 수 없다.

완료 보고에서는 지침의 내용 확인, 파일 및 형식 확인, 실제 답변 비교를 구분한다. 지침과 형식을 반영했지만 비교 실행을 못했다면 그 사실을 함께 기록한다. 구현이 끝나지 않은 작업을 문서 작성만으로 완료 처리하지 않는다.
