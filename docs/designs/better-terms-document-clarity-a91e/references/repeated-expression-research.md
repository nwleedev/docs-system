# 반복 표현 탐지와 의미를 보존하는 재작성 조사

`업무`, `지위`, `소비`는 고정 후보에 추가하고, 목록 밖의 반복은 빈도에 따른 별도 후보로 찾는 방향이 적절하다. 두 경우 모두 자동 치환하지 않고 기존 대안 탐색 절차에 연결한다. 한국어 기술 문서에 공통으로 적용할 수 있는 과다 반복 횟수는 이번 조사에서 확인하지 못했다. 따라서 수치는 오류 판정선이 아니라 문맥을 살펴볼 임시 기준으로 제안한다.

이 문서는 [요구사항](../requirements.md)의 반복 탐지 기능을 구체화할 개발자를 위한 자료다. 2026-09-11에 저장소 `89d6f08`의 구현과 아래 1차 자료를 확인했다. 공식 검사기 문서와 소스, 언어 표준, 기술 문서 작성 지침, 어휘 다양성 및 언어 모델 연구를 비교했다. 스킬과 스크립트는 아직 변경하지 않았다.

## 현재 구현과 변경 범위

[`scan.mjs`](../../../../skills/use-better-terms/scripts/scan.mjs)는 같은 입력을 고정 표현 검사와 긴 문단 검사에 전달한다. [`korean-expressions.mjs`](../../../../skills/use-better-terms/scripts/korean-expressions.mjs)는 등록한 표현과 활용 규칙을 찾으며, 임의의 단어가 자주 나오는지를 계산하지 않는다. `업무`는 다른 규칙의 예문에 있지만 세 단어 자체를 탐지하는 규칙은 없다. [`long-paragraphs.mjs`](../../../../skills/use-better-terms/scripts/long-paragraphs.mjs)는 일반 문단의 문장을 세며 어휘 반복을 세지 않는다.

세 고정 후보의 추가는 기존 규칙 자료를 확장하는 일이다. 목록 밖의 반복 탐지는 집계 대상, 단위와 결과 표현을 새로 정해야 한다. 두 변경을 같은 난이도나 같은 파일의 자료 추가로 설명해서는 안 된다. 대안 생성은 이미 [`SKILL.md`](../../../../skills/use-better-terms/SKILL.md)가 맡으므로 별도 재작성 모델이나 네트워크 기능을 스크립트에 넣을 필요는 없다.

## 세 표현은 잘못된 단어가 아니라 문맥 확인 신호다

`업무`가 사람이 맡은 일을 뜻하면 유지할 수 있다. 반면 프로그램이 무엇을 하는지 대신하는 말이면 실제 행동을 찾아 쓴다. 가상의 원문 자료가 파일의 날짜 형식 검사를 설명한다면 “업무를 수행한다”보다 “파일의 날짜 형식을 검사한다”가 구체적이다. 자료가 그 행동을 확인해 주지 않으면 이 문장을 대안으로 확정하지 않는다.

`지위`는 법적 지위처럼 정확한 용례가 있다. 그러나 검토 단계나 승인 여부를 가리킨다면 확인한 상태를 직접 쓴다. 가상의 승인 기록이 아직 검토 중임을 보여 줄 때에는 “문서의 지위는 검토 중이다”를 “문서는 아직 검토 중이다”로 고칠 수 있다. `지위`를 모든 문맥에서 `상태`로 바꾸는 규칙은 만들지 않는다.

`소비`가 무엇의 사용이나 처리를 뜻하는지 구별한다. “이 스크립트가 JSON을 소비한다”가 실제로 파일을 읽어 경고 목록을 만드는 동작을 가리킨다면 그 행동을 적는다. 반면 `전력 소비` 같은 확립된 표현은 유지할 수 있다. 데이터를 읽는 것과 처리 완료를 같은 뜻으로 바꾸어서는 안 된다.

세 후보에는 각각 대상을 구체화하는 질문과 유지할 수 있는 용례를 함께 둔다. 조사 결합형과 파생어의 처리도 구분해야 한다. `업무를`에서 명사를 찾는 것과 `소비자` 전체를 `소비`와 같은 뜻으로 처리하는 것은 다르며, 일부 문자열이 일치했다고 전체 단어의 뜻을 단정하지 않는다.

## 반복 기준에 관한 외부 사례

### 연속 오타와 가까운 문장의 어휘 반복은 다르다

[Vale의 repetition 문서](https://docs.vale.sh/checks/repetition)는 “the the”처럼 연속된 단어를 찾는 내장 규칙을 설명한다. `max` 기본값 0은 첫 반복을 알린다. 이는 오타 탐지 사례이며 문단에서 같은 전문용어를 두 번 쓰지 말라는 기준이 아니다.

[Vale의 occurrence 문서](https://docs.vale.sh/checks/occurrence)는 지정한 범위 안에서 특정 표현의 최소 및 최대 출현 횟수를 설정한다. 문장 안의 쉼표를 세는 예에서 `max: 3`을 사용하지만, 한국어 어휘 과다 사용의 권장값을 제시한 것은 아니다. 두 문서는 조회 시점의 공식 문서이며 페이지의 갱신일은 따로 확인되지 않았다.

[LanguageTool의 AdvancedWordRepeatRule](https://github.com/languagetool-org/languagetool/blob/master/languagetool-core/src/main/java/org/languagetool/rules/AdvancedWordRepeatRule.java)은 같은 문장 안에서 떨어져 있는 반복도 찾는다. 조회한 `master` 소스는 기본 비활성 상태이며, 표제어 정보와 제외 단어 및 품사를 활용한다. 따라서 단순 출현 횟수뿐 아니라 형태와 제외 조건이 구현의 일부다. 이 규칙을 한국어 기술 문서에 그대로 적용할 근거는 없다.

### 어휘 다양성 점수는 문서 길이에 영향을 받는다

2023-07-29 v2의 [Measuring Lexical Diversity in Texts: The Twofold Length Problem](https://arxiv.org/abs/2307.04626v2)은 영어 학습자 글의 세 자료 집합을 분석했다. 길이를 맞추는 방법이 문서 길이 의존 문제를 줄여도, 계산에 사용하는 구간 길이에 대한 민감성은 남았다.

따라서 긴 문서의 총출현 횟수나 서로 다른 단어의 비율만으로 반복을 판정하지 않는 편이 타당하다. 이 논문은 한국어 경고 횟수를 정한 연구가 아니며, 특정 단어가 부적절한지 판단하는 연구도 아니다.

### 여러 문서에서 유난히 자주 쓰는 표현은 별도 문제다

ICLR 2026의 [Antislop](https://proceedings.iclr.cc/paper_files/paper/2026/file/467746c8e15fbfca34dcf23be9ef9229-Paper-Conference.pdf) 3절은 모델별 창작문 2,000개에서 단어와 2~3단어 묶음의 빈도를 사람 글과 비교한다. 일부 문구가 1,000배 이상 자주 나타났다는 결과는 해당 자료와 모델의 관찰이다. 가까운 구간의 반복을 줄이는 방법이 전체 자료의 어휘 편중까지 없애지는 않았다는 결과도 보고한다.

이는 “한 문서 안에서 많이 나온다”와 “많은 문서에서 습관적으로 선택된다”를 구분할 근거다. 사람 글 대비 빈도 비율을 여기서 적용하려면 분야와 언어가 맞는 비교 자료가 필요하다. 이번 개선에는 그런 자료 집합의 구축, 모델 재학습이나 생성 확률 제어를 포함하지 않는다. 단일 파일 스캐너가 장기간의 작성 습관까지 측정한다고 설명하지 않는다.

### 정확한 이름은 반복할 수 있다

Microsoft의 [Word choice checklist](https://learn.microsoft.com/en-us/style-guide/checklists/word-choice-checklist)는 2025-01-08 갱신본에서 “If you mean the same thing, use the same word.”라고 권한다. 같은 개념을 동의어로 번갈아 부르면 서로 다른 개념처럼 읽힐 수 있다.

따라서 반복 후보를 찾았다는 이유만으로 대체 어휘를 강제하지 않는다. 필요한 반복인지 확인한 뒤, 명사만 바꿀지보다 문장에 행동이나 조건을 드러낼 수 있는지를 먼저 판단한다.

## 이 체계에 제안하는 첫 탐지 기준

목록 밖의 반복에는 같은 일반 문단에서 같은 어절이 3회 이상 나타나는 경우를 첫 후보로 제안한다. 두 번의 언급은 설명과 지칭에 흔히 필요하고, 세 번째부터는 문맥을 살펴보게 한다는 운영상 선택이다. 연구로 입증한 최적값이나 채택이 끝난 값은 아니다. 문단 단위를 쓰면 기존 일반 문단 추출 동작을 활용할 가능성이 있고, 서로 다른 절의 횟수를 합쳐 생기는 경고를 줄일 수 있다.

비교한 다른 방법은 문서 전체의 횟수 집계와 최근 5문장 안의 3회 집계다. 전자는 긴 문서의 정상적인 용어 반복을 많이 잡을 수 있고, 후자는 문단을 가로지르는 집계와 겹치는 구간의 처리 규칙이 더 필요하다. 첫 제안은 여러 짧은 문단에 흩어진 반복을 놓친다. 그 누락이 실제 사용에서 문제가 되면 문장 구간 방식으로 확장할 이유가 생긴다. 이 한계는 목록 밖 후보의 탐지 범위이며, 스킬이 문서 전체에서 의미를 판단할 책임을 줄이지 않는다.

어절의 정확한 표기부터 세는 제안은 `검토`, `검토를`, `검토가`를 자동으로 합치지 못한다. [Unicode UAX #29 revision 49](https://www.unicode.org/reports/tr29/tr29-49.html)는 글자, 단어와 문장 분할 기준을 설명하지만 문맥만으로 모든 분할을 확정할 수 없다고 명시한다. [ECMA-402의 Intl.Segmenter](https://tc39.es/ecma402/#sec-intl.segmenter)는 분할 기능이지 한국어 표제어 복원 기능이 아니다. 임의로 어미나 조사를 잘라 서로 다른 단어를 합치는 것보다 놓치는 형태를 명시하는 편이 안전하다. 형태를 합치는 지원 범위는 구현 전에 별도로 결정해야 한다.

새 집계는 코드, URL, 표나 인용문을 일반 산문처럼 세지 않는 방향으로 제안한다. 현재 긴 문단 탐지의 제외 동작을 먼저 확인하고, 새 집계가 원문 위치를 보존할 수 있는 부분만 재사용한다. 기존 고정 표현 탐지의 입력 범위를 함께 줄이지 않는다. 문법 기능어와 관용적인 문장 끝 표현을 제외할 기준도 필요하지만, 자주 나온다는 이유만으로 광범위한 예외 목록을 미리 만들지는 않는다.

경고에는 무엇을 어떤 구간에서 몇 번 셌는지와 원문을 찾을 위치가 필요하다. 같은 문단의 같은 표현을 출현 수만큼 중복 판단하게 만들지 않고 반복 사례를 함께 보여 주는 방향이 적절하다. 이미 고정 후보인 표현이 반복된 경우도 한 번의 문맥 판단에 두 탐지 근거를 연결한다. 판정자는 대체 문장을 만들고 뜻과 정확성을 비교한 뒤 수정하거나 유지 근거를 남긴다.

## 생성 과정에서 확인된 반복 현상과 한계

NeurIPS 2022의 [Learning to Break the Loop](https://arxiv.org/abs/2206.02369v2)는 같은 문장이 이미 여러 번 등장할수록 다시 생성될 확률이 높아지는 현상을 “self-reinforcement effect”라고 설명한다. NeurIPS 2023의 [Repetition In Repetition Out](https://arxiv.org/abs/2310.10226)은 학습 자료의 반복과 생성 반복의 관계를 분석했다. 두 연구는 주로 반복되는 문장과 생성 퇴행을 다루며, 특정 한국어 추상 명사가 많이 쓰이는 원인을 직접 밝혀 준 것은 아니다.

NAACL 2025의 [Repetition Neurons](https://aclanthology.org/2025.naacl-short.41/)는 영어 모델 세 개와 일본어 모델 한 개에서 반복 중 더 강하게 활성화되는 뉴런을 관찰했다. 앞선 내용을 복사하는 동작과 관련된 분석이며, 모델이 어떤 목적을 스스로 선택했다는 증거가 아니다.

어휘 편중에는 더 직접적인 자료도 있다. 앞서 소개한 Antislop은 일관된 글에서도 반복적인 문구 선택이 남는 현상을 다룬다. ACL 2026년 7월의 [More Aligned, Less Diverse?](https://aclanthology.org/2026.acl-long.1803/)는 두 세대 모델의 영어 뉴스 문장을 비교해, 새로운 지시 학습 모델에서 특히 어휘 다양성이 낮은 결과를 보고했다. 다만 세대와 학습 조건이 함께 달라지므로 지시 학습 하나만을 원인으로 확정하거나 현재 스킬에 같은 결과를 일반화하지 않는다.

입력 길이를 관리하는 기술은 이 현상들과 구분해야 한다. Anthropic의 2025-09-29 [Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)은 대화 요약과 중복 자료 제거를 설명하며 지나친 요약이 중요한 세부 정보를 잃을 수 있다고 지적한다. 이는 입력 관리 방법의 설명이지, 모호한 단어를 반복해서 선택하는 동기를 입증한 자료가 아니다.

[Hugging Face의 토큰화 설명](https://huggingface.co/docs/transformers/main/en/tokenizer_summary)은 단어를 하나 또는 여러 부분으로 나누는 방식을 설명한다. 여기서 도출할 수 있는 것은 표현별 토큰 수가 다를 수 있다는 점이다. 같은 단어를 다시 쓴다는 사실만으로 입력 공간이 절약되는 것은 아니다. 더 짧은 표현 선택과 동일 표현의 반복, 요약 중 정보 누락을 하나의 원인으로 묶지 않는다.

현재 확인한 연구는 학습 자료, 생성 방식, 반복의 강화와 어휘 편중을 뒷받침하지만, 이 저장소의 관찰을 특정 자원 절약 동기로 설명할 직접 근거는 찾지 못했다. 개선은 내부 동기를 추정하는 지시보다 실제 출력에 필요한 대상과 행동이 남았는지 확인하는 방식으로 정한다.

## 구현 전에 남은 결정

고정 후보 추가와 대안 탐색은 기존 표현 규칙 및 판정 절차를 활용한다. 목록 밖 집계에는 위 임시 기준의 채택 여부, 형태를 합치는 범위, 제외할 본문 요소와 경고 표시 방식을 결정해야 한다. 외부 패키지 없이 동작한다는 기존 배포 조건을 유지한다.

[출력 구조 유지 결정](../../korean-scanner-coverage-9b4e/decisions/output-structure-and-alternative-search.md)과 [검사기 개발 지침](../../../dev/node/mjs-cli.md)은 현재 두 검사와 세 배포 파일을 전제로 한다. 반복 집계 결과가 이 구조에 들어간다고 미리 단정하지 않는다. 후속 설계에서 기존 결과를 읽는 절차가 반복 후보를 실제로 판단할 수 있는지 확인하고, 구조 변경이 필요하면 해당 결정을 먼저 갱신한다. 이번 문서화로 그 변경까지 승인된 것은 아니다.
