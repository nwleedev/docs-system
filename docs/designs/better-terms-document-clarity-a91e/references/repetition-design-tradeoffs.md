# 반복 검사의 입력, 집계와 전달 방식 비교

반복 집계의 알고리즘과 출력 형식은 현재 구현 범위에서 제외했다. 이 문서는 그전에 비교한 입력 제한, 형태 처리, 계산 비용과 경고 형식을 보존한다. 아래의 선택과 구현 조건은 당시 설계에 관한 분석이며, 현재 실행할 작업은 [요구사항](../requirements.md)과 [계획](../plan.md)을 따른다. 적용 중단 이유는 [결정 이력](../decisions/repetition-aggregation-and-output.md)에 둔다. 빈도 계산과 표현의 의미 판단은 구분한다.

2026-09-11 기준으로 공식 명세, 도구 문서, 연구와 공개 수정 기록을 비교했다. 저장소 코드는 `e6331e6`의 현재 동작을 확인하는 데 사용했다. 아래 비용 분석은 설계 분석이며 구현을 실행해 얻은 시간이나 정확도 측정값이 아니다.

## 입력 상한은 계산 안전성과 판단량을 함께 제한한다

### 서비스 한도와 문서 길이

기존 [입력 크기 조사](repetition-input-size.md)는 10,000자, 20,000자와 50,000자를 비교했다. 조사한 설계 문서 중 13,139자인 파일을 온전히 받을 수 있다는 점은 20,000자를 초기값으로 고를 근거다. 그러나 네 파일의 길이만으로 적정 상한이나 처리 시간을 입증할 수는 없다. LanguageTool의 byte 한도와 ProWritingAid의 기능별 단어 수 한도도 한국어 품질 기준이 아니다.

파일별 20,000자만 제한하면 여러 파일의 총량이 커진다. 실행 전체를 20,000자로 제한하면 묶음을 나누는 수고가 있지만, 반복 계산에 들어가는 원문과 그 원문에서 발생할 경고량을 함께 제한할 수 있다. 파일을 통째로 나누어 실행하면 파일별 빈도는 같지만, 한 파일을 조각내면 분모와 횟수가 달라진다. 자동 분할과 자동 절단은 문서 전체 집계와 양립하지 않는다.

공통 CLI에서 초과 입력을 오류로 거부하면 기존 두 검사까지 실행하지 못한다. 반복 검사만 미실행으로 표시하면 기존 기능을 보존하지만, 이를 경고 없음이나 전체 통과로 오해하지 않도록 상태를 읽는 스킬도 바꿔야 한다. 이 둘의 호환 비용을 비교해 반복 검사만 제한하는 방식을 선택할 수 있다.

### 문자 단위와 사전 확인

[Unicode UAX #29 revision 49](https://www.unicode.org/reports/tr29/tr29-49.html)는 사용자 인식 문자와 코드 포인트가 다르며 글자, 단어와 문장의 분할도 다름을 설명한다. 코드 포인트는 보이는 글자 수와 완전히 같지 않지만, 모델별 토크나이저나 locale별 단어 분리에 의존하지 않는 입력량 단위다. 공백과 Markdown 기호를 빼고 세면 마크업만 큰 입력이 제한을 우회하므로 원문으로 센다.

20,001번째 코드 포인트를 발견하면 초과 여부는 확정된다. 전체를 배열로 펼치거나 분해 정규화한 뒤 길이를 셀 필요가 없다. 원문을 순회하며 상한까지만 세면 사전 확인 비용도 제한된다. 다만 기존 byte 제한과 UTF-8 검증은 이 확인보다 먼저 수행되므로, CLI 전체의 읽기 비용까지 20,000자로 제한됐다고 설명하면 안 된다. decoder가 제거하는 source 맨 앞 BOM과 CRLF의 처리도 단위를 문서화해야 한다.

## 집계가 빨라도 전처리와 인용문 생성은 느릴 수 있다

### 전수 비교, 색인과 근사 집계

N개 토큰의 모든 쌍을 비교하면 비교 횟수가 N의 제곱에 비례한다. 토큰 하나마다 문서 전체에서 출현을 다시 찾는 방법도 서로 다른 토큰이 많을 때 같은 문제가 생긴다. 토큰별 `Map`에 횟수를 더하고 위치를 추가하면 이런 전수 비교가 필요 없다. 입력 길이를 C, 토큰 수를 N, 서로 다른 키 수를 U라 할 때 집계에는 N번의 키 조회와 C에 비례하는 문자열 처리가 필요하다.

[ECMAScript 2026의 Map 명세](https://tc39.es/ecma262/2026/multipage/keyed-collections.html#sec-map-objects)는 평균 접근 시간이 원소 수에 대해 “sublinear”여야 한다고 정한다. 최악 O(1)을 보장하는 규정은 아니다. 따라서 해시 기반 구현에서 기대하는 집계 비용 O(C)는 분석상의 기대값으로 표현해야 한다. 키 길이를 무시하거나 기존 고정 표현 검사 전체도 선형이라고 주장하지 않는다.

정렬 후 같은 토큰을 모으면 일반적인 비교 정렬에서 N log N의 비교가 필요하고 원문 순서도 다시 보존해야 한다. 확률적 빈도 추정과 heavy-hitter 알고리즘은 훨씬 큰 스트림의 메모리를 줄일 때 비교할 수 있지만, 20,000자 입력에서는 정확한 횟수와 모든 출현 위치가 더 중요하다. 외부 저장소, Worker, trie와 확률적 스케치는 추가하지 않는 편이 적절하다.

### 실제 이차 시간 사례

[GitHub Security Lab의 GHSL-2023-031](https://securitylab.github.com/advisories/GHSL-2023-031_cmark/)은 cmark의 시험 revision `7195c67`에서 깊게 중첩한 목록 뒤의 빈 줄마다 중첩을 다시 순회해 이차 시간 동작이 발생했음을 보고한다. 초기 [깊이 제한 제안](https://github.com/commonmark/cmark/pull/475)과 달리, 공식 저장소의 [수정 b69051f](https://github.com/commonmark/cmark/commit/b69051f12a271e6e1fe365b997eb7614e742b73d)는 연속된 빈 줄에서 일찍 반환하도록 계산 자체를 바꿨다. 상한만 두는 방법과 반복 계산을 없애는 방법이 다른 대처임을 보여 준다.

2026-08-05의 [commonmark-java 이슈 447](https://github.com/commonmark/commonmark-java/issues/447)은 닫히지 않은 HTML 시작 표기마다 끝까지 다시 검색하는 문제를 보고한다. 보고자의 시간 측정은 그 구현과 입력에 한정한다. 여기서는 같은 접미 구간을 여러 번 탐색하지 말아야 한다는 알고리즘상 근거로만 사용한다.

[Node.js의 이벤트 루프 안내](https://nodejs.org/en/learn/asynchronous-work/dont-block-the-event-loop)는 입력 상한과 최장 입력 비용 확인을 권하고, 중첩 수량자 정규식 및 JSON 연산의 비용도 설명한다. 웹 서버의 서비스 거부와 로컬 CLI의 지연은 영향이 다르지만, 동기 계산을 `async`로 감싼다고 계산량이 줄지 않는다는 점은 같다.

이 검사에서는 한 방향으로 이동하는 cursor와 종료 위치 색인을 사용한다. 각 여는 기호에서 문서 끝까지 새로 검색하지 않는다. 일치한 표현마다 줄의 처음이나 문서 처음부터 다시 위치를 계산하지 않고, 토큰 추출 때 줄과 UTF-16 열을 기록한다. 문맥 인용은 후보 판정이 끝난 묶음에만 한 번 만든다. 이것은 코드 구현이 아닌 후속 구현의 계산 조건이다.

### 확인해야 할 최악 입력

최대 길이의 한 줄, 모두 다른 토큰, 같은 토큰의 연속, 닫는 기호 없는 backtick과 대괄호, 여러 길이의 backtick, CRLF와 분해 한글을 포함한 입력을 따로 확인해야 한다. 평범한 문서 한 개가 빠르다는 사실만으로 종료성과 증가율을 판단하지 않는다. 5,000자, 10,000자와 20,000자에서 반복 방문 수와 시간 및 메모리 증가를 비교할 수 있지만, 하드웨어에 종속된 밀리초 값을 통과 기준으로 미리 고정하지 않는다. 별도 벤치마크 체계는 필요하지 않으며 기존 자체 검사와 한시적 실행 관찰로 확인할 수 있다.

## 반복 임계값은 길이와 후보 수를 함께 고려한다

횟수만 3으로 정하면 긴 문서에서 정상적인 설명도 많이 걸린다. 비율만 쓰면 짧은 문서의 한두 번 출현이 높은 비율로 보인다. 상위 몇 개만 알리면 순위 밖의 반복을 숨기고, 비교 말뭉치로 상대 빈도를 계산하면 분야와 언어가 맞는 자료를 추가로 관리해야 한다.

[Vale occurrence](https://docs.vale.sh/checks/occurrence)는 지정한 범위의 최소 및 최대 출현 수를 설정하게 하지만 한국어 권장 숫자는 제시하지 않는다. Bestgen의 [어휘 다양성 연구, 2023-07-29 v2](https://arxiv.org/abs/2307.04626v2)는 문서 길이와 계산 구간 길이가 지표에 영향을 준다고 보고한다. 영어 학습자 글의 연구이므로 특정 한국어 단어의 1%가 부적절하다는 근거로 쓰면 안 된다.

출현 3회 이상과 토큰 비율 1% 이상을 함께 쓰는 것은 최소 증거와 문서 내 비중을 요구하는 초기 절충안이다. N이 100이면 3회, 1,000이면 10회, 5,000이면 50회부터 후보가 된다. 각 토큰이 하나의 키에만 속하면 한 파일에서 1% 이상인 서로 다른 후보는 최대 100개다. 이는 수학적인 후보 수 상한이지 문장 품질의 증거가 아니다. 문법 기능어를 미리 대량 제외하지 않고, 한 글자 토큰은 분모에는 넣되 후보에서는 제외하는 방식으로 첫 구현을 제한할 수 있다.

희소하지만 부적절한 표현은 이 기준을 통과하지 못할 수 있다. 고정 후보 `업무`, `지위`, `소비`는 반복 횟수와 무관하게 기존 표현 검사에서 알리므로 두 검사의 목적은 다르다. [Microsoft Word choice checklist](https://learn.microsoft.com/en-us/style-guide/checklists/word-choice-checklist)의 “If you mean the same thing, use the same word.”처럼 정확한 개념 이름의 반복은 필요할 수 있다. 경고는 동의어 교체 명령이 아니다.

## 한국어 형태 합산은 알려진 자료에 한정한다

정확한 표기는 재현하기 쉽지만 조사 결합형을 놓친다. 모든 어절에서 짧은 조사처럼 보이는 끝부분을 자르면 본래 다른 단어까지 합칠 수 있다. 원형이 문서 안에 있다는 조건을 더해도 그 원형과 파생어가 우연히 함께 등장할 수 있어 분석의 근거가 되지 않는다.

[Elastic의 Nori tokenizer 문서](https://www.elastic.co/docs/reference/elasticsearch/plugins/analysis-nori-tokenizer)는 mecab-ko-dic, 사용자 명사 사전, 품사와 복합어 분해 설정을 설명한다. 한국어 형태소 분석에는 그런 언어 자료와 정책이 필요하다는 비교 사례다. 현재 배포 조건은 외부 패키지 없는 Node.js 실행이므로 Nori를 도입하지 않는다. [ECMA-402 Intl.Segmenter](https://tc39.es/ecma402/#sec-intl.segmenter)는 텍스트 분할 API이며 명사 표제어를 보장하는 사전은 아니다. 조회본은 2027 작업 명세로 표시되며 Node.js 22의 구현과 완전히 같다는 뜻은 아니다.

기존 스크립트의 `buildForms()`는 등록 동사와 형용사의 활용형을 만든다. 반면 반환하는 경고는 표제어를 모두 보존하지 않고, 내부 descriptor도 같은 규칙에 속한 해석을 하나로 줄일 수 있다. 반환된 `warnings`를 세는 방식은 이미 생략된 경고 때문에 횟수를 잃을 수 있다. 따라서 반복 키는 경고 배열이 아니라 원래 표제어 자료와 공통 활용 생성 계산에서 만든다. 한 표면형이 여러 표제어에 해당하면 임의로 하나를 고르지 않는 처리가 필요하다.

명사는 `검토`, `업무`, `지위`, `소비`처럼 이번에 필요한 항목만 별도의 명사 표기로 명시할 수 있다. `검토`를 합산용으로 등록하는 것과 문제 표현으로 경고하는 것은 다르다. 사전 전체를 확장하거나 미등록 명사의 어근을 추정하는 일은 포함하지 않는다. [Unicode UAX #15](https://www.unicode.org/reports/tr15/)의 정준 정규화로 완성형과 정준 분해형의 비교 키를 맞추되, 호환 정규화와 원문 수정은 하지 않는다.

## Markdown은 지원할 표기를 명시한다

[CommonMark 0.31.2](https://spec.commonmark.org/0.31.2/)는 같은 길이의 backtick으로 닫힌 코드 구간, 여러 줄 링크와 중첩 등 단순 정규식보다 넓은 문법을 정의한다. [Vale의 구조별 검사 설명](https://vale.sh/features/markup)은 실제 parser로 코드와 링크 주소를 제외한다. parser 없는 문자 검사기를 같은 수준의 Markdown 분석기로 설명해서는 안 된다.

원문 전체를 세면 구현은 쉽지만 예시 코드와 인용이 글의 습관으로 집계된다. 긴 문단 추출기를 그대로 쓰면 목록이 빠지고 `trim()` 때문에 원문 열이 달라진다. 새 범용 parser를 만들거나 외부 패키지를 넣는 대신 반복 검사 전용의 제한된 제외 규칙을 명시하는 것이 현재 조건에 맞다. 제목과 목록은 포함하고, fence, backtick 구간, URL과 표 및 블록 인용처럼 구분 가능한 요소를 제외한다. 복잡한 구문을 정확히 해석했다고 주장하지 않고 보수적으로 줄이나 구간을 제외한 사실을 정책에 공개한다.

이 방식은 일부 산문도 빠질 수 있다. 예를 들어 세로줄이 들어간 문장 전체를 표 후보로 제외하면 실제 표가 아닌 문장도 제외된다. 반대로 일반 따옴표 속의 짧은 인용까지 의미로 알아내지는 못한다. 제외는 반복 검사에만 적용하고 기존 표현 검사가 보던 원문은 그대로 유지해야 한다.

## 경고 형식은 원문 위치와 집계 의미를 보존한다

출현마다 경고를 만들면 같은 판단을 반복하게 된다. 한 묶음에 횟수만 남기면 조사 결합형을 잘못 합쳤는지 확인하기 어렵다. 한 경고에 모든 위치를 담고 인용문은 대표 위치 한 곳에만 두면 양쪽 비용을 줄일 수 있다. 20,000자라는 상한에서는 위치를 먼저 전부 보존하는 방식을 택할 수 있으며, 상한 없이 모든 문맥을 복제하는 경우와 다르다.

[OASIS SARIF 2.1.0, 3.27.22](https://docs.oasis-open.org/sarif/sarif/v2.1.0/os/sarif-v2.1.0-os.html)는 하나의 진단을 이해하는 데 필요한 여러 위치를 담는다. 이는 묶음과 위치를 구분하는 비교 근거다. 같은 명세의 `occurrenceCount`는 같은 진단이 관찰된 횟수를 뜻하므로 단어의 출현 횟수와 동일한 필드 의미로 복사하지 않는다. 이번 변경에 SARIF 전체나 별도 schema 패키지를 도입할 필요는 없다.

현재 `limitCheckByBytes()`는 알려진 다섯 필드만 새 객체로 만들므로 새 상태 필드를 전달받아도 그대로 보존하지 않는다. `checks`에 항목만 추가해서는 미실행 상태를 끝까지 전달할 수 없다. 기존 두 검사의 JSON을 바꾸지 않고 반복 검사의 상태를 유지하도록 조립 단계와 이를 읽는 스킬을 함께 바꿔야 한다.

## 비교에서 남는 불확실성

수치 20,000, 최소 3회와 비율 1%는 초기 동작을 정하는 값이다. 한국어 기술 문서에서의 오탐률이나 개선 효과를 입증한 자료는 없다. 명시적 명사 목록 밖의 조사, 모호한 활용형, 제외된 산문과 여러 단어의 반복 구문도 놓친다. 이러한 제한은 초기 구현에서 의도적으로 남기며, 실제 문서에서 확인한 오탐과 누락이 생길 때 해당 규칙만 재검토한다. 독립적인 스킬 변형이나 비교 말뭉치 구축을 먼저 요구하지 않는다.
