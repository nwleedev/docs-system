# 반복 검사의 입력 크기 기준

한 실행의 원문 합계 20,000 Unicode 코드 포인트와 파일별 독립 집계를 초기 운영값으로 채택했다. 초과 시에는 기존 두 검사를 유지하고 반복 검사의 미실행을 명시한다. 이 문서는 그 결정 전의 입력 상한 비교를 보존한다. 아래의 제안과 당시 미결정 사항은 현재 상태가 아니며, 현재 동작과 변경 이유는 [결정 이력](../decisions/repetition-aggregation-and-output.md), 계산 비용은 [추가 알고리즘 조사](repetition-design-tradeoffs.md)를 따른다. 수치가 연구로 입증된 한국어 품질 기준은 아니다.

2026-09-11에 아래 공식 문서와 연구, 저장소 `e6331e6`의 입력 상수 및 문서 크기를 확인했다. 검사 시간, 경고량이나 의미 판단 정확도를 측정한 실험은 하지 않았다.

## 외부 도구의 한도는 같은 기준이 아니다

[LanguageTool의 HTTP API 안내](https://dev.languagetool.org/public-http-api)는 요청당 텍스트 한도를 `20KB`로 표시한다. 원문 단위를 그대로 기록하며 이를 20,000글자로 바꾸어 해석하지 않는다. 무료 서비스의 처리 한도이며 한국어 반복 판단의 적정 길이를 입증한 자료가 아니다.

[Grammarly의 제한 안내](https://support.grammarly.com/hc/en-us/articles/115000090911-What-are-the-limitations-when-using-Grammarly)는 웹 편집기의 입력 한도를 공백 포함 100,000자로, 업로드 파일 크기를 4 MB 이하로 따로 설명한다. 같은 안내에서도 데스크톱 앱에는 다른 조건을 적용한다. 따라서 서비스의 최대 입력량을 이 검사기의 기본값으로 복사할 근거는 없다.

2026-05-10 갱신된 [ProWritingAid의 입력 길이 안내](https://help.prowritingaid.com/article/161-does-prowritingaid-have-a-word-limit)는 서비스 전체에 하나의 단어 수 상한을 두지 않고, 동의어 검사는 2,000단어, 장별 비평은 4,000단어 등 기능별 조건을 설명한다. 파일이나 장을 나누면 속도와 제안 처리량에 도움이 된다고 안내한다. 2024-08-12의 [Combo Report 안내](https://help.prowritingaid.com/article/156-why-doesnt-my-combo-report-run-on-all-of-my-selected-text)는 여러 검사를 함께 실행할 때 완료 시간을 줄이려고 10,000단어로 제한한다고 설명한다. 새 안내의 서비스 전체 설명과 이전의 특정 기능 제한을 같은 정책으로 합치지 않는다. 두 자료 모두 한국어 어절의 권장 수를 제시한 것은 아니다.

2023-07-29 v2의 [어휘 다양성과 길이 연구](https://arxiv.org/abs/2307.04626v2)는 영어 학습자 글에서 문서 길이뿐 아니라 계산 구간의 길이도 지표에 영향을 준다고 보고한다. 입력에 최대 길이를 두더라도 짧은 글과 긴 글의 빈도 차이가 없어지지는 않는다. 글자 수 제한과 반복 후보 판정식은 별도로 정해야 한다.

외부 자료가 뒷받침하는 것은 처리량과 판단 목적에 맞게 길이를 제한하고 단위를 명시해야 한다는 점이다. 한국어 기술 문서에 공통으로 적용할 최적 상한은 이 자료들에서 확인하지 못했다. 외부 서비스는 비교 근거일 뿐 스크립트의 의존성이나 호출 대상으로 추가하지 않는다.

## 크기를 세는 단위

사람이 입력량을 이해할 기준으로는 Unicode 코드 포인트를 제안한다. 한글 완성형 음절과 보통의 영문자는 각각 하나로 세고, 공백, 줄바꿈과 Markdown 표기도 포함한다. 결합 문자나 분해된 한글은 보이는 한 글자가 여러 코드 포인트일 수 있다. [Unicode UAX #29 revision 49](https://www.unicode.org/reports/tr29/tr29-49.html)의 사용자 인식 문자 단위와 코드 포인트는 구분해야 한다. 이 제안에서는 크기 계산을 위해 원문을 정규화하거나 고치지 않는다.

UTF-8 byte는 읽기와 메모리 보호에 계속 사용한다. [Node.js 22.20.0의 Buffer 문서](https://nodejs.org/download/release/v22.20.0/docs/api/buffer.html#static-method-bufferbytelengthstring-encoding)는 인코딩된 byte 길이와 JavaScript 문자열 길이가 다름을 설명한다. 코드 포인트 수도 기존 원문 위치의 UTF-16 열 번호와 혼용하지 않는다.

어절 수는 반복 비율의 분모 후보지만, 조사와 구두점을 어떻게 처리할지에 따라 달라진다. 모델 토큰 수는 사용하는 토크나이저에 종속된다. 현재는 외부 패키지 없는 스크립트이며 특정 모델도 고정하지 않았으므로 입력 상한에 모델 토큰 환산식을 도입하지 않는 편이 적절하다.

## 저장소 문서와 비교한 상한 후보

현재 `scan.mjs`는 입력 하나당 2 MiB, 전체 32 MiB와 최대 512개 입력을 허용한다. 이는 byte 기준의 실행 제한이며 사람이 반복 후보의 문맥을 판단할 적정 분량이 아니다. 새 문자 수 상한으로 기존 상수를 이미 바꿨다고 설명하지 않는다.

변경 전 원문을 `wc -m`으로 읽은 결과, 이 설계의 `requirements.md`는 3,322자, `repeated-expression-research.md`는 7,078자, `document-comprehension-research.md`는 13,139자였다. 비교한 `docs/dev/node/mjs-cli.md`는 55,817자였다. 이 네 파일의 크기는 해당 문서의 관찰값이며 저장소 전체나 한국어 기술 문서 일반의 분포를 대표하지 않는다.

- 10,000자는 앞의 두 문서를 각각 입력할 수 있지만 13,139자의 조사 문서도 나누거나 거부해야 한다. 판단량을 더 엄격히 제한할 때의 선택이다.
- 20,000자는 세 설계 문서를 각각 온전히 입력할 수 있고, 55,817자의 개발 지침은 제한한다. 완결된 조사 문서를 자주 나누지 않으면서 큰 지침 전체의 일괄 처리를 제한하는 초기 후보로 제안한다.
- 50,000자는 더 긴 문서를 한 번에 처리할 수 있지만, 크기에 비례해 늘어날 수 있는 후보와 문맥을 한 번에 판단해야 한다. 현재 자료만으로 이 정도 입력이 필요하거나 적정하다고 판단할 근거는 부족하다.

한 실행의 합계를 20,000자로 제한하는 안에서는 세 설계 문서의 합계 23,539자를 한 번에 받을 수 없다. 파일을 온전히 유지한 채 두 실행으로 나눌 수 있다. 이보다 파일별 20,000자만 적용하는 안은 묶음 입력을 덜 제한하지만 전체 판단량을 같은 크기로 통제하지 못한다. 어느 적용 단위를 사용할지도 승인 전이다.

## 초과 입력에 관한 당시 제안과 미결정 사항

초과 입력은 자동 절단하지 않고 실패로 알리는 방안을 제안한다. 파일별 집계를 택하면 여러 파일을 나누어 실행해도 각 파일의 전체 빈도는 유지된다. 그러나 한 파일 자체가 상한을 넘으면 파일을 조각내는 순간 집계 대상이 바뀐다. 절별 분석을 명시적으로 허용하거나 상한을 다시 정해야 하며, 조각 결과를 원래 문서 전체의 집계라고 보고하지 않는다.

문자 수 제한을 공통 CLI 입력에 적용하면 현재 byte 제한 안에 있던 큰 파일도 거부하게 된다. 반복 검사에만 적용하고 기존 두 검사를 계속 실행하는 선택은 미실행 반복 검사를 결과에 표시하는 방식이 추가로 필요하다. 어느 쪽도 아직 승인하지 않았다. 기존 두 검사를 정상 실행한 것과 세 검사 전체를 정상 실행한 것을 구별해야 한다.

현재 제안은 문자 수 상한과 원문 전체 보존을 설명한다. 반복 비율을 사용할지, 분모에서 코드와 인용문 등을 뺄지, 최소 출현 횟수를 함께 적용할지, 조사 결합형을 합산할지는 정하지 않았다. 입력량 제한만으로 전문용어의 정상 반복을 걸러내거나 의미 판단을 보장할 수는 없다.
