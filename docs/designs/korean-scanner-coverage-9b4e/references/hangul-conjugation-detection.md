# 한글 활용형 탐지 방법 조사

## 조사 질문

`use-words-review` 검사 스크립트의 literal 음절 매칭이 받침이 붙어 음절이 달라진 활용형을 찾지 못하는 문제를, 외부 패키지 없이 Node.js 표준 기능만으로 해결할 수 있는지 조사했다. 이 조사는 [요구사항의 목표](../requirements.md#목표) 가운데 활용형 탐지 방법에 해당한다. 조사일은 2026년 8월 20일이다.

## 누락 재현

다음 입력을 검사 스크립트의 `--stdin` 모드로 실행했다.

> 검토 범위를 좁힘으로 정리한다. 대상을 좁힐 계획이다. 좁힌 기준을 적용한다. 이슈를 닫힘 상태로 바꾼다. 검토를 닫는다. 작업이 닫혔다.

표현 검사의 `summary.total`은 1이었고, 유일한 경고는 `ko.scope` 규칙의 `범위`였다. `좁힘`, `좁힐`, `좁힌`과 `닫힘`, `닫는다`, `닫혔다`는 경고가 발생하지 않았다.

두 누락의 원인은 서로 다르다. `ko.narrow` 규칙은 존재하지만 literal 표현이 `좁히`와 `좁혀`뿐이어서, 받침이 붙어 마지막 음절이 달라진 형태를 substring으로 찾지 못한다. 반면 `닫다` 계열은 `skills/use-words-review/scripts/korean-expressions.mjs`의 내장 규칙에 해당 규칙 자체가 없다. `닫`은 어간 받침 ㄷ이 첫 음절 안에 유지되므로, 규칙만 추가하면 literal 표현 `닫` 하나로 `닫다`, `닫힘`, `닫힌`, `닫혔다`, `닫는다`를 현재 음절 매칭으로도 모두 찾을 수 있다. 즉 규칙 추가는 [닫다, 닫히다, 좁히다 용법 조사](./close-and-narrow-usage.md)가 다루는 판정 기준의 문제이고, 이 문서는 `좁히다`처럼 어간의 마지막 음절이 변하는 경우의 탐지 방법을 다룬다.

## 음절 매칭이 활용형을 놓치는 이유

한글 완성형 음절 U+AC00부터 U+D7A3은 초성, 중성, 종성이 하나의 코드 포인트로 합쳐져 있다. `좁히`는 U+C881 U+D788이고 `좁힘`은 U+C881 U+D798이므로, 두 문자열은 코드 포인트 수준에서 마지막 글자가 다르다. 음절 단위 substring 매칭은 어간의 마지막 음절에 받침이 붙는 순간 실패한다.

유니코드 표준은 이 완성형 음절을 조합형 자모로 산술 분해하는 알고리즘을 정의한다.

- 완성형 음절은 SBase U+AC00, LBase U+1100, VBase U+1161, TBase U+11A7 상수를 사용한 뺄셈과 나눗셈으로 초성, 중성, 종성 자모로 분해된다.
  - [The Unicode Standard 3.12절 Conjoining Jamo Behavior](https://www.unicode.org/versions/Unicode16.0.0/core-spec/chapter-3/)의 3.12.2 Hangul Syllable Decomposition이 이 산술 분해를 정의한다.
  - [UAX #15 Unicode Normalization Forms](https://unicode.org/reports/tr15/)는 한글 음절의 분해와 조합을 조회 테이블 대신 산술 알고리즘으로 처리하도록 안내한다.

JavaScript에서는 `String.prototype.normalize("NFD")`가 이 분해를 수행한다. Node.js 22에서 직접 확인한 결과는 다음과 같다.

- `좁히`의 NFD는 U+110C U+1169 U+11B8 U+1112 U+1175다.
- `좁힘`의 NFD는 같은 다섯 자모 뒤에 종성 U+11B7이 붙는다. `좁힐`은 U+11AF, `좁힌`은 U+11AB이 붙는다.
- `"좁힘".normalize("NFD").startsWith("좁히".normalize("NFD"))`는 true이며, `좁힐`, `좁힌`, `좁힙니다`, `좁히지`에서도 true다.
- `좁혀`는 중성이 U+1167로 달라 접두 매칭이 성립하지 않는다. 자모 매칭을 채택해도 `좁혀`는 지금처럼 별도 표현으로 유지해야 한다.

따라서 규칙 표현과 원문을 모두 NFD로 분해한 뒤 자모열 접두 매칭을 수행하면, 받침이 붙은 활용형을 표현 열거 없이 찾을 수 있다.

## 자모 접두 매칭의 주의점

같은 검증에서 다음 제약을 확인했다.

- **복합 받침은 원자적 자모다.** NFD에서 ㄻ은 U+11B1, ㄺ은 U+11B0 하나의 코드 포인트다. `살`의 자모열은 `삶`의 접두가 아니다. 복합 받침으로 확장되는 활용형까지 잡으려면 종성 자모를 다시 나누는 테이블이 별도로 필요하다.
- **매칭이 음절 중간에서 끝날 수 있다.** `가`의 자모열은 `값`의 접두로 매칭된다. 받침 없는 음절로 끝나는 짧은 표현일수록 무관한 단어의 음절 내부를 잡을 위험이 커진다. `좁히`는 해당 자모열로 시작하는 다른 일반어가 확인되지 않아 위험이 낮지만, 규칙마다 오탐 위험을 따로 평가해야 한다.
- **오프셋 매핑이 필요하다.** NFD 문자열의 인덱스는 원본 UTF-16 인덱스와 다르다. `범위를 좁힙니다`는 원본 8자, NFD 19자였고 매칭이 `좁힙`의 음절 중간에서 끝났다. 현재 경고가 제공하는 `startUtf16`과 `endUtf16`을 유지하려면 원본 문자별 NFD 길이로 매핑 테이블을 만들고, 음절 중간에서 끝난 매칭을 그 음절의 끝으로 올림 처리해야 한다.

## 형태소 분석기와 표준 기능 비교

형태소 분석기는 어간과 어미를 사전으로 분리하므로 활용형 문제를 근본적으로 다루지만, 모두 외부 실행 환경이나 대용량 자료가 필요해 외부 패키지 없이 실행해야 하는 현재 배포 조건과 충돌한다.

- [Kiwi](https://github.com/bab2min/Kiwi)는 C++ 라이브러리이며 모델 파일을 Git LFS로 배포한다.
- [mecab-ko-dic](https://bitbucket.org/eunjeon/mecab-ko-dic/raw/master/README.md)은 MeCab 포크의 설치와 사전 컴파일이 필요하다.
- [Open Korean Text](https://github.com/open-korean-text/open-korean-text)는 JVM에서 실행되는 Scala 라이브러리다.

Node.js가 내장한 `Intl.Segmenter`는 대안이 아니다. [MDN의 Intl.Segmenter 문서](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/Segmenter)는 locale 기반 텍스트 분할을 설명할 뿐 형태소 분석을 제공하지 않으며, [ECMA-402](https://tc39.es/ecma402/#segmenter-objects)의 규범 참조도 UAX #29 계열 경계 분할이다. 한국어 단어 분할은 대체로 어절 단위로 나오므로 `좁힙니다`에서 `좁히`를 분리하지 못한다.

자모 분해 후 문자열 매칭 자체는 한국어 소프트웨어에서 확립된 기법이다. 초성 검색과 자동완성에 쓰이는 [es-hangul](https://github.com/toss/es-hangul)과 [Hangul.js](https://github.com/e-/Hangul.js)가 자모 분해 API를 검색 용도로 제공한다. 두 라이브러리는 외부 패키지라 의존할 수 없지만, 표준 내장 `normalize("NFD")`만으로 같은 분해를 얻을 수 있음을 위 검증에서 확인했다.

## 결론과 제안

다음은 조사 결과에서 도출한 제안이며 승인된 결정이 아니다.

NFD 자모열 접두 매칭이 현재 배포 조건 안에서 활용형 누락을 없앨 수 있는 방법으로 확인됐다. 다만 모든 규칙에 일괄 적용하면 짧은 표현의 오탐이 늘 수 있으므로, 규칙마다 음절 매칭과 자모 매칭 가운데 하나를 선택하게 하는 방안과 활용형을 표현 목록에 열거하는 기존 방식(`좁힘`, `좁힐`, `좁힌`을 `expressions`에 추가)을 함께 비교해야 한다. 열거 방식은 구현 변경이 없지만 새 활용형이 나타날 때마다 목록을 갱신해야 하고, 자모 매칭은 갱신 부담이 없지만 오프셋 매핑과 오탐 평가가 필요하다. 어느 방식을 채택할지는 [요구사항의 미해결 질문](../requirements.md#미해결-질문)대로 결정 소유자가 판단한다.

## 한계

- ECMA-402에서 경계 결정 함수의 규범 문구 원문은 확인하지 못했고, 규범 참조 목록에 UAX #29가 포함된 사실까지 확인했다.
- `좁히` 자모열로 시작하는 다른 한국어 단어의 사전 전수 조사는 수행하지 않았다.
- 검증은 macOS의 Node.js 22에서 수행했으며 다른 운영체제 동작은 확인하지 않았다.
