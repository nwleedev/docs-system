# 작업별 패턴 기록의 근거와 구체화 제안

## 조사 목적과 현재 판단

[요구사항](../requirements.md)의 별도 기술 가이드 파일을 생성하지 않는 조건을 유지하면서, 필요한 기술 판단을 작업 기록에 남기고 압축 뒤에도 활용하는 방법을 비교한다. 이 문서는 요구사항을 구체화할 사람을 위한 자료다. 아래 제안과 예시는 확정한 요구사항이나 구현 계획이 아니다.

현재 자료는 지침의 존재, 에이전트가 읽은 내용, 실제 구현을 구분할 필요가 있음을 보여준다. 특정 기록 방식을 사용하면 필요한 패턴을 항상 파악하고 계속 지킬 수 있다는 근거는 확보하지 못했다.

## 전환 전 스킬에서 확인한 동작

2026년 10월 29일 [전환 전 스킬](../../../../skills/use-dev-guidance/SKILL.md)의 기준 문서 선택, 작업 선택과 종료 절차를 확인했다. 스킬은 `docs/dev/README.md`를 기준으로 삼고, 기준 문서가 없으면 생성 승인 절차를 거친다. 문서 작성 외에도 현황 파악, 조사, 도구 비교, 승인된 변경의 적용과 검증을 작업으로 열거한다.

전환할 이름과 역할은 [스킬 이름과 역할 요구사항](../requirements.md#스킬-이름과-역할)에 따른다. 위 링크는 기존 동작의 근거이며 새 이름으로의 전환을 완료했다는 뜻은 아니다.

새 방안에서 기존의 조사, 적용과 검증 절차를 얼마나 유지할지는 별도 선택이 필요하다.

[개발 지침 기준](../../../dev/README.md#find-and-apply-guidance)은 현재 코드와 지침을 대조하도록 한다. 같은 문서의 유지보수 절은 지침이 설명하는 기술과 근거가 바뀔 때 다시 확인하고, 반복 위반 중 기계적으로 확인할 수 있는 규칙은 도구 검사로 옮기도록 한다. 이 규칙들이 적혀 있다는 사실은 실제 장기 작업에서 지켜졌다는 증거가 아니다.

## 외부 사례에서 확인한 사실

아래 자료는 모두 2026년 10월 29일에 확인했다.

### 명시적인 사용 지시와 문서 색인을 비교한 평가

[Vercel의 Next.js 평가](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)는 스킬만 제공한 조건의 통과율을 53%, 스킬 사용을 명시한 조건을 79%, 압축한 문서 색인을 `AGENTS.md`에 넣은 조건을 100%로 보고했다. 스킬만 제공한 조건에서는 사례의 56%에서 스킬을 호출하지 않았다.

이는 문서를 읽을 수 있는 상태와 실제로 읽는 행동이 다를 수 있다는 근거다. Next.js 16 API를 대상으로 한 자체 평가이므로 모든 기술, 에이전트와 장기 작업에서 같은 효과가 난다는 뜻은 아니다. 문서 전체를 계획에 복사하는 방법을 평가한 자료도 아니다.

### 재개에 필요한 내용을 계획 안에 기록하는 예시

[OpenAI Cookbook의 ExecPlan](https://developers.openai.com/cookbook/articles/codex_exec_plans)은 계획만으로 작업을 재개할 수 있도록 필요한 지식, 변경 대상과 구현 뒤 확인할 동작을 포함하고 진행에 따라 갱신하도록 한다. 필요한 지식을 외부 문서 참조에만 맡기지 말라는 지침도 포함한다.

이는 작업 기록에 적용할 판단을 직접 남기는 방식의 사례다. 모든 프로젝트가 같은 계획 양식을 사용해야 한다거나 모든 패턴 설명을 반복해서 적어야 한다는 근거로 사용하지 않는다.

### 참조와 실제 문맥 포함의 차이

[Cursor의 규칙 문서](https://cursor.com/docs/rules#referencing-files-from-a-rule)는 규칙에서 파일을 언급해도 그 파일 내용이 프롬프트에 자동으로 포함되지 않으며, 에이전트가 필요할 때 도구로 읽는다고 설명한다. 항상 문맥에 필요한 내용은 규칙 본문에 적으라고 안내한다.

이는 링크만 있는 기록으로 충분한지 별도로 판단해야 한다는 근거다. 특정 도구의 규칙 전달 방식이므로 다른 도구의 컨텍스트 압축과 복구 동작까지 설명하지는 않는다.

## 구체화 제안

### 기록할 파일의 후보 제안

파일 지정 여부에 따른 작성 시점은 [요구사항의 기록 위치 규칙](../requirements.md#프로젝트에-따른-기록-위치)을 따른다. 파일이 지정되지 않았을 때는 프로젝트에서 정한 기록 위치와 실제로 후속 작업에 사용하는 기존 기록을 후보로 조사하는 방안을 제안한다. 후보를 제안할 때 선택 이유와 내용을 추가할 절을 함께 설명하면 작성 대상을 결정하기 쉽다.

계획이 아닌 이슈 본문이나 다른 작업 기록에도 적용할 수 있지만, 외부 서비스 수정 권한까지 생기는 것은 아니다. 기존 기록을 고칠 수 없을 때는 대화에 반영안을 제시하는 방안과 대상이 정해질 때까지 기록을 보류하는 방안을 비교해야 한다.

### 패턴 이름보다 적용할 행동을 기록

목적 파악과 프로젝트에 맞는 코드 예시는 [작업별 판단](../requirements.md#작업을-기준으로-기술-판단-기록)과 [코드 예시 조건](../requirements.md#프로젝트에-맞는-코드-예시)에 따른다. 추가로 피하려는 실패, 적용 조건, 판단 근거와 확인 방법을 남기는 방안을 제안한다. 같은 작업의 공통 조건은 한 번 설명하고 절차별로 다른 판단을 적되, 재개할 때 필요한 내용이 연결만 남아 사라지지 않도록 한다.

예를 들어 컴포넌트를 합성하는 절차에서는 패턴 이름만 적는 대신, 정적인 화면 조각은 `children`으로 조합하고 각 항목의 값을 전달해야 하는 렌더링은 별도로 판단한다는 설명을 남길 수 있다. 이 예시는 기록의 구체성을 설명할 뿐, 모든 프로젝트에 이 작성 방식을 요구하지 않는다.

### 조사할 문제를 작업에 연결

절차별 변경 대상, 사용하는 기술과 버전, 다른 코드와 연결하는 부분, 유지할 동작을 바탕으로 조사할 문제를 정하는 방안을 제안한다. 이 문제 목록과 실제 패턴 기록을 대조하면 무엇을 조사했고 무엇이 남았는지 확인하기 쉽다.

모든 이론적 디자인 패턴을 나열하는 방식은 현재 작업과 무관한 내용을 늘릴 수 있다. 특정 절차에 별도 패턴이 필요하지 않다는 판단과, 조사했으나 판단하지 못한 상태를 구분할지도 정해야 한다. 기록 개수나 분량만으로 누락이 없다고 판단하지 않는다.

### 압축 뒤 재개하는 동작을 평가

압축 전 대화 없이 작업 기록만 전달하고, 다음 작업에 필요한 패턴과 금지할 안티패턴을 설명하게 하는 평가를 제안한다. 기록에 필요한 내용이 있어도 읽지 않는 경우와, 읽었지만 필요한 내용이 빠진 경우를 구분한다.

계획의 모든 절차를 한꺼번에 전달하는 방식과 다음 절차에 필요한 부분을 전달하는 방식은 읽는 양과 누락 위험이 다를 수 있다. 어느 방식으로 재개할지, 설명의 일치뿐 아니라 실제 작업 반영까지 평가할지 정해야 한다. 평가 자동화나 별도 테스트 코드 작성은 이 제안만으로 확정하지 않는다.

### 기존 지침과 달라진 상황의 처리

기존 `docs/dev`는 참고 근거로 읽되, 이번 작업의 코드와 버전에 맞는지 확인한 뒤 기록에 반영하는 방안을 제안한다. 새 방안만을 이유로 기존 문서를 삭제하거나 내용을 자동 이전하지 않는다.

변경할 대상, 기술 버전 또는 패턴의 근거가 바뀌면 영향을 받은 작업 기록을 다시 확인하는 방안도 제안한다. 패턴 조사의 재사용 조건과 갱신 시점은 아직 정하지 않았다.

## 목적에 맞는 코드와 테스트를 위한 추가 제안

다음 제안은 [테스트 대상과 목적](../requirements.md#테스트-대상과-목적)을 구체화하고, 코드 작성 규칙의 적용 조건을 판단하기 위한 것이다. 특정 프레임워크의 규칙을 모든 프로젝트의 요구사항으로 채택한 것은 아니다. 아래 공식 자료도 2026년 10월 29일에 확인했다.

### 테스트가 발견해야 할 실패를 먼저 설명

테스트마다 정상 동작, 막으려는 실패, 기대하는 관찰과 그 관찰을 확인할 검증문을 연결하는 방안을 제안한다. fixture나 mock은 이 실패를 재현하는 데 필요한 값과 외부 의존성을 설명하도록 한다. 테스트할 동작까지 가짜 구현으로 바꾸고 그 가짜 구현만 검사하는 예시를 걸러내려는 목적이다.

[Testing Library의 원칙](https://testing-library.com/docs/guiding-principles/)은 실제 사용하는 방식과 가까운 테스트를 지향하며, 컴포넌트 인스턴스보다 DOM을 조작하고 관찰하도록 한다. [Playwright의 권장 방식](https://playwright.dev/docs/best-practices#test-user-visible-behavior)도 내부 함수 이름이나 CSS 클래스보다 사용자가 관찰하는 동작을 검사하도록 한다. 두 자료는 UI 테스트 예시의 판단 근거이며, 모든 백엔드 테스트를 브라우저로 확인하라는 근거는 아니다.

### 테스트 필요성과 TDD 선택을 구분

테스트를 사용해야 하는 이유와 사용할 테스트의 기록은 [테스트 대상과 목적 요구사항](../requirements.md#테스트-대상과-목적)에 따른다. 추가로 확인할 동작과 실패를 먼저 정하고, 그다음 테스트를 먼저 작성할지와 어떤 도구로 확인할지를 판단하는 방안을 제안한다. TDD라는 이름이나 브라우저 테스트 실행 자체가 테스트의 목적을 대신하지 않도록 한다.

문서에 담을 테스트 예시와 실제 테스트 파일 작성도 구분해야 한다. 예시가 있다는 사실만으로 실행을 통과했다고 표현하지 않으며, 예시의 실행까지 요구할지는 별도로 정한다. 테스트 수나 코드 줄 수를 늘리는 일을 완료 기준으로 삼지 않는 방안도 검토할 수 있다.

### 프로젝트에 맞는 예시의 판단 기준

예시가 사용할 기술 버전, 타입, 모듈 구성과 호출 관계를 프로젝트에서 확인하는 방안을 제안한다. 기존 코드는 이 조건을 파악할 자료로 사용하고, 가까운 코드의 작성 방식을 그대로 권장 예시에 복제하지 않는다. 실제 프로젝트에 연결하는 데 필요한 준비와 아직 정하지 않은 전제를 밝히면 독자가 적용 가능성을 판단하기 쉽다.

코드의 변경 방식과 추가하지 않는 이유는 [작업별 기술 판단 요구사항](../requirements.md#작업을-기준으로-기술-판단-기록)에 따른다. 더 구체적으로는 새 fixture, 객체, 스크립트와 공통 컴포넌트를 만드는 이유를 설명하는 방안을 제안한다. 무조건 공통화하는 방식도 다른 책임을 억지로 묶을 수 있으므로 대안 중 하나로 비교한다.

### 코드 형태의 금지와 막으려는 문제를 구분

모듈 표기 규칙은 타입 사용과 실제 실행 방식을 함께 확인하도록 제안한다. [TypeScript의 모듈 문서](https://www.typescriptlang.org/docs/handbook/modules/reference.html#file-extension-substitution)는 `.js`로 지정한 import를 `.ts` 파일로 해석할 수 있음을 설명한다. 같은 문서의 확장자 없는 상대 import 설명은 Node.js ESM과 bundler의 허용 조건이 다름을 보여준다. `.js` 표기만으로 JavaScript로 작성했거나 타입을 생략했다고 판단할 수는 없다.

기존 프로젝트가 확장자를 생략하도록 정했다면 그 규칙과 실행 설정을 확인하고, 둘이 충돌하면 조용히 어느 쪽을 바꾸지 말고 차이를 제시하는 방안을 제안한다. kebab-case 파일명과 사용하지 않을 역할 이름도 프레임워크의 보편 규칙이 아니라 프로젝트에서 정한 작성 규칙으로 구분할 수 있다.

순환 의존성을 피하려는 목적과 `forwardRef()`라는 해결 수단도 구분할 수 있다. [NestJS의 순환 의존성 문서](https://docs.nestjs.com/fundamentals/circular-dependency)는 순환 의존성을 가능한 한 피하되, 남아 있는 순환 참조를 해결하는 수단으로 forward reference와 `ModuleRef`를 설명한다. 프로젝트가 `forwardRef()`를 금지했다면 오류를 우회하는 예시 대신 의존 방향을 바꾸는 대안을 조사하는 방안을 제안한다. 프레임워크가 제공하는 수단과 프로젝트에서 허용한 수단을 구분하려는 목적이다.

### 조사 자료의 재사용과 파일 작성 조건

수집한 자료를 저장할 곳을 정할 때는 [자료 기록 요구사항](../requirements.md#수집한-자료의-기록-위치)을 따른다. 반복 조회를 줄이려면 조회한 기술과 버전, 자료가 설명하는 문제, 다시 사용할 수 있는 조건도 확인하는 방안을 제안한다.

임시 파일 저장도 파일 작성이므로 기록할 파일을 지정받는 조건과 함께 판단한다. 저장소에 자료 기록 규칙이 없을 때 무엇을 제안할지, 저장한 자료를 언제 다시 확인하거나 버릴지는 아직 정하지 않았다.

## 재개와 조사 완료를 위한 선택지

아래 선택지는 확정한 요구사항이 아니다. 추천도 제안이며, 선택 전에는 요구사항이나 실행 계획으로 옮기지 않는다. 모든 선택지는 스킬 전용 파일을 생성하지 않는 조건과 [실제 소스 변경 조건](../requirements.md#스킬-이름과-역할)을 유지한다.

### 컨텍스트 압축에 관한 근거

2026년 10월 29일에 확인한 [Anthropic의 컨텍스트 관리 설명](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)은 압축 과정에서 중요한 맥락이 빠질 수 있으며, 외부에 보존한 정보를 나중에 다시 읽는 방법을 설명한다. 이는 보존과 재읽기가 서로 다른 작업이라는 근거다. 스킬이 모든 실행 도구의 압축 시점을 감지할 수 있다는 근거는 아니다.

[도구의 hooks 문서](https://code.claude.com/docs/en/hooks#postcompact)는 압축 전후 이벤트의 사례를 제공하지만, 압축 뒤 이벤트에서 전달할 수 있는 정보와 제어에는 제한이 있다. 특정 이벤트가 존재한다는 사실만으로 그 이벤트에서 읽기 지시를 모델에 주입할 수 있다고 가정하지 않는다. [Cursor의 파일 참조 설명](https://cursor.com/docs/rules#referencing-files-from-a-rule)도 파일 언급과 실제 내용 읽기를 구분한다. 이 도구별 설명을 다른 도구에 그대로 적용하지 않는다.

### 작업 기록을 다시 읽는 시점

#### 압축 또는 재개를 인지했을 때만 읽기

압축 안내나 재개 지시가 있으면 지정된 작업 기록에서 현재 절차와 기술 판단을 읽는다.

- 장점: 평소 반복해서 읽는 양이 적고, 기존의 재개 프롬프트와 연결하기 쉽다.
- 단점: 압축 사실이 전달되지 않거나 재개 지시가 빠지면 다시 읽지 않을 수 있다.

#### 작업 단위 시작 시 읽기

스킬로 작업을 시작하거나 재개할 때와 다음 절차를 시작할 때, 기존에 지정된 기록에서 필요한 부분을 읽는다. 압축을 감지했는지는 재읽기의 필수 조건으로 삼지 않는다.

- 장점: 압축이 언제 일어났는지 몰라도 다음 작업 단위에서 판단을 다시 확인할 수 있다. 도구별 이벤트나 전용 파일이 필요하지 않다.
- 단점: 읽기 비용이 반복되며, 한 절차가 길어지면 그 중간의 압축에는 바로 반응하지 못한다. 스킬이 다시 적용되거나 기존 프로젝트 지침이 이 재개 행동을 전달해야 한다.

현재 조건에는 작업 단위 시작 시 읽기를 추천한다. 필요한 부분만 읽되 현재 목적, 변경 판단과 적용할 예시를 함께 찾는 방식이 적합한지 실제 재개 사례로 확인해야 한다.

#### 실행 도구의 이벤트와 연결

기존 실행 도구가 제공하는 압축 또는 재개 이벤트에서 작업 기록을 다시 찾도록 안내한다. 기존 프로젝트 설정이 있는 경우 활용 가능성을 조사하되, 새 설정 추가나 변경을 이 선택만으로 실행하지 않는다.

- 장점: 모델이 스스로 압축을 인지하는 데 대한 의존을 줄일 수 있다. 작업 단위 시작 시 읽기와 함께 사용할 수도 있다.
- 단점: 이벤트와 지시 전달 방식이 도구마다 다르고, 설정 관리와 별도 동작 확인이 필요하다. 모든 환경의 공통 필수 조건으로 삼기는 어렵다.

### 조사를 끝낼 기준

#### 모든 작업에 같은 조사 항목 적용

각 작업에서 목적, 변경 대상, 기술 버전, 적용 조건, 피할 실패와 확인 방법을 모두 조사하고, 근거를 찾지 못한 항목은 미해결로 표시한다.

- 장점: 조사 누락을 대조하기 쉽고 작업 사이의 판단 기준이 일정하다.
- 단점: 코드 변경이 없는 절차나 단순한 수정에도 같은 조사 비용이 든다. 항목을 채우기 위한 무관한 설명이 늘어날 수 있다.

#### 공통 확인 뒤 실패 영향에 따라 추가 조사

먼저 작업 목적, 변경 대상과 기술 버전을 확인한다. 나머지는 그 작업에서 발생할 수 있는 실패와 영향에 따라 조사하며, 조사할 문제와 미해결 사항을 기존 기록에 남긴다. 확인하지 않은 내용을 해결한 것으로 취급하지 않는다.

- 장점: 실제 작업에서 필요한 문제에 조사를 집중할 수 있고 반복 조사 비용을 줄일 수 있다.
- 단점: 처음에 실패를 빠뜨리면 조사도 빠질 수 있다. 무엇을 추가 조사할지 판단하는 기준이 필요하다.

실패 영향에 따라 추가 조사하는 방식을 추천한다. 비용, 보존할 동작과 불확실성이 큰 판단을 우선하되 근거를 찾지 못했을 때 영향을 받는 판단을 보류할지까지 함께 정해야 한다.

### 코드 예시와 테스트의 확인 수준

#### 문서와 프로젝트 근거 대조

기술 버전, 타입, 호출 관계와 프로젝트 규칙을 대조하고, 테스트 예시가 대상 동작과 기대하는 관찰을 연결하는지 읽어서 확인한다. 실행하지 않은 예시는 실행 미확인으로 구분한다.

- 장점: 실제 소스나 테스트 파일을 바꾸지 않고 적용할 수 있다. 실행 환경이 없는 작업에도 예시를 제시할 수 있다.
- 단점: 구문, 타입과 실행 문제를 모두 발견할 수는 없으며 테스트가 실패를 잡는다는 실행 증거도 없다.

#### 허용된 기존 검사까지 추가

문서와 프로젝트 근거 대조에 더해, 실행 권한과 기존 검사 환경이 있는 부분은 프로젝트가 정한 검사로 확인한다. 예시를 확인하려고 새 소스나 테스트 파일을 만들지는 않는다. 실행할 수 없거나 추가 개발이 필요한 부분은 그 이유와 미확인 사항을 밝힌다.

- 장점: 적용할 수 있는 부분은 실행 근거를 추가하면서도 스킬의 기본 작업을 예시 작성으로 유지한다.
- 단점: 확인할 수 있는 정도가 프로젝트마다 다르다. 기존 검사가 새 예시를 실제로 검사했는지 따져야 하며, 기존 검사 통과를 예시 전체의 통과로 확대하면 안 된다.

허용된 기존 검사까지 추가하는 방식을 추천한다. 모든 예시의 실행 확인을 필수로 요구하면 개발 명령이나 환경이 없는 경우 예시 작성 자체를 완료하기 어려워질 수 있다.

### 파일을 기록할 수 없거나 기준이 충돌할 때

#### 영향을 받는 판단을 보류

지정 파일이 없거나 수정할 수 없으면 기록 작업을 보류한다. 저장소 규칙과 조사 근거가 충돌하면 영향을 받는 판단을 보류하고 필요한 선택을 설명한다. 영향을 받지 않는 읽기와 조사는 이어갈 수 있다.

- 장점: 의도하지 않은 위치에 기록하거나 미정인 선택을 확정하는 일을 막을 수 있다.
- 단점: 보류한 기록이나 판단은 답변을 받기 전까지 완료할 수 없다.

#### 대화에 반영안 제시

파일은 바꾸지 않고 작성할 내용, 후보 위치와 충돌하는 선택지를 대화에 제시한다. 선택되지 않은 방안을 구현 입력으로 취급하지 않는다.

- 장점: 파일을 기록할 수 없어도 검토할 수 있는 내용을 전달할 수 있다.
- 단점: 대화만 남으면 다음 세션에서 찾기 어려우며, 파일에 반영하는 후속 작업이 필요하다.

두 방식을 함께 쓰는 것을 추천한다. 영향을 받는 파일 변경과 판단은 보류하고, 대화에는 선택에 필요한 반영안을 제공한다.

### 기존 개발 지침을 취급하는 방법

#### 기존 지침을 먼저 읽고 현재 근거와 대조

프로젝트가 지정한 기존 개발 지침을 읽고 코드와 버전에 맞는지 확인하여 필요한 판단에 사용한다. 오래된 내용이나 충돌은 별도로 알리며 문서를 자동으로 이전하거나 삭제하지 않는다.

- 장점: 프로젝트에서 정한 이유와 예외를 놓칠 가능성을 줄인다.
- 단점: 오래된 지침을 읽고 대조하는 비용이 남으며, 기존 지침이 지나치게 크면 읽는 양이 늘어난다.

#### 필수 지침 외에는 필요한 내용만 검색

프로젝트가 반드시 읽도록 정한 자료는 따르되, 그 외 개발 지침은 현재 작업에 필요한 부분만 찾는다. `docs/dev` 전체를 새 스킬의 고정 입력으로 삼지 않는다.

- 장점: 프로젝트별 기록 구조를 유지하면서 무관한 지침을 읽는 양을 줄일 수 있다.
- 단점: 적용할 자료를 찾는 설명이 부족하면 필요한 규칙과 예외를 놓칠 수 있다.

필수 지침 외에는 필요한 내용만 검색하는 방식을 추천한다. 프로젝트가 정한 필수 참조를 무시한다는 뜻은 아니며, 기존 문서의 정리나 삭제는 별도 변경 작업이다.

### 기존 기록을 다시 조사하는 시점

#### 변경을 확인했을 때 영향받는 부분 조사

작업 목적, 변경 대상, 기술 버전이나 근거가 바뀐 사실을 확인하면 영향받는 기록만 다시 조사한다.

- 장점: 바뀌지 않은 내용을 반복 조사하는 비용이 적다.
- 단점: 변경 사실을 놓치면 낡은 판단을 계속 사용할 수 있다.

#### 사용할 때 현재 근거와 대조

작업 기록을 사용할 때 그 기록의 전제와 현재 코드 및 버전을 대조한다. 차이가 있으면 영향받는 판단을 다시 조사한다.

- 장점: 변경 알림이 없었어도 오래된 전제를 발견할 기회가 생긴다.
- 단점: 기록을 사용할 때마다 확인 비용이 들고, 전제가 모호하게 적혀 있으면 대조하기 어렵다.

사용할 때 전제를 대조하고 실제 재조사는 달라진 부분에 한정하는 방식을 추천한다. 시간 간격만으로 전체를 다시 조사하는 규칙은 제안하지 않는다.

## 스킬 구성 제안

한 스킬에서 작업 목적과 변경 권한 확인, 프로젝트 규칙 및 기록 대상 확인, 필요한 코드 변경 판단, 조사와 코드 예시 작성, 지정 위치 반영을 이어가는 구성을 제안한다. 여기서 코드 변경 판단은 실제 변경의 실행과 다르다.

재개 시 읽을 내용과 조사할 문제를 스킬 전용 파일로 나누지 않는다. 작성할 내용은 프로젝트가 지정한 계획이나 다른 작업 기록의 구성에 맞춘다. 내부 참고 자료가 필요하면 스킬이 관리하는 자료로 둘 수 있지만, 이를 실행할 프로젝트에 복사하거나 고유 기록 양식을 강제하는 구성은 제안하지 않는다.
