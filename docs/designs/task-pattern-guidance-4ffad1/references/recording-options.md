# 코딩 판단 기록의 조사 근거

## 조사 목적과 적용 기준

[요구사항](../requirements.md)을 구체화할 사람이 작업 기록, 재개, 조사와 예시 확인 방식을 판단할 수 있도록 근거를 정리한다. 특정 폴더나 문서 구조를 대상 프로젝트에 요구하지 않으며, 사용자가 지정한 파일이 기록 대상이다.

아래 자료는 2026년 10월 29일에 확인했다. 외부 운영 사례는 요구사항의 구현 효과를 증명하지 않으며, 도구별 동작도 다른 도구에 그대로 적용하지 않는다.

## 확인한 저장소 근거

[기존 스킬](../../../../skills/use-dev-guidance/SKILL.md)은 고정된 개발 지침 README를 기준으로 삼고, 그 문서가 없으면 생성 승인 절차를 거친다. [스킬 이름과 변경 권한](../requirements.md#스킬-이름과-변경-권한)에 따라 기존 스킬은 유지하고 신규 스킬을 별도로 추가한다. 신규 스킬은 이 기준 문서와 생성 절차에 의존하지 않으며 기존 스킬을 실행 입력으로 사용하지 않는다.

기존 스킬에는 현황 파악, 조사, 도구 비교, 승인된 변경의 적용과 검증도 열거돼 있다. [스킬 이름과 변경 권한](../requirements.md#스킬-이름과-변경-권한)은 이보다 구체적으로 기본 작업을 조사와 예시 작성으로 정하고 실제 소스 변경에 필요한 지시를 구분한다.

## 외부 자료에서 확인한 사실

### 지침의 존재와 실제 사용은 다름

[Vercel의 Next.js 평가](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)는 스킬만 제공한 조건의 통과율을 53%, 스킬 사용을 명시한 조건을 79%, 압축한 문서 색인을 지침 파일에 넣은 조건을 100%로 보고했다. 스킬만 제공한 조건에서는 사례의 56%에서 스킬을 호출하지 않았다.

이는 자료를 제공하는 것과 실제 사용하는 것이 다를 수 있다는 근거다. 특정 버전의 API를 대상으로 한 자체 평가이므로 모든 기술과 장기 작업에서 같은 효과가 난다는 뜻은 아니다.

[Cursor의 파일 참조 설명](https://cursor.com/docs/rules#referencing-files-from-a-rule)은 파일 언급만으로 내용이 프롬프트에 자동 포함되지 않으며 에이전트가 필요할 때 읽는다고 설명한다. 기록 위치를 아는 것과 현재 작업에 필요한 판단을 읽는 것을 구분해야 한다.

### 압축과 재읽기는 다른 작업

[Anthropic의 컨텍스트 관리 설명](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)은 압축 과정에서 중요한 맥락이 빠질 수 있으며 외부에 보존한 정보를 나중에 다시 읽는 방법을 설명한다. 이것이 특정 재개 파일이나 모든 도구의 압축 이벤트 감지를 요구하는 근거는 아니다.

[도구의 hooks 문서](https://code.claude.com/docs/en/hooks#postcompact)는 압축 전후 이벤트의 사례와 제어 제한을 설명한다. 이벤트 존재만으로 읽기 지시를 모델에 전달할 수 있다고 가정하지 않는다. 도구별 자동화는 필수 동작으로 채택하지 않았다.

### 테스트는 검사하려는 동작과 연결

[Testing Library의 원칙](https://testing-library.com/docs/guiding-principles/)은 실제 사용하는 방식과 가까운 테스트를 지향한다. [Playwright의 권장 방식](https://playwright.dev/docs/best-practices#test-user-visible-behavior)도 내부 함수 이름이나 CSS 클래스보다 사용자가 관찰하는 동작을 검사하도록 한다.

두 자료는 UI 테스트 예시의 판단 근거이며 모든 백엔드 테스트를 브라우저로 확인하라는 근거는 아니다. 예시의 테스트 대상과 기대하는 관찰을 대조하는 데 사용하되, 실제 실행 확인과 구분한다.

### 스킬의 설명과 본문을 나누는 형식

[Agent Skills 명세](https://agentskills.io/specification)는 이름과 호출 조건을 설명하는 필드, 실행 지침 본문과 선택적인 내부 참고 자료를 구분한다. 이름은 부모 디렉터리 이름과 같아야 한다.

이 형식은 스킬 내부 구성을 정할 근거다. 스킬을 사용하는 프로젝트에 별도 기록 파일이나 고유 문서 체계를 만들도록 요구하는 근거로 사용하지 않는다.

## 선택한 방식과 고려한 대안

### 작업 단위마다 기록 확인

압축이나 재개를 인지했을 때만 읽는 방식, 작업 단위마다 읽는 방식과 도구 이벤트를 사용하는 방식을 비교했다. [작업 시작과 재개 시 기록 확인](../requirements.md#작업-시작과-재개-시-기록-확인)은 작업 단위마다 필요한 기록을 읽도록 정한다.

압축 시점을 모르는 경우에도 다음 작업에서 판단을 확인할 기회가 생기는 대신 읽기 비용이 반복된다. 스킬이 다시 적용되거나 프로젝트 지침이 재개 행동을 전달해야 한다는 한계는 남는다.

### 작업 특성을 확인한 뒤 실패 영향에 따라 조사

모든 작업에 같은 조사 항목을 적용하는 방식과, 현재 작업에서 발생할 수 있는 실패에 따라 조사를 추가하는 방식을 비교했다. [작업 특성에 따른 조사와 변경 판단](../requirements.md#작업-특성에-따른-조사와-변경-판단)은 후자를 사용한다.

목적, 변경 대상과 버전도 작업마다 확인하며 같은 특징을 가진다고 가정하지 않는다. 실제 문제에 집중할 수 있는 대신 처음에 놓친 실패는 조사에서도 빠질 수 있으므로 미확인 사항을 밝히는 조건이 필요하다.

### 문서와 선택한 프로젝트 파일로 예시 확인

문서 및 프로젝트 근거 대조와 기존 실행 검사까지 추가하는 방식을 비교했다. [읽을 파일의 선택과 예시 대조](../requirements.md#읽을-파일의-선택과-예시-대조)는 문서와 프로젝트 근거 대조를 사용한다.

모든 파일을 찾는다고 가정하지 않고 목적, 변경 대상, 버전, 타입과 호출 관계 및 검사할 동작을 근거로 필요한 파일을 선택한다. 소스나 테스트 파일을 바꾸지 않고 예시를 검토할 수 있는 대신 실행 문제를 모두 발견할 수는 없다.

### 기록 불가와 충돌은 보류하고 대화에 반영안 제시

기록 작업 보류와 대화 반영안 제시를 비교하고 두 방식을 함께 사용한다. [사용자가 지정한 파일에 기록](../requirements.md#사용자가-지정한-파일에-기록)에 따라 영향을 받는 변경과 판단은 보류하고, 대화에는 선택에 필요한 정보를 제공한다.

대화에 제시한 반영안을 검토할 수 있지만 실제 파일 기록을 대신하지는 않는다. 미정인 판단을 확정한 구현 입력으로 취급하지 않는다.

## 스킬 구성에 대한 적용 제안

본문에는 작업과 권한 확인, 파일 지정 여부, 작업별 조사와 변경 판단, 프로젝트 코드 및 테스트 예시, 재개와 미확인 사항 처리에 필요한 지침만 둔다. 기술별 패턴 목록, 조사 자료 전체, 도구별 재개 설정과 같은 내용을 본문에 복제하지 않는다.

사용할 때마다 특정 문서 구조를 준비하게 하지 않는다. 고정된 기준 README나 생성용 기본본 없이 동작하는 단일 진입점을 먼저 구성하고, 내부 참고 자료가 실제로 필요한지 판단한다. 분량의 목표 숫자를 정하는 대신 각 문장이 어떤 필수 행동을 바꾸는지 확인하는 방식을 제안한다.
