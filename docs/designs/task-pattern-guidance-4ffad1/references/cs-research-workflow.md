# 프로젝트 문제에서 컴퓨터 공학 조사 질문을 찾는 방법

## 조사 결론과 적용 범위

프로젝트의 저장 모델과 실행 순서에서 조사할 질문을 만들고, 필요한 원리와 적용 조건, 대안, 선택 이유와 확인 방법을 연결하는 방안을 제안한다. 분야별 지식 목록만 제공하거나 관측된 성능 문제만 조사하면 데이터 일관성과 보안 문제를 놓칠 수 있다.

이 자료는 [컴퓨터 공학 조사 요구사항](../requirements.md#프로젝트에-필요한-컴퓨터-공학-지식)을 구현할 방법과 스킬 파일 구성을 비교한다. 구현 계획을 읽고 보완할 사람이 독자다. 아래 설계 제안은 출처에서 직접 확인한 사실과 구분하며, 새로운 요구사항이나 구현 완료의 증거로 사용하지 않는다. 자료 확인일은 2026-10-29다.

## 조사 질문을 만드는 관점

### 프로젝트의 미확인 사항에서 시작

구현할 동작을 기준으로 기술적으로 모르는 사항을 조사하면 선택 근거를 설계에 연결하기 쉽다. GitHub Spec Kit은 기술적 미확인 사항, 의존성과 연동을 조사 과제로 바꾸고 선택한 방식, 이유와 대안을 기록하도록 한다. 이어서 데이터 모델과 검증 시나리오를 작성한다. [Spec Kit 계획 지침](https://github.com/github/spec-kit/blob/b60057692cd726ea56331ec47f9ebc3e8877d8f7/templates/commands/plan.md)의 조사 절에서 확인했다.

장점은 질문과 실제 작업을 연결할 수 있다는 점이다. 한계는 미확인 사항 자체를 발견하지 못하면 조사가 시작되지 않는다는 점이다. 이 사례의 파일 생성 규칙과 하위 에이전트 실행은 가져오지 않고 질문 도출과 근거 기록 방식을 참고한다. 지침이 있다는 사실만으로 실제 모델의 행동이 입증되지는 않는다.

### 지켜야 할 동작과 실패 가능성에서 시작

문제가 아직 관측되지 않았어도 잘못된 데이터 저장이나 권한 없는 접근을 먼저 검토할 수 있어야 한다. OWASP는 위협 모델링에서 작업 대상, 잘못될 수 있는 일, 이를 막을 방법과 그 방법이 충분한지의 판단을 질문하도록 한다. 데이터 흐름과 외부 입력 등 대상 시스템을 먼저 분석하도록 한다. [OWASP 위협 모델링 지침](https://cheatsheetseries.owasp.org/cheatsheets/Threat_Modeling_Cheat_Sheet.html)에서 네 질문과 시스템 분석 과정을 확인했다.

이 관점을 일반 기술 조사에 적용하는 것은 이 자료의 제안이다. 저장해야 할 사실과 변경 규칙, 입력과 접근 권한, 작업에 필요한 반복 처리와 CPU 및 메모리 사용을 살펴 질문을 찾는다. 모든 작업에 모든 질문을 채우거나 일반 코딩 요청을 전체 보안 감사로 확대하지 않는다. 출처의 도식 작성 방법도 기존 시각 표현 조건을 대신하지 않는다.

### 관측한 지연과 자원 비용에서 시작

성능과 부하 판단에는 입력 규모와 실행 조건이 필요하다. Google SRE의 NALSD는 설계를 CPU, 메모리, 저장 공간과 네트워크 등의 실제 자원 추정으로 연결하고, 추정에 사용한 가정을 강조한다. [NALSD 설명](https://sre.google/workbook/non-abstract-design/)은 최종 수치보다 추론과 가정의 중요성을 설명한다.

PostgreSQL은 조회 조건과 데이터 특성에 따라 실행 계획을 선택하며, 실행 계획의 비용이 클라이언트 전송 등 실제 지연의 모든 요소를 포함하지는 않는다고 설명한다. [PostgreSQL 18의 EXPLAIN 설명](https://www.postgresql.org/docs/18/using-explain.html)은 인덱스 사용 여부만으로 성능을 판정할 수 없는 근거다.

이 방안은 개선 효과를 확인할 방법을 구체화하기 좋다. 다만 측정 자료를 필수 진입 조건으로 삼으면 설계 초기의 조사를 막는다. 정적 분석, 조건을 밝힌 추정과 실행 측정을 구분하고, 측정 자료가 없으면 필요한 자료를 설명하는 방안을 제안한다. 실제 환경의 검사나 부하 발생 권한은 별도로 확인해야 한다.

### 기술별 지식 목록에서 시작

지식 목록은 조사 누락을 발견하는 보조 수단이며 적용 결론은 아니다. arc42는 여러 구성요소에 영향을 주는 기술적 개념을 설명하면서 가장 필요한 주제만 선택하도록 한다. [arc42 기술 개념 설명](https://docs.arc42.org/section-8/)은 모든 주제를 다루려 하지 말라고 명시한다.

정규화, 보안, 캐시와 알고리즘 등의 목록은 탐색 방향을 떠올리는 데 도움이 된다. 반면 각 분야의 적용 조건을 생략한 규칙 모음은 기술 이름 채우기와 불필요한 변경을 유도할 수 있다. 따라서 예시 분야를 조사 시작을 돕는 단서로만 사용하고, 프로젝트의 어떤 문제를 설명하는지에 따라 조사 여부를 판단하는 방안을 제안한다.

## 이유와 이력을 설명하는 범위

선택의 배경은 기술 지식의 배경과 프로젝트의 선택 이력을 구분해야 이해하기 쉽다. AWS ADR 지침은 결정 당시의 상황, 선택과 그에 따른 영향 및 이후 결정을 바꾸는 절차를 설명한다. [AWS ADR 절차](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html)는 프로젝트가 왜 그 방식을 선택했는지 보존하는 근거다. 별도 ADR 파일이나 AWS 지침의 승인 절차를 도입하는 제안은 아니다.

기술 지식의 배경은 원래 어떤 문제를 해결하려 했는지 설명하는 데 사용한다. Codd의 1970년 논문 소개는 데이터 표현 변경과 중복 및 일관성 문제를 관계형 모델과 연결한다. [IBM Research의 원 논문 소개](https://research.ibm.com/publications/a-relational-model-of-data-for-large-shared-data-banks)는 이 배경을 확인하는 자료이며 현재 프로젝트에 특정 정규형을 적용할 직접 근거는 아니다.

구현에서는 선택을 이해하는 데 필요한 원리의 배경을 설명하고, 프로젝트의 이전 방식과 변경 이유는 문서, 이슈와 Git 기록 등으로 확인하는 방안을 제안한다. 기록이 없으면 현재의 적용 제안과 확인하지 못한 과거 이유를 구분한다. 누가 언제 무엇을 승인했는지 추정하거나 모든 개념의 학술사를 장문으로 덧붙이지 않는다.

## 요구사항과 계획 및 참고 자료의 연결

같은 설명을 여러 문서에 복제하기보다 독자가 해야 할 판단에 맞게 나누는 편이 적합하다. OpenSpec은 요구사항에 관측 가능한 동작과 제약을, 설계에는 기술 선택과 이유 및 대안을, 작업에는 확인 방법을 연결한다. [OpenSpec의 기본 절차](https://github.com/Fission-AI/OpenSpec/blob/852a0738832645f0549aa035f836ae09bea71ee2/schemas/spec-driven/schema.yaml)에서 이 구분과 보안, 성능 및 데이터 모델 변경의 설계 검토 조건을 확인했다.

이 사례를 현재 요구사항에 적용할 때는 요구사항에 해결할 문제와 지켜야 할 조건, 계획에 조사한 근거로 달라지는 작업과 확인 방법, 참고 자료에 원리와 출처 및 적용 조건을 담는 방안을 제안한다. 승인되지 않은 기술 제안은 요구사항으로 확정하지 않는다. 각 문서가 지정됐을 때만 반영하며, 하나만 지정됐으면 그 파일의 목적에 맞는 내용을 기록한다. 다른 문서의 필요성은 제안할 수 있으나 자동 생성하지 않는다.

## 스킬 파일 구성 비교

### 기존 두 파일에서 조사 절차 보완

현재 `skills/use-flexible-coding/SKILL.md`와 `agents/openai.yaml`만 유지하는 방안을 우선한다. 조사할 질문의 발견, 원리의 적용 조건과 대안, 이유와 이력 및 검증 방법은 같은 기술 판단 과정에서 필요하다. 별도 자료를 찾는 절차 없이 본문에서 연결할 수 있다.

장점은 읽을 파일과 유지할 내용이 늘지 않는다는 점이다. 단점은 분야별 사례를 많이 넣으면 본문이 길어진다는 점이다. 따라서 본문에는 질문을 만드는 방법과 근거를 연결하는 필수 지침만 두고 기술별 설명 전체는 넣지 않는다.

### 조건부 참고 파일 추가

복잡한 분야별 절차가 반복해서 필요하다면 내부 참고 파일을 선택적으로 읽게 할 수 있다. [Agent Skills 명세](https://agentskills.io/specification)는 참고 자료를 선택 사항으로 두며, [작성 권고](https://agentskills.io/skill-creation/best-practices)는 큰 스킬의 상세 자료를 분리할 때 읽을 조건을 명확히 하도록 한다.

장점은 본문에 필요하지 않은 세부 정보를 싣지 않아도 된다는 점이다. 단점은 참고 파일을 언제 읽어야 하는지 판단하고 링크를 유지해야 하며, 기술별 자료가 오래될 수 있다는 점이다. 현재는 독립적인 상세 절차보다 같은 조사 절차의 보완이 필요하므로 추가하지 않는 방안을 제안한다.

### 기술별 자료 모음이나 별도 스킬

데이터베이스, 보안과 성능을 별도 스킬이나 교재 파일로 나누면 각 분야의 운영 및 변경 절차까지 설명할 수 있다. 반면 하나의 캐시 판단에서도 보안과 성능을 함께 조사해야 하므로 어느 파일을 읽을지 선택하는 부담이 커진다. 이는 구성 대안에 대한 이 자료의 분석이며, 외부 사례가 분리를 금지한다는 뜻은 아니다.

현재 목표는 특정 기술의 운영이나 변경을 수행하는 절차가 아니라 필요한 지식을 조사해 판단 이유를 설명하는 절차다. 스킬 분리와 기술별 자료 모음은 이번 구현 범위에서 제외하는 방안을 제안한다. 이 설계 묶음의 조사 자료는 스킬의 실행 의존성으로 연결하지 않는다.

## 구현과 확인에 미치는 영향

[구현 계획](../plan.md#컴퓨터-공학-조사-보완-순서)은 두 파일 구성을 유지하면서 본문의 조사, 이유 및 예시 지침과 호출 안내를 보완한다. 분야별 예시가 필요한 근거를 발견하는지, 작업에 영향을 주지 않는 분야까지 억지로 조사하지 않는지, 이력이 없을 때 만들어내지 않는지 확인할 사례도 계획에 포함한다.

출처들은 질문 도출, 기술 선택과 문서 연결을 각각 뒷받침한다. 이들을 조합한 지침이 실제 에이전트의 조사 누락을 줄이는지는 별도의 행동 확인이 필요하며, 명세 검사나 문서 대조만으로 그 효과를 입증할 수 없다. 컴퓨터 공학의 모든 문제를 발견한다는 완료 조건도 만들지 않는다.
