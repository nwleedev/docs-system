# 작업에 필요한 패턴을 기록하는 개발 지침 스킬

## 목표

`use-dev-guidance`는 앞으로 수행할 작업의 목적을 파악하고, 필요한 디자인 패턴과 피해야 할 안티패턴을 조사한다. 기록할 파일이 지정되면 그 파일에 프로젝트에 맞는 코드 예시와 함께 작성한다. 기술 지침을 담을 별도 파일을 생성하지 않으며, 기록 위치를 `docs/dev` 등 특정 폴더로 고정하지 않는다.

이 요구사항은 스킬을 개선할 내용을 구체화하는 사람이 읽는다. 적용할 패턴을 판단하는 AI 에이전트가 컨텍스트 압축 뒤에도 필요한 기술 판단을 다시 파악하여 작업을 이어갈 수 있어야 한다.

## 작업을 기준으로 기술 판단 기록

스킬은 앞으로 진행할 작업을 기준으로 필요한 디자인 패턴과 안티패턴을 빠짐없이 파악한다. 문서가 있다는 사실이나 문서를 참고하라는 지시만으로 필요한 기술 판단의 기록을 대신하지 않는다.

디자인 패턴의 이름을 붙이는 것보다 작업의 목적을 파악하는 데 우선순위를 둔다. 목적에 맞는 작성 방법과 피해야 할 문제를 설명하며, 패턴 이름을 채우는 일을 목표로 삼지 않는다.

계획의 각 절차에 필요한 패턴을 명시하는 작업에서는 절차별로 조사한 패턴과 안티패턴을 그 절차에 반영한다. 이후 작업을 수행할 에이전트가 어떤 패턴을 적용하고 어떤 안티패턴을 피해야 하는지 알 수 있어야 한다.

앞서 파악한 패턴을 컨텍스트 압축 뒤에 잊지 않고 작업에 활용할 수 있도록 기록한다. 압축 전 대화의 기억만을 전제로 삼지 않는다.

## 프로젝트에 따른 기록 위치

기술 정보를 작성하는 위치는 프로젝트마다 다를 수 있다. 스킬은 모든 프로젝트에 같은 폴더나 파일 이름을 요구하지 않는다.

스킬은 먼저 파일을 수정하거나 작성하지 않고 작업과 기록할 대상을 확인한다. 기록할 파일 위치가 직접 제시되면 그 파일에 작성한다. 사용자가 계획의 각 절차에 기록하도록 지정하면 지정한 계획에 반영한다.

프롬프트에 기록할 파일이 없으면 적절한 파일을 찾아 제안한다. 후보를 찾았다는 이유만으로 파일을 수정하거나 새로 작성하지 않는다. 스킬은 조사한 기술 판단을 보관할 독립적인 기술 가이드 파일을 새로 만들지 않는다.

## 프로젝트에 맞는 코드 예시

파일 위치를 전달받아 디자인 패턴을 기록할 때는 설명과 단순 지침만 남기지 않고 작업 대상 프로젝트에 맞는 코드 예시를 포함한다. 예시를 통해 그 프로젝트의 작업에서 어떤 코드를 어떻게 작성할지 이해할 수 있어야 한다.

## 테스트 대상과 목적

테스트 코드 작성에 관한 기술 판단을 기록할 때는 무엇을 테스트하는지와 왜 테스트하는지를 명확히 설명한다. 테스트 코드 작성 방법을 조사하고, 프로젝트에 맞는 테스트 코드 예시도 기록에 포함한다.

테스트 예시는 설명한 대상과 목적을 검사하는 코드를 보여줘야 한다. 무의미한 가짜 테스트를 작성하지 않도록 하는 것이 이 조건의 목적이다.

## 완료를 판단할 근거

스킬 변경을 완료했다고 판단하려면 다음 동작을 관찰할 수 있어야 한다. 아래 항목은 요구하는 동작이며, 특정 테스트 코드나 평가 도구를 지정하지 않는다.

- 절차별 기술 판단을 요청한 계획에서 각 절차에 필요한 디자인 패턴과 피해야 할 안티패턴을 확인할 수 있다.
- 각 절차에서 달성할 목적과 그 목적에 맞는 코드 작성 방법을 설명할 수 있으며, 패턴 이름의 나열만으로 기록을 대신하지 않는다.
- 계획의 작업과 기술 판단 기록을 전달받은 에이전트가 압축 전 대화 없이도 적용할 패턴과 피할 안티패턴을 설명하고 후속 작업에 사용할 수 있다.
- 기술 정보의 기록 위치가 다른 프로젝트에서도 지정된 위치에 조사한 패턴과 안티패턴이 반영되며, `docs/dev` 사용이 필수 조건이 되지 않는다.
- 파일이 지정되지 않은 경우 적절한 파일을 찾아 제안하며, 그 과정에서 파일을 수정하거나 새로 작성하지 않는다.
- 파일이 지정된 경우 그 파일에 단순 지침과 프로젝트에 맞는 코드 예시가 함께 있다.
- 테스트 코드 작성 방법을 설명한 기록에는 테스트 대상, 테스트가 필요한 이유, 작성 방법을 조사한 내용과 프로젝트에 맞는 테스트 코드 예시가 있다. 예시의 검사 내용이 설명한 대상과 목적에 부합한다.
- 스킬 실행으로 조사한 기술 판단을 담는 별도 기술 가이드 파일이 추가되지 않는다.

어떤 문제와 자료까지 조사할지, 패턴의 누락을 무엇과 대조해 판정할지는 아직 정하지 않았다. 패턴 이름이 적혀 있다는 사실만으로 이 완료 조건을 충족했다고 판단하지 않는다.

## 동작을 정하기 위해 남은 질문

- 제안할 파일은 어떤 근거와 순서로 찾는가? 적절한 후보가 없거나 지정한 파일이 존재하지 않거나 수정할 수 없을 때는 어떻게 안내하는가?
- 패턴과 안티패턴을 빠짐없이 파악했는지 어떤 변경 대상과 자료를 기준으로 판정하는가?
- 목적, 프로젝트에 맞는 코드 예시와 테스트 설명 외에 적용 조건, 예외, 출처와 확인 방법을 얼마나 상세히 기록해야 하는가?
- 프로젝트에 맞는 코드 예시로 인정할 기준과, 의미 없는 가짜 테스트를 구분할 기준은 무엇인가?
- 기존 `docs/dev`와 현재 스킬의 문서 생성 및 유지보수 동작을 앞으로 어떻게 다루는가?
- 기술 버전이나 작업 내용이 바뀌었을 때 이미 기록한 패턴을 언제 다시 조사하고 갱신하는가?
