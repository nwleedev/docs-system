# 프로젝트에 필요한 컴퓨터 공학 조사 보완 계획

## 목표와 기준

`use-flexible-coding`이 프로젝트에 필요한 컴퓨터 공학 지식을 찾아 조사하고, 적용 이유와 배경 및 이력을 지정한 문서에 연결하도록 보완한다. 기존 디자인 패턴, 모듈과 시스템 아키텍처 조사를 이 과정에 통합하며 별도 스킬을 만들지 않는다.

기준은 [요구사항 전체](./requirements.md)이며 특히 [컴퓨터 공학 조사](./requirements.md#프로젝트에-필요한-컴퓨터-공학-지식), [지정 파일 기록](./requirements.md#사용자가-지정한-파일에-기록), [프로젝트 예시](./requirements.md#프로젝트와-판단에-맞는-예시)와 [간결한 구성](./requirements.md#간결한-스킬-구성)을 함께 적용한다. 이 계획을 마지막으로 수정한 커밋의 요구사항을 변경 영향 비교의 기준으로 삼는다.

[조사 방법과 파일 구성 비교](./references/cs-research-workflow.md)는 구현안의 근거다. [기존 조사](./references/recording-options.md)는 기록 권한, 재개와 예시 조건을 보존할 때 참고한다. 조사에서 제안한 운영 방식은 요구사항과 구분한다.

컴퓨터 공학 조사 보완은 아래 순서로 구현한다. 단계별 작성 상태는 현재 진행 상태에서 구분하며, 이전 아키텍처 구현과 초기 구현 기록을 새 요구사항의 충족 증거로 사용하지 않는다.

## 이번에 작성하는 문서

- `docs/designs/task-pattern-guidance-4ffad1/requirements.md`: 프로젝트에 필요한 컴퓨터 공학 지식의 능동적인 조사, 적용 이유와 배경 및 이력, 지정 문서에 반영하는 조건과 완료 근거를 추가한다. 조사에서 도출한 세부 구현안은 요구사항으로 확정하지 않는다.
- `docs/designs/task-pattern-guidance-4ffad1/references/cs-research-workflow.md`: 새로 추가하는 유일한 파일이다. 미확인 사항을 찾는 방법, 실패 가능성을 검토하는 방법, 실행 시간과 CPU 및 메모리 사용량을 조사하는 방법, 기술 목록을 참고하는 방법의 장단점을 비교한다. 출처, 적용 이유와 선택 이력을 설명할 내용, 스킬 파일 구성 대안도 기록한다.
- 이 `plan.md`: 기존 파일 구성과 보완할 본문, 단계별 작업과 확인 방법을 연결한다.
- `HANDOFF.md`: 기존 코딩 스킬 기록에 이번에 작성한 문서와 구현하지 않은 항목을 구분해 남긴다.

## 구현할 스킬의 파일과 내용

기존 두 파일 구성을 유지한다. 이는 필수 조사 절차를 한곳에서 읽도록 하는 구현 선택이며 기술별 지식 모음을 추가하는 선택과 [비교했다](./references/cs-research-workflow.md#스킬-파일-구성-비교).

### 스킬 본문

`skills/use-flexible-coding/SKILL.md`의 이름과 영어 작성 조건을 유지하고 다음 부분을 보완한다.

- frontmatter의 `description`과 도입: 디자인 패턴과 아키텍처뿐 아니라 프로젝트에 필요한 컴퓨터 공학 원리의 조사와 적용 이유 설명도 수행함을 알린다. 목록을 나열해 모든 개발 요청을 유도하거나 구현 권한을 확대하지 않는다.
- `Research each task`: 현재 작업의 목적과 버전 확인 뒤 저장할 사실의 의미와 변경 규칙, 외부 입력과 접근 권한, 처리량과 반복 작업 및 CPU와 메모리 사용에서 조사 질문을 도출하도록 한다. 이는 질문을 찾는 단서이며 모든 단서를 매번 채우는 고정 목록으로 만들지 않는다. 프로젝트 근거로 필요한 분야를 선택하고 중요한 미확인 사항을 추가 조사한다.
- 같은 조사 절: 현재 버전의 공식 자료와 필요한 원문에서 원리와 적용 조건을 조사한다. 대안을 비교할 때는 실행 시간과 메모리 사용량, 저장 공간, 변경 후 계속 관리해야 할 코드처럼 판단에 영향을 주는 항목을 구체적으로 설명한다. 여러 분야가 영향을 주면 함께 검토한다. 관측한 사실, 조건을 밝힌 추정과 확인하지 않은 성능 주장을 구분하며, 자료가 부족하면 필요한 확인을 설명한다.
- `Explain principles and decision history` 절 추가: 지식이 해결하는 문제와 프로젝트에서 필요한 이유를 연결한다. 판단을 이해하는 데 필요한 원리의 배경과 실제 프로젝트의 선택 이력을 구분한다. 이전 방식과 변경 이유는 근거를 확인하며, 기록이 없으면 과거의 이유나 승인 사실을 만들어내지 않는다.
- `Explain changes and examples`: 기존 코드 및 테스트 예시 조건에 원리와 확인 방법을 연결한다. 구현 예시만으로 충분하지 않으면 저장할 사실 사이의 의존 관계, 쿼리, 처리 순서를 설명하거나 실행 시간과 메모리 사용량 등을 비교한다. 비교 항목은 판단할 문제에 맞게 선택한다. 설명을 위한 가짜 파일이나 무의미한 테스트는 추가하지 않는다.
- 기록 지침과 재개: 사용자가 지정한 요구사항에는 해결할 문제와 지켜야 할 조건, 계획에는 선택한 방식을 적용할 작업과 확인 방법, 참고 문서에는 원리와 출처 및 적용 조건을 담도록 한다. 지정된 파일의 목적이 우선이며 다른 문서가 있다고 가정하지 않는다. 재개할 때 이유와 적용 조건 및 미확인 사항도 회복할 수 있게 한다.

같은 지침을 여러 절에 복제하지 않는다. 기록 권한은 기존 기록 절에서, 원리와 이력은 새 절에서 설명한다. 기술별 교재, 정규화나 캐시를 일률적으로 요구하는 규칙, 고정 문서 양식과 필수 외부 도구를 넣지 않는다. 이 저장소의 설계 문서는 스킬 실행 중 읽어야 할 자료로 연결하지 않는다.

### 호출 정보

`skills/use-flexible-coding/agents/openai.yaml`은 기존 필드를 유지한다. `short_description`과 `default_prompt`에 프로젝트에 필요한 기술 원리의 조사와 이유 설명을 반영하고, 기본 호출 `$use-flexible-coding`과 지정 파일 조건을 보존한다. 영어 설명은 본문과 같은 역할을 나타내야 하며 정책이나 도구 의존성은 추가하지 않는다.

### 저장소 사용 안내와 진행 기록

`README.md`와 `README.ko.md`는 기존 `use-flexible-coding` 소개 한 항목씩을 보완한다. `src/AGENTS.en.md`와 `src/AGENTS.ko.md`는 같은 스킬의 호출 조건 한 항목씩을 보완한다. 디자인 패턴과 아키텍처의 기존 역할을 유지하면서 필요한 컴퓨터 공학 지식과 적용 이유를 조사하는 역할을 같은 의미로 설명한다.

구현 변경 대상은 위 여섯 파일과 진행 상태를 갱신할 이 `plan.md`, `HANDOFF.md`까지 여덟 파일이다. 스킬 내부 참고 파일, `references/_README.md`, 스크립트, 별도 스킬과 기술별 템플릿은 추가하지 않는다. 기존 `skills/use-dev-guidance/`, 다른 스킬, 검사 설정과 의존성 파일은 수정하지 않는다.

대상 프로젝트의 기록 파일은 사용자가 정한다. 이 저장소에서 구현할 파일 목록은 그 프로젝트의 문서 생성 규칙이 아니다.

## 컴퓨터 공학 조사 보완 순서

### 조사 질문과 원리의 선택 보완

먼저 `SKILL.md`의 도입과 조사 절을 보완한다. 사용자가 기술 이름을 먼저 말하지 않아도 선택한 프로젝트 자료의 저장 모델, 실행 순서와 실패 영향에서 조사할 질문을 만들게 한다. 지식을 적용하지 않는 판단도 프로젝트 조건으로 설명한다.

구현 전 확인할 사례는 아래의 저장 모델과 조회, 외부 입력, 캐시, UI와 부하 사례다. 실행 로직을 바꾸지 않으므로 구현 전 테스트 코드는 작성하지 않는다. 최종 확인에서 각 사례를 지침에 대조해 조사 질문에 답하는 원리와 적용 조건을 설명할 근거가 있는지 판단한다. 특정 단어나 제목의 존재만 확인하는 자동 테스트로 대신하지 않는다.

### 이유와 이력 및 문서 연결 보완

조사 절 보완 뒤 원리와 이력을 설명하는 절을 추가하고, 예시 및 기록 지침을 연결한다. 이력이 없는 경우, 지정 문서가 하나인 경우와 기록할 파일이 없는 경우에도 기록 권한과 미확인 사실의 구분을 유지한다.

실행 로직이 없어 구현 전 테스트 코드는 작성하지 않는다. 최종 확인에서는 선택 이유가 원리와 프로젝트 근거에 연결되는지, 근거가 없는 과거 이야기를 사실로 만드는 지침은 없는지, 승인되지 않은 제안이 요구사항으로 확정되지 않는지 대조한다. 기존 테스트의 대상, 필요성, 종류와 예시 조건도 보존해야 한다.

### 호출 정보와 사용 안내 반영

본문이 정리된 뒤 YAML과 두 언어의 사용 안내를 보완한다. 이름을 바꾸거나 기존 스킬의 호출 조건을 대체하지 않는다. 진행 상태와 실제로 확인한 항목은 계획과 인수인계 기록에 남긴다.

실행 로직이 없어 구현 전 테스트 코드는 작성하지 않는다. 최종 확인에서 YAML 형식, 호출 이름, 설명과 본문의 일치 및 한국어와 영어가 요구하는 행동을 대조한다.

### 최종 확인과 커밋

수정이 끝나면 다음 사례를 한 번 대조한다. 각 사례는 조사 질문의 출발점이며 정답이나 특정 기술의 강제 적용 목록이 아니다.

- 데이터 모델과 조회: 같은 사실의 중복 저장과 변경 시 일관성, 키와 관계 및 주요 조회 조건에서 정규화와 쿼리 조사 필요성을 찾는다. 무조건 테이블을 나누거나 인덱스를 추가하는 결론을 피한다. 판단에 필요한 행 수와 값의 분포, 조회 시간, 추가 저장 공간과 쓰기 작업의 변화 등을 설명하고 확인하지 못한 항목을 밝혀야 한다.
- 외부 입력을 받는 조회: 입력이 SQL에 사용되는 방식과 필요한 접근 권한에서 인젝션 및 웹 보안 질문을 도출한다. 특정 ORM을 사용한다는 사실만으로 안전하다고 판정하지 않아야 한다.
- 응답 재사용: HTTP 캐시의 재사용 조건, 최신성, 사용자마다 달라지는 응답 내용과 성능의 관계를 함께 조사할 수 있어야 한다. 캐시 추가를 전제하지 않는다.
- 반복 조회와 UI 지연: 입력 크기와 탐색 횟수, 렌더링 및 메인 스레드 작업에서 자료구조와 알고리즘 또는 UI 성능 조사 필요성을 판단한다. 입력 크기에 따른 연산 횟수와 실제 실행 시간을 구분하고, 측정하지 않은 성능 개선을 사실로 표현하지 않아야 한다.
- 백엔드 요청 증가: 동시 실행, 대기 작업과 CPU 및 메모리 사용에서 부하가 증가했을 때의 조사 질문을 도출한다. 알려지지 않은 처리량이나 지연 목표를 임의로 요구사항에 넣지 않아야 한다.
- 기술 판단이 필요 없는 변경: 기술 판단이 필요하지 않은 명칭 수정 등을 모든 분야의 조사로 확대하지 않는다. 코드나 테스트를 추가하지 않는 이유도 설명할 수 있어야 한다.
- 이력 부재와 재개: 과거 선택 근거가 없으면 미확인으로 구분하고, 지정한 기록만으로 현재 판단 이유와 적용 조건을 다시 파악할 수 있어야 한다.
- 지정 파일과 권한: 요구사항, 계획 또는 참고 문서 중 하나만 지정돼도 그 파일의 목적에 맞게 기록한다. 미지정 시 후보만 제안하며 실제 구현과 측정을 자동 실행하지 않아야 한다.

이 대조는 지침의 내용 확인이다. 실제 에이전트 실행으로 조사 누락이 줄어드는지는 별도 확인이 필요하다. 실행 평가를 하지 않았다면 미수행으로 기록하고 행동을 확인했다고 표현하지 않는다. 평가를 위해 가짜 애플리케이션, fixture나 검사 프로그램을 추가하지 않는다.

frontmatter와 YAML의 형식 및 영어 작성, 기존 두 파일 구성, 이름과 호출문을 확인한다. 기본 스킬 검사기를 사용할 수 없으면 그 이유와 대체 검사로 확인한 조건을 밝힌다. 상대 링크와 절 연결, 민감정보와 한국어 표현을 확인하고 `git diff --check` 및 `pnpm lint`를 실행한다. 기존 스킬과 다른 항목의 안내가 유지되는지 변경 목록과 diff로 확인한다.

각 구현 단계가 끝나면 진행 상태를 갱신하고 조사 지침, 기록 지침과 호출 안내 등 의미 있는 작업 단위로 커밋한다. 최종 검토는 모든 구현 뒤 한 번 수행하며, 문서 검사와 실제 행동 확인의 차이를 남긴다.

## 현재 진행 상태와 중단 조건

조사 질문과 원리를 선택하는 지침을 본문에 반영했다. 이유와 이력 지침 및 호출 안내는 미착수이며, 전체 사례 대조와 형식 검사는 마지막 단계에서 수행한다. 이전 완료 기록은 아래에서 구분한다.

- 조사 질문과 원리의 선택 보완: 작성 완료
- 이유와 이력 및 문서 연결 보완: 미착수
- 호출 정보와 사용 안내 반영: 미착수
- 최종 확인과 커밋: 미착수

`Research each task`에 저장할 사실의 변경 규칙, 외부 입력과 접근 권한, 반복 처리와 CPU 및 메모리 사용 등에서 질문을 찾도록 작성했다. 필요한 원리와 적용 조건, 대안과 확인 방법을 연결하고 관측, 추정과 측정하지 않은 주장을 구분한다. 스킬 이름과 기록 권한은 유지했다. 실행 로직을 추가하지 않아 구현 전 테스트 코드는 작성하지 않았다. 내용의 충족 여부는 최종 사례 대조에서 판정한다.

기술 문제로 필요한 근거를 확인할 수 없거나 동작을 바꾸는 결정이 필요하면 영향을 받는 작업을 멈추고 판단에 필요한 정보를 제시한다. 지정되지 않은 파일 생성이나 실제 소스, 테스트, 설정 및 측정 실행이 필요해져도 권한을 추정하지 않는다. 예정에 없는 파일이나 별도 스킬을 추가해야 한다면 이 계획의 파일 구성부터 다시 확인한다.

## 이전 아키텍처 구현의 파일 구성

스킬은 기존 두 파일을 유지한다.

- `skills/use-flexible-coding/SKILL.md`: 조사 대상, 읽을 근거의 선택 기준, 판단별 예시와 시각 표현 지침을 보완한다.
- `skills/use-flexible-coding/agents/openai.yaml`: 확대된 조사 대상과 예시 선택을 영어 사용 설명 및 기본 호출문에 반영한다.

사용 안내는 다음 네 파일의 `use-flexible-coding` 항목만 수정한다.

- `README.md`
- `README.ko.md`
- `src/AGENTS.en.md`
- `src/AGENTS.ko.md`

진행 상태와 확인 근거는 이 `plan.md`와 `HANDOFF.md`에서 갱신한다. 후속 구현의 변경 대상은 위 여덟 파일이다. 다른 파일을 수정할 필요가 발견되면 대상과 이유를 먼저 계획에 반영한다.

스킬 이름과 영어 작성 조건, 기존 `skills/use-dev-guidance/`의 세 파일 및 호출 규칙, 과거 문서의 링크는 유지한다. 새 스킬, 내부 참고 파일, 기본본, 전용 기록 파일과 스크립트는 추가하지 않는다. 대상 프로젝트에서 기록할 파일은 사용자가 정하며, 이 저장소의 스킬 파일 구성과 구분한다.

## 이전 아키텍처 구현 순서

### 작업별 조사 대상과 프로젝트 근거 보완

[작업 특성에 따른 조사와 변경 판단](./requirements.md#작업-특성에-따른-조사와-변경-판단)과 [읽을 파일의 선택과 예시 대조](./requirements.md#읽을-파일의-선택과-예시-대조)를 `SKILL.md`의 설명 및 `Research each task` 절에 반영한다.

코드 작성 방법, 모듈의 파일 및 폴더 구성과 의존 관계, 시스템 구성과 상호작용을 같은 조사 절차에서 선택할 수 있도록 한다. 모든 요청에 같은 조사 목록을 적용하지 않고 작업 목적, 변경 대상, 기술 버전과 실패 영향에 따라 조사할 문제를 정한다. 패턴 이름을 채우는 방식으로 확대하지 않는다.

현재의 파일 선택 기준을 유지하면서 모듈과 시스템 판단에 필요한 구성 및 관계를 선택한 코드와 설정 등에서 확인하도록 문장을 보완한다. 책임과 관계를 프로젝트 근거에서 설명하며, 모든 파일을 찾았다고 전제하거나 현재 구조를 그대로 권장하지 않는다. 추가, 제거, 통합, 분리와 수정 및 추가하지 않는 판단과 이유를 연결한다.

이 작업은 실행 로직을 추가하지 않으므로 구현 전 테스트 코드는 작성하지 않는다. 완료 여부는 최종 확인에서 코드, 모듈과 시스템 판단이 함께 필요한 사례 및 그중 일부만 필요한 사례를 지침에 대조해 판단한다. 각 조사 대상과 선택 이유, 프로젝트 근거와 미확인 사항을 설명할 조건이 있어야 한다.

### 판단별 예시와 시각 표현 지침 보완

앞 작업의 조사 대상이 정리된 뒤 [프로젝트와 판단에 맞는 예시](./requirements.md#프로젝트와-판단에-맞는-예시)와 [설명과 시각 표현](./requirements.md#설명과-시각-표현)을 `SKILL.md`의 예시 지침에 반영한다.

모든 기술 판단에 코드 예시를 요구하는 현재 문장을 바꾼다. 구현 방법에는 프로젝트 코드 예시를, 모듈 구성에는 파일과 폴더 구성 및 의존 관계 예시를, 시스템 구성에는 통신과 데이터 흐름 예시를 선택하도록 한다. 여러 예시가 함께 필요하면 함께 사용한다. 선택한 예시는 판단의 이유와 프로젝트 근거를 설명해야 한다.

시각화는 주제 이해에 도움이 되는 경우에 선택하도록 한다. 의미 없는 요소와 연결로 설명을 대신하지 않으며, 도구의 사용 가능 여부와 본래 목적을 고려하도록 한다. 마크다운 표와 ASCII 문자로 만든 도식처럼 코드 편집기에서 한 번에 이해하기 어려운 시각 표현을 사용하지 않는 조건을 명시한다.

테스트가 필요하면 대상, 필요성, 종류, 작성 방법 조사와 프로젝트 예시를 연결하는 현재 지침을 유지한다. 테스트가 필요하지 않으면 이유를 설명하고 불필요한 예시를 만들지 않는다. 코드 예시의 버전, 타입과 호출 관계 대조 및 실행 여부 구분도 유지한다.

이 작업에도 실행 로직이 없어 구현 전 테스트 코드는 작성하지 않는다. 최종 확인에서는 구현 설명의 코드 예시 조건, 모듈 및 시스템 판단의 예시 선택, 책임과 관계 설명, 시각화 선택 및 금지 표현 조건을 사례에 대조한다. 예시 작성 방법을 설명하기 위해 가짜 프로젝트, fixture나 테스트용 스크립트를 추가하지 않는다.

### 호출 정보와 두 언어 사용 안내 보완

본문 보완 뒤 [스킬의 작성 언어](./requirements.md#스킬의-작성-언어)에 맞춰 `agents/openai.yaml`의 사용 설명과 기본 호출문을 수정한다. 이름과 기본 호출 `$use-flexible-coding`은 유지하고 기존의 코드 예시 중심 설명을 조사 대상과 판단별 예시 선택에 맞춘다.

두 README의 스킬 소개와 두 `src/AGENTS` 파일의 신규 스킬 호출 항목에도 같은 역할을 반영한다. 한국어와 영어의 의미를 맞추되 각 안내의 언어를 유지한다. 기존 스킬의 호출 규칙을 대체하거나 두 스킬을 서로의 필수 실행 조건으로 연결하지 않는다.

실행 로직 변경이 없어 구현 전 테스트 코드는 작성하지 않는다. 최종 확인에서는 YAML 필드와 호출 이름, 설명과 실제 본문의 일치 및 두 언어가 요구하는 행동을 대조한다. 세 조사 대상이 설명에 포함되고, 실제 구현 권한이 확대되지 않아야 한다.

### 최종 확인과 진행 기록 마무리

모든 수정 뒤 아래 사례와 형식 조건을 한 번 확인한다. 각 단계의 완료 상태는 그 단계에서 작성한 파일과 남은 확인을 구분해 기록하며, 최종 판정은 이 단계에 남긴다.

- 기록 파일이 지정되지 않은 요청: 저장소 근거로 후보와 이유만 제안하고 파일을 바꾸지 않는지 확인한다.
- 지정 파일이 있는 요청: 목적과 구성에 맞게 기록하며, 실제 소스 및 테스트 변경에는 명시적인 개발 지시를 요구하는지 확인한다.
- 지정 파일 부재나 기록 불가 또는 기준 충돌: 영향을 받는 기록과 판단을 보류하고 대화에 반영안과 필요한 선택을 제시하는지 확인한다.
- 코드, 모듈과 시스템 조사가 함께 필요한 요청과 일부만 필요한 요청: 작업 특성에 맞는 조사, 프로젝트 근거 선택과 누락 가능성 설명이 있는지 확인한다.
- 구현 방법, 모듈 구성과 시스템 구성의 판단: 목적에 맞는 예시를 선택하고, 코드 예시가 필요한 경우 버전과 타입 및 호출 관계에 대조하도록 하는지 확인한다.
- 설명과 시각 표현: 책임과 관계를 근거로 설명하고, 이해에 도움이 될 때 시각화를 선택하며, 도구 선택 조건과 마크다운 표 및 ASCII 도식 등의 금지가 있는지 확인한다.
- 코드와 테스트를 추가하지 않는 판단: 이유를 설명하는지 확인한다. 테스트가 필요하면 대상, 필요성, 종류와 예시가 연결되고 가짜 동작만 검사하는 예시를 금지하는지 확인한다.
- 작업 시작, 재개와 다음 작업 단위: 압축 감지와 무관하게 지정 기록을 다시 읽도록 하는지 확인한다.
- 스킬 구성과 권한: 고정 폴더나 기준 README, 전용 기록 파일을 요구하지 않으며, 기존 스킬과 호출 규칙을 유지하는지 확인한다.

신규 스킬의 두 파일 구성, 이름과 디렉터리 일치, frontmatter와 `openai.yaml`의 형식 및 영어 문구를 검사한다. 기본 스킬 검사기를 사용할 수 없으면 확인하지 못한 조건을 밝히고 사용 가능한 YAML 파서 등으로 확인할 수 있는 형식 조건을 검사한다. 검사 도구의 성공을 실제 에이전트 행동의 증거로 표현하지 않는다.

변경 문서의 상대 링크와 절 연결, 민감정보, 한국어 표현, 두 언어 안내와 변경 파일 목록을 확인한다. 저장소의 `pnpm lint`를 실행한다. 같은 지침을 본문 여러 절에 반복하거나 조사 자료 및 기술별 규칙 전체를 추가하지 않았는지 읽는다.

별도 테스트 코드나 평가 프로그램은 추가하지 않는다. 문서 대조, 형식 검사와 실제 에이전트 실행 여부를 구분하고 확인하지 않은 행동은 확인한 것으로 표현하지 않는다.

## 이전 아키텍처 구현의 의존 관계와 중단 조건

조사 지침, 예시 지침, 호출 정보와 사용 안내, 최종 확인 순서로 진행한다. 각 단계가 끝나면 이 계획의 진행 상태와 필요한 인수인계 기록을 갱신하고 작업 단위별로 커밋한다. 본문에서 필요한 판단과 행동을 완결하고 이 저장소의 설계 문서를 실행 의존성으로 만들지 않는다.

[파일 지정](./requirements.md#사용자가-지정한-파일에-기록), [실제 변경 권한](./requirements.md#스킬-이름과-변경-권한), [재개](./requirements.md#작업-시작과-재개-시-기록-확인)와 [간결한 구성](./requirements.md#간결한-스킬-구성)은 후속 보완에서도 유지할 조건이다. 새 의존성, 검사 설정 변경이나 애플리케이션 구현은 포함하지 않는다. 사용자 환경에 설치된 스킬과 설정을 자동으로 바꾸지 않는다.

필수 지침이나 자료를 읽을 수 없거나, 해결할 수 없는 기술 문제가 발생하거나, 선택에 사람의 결정이 필요하면 즉시 멈추고 대기한다. 요구사항이 바뀌면 구현을 멈추고 변경 영향을 확인한 뒤 요구사항과 영향을 받은 조사 자료 및 계획을 먼저 갱신한다.
