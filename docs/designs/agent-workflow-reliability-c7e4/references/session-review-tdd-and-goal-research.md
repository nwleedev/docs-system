# 구현 세션, 리뷰 세션과 Goal 운용 조사

## 조사 결론

구현 판단을 다시 평가해야 하는 작업에는 구현 담당 세션과 읽기 전용 리뷰 담당 세션을 나누는 방안을 우선 비교할 수 있다. 다만 모든 작업을 두 세션으로 보내거나 대화만 새로 만든다고 독립적인 리뷰가 되지는 않는다. 리뷰 담당 세션은 구현에 참여하지 않고 요구사항, 기준 commit, 검토할 commit 범위, 적용 지침과 검사 결과에서 별도의 판단을 세워야 한다. 리뷰 결과를 반영해 파일을 수정하는 책임도 구현 담당 세션에 남겨야 한다.

두 세션이 같은 worktree branch를 참조하고 커밋하지 않는 파일로 결과를 주고받는 대안은 실행할 수 있다. 단, 이 파일은 대화만 분리할 뿐 파일 시스템을 격리하지 않는다. 구현 담당 세션이 검토 중 추적 파일을 바꾸지 않고, 리뷰 담당 세션이 검토한 마지막 commit을 결과에 기록하며, Git 제외와 비추적 상태를 확인할 때만 검토 대상과 결과의 관계를 다시 확인할 수 있다. 결과 파일 위치와 제외 방식은 저장소가 정하고 공통 파일명을 이 문서에서 만들지 않는다.

TDD 작업의 테스트와 구현을 두 commit으로 나누면 리뷰 담당자가 테스트의 의도를 먼저 읽는 데 도움이 된다. 그러나 모든 작업에서 두 commit을 각각 제출하거나 병합하는 방식은 적합하지 않다. 새 동작의 테스트와 구현은 하나의 완결된 변경으로 검토하되, branch 안에서 테스트 commit과 구현 commit을 구분해 읽을 수 있다. 기존 동작을 고정하는 characterization test는 후속 리팩터링보다 먼저 독립적으로 제출할 수 있다.

Goal은 검증 가능한 종료 조건이 있는 장기 작업을 이어 가는 수단이다. Git 기록이 일정 시간 바뀌지 않았다는 사실은 작업 불능을 뜻하지 않으므로, 시간만으로 Goal을 `Blocked`로 바꾸면 안 된다. 리뷰할 새 commit이 없으면 검토를 다시 실행하지 않고 대기하거나 작업을 끝내며, 필요한 입력이나 권한이 없어 더 진행할 수 있을 때만 막힌 상태로 판정한다.

이 문서는 [세션 분리, TDD와 Goal에 관한 요구사항](../requirements.md#목표)을 조사한 자료이며 운영 결정이 아니다. 최초 조사일은 2026년 8월 27일이고, 같은 worktree에서 결과 파일을 인계하는 대안은 2026년 8월 28일에 추가로 조사했다.

## 확인한 자료와 적용 한계

OpenAI의 현재 Code review 문서는 `/review`가 선택한 diff를 읽는 전용 reviewer를 시작하며, 데스크톱 앱과 IDE 확장에서 별도 리뷰 대화를 선택할 수 있다고 설명한다. 같은 문서는 branch, commit, 작업 트리처럼 검토 대상을 명시할 수 있고 reviewer가 파일을 바꾸지 않은 채 결과를 반환한다고 밝힌다. 미커밋 변경 리뷰에는 stage한 변경, stage하지 않은 변경과 untracked 파일이 포함된다. [OpenAI, Code review](https://learn.chatgpt.com/docs/code-review)

따라서 단순히 untracked 상태인 결과 파일은 다음 미커밋 리뷰의 입력에 섞일 수 있다. 파일을 직접 작성하는 인계는 작업 트리를 수정하지 않는 `/review` 자체가 아니라 같은 worktree에서 연 별도 일반 리뷰 세션으로 시험해야 한다. 별도 리뷰 대화를 사용할 수 있지만, 별도 대화가 모델 내부 상태까지 공유하지 않는다는 뜻은 아니다. 여기서는 구현 대화가 리뷰 transcript에 포함되지 않는 관찰 가능한 차이만 사용한다.

OpenAI의 worktree 안내는 각 worktree가 자체 파일 사본을 가지며 permanent worktree에서는 여러 대화를 열 수 있다고 설명한다. 또한 무시된 파일은 다른 worktree로 옮길 때 포함되지 않을 수 있다고 경고한다. 따라서 이번 대안에서 결과 파일을 직접 공유할 수 있는 이유는 두 세션이 같은 worktree를 사용한다는 전제에 있고, 별도 worktree를 쓰는 구조로 바꾸면 파일 전달 수단을 다시 정해야 한다. [OpenAI, Worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees)

Git 문서는 `.gitignore`를 복제되는 공통 제외 규칙에, `$GIT_COMMON_DIR/info/exclude`를 저장소에만 필요한 개인 작업 파일에 사용하도록 구분한다. 이미 추적된 파일에는 제외 규칙이 적용되지 않으며, `git add --force`는 무시된 파일도 stage할 수 있다. `git check-ignore -v`는 어떤 제외 규칙이 적용됐는지 보여 준다. 그러므로 파일명을 정하는 것만으로 commit을 막을 수 없고, 저장소가 선택한 제외 규칙, 비추적 상태와 stage 목록을 각각 확인해야 한다. [Git, gitignore](https://git-scm.com/docs/gitignore), [Git, git-check-ignore](https://git-scm.com/docs/git-check-ignore), [Git, git-add](https://git-scm.com/docs/git-add)

NASA의 독립 검증 표준은 기술적 독립성을 개발에 참여하지 않은 검증자가 문제와 구현의 관계를 별도로 이해하는 상태로 정의한다. 같은 표준은 모든 항목을 독립 검증할 수 없으므로 위험과 사용 가능한 자원을 비교해 대상을 정하도록 한다. NASA의 적용 대상과 의무 수준을 일반 애플리케이션 저장소에 옮기지는 않지만, 구현 대화를 받지 않는 것, 개발에 참여하지 않는 것과 자체 판정 근거를 만드는 것을 서로 다른 조건으로 봐야 한다는 근거로 사용할 수 있다. [NASA-STD-8739.8B, Software Assurance and Software Safety Standard](https://standards.nasa.gov/system/files/tmp/NASA-STD-87398-Revision-B_0.pdf)

OpenAI의 Goal 안내는 하나의 목표, 검증 가능한 종료 조건, 먼저 읽을 자료, 진전을 증명할 명령이나 산출물과 checkpoint 기록을 요구한다. 작업이 끝났거나 막혔거나 방향이 바뀌면 Goal을 pause, resume 또는 clear하도록 안내하지만, commit이 일정 시간 바뀌지 않았을 때 자동으로 막힌 상태가 된다는 규칙은 제시하지 않는다. [OpenAI, Follow a goal](https://learn.chatgpt.com/use-cases/follow-goals)

Google의 리뷰 지침은 테스트가 스스로 테스트의 타당성을 증명하지 못하므로 사람이 테스트의 정확성, 유용성, 실제 결함에서 실패하는지를 확인해야 한다고 설명한다. 새 동작의 테스트는 구현과 같은 변경 단위에 두는 것을 기본으로 삼고, 기존 동작을 확인하는 새 테스트는 리팩터링보다 먼저 별도 변경으로 제출할 수 있다고 구분한다. 이는 Google의 변경 제출 방식에 관한 지침이며 모든 저장소의 commit 정책은 아니다. [Google, What to look for in a code review](https://google.github.io/eng-practices/review/reviewer/looking-for.html), [Google, Small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html)

Test-First와 Test-Last를 비교한 실험에서는 branch coverage와 mutation score의 유의한 차이를 찾지 못했다. 별도의 TDD와 mutation testing 실험은 mutation 정보를 함께 제공했을 때 더 강한 테스트를 작성하도록 도울 수 있음을 조사했다. 두 결과는 테스트를 먼저 썼다는 순서만으로 테스트 품질이 확정되지 않으며, 잘못된 구현에서 실제로 실패하는지 별도 증거가 필요함을 보여준다. [Madeyski와 Szala, The impact of Test-First programming on branch coverage and mutation score indicator of unit tests](https://doi.org/10.1016/j.infsof.2009.08.007), [Roman과 Mnich, Test-driven development with mutation testing](https://doi.org/10.1007/s11219-020-09534-x)

Test-Driven Code Review 실험에서는 테스트를 먼저 읽은 검토자가 테스트 코드의 결함을 더 찾았지만, production code의 유지보수 문제는 덜 찾았고 전체 production defect 발견 비율은 같았다. 따라서 `C0..C1`을 먼저 읽는 순서는 테스트 타당성을 확인하는 한 관점이지 전체 리뷰를 대신하는 방법이 아니다. [Spadini 외, Test-Driven Code Review](https://zenodo.org/records/2551217)

별도의 checklist 실험도 단계별 안내가 모든 변경에서 일관되게 나은 결과를 만들지 않았고 일부 작업에서는 시간이 더 들었다. 리뷰 전략은 변경 복잡도와 검토자의 경험에 따라 효과가 달랐다. 체크 항목을 늘리거나 같은 checklist를 반복하는 것보다 현재 변경에서 보호해야 할 동작과 기대 결함을 먼저 정해야 한다. [Gonçalves 외, Do explicit review strategies improve code review performance?](https://doi.org/10.1007/S10664-022-10123-8)

## 검토 책임을 세 단계로 비교하는 실험안

다음 구분은 승인된 운영 규칙이 아니라 대표 작업에서 비교할 후보이다. 작업 위험을 숫자로 추정하지 않고, 요구사항에서 보호하라고 정한 동작과 현재 검사로 확인할 수 있는지를 사용해 각 후보의 입력을 만든다.

**결정적 확인만 수행한다.** 포맷, 생성 파일 일치, 링크 형식처럼 기대 결과를 반복 가능한 명령으로 모두 판정할 수 있는 변경은 구현 세션이 명령과 diff를 확인한다. 이 결과를 독립 리뷰라고 부르지 않는다.

**별도 리뷰 세션이 판정한다.** 요구사항을 충족하는 방법, 오류 처리, 상태 변화 또는 기존 동작 유지처럼 diff와 실행 증거를 함께 해석해야 하면 구현에 참여하지 않은 리뷰 세션이 고정된 commit 범위를 읽는다. 이 후보가 실제로 필요한지는 같은 작업을 단일 세션 방식과 비교해 확인한다.

**요구사항 작성자나 책임 있는 검토자에게 판단을 돌린다.** 유지할 동작, 허용할 위험이나 승인 역할이 요구사항과 결정 문서에 없으면 모델이 기준을 만들지 않는다. 구현과 리뷰를 모두 멈추는 것이 아니라, 결정이 필요한 항목만 분리하고 영향받지 않는 검사는 계속할 수 있다.

## 구현과 리뷰 세션의 책임

### 구현 담당 세션

구현 담당 세션은 승인된 요구사항과 개발 지침을 읽고 변경을 만든다. 이 세션에서 호출할 서브에이전트가 있다면 구현과 직접 연결되고 독립적으로 나눌 수 있는 작업만 맡긴다. 예를 들어 서로 다른 package의 독립적인 build 오류 수정은 후보가 될 수 있지만, 같은 함수의 구현과 구조 검토를 각각 맡기는 방식은 제외한다.

구현 담당 세션이 리뷰에 전달할 자료는 다음으로 제한한다.

- 요구사항 문서와 변경하지 말아야 할 동작
- 기준 branch와 검토할 처음 및 마지막 commit
- 변경한 파일과 생성 파일 여부
- 실행한 검사 명령, 종료 상태와 실패를 포함한 원문 결과
- 사용자가 승인한 예외와 아직 결정하지 않은 사항

구현 이유를 설명하는 대화 전체나 “이 구조가 맞다”와 같은 자기 평가는 전달 자료에서 제외한다. 설계 결정이 승인됐다면 대화가 아니라 승인된 결정 문서를 전달한다.

### 리뷰 담당 세션

리뷰 담당 세션은 작업 파일을 수정하지 않고 요구사항과 commit 범위를 기준으로 판정한다. 첫 단계에서 Git 기록으로 시작 commit과 마지막 commit이 실제로 존재하는지 확인하고, 이후에는 시작 commit을 포함한 고정 목록을 순서대로 한 번 검토한다. 구현 담당 세션의 보고를 완료 증거로 사용하지 않고 diff와 검사 결과를 직접 읽는다.

리뷰 결과에는 발견 위치, 사용자에게 보이는 실패, 근거와 필요한 수정 조건을 기록한다. 단순한 선호나 더 넓은 개선 제안은 현재 작업을 막는 결함과 구분한다. 리뷰 담당 세션이 수정까지 수행하면 다음 검토에서 다시 자기 변경을 평가하게 되므로 수정은 구현 담당 세션으로 돌려보낸다.

### 지정된 commit부터 검토하는 순서

시작 commit과 마지막 commit은 전체 OID로 고정하고, 시작 commit이 마지막 commit의 조상인지 먼저 확인해야 한다. Git의 `merge-base --is-ancestor`는 첫 commit이 둘째 commit의 조상이면 성공하고 조상이 아니면 상태 `1`을 반환한다. 이 관계가 성립하지 않으면 두 commit 사이에 하나의 진행 순서를 만들지 않고 인계를 중단한다. [Git 2.55까지 변경이 없는 `git-merge-base` 조상 확인](https://git-scm.com/docs/git-merge-base)

검토 목록은 시작 commit을 포함하고 부모가 자식보다 먼저 오도록 만든다. Git의 두 점 범위는 왼쪽 commit 자체와 그 조상을 제외하므로 `start..end`만 사용하면 시작 commit이 빠진다. `git rev-list`는 부모 연결을 따라 도달 가능한 commit을 선택하고 `--reverse`로 선택 결과를 반대 순서로 출력할 수 있다. `--topo-order`는 기본 출력에서 모든 자식을 보여 주기 전에 부모를 보여 주지 않으며, 이를 `--reverse`와 함께 적용하면 검토에서는 부모가 자식보다 먼저 온다. commit 날짜는 병렬 계보에서 부모 관계와 다른 순서를 만들 수 있으므로 검토 순서의 기준으로 사용하지 않는다.

- [Git revisions](https://git-scm.com/docs/gitrevisions)는 두 점 범위가 오른쪽에서 도달할 수 있지만 왼쪽에서는 도달할 수 없는 commit을 선택한다고 설명한다.
- [Git 2.55 `git-rev-list`](https://git-scm.com/docs/git-rev-list)는 부모 연결에 따른 선택, `--reverse`, `--ancestry-path`와 `--first-parent`의 차이를 설명한다.
- [Git 2.55 `git-log`](https://git-scm.com/docs/git-log)는 날짜 순서와 위상 순서가 서로 다를 수 있음을 예시로 보여 준다.

리뷰 담당 세션은 고정한 목록의 각 commit에서 부모와 비교한 변경을 읽고, 마지막에는 시작 commit 직전 상태부터 마지막 commit까지의 누적 변경을 확인한다. 이것은 여러 리뷰를 반복하는 절차가 아니라 한 리뷰 안에서 의도와 상호작용을 다른 단위로 확인하는 순서다. OpenAI의 현재 Code review 문서는 하나의 commit을 선택하면 그 commit의 정확한 변경 묶음을 검토한다고 설명하므로, 여러 commit을 순차 검토하려면 먼저 목록을 고정하고 각 commit을 별도 입력으로 선택하는 조정 절차가 필요하다. [OpenAI, Code review](https://learn.chatgpt.com/docs/code-review)

시작 commit이 저장소의 최초 commit이면 부모가 없으므로 부모 commit을 전제로 범위를 만들거나 diff를 계산하면 안 된다. Git의 `diff-tree --root`는 최초 commit을 빈 tree와 비교한 생성 사건으로 표시한다. Merge commit은 어느 계보를 목록에 포함하고 어느 부모와 비교할지에 따라 결과가 달라진다. `--first-parent`는 merge에서 첫 부모만 따라가며, 전체 계보 순회는 merge로 들어온 commit도 포함할 수 있다. `diff-tree -m`은 merge 결과를 모든 부모와 각각 비교한다. 따라서 merge가 포함된 범위에서는 첫 부모 계보만 검토할지 모든 조상 경로를 검토할지, merge commit을 어느 부모와 비교할지를 저장소가 승인하기 전까지 순서 규칙을 확정하지 않는다. [Git 2.55 `git-diff-tree`](https://git-scm.com/docs/git-diff-tree)

결과 파일에는 시작 및 마지막 commit의 전체 OID, 고정된 검토 목록, 실제로 검토를 마친 순서, commit별 지적과 누적 변경 판정을 남긴다. 검토 도중 현재 `HEAD`, 추적 파일 또는 commit 목록이 달라지면 일부 결과를 새 범위에 이어 붙이지 않고 완료되지 않은 결과로 처리한다.

### 커밋하지 않는 결과 파일을 사용하는 인계안

이 절차는 승인된 운영 규칙이 아니라 같은 worktree branch를 공유하는 두 세션을 비교하기 위한 구체적인 후보이다. 파일 위치와 확장자는 저장소가 정하며, 다른 저장소에도 같은 파일명을 요구하지 않는다.

이 대안의 리뷰 담당자는 파일을 수정하지 않는 Codex `/review`가 아니라 같은 worktree에서 연 별도 일반 세션이다. 이 세션은 결과 파일만 쓰도록 제한하지만 파일 시스템 권한까지 읽기 전용인 것은 아니다. 그러므로 지침만 신뢰하지 않고 리뷰 전후에 추적 파일의 diff와 stage 영역이 비어 있는지 확인해야 한다.

구현 담당 세션은 요구사항과 검사를 충족하는 마지막 commit을 만든 뒤 리뷰가 끝날 때까지 추적 파일을 바꾸지 않는다. 인계에는 시작 commit과 마지막 commit의 전체 OID를 넣는다. 작업 중인 미커밋 diff를 검토 대상으로 삼으면 두 세션이 같은 파일을 보면서도 시점에 따라 다른 내용을 읽을 수 있으므로 이 대안에서는 제외한다.

리뷰 담당 세션은 먼저 현재 `HEAD`가 인계받은 마지막 commit과 같은지 확인한다. `git status --short --untracked-files=all`의 출력이 비어 있고, `git diff --quiet`와 `git diff --cached --quiet`가 성공하는지도 확인한다. 결과 파일은 Git에서 제외되므로 상태 출력에 나타나지 않아야 한다. 그다음 요구사항, 적용 지침, 지정된 commit 범위와 검사 원문을 읽고, 소스나 설정은 바꾸지 않은 채 결과 파일만 작성한다. 결과 파일에는 다음 내용을 남긴다.

- 시작 commit과 검토한 마지막 commit의 전체 OID
- 고정된 검토 목록과 실제로 검토한 순서
- 읽은 요구사항과 저장소 지침
- 직접 확인한 diff 범위와 검사 결과
- 발견 위치, 재현되거나 예상되는 동작, 근거와 수정이 필요한 조건
- 현재 변경을 막는 문제와 범위 밖 제안의 구분
- 완료 여부와 요구사항 작성자의 판단이 필요한 항목

결과 파일은 저장소가 선택한 Git 제외 규칙에 포함하고 한 번도 추적하지 않은 상태로 유지한다. 작성 전에는 `git check-ignore -v -- <path>`로 적용된 제외 규칙을 확인하고, `git ls-files --error-unmatch -- <path>`가 파일을 찾지 못하는지 확인한다. 구현 담당 세션이 다음 commit을 만들기 전에는 `git diff --cached --name-only`에서 결과 파일이 없는지도 확인한다. 제외된 파일도 `git add --force`로 stage할 수 있으므로 광범위한 강제 stage를 피하고 commit할 파일을 명시한다.

리뷰 담당 세션은 결과를 모두 쓴 뒤 완료 표시를 마지막에 기록하고, 다시 tracked diff와 stage가 비어 있는지 확인한다. 구현 담당 세션은 이 완료 상태와 마지막 commit OID가 현재 인계 대상과 모두 일치할 때만 지적을 반영한다. 리뷰 중 새 commit이나 추적 파일 변경이 생겼거나 결과 파일이 일부만 작성됐다면 그 결과를 완료된 리뷰로 사용하지 않는다. 이 경우 기존 결과를 현재 코드에 맞는 것으로 고쳐 읽지 않고, 변경된 commit 범위를 새로운 검토 입력으로 분리한다.

같은 worktree는 무시된 build 산출물, 개발 서버, 테스트 데이터베이스와 실행 중인 프로세스도 자동으로 격리하지 않는다. 구현 담당 세션은 리뷰 중 소스 변경뿐 아니라 이런 공용 상태를 바꾸는 명령도 멈춘다. 리뷰 검사가 공용 상태를 바꾼다면 저장소가 승인한 격리 방법을 사용하거나 두 세션의 명령을 순차 실행한다. 결과 파일은 한 리뷰 세션만 작성한다.

Git 제외 규칙은 파일 내용을 보호하지 않는다. 결과 파일에는 인증정보, 개인 계정이 담긴 절대 경로와 외부에 노출할 수 없는 원문을 기록하지 않는다.

이 파일은 commit 기록에 남지 않으므로 장기 감사 자료로도 사용할 수 없다. 보관 기간, 삭제 시점과 공유 제외 규칙을 `.gitignore`에 둘지 로컬 제외 파일에 둘지는 저장소의 협업 방식과 감사 요구에 따라 정한다. 장기 보관이 필요하면 결과 파일을 그대로 commit하는 방식이 아니라 저장소가 승인한 issue, pull request 또는 문서 기록 절차를 별도로 선택해야 한다.

### 실패 예시

구현 담당 세션이 인증 오류를 모두 `401`로 바꾼 뒤 같은 대화에서 API 리뷰를 수행한다고 가정한다. 구현 대화에 “존재 여부를 숨기기 위한 보안 결정”이라는 설명이 있으면 reviewer가 요구사항에 없는 결정을 전제로 삼을 수 있다. 별도 리뷰 세션은 요구사항, 이전 응답 형식, API 지침과 diff만 읽어 인증 실패와 권한 부족의 응답을 각각 다시 판정한다.

반대로 리뷰 세션에 diff만 주고 요구사항을 주지 않으면 `401`과 `403` 중 어느 동작을 유지해야 하는지 알 수 없다. 세션 분리는 판단 근거를 없애는 방식이 아니라 구현자의 미승인 설명을 제외하는 방식이다.

## TDD commit을 읽는 순서

### 새 동작을 구현할 때

branch의 기준을 `C0`, 테스트만 추가한 commit을 `C1`, 구현 commit을 `C2`라고 한다. 시작 commit을 `C1`, 마지막 commit을 `C2`로 지정하면 리뷰 담당 세션은 `C1`, `C2` 순서로 한 번의 리뷰를 수행할 수 있다. `C0`는 `C1`의 변경을 계산하는 부모 상태이며 검토 목록에는 포함하지 않는다.

1. `C0..C1`에서 테스트 이름, 입력과 예상 결과가 어느 요구사항을 확인하는지 읽는다.
2. `C0`의 구현에 `C1` 테스트를 실행했을 때 의도한 이유로 실패한 기록을 확인한다.
3. `C1..C2`에서 테스트를 바꾸지 않고 구현이 동작을 충족했는지 확인한다.
4. `C0..C2` 전체에서 테스트와 구현이 함께 완결된 변경인지 확인한다.

`C1`은 리뷰 순서를 위한 branch 내부 checkpoint다. 기본 branch에 단독으로 병합하면 build나 필수 검사를 깨뜨리는 저장소에서는 `C1`을 따로 병합하지 않는다. 저장소가 모든 commit의 성공을 요구하면 실패 테스트를 비활성화해 숨기지 말고, patch나 별도 실행 기록으로 Red 상태를 남긴 뒤 테스트와 구현을 하나의 성공 commit으로 만들 수 있다.

### 기존 동작을 보존하며 리팩터링할 때

현재 동작을 설명하는 테스트가 없다면 characterization test를 먼저 추가하고 성공하는 독립 변경으로 제출할 수 있다. 그다음 리팩터링 commit은 테스트를 바꾸지 않은 채 같은 동작을 유지해야 한다. 이 경우 테스트 commit 자체가 기존 코드를 깨뜨리지 않으므로 별도 제출의 이점이 크다.

### 리뷰 담당 세션이 테스트에서 확인할 사항

- 테스트의 각 기대값이 요구사항이나 보존할 현재 동작에서 나왔는가.
- 요구사항을 결정하는 조건을 제거하거나 반대로 바꾸면 테스트가 실패하는가.
- 성공 사례만이 아니라 오류, 값의 한계와 상태 전이를 확인하는가.
- 내부 함수 호출 순서처럼 바뀔 수 있는 구현 세부사항에만 의존하지 않는가.
- assertion이 단순히 값의 존재나 상태 코드 범주만 확인해 잘못된 결과를 통과시키지 않는가.
- fixture와 mock이 실제로 검증해야 할 실행 흐름을 우회하지 않는가.

예를 들어 할인 계산 테스트가 결과가 0보다 크다는 사실만 확인하면 잘못된 할인율도 통과한다. 요구사항이 10,000원 주문에 10퍼센트 할인을 정했다면 9,000원이라는 결과와 적용되지 않는 한계값을 확인해야 한다. reviewer는 구현을 보기 전에 이 기대값의 근거를 요구사항에서 찾고, 구현을 본 뒤 조건을 반대로 바꾼 경우 테스트가 실패할지 판단한다.

## 한 번의 리뷰와 Git 기록 감시

한 작업의 리뷰 입력은 변경되지 않는 시작 commit, 마지막 commit과 순서가 정해진 commit 목록으로 고정한다. 리뷰 세션은 각 commit과 전체 누적 변경을 정해진 순서로 확인하고 마지막 commit을 결과 파일에 기록한 뒤 완료 상태를 남긴다. 구현 담당 세션이 수정하면 새 마지막 commit이 생기므로 기존 결과 파일을 현재 변경의 리뷰로 간주하지 않고, 수정된 지적의 확인은 별도 입력 단위로 다룬다. 현재 요구사항의 “각 작업마다 1회”는 이 방식으로 해석할 수 있다.

리뷰 전용 세션을 장시간 유지해야 한다면 매번 전체 Git 기록을 다시 읽지 않는다. 마지막으로 본 commit OID와 현재 OID를 비교해 같으면 새 리뷰를 시작하지 않는다. 일정 시간 변화가 없다는 사실은 다음 두 상태 중 하나다.

- 구현 작업이 아직 진행 중이거나 외부 결과를 기다리는 중이면 대기 또는 pause 상태다.
- 리뷰 요청이 취소됐거나 더 이상 새 변경이 없으면 정상 종료 상태다.

다음 입력을 얻을 방법이 없거나, 승인이나 접근 권한이 없어 진행할 수 없고 안전한 대안도 없을 때만 막힌 상태다. 따라서 “30분 동안 commit이 없으면 Blocked” 같은 규칙은 사용하지 않는다. “새 commit이 생기면 그 commit 범위를 한 번 리뷰하고, 없으면 다시 읽지 않는다”를 중단 규칙으로 삼는다.

## 도입 전 평가할 지표

동일한 유형의 작업을 현재 방식과 분리 방식으로 수행해 다음 값을 비교해야 한다.

- 구현 및 리뷰 세션의 입력과 출력 토큰 합계
- 첫 변경부터 리뷰 결과까지 걸린 시간
- 요구사항 위반 중 reviewer가 찾은 수와 사람이 추가로 찾은 수
- 잘못된 지적과 근거가 부족한 지적 수
- 테스트가 알려진 결함 또는 준비한 mutation을 실제로 잡은 비율
- 같은 commit을 중복 검토한 횟수

분리 방식이 한두 사례에서 더 많은 결함을 찾았다는 사실만으로 기본 운영 규칙으로 채택하지 않는다. 적어도 대표 작업군마다 같은 평가 입력과 정답 기준을 두고 비교해야 한다.

대표 작업과 기대 판정은 요구사항 작성자 또는 저장소가 지정한 책임 있는 검토자가 실행 전에 승인해야 한다. 현재 자료에는 최소 발견률, 허용할 잘못된 지적 수와 토큰 절감률을 정할 근거가 없으므로, 수치 통과 조건을 먼저 만들지 않는다. 승인된 기대 판정을 충족한 후보끼리만 토큰과 경과 시간을 비교한다.

## 남은 결정

- 이 저장소에서 branch 내부의 실패 테스트 commit을 허용할지, 모든 commit이 검사를 통과해야 하는지 정해야 한다.
- Merge commit이 있는 범위에서 첫 부모 계보만 검토할지 모든 조상 경로를 검토할지와 merge 결과를 어느 부모와 비교할지 정해야 한다.
- 리뷰 담당 세션이 결과를 반환한 뒤 수정 확인을 새 작업으로 볼지, 원래 작업의 조건부 후속 단계로 볼지 정해야 한다.
- 저장소마다 결과 파일 위치, 공통 또는 로컬 Git 제외 방식, 보관 기간과 삭제 책임을 정해야 한다.
- Goal이 아닌 task 대기나 알림으로 새 commit을 감지할 필요가 있는지 운영 환경에서 확인해야 한다.
- 별도 리뷰 대화가 실제 결함 발견률과 토큰 사용량을 개선하는지는 대표 작업 평가 전에는 확정할 수 없다.
- 어떤 보호 동작이 별도 리뷰 세션의 판정을 필요로 하는지는 저장소별 요구사항과 기존 검사 능력을 확인한 뒤 정해야 한다.
