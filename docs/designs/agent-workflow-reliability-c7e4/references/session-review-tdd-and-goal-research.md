# 구현 세션, 리뷰 세션과 Goal 운용 조사

## 조사 결론

구현 담당 세션과 리뷰 담당 세션을 나누는 방안은 Codex가 제공하는 별도 리뷰 대화와 잘 맞는다. 다만 세션을 나누는 것만으로 독립적인 리뷰가 되지는 않는다. 리뷰 담당 세션은 구현 대화 대신 요구사항, 기준 commit, 검토할 commit 범위, 적용 지침과 검사 결과를 입력으로 받아야 한다. 리뷰 결과를 수정하는 책임도 구현 담당 세션에 남겨야 한다.

TDD 작업의 테스트와 구현을 두 commit으로 나누면 리뷰 담당자가 테스트의 의도를 먼저 읽는 데 도움이 된다. 그러나 모든 작업에서 두 commit을 각각 제출하거나 병합하는 방식은 적합하지 않다. 새 동작의 테스트와 구현은 하나의 완결된 변경으로 검토하되, branch 안에서 테스트 commit과 구현 commit을 구분해 읽을 수 있다. 기존 동작을 고정하는 characterization test는 후속 리팩터링보다 먼저 독립적으로 제출할 수 있다.

Goal은 검증 가능한 종료 조건이 있는 장기 작업을 이어 가는 수단이다. Git 기록이 일정 시간 바뀌지 않았다는 사실은 작업 불능을 뜻하지 않으므로, 시간만으로 Goal을 `Blocked`로 바꾸면 안 된다. 리뷰할 새 commit이 없으면 검토를 다시 실행하지 않고 대기하거나 작업을 끝내며, 필요한 입력이나 권한이 없어 더 진행할 수 있을 때만 막힌 상태로 판정한다.

이 문서는 [세션 분리, TDD와 Goal에 관한 요구사항](../requirements.md#목표)을 조사한 자료이며 운영 결정이 아니다. 조사일은 2026년 8월 27일이다.

## 확인한 자료와 적용 한계

OpenAI의 현재 Code review 문서는 `/review`가 선택한 diff를 읽는 전용 reviewer를 시작하며, 데스크톱 앱과 IDE 확장에서 별도 리뷰 대화를 선택할 수 있다고 설명한다. 같은 문서는 branch, commit, 작업 트리처럼 검토 대상을 명시할 수 있고 reviewer가 파일을 바꾸지 않은 채 결과를 반환한다고 밝힌다. 별도 리뷰 대화를 사용할 수 있지만, 별도 대화가 모델 내부 상태까지 공유하지 않는다는 뜻은 아니다. 여기서는 구현 대화가 리뷰 transcript에 포함되지 않는 관찰 가능한 차이만 사용한다. [OpenAI, Code review](https://learn.chatgpt.com/docs/code-review)

OpenAI의 Goal 안내는 하나의 목표, 검증 가능한 종료 조건, 먼저 읽을 자료, 진전을 증명할 명령이나 산출물과 checkpoint 기록을 요구한다. 작업이 끝났거나 막혔거나 방향이 바뀌면 Goal을 pause, resume 또는 clear하도록 안내하지만, commit이 일정 시간 바뀌지 않았을 때 자동으로 막힌 상태가 된다는 규칙은 제시하지 않는다. [OpenAI, Follow a goal](https://learn.chatgpt.com/use-cases/follow-goals)

Google의 리뷰 지침은 테스트가 스스로 테스트의 타당성을 증명하지 못하므로 사람이 테스트의 정확성, 유용성, 실제 결함에서 실패하는지를 확인해야 한다고 설명한다. 새 동작의 테스트는 구현과 같은 변경 단위에 두는 것을 기본으로 삼고, 기존 동작을 확인하는 새 테스트는 리팩터링보다 먼저 별도 변경으로 제출할 수 있다고 구분한다. 이는 Google의 변경 제출 방식에 관한 지침이며 모든 저장소의 commit 정책은 아니다. [Google, What to look for in a code review](https://google.github.io/eng-practices/review/reviewer/looking-for.html), [Google, Small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html)

Test-First와 Test-Last를 비교한 실험에서는 branch coverage와 mutation score의 유의한 차이를 찾지 못했다. 별도의 TDD와 mutation testing 실험은 mutation 정보를 함께 제공했을 때 더 강한 테스트를 작성하도록 도울 수 있음을 조사했다. 두 결과는 테스트를 먼저 썼다는 순서만으로 테스트 품질이 확정되지 않으며, 잘못된 구현에서 실제로 실패하는지 별도 증거가 필요함을 보여준다. [Madeyski와 Szala, The impact of Test-First programming on branch coverage and mutation score indicator of unit tests](https://doi.org/10.1016/j.infsof.2009.08.007), [Roman과 Mnich, Test-driven development with mutation testing](https://doi.org/10.1007/s11219-020-09534-x)

## 구현과 리뷰 세션의 책임

### 구현 담당 세션

구현 담당 세션은 승인된 요구사항과 개발 지침을 읽고 변경을 만든다. 이 세션에서 호출할 서브에이전트가 있다면 구현과 직접 연결되고 독립적으로 나눌 수 있는 작업만 맡긴다. 예를 들어 서로 다른 package의 독립적인 build 오류 수정은 후보가 될 수 있지만, 같은 함수의 구현과 구조 검토를 각각 맡기는 방식은 제외한다.

구현 담당 세션이 리뷰에 전달할 자료는 다음으로 제한한다.

- 요구사항 문서와 변경하지 말아야 할 동작
- 기준 branch와 검토할 처음 및 마지막 commit
- 변경한 파일과 생성 파일 여부
- 실행한 검사 명령, 종료 상태와 실패를 포함한 원문 결과
- 사용자가 승인한 예외와 아직 결정하지 않은 사항

구현 이유를 설명하는 대화 전체나 “이 구조가 맞다”와 같은 자기 평가는 전달 자료에서 제외한다. 설계 결정이 승인됐다면 대화가 아니라 승인된 결정 문서를 전달한다.

### 리뷰 담당 세션

리뷰 담당 세션은 작업 파일을 수정하지 않고 요구사항과 commit 범위를 기준으로 판정한다. 첫 단계에서 Git 기록으로 기준 commit과 마지막 commit이 실제로 존재하는지 확인하고, 이후에는 같은 commit 범위만 한 번 검토한다. 구현 담당 세션의 보고를 완료 증거로 사용하지 않고 diff와 검사 결과를 직접 읽는다.

리뷰 결과에는 발견 위치, 사용자에게 보이는 실패, 근거와 필요한 수정 조건을 기록한다. 단순한 선호나 더 넓은 개선 제안은 현재 작업을 막는 결함과 구분한다. 리뷰 담당 세션이 수정까지 수행하면 다음 검토에서 다시 자기 변경을 평가하게 되므로 수정은 구현 담당 세션으로 돌려보낸다.

### 실패 예시

구현 담당 세션이 인증 오류를 모두 `401`로 바꾼 뒤 같은 대화에서 API 리뷰를 수행한다고 가정한다. 구현 대화에 “존재 여부를 숨기기 위한 보안 결정”이라는 설명이 있으면 reviewer가 요구사항에 없는 결정을 전제로 삼을 수 있다. 별도 리뷰 세션은 요구사항, 이전 응답 형식, API 지침과 diff만 읽어 인증 실패와 권한 부족의 응답을 각각 다시 판정한다.

반대로 리뷰 세션에 diff만 주고 요구사항을 주지 않으면 `401`과 `403` 중 어느 동작을 유지해야 하는지 알 수 없다. 세션 분리는 판단 근거를 없애는 방식이 아니라 구현자의 미승인 설명을 제외하는 방식이다.

## TDD commit을 읽는 순서

### 새 동작을 구현할 때

branch의 기준을 `C0`, 테스트만 추가한 commit을 `C1`, 구현 commit을 `C2`라고 한다. 리뷰 담당 세션은 다음 순서로 한 번의 리뷰를 수행할 수 있다.

1. `C0..C1`에서 테스트 이름, 입력과 예상 결과가 어느 요구사항을 확인하는지 읽는다.
2. `C0`의 구현에 `C1` 테스트를 실행했을 때 의도한 이유로 실패한 기록을 확인한다.
3. `C1..C2`에서 테스트를 바꾸지 않고 구현이 동작을 충족했는지 확인한다.
4. `C0..C2` 전체에서 테스트와 구현이 함께 완결된 변경인지 확인한다.

`C1`은 리뷰 순서를 위한 branch 내부 checkpoint다. 기본 branch에 단독으로 병합하면 build나 필수 검사를 깨뜨리는 저장소에서는 `C1`을 따로 병합하지 않는다. 저장소가 모든 commit의 성공을 요구하면 실패 테스트를 비활성화해 숨기지 말고, patch나 별도 실행 기록으로 Red 상태를 남긴 뒤 테스트와 구현을 하나의 성공 commit으로 만들 수 있다.

### 기존 동작을 보존하며 리팩터링할 때

현재 동작을 설명하는 테스트가 없다면 characterization test를 먼저 추가하고 성공하는 독립 변경으로 제출할 수 있다. 그다음 리팩터링 commit은 테스트를 바꾸지 않은 채 같은 동작을 유지해야 한다. 이 경우 테스트 commit 자체가 기존 코드를 깨뜨리지 않으므로 별도 제출의 이점이 크다.

### 리뷰 담당 세션이 테스트에서 확인할 사항

- 테스트의 각 기대값이 요구사항이나 보존할 현재 동작에서 나왔는가.
- 요구사항을 결정하는 조건을 제거하거나 반대로 바꾸면 테스트가 실패하는가.
- 성공 사례만이 아니라 오류, 값의 한계와 상태 전이를 확인하는가.
- 내부 함수 호출 순서처럼 바뀔 수 있는 구현 세부사항에만 의존하지 않는가.
- assertion이 단순히 값의 존재나 상태 코드 범주만 확인해 잘못된 결과를 통과시키지 않는가.
- fixture와 mock이 실제로 검증해야 할 실행 흐름을 우회하지 않는가.

예를 들어 할인 계산 테스트가 결과가 0보다 크다는 사실만 확인하면 잘못된 할인율도 통과한다. 요구사항이 10,000원 주문에 10퍼센트 할인을 정했다면 9,000원이라는 결과와 적용되지 않는 한계값을 확인해야 한다. reviewer는 구현을 보기 전에 이 기대값의 근거를 요구사항에서 찾고, 구현을 본 뒤 조건을 반대로 바꾼 경우 테스트가 실패할지 판단한다.

## 한 번의 리뷰와 Git 기록 감시

한 작업의 리뷰 입력은 변경되지 않는 commit 범위로 고정한다. 리뷰 시작 시점의 마지막 commit을 기록하고 그 범위를 한 번 검토한 뒤 결과를 반환한다. 구현 담당 세션이 수정하면 새 마지막 commit이 생기므로 기존 리뷰를 반복하지 않고, 수정된 지적의 확인은 별도 입력 단위로 다룬다. 현재 요구사항의 “각 작업마다 1회”는 이 방식으로 해석할 수 있다.

리뷰 전용 세션을 장시간 유지해야 한다면 매번 전체 Git 기록을 다시 읽지 않는다. 마지막으로 본 commit OID와 현재 OID를 비교해 같으면 새 리뷰를 시작하지 않는다. 일정 시간 변화가 없다는 사실은 다음 두 상태 중 하나다.

- 구현 작업이 아직 진행 중이거나 외부 결과를 기다리는 중이면 대기 또는 pause 상태다.
- 리뷰 요청이 취소됐거나 더 이상 새 변경이 없으면 정상 종료 상태다.

다음 입력을 얻을 방법이 없거나, 승인이나 접근 권한이 없어 진행할 수 없고 안전한 대안도 없을 때만 막힌 상태다. 따라서 “30분 동안 commit이 없으면 Blocked” 같은 규칙은 사용하지 않는다. “새 commit이 생기면 그 commit 범위를 한 번 리뷰하고, 없으면 다시 읽지 않는다”를 중단 규칙으로 삼는다.

## 도입 전 평가할 지표

동일한 유형의 작업을 현재 방식과 분리 방식으로 수행해 다음 값을 비교해야 한다.

- 구현 및 리뷰 세션의 입력과 출력 토큰 합계
- 첫 변경부터 리뷰 결과까지 걸린 시간
- 요구사항 위반 중 reviewer가 찾은 수와 사람이 추가로 찾은 수
- 잘못된 지적과 근거가 부족한 지적 수
- 테스트가 알려진 결함 또는 준비한 mutation을 실제로 잡은 비율
- 같은 commit을 중복 검토한 횟수

분리 방식이 한두 사례에서 더 많은 결함을 찾았다는 사실만으로 기본 운영 규칙으로 채택하지 않는다. 적어도 대표 작업군마다 같은 평가 입력과 정답 기준을 두고 비교해야 한다.

## 남은 결정

- 이 저장소에서 branch 내부의 실패 테스트 commit을 허용할지, 모든 commit이 검사를 통과해야 하는지 정해야 한다.
- 리뷰 담당 세션이 결과를 반환한 뒤 수정 확인을 새 작업으로 볼지, 원래 작업의 조건부 후속 단계로 볼지 정해야 한다.
- Goal이 아닌 task 대기나 알림으로 새 commit을 감지할 필요가 있는지 운영 환경에서 확인해야 한다.
- 별도 리뷰 대화가 실제 결함 발견률과 토큰 사용량을 개선하는지는 대표 작업 평가 전에는 확정할 수 없다.
