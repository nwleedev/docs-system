# 지침 크기와 금지 문구 설계 조사

## 조사 결론

현재 근거는 AGENTS.md와 `SKILL.md`를 금지 문구 중심으로 바꾸는 방안을 지지하지 않는다. 금지해야 할 행동은 남겨야 하지만, 금지 문구만으로는 모델이 대신 수행할 행동과 완료 조건을 알 수 없다. 특히 부정형 지시를 이해하는 능력을 측정한 연구에서는 조사한 모델들이 원래 지시보다 부정형 지시에서 낮은 성능을 보였다. 현재 OpenAI 지침도 결과, 성공 조건과 허용된 행동을 먼저 밝히고, `ALWAYS`나 `NEVER` 같은 절대 규칙은 실제 불변 조건에만 사용하라고 권한다.

지침 용량은 줄인 바이트 수가 아니라 같은 대표 작업에서 유지되는 행동으로 평가해야 한다. 모든 호출에 필요한 절차는 `SKILL.md`에 한 번만 두고, 특정 작업에서만 필요한 판정 기준은 읽을 조건이 분명한 참고 파일로 옮기며, 반복 가능한 탐지는 스크립트가 맡는 구조가 적합하다. 축소 전후에 같은 평가 사례를 실행하지 않으면 중복을 없앤 것인지 필요한 조건을 지운 것인지 구분할 수 없다.

두 `_README.md`는 원본 저장소에서 조건부 시작 자료이지만 애플리케이션 저장소에 복사된 뒤에는 반복해서 사용하는 기준 문서가 된다. 따라서 원본 파일이 직접 읽히는지에만 근거해 비용을 제외하면 안 된다. 배포 원본의 구성, 복사된 기준 문서의 실제 사용량과 Skill 실행 시 읽는 자료를 서로 다른 단계로 측정해야 한다.

설계 문서용 `_README.md`는 애플리케이션 저장소의 `docs/designs/README.md`로, 개발 지침용 `_README.md`는 `docs/dev/README.md`로 복사된다. 복사된 파일 하나만으로 문서 기준을 제공해야 하므로 여러 파일로 분할하는 방안은 최적화 후보에서 제외한다. 파일 안에서 모든 문서에 공통으로 적용하는 규칙은 한 번만 설명하고, 문서 종류별 절에는 그 종류에만 필요한 생성 조건, 필수 정보, 금지 내용과 검증 방법을 남기는 방안을 평가해야 한다.

`use-words-review`에서 서브에이전트 호출을 모든 검토의 필수 단계로 둘 근거도 부족하다. 현재 절차는 서브에이전트가 낸 판정을 메인 에이전트가 원문과 다시 대조하도록 하므로, 간단한 문구 검토에도 전달용 문맥 작성, 별도 추론과 재검증 비용이 발생한다. 기본값을 메인 세션의 1회 검토로 바꾸고, 서로 독립된 관점이 실제로 필요하며 그 효과가 평가 사례에서 확인된 작업만 별도 리뷰 세션으로 보내는 방안을 우선 검토할 수 있다. 이때 메인 세션 판정을 독립 검토라고 부르면 안 되며, 변경 전에 각 방식의 문제 누락, 잘못된 지적, 토큰과 경과 시간을 같은 사례로 비교해야 한다.

이 문서는 [Skill 용량과 금지 지침에 관한 요구사항](../requirements.md#목표)을 조사한 자료이며 실제 지침 변경을 승인하지 않는다. 최초 조사일은 2026년 8월 27일이고, 공개 오픈소스 안티패턴 조사 방식은 2026년 8월 28일에 추가로 반영했다.

## 외부 근거

Anthropic의 공식 `skill-creator`는 Skill 이름과 설명, `SKILL.md`, 필요할 때 읽는 참고 자료를 단계적으로 불러오는 구조를 설명한다. 본문은 500줄 미만을 이상적인 기준으로 제시하고, 큰 참고 파일은 언제 읽을지 본문에 적도록 한다. 2026년 8월 27일 GitHub API로 공식 저장소의 파일과 최근 변경 `b0cbd3df1533b396d281a6886d5132f623393a9c`를 확인했다. 500줄은 품질 기준이나 이 저장소의 목표 크기가 아니라 참고 상한이다. [Anthropic, skill-creator](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md)

OpenAI의 현재 Skill 안내도 이름과 설명을 먼저 제공하고 Skill이 선택된 뒤 `SKILL.md` 전체를 읽는 단계적 로딩을 설명한다. 이 안내에 따르면 스크립트와 참고 문서는 선택 자료로 분리할 수 있지만, 선택된 `SKILL.md` 본문은 전체가 입력된다. 따라서 본문에 남길 공통 절차와 조건부 참고 자료를 구분하는 것이 실제 입력을 줄이는 직접 수단이다. [OpenAI, Build skills](https://learn.chatgpt.com/docs/build-skills)

OpenAI의 현재 모델 지침은 반복 지침과 예시를 제거하고 도구 설명을 간결하게 한 내부 coding-agent 평가에서 평가 점수가 약 10퍼센트에서 15퍼센트 높아지고 전체 토큰이 41퍼센트에서 66퍼센트 줄었다고 보고한다. 작업마다 결과가 달라지므로 한 묶음씩 제거한 뒤 같은 평가를 다시 실행하라고 권한다. 또한 각 지침을 한 번만 적고, 장기 세션에서 반복 prompt와 tool 내용이 증폭될 수 있다고 설명한다. [OpenAI, Favor leaner prompts](https://developers.openai.com/api/docs/guides/latest-model#favor-leaner-prompts)

부정형 prompt를 9개 NLP task와 여러 크기의 OPT, GPT-3, InstructGPT에 적용한 연구에서는 모델 크기가 커져도 부정형 지시의 성능이 개선되지 않았고 원래 지시와 큰 차이가 남았다. 이 연구는 2023년 모델과 분류형 과제를 다루므로 현재 coding agent의 모든 금지 규칙에 그대로 적용할 수 없다. 다만 “하지 말아야 할 것만 쓰면 더 잘 따른다”는 일반 주장을 지지하지 않으며, 부정형 지시를 별도 평가해야 한다는 근거는 된다. [Jang, Ye와 Seo, Can Large Language Models Truly Understand Prompts?](https://proceedings.mlr.press/v203/jang23a.html)

OpenAI의 현재 prompt 지침은 기대 결과, 성공 조건, 제약과 종료 조건을 먼저 쓰도록 한다. `ALWAYS`, `NEVER`, `must`, `only`는 안전 규칙이나 필수 출력처럼 실제 불변 조건에 사용하고, 검색 여부나 반복 횟수처럼 판단이 필요한 행동에는 결정 규칙을 쓰라고 한다. 같은 문서는 허용된 안전한 행동도 명시해 불필요한 승인 요청을 줄이라고 권한다. [OpenAI, Outcome-first prompts and stopping conditions](https://developers.openai.com/api/docs/guides/latest-model#outcome-first-prompts-and-stopping-conditions), [OpenAI, Define autonomy and approval boundaries](https://developers.openai.com/api/docs/guides/latest-model#define-autonomy-and-approval-boundaries)

OpenAI는 다중 에이전트 실행이 여러 독립 작업으로 나뉘는 복잡한 문제에서 경과 시간을 줄이고 성능을 높일 수 있다고 설명한다. 같은 지침은 도구 호출이 여러 개라는 사실만으로 복잡한 실행 방식을 선택하지 말고, 대표 작업에서 성공률, 근거 완전성, 토큰, 지연과 비용을 비교하라고 한다. 따라서 “검토이므로 서브에이전트를 쓴다”가 아니라 검토 작업이 실제로 독립 분할되는지와 추가 호출의 이득을 측정해야 한다. [OpenAI, Multi-agent와 평가 지침](https://developers.openai.com/api/docs/guides/latest-model#what-is-new)

Anthropic의 Research 시스템은 넓은 조사에서 서브에이전트가 독립된 문맥으로 여러 방향을 동시에 탐색하는 이점을 보고했다. 반면 자체 자료에서 다중 에이전트 시스템은 일반 대화의 약 15배 토큰을 사용했고, 공유 문맥과 작업 간 의존이 큰 분야에는 맞지 않으며 대부분의 코딩 작업도 독립적으로 나눌 부분이 조사보다 적다고 설명한다. 이 수치는 Anthropic의 특정 Research 시스템에서 측정한 값이므로 `use-words-review`의 예상 비용으로 환산할 수 없지만, 필수 호출의 비용을 따로 측정해야 한다는 근거가 된다. [Anthropic, How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)

Google Research와 공동 연구진은 180개 에이전트 구성 평가에서 병렬화 가능한 작업은 중앙 조정 방식이 단일 에이전트보다 나았지만, 순차 추론 작업에서는 조사한 모든 다중 에이전트 구성이 39퍼센트에서 70퍼센트 낮은 성능을 보였다고 보고했다. 독립 에이전트의 판정을 마지막에 합치는 방식은 오류 증폭도 가장 컸다. `use-words-review`가 검사 결과, 참고 자료, 문맥 판정과 최종 대조를 차례로 수행한다는 점을 고려하면, 에이전트 수보다 이 순차 의존과 판정 통합 방식을 먼저 평가해야 한다. [Google Research, Towards a science of scaling agent systems](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/), [Kim 외, Towards a Science of Scaling Agent Systems](https://arxiv.org/abs/2512.08296)

Silo-Bench 사전 공개 논문은 30개 알고리즘 작업과 1,620회 실험에서 에이전트들이 필요한 정보를 교환하고도 분산된 상태를 최종 추론으로 합치는 단계에서 실패할 수 있으며, 에이전트 수가 늘면 조정 비용이 병렬화 이득을 없앨 수 있다고 보고한다. 이는 문구 검토 정확도를 직접 측정한 연구는 아니지만, 여러 에이전트의 판정이 생겼다는 사실을 검토 품질의 증거로 간주하면 안 된다는 반례를 제공한다. [Zhang 외, Silo-Bench](https://arxiv.org/abs/2603.01045)

Anthropic의 에이전트 설계 지침은 단순한 방법으로 시작하고, 복잡성이 결과를 실제로 개선할 때만 다단계 에이전트 구성을 추가하라고 권한다. 별도 평가자 호출은 평가 기준이 명확하고 반복 수정이 측정 가능한 개선을 만들 때 적합하다고 설명한다. 따라서 `use-words-review`에는 상시 서브에이전트 호출보다 먼저 명확한 판정 사례와 종료 조건이 필요하다. [Anthropic, Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)

Anthropic의 장시간 개발 실험은 새 세션과 구조화된 전달 자료로 이전 작업의 추론에서 벗어날 수 있다고 설명한다. 동시에 전달 자료가 다음 세션에 충분한 상태를 담아야 하고, 이런 분리는 매 실행의 조정 복잡성, 토큰과 지연을 늘린다고 보고한다. 별도 리뷰 세션도 독립성을 자동으로 보장하는 장치가 아니라, 필요한 근거만 전달하고 추가 비용을 측정해야 하는 선택지로 다뤄야 한다. [Anthropic, Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps)

긴 입력을 처리할 수 있는 모델도 질문에 답하는 정보가 입력 가운데에 있을 때 검색과 질의응답 성능이 낮아질 수 있다는 실험 결과가 있다. 이 연구는 현재 Skill 파일을 직접 평가하지 않았으므로 특정 줄 수를 정하는 근거가 되지는 않는다. 다만 중요한 절차를 긴 문서에 넣었다는 사실만으로 실행 중 회수를 확신하지 말고, 대표 작업에서 그 절차가 실제 판정에 사용됐는지 확인해야 한다. [Liu 외, Lost in the Middle](https://aclanthology.org/2024.tacl-1.9/)

## 문서 크기 문제를 세 단계로 나누어 해결한다

### 배포 원본과 애플리케이션 기준 문서를 구분한다

`skills/use-design-docs/references/_README.md`와 `skills/use-dev-guidance/references/_README.md`는 새 저장소 기준을 만드는 시작 자료다. 복사 뒤에는 애플리케이션 저장소의 `docs/designs/README.md`와 `docs/dev/README.md`가 현재 기준을 관리하며, 원본과 자동으로 동기화하지 않는다. 따라서 이 저장소에서는 공통 시작 자료의 중복과 배포 방식을 조사하고, 애플리케이션 저장소에서는 복사된 문서가 실제 작업에서 읽힌 횟수와 입력 토큰을 측정한다.

설계 문서용 파일과 개발 지침용 파일은 각각 하나의 README로 복사되어 독립적으로 사용되어야 한다. 본문을 다른 참고 파일로 옮기거나 복사할 파일을 늘리는 변경은 이 요구사항을 충족하지 않는다. 같은 주체, 적용 조건, 수행할 일과 후속 상태를 설명하는 규칙이 파일 안에서 반복될 때만 공통 절로 합친다. 한 문장을 없앴을 때 애플리케이션 저장소의 에이전트가 문서 생성 조건, 작성 권한, 필수 정보, 금지 내용 또는 검증 방법을 판단할 수 없다면 그 문장은 유지한다.

### 항상 읽는 내용과 조건부 자료를 구분한다

`SKILL.md`에는 실행 조건, 중단 조건, 입력, 반환 형식과 참고 자료 선택 규칙처럼 매 실행에 필요한 내용만 둔다. 특정 언어, 산출물 또는 경고 종류에서만 필요한 사례와 판정 근거는 참고 파일에 두고, 본문에는 그 파일을 읽을 조건과 읽지 않을 조건을 함께 적는다. AGENTS.md, Skill과 저장소 README에 같은 절차가 반복되면 책임 문서 한 곳을 정하고 나머지 문서는 호출 조건이나 링크만 남긴다.

이 조건부 참고 자료 분리는 Skill 실행 자료에만 적용한다. 애플리케이션 저장소의 단독 기준이 되는 `_README.md`에는 적용하지 않는다. Skill은 README의 위치 확인, 생성 승인, 작업 선택과 실행 순서를 맡고, 복사된 README는 문서 구조, 작성 권한, 필수 정보와 검증 기준을 맡도록 중복 책임을 정리한다.

이 구분은 문장을 짧게 고치는 작업과 다르다. 긴 문장을 여러 파일에 복제하거나 모든 참고 파일을 항상 읽게 하면 전체 입력은 줄지 않는다. 반대로 안전이나 승인처럼 모든 작업에 필요한 규칙을 조건부 참고 자료로 옮기면 파일 크기는 줄어도 행동이 달라진다.

### 실제 작업에서 행동과 비용을 함께 측정한다

대표 작업마다 어떤 Skill과 참고 문서를 읽었는지, 실행 환경이 보고한 입력 및 출력 토큰, 경과 시간과 기대 판정을 기록한다. 입력 토큰을 제공하지 않는 실행 환경에서는 바이트 수를 토큰으로 환산하지 않고 측정 불가로 기록한다. 같은 기대 판정을 모두 만족한 변경끼리만 비용을 비교한다.

한 번에는 반복 사례 제거, 참고 자료 선택 조건 변경 또는 `_README.md` 내부의 공통 규칙 통합 중 한 묶음만 바꾼다. 변경 뒤 기대 판정이 달라지면 크기 감소를 채택 근거로 삼지 않는다. 현재 자료에는 적정 바이트 수나 감소율을 정할 근거가 없으므로 숫자 목표는 후속 평가보다 먼저 만들지 않는다.

## 필수 서브에이전트 의존성 검토

### 현재 의존성과 비용 발생 지점

현재 `use-words-review`는 모든 산출물에 기계 검사를 실행하고 필요한 참고 자료를 읽은 뒤, 검토에 필요한 자료만 추린 메시지를 서브에이전트에 전달한다. 서브에이전트는 읽기 전용 의미 검토를 수행하고, 메인 에이전트는 모든 지적을 원문과 저장소 규칙에 다시 대조한다. 서브에이전트를 사용할 수 없을 때에는 같은 기준을 메인 문맥에서 적용하는 대체 절차도 이미 정의되어 있다.

이 구조에서 서브에이전트만 수행할 수 있는 일은 독립된 문맥에서 두 번째 판정을 내리는 것이다. 기계 검사, 참고 자료 선택, 근거 수집, 최종 판정 채택과 커밋 중단 여부는 메인 에이전트의 책임이다. 따라서 필수 호출을 없애도 검사 기준 자체는 유지할 수 있지만 다음 비용과 성질이 달라진다.

- 전달 메시지를 만들고 같은 근거를 다른 문맥에서 다시 읽는 입력 비용이 사라진다.
- 별도 모델 호출을 기다리고 결과를 다시 대조하는 경과 시간이 줄어든다.
- 서브에이전트를 제공하지 않는 실행 환경에서도 동일한 기본 절차를 사용할 수 있다.
- 작성에 사용한 문맥과 분리된 판정을 얻지 못하므로 결과를 독립 검토라고 표시할 수 없다.
- 작성자가 자신의 표현을 정당화하는 방향으로 판정할 가능성을 별도 관점으로 완화하지 못한다.

### 검토 방식 후보

**메인 세션 1회 검토를 기본값으로 사용.** 기계 검사와 의미 판정을 한 공유 단위의 마지막에 한 번 수행한다. 문구 후보를 찾을 때마다 검토를 다시 시작하지 않으며, 검토에서 확인된 수정만 적용한 뒤 형식과 민감정보 검사를 실행한다. 일반 문서와 낮은 영향의 변경에서 반복 비용을 가장 적게 만들지만 독립성은 제공하지 않는다.

**조건부로 별도 리뷰 세션 사용.** 개인정보, 보안, 라이선스, 승인 주체 또는 외부 공개 문구를 잘못 쓰면 영향이 크거나, 작성 문맥을 모르는 검토자의 판정이 필요할 때 별도 세션에 고정된 변경사항과 검토 기준을 전달한다. 구현 또는 작성 세션 내부의 자식 에이전트가 아니라 독립된 세션을 쓰면 작성 과정의 추론을 이어받지 않는다는 운영 조건을 분명히 할 수 있다. 다만 전달 자료가 부족하면 근거를 놓치고, 많으면 문맥 비용이 다시 커진다.

**필수 서브에이전트 방식을 유지.** 모든 저장과 커밋에 독립된 두 번째 판정을 확보하려는 경우다. 현재 실행 환경이 서브에이전트를 제공해야 하며, 낮은 영향의 짧은 문구에도 같은 전달과 대조 비용을 지불한다. 이 방식을 유지하려면 메인 단독 방식보다 놓친 문제를 유의미하게 줄인다는 저장소 평가가 필요하다.

현재 조사에서는 메인 세션 1회 검토를 기본값으로 삼고 조건부 별도 리뷰 세션을 두는 방안이 가장 검증할 가치가 높다. 이는 구현 결정이 아니다. 별도 세션의 생성 권한, 적용 대상과 전달 형식도 아직 승인되지 않았다.

### 변경 전에 비교할 사례와 지표

같은 저장 문구를 현재 필수 서브에이전트 방식, 메인 세션 1회 방식과 별도 리뷰 세션 방식에 각각 적용한다. 각 실행은 작성 완료 후 한 번만 검토하고, 검토 결과를 보고 다시 검토하지 않는다.

평가 사례에는 자연스러운 대체 표현이 있는 경고, 기술 용어라 유지해야 하는 경고, 근거가 없어 사람의 판단이 필요한 문장, 개인 경로가 섞인 문장, 멀리 떨어진 문장 사이에서 책임 주체가 바뀌는 문단을 포함한다. 작성자가 이미 선택한 표현을 과도하게 옹호하는 사례와, 반대로 경고 후보를 근거 없이 모두 고치는 사례도 넣는다.

각 방식에서 문제 누락, 잘못된 지적, `needs human input` 누락, 근거 없는 수정 제안, 입력 및 출력 토큰, 경과 시간과 모델 호출 수를 기록한다. 별도 관점이 추가로 찾은 문제가 최종 대조에서 실제 결함으로 확인됐는지도 구분한다. 메인 세션 방식이 승인된 기대 판정을 모두 충족하면 필수 서브에이전트 지침을 제거할 수 있다. 그렇지 않으면 실패한 사례의 성질에 따라 조건부 별도 세션의 적용 대상을 정하고, 실패 사례가 모든 검토에 공통되는지 별도로 확인한다.

## 금지 문구가 필요한 경우와 부족한 경우

금지 문구는 실행하면 복구하기 어렵거나 정책을 위반하는 행동에 적합하다. 대상, 조건과 대신 수행할 행동을 함께 써야 한다.

예를 들어 다음 문장은 금지 대상만 있다.

> 사용자 승인 없이 파일을 삭제하지 않는다.

이 문장은 삭제 대신 무엇을 해야 하는지 알려주지 않는다. 다음처럼 판정과 후속 행동을 더할 수 있다.

> 삭제 대상과 영향이 사용자의 요청에서 확정되지 않으면 파일을 바꾸지 않고 정확한 대상을 확인한다. 삭제가 필요하지만 복구 가능한 이동으로 목적을 달성할 수 있으면 그 방법을 먼저 제안한다.

반대로 다음처럼 수행 지침만 있으면 위험한 예외를 놓칠 수 있다.

> 실패한 테스트를 모두 통과시킨다.

이 지침은 테스트 삭제나 assertion 약화도 성공으로 오인할 수 있다. 기대 결과와 금지 조건을 함께 써야 한다.

> 실패 원인을 고치고 실패한 동작을 확인하는 테스트를 실행한다. 테스트를 삭제하거나 assertion을 약화해 실패를 숨기지 않는다. 요구사항과 테스트가 충돌하면 둘 중 하나를 임의로 바꾸지 않고 충돌 근거를 보고한다.

따라서 선택 기준은 긍정형과 부정형 중 어느 쪽이 더 중요한지가 아니다. 결과와 정상 행동을 먼저 쓰고, 실제로 발생했거나 피해가 큰 우회 행동만 금지하며, 실패했을 때 중단하거나 문의할 조건을 이어 쓴다.

## 안티패턴 금지 지침과 조사 기록을 구분한다

`God object를 사용하지 않는다`처럼 이름만 금지하는 문장은 판정할 실패, 적용 조건과 예외를 제공하지 않는다. 그렇다고 이 문서에서 임의의 클래스 크기나 책임 개수를 정해 판정 기준으로 바꾸면 근거 없는 안티패턴 정의가 된다.

안티패턴과 권장 패턴의 실제 항목은 작업 중인 애플리케이션 코드를 보지 않고 공개 오픈소스 애플리케이션의 수정 commit이나 pull request, 고정된 revision과 공식 작성 방식을 교차 검증해 작성한다. 상세 설명, 수정 전후를 줄인 코드 예시, 권장 이유, 적용 조건, lint 설정과 탐지 한계까지 갖추지 않은 문장은 조사 항목이 아니라 조사 질문으로 남긴다. 자료 선택과 기록 형식은 [공개 오픈소스 애플리케이션에서 근거를 찾는 절차](agent-workflow-and-review-research.md#공개-오픈소스-애플리케이션에서-근거를-찾는-절차)가 관리한다.

따라서 배포 지침에는 검증된 조사 항목 전체를 다시 복사하지 않는다. 현재 작업에 적용되는 항목을 읽을 조건, 위반으로 판정할 관찰 가능한 결과와 사용할 검사만 남긴다. 같은 코드 모양을 판정하는 lint가 없으면 규칙 이름을 만들지 않고 type 검사, 테스트, 실행 증거 또는 담당 리뷰를 지정한다.

## 같은 행동을 유지하며 Skill을 줄이는 절차

### 1. 먼저 행동 기준을 고정한다

Skill을 수정하기 전에 대표 입력과 기대 판정을 만든다. `use-words-review`라면 다음 사례를 포함할 수 있다.

- 문제 후보가 있지만 자연스러운 대체 문장이 있어 `needs revision`인 한국어 문장
- API 이름이나 정확한 기술 용어라서 후보 표현을 유지해야 하는 문장
- 책임 주체가 없어 새 뜻을 추정할 수 없으므로 `needs human input`인 문장
- 개인정보가 있는 절대 경로를 제거해야 하는 문장
- 경고가 없지만 문장 사이의 승인 관계가 끊긴 문단

각 사례에는 판정뿐 아니라 바꿀 위치, 대체 문장 또는 유지 근거가 있어야 한다. 전체 결과가 같은지 확인하지 않고 파일만 줄이면 행동 보존을 확인할 수 없다.

### 2. 항상 필요한 내용만 본문에 남긴다

다음 내용은 `SKILL.md` 본문 후보이다.

- Skill이 실행되는 조건과 실행하지 않는 조건
- 입력과 최종 결과 형식
- 반드시 지켜야 할 순서와 중단 조건
- 참고 파일을 선택하는 조건
- 스크립트 결과를 해석하는 책임

긴 사례, 언어별 판정 목록, 특정 산출물에만 적용되는 설명과 중복된 근거는 참고 파일 후보이다. 본문과 참고 파일에 같은 규칙을 반복하지 않는다.

### 3. 참고 파일의 선택 조건을 구체화한다

파일을 잘게 나눈 뒤 모두 읽도록 하면 호출과 토큰이 오히려 늘어난다. 예를 들어 한국어 검사 결과에 문장 관계 경고가 없고 한 낱말의 대체 표현만 판정한다면 낱말 판정 자료만 읽게 할 수 있다. 반대로 긴 문단이나 지칭 관계를 판단해야 하면 문장 관계 자료를 추가로 읽는다.

참고 파일마다 다음 정보를 본문에 둔다.

- 어떤 입력이나 검사 경고가 있을 때 읽는가.
- 어떤 경우에는 읽지 않는가.
- 그 파일을 읽고 어떤 판정을 내려야 하는가.

### 4. 기계 검사와 의미 판정을 분리한다

문자열 탐지, 줄 번호, 파일 형식과 금지된 개인 경로는 스크립트가 반복 가능하게 찾을 수 있다. 문장이 실제 대상을 밝히는지, 대체 문장이 뜻을 보존하는지와 전문용어를 유지해야 하는지는 모델이나 사람이 판정한다. 스크립트로 옮긴 규칙을 본문에서 다시 긴 목록으로 설명하지 않고, 결과를 어떻게 처리할지만 남긴다.

### 5. 한 묶음씩 줄이고 같은 평가를 실행한다

다음 값을 변경 전후에 기록한다.

- Skill 본문과 실제로 읽은 참고 파일의 입력 토큰
- 전체 경과 시간과 도구 호출 수
- 기대 판정과 일치한 사례 수
- 놓친 문제와 잘못 지적한 문제 수
- 대체 문장을 적용한 수와 원문을 유지한 수

한 번에 구조 전체를 바꾸면 어떤 삭제가 회귀를 만들었는지 알 수 없다. 중복 사례, 반복 규칙, 참고 파일 순서처럼 한 묶음씩 바꾸고 같은 평가를 한 번 실행한다. 성능이 유지되지 않으면 크기 목표보다 행동 기준을 우선한다.

## 프로젝트 반영 후보

다음 항목은 조사 결과에서 나온 변경 후보이며 아직 승인된 구현 항목이 아니다.

- `use-words-review`에서 모든 검토가 읽는 자료와 한국어 경고 종류에 따라 읽는 자료를 구분한다.
- `use-words-review`의 필수 서브에이전트 호출을 메인 세션 1회 검토로 바꿀 수 있는지 같은 평가 사례로 비교한다.
- 독립된 관점이 필요한 고영향 문구는 작성 세션의 자식 에이전트 대신 별도 리뷰 세션으로 전달하는 조건을 정한다.
- AGENTS.md의 금지 문구 중 대체 행동이나 문의 조건이 없는 항목을 찾아 정상 행동과 중단 조건을 추가한다.
- 공개 오픈소스 애플리케이션의 수정 근거로 만든 안티패턴 항목 중 현재 작업 조건에 맞는 항목만 저장소별 개발 지침과 검사에 연결한다.
- Skill별 대표 평가 사례, 실제 입력 토큰과 판정 정확도를 기록한 뒤 파일을 한 묶음씩 줄인다.
- 같은 규칙이 AGENTS.md, Skill 본문과 참고 파일에 반복되면 책임 문서 한 곳을 정하고 다른 문서는 읽기 조건만 둔다.
- 두 `_README.md`는 각각 한 파일로 유지하고, 파일 안에서 모든 문서에 적용되는 반복 규칙을 한 곳으로 합칠 수 있는지 대표 작업으로 확인한다.

## 남은 결정

- Skill별로 어떤 작업 표본과 기대 판정을 행동 보존 기준으로 삼을지 정해야 한다.
- 필수 서브에이전트 호출을 제거할 최소 통과 기준과 조건부 별도 리뷰 세션의 적용 대상을 정해야 한다.
- 별도 리뷰 세션을 사용할 경우 생성 권한, 전달 자료와 판정을 현재 작업에 반영할 책임을 정해야 한다.
- 참고 파일을 경고 종류별로 나눌 때 파일 호출 증가가 토큰 감소보다 큰지 측정해야 한다.
- 애플리케이션 저장소에 복사된 두 기준 README가 어떤 작업에서 얼마나 자주 읽히는지 실제 실행값을 확보해야 한다.
- `_README.md` 안에서 합칠 반복 규칙과 문서 종류별로 보존할 고유 기준을 대표 작업의 기대 판정으로 확정해야 한다.
- 금지 규칙을 실제 불변 조건으로 판정할 책임자와 예외 승인 방식을 정해야 한다.
- 현재 파일의 목표 바이트나 토큰 수는 근거가 없으므로 평가 전에 임의로 정하지 않는다.
