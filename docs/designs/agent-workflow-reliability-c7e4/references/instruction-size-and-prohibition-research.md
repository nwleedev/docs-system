# 지침 크기와 금지 문구 설계 조사

## 조사 결론

현재 근거는 AGENTS.md와 `SKILL.md`를 금지 문구 중심으로 바꾸는 방안을 지지하지 않는다. 금지해야 할 행동은 남겨야 하지만, 금지 문구만으로는 모델이 대신 수행할 행동과 완료 조건을 알 수 없다. 특히 부정형 지시를 이해하는 능력을 측정한 연구에서는 조사한 모델들이 원래 지시보다 부정형 지시에서 낮은 성능을 보였다. 현재 OpenAI 지침도 결과, 성공 조건과 허용된 행동을 먼저 밝히고, `ALWAYS`나 `NEVER` 같은 절대 규칙은 실제 불변 조건에만 사용하라고 권한다.

지침 용량은 줄인 바이트 수가 아니라 같은 대표 작업에서 유지되는 행동으로 평가해야 한다. 모든 호출에 필요한 절차는 `SKILL.md`에 한 번만 두고, 특정 작업에서만 필요한 판정 기준은 읽을 조건이 분명한 참고 파일로 옮기며, 반복 가능한 탐지는 스크립트가 맡는 구조가 적합하다. 축소 전후에 같은 평가 사례를 실행하지 않으면 중복을 없앤 것인지 필요한 조건을 지운 것인지 구분할 수 없다.

이 문서는 [Skill 용량과 금지 지침에 관한 요구사항](../requirements.md#목표)을 조사한 자료이며 실제 지침 변경을 승인하지 않는다. 조사일은 2026년 8월 27일이다.

- **`skills/use-design-docs/references/_README.md`.** 241줄, 20,560바이트다. 저장소 README가 없을 때 대체 기준으로 사용한다.
- **`skills/use-dev-guidance/SKILL.md`.** 104줄, 9,456바이트다. 코드와 개발 지침 작업에서 실행한다.
- **`skills/use-dev-guidance/references/_README.md`.** 206줄, 19,776바이트다. 저장소 README가 없을 때 대체 기준으로 사용한다.
- **`skills/use-words-review/SKILL.md`.** 114줄, 14,152바이트다. 저장하거나 공유할 글을 검토할 때 실행한다.
- **`skills/use-words-review/references/examples.md`.** 214줄, 10,018바이트다. 모든 언어의 의미 판정을 보정할 때 읽는다.
- **`skills/use-words-review/references/korean.md`.** 179줄, 12,112바이트다. 한국어 문서나 문구를 검토할 때 읽는다.

이 목록은 큰 파일을 알려줄 뿐 불필요한 문장을 알려주지 않는다. 예를 들어 `_README.md`는 fallback에서만 읽으므로 평소 실행 비용에 포함되지 않을 수 있다. 반면 한국어 글을 자주 검토하면 `use-words-review` 본문과 두 참고 파일을 함께 읽는 비용이 반복된다. 최적화 우선순위는 파일 크기 순서가 아니라 실제 호출 빈도와 조건별 입력 토큰으로 정해야 한다.

## 외부 근거

Anthropic의 공식 `skill-creator`는 Skill 이름과 설명, `SKILL.md`, 필요할 때 읽는 참고 자료를 단계적으로 불러오는 구조를 설명한다. 본문은 500줄 미만을 이상적인 기준으로 제시하고, 큰 참고 파일은 언제 읽을지 본문에 적도록 한다. 2026년 8월 27일 GitHub API로 공식 저장소의 파일과 최근 변경 `b0cbd3df1533b396d281a6886d5132f623393a9c`를 확인했다. 500줄은 품질 기준이나 이 저장소의 목표 크기가 아니라 참고 상한이다. [Anthropic, skill-creator](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md)

OpenAI의 현재 모델 지침은 반복 지침과 예시를 제거하고 도구 설명을 간결하게 한 내부 coding-agent 평가에서 평가 점수가 약 10퍼센트에서 15퍼센트 높아지고 전체 토큰이 41퍼센트에서 66퍼센트 줄었다고 보고한다. 작업마다 결과가 달라지므로 한 묶음씩 제거한 뒤 같은 평가를 다시 실행하라고 권한다. 또한 각 지침을 한 번만 적고, 장기 세션에서 반복 prompt와 tool 내용이 증폭될 수 있다고 설명한다. [OpenAI, Favor leaner prompts](https://developers.openai.com/api/docs/guides/latest-model#favor-leaner-prompts)

부정형 prompt를 9개 NLP task와 여러 크기의 OPT, GPT-3, InstructGPT에 적용한 연구에서는 모델 크기가 커져도 부정형 지시의 성능이 개선되지 않았고 원래 지시와 큰 차이가 남았다. 이 연구는 2023년 모델과 분류형 과제를 다루므로 현재 coding agent의 모든 금지 규칙에 그대로 적용할 수 없다. 다만 “하지 말아야 할 것만 쓰면 더 잘 따른다”는 일반 주장을 지지하지 않으며, 부정형 지시를 별도 평가해야 한다는 근거는 된다. [Jang, Ye와 Seo, Can Large Language Models Truly Understand Prompts?](https://proceedings.mlr.press/v203/jang23a.html)

OpenAI의 현재 prompt 지침은 기대 결과, 성공 조건, 제약과 종료 조건을 먼저 쓰도록 한다. `ALWAYS`, `NEVER`, `must`, `only`는 안전 규칙이나 필수 출력처럼 실제 불변 조건에 사용하고, 검색 여부나 반복 횟수처럼 판단이 필요한 행동에는 결정 규칙을 쓰라고 한다. 같은 문서는 허용된 안전한 행동도 명시해 불필요한 승인 요청을 줄이라고 권한다. [OpenAI, Outcome-first prompts and stopping conditions](https://developers.openai.com/api/docs/guides/latest-model#outcome-first-prompts-and-stopping-conditions), [OpenAI, Define autonomy and approval boundaries](https://developers.openai.com/api/docs/guides/latest-model#define-autonomy-and-approval-boundaries)

## 금지 문구가 필요한 경우와 부족한 경우

금지 문구는 실행하면 복구하기 어렵거나 정책을 위반하는 행동에 적합하다. 대상, 조건과 대신 수행할 행동을 함께 써야 한다.

예를 들어 다음 문장은 금지 대상만 있다.

> 사용자 승인 없이 파일을 삭제하지 않는다.

이 문장은 삭제 대신 무엇을 해야 하는지 알려주지 않는다. 다음처럼 판정과 후속 행동을 더할 수 있다.

> 삭제 대상과 영향이 사용자의 요청에서 확정되지 않으면 파일을 바꾸지 않고 정확한 대상을 확인한다. 삭제가 필요하지만 복구 가능한 이동으로 목적을 달성할 수 있으면 그 방법을 먼저 제안한다.

반대로 다음처럼 수행 지침만 있으면 위험한 예외를 놓칠 수 있다.

> 실패한 테스트를 모두 통과시킨다.

이 지침은 테스트 삭제나 assertion 약화도 성공으로 오인할 수 있다. 기대 결과와 금지 조건을 함께 써야 한다.

> 실패 원인을 고치고 실패한 동작을 확인하는 테스트를 실행한다. 테스트를 삭제하거나 assertion을 약화해 실패를 숨기지 않는다. 요구사항과 테스트가 충돌하면 둘 중 하나를 임의로 바꾸지 않고 충돌 근거를 보고한다.

따라서 선택 기준은 긍정형과 부정형 중 어느 쪽이 더 중요한지가 아니다. 결과와 정상 행동을 먼저 쓰고, 실제로 발생했거나 피해가 큰 우회 행동만 금지하며, 실패했을 때 중단하거나 문의할 조건을 이어 쓴다.

## 안티패턴 금지 지침에 적용한 예시

다음 지침은 이름만 금지한다.

> God object와 service locator 안티패턴을 사용하지 않는다.

모델은 클래스가 몇 개의 책임을 가지면 God object인지, framework의 dependency container가 service locator와 같은지 판정할 수 없다. 대신 관찰 가능한 실패와 확인 수단을 적는다.

> 새 모듈이 요청 검증, 영속화와 외부 API 호출을 모두 맡으면 각 책임의 변경 이유와 독립 테스트 가능성을 확인한다. 서로 다른 변경 이유가 있고 한 책임을 테스트하려고 다른 두 시스템을 함께 준비해야 하면 책임을 나눌 후보로 보고한다. framework가 생성자나 함수 인자로 제공한 dependency는 전역 registry 조회 금지 대상에 포함하지 않는다.

이 지침도 모든 설계 문제를 자동으로 제거하지 않는다. 하지만 reviewer가 확인할 코드 관계, 예외와 보고 조건을 제공하므로 안티패턴 이름만 나열한 문장보다 평가 사례를 만들기 쉽다.

## 같은 행동을 유지하며 Skill을 줄이는 절차

### 1. 먼저 행동 기준을 고정한다

Skill을 수정하기 전에 대표 입력과 기대 판정을 만든다. `use-words-review`라면 다음 사례를 포함할 수 있다.

- 문제 후보가 있지만 자연스러운 대체 문장이 있어 `needs revision`인 한국어 문장
- API 이름이나 정확한 기술 용어라서 후보 표현을 유지해야 하는 문장
- 책임 주체가 없어 새 뜻을 추정할 수 없으므로 `needs human input`인 문장
- 개인정보가 있는 절대 경로를 제거해야 하는 문장
- 경고가 없지만 문장 사이의 승인 관계가 끊긴 문단

각 사례에는 판정뿐 아니라 바꿀 위치, 대체 문장 또는 유지 근거가 있어야 한다. 전체 결과가 같은지 확인하지 않고 파일만 줄이면 행동 보존을 확인할 수 없다.

### 2. 항상 필요한 내용만 본문에 남긴다

다음 내용은 `SKILL.md` 본문 후보이다.

- Skill이 실행되는 조건과 실행하지 않는 조건
- 입력과 최종 결과 형식
- 반드시 지켜야 할 순서와 중단 조건
- 참고 파일을 선택하는 조건
- 스크립트 결과를 해석하는 책임

긴 사례, 언어별 판정 목록, 특정 산출물에만 적용되는 설명과 중복된 근거는 참고 파일 후보이다. 본문과 참고 파일에 같은 규칙을 반복하지 않는다.

### 3. 참고 파일의 선택 조건을 구체화한다

파일을 잘게 나눈 뒤 모두 읽도록 하면 호출과 토큰이 오히려 늘어난다. 예를 들어 한국어 검사 결과에 문장 관계 경고가 없고 한 낱말의 대체 표현만 판정한다면 낱말 판정 자료만 읽게 할 수 있다. 반대로 긴 문단이나 지칭 관계를 판단해야 하면 문장 관계 자료를 추가로 읽는다.

참고 파일마다 다음 정보를 본문에 둔다.

- 어떤 입력이나 검사 경고가 있을 때 읽는가.
- 어떤 경우에는 읽지 않는가.
- 그 파일을 읽고 어떤 판정을 내려야 하는가.

### 4. 기계 검사와 의미 판정을 분리한다

문자열 탐지, 줄 번호, 파일 형식과 금지된 개인 경로는 스크립트가 반복 가능하게 찾을 수 있다. 문장이 실제 대상을 밝히는지, 대체 문장이 뜻을 보존하는지와 전문용어를 유지해야 하는지는 모델이나 사람이 판정한다. 스크립트로 옮긴 규칙을 본문에서 다시 긴 목록으로 설명하지 않고, 결과를 어떻게 처리할지만 남긴다.

### 5. 한 묶음씩 줄이고 같은 평가를 실행한다

다음 값을 변경 전후에 기록한다.

- Skill 본문과 실제로 읽은 참고 파일의 입력 토큰
- 전체 경과 시간과 도구 호출 수
- 기대 판정과 일치한 사례 수
- 놓친 문제와 잘못 지적한 문제 수
- 대체 문장을 적용한 수와 원문을 유지한 수

한 번에 구조 전체를 바꾸면 어떤 삭제가 회귀를 만들었는지 알 수 없다. 중복 사례, 반복 규칙, 참고 파일 순서처럼 한 묶음씩 바꾸고 같은 평가를 한 번 실행한다. 성능이 유지되지 않으면 크기 목표보다 행동 기준을 우선한다.

## 프로젝트 반영 후보

다음 항목은 조사 결과에서 나온 변경 후보이며 아직 승인된 구현 항목이 아니다.

- `use-words-review`에서 모든 검토가 읽는 자료와 한국어 경고 종류에 따라 읽는 자료를 구분한다.
- AGENTS.md의 금지 문구 중 대체 행동이나 문의 조건이 없는 항목을 찾아 정상 행동과 중단 조건을 추가한다.
- 안티패턴 이름 목록을 늘리는 대신 실제 실패 사례를 저장소별 개발 지침과 테스트에 연결한다.
- Skill별 대표 평가 사례, 실제 입력 토큰과 판정 정확도를 기록한 뒤 파일을 한 묶음씩 줄인다.
- 같은 규칙이 AGENTS.md, Skill 본문과 참고 파일에 반복되면 책임 문서 한 곳을 정하고 다른 문서는 읽기 조건만 둔다.

## 남은 결정

- Skill별로 어떤 작업 표본과 기대 판정을 행동 보존 기준으로 삼을지 정해야 한다.
- 참고 파일을 경고 종류별로 나눌 때 파일 호출 증가가 토큰 감소보다 큰지 측정해야 한다.
- 금지 규칙을 실제 불변 조건으로 판정할 책임자와 예외 승인 방식을 정해야 한다.
- 현재 파일의 목표 바이트나 토큰 수는 근거가 없으므로 평가 전에 임의로 정하지 않는다.
