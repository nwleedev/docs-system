# 에이전트 작업 분리와 검증 구조 조사

## 조사 결론

현재 조사에서는 일곱 문제의 해결 단계를 입력 절감, 결정적 검사, 독립 판정과 변경 감지로 나누는 방안을 우선 비교해야 한다. 먼저 자주 읽는 지침과 작업 입력에는 현재 행동에 필요한 정보만 남긴다. Git diff, 검사 결과, 링크 접근 여부처럼 반복 가능한 사실은 도구로 확인한다. 구현자의 판단을 다시 평가해야 하는 작업에는 구현 대화가 없는 읽기 전용 리뷰 세션을 비교 후보로 둔다. 마지막으로 새 commit이나 요구사항 변경처럼 검토 입력이 달라졌을 때만 새 판정을 시작한다.

이 구조를 현재 문제에 적용하면 다음과 같이 해결 방향이 달라진다.

- **서브에이전트 사용.** 순차 의존이 있는 작업은 한 세션에서 처리하고, 앞 작업의 산출물을 입력으로 쓰지 않는 읽기 중심 작업만 분리 후보로 둔다. 분리 여부는 에이전트 수가 아니라 실제 토큰, 경과 시간과 기대 판정의 일치 여부를 같은 작업에서 비교해 정한다.
- **큰 Skill과 참고 문서.** 원본 파일의 바이트 수, Skill이 선택될 때 읽는 본문, 조건부 참고 자료와 애플리케이션 저장소에 복사된 README의 반복 사용량을 따로 측정한다. `_README.md`는 복사 뒤 한 파일만으로 기준을 제공해야 하므로 분할하지 않고 파일 안의 반복 규칙을 합치는 방안을 평가한다. 필요한 행동을 고정하기 전에 목표 파일 크기를 정하지 않는다.
- **같은 세션의 구현과 리뷰.** 구현 세션은 기계 검사와 누락 확인을 수행할 수 있지만 이를 독립 리뷰라고 부르지 않는다. 독립 판정이 필요한 변경은 고정된 commit 범위와 요구사항을 별도 리뷰 세션에 전달한다. 같은 worktree를 쓰는 경우에는 저장소가 정한 커밋하지 않는 결과 파일로 판정을 인계하되, 구현 세션이 검토 중 추적 파일을 바꾸지 않고 결과 파일에 검토한 commit을 기록해야 한다.
- **반복 리뷰.** 한 번의 리뷰 대상을 변경되지 않는 commit 범위로 고정한다. 새 commit, 요구사항 변경 또는 처음 읽지 못한 자료가 있을 때만 새 검토 단위가 생긴다.
- **안티패턴.** 작업 중인 애플리케이션 코드를 조사 자료로 사용하지 않고, 공개 오픈소스 애플리케이션의 수정 commit과 pull request를 공식 작성 방식 및 검사 규칙과 교차 검증한다. 각 항목에는 실패 조건, 안티패턴과 권장 패턴 코드, 권장 이유, 적용 조건, lint 예시와 탐지하지 못하는 범위를 함께 기록한다.
- **출처.** 링크가 있다는 사실과 링크의 본문이 가까운 주장을 뒷받침한다는 판정을 분리한다. 문장을 최소 주장으로 나누고 출처에서 확인할 수 있는 내용에 맞춰 문장을 줄이거나 근거를 보충한다.
- **문제 후보 표현.** 작성 단계에서 자연스러운 대체 문장을 먼저 적용하고, 검토 단계에서는 그대로 남은 후보의 유지 근거만 엄격하게 확인한다. 뜻이나 책임 주체를 새로 정해야 하는 경우에는 자동으로 바꾸지 않는다.

이 결론은 [요구사항의 목표](../requirements.md#목표)를 위한 조사 결과이며 승인된 운영 결정이 아니다. 최초 조사일은 2026년 8월 27일이고, 결과 파일 인계와 공개 오픈소스 패턴 조사 방안은 2026년 8월 28일에 추가로 조사했다.

요구사항 변경으로 추가된 질문은 다음 자료에서 자세히 다룬다.

- [구현 세션, 리뷰 세션과 Goal 운용 조사](session-review-tdd-and-goal-research.md)는 세션별 책임, TDD commit을 읽는 순서, 테스트 타당성 판정과 Git 기록이 바뀌지 않을 때의 중단 조건을 다룬다.
- [지침 크기와 금지 문구 설계 조사](instruction-size-and-prohibition-research.md)는 현재 Skill 크기, 부정형 지시 연구, 행동을 유지하며 참고 자료를 나누는 절차와 프로젝트 반영 후보를 다룬다.

## 조사 범위와 방법

이 저장소의 Skill 크기, 설계 문서 규칙, 개발 지침, 한국어 후보 표현을 다룬 결정과 조사 문서를 확인했다. 외부 자료는 OpenAI와 Anthropic의 공식 문서 및 운영 보고, GitHub와 Git의 공식 문서, NIST 지침, OWASP 지침, 공식 소스 저장소와 원 논문을 우선했다. GitHub의 `anthropics/skills` 파일과 변경 이력도 확인했다.

추가 대안은 작업 중인 애플리케이션 저장소를 조사 자료로 사용하지 않았다. GitHub에서 공개된 Grafana 수정 commit `6934c0a2c73c1e8a9e262f80f8c6d670bcb642ce`와 pull request 131250, VS Code 수정 commit `b97b19d0bcbfa5e0a193a454c460ea39c29e9cc8` 및 두 revision의 라이선스를 확인했다. 코드 의미와 검사 범위는 typescript-eslint와 Node.js 공식 문서에서 교차 검증했다.

조사는 운영 구조를 비교하는 데 그친다. 실제로 세션을 분리했을 때 발견율, 토큰, 경과 시간과 잘못된 지적이 어떻게 달라지는지는 대표 작업으로 평가하지 않았다. 따라서 아래의 세션 구성과 중단 조건은 도입 전 실험이 필요한 제안이다.

## 서브에이전트는 병렬화 이익이 분배 비용보다 클 때만 사용한다

### 확인한 문제

서브에이전트마다 작업 설명, 저장소 규칙, 필요한 파일과 결과 형식을 다시 전달해야 한다. 결과를 받은 메인 세션은 보고를 원본 파일과 대조하고 충돌을 해결해야 한다. 하나의 문맥에서 순서대로 판단해야 하는 작업을 나누면 이 전달 비용은 늘어나지만 병렬 실행으로 줄어드는 시간은 적다.

Anthropic은 자사 Research 시스템에서 일반 agent가 chat보다 약 4배, multi-agent가 chat보다 약 15배의 토큰을 사용했다고 보고했다. 원문의 짧은 표현은 “multi-agent systems use about 15× more tokens than chats”다. 같은 보고서는 코딩 작업에는 독립적으로 병렬화할 부분이 적고 agent 간 실시간 조율이 아직 어렵다고 설명한다. 이 수치는 모든 서브에이전트 호출의 고정 배율이 아니라 Anthropic Research 시스템의 관측값이지만, 분할 자체를 기본값으로 두면 안 된다는 직접 근거다. [Anthropic, How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)

OpenAI의 현재 Subagents 안내도 병렬 실행이 복잡하고 병렬화하기 쉬운 작업에 특히 유용하다고 설명하는 한편, 각 서브에이전트가 별도의 모델 추론과 도구 작업을 수행하므로 단일 에이전트보다 토큰을 더 사용한다고 명시한다. 같은 안내는 읽기 중심의 탐색, 테스트 결과 분석과 요약을 시작점으로 제안하고, 여러 에이전트가 동시에 파일을 바꾸는 작업에는 충돌과 조정 비용이 생길 수 있다고 경고한다. [OpenAI, Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)

### 실패 예시

한 파일의 서비스 구조를 고치는 작업에서 구현, 공통화 검토와 오류 처리를 각각 서브에이전트에 맡기면 세 작업은 같은 함수 이름과 변경 중인 diff에 의존한다. 뒤의 두 작업은 구현 결과가 확정되기 전에 정확한 판단을 할 수 없고, 메인 세션은 세 결과를 다시 읽어 하나의 수정안으로 합쳐야 한다. 이 경우 서브에이전트는 시간을 줄이지 못하고 같은 코드를 여러 컨텍스트에 적재한다.

반대로 서로 다른 외부 표준 세 개를 조사하고 결과만 비교하는 일은 입력과 산출물이 독립적이다. 각 조사 결과를 같은 형식으로 반환하게 하면 병렬 실행 시간이 분배와 종합 비용보다 작아질 수 있다.

### 제안하는 사용 조건

다음 조건을 모두 만족할 때만 서브에이전트를 후보로 둔다.

- 작업 단위가 서로의 결과를 입력으로 사용하지 않는다.
- 같은 파일, 공용 인터페이스, 설정, 생성 파일이나 실행 상태를 변경하지 않는다.
- 각 작업에 전달할 자료가 전체 세션 문맥보다 훨씬 작다.
- 메인 세션이 원본과 대조할 수 있는 구체적인 결과 형식이 있다.
- 예상 병렬 절감 시간이 작업 설명, 결과 대조와 충돌 해결 시간보다 크다.

하나라도 판단하기 어렵다면 단일 세션에서 순차 실행하는 편이 낫다. 이 기준은 서브에이전트 금지가 아니라 사용 전 비용 판단이다.

## Skill은 자주 실행할 절차와 필요할 때 읽을 근거를 분리한다

### 저장소에서 확인한 상태

현재 `skills/use-words-review/SKILL.md`는 114줄, 14,152바이트다. 이 Skill이 한국어 문서를 검토할 때 완독하도록 요구하는 `references/korean.md`는 179줄, 12,112바이트이고, 일반 사례를 보정할 때 읽는 `references/examples.md`는 214줄, 10,018바이트다. `use-design-docs`와 `use-dev-guidance`의 배포용 참고 README는 각각 20,560바이트와 19,776바이트다.

파일 크기만으로 불필요한 내용을 판정할 수는 없다. 문제는 한 작업에서 실제로 필요한 부분과 관계없이 큰 파일 전체를 반드시 읽도록 지시할 때 발생한다. 이때 Skill 본문, 참고 자료와 작업 파일이 같은 컨텍스트를 차지하고, 뒤의 구현 및 검토에 사용할 여유가 줄어든다.

`_README.md`는 일반적인 조건부 참고 자료와 역할이 다르다. 애플리케이션 저장소에 복사된 뒤에는 `docs/designs/README.md` 또는 `docs/dev/README.md` 한 파일이 문서 작업의 기준이 된다. 따라서 이 파일의 내용을 별도 참고 파일로 옮기지 않는다. 모든 문서에 적용되는 규칙은 파일 안에서 한 번만 설명하고, 문서 종류별 절에는 그 종류에만 적용되는 기준을 남기는 방식으로 줄여야 한다.

### 외부 기준

Anthropic의 공식 `skill-creator`는 Skill을 세 단계로 읽도록 설명한다. 이름과 설명은 항상 보이지만, `SKILL.md` 본문은 Skill이 선택됐을 때, 추가 자료는 필요할 때만 읽는다. 본문은 500줄 미만을 이상적인 기준으로 제시하고, 큰 참고 문서는 읽을 조건을 본문에 명시하라고 한다. 2026년 8월 27일 `anthropics/skills`의 원문과 최근 커밋을 확인했다. [Anthropic 공식 skill-creator 원문](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md)

OpenAI의 현재 모델 지침도 반복 지침과 예시를 제거한 간결한 입력 지침이 내부 coding-agent 평가에서 평가 점수를 약 10퍼센트에서 15퍼센트 높이고, 전체 토큰을 41퍼센트에서 66퍼센트 줄였다고 보고한다. 이 수치는 저장소 Skill에 그대로 재현된 결과는 아니므로 방향 근거로만 사용해야 한다. [OpenAI, Favor leaner prompts](https://developers.openai.com/api/docs/guides/latest-model#favor-leaner-prompts)

OpenAI의 Skill 작성 안내는 이름과 설명을 먼저 제공하고 Skill이 선택된 뒤 `SKILL.md` 전체를 읽으며, 스크립트와 참고 자료는 별도 파일로 둘 수 있다고 설명한다. 따라서 본문을 짧게 만드는 것만으로는 충분하지 않다. 어떤 참고 자료를 언제 읽는지까지 바뀌어야 실제 입력이 줄어든다. [OpenAI, Build skills](https://learn.chatgpt.com/docs/build-skills)

긴 입력을 받을 수 있다는 사실도 모든 정보를 같은 정도로 사용하는 능력을 뜻하지 않는다. TACL에 게재된 실험에서는 질문에 답하는 정보가 긴 입력의 가운데에 있을 때 검색과 질의응답 성능이 유의하게 낮아졌다. 이 연구는 현재 Codex Skill을 직접 시험한 결과가 아니지만, 중요한 규칙을 긴 문서에 넣어 두는 것만으로 사용을 확신하지 말고 대표 작업에서 회수 여부를 확인해야 한다는 근거가 된다. [Liu 외, Lost in the Middle](https://aclanthology.org/2024.tacl-1.9/)

### 실패 예시와 개선 후보

한국어 문서에서 한 표현의 자연스러움만 판정하는 작업이 문장 연결 사례 전체와 모든 표현 규칙을 매번 읽으면, 해당 표현과 무관한 사례가 컨텍스트에 포함된다. 반면 표현 범주별 참고 파일과 명시적인 읽기 조건을 두면 필요한 규칙만 선택할 수 있다.

향후 Skill 축소 작업에서는 다음 순서가 적합하다.

1. 모든 실행에서 필요한 절차와 조건만 `SKILL.md`에 남긴다.
2. 특정 언어, 산출물 종류와 검사 경고에만 필요한 판정 자료는 각각의 참고 파일로 나눈다.
3. 본문에서 각 참고 파일을 읽는 조건과 읽지 않는 조건을 함께 적는다.
4. 반복 가능하고 판단이 필요 없는 검사는 스크립트로 옮기되, 실행 결과를 해석하는 기준은 Skill에 남긴다.
5. 변경 전후의 대표 작업에서 입력 토큰, 누락과 잘못된 지적을 측정한다.

참고 파일을 작게 나누는 행위 자체가 개선을 보장하지는 않는다. 여러 파일을 매번 전부 읽게 하면 호출 수만 늘어난다.

이 절차에서 참고 파일 분리는 `SKILL.md`가 조건에 따라 읽는 자료에만 적용한다. `_README.md`는 한 파일로 유지하며, 문장을 합친 뒤에도 복사된 README만 읽고 문서 생성 조건, 작성 권한, 필수 정보, 금지 내용과 검증 방법을 축소 전과 같이 판단하는지 확인한다.

## 구현과 리뷰는 대화 문맥을 분리할 수 있다

### 분리 근거

같은 세션의 자기 리뷰는 구현 중 선택한 구조와 설명을 이미 정답 후보로 받아들인다. 새로운 검토 질문을 추가해도 모델은 같은 대화에 남은 전제와 자기 설명을 사용하므로, diff만 처음 읽는 검토자와 입력 조건이 다르다.

LLM의 내재적 자기 교정을 조사한 ICLR 2024 논문은 외부 피드백 없이 모델이 자기 답을 다시 검토할 때 일반적으로 추론 성능이 개선되지 않았고 일부 조건에서는 악화됐다고 보고했다. 코드 리뷰만을 대상으로 한 실험은 아니지만, 같은 모델의 반복 자기 판단을 독립 검증으로 간주할 수 없다는 근거다. [Huang 외, Large Language Models Cannot Self-Correct Reasoning Yet](https://proceedings.iclr.cc/paper_files/paper/2024/hash/8b4add8b0aa8749d80a34ca5d941c355-Abstract-Conference.html)

OpenAI의 Codex 공식 문서는 `/review`가 선택한 diff를 읽는 “dedicated reviewer”를 시작한다고 설명한다. 리뷰는 기본적으로 현재 대화에서 실행되지만, 설정을 `Detached`로 바꾸면 별도 검토 대화를 시작할 수 있다. 이 설정은 구현 담당 세션과 리뷰 담당 세션을 나누는 제안을 실제로 시험할 수 있는 기능 근거다. [OpenAI, Code review](https://learn.chatgpt.com/docs/code-review)

GitHub도 pull request 작성자가 자신의 pull request를 승인할 수 없게 하고, 코드 변경 커밋이 추가되면 설정에 따라 기존 승인을 무효화할 수 있다. 사람의 협업 규칙이지만 작성과 승인 책임을 나누고 변경된 증거를 다시 보게 하는 참고 사례다. [GitHub, About pull request reviews](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/about-pull-request-reviews)

NASA의 독립 검증 표준은 기술적 독립성을 개발에 참여하지 않은 검증자가 별도의 문제 이해를 세우는 상태로 정의한다. 또한 모든 항목을 같은 강도로 검증할 수 없으므로 위험과 자원을 비교해 검증 대상을 정하도록 요구한다. NASA의 안전 및 임무 중요 소프트웨어 절차를 이 저장소에 그대로 적용할 수는 없지만, 별도 세션의 이름만으로 독립성이 생기지 않으며 독립 판정이 필요한 대상을 근거 없이 모든 작업으로 확대해서도 안 된다는 근거가 된다. [NASA-STD-8739.8B, Software Assurance and Software Safety Standard](https://standards.nasa.gov/system/files/tmp/NASA-STD-87398-Revision-B_0.pdf)

### 제안하는 두 세션의 입력

**구현 담당 세션.** 승인된 요구사항과 개발 지침을 읽고 코드를 변경한다. 변경한 파일에 적용되는 lint, type 검사, 테스트와 실행 증거를 남긴다. 자체 점검은 diff 누락, 명백한 검사 실패와 민감정보처럼 기계적으로 확인할 항목에 한정한다. 리뷰를 대신하는 품질 판정을 내리지 않는다.

**리뷰 담당 세션.** 구현 대화와 구현자의 내부 설명을 전달받지 않는다. 기준 branch 또는 commit, 요구사항, 적용할 개발 지침, 최종 diff와 검사 결과만 읽는다. 변경하지 말아야 할 기존 동작, 오류 처리, 외부 인터페이스와 테스트 증거를 기준으로 검토 결과만 반환하고 작업 파일을 수정하지 않는다.

리뷰 세션에 구현 세션의 대화 기록 전체를 전달하면 분리 효과가 줄어든다. 반대로 요구사항과 검사 환경까지 빼면 리뷰가 의도를 알 수 없다. 독립성은 정보 차단이 아니라 구현 과정의 자기 정당화는 제외하고 판정에 필요한 근거는 공유하는 방식이어야 한다.

같은 worktree branch를 공유하면서 결과 파일로 인계하는 후보에서는 구현 세션이 마지막 commit을 만든 뒤 추적 파일 변경을 멈춘다. 리뷰 세션은 그 commit 범위만 읽고 저장소가 정한 Git 제외 대상 파일에 검토한 commit과 결과를 쓴다. 파일 경로, 제외 방식과 보관 기간은 저장소가 정하되, 비추적 상태와 stage 목록을 명령으로 확인해야 한다. 구체적인 인계 순서와 오래된 결과를 거르는 조건은 [커밋하지 않는 결과 파일을 사용하는 인계안](session-review-tdd-and-goal-research.md#커밋하지-않는-결과-파일을-사용하는-인계안)에 기록했다.

### 실패 예시

구현 세션이 “이 함수는 adapter이므로 이 위치가 맞다”고 설명한 뒤 같은 세션에 구조 리뷰를 요청하면, 리뷰가 그 분류를 검증하지 않고 출발점으로 사용할 수 있다. 별도 리뷰 세션에는 실제 호출 흐름, 적용 지침과 diff만 주고 함수가 어느 책임에 속하는지 다시 판정하게 한다.

## 리뷰 횟수 대신 재검토 조건과 중단 조건을 정한다

### 한 번과 여러 번의 공통 한계

한 번의 리뷰는 누락 가능성이 있고, 여러 번의 같은 리뷰는 같은 전제와 탐지 능력을 반복할 수 있다. 횟수만 늘리면 잘못된 지적을 처리하고 수정 diff를 다시 읽는 비용도 늘어난다. 앞서 확인한 자기 교정 연구는 외부 피드백 없는 반복이 자동으로 개선되지 않음을 보여준다.

Google의 code review 기준은 완벽한 코드를 요구해 진행을 막기보다 코드베이스가 전반적으로 나아지는지 판단하라고 안내한다. 이는 리뷰가 모든 결함의 부재를 증명하는 절차가 아니라 위험과 개선을 판정하는 절차라는 근거다. [Google, The Standard of Code Review](https://google.github.io/eng-practices/review/reviewer/standard.html)

전문 개발자 70명이 세 가지 review 전략을 사용한 실험에서는 일반 checklist와 단계별 checklist가 모든 변경에서 일관되게 높은 발견율을 보이지 않았다. 단계별 안내는 일부 작업에서 도움이 됐지만 시간이 더 걸렸고, 변경 복잡도와 검토 경험에 따라 결과가 달랐다. 따라서 checklist를 여러 번 실행하거나 더 세밀하게 만드는 행위 자체를 누락 감소의 증거로 사용할 수 없다. [Gonçalves 외, Do explicit review strategies improve code review performance?](https://doi.org/10.1007/S10664-022-10123-8)

### 제안하는 중단 규칙

기본값은 범위가 분명한 독립 리뷰 한 번이다. 다음 중 하나가 발생할 때만 같은 리뷰 세션에서 수정된 diff를 대상으로 재검토한다.

- 검토 결과를 반영하면서 외부 인터페이스, 데이터 형식, 권한, 트랜잭션 또는 오류 처리 흐름이 새로 바뀌었다.
- 테스트나 실행 결과가 처음 가정과 충돌한다.
- 첫 리뷰가 파일이나 요구사항을 읽지 못해 판정 범위를 충족하지 못했다.
- 보안, 데이터 손실과 같은 높은 위험의 별도 기준이 처음 리뷰에 포함되지 않았다.

맞춤법 수정처럼 검토 결과가 지적한 한 위치만 바뀌고 결정적 검사가 통과하면 전체 리뷰를 반복하지 않는다. 재검토하더라도 “모든 문제가 없어질 때까지”가 아니라 위 조건이 해소되고 새 검토 결과가 현재 변경 대상 밖이면 중단한다. 변경 대상 밖 문제는 별도 작업 후보로 보고하되 현재 diff에 섞지 않는다.

### 실패 예시

첫 리뷰에서 nullable 입력 처리가 빠졌다는 지적이 나와 조건문 하나와 그 동작을 확인하는 테스트만 추가했다. 전체 아키텍처 리뷰를 다시 실행하면 같은 파일을 다시 읽는 비용이 크다. 테스트가 정확한 실패를 재현하고 통과했다면 그 지적과 직접 연결된 증거만 확인한다. 반면 수정 과정에서 API 응답 형식까지 바뀌었다면 외부 인터페이스 검토가 새로 필요하다.

## 안티패턴은 이름이 아니라 관찰 가능한 실패와 적용 조건으로 관리한다

### 금지 문구가 부족한 이유

“안티패턴을 사용하지 않는다”는 문장은 무엇을 찾고 어떤 상황에서 예외인지 알려주지 않는다. 같은 구조도 언어, framework, 트랜잭션 범위와 부하 조건에 따라 문제가 되거나 적절할 수 있다. 모든 이론적 안티패턴을 미리 조사하면 현재 저장소와 관계없는 지침이 늘어나고, 모델은 긴 목록에서 해당 사례를 선택해야 한다.

NIST IR 8397은 소프트웨어 검증의 최소 기법으로 threat modeling, 자동 검사, static scanning, black-box test, 구조 test, 과거 회귀 사례, fuzzing과 web scanner 등을 함께 권고한다. 한 기법이 전체 품질을 증명하지 않는다는 구조다. [NIST IR 8397, Guidelines on Minimum Standards for Developer Verification of Software](https://csrc.nist.gov/pubs/ir/8397/final)

OWASP의 secure code review 지침은 static 도구가 많은 코드를 훑고 최소 기준을 세우는 데 유용하지만 dynamic data flow와 business logic을 이해하지 못한다고 설명한다. 특히 작업 순서, 상태 전이와 domain 규칙의 결함은 signature가 없어 scanner만으로 찾기 어렵다. [OWASP, Secure Code Review](https://owasp.org/www-project-code-review-guide/assets/OWASP_Code_Review_Guide_v2.pdf)

NIST의 static source analyzer 연구는 분석기가 계산 가능한 근사를 사용하므로 실제 결함을 놓치거나 정상 코드를 결함으로 보고할 수 있다고 설명한다. 따라서 lint 규칙의 존재를 안티패턴 부재의 증거로 삼지 않고, 규칙이 판정하는 구문과 판정하지 못하는 동작을 함께 기록해야 한다. [NIST, Source Code Security Analysis Tool Functional Specification](https://tsapps.nist.gov/publication/get_pdf.cfm?pub_id=51196)

### 실패 예시

lint는 route 함수가 특정 repository를 직접 호출하는 패턴을 금지할 수 있다. 그러나 transaction이 여러 application action에 잘못 나뉘어 중간 상태가 저장되는 문제는 import 규칙만으로 알기 어렵다. 반대로 모든 repository 호출을 service 한 층으로 강제하면 단순 조회까지 불필요한 wrapper가 늘어날 수 있다.

“이 framework의 안티패턴을 조사하고 현재 코드에서 모두 제거하라”는 prompt도 완료 조건이 되지 못한다. 조사 대상 버전, 유지할 동작과 실패 사례가 없으므로 모델은 일반 목록에서 이름이 비슷한 구조를 골라 바꿀 수 있다. 예를 들어 framework가 request 단위로 제공하는 dependency container를 service locator로 분류해 모두 생성자 주입 wrapper로 감싸면 파일 수와 연결 코드만 늘고 관찰 가능한 결함은 없어지지 않는다. 반대로 실제 문제인 transaction 중간 저장은 목록에 이름이 없다는 이유로 남을 수 있다.

### 공개 오픈소스 애플리케이션에서 근거를 찾는 절차

패턴 조사와 대상 애플리케이션 검사는 서로 다른 작업이다. 패턴 조사 단계에서는 작업 중인 애플리케이션 저장소의 파일, Git 기록과 리뷰 내용을 읽지 않는다. 코드가 아직 없어도 요구사항에서 보호할 동작과 승인된 기술 스택을 질문으로 삼아 GitHub에 배포된 공개 오픈소스 애플리케이션을 찾는다. 기술 스택이 정해지지 않았다면 요구사항이 보호하는 동작의 실패 사례를 조사하되, 각 예시의 언어와 framework를 명시하고 대상 애플리케이션에 그대로 적용할 수 있다고 판정하지 않는다.

공개 저장소의 현재 코드만 보고 안티패턴이나 권장 패턴으로 분류하지 않는다. branch의 파일은 이후 바뀔 수 있으므로 commit OID가 포함된 permalink를 사용한다. GitHub도 branch URL은 내용이 바뀔 수 있고 commit ID를 넣은 URL은 본 버전을 고정한다고 설명한다. [GitHub, Getting permanent links to files](https://docs.github.com/en/repositories/working-with-files/using-files/getting-permanent-links-to-files)

근거 수집은 다음 순서로 진행한다.

1. 실행 가능한 애플리케이션을 배포하는 공식 저장소에서 문제를 고친 merged pull request, 수정 commit, 연결된 issue 또는 회귀 테스트를 찾는다.
2. 유지보수자가 기록한 실패 현상, 발생 조건과 수정 이유를 분리한다. 현재 코드에 같은 모양이 있다는 사실만으로 실패 이유를 추정하지 않는다.
3. 언어, framework 또는 검사 도구의 공식 문서에서 권장 작성 방식과 규칙이 실제로 판정하는 구문을 확인한다.
4. 수정 전후 코드에서 사례에 필요한 부분만 줄여 안티패턴과 권장 패턴 예시를 새로 작성하고, 어떤 revision에서 도출했는지 바로 옆에 링크한다.
5. 저장소 라이선스와 예시 사용 범위를 확인한다. 공개 저장소라는 사실만으로 복제나 파생 저작물 작성 권한이 생기지는 않으므로, 라이선스가 확인되지 않으면 원문 코드를 복사하지 않고 동작을 설명하는 최소 예시를 작성한다. [GitHub, Licensing a repository](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository)
6. lint가 잡는 모양, 잡지 못하는 의미와 대신 사용할 검사를 각각 기록한다. 규칙 문서가 탐지한다고 밝히지 않은 코드를 임의로 탐지 가능하다고 쓰지 않는다.

대상 애플리케이션에 실제로 적용하는 단계에서는 이 조사 기록의 적용 조건과 현재 요구사항을 먼저 비교한 뒤 코드를 검사한다. 조사 단계에서 대상 코드를 보지 않는다는 조건은 사전 지식을 만들기 위한 것이며, 이후 구현이나 리뷰에서 실제 변경을 확인하지 않아도 된다는 뜻은 아니다.

### 항목마다 기록할 내용

각 안티패턴 및 권장 패턴 항목은 다음 정보를 빠짐없이 제공해야 한다.

- 문제를 드러내는 이름과 상세 설명
- 공개 애플리케이션 저장소, 라이선스, 고정된 revision과 수정 근거
- 관찰된 실패, 발생 조건과 적용되지 않는 조건
- 출처에서 필요한 부분만 줄인 안티패턴 코드 예시
- 같은 실패를 피하는 권장 패턴 코드 예시
- 권장 패턴이 실행 순서, 오류 처리, 상태 또는 책임을 어떻게 바꾸는지에 대한 이유
- 공식 lint 규칙의 설정 예시, 필요한 type 정보와 규칙이 판정하는 코드 모양
- lint가 판정하지 못하는 영역과 대신 사용할 type 검사, 테스트, 실행 검사 또는 담당 리뷰
- 대상 애플리케이션에 적용하기 전에 확인할 기술 버전과 요구사항

문제의 코드 모양을 정확히 판정하는 lint 규칙이 없다는 사실도 유효한 조사 결과다. 이 경우 다른 문제를 검사하는 규칙을 억지로 붙이지 않고 “정확한 규칙을 확인하지 못함”과 다른 검사 방법을 기록한다.

### 공개 사례로 만든 예시: Promise 완료 책임

결론은 호출 결과가 다음 동작의 입력이면 `await`로 완료와 실패를 호출자에게 연결해야 하고, 결과를 기다리지 않는 호출은 실패를 누가 처리하는지 별도로 밝혀야 한다는 것이다.

Grafana의 2026년 8월 21일 병합 변경은 비동기 `createDefaultAnnotationLayer()`의 결과를 기다리지 않아 `Promise`를 `DataLayer`가 필요한 함수에 전달했고 TypeScript `TS2322` 오류가 발생했다고 기록한다. 수정은 콜백을 `async`로 만들고 반환값을 `await`한 뒤 다음 함수에 넘겼다. 이는 실제 애플리케이션 저장소의 빌드 실패와 수정 이유가 함께 있는 사례다. [Grafana pull request 131250](https://github.com/grafana/grafana/pull/131250), [Grafana commit `6934c0a`](https://github.com/grafana/grafana/commit/6934c0a2c73c1e8a9e262f80f8c6d670bcb642ce), [Grafana AGPL-3.0 license at the reviewed revision](https://github.com/grafana/grafana/blob/6934c0a2c73c1e8a9e262f80f8c6d670bcb642ce/LICENSE)

다음 안티패턴 예시는 Grafana 변경에서 함수 이름을 일반화해 다시 작성한 것이다.

```ts
function addDefaultLayer() {
  const layer = createDefaultLayer();
  registerLayer(layer);
}
```

`createDefaultLayer()`가 `Promise<DataLayer>`를 반환하면 `registerLayer()`에는 완성된 layer가 아니라 Promise가 전달된다. 호출 순서가 코드에 드러나지 않고 거부된 Promise의 처리 주체도 정해지지 않는다.

결과가 필요한 경우의 권장 패턴은 다음과 같다.

```ts
async function addDefaultLayer() {
  const layer = await createDefaultLayer();
  registerLayer(layer);
}
```

이 코드는 layer 생성이 끝난 뒤 등록하며, 생성 실패를 `addDefaultLayer()`가 반환하는 Promise로 전달한다. 호출자는 다시 `await`, `return` 또는 `catch` 중 요구사항에 맞는 방법으로 실패를 처리할 수 있다.

의도적으로 완료를 기다리지 않는 호출은 다른 경우다. VS Code의 2026년 6월 25일 변경은 리뷰 지적에 따라 두 `openView()` 호출 앞에 `void`를 붙여 완료를 기다리지 않는 의도를 드러냈다. 그러나 이 commit은 동작 결함을 고쳤다고 주장하지 않고 기존 작성 방식과 맞췄다고 설명한다. 따라서 `void`가 있다는 사실만으로 권장 패턴이나 오류 처리 완료의 근거로 사용하면 안 된다. [VS Code commit `b97b19d`](https://github.com/microsoft/vscode/commit/b97b19d0bcbfa5e0a193a454c460ea39c29e9cc8), [VS Code MIT license at the reviewed revision](https://github.com/microsoft/vscode/blob/b97b19d0bcbfa5e0a193a454c460ea39c29e9cc8/LICENSE.txt)

typescript-eslint의 `no-floating-promises`는 처리되지 않은 Promise 문장을 찾으며 type 정보가 필요하다. type 정보를 사용하는 typescript-eslint가 이미 구성된 프로젝트에서는 다음처럼 규칙을 error로 설정할 수 있다. [typescript-eslint, no-floating-promises](https://typescript-eslint.io/rules/no-floating-promises/)

```js
{
  rules: {
    "@typescript-eslint/no-floating-promises": "error",
  },
}
```

같은 공식 문서는 기본 `ignoreVoid: true`에서 `void`가 의도적으로 기다리지 않는다는 표시는 할 수 있지만 Promise를 처리하거나 실행 동작을 바꾸지 않으므로 Promise 거부는 여전히 처리되지 않을 수 있다고 경고한다. Node.js도 이벤트 루프 한 차례 안에 오류 처리기가 붙지 않은 거부를 `unhandledRejection`으로 보고하며, 기본 설정에서는 처리되지 않은 거부가 잡히지 않은 예외로 이어질 수 있다고 설명한다. [Node.js, `unhandledRejection`](https://nodejs.org/api/process.html#event-unhandledrejection)

따라서 이 항목의 lint 예시는 Promise 반환 호출을 독립된 문장으로 버리는 모양을 찾는 데 사용한다. Grafana 사례처럼 Promise를 변수에 저장한 뒤 다른 type이 필요한 함수에 넘기는 정확한 모양까지 이 규칙이 판정한다고 공식 문서가 밝히지는 않는다. Grafana 사례는 TypeScript type 검사에서 `TS2322`로 검출됐으므로 type 검사도 함께 기록해야 한다. 결과를 기다리지 않아도 되는 호출은 `void`만 추가하지 않고, 호출된 함수가 Promise 거부를 처리한다는 API 근거나 호출자가 `catch`로 실패를 처리하는 코드를 확인한다.

이 설정 예시는 lint 의존성 추가나 버전 선택을 승인하지 않는다. 실제 저장소에 적용할 때에는 그 저장소가 승인한 TypeScript, ESLint와 typescript-eslint 버전 및 공식 설정 방식을 먼저 확인한다.

### 제안하는 관리 단위

안티패턴 지침은 앞 절의 항목별 기록을 요약해 실제 실패, 적용 조건, 코드 예시, 권장 이유와 확인 수단을 한 묶음으로 가리켜야 한다. 이름 목록이나 lint 규칙 이름만 지침에 복제하지 않는다.

lint로 구문과 의존 방향을 안정적으로 판정할 수 있으면 자동화한다. 데이터 일관성, 사용자 작업 흐름, 성능과 설계 책임처럼 문맥이 필요하면 시나리오 test, runtime 증거 또는 명시된 담당 리뷰를 사용한다. 조사 항목은 공개 오픈소스 애플리케이션의 수정 근거와 공식 자료에서 추가하고 이론적 목록 전체를 복제하지 않는다. 대상 애플리케이션에서 발생한 incident나 현재 코드는 사전 패턴 조사 근거로 사용하지 않고, 별도의 적용 및 검증 근거로만 다룬다.

안티패턴 제거를 완료했다고 판정하려면 이름 검색이 아니라 요구사항에서 보호할 동작, 재현 가능한 실패, 적용 버전의 공식 작성 방식, 변경 diff와 실패를 막는 검사 결과가 함께 있어야 한다. 하나라도 없으면 “안티패턴 없음”이 아니라 확인하지 못한 영역을 기록한다.

## 출처 링크와 주장 뒷받침 여부를 별도로 검사한다

### 링크만으로는 확인되지 않는 항목

URL이 열리고 신뢰할 수 있는 기관의 문서라는 사실은 답변의 주장이 그 문서에 있다는 뜻이 아니다. 출처 검사는 최소한 다음을 분리해야 한다.

- **접근 가능성.** 링크가 실제 문서로 열리는가.
- **출처 품질.** 공식 문서, 표준, 원 논문이나 공식 source인가.
- **주장 뒷받침 여부.** 인용한 부분이 가까운 주장을 직접 지지하는가.
- **범위.** 출처가 조건부 관측을 일반 법칙으로 확대하지 않는가.
- **완전성.** 외부 확인이 필요한 주요 주장에 근거가 빠지지 않았는가.

ALCE 연구는 LLM 답변의 인용 품질을 정확성과 완전성으로 나누고, 정확성에서는 인용한 문단이 주장을 논리적으로 뒷받침하는지 평가한다. 인용 표시 개수만 세지 않고 주장과 근거의 관계를 판정해야 한다는 직접 근거다. [Gao 외, Enabling Large Language Models to Generate Text with Citations](https://aclanthology.org/2023.emnlp-main.398/)

RARR 연구는 이미 작성된 문장을 질문 단위로 조사하고, 근거와 맞지 않는 내용을 확인한 뒤 원래 뜻을 가능한 한 유지하며 고치는 절차를 평가했다. 이는 링크를 나중에 붙이는 단계와 근거에 맞춰 문장을 줄이는 단계를 분리할 수 있음을 보여준다. 다만 RARR도 모델 판정을 사용하므로 현재 저장소의 자동 통과 기준으로 바로 사용할 수는 없다. [Gao 외, RARR](https://aclanthology.org/2023.acl-long.910/)

FActScore는 긴 답변을 원자적 사실로 나누고 각 사실이 지식 출처에 의해 뒷받침되는 비율을 평가한다. 이 연구의 점수를 현재 문서에 적용할 필요는 없지만, 여러 사실을 한 문장에 묶은 채 링크 하나가 문장 전체를 뒷받침한다고 판정하지 말아야 한다는 근거가 된다. [Min 외, FActScore](https://aclanthology.org/2023.emnlp-main.741/)

### 실패 예시

Anthropic 보고서가 특정 Research 시스템에서 multi-agent가 chat보다 약 15배 토큰을 사용했다고 했는데, 답변이 “모든 서브에이전트 호출은 정확히 15배의 토큰을 사용한다”고 쓰면 링크는 같은 주제를 다루지만 주장한 범위까지 뒷받침하지 않는다. 올바른 문장은 관측 대상과 조건을 함께 적고 다른 코딩 작업에 그대로 일반화하지 않는 것이다.

### 제안하는 검사 절차

1. 답변을 외부 확인이 필요한 최소 주장 단위로 나눈다.
2. 각 주장 가까이의 링크를 열고 해당 문단이나 표를 확인한다.
3. `뒷받침함`, `일부만 뒷받침함`, `뒷받침하지 않음` 중 하나로 판정한다.
4. 부분 지지는 답변의 조건을 좁히거나 추가 근거를 찾고, 미지원 주장은 삭제하거나 불확실성으로 표시한다.
5. 출처가 없는 주요 주장을 다시 훑고, 출처 종류와 최신성을 확인한다.

링크 형식 검사는 URL 수와 위치를 찾을 수 있지만 주장과 근거의 논리적 관계 및 적용 조건은 판정하지 못한다. 자동화하려면 주장, 인용 문단과 판정 이유를 구조화하고, 대표 사례에서 사람이 정한 기대 판정과 모델 평가를 보정해야 한다.

## 문제 후보 표현은 대체 문장을 먼저 만들고 유지 근거를 요구한다

### 현재 기준과 남은 문제

현재 [한국어 스캐너 활용형 탐지와 대체 표현 제안 요구사항](../../korean-scanner-coverage-9b4e/requirements.md)은 경고를 자동 실패나 수정 명령으로 다루지 않는 조건을 유지한다. [검사 도구의 대체 표현 제안 방식 조사](../../korean-scanner-coverage-9b4e/references/rewrite-suggestion-practices.md)는 후보 발견 뒤 대체 표현을 먼저 찾는 방향을 제시했고, 이후 결정 문서는 출력 구조를 유지하면서 검토자가 대체 표현을 먼저 찾도록 정했다.

이 절차에서도 검토자가 후보 표현을 확립된 용법이라고 관대하게 판정하면 원문이 유지된다. 자연스러운 문장을 우선 적용하려는 현재 요구는 기존의 읽기 전용 리뷰와 자동 변경 금지 결정을 바꾸지 않고는 완전히 충족할 수 없다.

### 외부 사례

Google 개발 문서의 word list는 모호하거나 뜻이 넓은 표현에 더 구체적인 대안을 제시하고, 기술적으로 필요한 경우에는 유지할 수 있게 한다. 특히 단순한 낱말 치환보다 문맥의 실제 행동을 정확히 쓰도록 권한다. [Google developer documentation style guide, Word list](https://developers.google.com/style/word-list)

Vale의 substitution rule은 문제 표현과 선호 표현을 연결해 정적 대체 후보를 제공할 수 있다. 공식 문서는 `replace` action이 하나 이상의 교체 후보를 반환한다고 설명한다. 다만 정규식 기반 규칙은 문장 전체의 의미를 판단하지 않으므로, 후보 제시와 최종 적용을 나눠야 한다. [Vale, replace fixer](https://vale.sh/docs/fixers/replace)

### 제안하는 대체 문장 우선 절차

미래의 Skill 변경에서는 작성과 리뷰를 다음처럼 나누는 방안을 평가할 수 있다.

1. 작성 세션이 검사기의 문제 후보마다 실제 대상, 행동, 조건과 결과를 드러내는 대체 문장 한 개 이상을 먼저 만든다.
2. 기술 용어, 승인된 이름, 코드와 인용처럼 바꾸면 안 되는 근거가 없으면 대체 문장을 초안에 적용한다.
3. 리뷰 세션은 원문 후보를 유지한 위치만 확인하고, 각 위치에 구체적인 유지 근거가 없으면 `needs revision`으로 판정한다.
4. 대체 문장이 원래 의미를 바꾸거나 책임 주체를 추정해야 하면 `needs human input`으로 판정하고 자동 적용하지 않는다.

현재 승인된 결정은 이미 검토자가 대체 표현을 먼저 찾도록 요구한다. 남은 문제는 새 금칙어가 아니라 각 경고가 어떻게 처리됐는지 빠짐없이 대조하는 절차다. 작성 세션은 의미 검토 전에 대체할 수 있는 표현을 적용한다. 마지막 검사에도 경고가 남으면 대체 표현 없음과 유지 근거, 수정 필요 또는 요구사항 작성자의 판단 필요 중 하나로 판정한다. 경고가 있다는 이유만으로 통과시키거나 모두 자동 교체하지 않는다.

한 번의 의미 검토 뒤 `needs revision`이 나오면 확인된 문구를 고치고 검사기를 다시 실행할 수 있다. 같은 문단 전체를 다시 의미 검토하는 것은 기본값이 아니다. 수정하면서 대상, 책임 주체, 승인 상태 또는 조건을 새로 바꿨다면 처음 검토와 입력이 달라졌으므로 그 변경만 새 검토 단위로 본다.

예를 들어 “검토 범위를 좁힌다”는 문장은 무엇을 제외하는지 알 수 없다. 실제 의도가 변경 파일만 검사하는 것이라면 “리뷰 세션은 기준 branch와 비교한 변경 파일만 검사한다”로 바꿀 수 있다. 반면 software architecture의 확립된 용어인 “transaction boundary”를 설명하는 한국어 표현은 정확한 대상을 가리키므로 단순 후보 일치만으로 바꾸지 않는다.

이 방식은 문제 후보를 자동 치환하는 것과 다르다. 작성 단계에서 문맥에 맞는 대체 문장을 우선 적용하고, 리뷰 단계는 예외 유지 근거를 엄격하게 판정한다. 현재 `use-words-review`의 읽기 전용 책임과 결과 형식을 바꾸려면 결정 소유자의 승인이 필요하다.

## 실험할 작업 흐름

아래 흐름은 조사에서 도출한 실험안이며 아직 승인되지 않았다.

1. 요구사항 소유자가 완료 증거와 변경하지 않을 동작을 문서화한다.
2. 구현 담당 세션 하나가 Skill과 참고 자료를 필요한 범위만 읽고 구현 및 결정적 검사를 끝낸다.
3. 구현 담당 세션은 기준 commit과 마지막 commit을 만든 뒤 추적 파일 변경을 멈춘다.
4. 별도 리뷰 담당 세션 하나가 구현 대화 기록 없이 요구사항, commit 범위와 검사 결과를 읽고, 같은 worktree에서 저장소가 정한 커밋하지 않는 파일에 검토한 commit과 결과만 작성한다.
5. 구현 담당 세션이 결과 파일의 완료 상태와 commit 일치를 확인하고, 근거가 확인된 지적을 수정한 뒤 그 지적의 결정적 증거를 확인한다.
6. 수정이 외부 인터페이스나 새로운 위험 영역을 바꿨을 때만 리뷰 담당 세션이 변경된 범위를 다시 본다.
7. 요구사항 완료 증거가 충족되고 미해결 지적이 없거나 책임자가 명시적으로 판단해야 할 항목으로 분리되면 중단한다.

이 흐름의 비교 평가는 같은 유형의 작업 표본에서 수행해야 한다. 기존 단일 세션 반복 방식과 분리 방식에 같은 요구사항을 주고, 전체 입력 및 출력 토큰, 경과 시간, 실제 결함 발견 수, 잘못된 지적 수, 수정 뒤 새 결함 수와 사람 검토 결과를 비교한다. 한두 성공 사례만으로 기본 운영 방식으로 채택하지 않는다.

## 반영 순서를 근거 상태에 따라 나눈다

### 현재 문서에 바로 반영할 수 있는 사실

- OpenAI의 현재 안내는 서브에이전트가 병렬 작업에 유용하지만 단일 에이전트보다 토큰을 더 사용한다고 명시한다.
- 선택된 Skill은 `SKILL.md` 전체를 읽으므로 본문과 조건부 참고 자료의 구분이 실제 입력에 영향을 준다.
- `/review`는 선택한 diff를 읽는 전용 reviewer를 시작하고 파일을 바꾸지 않은 채 결과를 반환할 수 있다.
- `/goal`은 검증 가능한 종료 조건을 요구하지만 commit이 일정 시간 바뀌지 않으면 `Blocked`로 판정한다는 시간 기준을 제공하지 않는다.
- 한국어 후보 표현은 대체 표현을 먼저 찾고 유지할 때 근거를 남기도록 이미 승인된 결정이 있다.

이 사실들은 조사 문서의 잘못된 설명을 바로잡는 근거다. 아직 에이전트 지침이나 Skill의 실행 절차를 바꿀 권한은 만들지 않는다.

### 대표 작업 평가가 필요한 변경 후보

- 서브에이전트를 사용하지 않는 단일 세션과 조건부 분리 방식의 토큰, 시간과 판정 차이
- 구현 세션과 별도 리뷰 세션의 결함 발견, 잘못된 지적과 전달 비용 차이
- 같은 worktree의 결과 파일 인계가 오래된 결과 적용과 우발적 commit을 막는지
- 공개 오픈소스 수정 근거로 작성한 안티패턴 항목이 코드가 없는 작업에서도 적용 조건, 권장 이유와 검사 한계를 일관되게 설명하는지
- Skill 본문, 조건부 참고 자료 또는 단일 `_README.md` 안의 반복 규칙 한 묶음을 줄였을 때 기대 판정이 유지되는지
- 주장 단위 출처 검토와 현재 링크 검토가 근거로 확인되지 않는 주장을 얼마나 찾는지
- 작성 단계의 대체 문장 우선 적용이 원문 의미를 바꾸지 않으면서 후보 유지 문제를 줄이는지

평가 사례와 기대 판정은 실행 전에 요구사항 작성자 또는 저장소가 정한 책임 있는 검토자가 승인해야 한다. 실행 환경이 제공하지 않는 토큰 값은 추정하지 않는다.

### 요구사항 작성자의 결정이 필요한 선택

- 별도 리뷰 세션을 기본 운영 방식으로 사용할 작업의 종류
- 리뷰 지적 수정 뒤 확인을 원래 작업의 후속 단계로 볼지 새로운 검토 단위로 볼지
- 필수 서브에이전트 호출을 제거할지와 별도 문구 리뷰 세션이 필요한 경우
- 시간이 아니라 어떤 실제 진행 불능 상태를 `Blocked`로 기록할지

이 선택은 조사 결과만으로 승인된 결정이 되지 않는다. 결정 전에는 현재 동작을 유지하고 실험안으로만 기록한다.

## 한계와 후속 결정

- 별도 리뷰 대화가 구현 세션과 내부적으로 어느 정도의 모델 상태를 공유하는지는 공식 문서에서 확인하지 못했다. 이번 제안은 대화 기록이 분리되고 전용 reviewer가 diff를 새로 읽는 관찰 가능한 동작만 근거로 한다.
- 같은 worktree의 결과 파일은 세션 대화만 분리하고 파일 시스템은 분리하지 않는다. 구현 세션이 리뷰 중 파일을 바꾸는 운영을 허용하면 이 대안으로 검토 대상을 고정할 수 없다.
- 공개 사례 예시는 Promise 완료 책임 한 항목에서 조사 절차를 시험한 결과다. 다른 언어, framework와 상태 일관성 문제에 같은 절차가 충분한지는 추가 사례 없이 확정할 수 없다.
- 자기 교정 연구는 일반 추론 과제를 다루므로 코드 리뷰 발견율에 그대로 대입할 수 없다. 실제 저장소 작업으로 별도 평가가 필요하다.
- Skill 바이트 수와 토큰 수는 같지 않으며, 이번 조사에서는 Skill별 실제 입력 토큰을 측정하지 않았다.
- 한 번의 독립 리뷰와 조건부 재검토가 현재 반복 방식보다 나은지는 평가 전에는 확정할 수 없다.
- `use-words-review`의 대체 문장 우선 변경은 기존 결정의 책임 분리를 바꿀 수 있으므로, 적용 대상과 승인 책임자를 먼저 정해야 한다.
