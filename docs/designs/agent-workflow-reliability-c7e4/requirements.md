# 에이전트 작업 흐름 개선 조사 요구사항

## 목표

AI 에이전트가 구현, 검토와 문서 작성을 수행할 때 불필요한 컨텍스트 소비를 줄이고, 같은 문맥에 의존한 자기 검토와 근거 없는 완료 판정을 피할 수 있는 작업 구조를 리서치하여 우리 프로젝트에 반영한다.

다음과 같은 문제가 존재한다.

각 문제에 대해서 상세 내용과 관련된 예시를 리서치한다.

- 독립적으로 나눌 필요가 없는 작업까지 서브에이전트에 맡길 때 컨텍스트와 시간이 늘어나는 문제
  - 단일 메인 세션을 기반으로 서브에이전트를 생성하여 구현과 리뷰, 검증을 지시하는 방법 대신 다른 방법을 검토한다. 예를 들어 애플리케이션 개발의 경우 구현 담당 세션과 리뷰 담당 세션을 분리한다. 서브에이전트의 경우 개발 세션에서는 개발 관련된 서브에이전트만 호출한다.
  - 구현 담당 세션과 리뷰 담당 세션이 같은 worktree branch를 참조하는 대안을 검토한다. 구현 담당 세션은 리뷰할 commit을 만든 뒤 추적 파일 변경을 멈추고, 리뷰 담당 세션은 저장소가 정한 커밋하지 않는 파일에 결과만 기록한다.
  - 리뷰 결과를 기록할 파일의 위치와 Git 제외 방식은 각 저장소가 정한다. 이 파일이 추적, stage 또는 commit되지 않는지 확인하는 방법과 인계한 마지막 commit이 현재 `HEAD`와 다를 때 검토 결과를 사용하지 않는 조건을 함께 조사한다.
  - TDD 기반으로 애플리케이션 개발을 진행할 때, 테스트와 구현을 각각 커밋을 분리해서 "리뷰 담당 메인 세션"이 "테스트 코드에 문제가 있는지", "테스트 코드를 기반으로 구현 코드를 개선해야 하는지"를 결정하도록 하는 방안에 대해서 리서치한다.
- `skills/` 아래의 큰 `SKILL.md`와 참고 문서가 실행 컨텍스트에 주는 영향
  - 동일한 기능을 제공하면서 용량을 최적화하는 방안을 리서치하고 반영한다.
  - AI 에이전트 지침은 "무엇을 해라"라는 지시보다 "무엇을 하지 마라"는 지침을 작성하는게 더 중요하다는 의견에 대해서 리서치한다.
  - 그래서 AGENTS.md 예시와 스킬 마크다운 파일도 "무엇을 금지한다"를 중심으로 작성하는 것을 검토한다.
  - 그리고 스킬에 서브에이전트를 사용하라는 지침을 제거해서, 서브에이전트 의존성을 없애는 것도 검토한다.
  - "\_README.md"의 경우 단순한 참조 파일이 아니다. 실제 애플리케이션 레포에서 docs 폴더에 복사되고 작업에 사용된다. 그래서 파일의 사이즈가 너무 커지면 애플리케이션 개발 레포에서 작업을 진행할 때 컨텍스트에 영향을 줄 수 있다.
  - 각 `_README.md`는 애플리케이션 저장소의 `docs/designs/README.md` 또는 `docs/dev/README.md` 한 파일로 복사된 뒤, 그 파일만으로 기준을 제공해야 한다. 크기 최적화를 위해 여러 파일로 분할하거나 복사 대상 파일을 늘리지 않는다.
  - `_README.md`의 크기 최적화는 단일 파일 안에서 같은 규칙을 합치되 문서 생성 조건, 작성 권한, 필수 정보, 금지 내용과 검증 방법을 보존하는 방식으로 조사한다.
- 구현과 리뷰를 같은 세션에서 수행할 때 구현 과정의 전제에 의존하는 문제
- 작업 중 검토를 반복해도 누락이 없어졌는지 판단할 기준이 없음
  - 그 대신 리뷰 전용 메인 세션에서 `Goal` 등을 호출해서 Git 히스토리를 참고하여 리뷰를 진행하는 것에 대해서 리서치한다. 컨텍스트 낭비를 방지하기 위해 Git 히스토리가 일정 시간 이상 변경되지 않으면 Goal을 Blocked(Codex 기준) 상태로 전환시킨다.
- 안티패턴 금지 지침과 lint만으로 실제 안티패턴을 식별하기 어려운 문제. "안티패턴에 대해서 리서치하고 안티패턴이 있는지 검사한다"라는 프롬프트만으로는 안티패턴의 제거를 보장하기 어려운 문제
  - 안티패턴과 권장 코드 패턴의 조사에는 작업 중인 애플리케이션 저장소의 코드를 사용하지 않는다. 코드가 아직 없는 작업에도 사용할 수 있도록 GitHub에 배포된 공개 오픈소스 애플리케이션의 고정된 revision, 수정 commit, issue 또는 pull request와 적용 기술의 공식 자료를 근거로 조사한다.
  - 공개 저장소의 현재 코드 모양만으로 안티패턴이나 권장 패턴이라고 단정하지 않는다. 확인된 실패나 수정 이유, 적용 조건과 공식 작성 방식을 서로 대조한다.
  - 각 조사 항목에는 상세 설명, 안티패턴 코드 예시, 같은 실패를 피하는 권장 코드 예시, 권장하는 이유, 적용 조건과 예외, lint 설정 예시와 lint가 판정하지 못하는 범위를 기록한다. 문제의 코드 모양을 정확히 판정하는 lint 규칙이 없으면 그 사실과 대신 사용할 type 검사, 테스트, 실행 검사 또는 담당 리뷰를 기록한다.
- 답변의 외부 링크가 가까운 주장을 실제로 뒷받침하는지 확인하기 어려운 문제
- `use-words-review`가 문제 후보를 유지하는 쪽으로 판정하고 자연스러운 대체 표현이 적용되지 않는 문제
  - 차라리 문제 후보에 대해서 자연스러운 대체 표현을 적극적으로 교체하고, 대체 표현이 없는 상황에서만 문제 후보 표현을 유지하는 것을 검토한다.

## 문제에 대한 대응

- 현재 문제에 대해서 리서치 및 문서화를 진행한다.
  - 현재 문제 해결 방법을 리서치한 다음 현재 우리 폴더에 존재하는 에이전트 지침, 스킬, 스크립트를 개선한다.
- 각 문제를 한 가지 해결 방법으로 곧바로 확정하지 않는다. 서로 다른 자료에서 확인한 대안의 적용 조건, 예상 비용, 실패 가능성과 검증 방법을 비교한다.
- 적용 기준, 수치, 분류와 통과 조건은 요구사항, 승인된 결정, 공식 자료, 저장소에서 확인한 사실 또는 실제 측정 결과를 근거로 정한다. 근거가 없으면 임의로 확정하지 않고 후속 결정 사항으로 남긴다.
- 서로 다른 작업 세션을 두는 방안은 조사 결과에서 제안할 수 있지만 승인된 운영 규칙으로 기록하지 않는다.
- 외부 근거는 최신 공식 문서, 표준, 원 논문과 공식 소스 저장소를 우선하고, 서로 다른 기관의 1차 자료를 다섯 개 이상 확인한다.

## 완료 전 확인할 사항

- 각 문제의 발생 조건, 실패 예시, 자동 검사와 사람 또는 모델 판단의 한계가 조사 문서에 기록되어 있다.
- 서브에이전트를 쓰지 않는 단일 담당 세션과 별도 리뷰 세션을 비교하고, 전달할 입력과 중단 조건이 기록되어 있다.
- 같은 worktree branch를 사용하는 구현 및 리뷰 세션 사이에서 검토할 commit을 고정하고, 커밋하지 않는 결과 파일을 선택, 확인, 작성, 판독하는 조건이 기록되어 있다.
- 공개 오픈소스 애플리케이션에서 안티패턴과 권장 패턴의 근거를 찾는 절차, 항목별 필수 정보와 lint의 판정 한계가 실제 사례와 함께 기록되어 있다.
- 출처가 있다는 사실과 출처가 주장을 뒷받침한다는 판정을 구분하는 검사 방법이 기록되어 있다.
- 문제 후보 표현의 대체 문장을 먼저 만들고 유지할 표현만 근거와 함께 남기는 방안이 기존 결정과 구분되어 기록되어 있다.
- `_README.md` 축소 방안이 단일 파일로 독립적으로 사용하는 조건을 유지하고, 합칠 수 있는 반복과 보존해야 할 정보를 구분한다.
- 각 문제마다 바로 적용할 수 있는 조치, 대표 작업의 평가가 필요한 조치와 요구사항 작성자의 결정이 필요한 선택이 구분되어 있다.
- 조사 범위와 한계, 후속 결정이 필요한 사항이 기록되어 있다.
- 새 설계 패키지가 문서 검사와 문구 검토를 거쳐 현재 작업 브랜치에 커밋되어 있다.

## 주의점

- 작업에 대한 리뷰, 검증은 각 작업마다 1회만 진행한다.
- 서브에이전트는 우선 사용하지 않는다.
- 문제에 대해서 리서치를 할 때 이 레포와 애플리케이션 개발 레포를 반드시 구별해야 한다는 사실을 인지할 것.
