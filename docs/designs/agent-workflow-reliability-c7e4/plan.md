# 에이전트 작업 흐름 개선 적용 계획

이 계획은 먼저 대표 사례와 기대 판정을 승인받고, 그 결과로 확인된 변경만 에이전트 지침, Skill과 검사 스크립트에 적용한다. 별도 리뷰 세션, 필수 서브에이전트 제거와 지침 축소를 조사 결과만으로 기본 동작으로 확정하지 않는다.

대표 사례의 작성, 승인과 실행은 이 계획을 확정한 뒤 진행하는 별도 작업이다. 계획 문서를 승인했다는 사실을 평가가 수행됐거나 후보의 효과가 확인됐다는 근거로 사용하지 않는다.

## 기준과 적용 범위

기준 문서는 [`requirements.md`](./requirements.md)의 "목표", "문제에 대한 대응", "완료 전 확인할 사항"과 "주의점"이다. 작업 순서와 근거는 다음 조사 문서를 따른다.

- [에이전트 작업 분리와 검증 구조 조사](./references/agent-workflow-and-review-research.md)는 서브에이전트 선택, 독립 리뷰, 안티패턴 조사, 출처 확인과 문제 후보 표현의 대응 방향을 관리한다.
- [지침 크기와 금지 문구 설계 조사](./references/instruction-size-and-prohibition-research.md)는 Skill과 단일 README의 축소 조건, 부정형 지침의 한계와 검토 방식 비교를 관리한다.
- [구현 세션, 리뷰 세션과 Goal 운용 조사](./references/session-review-tdd-and-goal-research.md)는 commit 순서, 결과 파일 인계, TDD 변경 읽기와 중단 조건을 관리한다.

세 조사 문서는 완료된 조사 입력이며 이 계획에서 같은 조사를 다시 수행하지 않는다. 요구사항이나 근거가 달라지면 영향받은 주장만 다시 확인한다. 조사에서 지지하지 않은 금지 문구 중심 구성과 Git 기록의 시간상 정체만으로 `Blocked`를 판정하는 방식은 적용 후보로 다루지 않는다. 별도 리뷰 세션과 필수 서브에이전트 제거는 승인된 평가 결과가 생길 때까지 제안 상태로 유지한다.

나중에 `.mjs` 검사 스크립트를 변경하거나 추가할 때에는 [`docs/dev/README.md`](../../dev/README.md)를 적용한다. 기존 문구 검사 스크립트의 실행 방식을 바꾸는 작업에는 [Node.js MJS 명령줄 검사기](../../dev/node/mjs-cli.md)도 적용한다. 새 commit 순회 스크립트에 이 지침의 저장소 전용 규칙을 확장해야 한다면 해당 지침의 적용 범위를 먼저 승인받는다.

변경 대상은 이 저장소의 `src/AGENTS.en.md`, `src/AGENTS.ko.md`, `skills/`, `README.md`, `README.ko.md`와 이 설계 패키지다. 작업 중인 애플리케이션 저장소의 코드, Git 기록과 비공개 검토 자료는 패턴 조사나 평가 사례에 사용하지 않는다. 외부 패키지는 추가하지 않는다.

이 계획의 작업 단위는 메인 세션에서 순서대로 수행한다. 별도 리뷰가 승인된 경우에도 구현 세션의 자식 에이전트가 아니라 별도의 메인 세션을 사용한다. 서브에이전트를 사용하는 후속 실험이 별도로 승인되기 전에는 평가, 구현과 검토에 서브에이전트를 사용하지 않는다. 각 작업 단위는 최종 후보를 대상으로 정해진 검증과 문구 검토를 각각 한 번만 수행한다.

## 먼저 확정할 결정

구현 전에 평가 사례와 다음 선택을 요구사항 작성자 또는 저장소가 지정한 검토자가 승인해야 한다. 승인되지 않은 선택과 연결된 작업만 멈추고, 영향을 받지 않는 자료 준비와 결정적 검사는 계속할 수 있다.

- Merge commit이 있는 범위에서 첫 부모 계보만 검토할지 모든 조상 경로를 검토할지 정한다. Merge 결과를 첫 부모와 비교할지 모든 부모와 비교할지도 함께 정한다.
- 별도 리뷰 세션을 사용할 변경의 종류와 리뷰 요청에 포함할 Git 정보를 정한다. 작업 세션과 리뷰 세션을 분리할 때 어떤 Git 정보로 리뷰 대상을 확정할지, 필요한 정보가 없거나 서로 일치하지 않으면 어느 작업을 멈출지, 리뷰 결과를 반영한 뒤 언제 새 검토 입력을 만들지를 함께 정한다.
- 리뷰 요청과 AGENTS 지침만 사용할지, commit 목록을 고정하는 결정적 스크립트를 함께 사용할지, 반복 절차를 사용자 정의 Skill로 묶을지 정한다. Skill 생성은 이 선택의 결과이지 기본 전제가 아니다.
- 리뷰 시작 전에 이미 존재하는 tracked 변경, stage된 변경과 결과 파일 이외의 untracked 파일을 commit 객체만 읽는 검토와 현재 worktree를 사용하는 검사에서 각각 어떻게 처리할지 정한다. 인계 상태와 달라진 경우의 중단 조건과 처음부터 허용하지 않을 상태를 구분한다.
- TDD 작업에서 실패하는 테스트 전용 commit을 branch 안에 허용할지 정한다.
- `use-words-review`의 기본 의미 검토를 메인 세션 한 번으로 바꿀 때 반드시 유지할 기대 판정과, 별도 리뷰 세션이 필요한 문구의 조건을 정한다.
- 각 저장소가 결과 파일 위치, Git 제외 방식, 보관 기간과 삭제 책임을 정한다. 공통 참고 구현은 이 값을 기본값으로 만들지 않고 필수 입력으로 받는다.

승인 결과는 내용에 따라 `decisions/review-session-operation.md`와 `decisions/instruction-evaluation.md`에 나눠 기록한다. 승인 전에는 빈 결정 문서나 임시 문구를 만들지 않는다.

## 작업 단위와 순서

### 대표 사례와 측정 기준을 고정한다

**목표.** 각 변경이 해결해야 할 실패와 보존해야 할 동작을 실행 전에 확인한다.

**대상 파일.** `docs/designs/agent-workflow-reliability-c7e4/references/agent-workflow-evaluation-cases.md`를 만든다. 승인된 선택이 생기면 앞 절의 결정 문서를 함께 만든다.

**진행 방법.** 평가 자료에는 다음 사례를 서로 구분해 기록한다.

- 한 세션에서 끝나는 순차 작업과 독립적으로 나눌 수 있는 읽기 작업을 같은 입력으로 비교한다.
- 같은 구현 및 검토 작업을 서브에이전트 없는 단일 메인 세션과 분리된 구현 및 리뷰 메인 세션에 제공하고, 두 방식이 받은 입력, 중단 조건, 찾은 문제와 근거 없는 지적을 구분한다.
- 선형 Git 기록에서 시작 commit이 포함되고 마지막 commit까지 부모가 먼저 오는 순서로 나열되는지 확인한다.
- 시작과 마지막이 같은 경우, 시작 commit이 최초 commit인 경우와 시작 commit이 마지막 commit의 조상이 아닌 경우를 포함한다.
- Merge 기록에서는 앞 절에서 승인한 계보와 부모 비교 방식이 적용되고, 선택이 없으면 진행을 멈추는지 확인한다.
- 승인된 시작 상태별로 기존 tracked 변경, stage된 변경과 결과 파일 이외의 untracked 파일을 계속 허용하거나 중단하는 판정이 일치하는지 확인한다. 리뷰 도중 `HEAD`, 인계한 작업 트리 상태 또는 고정된 commit 목록이 달라진 결과는 완료된 리뷰로 사용하지 않는다.
- 테스트 commit과 구현 commit이 분리된 사례에서 테스트 의도와 실패 기록을 근거로 테스트 자체의 문제를 먼저 판정하고, 구현 commit과 누적 결과를 읽은 뒤 테스트를 바꾸지 않고 구현을 개선해야 하는지 판정한다.
- 공개 오픈소스 수정 근거가 충분한 안티패턴 항목과 현재 코드 모양만 인용한 항목을 구분한다.
- 출처가 주장을 전부, 일부 또는 전혀 뒷받침하지 않는 문장을 구분한다.
- 자연스러운 대체 표현이 있는 한국어 문장, 정확한 기술 용어를 유지할 문장과 뜻을 정할 근거가 없는 문장을 구분한다.
- 금지 행동만 적은 지침과 기대 결과, 정상 행동, 필요한 금지 조건과 중단 조건을 함께 적은 지침을 구분한다. 금지 문구의 수를 평가 기준으로 사용하지 않는다.
- 마지막으로 확인한 commit과 현재 commit이 같은 상태, 새 commit을 기다리는 상태와 입력 또는 권한이 없어 진행할 수 없는 상태를 구분한다. 시간 경과만으로 `Blocked`를 기대 판정으로 만들지 않는다.
- Skill과 단일 README를 줄인 뒤 문서 생성 권한, 필수 정보, 금지 내용과 검증 결과가 유지되는지 확인한다.

각 사례에는 입력, 기대 판정, 판정 근거와 사람이 결정해야 할 조건을 기록한다. 실행 환경이 제공하는 입력 및 출력 토큰과 경과 시간만 측정하고, 제공하지 않는 값은 추정하지 않는다. 기대 판정을 모두 충족한 후보끼리만 비용을 비교한다.

**검증.** 각 사례가 `requirements.md`의 어느 문제와 완료 조건을 확인하는지 링크로 연결한다. 요구사항 작성자 또는 지정 검토자가 기대 판정을 승인하기 전에는 다음 작업의 기본 동작을 바꾸지 않는다.

### 고정된 commit 리뷰 방식을 선택해 구현한다

**의존 관계.** 대표 Git 사례, merge 처리, 리뷰 방식과 리뷰 시작 상태의 결정을 먼저 확정한다.

**목표.** 별도 리뷰 메인 세션이 구현 대화와 서브에이전트 없이 고정된 commit 목록을 한 번 검토하고, 저장소가 지정한 비추적 파일로 결과를 전달할 수 있게 한다. 이 목표를 충족하는 데 필요한 가장 단순한 방식을 선택한다.

**대상 파일.** 리뷰 요청과 AGENTS 지침만으로 기대 판정을 충족하면 이 작업 단위에서는 새 Skill이나 스크립트를 만들지 않고, AGENTS 변경과 최종 확인은 뒤의 배포용 지침 작업에서 수행한다. 결정적 commit 목록 생성이 필요하면 승인된 위치에 무의존성 `.mjs` 스크립트를 만든다. 반복 절차를 Skill로 관리하기로 승인한 경우에만 다음 파일을 만든다.

- `skills/review-commit-sequence/SKILL.md`
- `skills/review-commit-sequence/agents/openai.yaml`
- `skills/review-commit-sequence/scripts/commit-sequence.mjs`

**진행 방법.** 리뷰 요청은 저장소 위치, 시작 및 마지막 commit, 적용할 요구사항과 개발 지침, 검사 원문, 결과 파일 위치와 Git 제외 근거를 제공한다. 시작 또는 마지막 commit이 없거나 요청의 값과 현재 저장소 상태가 일치하지 않으면 리뷰 세션이 임의로 범위를 정하지 않고 중단한다.

선택한 방식은 두 commit을 전체 OID로 해석하고 조상 관계를 확인한 뒤 시작 commit이 포함된 검토 목록을 부모가 먼저 오는 순서로 고정한다. 최초 commit과 Merge commit을 별도 조건으로 처리하며, Git 오류와 결정이 필요한 merge를 성공으로 바꾸지 않는다. 스크립트를 선택했다면 출력에는 입력 OID, 순서가 고정된 목록, 각 commit의 부모와 누적 비교 범위를 포함하되 리뷰 판정은 넣지 않는다.

리뷰 방식과 관계없이 다음 순서를 한 번의 리뷰로 관리한다.

1. 요구사항, 적용할 개발 지침, 검사 결과, 결과 파일 위치와 Git 제외 근거를 확인한다.
2. 현재 `HEAD`, tracked diff, stage 영역과 승인된 결과 파일 이외의 untracked 파일이 인계 상태와 같은지 확인한다.
3. 선택한 방식이 고정한 commit을 순서대로 읽고 commit별 지적을 기록한다.
4. TDD commit이 있으면 테스트의 요구사항 근거와 의도한 실패를 먼저 판정하고, 구현을 읽은 뒤 테스트 변경 없이 구현을 개선해야 하는지 판정한다.
5. 시작 commit 직전 상태부터 마지막 commit까지 누적 변경을 확인한다.
6. 결과 파일의 마지막에 완료 상태와 전체 OID를 기록하고, 결과 파일을 제외한 인계 상태를 다시 확인한다.

리뷰 절차는 소스, 테스트, 설정과 요구사항 문서를 수정하지 않는다. 구현 세션의 대화 기록과 자기 평가는 입력에서 제외하고 승인된 요구사항, 결정, diff와 검사 원문만 사용한다. 결과 파일 위치와 Git 제외 방식은 저장소가 제공해야 하며 공통 파일명을 정하지 않는다. 새 commit이 생기거나 결과 파일 외의 작업 트리 상태가 인계 시점과 달라지면 기존 결과를 고쳐 이어 쓰지 않고 완료되지 않은 결과로 남긴다.

**검증.** 승인된 리뷰 방식은 대표 Git 사례를 최종 후보에 한 번 적용한다. 직접 프롬프트 방식은 뒤의 배포용 지침 작업에서 별도 리뷰 세션이 AGENTS와 리뷰 요청만으로 범위를 고정하고 결과 파일을 완성하는지 확인한다. 스크립트를 선택했다면 자체 검사에서 선형 기록, 단일 commit, 최초 commit, 비조상 입력, merge 방식 누락과 승인된 merge 방식을 확인한다. Skill을 선택했다면 Skill 디렉터리만 복사해 외부 패키지와 네트워크 없이 실행되는지도 확인한다. 모든 방식에서 무시되지 않거나 이미 추적된 결과 파일을 거부하고, 리뷰 전후에 결과 파일을 제외한 인계 상태가 같으며 결과 파일의 순서가 고정된 목록과 같은지 확인한다.

### 공개 코드 패턴 조사 절차를 조건부 자료로 분리한다

**의존 관계.** 안티패턴 평가 사례와 기대 판정을 먼저 승인받는다.

**목표.** 애플리케이션 코드가 없을 때에도 공개 수정 근거와 공식 작성 방식을 사용해 안티패턴, 권장 패턴과 검사 한계를 기록한다.

**대상 파일.** `skills/use-dev-guidance/SKILL.md`를 수정하고 `skills/use-dev-guidance/references/public-pattern-research.md`를 만든다. 단일 기준 문서에 남아야 할 저장소별 기록 조건은 `skills/use-dev-guidance/references/_README.md`와 `docs/dev/README.md`의 공통 내용에서 한 번만 관리한다.

**진행 방법.** `SKILL.md`에는 공개 패턴 조사를 실행할 조건과 참고 파일을 읽지 않을 조건만 둔다. 새 참고 파일은 다음 정보를 찾고 판정하는 순서를 관리한다.

- 실행 가능한 공개 애플리케이션의 고정된 revision, 수정 commit, issue 또는 pull request와 라이선스
- 유지보수자가 기록한 실패, 발생 조건과 수정 이유
- 적용 기술의 현재 공식 작성 방식과 공식 검사 규칙
- 원문을 그대로 복사하지 않고 실패 구조만 남긴 안티패턴 및 권장 패턴 코드 예시
- 권장 패턴이 실행 순서, 상태, 오류 처리 또는 책임을 바꾸는 이유
- 권장 패턴의 적용 조건과 예외
- lint 설정, 필요한 type 정보, lint가 판정하는 코드 모양과 판정하지 못하는 동작
- lint로 확인할 수 없을 때 사용할 type 검사, 테스트, 실행 증거 또는 지정 검토자

작업 중인 애플리케이션 코드는 이 조사 단계의 근거로 사용하지 않는다. 패턴 기록을 실제 저장소에 적용하는 단계에서만 대상 요구사항, 기술 버전과 변경 코드를 비교한다. 정확한 lint 규칙을 확인하지 못하면 다른 규칙을 대신 붙이지 않는다.

**검증.** 공개 수정 이유, 공식 작성 방식, 적용 조건과 예외, 검사 한계가 모두 있는 항목만 완성된 조사로 판정한다. 고정되지 않은 branch 링크, 라이선스가 확인되지 않은 원문 복제, 현재 코드 모양만으로 붙인 안티패턴 이름과 근거 없는 lint 설정은 평가 사례에서 실패해야 한다.

### 문구 검토를 한 번의 의미 판정으로 줄인다

**의존 관계.** 문구 평가 사례, 책임 있는 검토자와 기본 검토 방식의 채택 조건을 먼저 승인받는다.

**목표.** 작성 단계에서 자연스러운 대체 표현을 먼저 적용하고, 저장 직전 한 번의 문구 검토에서는 남아 있는 표현과 출처 근거를 판정한다.

**대상 파일.** 다음 파일을 수정하거나 만든다.

- `skills/use-words-review/SKILL.md`
- `skills/use-words-review/references/korean.md`
- `skills/use-words-review/references/examples.md`
- `skills/use-words-review/references/source-support.md`

**진행 방법.** `SKILL.md`는 같은 저장 또는 공유 단위를 완성한 뒤 한 번만 의미 검토한다. 승인된 평가에서 메인 세션 방식이 기대 판정을 모두 충족하면 필수 서브에이전트 호출을 제거한다. 별도 관점이 필요한 조건이 승인되면 자식 에이전트가 아니라 별도 리뷰 세션으로 넘기며, 두 방식을 동시에 실행하지 않는다.

`references/korean.md`에는 모든 한국어 판정에 필요한 판단 순서, 의미 보존, 대체 표현 우선 적용, 유지 근거와 세 결과 상태만 남긴다. 긴 사례와 검사 결과가 이미 제공하는 설명은 대표 평가로 중복 여부를 확인한 뒤 제거한다. `references/examples.md`는 언어와 관계없이 필요한 역할, 근거와 문장 연결 사례만 유지한다.

외부 확인이 필요한 주장이 있는 경우에만 `references/source-support.md`를 읽는다. 이 자료는 주장을 최소 단위로 나누고 가까운 원문이 전부, 일부 또는 전혀 뒷받침하지 않는지 판정하는 절차를 관리한다. 일부 근거만 있으면 문장의 적용 범위를 줄이거나 근거를 보충하고, 뒷받침하지 않으면 삭제하거나 불확실성을 밝힌다. 링크 접근 가능성 검사는 이 의미 판정을 대신하지 않는다.

검사 스크립트의 `sources`, `checks`, `catalog`, `rules`, `warnings`와 `summary` 구조는 유지한다. 출처와 주장의 논리 관계나 대체 문장의 의미 보존은 정규식으로 확정하지 않으므로 `scan.mjs`에 자동 통과 판정을 추가하지 않는다.

**검증.** 최종 후보에서 `scan.mjs --self-test`를 한 번 실행한다. 승인된 문구 사례에서 대체 표현이 있는 후보는 저장 전에 바뀌고, 정확한 기술 용어는 구체적인 유지 근거와 함께 남으며, 뜻이나 책임 주체를 정할 수 없는 문장은 `needs human input`이어야 한다. 출처 사례는 기대한 뒷받침 범위와 모두 일치해야 한다. 한 공유 단위에서 같은 의미 검토를 반복 호출하지 않았는지도 실행 기록으로 확인한다. 저장소 전체 lint는 마지막 통합 확인에서 한 번만 실행한다.

### Skill과 단일 README의 반복을 줄인다

**의존 관계.** 대표 문서 작업과 축소 전 기대 판정을 먼저 고정한다. 앞 작업에서 추가한 실행 조건도 평가 기준에 포함한다.

**목표.** 실행마다 읽는 내용은 줄이되 문서 생성 권한, 중단 조건과 검증 책임을 유지한다.

**대상 파일.** 다음 묶음을 각각 독립된 변경으로 다룬다.

- `skills/use-design-docs/SKILL.md`, `skills/use-design-docs/references/_README.md`, `docs/designs/README.md`
- `skills/use-dev-guidance/SKILL.md`, `skills/use-dev-guidance/references/_README.md`, `docs/dev/README.md`
- `skills/use-words-review/SKILL.md`와 이 Skill이 선택하는 참고 파일

**진행 방법.** 두 `use-*` Skill에는 기준 README 확인, 필요한 작업 선택, 실행 순서, 중단 조건과 참고 자료 선택만 남긴다. 문서 종류별 생성 조건, 작성 권한, 필수 정보, 금지 내용과 검증 기준은 각각의 README가 관리한다. 같은 규칙이 AGENTS, Skill과 README에 있으면 현재 책임 문서 한 곳에 전문을 남기고 다른 파일에는 실행 조건과 링크만 둔다.

두 `_README.md`는 여러 파일로 나누지 않는다. 설계용 파일은 복사 뒤 `docs/designs/README.md` 하나로, 개발용 파일은 `docs/dev/README.md` 하나로 독립적인 기준을 제공해야 한다. 공통 규칙을 파일 안에서 한 번만 설명하고 문서 종류별 절에는 그 종류만의 조건을 남긴다. 관리용 HTML 주석을 제외한 설계용 기본본과 현재 기준 README의 공통 내용이 계속 일치해야 한다. 개발용 기본본은 이 저장소에만 적용되는 링크와 규칙을 제외한 공통 내용을 유지한다.

한 번에는 반복 문장 제거, 참고 자료 선택 조건 변경 또는 README 내부 공통화 중 한 묶음만 바꾼다. 각 묶음 뒤 같은 대표 사례를 한 번 실행하고 기대 판정이 달라지면 그 묶음을 채택하지 않는다. 목표 바이트, 토큰 수나 감소율은 평가 전에 정하지 않는다.

**검증.** 변경 전후의 파일 바이트, 실제로 읽은 파일, 실행 환경이 제공한 입력 및 출력 토큰, 경과 시간과 기대 판정을 기록한다. 토큰을 제공하지 않으면 측정 불가로 남긴다. 문서 생성 승인, 생성 거절, 기존 README 사용, 위치 근거 부족, 문서 종류별 필수 정보와 금지 내용의 대표 사례가 모두 같은 판정을 내릴 때만 더 작은 후보를 채택한다.

### 배포용 지침과 적용 안내를 연결한다

**의존 관계.** 앞의 Skill 변경과 평가가 끝난 뒤 한 번만 수행한다.

**목표.** 전역 지침은 호출 조건만 제공하고 상세 절차는 각 Skill이 한 번만 관리하도록 한다.

**대상 파일.** `src/AGENTS.en.md`, `src/AGENTS.ko.md`, `README.md`와 `README.ko.md`를 같은 의미로 수정한다.

**진행 방법.** 두 AGENTS 예시는 다음 조건만 짧게 제공한다.

- 작성 단계에서는 문제 후보에 자연스러운 대체 표현이 있으면 먼저 적용하고, 새 뜻이나 책임 주체를 정해야 할 때에는 묻는다.
- 지침은 기대 결과와 정상 행동을 먼저 설명하고, 실제로 막아야 하는 우회 행동에는 조건, 대신 수행할 행동과 중단 또는 문의 조건을 함께 적는다. 안티패턴 이름이나 금지 문구의 수를 준수 근거로 사용하지 않는다.
- 서브에이전트는 독립 작업의 병렬 이익이 전달과 종합 비용보다 큰 경우에만 사용한다. 구현 세션이 서브에이전트를 사용하도록 승인받은 경우에도 구현과 직접 관련된 독립 작업만 맡기고, 리뷰나 검증을 자식 에이전트에 맡기지 않는다.
- 작업 세션과 리뷰 세션을 분리한 경우에는 리뷰 요청에 포함된 Git 정보와 승인된 저장소 규칙으로 검토 대상을 확정하도록 안내한다. 필요한 정보가 없거나 서로 일치하지 않을 때 어느 작업을 멈출지도 함께 설명한다.
- 별도 리뷰 메인 세션은 승인된 적용 조건과 고정된 commit 입력이 있을 때만 선택된 리뷰 방식을 사용하며, 구현 세션의 자식 에이전트로 대신하지 않는다. 사용자 정의 Skill이 선택되지 않았다면 Skill 호출을 요구하지 않는다.
- 마지막으로 확인한 commit과 현재 commit이 같으면 리뷰를 다시 시작하지 않는다. 시간 경과만으로 `Blocked`로 판정하지 않고, 입력이나 권한이 없어 안전하게 진행할 방법이 없을 때만 막힌 상태로 기록한다.
- 저장 또는 공유 단위의 문구 검토는 승인된 기본 방식으로 한 번만 실행하고, 다른 Skill이 같은 역할의 검토를 추가하지 않는다.

두 README는 승인된 리뷰 방식과 적용 조건을 설명한다. 사용자 정의 Skill을 선택했다면 연구용 참고 구현이며 자동으로 세션을 만들거나 결과 파일 위치를 정하지 않는다고 밝힌다. 설치할 때 Skill 디렉터리 전체를 복사하고 대상 저장소가 결과 파일과 Git 제외 정책을 정해야 한다는 조건을 두 언어에서 같게 유지한다. Skill을 선택하지 않았다면 존재하지 않는 Skill의 설치나 호출을 안내하지 않는다. 상세 commit 순회 절차와 평가 기준은 README에 복제하지 않는다.

**검증.** 두 언어의 호출 조건, 권한, 중단 조건과 조건부 설치 설명을 문장별로 대조한다. 작업 세션과 리뷰 세션을 분리한 사례에서 두 AGENTS 예시가 승인된 Git 정보와 중단할 작업을 같은 뜻으로 설명하는지 대조한다. 리뷰 세션이 두 AGENTS 예시와 리뷰 요청만으로 검토 대상을 고정할 수 있는지도 확인한다. AGENTS만 읽었을 때 전역 원칙과 선택한 리뷰 방식의 호출 조건을 알 수 있고, 추가 자료를 선택한 경우에만 그 자료에서 실행 입력과 결과를 알 수 있어야 한다. 금지 조건만 있고 정상 행동이나 후속 조치가 없는 지침, 시간만으로 `Blocked`를 정하는 지침과 같은 절차의 전문이 여러 파일에 남아 있지 않은지도 확인한다.

## 전체 검증과 완료 조건

각 작업 단위의 대표 사례 실행, 결정적 검사와 문구 검토는 해당 단위의 최종 후보에서 각각 한 번 수행한다. 전체 변경은 논리 단위가 모두 끝난 뒤 한 번 통합 확인하며, 이미 끝난 대표 사례와 의미 검토를 반복하지 않고 기록된 결과와 파일 사이의 연결만 확인한다.

- `pnpm lint`를 전체 최종 상태에서 한 번 실행한다. 변경하거나 추가한 `.mjs` 스크립트의 자체 검사는 해당 작업 단위에 기록된 한 번의 결과를 사용한다.
- 평가 자료의 각 기대 판정이 실제 결과와 일치하고, 측정할 수 없는 값을 추정하지 않는다.
- 두 AGENTS 예시는 작업 세션과 리뷰 세션을 분리한 경우 리뷰 요청에 포함할 Git 정보, 검토 대상 확정 방법과 필요한 정보가 없거나 서로 일치하지 않을 때 멈출 작업을 같은 뜻으로 설명한다.
- 별도 리뷰 세션은 승인된 직접 프롬프트, 스크립트 또는 Skill 방식으로 지정된 시작 commit을 포함한 고정 목록을 순서대로 검토하고, 결과 파일에는 같은 목록, commit별 판정과 누적 판정이 남는다.
- 리뷰 결과 파일은 추적, stage 또는 commit되지 않으며 인계한 마지막 commit과 현재 `HEAD`가 다르면 사용되지 않는다.
- TDD 변경에서는 테스트 자체의 문제와 테스트를 바꾸지 않고 구현을 개선할 필요를 구분한 판정이 남는다.
- 공개 패턴 조사 항목은 고정된 공개 revision, 수정 근거, 공식 작성 방식, 코드 예시, 권장 이유, 적용 조건과 예외, lint 예시와 탐지 한계를 갖춘다.
- 외부 출처가 있는 문장은 링크 존재 여부와 주장 뒷받침 판정을 구분한다.
- 한국어 문제 후보는 대체 표현을 먼저 적용하고, 남은 후보에는 유지 근거나 사람의 판단이 필요한 이유가 있다.
- 두 `_README.md`는 각각 한 파일로 독립적으로 사용할 수 있고 축소 전 문서 판정이 유지된다.
- 두 AGENTS 예시와 변경한 Skill은 기대 결과와 정상 행동을 먼저 설명하고 필요한 금지 조건에는 대체 행동과 중단 조건을 함께 제공한다.
- 새 commit이 없으면 리뷰를 반복하지 않으며, 시간 경과만으로 `Blocked`를 기록하지 않는다.
- 별도 승인이 생기기 전까지 계획 실행 기록에는 서브에이전트 호출이 없다.
- 변경한 한국어와 영어 산출물을 같은 공유 단위로 묶어 문구 검토를 한 번 수행하고, 개인 절대 경로, 비공개 식별자, 인증정보, HTML 임시 주석과 미해결 표시가 없는지 확인한다.

문서와 평가 결과만으로 실제 애플리케이션 저장소의 준수를 주장하지 않는다. 대표 작업에서 승인된 기대 판정과 실행 증거가 모두 확인된 변경만 배포용 참고 구현에 남긴다.

## 커밋 단위

1. 승인된 평가 사례와 결정 문서
2. 승인된 commit 리뷰 방식과 필요한 경우에만 추가하는 무의존성 검사 스크립트 또는 Skill
3. 공개 코드 패턴 조사 절차
4. 문구 검토, 출처 판정과 대체 표현 우선 절차
5. 각 Skill과 단일 README의 독립적인 축소 묶음
6. 두 언어 AGENTS와 README의 적용 안내 및 최종 측정 결과

각 commit은 이름을 지정한 파일만 stage한다. 한 단위의 결정적 검사가 실패하거나 승인된 기대 판정과 다르면 다음 commit으로 넘어가지 않는다.

## 중단 조건

- 대표 사례와 기대 판정의 승인 책임자를 저장소 근거로 확인할 수 없으면 행동 변경을 시작하지 않는다.
- Merge가 있는 commit 구간에서 계보와 부모 비교 방식이 정해지지 않으면 그 구간의 순회 결과를 만들지 않는다.
- 직접 프롬프트, 보조 스크립트와 사용자 정의 Skill 중 사용할 방식이 승인되지 않으면 리뷰용 Skill이나 스크립트를 만들지 않는다.
- 리뷰 시작 상태에 이미 있는 tracked, staged 및 untracked 변경의 처리 기준이 정해지지 않으면 해당 상태에서 리뷰를 시작하지 않는다.
- 별도 리뷰 세션을 기본값으로 삼을 작업 종류가 승인되지 않으면 분리 방식을 승인된 대표 사례 밖에 적용하지 않는다.
- `use-words-review`의 메인 세션 방식이 승인된 기대 판정을 충족하지 못하면 필수 서브에이전트 지침을 바로 제거하지 않는다. 실패 사례를 별도 리뷰 세션 조건으로 보낼 수 있는지 다시 결정한다.
- Git 기록이 일정 시간 바뀌지 않았다는 사실만으로 `Blocked`를 요구하는 변경은 적용하지 않는다. 실제 진행 불능 상태를 확인할 수 없으면 대기 또는 정상 종료 조건으로 남긴다.
- `_README.md`를 여러 파일로 나누거나 복사 대상 파일을 늘려야만 크기를 줄일 수 있으면 그 축소안을 적용하지 않는다.
- 외부 패키지, 네트워크 의존성 또는 저장소 전체 정책 변경이 필요하면 현재 계획에 포함하지 않고 요구사항 작성자에게 영향과 대안을 설명한다.
- 요구사항, 승인된 결정 또는 실제 측정 없이 통과 수치와 목표 크기를 정해야 하면 그 수치를 만들지 않는다.
