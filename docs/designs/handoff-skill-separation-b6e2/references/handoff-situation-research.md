# 안내형 문구와 인수인계 정보를 구분하는 상황 조사

안내형 문구, 주의사항과 지침은 문구의 형식보다 설명 대상, 독자가 해야 할 행동과 생략했을 때 달라지는 뜻으로 분류해야 한다. 작업이나 검토를 이어받는 데 필요한 부연은 인수인계 대상이 될 수 있다. 이용자가 과제를 수행하는 데 필요한 설명과 사실을 성립시키는 조건은 원래 자료에 유지해야 한다.

이 조사는 [다양한 상황의 인식](../requirements.md#다양한-상황의-인식)을 구체화하기 위한 자료다. 공식 자료는 2026-10-18에 확인했다. 아래 대조 문안은 판정 차이를 설명하려고 만든 예시이며, 실제 AI 결과물에서 수집한 사례나 발생 빈도에 관한 증거는 아니다.

## 공식 자료에서 확인한 구분

[Google의 알림 작성 지침](https://developers.google.com/style/notices)은 참고 정보, 신중한 진행이 필요한 주의사항, 손실이나 보안 문제를 막는 경고를 구분한다. 필요한 절차와 선행 조건을 부가 알림으로 처리하지 말라는 설명도 있다. 짧은 원문은 “Don't make a full procedural step into a note.”다. 따라서 주의나 안내 형식이라는 이유만으로 인수인계 대상으로 삼을 수 없다.

[Microsoft의 절차 작성 지침](https://learn.microsoft.com/en-us/style-guide/procedures-instructions/writing-step-by-step-instructions)은 독자가 어디에서 행동하는지와 절차를 끝내는 행동을 설명하도록 한다. 제목을 반복할 뿐인 도입 문장은 피한다. 짧은 원문은 “include actions that complete a procedure”다. 버튼을 누르는 순서도 사용 방법 문서의 본래 내용일 수 있으며, 같은 조작을 검토자에게 보여 주기 위한 부연과 구분해야 한다.

[W3C의 입력 설명 해설](https://www.w3.org/WAI/WCAG22/Understanding/labels-or-instructions.html)은 기대하는 입력과 형식, 선택 항목의 뜻을 설명한다. [입력 오류 해설](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html)은 오류가 난 항목과 잘못된 점을 글로 설명해야 한다고 밝힌다. 이는 화면에 필요한 설명을 보존할 근거다. 인수인계 파일에만 옮기면 화면을 사용하는 사람이 그 정보를 받을 수 없다.

[Google Python 지침의 함수 설명](https://google.github.io/styleguide/pyguide.html#383-functions-and-methods)은 코드를 읽지 않고 함수를 사용할 수 있을 만큼 호출 방법과 의미를 설명하도록 한다. 호출자가 알아야 할 부작용과 내부 구현 설명도 구분한다. API 호출 조건과 작성 완료 보고를 구분할 때 참고할 수 있다.

## 조사와 적용 확인에 사용할 상황

### 디자인 시안과 화면의 동작

시안 검토자에게 특정 상태를 재현하는 방법을 알려 주는 설명은 인수인계 후보로 조사한다. 같은 조작이 사용 방법 문서, 접근성 안내나 화면의 필수 도움말에 있으면 원래 역할을 먼저 확인한다. Microsoft의 절차 지침과 W3C의 입력 설명이 이 구분을 뒷받침한다.

대조 문안은 검토 메모의 “오류 상태를 보려면 빈 값으로 제출하세요”와 실제 입력란의 “날짜를 YYYY-MM-DD 형식으로 입력하세요”다. 앞 문장은 검토를 이어받기 위한 정보가 될 수 있다. 뒤 문장은 입력하는 사람에게 필요한 설명이다. 정렬 방향과 모달을 닫는 방법도 검토용 시연인지 실제 동작 규칙인지 확인해야 한다.

### 작성 경위, 완료 보고와 제출 형식

작성 완료 선언, 읽은 파일의 나열, 프롬프트를 사용했다는 부연과 양식을 따르지 않았다는 설명을 조사한다. 대조 대상으로 방법 안내의 절차, 요청된 검토 보고와 제출 형식의 필수 항목을 함께 확인한다. [기존 내용 선정 자료](../../../../skills/use-better-handoff/SKILL.md#decide-what-belongs-where)가 작업 수행 지시와 본래 문서 내용을 구분한다.

“자료를 읽고 초안 작성을 마쳤습니다”는 인수인계 후보지만, 보고서 자체의 조사 방법이나 요청된 검토 결과는 그 문서가 다루는 내용일 수 있다. 정해진 양식의 미충족 사실이 문서의 유효성에 영향을 준다면 부연만 이동해 문제를 감추지 않는다.

### 측정 보고서, 시연 자료와 수치 설명

미실행 항목, 확인하지 못한 환경과 후속 확인 안내를 조사하되 관측값의 조건과 구분한다. “실제 사용자 PC에서 측정한 값이 아닙니다”를 옮기기 전에 남은 수치가 어떤 환경의 값으로 읽히는지 확인한다. 수치가 시뮬레이션 값인지 실측값인지와 측정 환경은 결과 해석에 필요한 조건이다.

측정 조건의 보존 근거는 [기존 사실 조건 기준](../../../../skills/use-better-handoff/SKILL.md#decide-what-belongs-where)이다. “다음 작업에서 다른 환경도 확인해야 합니다”라는 후속 메모와 현재 수치의 근거는 따로 판정한다. 실행하지 않은 확인을 실행했다고 기록하지 않는다.

### 코드, API 설명과 유지보수 안내

코드 주석과 API 문서에 섞인 작성 완료 보고, 검토 순서와 후속 작업 안내를 조사한다. 함수의 입력 제한, 오류 조건, 부작용이나 구현 선택의 이유는 코드 사용자나 유지보수자가 알아야 할 수 있다. Google의 함수 설명 기준은 호출에 필요한 정보와 내부 구현 설명을 구분할 근거다.

대조 문안은 “이번 작업에서 재시도를 추가했습니다”와 “요청 본문은 재시도할 때 다시 읽을 수 있어야 합니다”다. 앞 문장은 작업 보고 후보지만, 뒤 문장은 호출 조건일 수 있다. 주석이라는 형식만으로 옮기거나 모든 구현 이유를 인수인계 파일로 모으지 않는다.

### 설치, 배포와 운영 절차

담당자가 이어서 확인할 미완료 작업과 실제 실행 지침을 함께 조사한다. “다음 작업에서 배포를 확인하세요”와 배포 절차의 “계속하기 전에 백업을 확인하세요”는 명령형이 같아도 설명 대상이 다르다. 후자는 실제 절차의 선행 조건일 수 있다.

Microsoft의 절차 작성 기준과 Google의 경고 구분을 적용하면 실행 순서와 손실 방지 조건을 인수인계 설명으로 오인해 빼면 안 된다. 미완료 작업의 근거를 인수인계 파일에 기록하더라도 작업 수행이나 권한 부여가 확인된 것처럼 바꾸지 않는다.

### 발표 자료, 표 계산 문서와 보조 설명

슬라이드 본문, 발표 메모, 표의 각주, 셀 메모와 파일 끝의 전달 문구도 조사 대상에 넣는다. 발표 준비를 이어받기 위한 확인 순서와 독자에게 필요한 단위, 출처, 가정과 해석 조건을 구분한다. 후속 [발표 자료의 적용 관찰](./handoff-behavior-cases.md#축약안의-오류와-보완)은 텍스트로 표현한 대본과 CSV를 사용했으며 원본 형식별 편집을 입증하지 않는다.

“이 슬라이드에서 시연 화면으로 전환하세요”가 발표 진행용 인수인계인지, 요청된 발표 대본의 일부인지 확인한다. “금액 단위는 USD이며 반올림했습니다”는 값을 읽는 조건이므로 메모나 각주에 있다는 이유로 이동하지 않는다. 표와 발표 자료에 적용할 때도 원래 제출 목적을 확인한다.

## 사례를 늘리면서 스킬 분량을 관리하는 방법

새 상황을 조사할 때에는 문구가 놓인 자료, 설명 대상, 독자의 행동, 이동하면 사라지는 정보와 필요한 조건을 기록한다. 같은 문장도 문서의 역할과 독자가 달라지면 판정이 달라지는 대조 문안을 만든다. 키워드를 포함하지 않는 부연, 여러 문장에 나뉜 조건과 한 문장에 작업 보고 및 필수 조건이 섞인 경우도 포함한다.

인수인계 스킬의 본문에는 조사에서 얻은 공통 판단만 정리하고 사례 자료에는 추가 판단이 필요한 대조만 둔다. 상황별 목록, 모든 수집 원문과 같은 뜻의 예문은 조사 및 평가 자료에 남긴다. 수집 사례와 다른 표현 및 배치를 사용한 입력에서 판정이 유지되는지 확인해야 처음 예문을 다시 처리하는 수준을 넘어서는지 알 수 있다.

영어 지침에서 각 언어의 문구를 판정하는 일과 문구를 영어로 번역하는 일도 구분한다. 언어별 원문과 혼합 문장의 확인 결과를 기록하며, 일부 언어의 성공을 전 세계 언어에 대한 검증으로 확대하지 않는다. 실제 적용과 누락 여부의 확인은 [플랜의 동작 및 비용 비교](../plan.md#5-같은-입력에서-동작과-문맥-비용을-비교한다)에서 수행한다.
