# 인수인계 정보 배치와 표현 검토의 책임 분리 근거

인수인계 정보의 배치 절차는 `use-better-handoff`로 이관하고 표현 검사는 `use-better-terms`에 유지할 수 있다. 인수인계 파일의 갱신과 읽기는 기존 내용 선정에 없던 책임이다. 나눌 책임은 [요구사항의 두 스킬의 책임](../requirements.md#두-스킬의-책임)에서 정한다.

## 기존 스킬에서 이관할 내용

분리 전 표현 스킬의 내용 선정 절은 작성 경위, 진행 보고와 부가 주의 문구를 제외하는 시점을 정했다. 상세 자료는 문장의 설명 대상, 명시적인 수록 지시, 인용과 사실 조건을 구분했다. [이관 기준](./handoff-behavior-cases.md#규칙의-이관과-보존)에 따라 이 분류를 보존하되 [새 스킬의 배치 판단](../../../../skills/use-better-handoff/SKILL.md#decide-what-belongs-where)에서는 인수인계 대상 설명을 지정 파일로 옮긴다.

내용 선정 규칙은 스킬의 여러 절에 있다. 시작 문장, 독자 정보 사용 조건, 첫 번째 문구 판정 기준에도 수록 여부에 관한 규칙이 있다. [공통 사례](../../../../skills/use-better-terms/references/examples.md)의 서로 다른 결정을 각 문서에 두는 예시는 문장 표현보다 정보 배치에 가깝다. 이관할 때 이 문장들을 함께 대조해야 두 스킬이 같은 판단을 반복하지 않는다.

2026-10-18의 마크다운 크기는 본문 95줄, 12,309바이트, 한국어 자료 137줄, 11,208바이트, 공통 사례 98줄, 4,432바이트, 내용 선정 자료 43줄, 4,485바이트다. 합계는 373줄, 32,434바이트다. 모든 파일을 매번 읽는다는 뜻은 아니므로 전체 크기를 실행당 토큰 수로 환산하지 않는다.

분리 전 본문과 한국어 자료는 문맥 확인, 근거 확인, 대안 작성과 의미 보존을 각각 설명했다. 현재는 [본문의 문구 판정 절](../../../../skills/use-better-terms/SKILL.md#improve-and-judge-the-outputs)에 공통 절차를 모으고 한국어 자료에는 한국어에서 달라지는 판단을 남긴다. 반면 구체적인 문장 대조는 판단을 적용한 예시이므로 같은 주제를 다룬다는 이유만으로 중복으로 판정하지 않는다.

## 새로 필요한 인수인계 파일 관리

[기존 구성 비교](../../document-content-selection-6e3b/references/skill-composition-comparison.md#적용한-구성과-재비교-조건)는 같은 수록 판정과 표현 검토를 한 번에 수행하는 방식을 채택했다. 내용 선정만 별도로 수행하는 상황은 당시 자료에서 확인되지 않았고, 실제 토큰 차이도 측정하지 않았다.

새 요구사항에는 기록할 위치의 지정, 기존 인수인계 내용의 갱신과 인수인계 파일을 통한 프로젝트 파악이 포함된다. 이전의 제외 판정을 두 스킬에 나눠 복제하는 것과는 작업이 다르다. 이전 결정을 고쳐 쓰지 않고 새 요구사항을 기준으로 분리를 계획할 수 있다.

## 짧은 스킬과 필요한 자료의 로딩

[Agent Skills 명세](https://agentskills.io/specification#progressive-disclosure)는 이름과 설명, 활성화한 본문, 필요한 자료를 읽는 시점을 구분한다. 짧은 원문은 “Resources (as needed)”다. 2026-10-18 확인본은 본문에서 필요한 참고 파일을 직접 연결하도록 하며, 여러 파일을 거쳐야 규칙을 찾는 구조를 피하도록 권한다. 파일을 나눠도 전부 필수로 읽으면 이점이 줄어든다.

[OpenAI Docs의 스킬 작성 지침](https://learn.chatgpt.com/docs/build-skills)은 `description`에 맞는 작업에서 에이전트가 스킬을 자동 선택할 수 있다고 설명한다. 2026-10-18 확인본의 표현은 “can choose a skill”이다. 설치 위치에 파일을 두고 이름을 등록하는 것과 실제 작업에서 호출되는 것은 다른 확인 대상이다. 짧은 호출 지침과 실제 입력에서의 관찰이 모두 필요하다.

[OpenAI의 스킬과 프롬프트 구성 지침](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra#better-skills)은 2026-09-11 게시본에서 긴 설명과 겹치는 호출 조건이 불필요한 스킬 로딩을 유발할 수 있다고 설명한다. 여러 작업을 가진 스킬에는 필요한 자료로 안내하는 짧은 본문을 권한다. 이는 모델별 조언이므로 두 스킬에 같은 분할 수나 절차 길이를 일괄 적용하는 근거는 아니다.

[Anthropic의 스킬 작성 지침](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices#concise-is-key)은 이미 제공된 지식을 반복하지 않고 각 설명의 필요성을 따져 보도록 한다. 짧은 원문은 “Does this paragraph justify its token cost?”다. 2026-10-18 확인본은 필요한 세부 자료만 읽는 구성과 실제 사용 관찰도 권한다. 이 자료에서는 작성 원칙을 참고하며 특정 모델 사용이나 새로운 실행 도구를 도입하지 않는다.

이 근거로 공통 판단은 짧은 본문에 모으고 대조 사례를 조건부 자료로 두는 구성을 제안한다. 항상 수행할 판단을 참고 자료로 옮긴 뒤 다시 필수로 읽게 하는 구성은 피한다. 문장을 줄일 때도 적용 조건, 예외와 필요한 행동을 보존한다.

## 스킬을 영어로 작성하는 기준

[작성 언어 요구사항](../requirements.md#스킬의-작성-언어)은 두 스킬을 영어로 작성하도록 정한다. `description`, 본문과 참고 자료의 지침 및 판정 설명에 같은 기준을 적용할 수 있다. 언어를 판단하는 원문과 예문은 지침의 설명 언어와 구분해야 한국어 표현 검사도 유지할 수 있다.

[Google의 국제 독자를 위한 작성 지침](https://developers.google.com/style/translation)은 2026-10-18 확인본에서 쉬운 단어, 모호하지 않은 문장, 일관된 용어와 행동에 앞서는 조건을 권한다. 짧은 원문은 “Use clear, concise, and unambiguous language”다. 관용구와 특정 문화에 의존하는 예시도 피하도록 한다. 이를 영어 지침의 작성 기준으로 참고하되 특정 영어권 관습이나 영어 결과물을 모든 작업에 강제하는 근거로 사용하지 않는다.

[상황별 조사](./handoff-situation-research.md)는 더 다양한 자료에서 이동과 보존을 구분할 근거를 정리한다. 조사한 전체 사례는 설계 자료에 보관하고, 스킬에는 공통 판단과 판단 차이를 보여 주는 대조 사례만 남기는 구성을 제안한다.

## 각 스킬의 파일별 내용 제안

### 인수인계 스킬

`skills/use-better-handoff/SKILL.md`는 호출 대상, 파일 지정의 우선순위, 이동과 보존의 판단, 읽기와 갱신의 순서, 완료 조건을 관리한다. 기본 동작은 이 파일만으로 결정할 수 있게 한다. 작업별 위치나 이름을 `description`에 고정하지 않는다.

`skills/use-better-handoff/references/examples.md`는 문장이 같아도 보관 위치가 달라지는 대조 사례만 담는다. 시안의 검토자용 설명과 사용 방법 문서, 부가 주의 문구와 측정 조건을 비교한다. 본문의 규칙을 다시 설명하지 않고 구체적인 판정이 더 필요한 경우에만 읽는다. 별도 분류 절차 파일은 만들지 않는 안이다.

### 표현 스킬

`skills/use-better-terms/SKILL.md`는 언어 공통의 검사 절차를 관리한다. 공유 단위 선택, 근거 확인, 기존 검사기 사용, 경고별 대안 비교와 판정의 의미를 한곳에 둔다. 같은 행동을 시작 절, 검사 절과 반환 절에 각각 다시 쓰지 않는다.

`references/korean.md`는 번역체, 한국어 문장의 주어와 서술어, 조사, 태와 문장 간 연결처럼 한국어에서 구체화할 판단과 사례를 맡는다. 본문의 공통 판정 순서를 다시 나열하지 않는다. 한국어 작성 전과 판정 시 필요한 기존 읽기 조건은 유지한다.

`references/examples.md`는 언어 공통의 모호한 지칭, 역할과 승인 관계, 민감한 위치와 정확한 기호 등의 대조 문안을 맡는다. 한국어 자료와 같은 사례가 있으면 별도 언어 판단을 제공하는지 확인한 뒤 한쪽에 둔다. 입력, 대안과 판정 이유는 서로 다른 정보를 제공하므로 규칙의 반복과 구분한다.

`references/document-content.md`의 인수인계 관련 책임은 새 스킬에 이관한다. 기존 파일을 읽는 호출과 링크를 확인한 뒤 정리하며, 같은 기준을 두 스킬에서 각각 관리하지 않는다. 기존 검사 스크립트의 역할은 바꾸지 않는다.

두 스킬에 별도 규칙 사본, 요약 문서와 공통 필수 참고 파일을 추가하는 것은 기본안에 포함하지 않는다. 스킬 간 필수 참조가 늘어 어느 한쪽만 설치한 환경에서 사용할 수 없게 만들지 않는다.

## 의미 중복을 판정하는 방법

문장을 행동 주체, 적용 조건, 수행할 행동과 예외로 풀어 비교한다. 표현과 제목이 달라도 이 요소가 같으면 하나의 규칙으로 묶는다. 규칙을 관리할 위치를 정하고 다른 파일에서는 읽어야 할 조건과 연결만 남긴다.

같은 뜻을 다시 말하는 도입과 결론, 기본 절차를 반복하는 체크 목록, 본문의 판정 상태를 다시 정의하는 참고 자료가 우선 정리 대상이다. 반면 다른 입력에서 판단이 달라지는 사례, 필요한 조건과 실제 검사 명령은 남긴다. 같은 단어의 출현 횟수나 문장 유사도만으로 삭제하지 않는다.

구현 시에는 각 규칙의 기존 위치, 담당 파일, 읽는 조건과 이동 또는 축약 이유를 평가 자료에 연결한다. 이 작업표는 설계 자료이며 두 스킬이 실행 때마다 읽는 새 파일로 추가하지 않는다.

## 분량 감소와 실행 성능의 비교

[OpenAI의 스킬 평가 지침](https://developers.openai.com/blog/eval-skills)은 직접 호출, 자동 선택과 실행하지 않아야 하는 입력을 함께 확인하도록 설명한다. 짧은 원문은 “Negative control”이다. 2026-10-18 확인본은 실제 실행에서 읽은 자료와 수행한 행동을 확인할 근거를 제공하며, 파일이 짧다는 사실을 동작 정확성의 증거로 사용하지 않는다.

분리 전 통합 스킬은 기존 표현 검사의 보존을 확인하는 기준이다. 인수인계 파일 관리가 없는 기존 구성과 새 구성을 전체 비용만으로 비교하면 기능 차이가 섞인다. 분량 최적화는 같은 인수인계 기능을 가진 초안과 중복을 줄인 안을 같은 입력으로 비교해야 한다.

같은 모델과 설정, 초기 자료, 도구와 권한에서 과제 완수, 필요한 조건의 보존, 호출 누락과 불필요한 호출, 재작업을 관찰한다. 비용은 전체 마크다운 크기, 실제 읽은 파일과 본문 분량, 도구 출력, 제공되는 경우의 입력 및 출력 토큰을 구분한다. 서로 다른 동작을 수행한 실행이나 토큰을 확인할 수 없는 기록을 단순한 절감률로 합치지 않는다.

필요한 동작을 유지하는 안에서 읽을 내용과 재작업이 줄어드는지 확인한다. 빠진 조건 때문에 판정이 나빠지면 그 조건을 복원하고 다시 비교한다. 범용 최적 분량이나 성능 최대치를 제시하는 자료는 아니며, 목표는 대표 입력에서 확인한 비용과 수행 능력을 개선하는 것이다.

## 인수인계 기록의 중복과 사실 확인

[GitLab의 AI 문서 작성 지침](https://docs.gitlab.com/development/documentation/styleguide/#ai-generated-content)은 연결한 문서의 내용을 반복하는 문제와 코드 또는 기존 문서로 확인할 수 없는 기능 설명을 지적한다. 짧은 원문은 “Each section should add new information.”이다. 2026-10-18 확인본을 적용하면 인수인계 파일에는 관련 자료의 연결과 현재 작업을 이해하는 데 필요한 설명을 남기는 편이 적합하다.

현재 [설계 문서 규칙](../../README.md#rules-for-every-document)도 요구사항, 확인된 사실, 제안과 승인된 결정을 구분하고 해당 내용을 관리하는 문서에 연결하도록 한다. 따라서 인수인계 설명은 요구사항을 대신하거나 새 기능을 승인하는 근거가 되지 않는다.

이 근거에 따른 구성안은 같은 대상을 설명하는 기존 항목을 갱신해 현재 상태를 먼저 보여 주는 방식이다. 다른 작업의 기록을 지우거나 일률적인 형식을 강제할 필요는 없다. 승인된 설계 의도, 구현에서 확인한 사실과 아직 확인하지 못한 사항은 구분해 적는다.

## 참조 금지의 적용 대상

[참조 방향 요구사항](../requirements.md#참조-방향과-프로젝트-파악)은 일반 결과물이 인수인계 파일로 독자를 보내는 일을 금지한다. 새 스킬이 지정 파일을 읽는 동작이나 인수인계 파일이 다른 자료를 연결하는 동작을 금지하지 않는다.

이 규칙을 설명하는 스킬 본문, 호출 지침과 평가 자료에서 파일 이름을 사용하는 것과 실제 웹 페이지에 파일을 열라는 안내를 넣는 것은 다른 경우다. 실제 결과물의 본문, 링크, 코드 주석과 화면에 표시되는 문구를 문맥에 따라 확인해야 한다. 파일 이름을 문자열로 찾았다는 사실만으로 위반을 확정할 수 없다.

## 적용 과정에서 보존할 내용

문서 자체가 방법 안내나 지침이면 그 절차는 본래의 내용이다. 화면에서 필요한 오류 안내, API 사용 조건과 측정 결과를 해석하는 조건도 인수인계 정보로 오인해 없애면 안 된다. 현재 [사실과 조건 보존 기준](../../../../skills/use-better-handoff/SKILL.md#decide-what-belongs-where)을 이관할 때 이 차이를 유지해야 한다.

설명만 옮겨도 원래 주장의 뜻이 달라지거나 기능, 접근성 또는 문서 제출 요건에 영향을 주는 경우에는 관련 변경을 멈추고 필요한 판단을 확인한다. 독자가 알아야 할 사실을 인수인계 파일에만 숨기는 방식으로 적용하지 않는다.

이 조사는 지침과 공식 문서가 뒷받침하는 구성 근거다. 후속 [적용 관찰](./handoff-behavior-cases.md#실제-적용-관찰)은 별도로 기록한다. 그 사례의 성공을 일반적인 설명 누락률이나 호출 신뢰성의 입증으로 확대하지 않는다.
