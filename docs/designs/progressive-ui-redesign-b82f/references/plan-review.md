# UI 재설계안 검토와 적용 근거

첨부 재설계안은 작업과 정보 구조를 먼저 분석하는 방향으로 적용할 수 있다. 이름 변경을 제외하고, 생성 시안 점검과 기존 결정 보호, 작업 재개 및 실패 처리 절차를 보완해야 실행 가능하다. 이 문서는 스킬 문서를 수정할 때 적용 이유와 기존 동작을 확인할 근거다.

## 검토 대상과 근거의 범위

2026년 10월 7일에 첨부 재설계안과 저장소의 [현재 스킬](../../../../skills/use-progressive-user-interfaces/SKILL.md), 연결된 여섯 참고 문서와 기존 설계 기록을 확인했다. 아래 외부 자료도 같은 날짜에 확인했다. 문서에서 설명하는 규칙을 조사했으며, 출시 서비스의 실제 화면이나 재설계 후 시안 품질을 관찰한 결과는 아니다.

## 이름과 실행 지침의 표현

첨부안의 이름 변경 단계와 완료 조건은 이름 유지 조건과 충돌한다. 디렉터리와 frontmatter의 `name`은 유지하고 `description`과 실행 지침만 재작성한다. `user`를 단순 검색해 전부 삭제하면 정확한 이름까지 바뀌므로 실행 문장과 식별자를 구분해야 한다.

## 생성 시안과 실행 화면의 완료 구분

첨부안은 실행 화면 검증을 강화하지만, 문제가 발생한 생성 이미지의 제출 전 점검은 구체적이지 않다. 이미지 생성 입력에 작업, 현실적인 정보량, 내용, 화면 전체의 위계와 공통 규칙을 포함하고, 생성 후 실제 이미지를 다시 보며 확인해야 한다. 이는 문제에 대응하는 계획상 보완이며 특정 도구의 생성 품질을 보장하는 주장이 아니다.

[WCAG 2.2](https://www.w3.org/TR/WCAG22/)는 정보 관계, 대비, 리플로와 키보드 초점 등을 검사 가능한 조건으로 규정한다. [GOV.UK의 입력 오류 복구 패턴](https://design-system.service.gov.uk/patterns/validation/)은 오류를 설명하고 수정하도록 돕는 동작과 입력값 보존을 설명한다. 두 자료는 정지 이미지의 외형과 실제 동작 검증을 구분할 근거다. 단일 이미지로 키보드 조작이나 접근성 준수를 확인할 수 없다.

## 작업에서 구조를 도출하되 익숙한 동작 유지

[GOV.UK의 답변 확인 패턴](https://design-system.service.gov.uk/patterns/check-answers/)은 제출 전 확인과 수정을 지원하는 특정 작업을 중심으로 사용 조건과 동작을 설명한다. 이 사례는 작업에서 화면 구조를 선택하는 방법을 뒷받침하며 GOV.UK 외형을 복제할 이유가 되지는 않는다.

[Nielsen Norman Group의 사용성 휴리스틱](https://www.nngroup.com/articles/ten-usability-heuristics/)은 “Follow platform and industry conventions.”라고 설명하고 내부 일관성도 함께 다룬다. 두 자료를 비교하면 작업에 맞는 구조 선택과 익숙한 동작 유지가 함께 필요하다는 해석이 가능하다. 독창성을 낯선 상호작용의 수로 측정해서는 안 된다.

장식 제거 후에도 작업 구조가 남는다는 조건은 설명력을 점검하는 데 유용하지만, 독창성이나 사용성을 단독으로 증명하지는 않는다. 실제 시안과 핵심 작업을 수행하는 실행 화면 근거가 추가로 필요하다.

## 기존 결정과 잠정 기본안 구분

현재 [선택 절차](../../../../skills/use-progressive-user-interfaces/references/preferences.md)는 응답 대기, 취소, 짧은 답변 재개, 적용 범위와 기존 규칙 충돌을 별도로 처리한다. 첨부안의 근거 기반 판단과 잠정 기본안 처리는 이 동작을 대신하지 않는다. 기존 결정과 충돌하는 안은 결과 차이가 작아도 자동 적용하지 않고, 미응답은 승인으로 기록하지 않아야 한다.

[기존 운영 결정](../../progressive-ui-design-system-7c9e/decisions/workflow.md)은 비교 제시와 응답을 한 차례로 세고 저장 형식을 강제하지 않는다. [코드 수정 역할 결정](../../progressive-ui-design-system-7c9e/decisions/code-editing-and-visual-validation.md)은 애플리케이션 코드 수정과 디자인 검증을 구분한다. 새 플랜에서도 이 조건을 보존한다.

## 통합 문서와 조건부 진입

[OpenAI의 스킬 작성 안내](https://learn.chatgpt.com/docs/build-skills)는 이름과 설명을 먼저 읽고 필요할 때 전체 지침을 읽는 점진적 로딩을 설명한다. 네 참고 문서로 통합하는 것 자체가 비용 감소의 증거는 아니다. 통합 문서 내부도 목적별 절차로 구분하고 현재 작업에 필요한 문서만 읽도록 해야 한다.

새 설계는 작업 분석에서 시작하되, 이미 결정된 방향의 적용이나 실행 화면 검증 요청까지 새 조사부터 시작시키지 않는다. 현재 [스킬의 절차 선택](../../../../skills/use-progressive-user-interfaces/SKILL.md#select-the-procedures-needed-now)을 유지하는 보완이다.

## 기존 기록과 새 기준의 관계

[이전 요구사항](../../progressive-ui-design-system-7c9e/requirements.md)과 [조사 개선 요구사항](../../progressive-ui-research-6d2a/requirements.md)은 취향 비교와 사례별 특성을 다루는 당시 기준이다. 이번 [요구사항](../requirements.md)의 작업 중심 설계와 충돌하는 부분은 새 변경의 기준으로 사용하지 않는다. 기존 기록은 수정하거나 이름을 일괄 치환하지 않는다. 증거 구분, 재개, 적용 범위와 코드 수정 역할처럼 충돌하지 않는 보호 조건은 새 플랜에서 연결한다.

Apple의 레이아웃 문서는 본문을 확보하지 못했고 Carbon의 그리드 문서는 열기 오류로 확인하지 못했다. 두 자료의 내용은 판단 근거로 사용하지 않았다. 확인한 다섯 1차 자료도 실제 결과의 완성도 향상을 입증하지 않으므로 후속 실행 검증이 필요하다.
