# UI의 불필요한 설명과 지정된 조작의 대체 문제

중복 설명을 줄이고, 작성 및 구현 과정을 독자용 내용과 구분하며, 지정된 조작을 보존해야 한다. 문구 길이만 줄이거나 모든 안내를 없애는 기준으로는 [AI Caption과 텍스트로 조작을 대신하는 문제](../requirements.md#ai-caption과-텍스트로-조작을-대신하는-문제)를 해결할 수 없다.

이 자료는 후속 스킬 문서와 확인 절차를 작성할 때 사용할 조사 근거다. 2026년 11월 1일에 아래 원문과 공식 문서의 현재 게시 내용을 확인했다. `AI Caption`은 이 요구사항에서 정의한 문제 이름이며, 아래 자료가 같은 이름이나 동일한 분류를 사용한다는 뜻은 아니다.

HTML 시안의 제공과 위치를 지정한 요청의 반영은 [현재 요구사항](../requirements.md#html-시안에서-위치를-지정한-요청과-반영)을 따른다. 현재 방식은 시안 밖에서 요소를 선택하고 전체 XPath를 복사해 대화로 수정 요청을 전달하는 것이다. 시안 안에 검토 메뉴를 추가하거나 자동 수정 연결을 위한 서버를 구현하지 않는다. 아래의 HTML 형식 선택과 작성 허용 여부에 관한 제안은 현재 요구사항을 대신하지 않는다.

## AI가 생성한 UI의 과잉 설명 실험 보고

Yuta Okada의 [AI-generated UIs come with unnecessary explanatory text](https://note.com/dhythm/n/n75f78a70e9cc?hl=en)는 2026년 9월 5일에 게시된 직접 실험 보고다. 장비 예약 목록을 여러 AI 에이전트로 생성하고, 설명을 줄이는 지시의 유무에 따른 차이를 비교했다고 서술한다.

원문은 제목 아래에 그 화면에서 가능한 행동을 다시 설명하는 경우, 버튼 문구가 설명문처럼 길어지는 경우, 이용 가능 배지 옆에 같은 상태를 다시 적는 경우를 보고한다. 짧은 원문 예시는 “Available now”와 “Immediate use possible”이다. 중복 설명을 억제하는 지시로 일부 정리되었지만 모든 경우에 완전히 통제되지는 않았다고 보고한다.

이는 불필요한 설명과 상태 중복이 실제로 보고된 사례다. 다만 원문 보고를 확인한 것이며 화면 생성을 직접 재현하거나 화면을 직접 관찰한 것은 아니다. 이 사례만으로 모든 AI나 서비스에서 발생하는 빈도와 원인을 확정할 수 없다.

## 문구의 필요성과 의미를 판단하는 공식 지침

Microsoft의 현재 [Windows 앱 Writing style](https://learn.microsoft.com/en-us/windows/apps/design/style/writing-style)은 불필요한 도입 없이 주요 내용을 먼저 전달하고, 무슨 일이 일어났으며 다음에 무엇을 할 수 있는지 쉽게 이해하도록 쓰라고 안내한다. 짧은 기준은 “Don't pad your words with unnecessary introductions.”이다. 뜻을 알 수 없는 문장을 단순히 짧게 만드는 것보다, 대상과 행동을 명확히 하는 근거로 사용할 수 있다.

Microsoft의 [User Interface Text](https://learn.microsoft.com/en-us/windows/win32/uxguide/text-ui)는 제목과 컨트롤 사이의 중복을 없애고 자명한 내용을 다시 설명하지 않도록 안내한다. 단, Windows 7용으로 작성되어 최신 Windows에 맞춰 갱신되지 않았다는 주의가 있으므로 현재 화면 양식의 기준으로 사용하지 않는다. 중복 설명에 대한 원칙은 위의 현재 앱 문구 지침과 비교해 참고한다.

Wikimedia의 [Writing for machine-assisted experiences](https://doc.wikimedia.org/codex/latest/style-guide/machine-assistance.html)는 “Explain only what people need in order to decide or act.”라고 안내한다. 동시에 중요한 한계와 판단에 영향을 주는 불확실성은 설명하도록 한다. 따라서 일반적인 면책 문구를 임의로 추가하는 문제와 이용자의 판단에 필요한 한계 고지는 구분해야 한다.

GOV.UK의 [Warning text](https://design-system.service.gov.uk/components/warning-text/)는 행동하거나 행동하지 않을 때 발생할 중요한 불이익 등을 경고하는 용도로 설명한다. 현재 미구현 사항을 나열하거나 일반적인 실패 가능성을 늘어놓는 것과는 목적이 다르다. 다만 미구현 상태가 실제 이용에 주는 영향을 숨겨도 된다는 뜻은 아니다.

## 상태 안내는 장황한 설명과 구분

W3C의 [WCAG 2.2 상태 메시지 해설](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)은 성공, 대기, 진행과 오류에 관한 상태 변경을 보조 기술이 전달할 수 있도록 하는 기준을 설명한다. 예시에는 “Searching...”와 “No results returned”가 있다. 이 문서는 성공 기준을 설명하는 자료이며 그 자체가 별도 의무를 추가하는 표준은 아니다.

따라서 답변 수신이 아직 끝나지 않았다는 설명을 발견해도 상태 안내 전체를 삭제하는 것으로 처리해서는 안 된다. 실제 대기, 생성, 수신 또는 실패 중 어느 상태인지 확인하고, 필요한 상태를 짧고 정확하게 전달하는지 판단해야 한다. 원래 문장의 길이나 AI가 작성했다는 사실만으로 필요 여부가 결정되지는 않는다.

## 드래그 조작과 대체 조작의 관계

W3C의 [WCAG 2.2 드래그 동작 해설](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)은 예외 조건을 제외하고 드래그 기능을 드래그 없이도 단일 포인터로 수행할 수 있어야 한다는 기준을 설명한다. 목록 항목을 선택한 후 위아래로 옮기는 컨트롤과, 보드 항목을 다른 열로 옮기는 메뉴를 예로 든다. 키보드 조작 가능 여부와 단일 포인터 대체 조작은 별도로 판단한다.

이 기준은 드래그를 유지하면서 대체 조작도 설계할 근거다. 명시적으로 요구한 드래그를 삭제하고 이동 버튼만 남겨도 요구사항을 충족한다는 근거는 아니다. 이 결론은 W3C 기준과 현재 요구사항을 함께 적용한 해석이다. 대체 조작을 상시 텍스트 버튼으로 반복 배치해야 한다고 정하지도 않는다.

## 적용 판단과 남은 한계

자료를 비교하면 문구의 필요성, 의미의 명확성, 실제 상태 및 조작과의 일치를 따로 판단해야 한다. 설명문으로 사용하기 어려운 UI를 보완하거나, 구현하지 않은 동작을 경고문으로 대신하는 방식은 각각 문구와 실제 동작을 확인해야 발견할 수 있다.

작성 및 구현 과정과 결정 설명이 화면이나 보고서에 섞이는 문제는 현재 요구사항에 포함되지만, 위 실험이 그 모든 유형을 관찰했다는 증거는 없다. 보고서의 불필요한 작성 과정과 주장에 필요한 조사 방법 및 측정 조건도 구분해야 한다. 이번 조사는 실제 사례 보고와 적용할 판단 기준을 확보한 것이며, 현재 스킬을 수정했거나 문제가 개선되었다는 실행 증거는 아니다.

## 해결 방안의 추가 조사

표시할 내용을 먼저 선별하고, 설명의 위치와 시점을 정하며, 지정된 조작을 실제로 확인하는 절차를 권고한다. 금지 문구 목록이나 문장 길이 제한만 추가하면 작성 과정이 섞이는 문제, 의미를 알 수 없는 짧은 문구와 요구한 조작의 누락을 함께 해결하기 어렵다.

아래는 2026년 11월 1일에 확인한 추가 자료와 현재 스킬을 비교한 제안이다. 승인된 새 요구사항이나 적용을 마친 실행 계획은 아니다.

### 생성 전에 독자에게 필요한 내용과 작성용 정보를 구분

[GOV.UK의 사용자 필요 확인 지침](https://guidance.publishing.service.gov.uk/writing-to-gov-uk-standards/plan-manage-content/identify-user-needs/)은 누가 무엇을 하려는지와 콘텐츠가 충족할 필요를 근거로 파악하고, 충족 여부를 판단할 조건도 기록하도록 안내한다. 이 기준을 적용하면 설명문을 넣을 때에도 누가 어떤 판단이나 행동에 사용하는지부터 확인할 수 있다.

현재 [시안 생성 절차](../../../../skills/use-progressive-user-interfaces/references/implementation.md#generate-and-inspect-a-mockup)는 목적, 시나리오, 콘텐츠, 상태, 제약과 미결정 사항을 생성 입력에 포함한다. 그러나 그중 무엇을 화면에 표시하고 무엇을 작성에만 참고할지 구분하는 지시는 없다. 이 구분의 부재가 실제 혼입을 일으켰는지는 실행 비교가 필요하다.

생성 입력에서 화면에 표시할 도메인 정보와 문구를 설계 의도, 결정 이유, 구현 메모와 구분하는 방식을 제안한다. 후자는 화면 문구로 전환하지 않도록 명시하고, 필요한 설명은 스킬 사용자에게 전달한다. 보고서도 독자의 판단에 필요한 본문과 작성자의 진행 보고를 구분한다. 보고서 자체가 방법이나 결정을 설명하는 문서이면 방법과 결정에 관한 설명은 본문에 남긴다.

화면이나 보고서의 모든 단어를 사전에 승인받도록 만들 필요는 없다. 레이블과 실제 콘텐츠는 작성하면서 구체화하되, 설명과 경고를 덧붙일 때에는 독자가 알아야 할 사실과 그 근거를 확인하는 방식이다. 작성 메모를 별도 파일로 저장하는 경우에는 저장소의 인수인계 지침을 따르며, 매번 새 문서나 고정 양식을 만들자는 제안은 아니다.

### 보조 설명은 필요성이 확인될 때 추가

[GOV.UK Task list](https://design-system.service.gov.uk/components/task-list/)는 사용자가 추가 정보를 필요로 한다는 증거가 있을 때에만 힌트를 사용하도록 한다. 짧은 원문 기준은 “Only use hint text if there is evidence”다. 이 기준을 모든 설명에 동일한 형식이나 글자 수를 강제하는 규칙으로 확대하지 않는다.

이 스킬에는 제목 아래 설명과 항목별 보조 문구를 관행적으로 생성하지 않고, 부족한 정보가 확인되면 추가하는 방식을 제안한다. 문구마다 무엇을 입력해야 하는지, 현재 어떤 상태인지, 다음에 무엇을 해야 하는지 또는 행동의 영향을 알아야 하는지로 필요성을 설명할 수 있어야 한다. 화면의 제목이나 조작 자체가 이미 같은 뜻을 전달한다면 반복 설명을 추가하지 않는다.

예를 들어 실제로 답변을 생성 중이며 진행 상태 안내가 필요한 경우에는 `답변 생성 중`처럼 현재 상태를 전달할 수 있다. 단순 대기나 전송 중인 상태를 생성 중이라고 바꾸지는 않는다. 입력 조건과 무관한 일반적인 성공 면책은 생략하고, 입력 형식에 제약이 있으면 그 조건을 직접 안내한다. 뜻을 알 수 없는 도메인 문구는 자연스러워 보이는 주장으로 다시 쓰기 전에 필요한 의미를 확인한다.

### 필요한 도움말의 위치와 표시 시점 결정

[GOV.UK Text input의 Hint text](https://design-system.service.gov.uk/components/text-input/#hint-text)는 대부분의 사용자에게 필요한 도움을 짧게 제공하도록 한다. [Details](https://design-system.service.gov.uk/components/details/)는 일부 사용자만 필요한 정보를 펼쳐 보게 할 수 있지만 대부분이 필요한 정보는 숨기지 말라고 안내한다. 두 지침을 함께 적용하면 설명을 무조건 없애거나 모두 접는 방식도 피할 수 있다.

따라서 입력 전에 알아야 하는 조건은 입력 가까이에 유지하고, 일부 사용자만 필요한 추가 설명은 요청할 때 볼 수 있도록 한다. 오류 안내는 오류가 발생한 시점과 대상에 연결한다. [GOV.UK Error message](https://design-system.service.gov.uk/components/error-message/)는 발생한 문제와 고치는 방법을 명확히 전달하도록 하며, [Atlassian의 오류 문구 지침](https://atlassian.design/foundations/content/designing-messages/error-messages)도 제목을 반복하지 않고 다음 행동을 안내하도록 한다. 일반적인 실패 가능성을 모든 입력 아래에 경고하는 것과 구분할 근거다.

설명 자체가 불필요하면 도움말이나 툴팁으로 옮겨 보존하지 않는다. 필요한 내용인지 먼저 판단한 뒤 표시 위치와 시점을 정한다. 화면을 줄이기 위해 필수 레이블과 접근성 정보를 제거하는 방식도 채택하지 않는다.

### 조작이 중요한 시안은 실행 화면으로 확인

[GOV.UK Making prototypes](https://www.gov.uk/service-manual/design/making-prototypes)는 목적에 맞는 시안 형식을 선택하며, 코드 시안은 실제와 유사한 상호작용을 확인하는 데 적합하다고 설명한다. 현재 스킬의 시안 생성은 이미지를 중심으로 하지만, 드래그 성공과 순서 반영은 정지 이미지로 확인할 수 없다.

따라서 문구, 배치와 외형만 비교할 때에는 이미지를 사용할 수 있고, 드래그, 입력, 오류 및 상태 전환이 판단 대상일 때에는 실행 가능한 HTML 시안을 우선 고려하는 방식을 권고한다. 이 선택은 이미지 생성을 없애거나 모든 시안을 코드로 작성하자는 결정이 아니다. HTML 작성 허용 여부와 기존 애플리케이션 수정 권한도 별도로 유지한다.

드래그 사례에서는 항목을 잡아 다른 위치에 놓고, 바뀐 순서가 반영되는지를 완료 근거로 삼는다. 접근성을 위한 대체 조작이 있어도 요구한 드래그를 대신한 것으로 처리하지 않는다. 상시 표시할 이동 버튼의 수를 늘리는 방식만 고려하지 말고, 선택한 항목의 메뉴 등 현재 화면 구성에 맞는 대안을 함께 판단한다. 근거는 앞의 [드래그 조작과 대체 조작의 관계](#드래그-조작과-대체-조작의-관계)다.

### 설명의 설득력과 실제 충족 여부를 별도로 판단

[Design Theater 연구 v2](https://arxiv.org/html/2607.22928v2)는 2026년 7월에 다섯 생성 도구로 만든 120개 UI에서 설계 설명과 실제 구현의 불일치를 조사했다. 설명과 화면의 일치 여부, 입력에 담긴 UX 원칙 충족 여부를 별도로 평가한다. HTML, CSS와 JavaScript만 사용하고 외부 라이브러리와 검색을 제외한 조건이므로 현재 스킬과 같은 환경의 실험은 아니다.

이 연구는 그럴듯한 설계 설명을 완료 근거로 대신하지 말아야 할 이유를 제공한다. UI 안에 설명이 섞이는 문제의 직접 원인이나 특정 해결 절차의 효과를 입증하지는 않는다. 현재 스킬에도 실제 상태와 조작을 확인하는 규칙은 있으므로 새 검토 단계를 계속 추가하기보다 기존 마지막 확인에서 문구 필요성과 지정된 조작의 보존을 구체적으로 판단하는 방식을 권고한다.

스킬 사용자에게도 모든 문장을 다시 확인해 달라고 요구하지 않는다. 근거가 있는 중복 설명은 직접 줄이고, 서비스 의미나 선택이 달라지는 부분만 확인한다. 마지막에는 실제 화면이나 보고서를 보고 불필요한 작성 설명, 의미를 확인할 수 없는 문구, 빠진 필수 안내와 누락된 조작을 함께 살핀다.

### 지시문과 자체 검토만으로 해결되는지는 별도 확인

앞의 직접 실험 보고에서는 짧은 지시로 설명을 일부 줄였지만 완전히 통제하지는 못했다고 한다. [Self-Refine](https://arxiv.org/abs/2303.17651)은 자체 피드백을 통한 개선을 보고한 반면, [Large Language Models Cannot Self-Correct Reasoning Yet](https://arxiv.org/abs/2310.01798)는 외부 피드백 없는 추론 수정이 실패하거나 악화될 수 있음을 보고한다. 과제와 평가 조건이 다르므로 두 연구를 동일한 조건을 비교한 실험으로 취급하지 않는다. 당시 모델의 개선 및 악화 정도를 현재 UI 문구의 개선률로 옮길 수도 없다.

따라서 단순히 다시 검토하라는 지시, 검토 횟수 증가나 에이전트 추가만으로 해결된다고 가정하지 않는다. 실제 입력 조건, 실행 중인 화면과 지정된 조작 뒤의 변화를 판단 근거로 제공하는 쪽을 우선 제안한다. 디자인 담당 에이전트의 사용 조건은 기존 요구사항을 유지하며 기본 해결책으로 자동 생성하지 않는다.

효과를 확인할 때에는 같은 시나리오를 변경 전후에 적용하고, 불필요한 설명과 의미 불명확 문구가 남는지, 필수 안내를 잃었는지와 지정된 조작을 충족하는지를 각각 비교하는 방식을 제안한다. 문장 수가 줄었다는 사실만으로 성공을 판단하지 않는다. 생성한 내용이 달라질 수 있으므로 한 번의 성공으로 안정적인 개선을 주장하지 않는다. 이 비교는 후속 스킬 변경 이후에 필요하며 현재는 실행하지 않았다.

## 현재 스킬에 적용할 때의 우선순위 제안

먼저 시안 생성 입력에서 표시할 내용과 작성용 정보를 구분하고, 불필요한 보조 설명을 기본으로 채우지 않는 기준을 추가하는 편이 현재 문제에 직접적이다. 다음으로 실제 조작을 판단할 시안 형식을 선택하고, 기존 마지막 확인에 문구 필요성 및 요구한 조작의 충족 여부를 연결하는 방식을 권고한다.

규칙은 [진입 문서](../../../../skills/use-progressive-user-interfaces/SKILL.md)에 목적과 필수 구분만 두고, 세부 판단은 [시안과 구현 입력](../../../../skills/use-progressive-user-interfaces/references/implementation.md), 마지막 확인은 [실행 UI 확인](../../../../skills/use-progressive-user-interfaces/references/validation.md)에 배치할 수 있다. 보고서 작성 전체를 UI 스킬이 맡거나, 문구 검사 프로그램과 추가 에이전트를 기본 의존성으로 만드는 제안은 아니다.

독자에게 필요한 내용과 작성용 정보의 구분은 현재 요구사항과 연결되는 제안이다. 생성 입력의 분리, 보조 설명을 추가하는 기본 조건과 HTML 시안의 우선 적용이 이 저장소에서 얼마나 개선하는지는 아직 검증하지 않은 가설이다. 다음 스킬 변경에서 채택할 방식과 확인할 시나리오는 결정이 필요하다.

## 서버 없이 구현하는 방식의 착수 가능성

현재 요구사항에 따른 저장소 스킬 개편은 착수할 수 있다. [현재 스킬](../../../../skills/use-progressive-user-interfaces/SKILL.md)은 진입 문서와 참고 문서 네 개로 구성되어 있다. 테마 비교와 HTML 작성, XPath를 전달받아 수정하는 절차를 이 문서들에 반영할 수 있으며, 피드백 서버나 브라우저 확장 프로그램을 새로 만들 필요는 없다. 시안 코드와 실제 서비스의 애플리케이션 코드를 구분하도록 현재의 코드 수정 제한도 고쳐야 한다.

2026년 11월 1일에 브라우저로 Chrome의 공식 검사 모드 안내를 열고 실제 화면을 확인했다. 이전의 브라우저 관찰 실패와 달리 이번 확인에서는 페이지 열기와 화면 캡처가 가능했다. 다만 로컬 HTML 열기, 개발자 도구의 복사 메뉴 조작과 수정 후 새로고침까지 이어지는 전체 동작은 확인하지 않았다. 현재 관찰 기능의 사용 가능 여부와 전체 사용 절차의 완료는 구분한다.

[Chrome 검사 모드 안내](https://developer.chrome.com/docs/devtools/inspect-mode)는 페이지에서 선택한 요소를 Elements 패널에서 확인하는 방법을 설명한다. 공식 저장소의 [DOMTreeContextMenu.ts](https://github.com/ChromeDevTools/devtools-frontend/blob/82e99f9678c78a51c8f0961a0d001445144f604b/front_end/panels/elements/DOMTreeContextMenu.ts#L383)에는 “Copy full XPath” 항목이 구현되어 있다. 외부 도구가 복사를 맡게 하면 검토 메뉴를 HTML에 추가하지 않아도 된다. 이 소스의 기능 존재를 확인했으며, 모든 브라우저와 내장 미리보기가 같은 메뉴를 제공한다고 판단하지는 않는다.

같은 리비전의 [DOMPath.ts](https://github.com/ChromeDevTools/devtools-frontend/blob/82e99f9678c78a51c8f0961a0d001445144f604b/front_end/panels/elements/DOMPath.ts#L189)는 상위 노드와 형제 순서를 사용해 XPath를 만든다. 따라서 전체 XPath를 영구 식별자로 취급하지 않는다. [Document.evaluate 안내](https://developer.mozilla.org/en-US/docs/Web/API/Document/evaluate)는 현재 DOM에서 XPath로 요소를 찾을 수 있음을 설명한다. AI는 현재 렌더링된 요소를 확인하고 그 요소와 HTML 소스의 관계를 대조해야 하며, XPath를 소스 파일의 줄 번호로 간주해서는 안 된다.

[동일 출처 정책 안내](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy)는 로컬 파일의 출처 처리에 브라우저별 차이가 있고 로컬 파일이 불러오는 다른 파일에 대한 접근이 제한될 수 있음을 설명한다. 서버 없이 여는 최초 시안에는 HTML 내부의 CSS와 JavaScript를 사용하는 구성을 계획할 수 있다. 별도 파일을 읽는 요청이나 운영 API가 필요한 경우에는 요구한 동작을 제거하거나 새 서버를 추가하지 않고 그 동작에 영향을 주는 조건을 확인해야 한다.

현재 저장소에는 구현된 HTML 시안이 없고, `skills/ui/`도 없다. 설치된 기존 스킬은 저장소 사본과 별개이며 새 `ui` 사본은 확인되지 않았다. 저장소의 개편 완료와 설치된 스킬의 실제 사용 확인은 별도다. 이번 개편에서는 설치 위치를 자동으로 바꾸지 않으며, 실제 사용 확인에는 새 스킬을 실행 환경에서 읽을 수 있게 하는 절차가 필요하다.

기술 수단이 없어 문서 수정을 보류해야 하는 조건은 발견하지 않았다. 다만 원하는 시각적 인상과 불필요한 설명의 제거는 실제 시안과 피드백으로 확인해야 한다. 문서에 규칙을 추가했다는 사실만으로 문제가 해결되었다고 판단하지 않으며, 대상이 바뀐 XPath, 재개 입력, 필요한 안내의 보존과 드래그 조작을 포함해 확인할 필요가 있다.
