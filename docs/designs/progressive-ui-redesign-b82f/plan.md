# ui 스킬 구현 계획

현재 요구사항에 따른 저장소 스킬 개편은 지금 착수할 수 있다. 기존 문서 다섯 개를 `skills/ui/`로 옮겨 역할별로 보완하고, 요소 선택과 복사는 브라우저 개발자 도구에 맡긴다. 피드백 서버, 자동 수정 연결 프로그램과 시안 내부의 검토 도구는 만들지 않는다. 실제 사용 품질과 전체 피드백 절차는 구현 후 확인하며, 문서 수정 가능성을 실행 완료로 판단하지 않는다.

이 계획은 스킬 문서를 변경하고 확인할 때 사용할 실행 기준이다. 기준 문서는 [현재 요구사항](requirements.md) 전체와 [개발 지침](../../dev/README.md)다. 구현 가능성의 근거와 미확인 조건은 [착수 가능성 조사](references/ui-copy-and-interaction.md#서버-없이-구현하는-방식의-착수-가능성)에 연결한다. 현재 요구사항은 이 계획 작성에서 변경하지 않는다.

## 착수 판단과 적용 대상

스킬 이름과 디렉터리 변경, 사용자와 대화하는 설계, 테마 검색과 비교, HTML 시안의 생성 및 수정, 문구 선별과 외부 XPath 피드백 절차는 구현할 수 있다. 문서 개편을 시작하기 위해 추가로 정해야 할 기술 선택은 없다. 대상별 실제 테마와 서비스 콘텐츠는 스킬을 사용하는 프로젝트에서 확인할 내용이며 스킬 자체에 고정하지 않는다.

브라우저 페이지 열기와 화면 캡처는 현재 사용 가능함을 확인했다. 로컬 HTML 열기와 개발자 도구에서의 XPath 복사까지 확인한 것은 아니다. 구현 후 실행할 브라우저가 전체 XPath 복사를 제공하고 로컬 시안을 열 수 있는지 확인한다. 내장 미리보기에 개발자 도구가 없으면 외부 브라우저에서 연다. 시안에 복사 메뉴를 넣어 이 차이를 보완하지 않는다.

저장소 사본과 설치된 스킬 사본은 별개다. 이 계획의 구현 대상은 저장소 사본이며 설치된 사본의 덮어쓰기나 제거를 포함하지 않는다. 실제 실행에서는 새 `SKILL.md`를 명시적으로 읽어 진행하는 방법과 설치된 스킬을 이름으로 선택하는 방법을 구분한다. 전자는 설치 사본 변경 없이 문서의 실행 절차를 확인할 수 있지만 자동 선택 동작까지 확인하는 것은 아니다. 실제 실행을 하지 못하면 저장소 문서 완료와 실행 미확인을 나누어 보고한다.

[개발 지침](../../dev/README.md)은 변경과 확인 방법을 선택하는 기준으로 적용한다. 실행 로직, 의존성, 검사 설정과 Node.js CLI는 바꾸지 않으므로 MJS 스캐너 구현 지침은 이번 스킬 개편의 대상이 아니다. 새 코드나 테스트를 작성하거나 검사 도구를 추가하지 않는다.

## 변경할 파일과 유지할 내용

현재 `skills/use-progressive-user-interfaces/`의 `SKILL.md`와 참고 문서 네 개를 `skills/ui/`의 같은 상대 위치로 옮긴다. 진입 문서에는 필수 구분과 절차 선택만 남기고, 세부 절차는 현재의 조사, 결정, 시안 및 구현 입력, 검증 문서에 배치한다. 고정 UI 템플릿과 범용 복사 스크립트는 추가하지 않는다.

- `SKILL.md`: `name: ui`, 설명과 제목, 사용자 대화, 테마 비교 우선 순서, 시안용 HTML 작성 허용과 기존 애플리케이션 수정 제외, 명시적 요청에 따른 디자인 담당 에이전트 생성.
- `references/research.md`: 서비스 UI와 디자인 테마 검색, 시각 자료 및 출처 비교, 명시적 요구가 없는 SaaS 디자인 제외, 선택 이유와 미확인 근거 구분.
- `references/decisions.md`: 테마 비교 질문과 응답, 확인한 특성에 한정한 선택 반영, 짧은 답변 및 기존 단계 재개, 외부에서 전달한 XPath와 요청 해석.
- `references/implementation.md`: 실제 서비스처럼 보이는 HTML 시안 작성, 표시할 내용과 작성용 정보 구분, 지정된 조작 보존, XPath의 현재 대상 확인과 시안 수정.
- `references/validation.md`: 문구의 필요성, 시안 내부 검토 도구의 부재, 실제 조작, 테마 반영과 XPath 피드백 반영을 기존 마지막 확인에 연결.
- `README.md`와 `README.ko.md`: 새 `ui` 이름, 역할과 사용 안내를 추가한다. 기존 스킬의 설명과 설치 절차는 유지한다.

이전 설계 문서에서 현재 존재하는 스킬 파일로 연결한 링크는 옮긴 위치에 맞게 수정한다. 과거 스킬 이름과 당시 결정, 완료 기록은 일괄 치환하지 않는다. 이미 존재하지 않는 과거 파일의 링크는 이번 이름 변경으로 발생한 문제와 구분하고 별도로 보고한다. `src/AGENTS.en.md`와 `src/AGENTS.ko.md`에는 기존 UI 스킬 호출 절이 없으므로 새 프로젝트 공통 규칙을 추가하지 않는다.

확정된 선택과 잠정안, 직접 관찰과 해석, 응답 대기와 취소, 기본 최대 3회 비교와 승인된 연장, 특정 대상에 한정한 검증과 공통 규칙 확정의 구분을 유지한다. 스킬 문서는 기존 영어를 유지하고 프로젝트별 선택을 스킬 자체에 저장하지 않는다.

## 구현 순서와 완료 근거

### 1. 이름과 진입 안내 변경

다섯 파일을 옮기고 진입 문서의 이름, 설명, 제목과 절차 연결을 수정한다. 새 UI 방향은 이용 목적과 시나리오 확인, 테마 검색과 비교, 사용자 피드백, HTML 시안 순서로 진행한다. 이미 제시한 테마의 응답이나 기존 시안 수정은 응답 또는 수정이 대기 중인 단계에서 재개한다.

디자인 담당 에이전트는 명시적으로 요청했을 때에만 생성하고 수가 없으면 1개로 정한다. 실행 환경에서 에이전트를 생성할 수 없으면 실행하지 못한 사실을 알리며 생성했다고 보고하지 않는다. HTML 시안 작성과 기존 애플리케이션 코드 수정을 구분하는 새 조건을 공통 규칙에 반영한다.

완료 근거는 디렉터리와 frontmatter 이름의 일치, 필요한 참고 문서의 연결, 이전 이름으로 남은 현재 호출 안내의 부재다. 기존 설계 기록의 옛 이름은 변경 누락으로 판정하지 않는다.

### 2. 테마 검색과 비교 및 대화 절차 보완

`research.md`에서 테마를 색상만의 차이가 아닌 타이포그래피, 이미지 사용, 정보량과 화면 구성의 차이로 비교하도록 한다. 실제 화면이나 디자인 자료를 열어 확인하고 출처를 제시한다. 서비스가 업무용이라는 이유로 SaaS 디자인을 포함하지 않는다. 테마 선택으로 서비스 전체 복제나 속성 조합을 정당화하지 않는다.

`decisions.md`에서는 비교한 대상, 질문, 확인한 선호와 비선호를 이어받아 필요한 특성만 시안에 반영하도록 한다. 전문 수치 선택은 대신 판단하고 사용자에게는 결과가 달라지는 방향을 묻는다. 기본 3회는 비교 상한이다. 재개나 확정 방향 적용에 허용되는 0회 처리가 신규 테마 비교 자체를 생략하는 근거가 되지 않게 한다.

완료 근거는 테마 자료가 최초 시안보다 먼저 제시되고, 사용자 피드백과 시안 방향이 연결되는 진행이다. 응답이 없으면 선택을 확정하지 않고 같은 비교에서 기다려야 한다. 자료 접근 실패는 시각 관찰을 마친 것으로 처리하지 않는다.

### 3. 서비스 화면으로 사용할 HTML 작성 절차 보완

`implementation.md`의 이미지 중심 시안 절을 HTML 생성 및 수정까지 포함하도록 재작성한다. 서버가 필요 없는 시안은 HTML 안에 CSS와 JavaScript를 포함하는 방식으로 계획한다. 현재 시나리오에 필요한 시각 규칙과 현실적인 콘텐츠를 사용하며, 지정된 드래그나 입력 등의 조작을 구현 대상으로 명시한다. 모든 요소를 텍스트 버튼으로 대신하지 않는다.

화면에 표시할 정보와 설계 의도, 작성 및 구현 과정, 결정 설명을 생성 입력부터 구분한다. 시안 소개, 검토 메뉴, XPath 복사 도구와 수정 요청 패널은 숨긴 형태로도 넣지 않는다. 서비스 이용에 필요한 레이블, 상태와 오류 해결 안내는 유지한다. 일반적인 면책과 미구현 경고를 추가해 빠진 기능을 대신하지 않는다. 운영 시스템과 연결하지 않은 시안의 한계는 대화에서 설명한다.

완료 근거는 실제 요구한 서비스로 읽히는 화면과 필요한 조작이다. HTML 문법이나 파일 존재만으로 완료하지 않는다. 이미지 생성은 테마나 외형 비교에 활용할 수 있으나 HTML과 실제 조작 확인을 대체하지 않는다.

### 4. 시안 밖에서 XPath를 복사해 수정하는 절차 연결

`decisions.md`와 `implementation.md`에 요소 선택과 전체 XPath 복사, 대화에서 요청, AI 수정, 다시 열기 또는 새로고침으로 확인하는 순서를 연결한다. 요소 선택과 복사는 브라우저 개발자 도구에서 수행한다. 사용법은 대화나 스킬 문서에 설명하고 시안 본문에 삽입하지 않는다.

전달받은 XPath를 현재 렌더링된 DOM에서 확인하고, 요소의 내용과 소스 파일을 대조해 수정한다. XPath를 소스 줄 번호로 취급하거나 목록 순서가 바뀐 뒤에도 같은 대상을 가리킨다고 가정하지 않는다. 찾을 수 없거나 다른 요소와 충돌하면 현재 대상에 필요한 정보만 확인하며 비슷한 요소를 임의로 수정하지 않는다. iframe, Shadow DOM과 동적으로 생성한 요소는 문서 및 상태를 먼저 확인하고 전체 XPath 하나로 항상 찾을 수 있다고 보장하지 않는다.

완료 근거는 전달한 대상에 변경이 반영되고 유지해야 할 다른 동작이 보존되는 것이다. 오래된 XPath와 대상 불일치에서는 잘못된 수정을 멈추고 다음 확인을 요청해야 한다. 대화에서 수정 반영 여부를 전달하고 화면 안에는 처리 상태를 추가하지 않는다.

### 5. 안내와 링크 정리

두 README에 새 스킬의 목적, 테마 비교와 서비스형 HTML 시안, 시안 밖에서의 XPath 피드백을 설명한다. 저장소 사본이 자동으로 설치되는 것으로 안내하지 않는다. 기존 유효 링크의 연결 위치만 새 디렉터리에 맞추며, 현재 설계 묶음의 링크와 후속 실행 순서도 연결한다.

완료 근거는 두 언어 안내에서 같은 역할과 제외 대상을 설명하고 새 스킬로 연결되는 것이다. 이전 설계 문서의 본문과 완료 이력은 보존되어야 한다.

### 6. 마지막 확인에서 문서와 실제 실행 구분

문서 개편이 끝나면 한 번의 최종 확인에서 이름, frontmatter, 절 연결과 상대 링크, 요구사항별 지침 위치, 표현과 민감정보를 확인한다. 사용 가능한 기존 스킬 형식 검사기를 우선 사용하고 의존성 부재로 실행할 수 없으면 그 사실과 대체 형식 확인 방법을 보고한다. 새 의존성이나 검사 프로그램을 추가하지 않는다. 수정이 필요하면 영향을 받은 항목만 다시 확인한다.

실제 사용 확인은 새 스킬을 실행 환경이 읽는 상태에서 진행한다. 다음 상황을 통해 문서 절차와 실행 증거를 구분한다.

- 신규 UI에서 테마를 검색하고 비교 자료를 제시한 뒤 피드백을 시안에 반영한다. SaaS 요구가 없는 경우와 명시한 경우의 후보 선택을 구분한다.
- HTML이 서비스 콘텐츠와 조작을 표현하고, 설명용 화면이나 내부 검토 메뉴로 바뀌지 않았는지 확인한다. 일반 면책과 중복 설명은 제거하면서 필요한 입력 조건과 상태 안내는 유지해야 한다.
- 드래그로 순서를 바꾸고 그 순서가 반영되는 모습을 확인한다. 대체 조작을 제공해도 요구한 드래그가 남아 있어야 한다.
- 개발자 도구에서 전체 XPath를 복사해 대화로 요청하고, 수정된 파일을 새로고침해 대상과 다른 조작을 확인한다. 대상 불일치와 뜻이 불명확한 요청도 구분한다.
- 짧은 응답과 취소, 기존 선택과의 충돌 및 이전 자료가 없는 재개에서 기존 보호 동작을 유지한다. 필요한 시점의 명시적 요청에 따라 디자인 담당 에이전트를 생성하고, 요청이 없을 때에는 생성하지 않는다.

실제 서비스 시나리오나 시안이 아직 없으면 위 실행은 후속 사용 확인으로 남긴다. 검증을 위해 별도의 애플리케이션, 테스트 코드나 평가 프로그램을 만들지 않는다. `pass`, `needs revision`, `needs human input`, `not applicable`로 확인 대상을 구분하고, 실행하지 않은 항목에는 문서 검사 결과를 대신 사용하지 않는다.

## 실행 순서의 의존 관계와 중단 조건

이름과 진입 안내를 먼저 정리하고 조사 및 결정 절차, HTML 작성과 XPath 수정 절차를 보완한 뒤 안내 및 링크를 정리한다. 새 이름과 지침이 연결된 다음 마지막 확인을 진행한다. 구현을 시작하기 전에는 현재 요구사항과 개발 지침을 기준으로 검토한 이 계획을 같은 공유 단위로 커밋해 기준을 남긴다.

문서 개편을 막는 미결정 사항은 없다. 후속 실행에서 필요한 브라우저 기능이나 실제 시나리오가 없으면 영향을 받는 실행 확인만 미완료로 남긴다. 운영 API나 서버가 있어야 하는 새로운 동작, 기존 애플리케이션 변경 또는 요구사항과 다른 기능 대체가 필요해지면 해당 변경을 멈추고 먼저 요구사항을 확인한다. 설치된 스킬 사본은 별도 변경 권한 없이 덮어쓰지 않는다.

현재 계획의 실행 단계는 모두 미착수다. 아래의 과거 완료 기록은 새 이름, 테마 우선 비교와 외부 XPath 피드백을 구현했다는 근거가 아니다.

## 추가 전 계획과 실행 기록

이용 목적, 사용 시나리오와 정보 구조에서 UI 방향을 도출하도록 스킬 문서를 재작성한다. 이름은 `use-progressive-user-interfaces`로 유지하고 참고 문서는 조사, 결정, 구현 입력과 검증의 네 책임으로 통합한다. 생성 시안의 완성도와 실행 UI의 동작은 별도 근거로 확인한다.

스킬 문서를 수정하고 검토할 때 사용할 실행 플랜이다. 기준은 [요구사항의 해결할 문제와 결과, 유지할 조건, 완료를 판단할 근거](requirements.md)다. 적용 이유와 첨부안의 보완점은 [재설계안 검토](references/plan-review.md)에 정리한다. 현재 진행 상태와 남은 항목은 아래 실행 기록에서 확인한다.

## 적용 범위와 보호 조건

변경 대상은 `skills/use-progressive-user-interfaces/SKILL.md`와 그 아래 참고 문서다. 디렉터리와 frontmatter 이름은 바꾸지 않는다. `research.md`와 `decisions.md`를 추가하고 `implementation.md`와 `validation.md`를 재작성한 뒤, 이전 네 참고 문서는 필요한 규칙을 옮긴 다음 제거한다.

후속 작업에는 [개발 지침](../../dev/README.md)을 적용한다. 스킬 안내 문서만 변경하므로 Node.js 스캐너 구현 지침은 적용하지 않는다. 애플리케이션 코드, 테스트 코드, 새 도구와 의존성 또는 설치된 개인 스킬 사본은 이 플랜의 변경 대상이 아니다.

기존 확정 결정, 비선호와 적용 범위, 응답 대기와 취소, 짧은 답변 재개, 최대 3회 비교 및 승인된 연장, 저장 형식을 강제하지 않는 단계 결과, 실제 UI 검증과 코드 수정 역할 분리를 유지한다. 이전 설계 기록의 요구사항과 승인 결정은 재작성하지 않는다.

## 스킬 서술의 표현 수정 기준

`SKILL.md`와 모든 참고 문서에서 `작업`, `task`, `work` 및 이 단어가 포함된 제목과 문장을 문맥별로 검토한다. 영어로 작성된 스킬은 같은 뜻을 자연스러운 영어로 표현한다. 단어가 있다는 이유만으로 바꾸지 않고, 무엇을 뜻하는지 확인한 뒤 문장을 다시 쓴다.

- 달성하려는 결과는 이용 목적으로 표현한다.
- 이용 목적과 함께 상황, 제약과 판단할 내용을 설명할 때는 사용 시나리오로 표현한다.
- 화면에서 하는 행동은 검색, 비교, 선택, 입력과 예약처럼 실제 행동을 적는다.
- 검색 필터나 예약 기능처럼 서비스가 제공하는 수단은 기능으로 표현한다. 기능 목록을 이용 목적이나 사용 시나리오의 대체로 사용하지 않는다.
- 스킬 자체의 진행이나 개발을 뜻하면 조사, 시안 생성, 구현 입력 작성과 코드 수정처럼 실제 절차를 적는다.

예를 들어 `핵심 작업 파악`은 `주요 이용 목적과 사용 시나리오 파악`으로, `반복 작업`은 확인된 행동에 따라 `반복적인 항목 비교` 등으로, `작업 적합성 검증`은 `이용 목적 달성과 수행 과정 검증`으로 다시 쓴다. 예시는 새 기능이나 시나리오를 추가할 근거가 아니다. 전문 개념이나 정확한 명칭을 보존해야 하면 뜻과 유지 이유를 확인하고, 뜻이 불명확하면 영향을 받는 문장만 판단을 보류한다.

이번 표현 수정은 기존 단계, 승인 조건과 기능 범위를 바꾸지 않는다. 요구사항의 표현 기준을 1단계의 수정 목록, 각 문서 재작성과 마지막 검증에 반영한다.

## 실행 기록

### 지침 분량과 읽기 범위 정리

스킬의 목적과 보호 동작을 유지하며 공통 규칙, 절별 진입과 문장 분량을 정리한다. 다섯 파일 구조와 이름은 유지한다. 수정 전 기준은 31,167바이트, 공백으로 구분한 4,270단어다. 실제 토큰 수와 실행 품질은 별도로 측정해야 한다.

1. 규칙 배치와 수정 목록 확정. 증거 분류, 결정 상태, 시각 근거, 코드 수정 제한과 결과 반환은 `SKILL.md`에서 정의한다. 참고 문서는 조사, 결정, 시안과 구현 입력, 검증의 고유 절차만 남긴다. 공통 규칙을 한 번 정의하고 절별로 읽는 구성을 적용한다.
2. 절별 진입 수정 완료. `SKILL.md`에 공통 규칙과 절별 링크를 정의했다. 짧은 답변은 결정 문서의 재개와 응답 해석, 시안은 생성과 직접 확인, 검증은 현재 증거와 화면의 네 검사 항목으로 연결한다. 다른 절은 실제 판단이나 후속 행동이 필요한 경우에만 읽는다. 공통 규칙과 선택한 절을 함께 읽는 조건은 유지한다.
3. 문장 축약 완료. 네 참고 문서의 반복 정의와 상세 반환 목록을 줄였다. 변경된 판단, 대기 질문과 다음 행동을 반환한다. 이전 결과가 없거나 압축된 경우에는 출처, 결정 범위, 차례와 미확인 조건을 포함해 재개할 수 있는 정보를 복원한다.
4. 최종 검토와 반영 완료. 절별 진입 검토에서 시안 생성의 공통 시각 규칙 확인과 조사 시작의 대기 질문 및 차례 확인이 생략될 수 있어 두 절에 조건부 연결을 보완했다. 잠정 기본안의 가역성도 명시했다. 규칙별 정의 위치, 절별 필수 조건, 짧은 답변과 취소, 기존 결정 충돌, 조사 실패, 생성 이미지 확인, 실행 화면과 재사용 검증을 확인한다. 발견한 문제를 수정한 뒤 영향받은 항목만 재검사한다. 파일 크기와 대표 입력별 읽기 분량을 수정 전과 비교한다.

문서와 절별 진입 검토는 `pass`다. 수정 후 전체는 22,241바이트, 공백으로 구분한 2,700단어로 각각 28.6%, 36.8% 감소했다. 진입 문서와 선택한 절 본문을 합산한 분량은 짧은 답변 9,141바이트, 시안 생성 9,290바이트, 실행 화면 검증 10,298바이트다. 질문이나 충돌이 추가되면 필요한 절의 분량이 더해진다. 합산에는 절 제목을 제외했으며 실제 실행 중 읽은 토큰 수를 뜻하지 않는다.

로컬 링크와 절 연결, 이름 유지, 필수 frontmatter 필드와 문서 형식 검사는 통과했다. 제공된 스킬 검사기는 필요한 `yaml` 라이브러리가 없어 실행하지 못했다. 새 의존성은 추가하지 않았다. 실제 이미지 생성 품질, 실행 UI와 토큰 사용량의 개선은 이번 문서 검토에서 측정하지 않았다.

필요한 참고 자료만 읽는 구성은 [공식 스킬 안내](https://learn.chatgpt.com/docs/build-skills)의 점진적 정보 제공 방식과 일치한다. [스킬 지침 개선 안내](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)는 진입 문서를 짧게 두고 무관한 자료를 읽도록 강제하지 않는 방식을 권한다. 읽기 분량 감소와 실제 성능 개선은 구분하며, 후자는 [스킬 평가 안내](https://developers.openai.com/blog/eval-skills)에 따라 같은 입력의 실행 결과와 사용량으로 판단한다.

### 재설계 절차

1. 규칙 이동 목록 작성 완료. `discovery.md`의 조사 진입과 종료, `inspection.md`의 도구 선택과 증거 분류, `rationale.md`의 사례별 분석을 `research.md`로 옮긴다. 시각 속성 중심 검색과 고정 후보 수, 속성 조합 지시는 제거한다. `preferences.md`의 결정 상태, 충돌, 응답 대기, 재개와 차례 계산은 `decisions.md`로 옮긴다. 생성 시안과 구현 입력은 `implementation.md`, 최신 실행 화면, 적용 범위와 재사용 판단은 `validation.md`가 맡는다. 기존 설계 기록 외에 스킬 밖의 직접 실행 참조는 발견하지 않았다.
2. 루트 안내 재작성 완료. 이름을 유지하고 이용 목적, 사용 시나리오와 잠정 디자인 근거를 먼저 확인하도록 바꿨다. 기존 단계 결과에 명시된 다음 절차에서 재개하고 확정 방향 적용과 변경 후 검증으로 바로 진입하는 안내를 유지했다.
3. 조사 절차 통합 완료. `research.md`에 질문별 조사 여부, 사용 시나리오 기반 검색, 실제 화면 확인, 네 증거 상태와 사례별 비교를 통합했다. 후보 수를 채우지 않고 해결 전략별 적용 판단과 미확인 사항을 반환하도록 정리했다.
4. 결정과 재개 절차 통합 완료. `decisions.md`에 근거로 해결할 판단, 잠정 기본안과 응답이 필요한 방향을 구분했다. 기존 결정 보호, 짧은 답변 재개, 응답 대기와 취소, 차례 계산 및 승인된 연장을 유지하고 저장 형식을 강제하지 않는 단계 결과에 디자인 근거를 포함했다.
5. 생성 시안과 구현 입력 재작성 완료. `implementation.md`에 현재 화면의 공통 시각 규칙과 현실적인 콘텐츠를 정의하고, 생성된 실제 이미지를 전체 구성부터 직접 확인한 뒤 결함을 수정하도록 추가했다. 생성 또는 시각 확인 실패와 개선이 멈춘 경우를 미완료로 반환하며 코드 수정 승인과 실행 화면 검증을 분리했다.
6. 실행 UI 검증 문서 재작성과 이전 문서 정리 완료. `validation.md`를 이용 목적 달성과 수행 과정, 시각적 일관성, 완성도와 차별성으로 구성했다. 최신 구현 증거, 상태별 미확인 사항, 확정 시각 판단과 다른 기존 대상에서의 재사용 검증을 유지했다. 규칙 이동을 마친 이전 네 참고 문서를 제거하고 현재 검토 문서의 선택 절차 링크를 새 문서로 연결했다.

표현 수정 목록은 `user task`를 이용 목적 또는 수행할 행동으로, `task pattern`을 사용 시나리오 또는 상호작용 방식으로, `work screens`를 실제 행동이 드러나는 화면 이름으로 바꾸는 것이다. `current work`, `implementation work`와 `next task`는 각각 현재 디자인 판단, 코드 수정과 다음 절차로 구체화한다. 정확한 스킬 이름은 유지하며 실행 지침에 특정 주체를 지칭하는 문장은 두지 않는다.

최종 문서 검토 결과는 `pass`다. 이름과 디렉터리, 네 참고 문서, 현재 링크, 규칙 이동, 요구사항 연결과 표현 기준을 확인했다. 애플리케이션과 테스트 코드는 추가하지 않았고 설치된 스킬 사본도 수정하지 않았다.

문서 절차 확인에서는 다음 입력별 진행과 종료 조건을 확인했다.

- 신규 UI는 이용 목적과 사용 시나리오, 잠정 디자인 근거에서 시작해 필요한 공통 규칙을 정의하고 생성된 이미지를 직접 확인하도록 이어진다.
- 기존 UI 개선은 유지할 동작과 수정할 외형을 구분하고 최신 실행 화면에서 보존할 동작과 수정할 외형을 확인하도록 이어진다.
- 일반 SaaS 화면은 정보 관계와 도메인 콘텐츠로 배치 이유를 설명한다. 목록이나 카드의 이름만으로 실패를 판정하지 않는다.
- 전문 디자인 판단이 없는 입력은 근거와 잠정 기본안으로 진행한다. 유효한 방향이 남을 때만 관찰 가능한 차이를 질문한다.
- 지정 레퍼런스는 전략을 채택하거나 변형하는 이유를 반환하며 접근 실패 시 대상을 조용히 교체하지 않는다.
- 짧은 답변은 하나의 대기 질문에 연결하고 취소와 미응답은 같은 차례에 남긴다. 기존 규칙 충돌은 승인 전 적용하지 않으며 접근 및 이미지 생성 실패는 필요한 화면 근거를 미확인으로 반환한다.

생성 시안의 실제 완성도, 실행 UI와 이전 결과 대비 개선 검증은 `needs human input`이다. 현재 실제 대상 UI나 이전 생성 시안이 제공되지 않아 문서 절차만 확인했다. 실제 사용 시나리오와 시안, 최신 구현을 보여 주는 실행 화면을 확보한 뒤 시안의 완성도와 실행 UI의 검증 조건을 확인해야 한다. 문서 검사 통과는 두 문제의 개선 증거가 아니다.

## 실행 순서

### 1. 기존 규칙의 이동 위치를 정한다

현재 스킬의 일곱 파일과 저장소 내 직접 참조를 조사한다. 각 규칙을 유지, 이동, 재작성 또는 제거로 분류하고 다음 단계의 수정 목록으로 사용한다. 애플리케이션이나 저장 시스템은 추가하지 않는다.

표현 수정 기준에 따라 제목과 문장마다 뜻과 대안을 기록한다. `user task`, `task pattern`, `work screens`와 같은 기존 표현도 포함하며, 확립된 개념을 유지하는 경우에는 검토한 대안과 유지 이유를 남긴다.

책임이 같은 규칙만 통합하는 문서 구성을 적용한다. 증거 분류와 결정 상태는 `SKILL.md`에서 정의한다. `research.md`는 조사, `decisions.md`는 비교와 재개, `implementation.md`는 시안과 구현 입력, `validation.md`는 실행 화면 판단을 설명한다. `SKILL.md`에는 공통 원칙과 진입 조건을 둔다.

마지막 검증에서는 보존할 규칙마다 이동 위치가 하나씩 있는지, 이전 파일을 참조하는 현재 실행 지침이 남는지 확인한다. 기존 기록의 역사적 참조는 삭제된 파일을 현재 안내로 사용하도록 오해시키는 경우만 별도 판단한다.

### 2. 절차 선택과 초기 디자인 근거를 재작성한다

`SKILL.md`의 설명과 본문을 수정한다. 새 설계는 이용 목적, 사용 시나리오, 이를 지원하는 기능, 정보 관계, 행동 빈도, 오류 비용, 화면에서 다룰 정보량, 도메인 특성, 플랫폼 조건과 기존 규칙을 먼저 확인한다. 화면 구조와 강조의 이유를 설명하는 잠정 디자인 근거를 만든 뒤 필요한 조사와 결정을 선택한다.

모든 입력에 같은 순서를 강제하지 않는다. 기존 단계 결과가 있으면 다음 행동에서 재개하고, 확정 방향 적용은 구현 입력으로, 변경 후 검증 요청은 검증으로 바로 연결한다. 근거가 달라졌을 때만 영향을 받는 앞 단계로 돌아간다.

필요한 절차만 읽는 점진적 로딩을 적용한다. 세부 상태 규칙을 본문에 중복하지 않고 상세 규칙을 정의한 참고 문서에 연결한다. 최종 검증에서 신규 입력이 서비스 검색부터 시작하지 않는지와 재개 입력이 불필요한 탐색으로 돌아가지 않는지를 확인한다.

### 3. 외부 조사 절차를 통합한다

`research.md`를 추가해 기존 `discovery.md`, `inspection.md`, `rationale.md`의 필요한 내용을 옮긴다. 후보 검색은 이용 목적, 사용 시나리오와 해결할 상호작용 문제로 시작하고, 색과 모서리 등은 실제 사례 분석에서 관찰한다. 후보 수를 채우는 기준은 제거한다.

후보 탐색, 화면 확인, 사례별 분석과 비교를 순서상 구분한다. 직접 관찰, 자료 설명, 해석과 미확인 상태를 유지한다. 정확한 값은 공식 명세, 코드 또는 DOM/CSS 근거가 있을 때만 확정한다. 해결 전략별 채택, 변형, 거부 또는 미확정 결과와 근거를 반환한다.

자료별 출처와 확인 범위를 연결하는 방식을 적용한다. 실제 시각 판단에는 현재 사용할 수 있는 MCP 화면 관찰 기능을 사용하고, 접근 실패나 필수 자료 부재는 미확인으로 남긴다. 같은 전략만 반복되거나 결정에 충분한 근거가 생기면 조사를 종료한다.

최종 검증에서 검색 요약이나 생성 이미지를 실제 UI 관찰로 기록하지 않는지, 근거 없는 수치가 남지 않는지와 전략별 출처를 다시 찾을 수 있는지 확인한다.

### 4. 결정과 재개 절차를 통합한다

`decisions.md`를 추가하고 `preferences.md`의 보호 동작을 옮긴다. 미해결 사항을 근거로 해결할 판단, 잠정 기본안을 둘 판단과 응답이 필요한 판단으로 구분한다. 근거로 해결되면 질문 없이 진행하고, 이용 목적을 달성하는 순서나 방법 또는 시각 방향의 의미 있는 차이가 남으면 화면과 관찰 가능한 장단점으로 비교한다.

잠정 기본안은 가역적이며 기존 결정과 충돌하지 않는 범위에만 적용한다. 확정 선택이나 검증된 규칙으로 기록하지 않는다. 기존 결정과 충돌하면 응답을 기다리며 미응답, 취소나 시간 경과를 승인으로 간주하지 않는다.

확정, 잠정, 미결정과 실행 검증 상태를 나누는 방식으로 진행 상태를 유지한다. 대기 질문, 비교 자료, 적용 범위, 완료한 차례와 다음 행동을 반환한다. 기본 3회는 상한이며 0회로 끝날 수 있다. 내부 검색은 차례로 세지 않는다.

최종 검증에서 번호만 있는 답변의 연결, 취소 후 대기, 기존 결정 충돌, 3회 이후 연장과 이전 결과가 없는 상황을 확인한다. 생성 시안을 선택했다고 실행 검증 상태로 승격되지 않아야 한다.

### 5. 생성 시안과 구현 입력을 재작성한다

`implementation.md`에서 레퍼런스별 속성 조합 지시를 제거한다. 초기 디자인 근거, 사용 시나리오의 행동 순서와 분기, 정보 관계, 기존 규칙과 확정 결정을 하나의 방향으로 정리한다. 현재 화면에 필요한 글자 위계, 간격, 정렬, 영역 구분, 행동의 중요도와 상태 및 화면 크기별 변화는 재사용 사례가 없더라도 정의한다. 전체 토큰 체계는 미리 만들지 않는다.

이미지 생성 입력에는 화면 목적, 대표 사용 시나리오와 주요 행동, 현실적인 콘텐츠와 정보량, 주요 영역의 관계, 시각 규칙, 필요한 상태, 피할 표현과 잠정 사항을 포함한다. 사용할 수 있는 이미지 생성 기능의 지침을 따르되 특정 도구를 필수로 만들지 않는다.

생성 후 이미지를 직접 확인해 먼저 보여야 할 정보와 주요 행동의 위계, 전체 배치, 내용의 구체성, 일관된 표현과 의미 있는 차별성을 점검한다. 위반한 조건이 있으면 위반한 조건을 반영해 시안을 수정하거나 미완료로 반환한다. 시각 자료를 텍스트 와이어프레임으로 대체하지 않는다.

단계마다 필요한 공통 규칙만 정의하는 방식을 적용한다. 값이 필요한 곳에는 잠정 값을 전달하되 그 값의 상태와 검증 조건을 함께 전달한다. 이미지에 없는 상호작용과 반응형 상태는 확인했다고 주장하지 않는다.

최종 검증에서 기능만 배치된 시안을 완성으로 제출하지 않는지, 시안의 구조를 서비스 이름 없이 설명하는지와 구현 입력에 상태 및 조건이 포함되는지 확인한다. 이미지 생성이 불가능하고 시각 근거가 필수면 영향을 받는 시안 판단을 보류한다.

### 6. 실행 UI 검증과 참고 문서 정리를 마친다

`validation.md`를 이용 목적 달성과 수행 과정, 시각적 일관성, 완성도와 차별성 중심으로 재작성한다. 주요 행동을 시작할 위치를 찾을 수 있는지, 정보 우선순위, 반복 조작, 위험 행동, 영역별 공통 규칙과 필요한 상태 및 반응형 변화를 구체적인 관찰 대상으로 정한다.

기본 라이브러리 외형 자체를 실패로 판단하지 않는다. 현재 방향과 맞지 않거나 영역별 표현이 불일치하는지가 기준이다. 일반적인 목록, 카드나 사이드바도 이름 때문에 배제하지 않고 현재 사용 시나리오에서의 필요와 구성 이유를 판단한다. 필요한 상태가 없거나 임시 문구, 정리되지 않은 전체 배치가 남으면 확인하지 못한 조건을 미완료로 반환한다.

최신 구현을 반영하는 실행 화면과 실제 상호작용을 근거로 사용한다. 적용 범위를 한정하는 검증을 유지하고 다른 기존 대상에서 확인한 경우에만 공통 규칙으로 확장한다. 관찰 가능한 사용 편의와 독창성 판단을 구분하며 시각 검사만으로 전체 사용성이나 접근성 준수를 선언하지 않는다.

1단계의 이동 목록에 따라 이전 네 파일을 제거하고 현재 실행 지침의 링크를 새 문서로 연결한다. 역할 지칭은 조건과 동작 중심으로 바꾸되 이름과 필요한 정확한 명칭은 유지한다. 기존 설계 기록은 일괄 변경하지 않는다.

## 마지막 검토와 검증

스킬 문서 변경을 마친 뒤 한 번의 최종 검증 단계에서 다음 항목을 확인한다. 실패에 대한 수정 후에는 영향받은 검사만 다시 수행한다. 새 테스트 코드나 애플리케이션을 만들지 않는다.

- 신규 UI에서는 검색 전 이용 목적과 사용 시나리오 분석, 초기 디자인 근거, 화면에 필요한 공통 규칙과 실제 생성 시안을 확인한다.
- 기존 UI 개선에서는 보존할 동작과 수정할 시각 문제를 구분하고 기능이 유지되는 실행 화면을 확인한다.
- 일반적인 SaaS 화면에서는 사용 시나리오에서 구조 선택의 이유를 설명할 수 있는지와 도메인 콘텐츠가 남는지 확인한다. 특정 서비스 이름만으로 방향을 설명하면 실패다.
- 전문 판단이 없는 입력에서는 근거 기반 판단과 잠정 기본안으로 진행하고 CSS 수치 선택을 불필요하게 요청하지 않는지 확인한다.
- 지정 레퍼런스에서는 해결 전략의 채택 또는 변형 이유를 확인하고 화면 전체 복제로 처리하지 않는지 확인한다.
- 짧은 답변, 취소, 기존 결정 충돌, 접근 실패와 이미지 생성 실패에서는 대기 및 미확인 상태와 다음 행동을 확인한다.
- 표현 검토에서는 스킬 본문과 네 참고 문서의 제목 및 문장에 있는 `작업`, `task`, `work`를 모두 확인한다. 이용 목적, 상황, 행동, 기능과 실행 절차를 혼동하거나 기능 목록만으로 사용 시나리오를 대신하지 않아야 한다. 남겨 둔 표현은 실제 문맥에 맞는 대안과 유지 이유를 확인한다.

문서 절차를 따라 읽는 검토와 실제 스킬 실행 결과를 구분한다. 기존 자료가 있으면 같은 과제의 이전 결과와 새 결과를 비교하고, 없으면 이번 실행에서 확보한 시안과 화면만으로 확인 범위를 명시한다. 필요한 실제 자료를 확보하지 못하면 문서 정리는 완료할 수 있지만 두 문제의 개선 검증은 미완료로 남긴다.

이름과 디렉터리 유지, 참고 문서 네 개, 삭제 파일을 가리키는 현재 링크, 규칙별 책임, 요구사항별 작업 및 검증 연결을 확인한다. 한국어 표현, 개인 계정이 드러나는 파일 위치와 민감정보도 검사한다. 완료 상태는 저장소의 `pass`, `needs revision`, `needs human input`, `not applicable`로 보고하며 생성 시안 확인과 실행 UI 검증을 각각 기록한다.

## 중단 조건과 계획 갱신

현재 계획 수립을 막는 미결정 사항은 없다. 후속 작업에서 기존 결정 변경, 필요한 기능 제거 또는 관찰할 수 없는 필수 화면이 발견되면 영향을 받는 작업을 멈추고 필요한 결정이나 근거를 확인한다. 영향을 받지 않는 문서 정리는 계속할 수 있다.

각 절차를 진행할 때 이 플랜의 현재 단계와 남은 작업을 갱신한다. 요구사항이 변경되면 영향을 비교하고 승인된 기준에 맞춰 파생 문서와 플랜을 갱신한다. 파일 통합이나 문서 검사 통과를 시안 품질 또는 실제 UI 개선의 증거로 기록하지 않는다.
