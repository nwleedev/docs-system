# ui 재설계 요구사항

`use-progressive-user-interfaces`를 `ui`로 변경한다. 스킬은 사용자와 대화하며 완성된 서비스 화면으로 느껴지는 시안을 제공하고, 이용 목적, 사용 시나리오와 정보 구조에서 도출한 독창적이고 사용하기 쉬운 UI 방향을 제시해야 한다. 스킬 디렉터리와 호출 안내도 새 이름에 맞춰야 한다.

이 문서는 스킬 문서를 수정하고 검토할 때 사용할 요구사항 기준이다.

## 해결할 문제와 결과

기능만 배치한 화면을 완성된 UI로 취급하지 않는다. 현재 화면에 필요한 정보 위계, 배치, 상태, 화면 크기에 따른 동작과 시각적 일관성을 갖춘다. 생성 시안에서도 완성된 화면 구성을 확인할 수 있어야 한다.

외부 서비스의 화면을 복제하거나 여러 서비스의 시각적 속성을 조합하는 방식으로 디자인 방향을 정하지 않는다. 주요 이용 목적, 정보 관계와 도메인 특성에서 구조와 표현을 도출한다. 익숙한 상호작용과 접근성 관습은 유지한다.

외부 UI와 디자인 사례는 해결 전략, 상호작용 관습과 표현 대안을 비교하는 근거로 사용한다. 초기 디자인 근거는 외부 조사 전에 마련하되, 다양한 서비스 UI와 디자인 사례를 검색해 방향을 탐색한다. 서비스 이름 없이 최종 구조와 선택 이유를 설명할 수 있어야 한다.

전문 UI 용어, CSS 값이나 디자인 토큰 지식 없이 진행할 수 있어야 한다. 근거로 해결할 판단과 결과 차이가 미미한 선택은 별도 질문 없이 처리하고, 실제 결과가 달라지는 유효한 방향이 남으면 관찰 가능한 차이와 장단점을 비교한다.

스킬 문서는 책임에 따라 통합하거나 다시 작성해 중복 규칙과 모호한 단계 책임을 줄인다. 실행 지침은 조건과 동작을 설명하는 문장으로 작성하되, 사용자와 디자인 담당 에이전트의 역할을 구분할 때에는 그 주체를 명시한다.

스킬 서술의 `작업`, `task`, `work`는 문맥에 맞는 구체적인 표현으로 정리한다. 이용 목적, 사용 시나리오, 화면에서 수행하는 행동, 이를 지원하는 서비스 기능과 스킬 실행 절차를 구분한다. 서로 다른 뜻을 모두 시나리오나 기능으로 치환하지 않는다.

### 사용자와 대화하는 설계

사용자와 대화하며 설계하는 것을 기본 진행 방식으로 삼는다. 설계 초기에 이용 목적과 원하는 인상, 피할 표현을 함께 확인하고, 방향과 시안을 보여 준 뒤 피드백을 다음 설계에 반영한다. 이미 확인한 내용은 다시 묻지 않으며 전문 용어나 수치 선택을 요구하지 않는다. 결과가 달라지는 방향에 대한 응답을 기다릴 때에는 사용자 대신 선택을 확정하지 않는다.

### 시안 제작 전 디자인 테마 검색과 비교

본격적인 UI 시안을 제작하기 전에 디자인 테마를 검색하고 사용자가 비교할 수 있게 제시한다. 화면을 먼저 만든 뒤 그 화면을 정당화하는 자료를 찾는 순서로 진행하지 않는다.

테마는 원하는 인상과 시각 표현의 방향을 비교할 수 있어야 한다. 색상, 타이포그래피, 이미지 사용과 화면 구성 등의 차이를 확인할 수 있는 시각 자료와 출처를 함께 보여 준다. 테마 이름과 추상적인 설명만으로 비교를 대신하지 않는다. 기존의 조사 범위와 SaaS 디자인 제외 조건은 테마 검색에도 적용한다.

사용자가 유지하고 싶은 부분과 피하려는 부분을 확인해 시안의 방향에 반영한다. 특정 테마의 일부를 선택했다는 이유로 그 테마의 모든 표현을 확정하거나 기존 서비스 화면을 그대로 복제하지 않는다.

### 조사 범위와 반복되는 SaaS 디자인 방지

다양한 서비스 분야의 UI뿐 아니라 그래픽, 편집, 타이포그래피와 이미지 구성 등 디자인 사례도 검색한다. 나열한 분야를 매번 모두 조사할 의무는 없지만, 비슷한 SaaS 화면만 찾아 색과 문구를 바꾸는 방식으로 탐색을 마치지 않는다. 디자인 사례에서 관찰한 표현과 실제 서비스에서 확인한 상호작용은 구분한다.

SaaS 디자인은 기본적으로 피한다. SaaS 디자인을 요구하는 명시적인 조건이 있을 때에만 조사 후보와 시안 방향에 포함한다. 서비스가 구독형이거나 업무용이라는 이유만으로 SaaS 디자인 요구가 있다고 추정하지 않는다.

### 화면 내용과 표현

모든 UI를 텍스트와 버튼만으로 채우지 않는다. 화면에서 다루는 대상과 정보 관계를 표현하는 데 필요한 사진, 일러스트레이션, 그래픽, 데이터 시각화 등도 설계 수단으로 고려한다. 화면 목적에 맞게 표현을 선택하며 장식의 수를 늘리는 것을 목표로 삼지 않는다.

### AI Caption과 텍스트로 조작을 대신하는 문제

`AI Caption`은 화면이나 보고서의 목적과 무관한 설명을 덧붙이거나, 요구사항과 연결되지 않고 뜻도 파악하기 어려운 문장을 생성하는 문제를 가리킨다. 다음 사례는 최소한의 예시이며, 여기에 없는 표현도 같은 기준으로 판단한다. 특정 단어나 문장 목록만 피하는 방식으로 해결하지 않는다.

- 근거 없이 추가한 면책 문구와 서비스 사용 지침
- 화면에 섞인 작업 보고, 작업 과정, 구현 과정과 결정 이유 및 결정 과정
- 보고서의 주제와 관계없이 삽입한 보고서 작성 과정
- 무엇을 가리키고 어떤 조건이나 행동을 설명하는지 알 수 없는 문구
- 현재 미구현 사항을 알리는 경고로 화면을 채우는 방식

사용자가 화면에서 무엇을 판단하거나 수행할 때 필요한 정보인지 설명할 수 없는 문구는 넣지 않는다. 제목, 레이블, 상태 표시나 조작 자체가 전달하는 내용을 설명문으로 반복하지 않는다. 스킬 사용자와 나눌 설계 설명, 변경 보고와 구현상의 한계를 서비스 이용자가 보는 문구로 옮기지 않는다.

문구가 필요하다면 실제 대상, 상태, 조건과 다음 행동을 이해할 수 있게 쓴다. 뜻을 확인할 수 없는 문장을 그럴듯한 문장으로 바꾸어 사실처럼 제시하지 않는다. 필요한 의미가 불명확하면 해당 문구의 확정을 보류하고 스킬 사용자에게 확인한다.

서비스 사용 지침과 경고라는 이유만으로 모두 없애지는 않는다. 실제 이용에 필요한 입력 조건, 진행 상태, 오류 해결 안내, 확인된 위험과 접근성 정보는 유지한다. 보고서에서도 주장에 필요한 조사 방법, 측정 조건, 근거와 한계는 유지한다. 과정이나 결정 자체가 문서에서 설명해야 할 주제인 경우에도 해당 내용을 유지한다. 작성자가 무엇을 했는지 설명하는 부가 보고와 독자가 내용을 판단하는 데 필요한 정보를 구분한다.

텍스트나 버튼으로 지정된 조작을 대신하는 문제도 함께 해결한다. 항목의 순서를 드래그 앤 드롭으로 바꾸도록 요구했다면, 각 항목에 `위로 이동`과 `아래로 이동` 버튼만 배치하고 요구를 충족했다고 판단하지 않는다. 지정된 조작과 화면 구성을 유지하며 필요한 대체 조작은 함께 설계한다. 대체 조작이 필요하다는 이유로 지정된 조작을 임의로 없애거나 버튼을 반복 배치해 화면 구성을 무너뜨리지 않는다.

미구현 경고문을 붙여 요구한 동작의 누락을 대신하지 않는다. 누락된 동작과 시안의 한계는 스킬 사용자에게 별도로 알린다. 서비스 이용에 실제 영향을 주어 화면 안내가 필요한 경우에는 사실로 확인된 현재 상태와 가능한 행동을 전달한다.

### HTML 시안에서 위치를 지정한 요청과 반영

HTML 시안은 요구한 서비스의 실제 화면처럼 보여야 하며, 그 서비스의 콘텐츠와 조작을 제공해야 한다. 시안을 소개하는 문구, 제작 과정과 설계 이유를 화면에 넣지 않는다. 필요한 설명은 스킬 사용자에게 대화나 지정된 기록으로 전달한다.

수정은 요소 선택과 복사, 대화에서 요청, AI 수정, 갱신된 시안 확인 순서로 진행한다. 사용자는 브라우저 개발자 도구 등 HTML 시안 밖의 수단으로 요소를 선택하고 전체 XPath를 복사해, 대화에서 수정 요청과 함께 전달할 수 있어야 한다.

HTML 시안에는 요소 선택, XPath 복사, 의견 입력이나 수정 요청 처리를 위한 메뉴, 버튼과 패널을 추가하지 않는다. 평소 숨겼다가 나타나는 검토 메뉴도 시안 안에 만들지 않는다. 요소 선택과 복사를 위해 서비스의 원래 우클릭, 버튼, 입력이나 드래그 동작을 바꾸지 않는다.

AI는 전달받은 전체 XPath와 현재 시안의 내용을 대조해 수정 대상을 확인하고 HTML 시안 파일을 수정한다. 구조 변경 등으로 대상이 일치하지 않거나 요청의 의미가 불명확하면 필요한 내용만 확인한다. 반영 여부와 처리하지 못한 사항은 대화에서 전달하며, 사용자는 수정된 시안을 다시 열거나 새로고침해 확인할 수 있어야 한다.

피드백 전달과 AI의 자동 수정을 위한 새 서버나 연결 프로그램 구현은 포함하지 않는다. HTML 시안 파일의 생성 및 수정은 기존 애플리케이션 코드 수정과 구분한다. 이미지 생성은 테마 비교나 외형 확인에 활용할 수 있지만, HTML 시안의 실제 조작 확인을 대신하지 않는다.

### 디자인 담당 에이전트

명시적인 요청이 있으면 디자인 담당 에이전트를 생성할 수 있어야 한다. 생성 요청에 수가 따로 지정되지 않으면 기본 1개를 생성한다. 요청이 없으면 자동으로 생성하지 않는다. 에이전트의 제안을 사용자의 확정된 선택으로 취급하지 않는다.

## 유지할 조건

검색 설명, 실제 화면 관찰, 자료에 명시된 내용, 해석과 미확인 사항을 구분한다. 출처가 불명확한 이미지나 생성 시안을 실제 서비스 관찰 근거로 취급하지 않는다. 정확한 구현 수치를 화면 외형만으로 확정하지 않는다.

확정된 선택, 잠정안, 미결정 사항과 실행 화면에서 검증된 규칙을 구분한다. 생성 시안 확인과 실제 UI 검증을 구분하고, 공통 규칙을 검증하지 않은 대상까지 확대하지 않는다. 처음부터 전체 토큰이나 컴포넌트 체계를 만들지 않는다.

시안용 HTML 파일을 생성하고 수정할 수 있어야 한다. 기존 애플리케이션과 테스트 코드 변경은 포함하지 않는다. 피드백은 HTML 시안 밖에서 요소를 선택하고 전체 XPath를 복사해 대화로 전달하는 방식을 따른다.

## 완료를 판단할 근거

후속 스킬 변경에서는 신규 UI, 기존 UI 개선, 전문 디자인 판단이 없는 입력과 특정 레퍼런스가 지정된 입력에 적용한 결과를 확인한다. 이용 목적, 사용 시나리오와 정보 구조에서 출발했는지, 현재 화면에 필요한 공통 규칙을 갖췄는지, 복제 없이 선택 이유를 설명하는지와 불필요한 전문 선택을 요구하지 않는지 확인한다.

사용자와 주고받은 설계 방향과 피드백, 서비스 UI 외의 디자인 조사 결과, 화면 목적에 따른 표현 선택을 확인할 수 있어야 한다. 텍스트와 버튼만으로 화면을 채우는 문제가 개선되었는지는 실제 시안으로 판단한다.

SaaS 디자인을 명시하지 않은 입력과 명시한 입력을 구분해 적용한 결과를 확인한다. 전자에서는 SaaS 디자인을 기본안으로 삼지 않고, 후자에서는 명시한 조건에 맞춰 포함할 수 있어야 한다.

UI 시안 제작 전에 검색한 디자인 테마를 시각 자료와 함께 비교할 수 있었는지, 테마에 대한 사용자 피드백이 시안에 반영되었는지 확인한다.

HTML 시안 밖에서 요소를 선택하고 전체 XPath를 복사한 뒤, 대화에서 수정 요청을 전달해 지정한 요소가 수정되는지 확인한다. 수정된 파일을 다시 열거나 새로고침해 반영 여부를 확인할 수 있어야 한다. 대상이 불명확한 경우에는 확인 후 이어갈 수 있어야 한다.

HTML 시안에는 요구한 서비스의 콘텐츠와 조작이 나타나야 한다. 시안을 소개하는 설명, 제작 과정, 검토용 메뉴와 의견 입력 도구가 포함되지 않았는지, 요소 선택과 복사를 위해 서비스의 조작을 변경하지 않았는지 확인한다.

스킬 이름, 디렉터리와 현재 호출 안내가 `ui`로 일치하는지 확인한다. 디자인 담당 에이전트를 요청하지 않은 경우에는 생성하지 않고, 수를 지정하지 않고 요청한 경우에는 1개를 생성하는지 확인한다.

생성 시안의 화면 구성과 실제 실행 UI에서 이용 목적에 맞는 구성, 시각적 일관성, 완성도와 차별성을 각각 확인한다. 문서 수정이나 컴포넌트 존재만으로 개선 완료를 판단하지 않는다.

화면과 보고서에서 각 문구가 독자의 판단이나 행동에 필요한지, 요구사항과 실제 상태에 근거하는지, 다른 요소와 같은 뜻을 반복하는지 확인한다. 면책 문구, 지침, 작성 및 구현 과정, 결정 설명, 미구현 경고와 이해할 수 없는 문구는 예시 밖의 표현까지 같은 기준으로 확인한다. 필요한 안내와 보고서의 근거는 남아 있어야 한다.

드래그 앤 드롭으로 순서를 바꾸는 시나리오에서는 그 조작이 실제로 가능하고 결과 순서가 반영되는지 확인한다. 텍스트 버튼의 존재만으로 완료를 판단하지 않으며, 대체 조작을 함께 제공해도 지정된 조작과 화면 구성이 유지되는지 확인한다.
