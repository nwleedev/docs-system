# 빈 요구사항 생성과 결정 기록 방식

빈 파일 생성은 내용 작성과 분리하고, 결정 기록은 확정된 선택의 이유와 계획 영향을 남기는 데 사용한다. 아래 기술 선택은 계획을 위한 제안이며 요구사항을 추가로 확정한 기록이 아니다. 자료 확인일은 2026-10-27이다.

## 전환 전 규칙과 바꿀 부분

[전환 전 스킬](../../../../skills/use-flexible-design/SKILL.md)의 「Establish the requirement baseline」과 [설계 기준](../../README.md)의 「Authority and creation」은 전환 전에 명시적인 요청에서 최소 초기 요구사항을 작성하는 것을 허용했다. 따라서 현재 상태를 요구사항 작성의 전면 금지로 설명할 수는 없다. 다만 초기 작성의 허용 조건과 별개로 빈 파일 생성 절차가 없고, 일부 보완과 전체 작성의 구분도 명시되어 있지 않다.

설계 기준은 요구사항 문서에 목표, 조건과 완료 근거를 요구하며 빈 디렉터리와 임시 문구를 금지한다. 빈 요구사항 생성에는 준비 단계와 작성된 문서를 구분하는 예외가 필요하다. 이 예외가 내용 없는 파일을 구현 기준으로 사용하는 근거가 되어서는 안 된다.

현재 스킬은 저장소의 기준 README를 우선한다. 이름을 바꾸면서 스킬 본문만 수정하면 저장소 기준과 다른 작업을 지시할 수 있으므로 기준 README와 기본본의 관련 규칙도 변경 대상으로 삼는다. 기존 README를 기본본으로 자동 교체하는 기능은 필요하지 않다.

## 스킬 이름과 실행 파일 배치

[Agent Skills 명세](https://agentskills.io/specification)는 `name`이 스킬의 상위 디렉터리 이름과 일치해야 한다고 정한다. 원문은 “Must match the parent directory name”이다. 같은 명세에서 `scripts/`는 실행 코드를 보관하는 선택 디렉터리다. 새 스킬 폴더 아래에 생성 스크립트를 두고 이름, 메타데이터와 호출 지침을 함께 바꾸는 근거다.

[저장소 사용 안내](../../../../README.md)는 `skills/` 전체를 필요한 설치 위치로 복사하는 방식을 설명한다. 따라서 실행 파일도 스킬 폴더에 포함하되 출력 대상 저장소를 스크립트의 설치 위치로 추정하지 않는 구성이 적합하다. 설치된 다른 복사본까지 자동 변경하는 기능은 현재 변경 범위에 없다.

## 파일 생성과 인수 처리

[Node.js 22 계열 파일 시스템 문서](https://nodejs.org/docs/latest-v22.x/api/fs.html#file-system-flags)는 `wx`에 대해 “fails if the path exists”라고 설명한다. 파일 존재 확인 뒤 일반 쓰기를 수행하는 방식은 두 작업 사이에 상태가 바뀔 수 있으므로 권장하지 않는다. 배타적 파일 생성으로 기존 내용을 보존하는 방식이 적합하다. 이 옵션만으로 상위 디렉터리의 symlink 교체나 모든 파일 시스템의 동시성 문제까지 해결되지는 않는다.

[Node.js 22.0.0의 `util.parseArgs`](https://nodejs.org/download/release/v22.0.0/docs/api/util.html#utilparseargsconfig)는 옵션 선언, 엄격한 파싱과 token 출력을 지원한다. [저장소 MJS 지침](../../../dev/node/mjs-cli.md)의 「인수 해석은 반복 option까지 검사한다」는 단일 옵션 반복이 앞선 값을 숨기는 문제를 다룬다. 필요한 옵션만 선언하고 반복 및 허용 조합을 별도로 검사하는 구성을 계획한다.

전환 전 `eslint.config.mjs`의 스크립트 검사 범위는 `skills/use-better-terms/scripts/**/*.mjs`다. 새 위치에 파일을 추가하는 것만으로 기존 lint가 적용된다고 볼 수 없다. 생성기에 맞는 별도 파일 설정이 필요하며 검사기 전용 제한을 그대로 복사하지 않는다.

## JSDoc의 구체적인 타입

[JSDoc의 `@typedef` 문서](https://jsdoc.app/tags-typedef)는 재사용할 사용자 정의 타입을 설명한다. [TypeScript의 JSDoc 문서](https://www.typescriptlang.org/docs/handbook/jsdoc-supported-types.html#typedef-callback-and-param)는 속성별 타입과 객체 리터럴을 사용한 typedef를 지원한다. 두 문서는 필드가 있는 타입을 표현할 수 있다는 점에서 일치한다.

공식 예시에 `object`가 쓰인다는 사실이 이번 스크립트에서 포괄 타입을 쓸 이유가 되지는 않는다. 입력 옵션과 생성 결과는 실제 필드를 직접 적는 형태로 정의할 수 있다. JSDoc 작성 자체는 타입 검사 실행의 증거가 아니며 현재 `package.json`에는 별도 타입 검사 명령이 없다.

## 결정 이유와 계획 연결

[결정 기록 원문](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)은 결정, 배경, 상태와 결과를 간결하게 보존하고, 대체된 결정도 이력으로 남기는 방식을 설명한다. 아직 합의되지 않은 상태와 확정된 상태를 구분한다는 점이 중요하다.

[현재 설계 기준](../../README.md)의 「decisions/*.md」도 확정된 중요한 선택만 결정 문서로 기록하도록 한다. 추가 결정이 필요한 즉시 확정 문서를 만드는 대신 질문과 선택지는 조사 자료에 두고, 확정 뒤 결정 문서를 만들고 계획에 연결하면 기존 규칙과 함께 적용할 수 있다. 원문의 순번 파일명이나 고정 양식을 도입할 필요는 없다.

외부 자료는 파일 생성 API, 타입 표현과 기록 방식의 근거다. 내용 작성 권한, 승인 여부와 필요한 요구사항은 외부 문서로 정할 수 없다. 이 자료를 실제 스크립트 동작이나 요구사항 확인을 대신하는 증거로 사용하지 않는다.
