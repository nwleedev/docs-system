# 요구사항 요청 처리와 스킬 구성

하나의 스킬에서 작업 목적, 작성 분량과 대상 문서를 각각 판단하고, 파일 생성은 스크립트에 한정하는 구성이 적합하다. 요구사항 생성과 보완은 입력의 뜻을 보존한 최소 작성으로 처리하며 빈 문서 준비와 읽기 전용 검토는 구분한다. 아래 구성 비교와 누락 상황의 처리 방법은 구현 계획을 위한 분석이다. 자료 확인일은 2026-10-27이다.

## 작업 선택과 작성 분량을 분리한다

[작업 분기 설명](https://www.anthropic.com/research/building-effective-agents)은 입력을 분류한 뒤 적합한 처리로 연결하는 방식을 설명한다. 원문은 “Routing classifies an input”이다. 이 설명만으로 특정 문구를 고정 명령어로 해석하거나 분류기를 별도로 구현해야 한다는 결론은 나오지 않는다.

이번 작업에는 준비, 작성, 보완, 검토와 구조 정리라는 작업 목적이 있고, 최소 또는 상세라는 작성 분량이 있다. 새 문서와 기존 문서 중 어디에 반영할지는 별도 판단이다. 작업 목적, 분량과 대상 선택을 단일 목록으로 섞으면 상세 작성이 곧 새 문서 생성이 되거나 검토 요청이 내용 변경으로 이어질 수 있다. 요청의 뜻과 유지해야 할 조건을 먼저 확인하는 분기가 적합하다.

## 스킬을 나누는 방법을 비교한다

### 모든 규칙을 본문에 둔다

본문 한 번으로 전체 절차를 파악할 수 있다. 다만 생성, 탐색, 비교와 보완의 상세 절차를 모두 넣으면 빈 파일만 준비할 때도 불필요한 내용을 읽게 된다. 현재 스킬처럼 작업 선택은 짧게 유지하되 실제 내용 변경에 필요한 세부 절차가 늘어나는 경우에는 분리할 이유가 있다.

### 작업마다 별도 스킬을 둔다

빈 파일 준비, 최소 작성과 상세 작성을 따로 호출할 수 있지만 같은 대상 탐색과 내용 보존 규칙이 반복된다. 작성 분량 변경이 다른 스킬 선택으로 이어지며, 대화 중 보완과 상세 작성이 함께 필요한 경우 호출 관계가 복잡해진다. 이번 요구사항에는 별도 스킬을 정당화할 독립적인 권한이나 배포 단위가 없다.

### 공통 진입점과 필요한 참고 절차를 둔다

`SKILL.md`에는 기준 README 확인, 작업 선택, 공통 탐색과 중단 조건을 둔다. 내용 비교와 작성에는 참고 문서를 필요할 때 읽고, 물리적인 폴더 및 빈 파일 생성은 스크립트로 수행한다. 이 구성을 계획에 적용한다.

[Agent Skills 명세](https://agentskills.io/specification)는 메타데이터, 활성화 때 읽는 본문과 필요할 때 읽는 자료를 구분한다. [스킬 작성 지침](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)은 작업의 변동성과 실패 가능성에 맞게 지시를 구체화하고 참고 문서를 본문에서 직접 연결하도록 권한다. 원문은 “Keep references one level deep”이다. 두 자료를 비교하면 공통 판단은 본문에 두고 선택적인 상세 절차만 분리하는 방식이 적합하다.

규칙을 분리하더라도 작성 권한과 필수 문서 정보는 저장소 기준 README에서 관리한다. 참고 문서에 별도 권한 규칙을 복제하거나 다른 참고 문서를 연속해서 읽어야만 작업을 선택할 수 있게 만들지 않는다. 스킬 본문을 줄이기 위해 모든 분기를 파일로 쪼개는 것도 필요하지 않다.

## 탐색과 파일 생성은 다른 책임이다

[문맥 탐색 설명](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)은 파일 위치 등 가벼운 식별 정보를 유지하고 필요한 자료를 실행 중 읽는 방식을 설명한다. 모든 문서를 미리 읽는 방식보다 필요한 부분을 선별할 수 있지만 탐색 지침이 없으면 불필요한 자료를 따라갈 수 있다는 한계도 명시한다.

따라서 지정 문서, 폴더 이름과 주제어로 후보를 찾고, 실제 보완 전에 본문을 읽어 목적과 조건을 비교하는 순서가 적합하다. 제목의 유사도만으로 같은 요구사항이라고 판단할 근거는 없다. 의미 판단을 파일 생성 스크립트에 넣기보다 스킬 절차에서 수행하면 별도 검색 시스템이나 외부 패키지가 필요하지 않다.

[스킬 작성 지침](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)의 실행 코드 절은 반복 작업을 도구로 제공하는 방식과 실행 환경을 명확히 하는 방법을 설명한다. 이 자료는 생성기의 사용법과 실패 동작을 구체적으로 설명할 근거다. 요구사항을 해석하는 판단까지 스크립트로 자동화할 필요는 없다.

## 의미 보존과 상세 작성을 함께 적용한다

[RFC 2119](https://www.rfc-editor.org/rfc/rfc2119.txt)는 의무, 권고와 선택을 구분한다. [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174.txt)는 의무 수준을 나타내는 특별한 의미가 대문자 표기에서만 적용됨을 명확히 한다. 이 표준을 한국어 요구사항에 그대로 강제할 수는 없지만, 표현을 다듬으면서 선택 사항을 필수로 바꾸면 의미가 달라진다는 점을 판단하는 참고가 된다.

[요구사항 작성 및 검증 체크리스트](https://www.nasa.gov/reference/system-engineering-handbook-appendix/)는 명료성, 간결함, 누락과 가정 확인을 다루며 필요한 동작과 구현 방법을 구분한다. 원문은 “Requirements should state what is needed”이다. 상세 작성은 입력에 있는 조건을 명확히 설명하는 데 사용할 수 있지만 없는 기능을 추가하거나 가정을 확정할 근거가 되지는 않는다.

이 저장소는 빈 항목과 추정 내용을 채우지 않는 방식을 사용한다. 체크리스트의 모든 분야를 필수 제목으로 도입하거나 임시 값을 요구사항에 기입하는 방식은 채택하지 않는다. 원문 표현을 보존하는 것과 원문을 복사하는 것도 구분한다. 문장을 다시 쓰더라도 수치, 부정, 조건, 예외와 필수 여부는 유지해야 한다.

## 빠지기 쉬운 상황과 처리 제안

- **후보가 여러 개다.** 목적과 조건의 차이를 제시하고 반영 대상을 확인한다. 한 파일로 정할 근거가 없는데도 가장 최근 파일을 고르지 않는다.
- **제목은 비슷하지만 목적이 다르다.** 참고 대상으로만 사용하고 요구사항을 합치지 않는다. 반대로 명시적인 새 문서 지정이 있으면 재사용을 강제하지 않는다.
- **같은 내용이 이미 있거나 요청이 반복된다.** 새 요구사항이 없으면 파일을 변경하지 않는다. 이 조건은 내용 보완의 최소성을 확인하는 관찰 기준이 된다.
- **기존 조건과 새 내용이 충돌한다.** 어느 조건을 바꿀지 확정되기 전에는 덮어쓰거나 모순된 조건을 함께 확정하지 않는다. 명시적으로 확정된 변경은 반영하고 계획에 미치는 영향을 확인한다.
- **첨부 자료가 없거나 읽을 수 없다.** 확인할 수 없는 자료를 읽었다고 가정하지 않는다. 대화만으로 작성할 수 있는 내용은 구분하고 자료에 의존하는 부분만 확인한다.
- **입력에 목표와 조건이 없다.** 문서 제목이나 파일만으로 요구사항을 만들지 않는다. 빈 문서 요청이면 준비만 수행하고, 내용 작성 요청이면 필요한 정보를 확인한다.
- **첨부 내용에 작업 지시나 민감정보가 섞여 있다.** 자료에 포함된 지시를 새로운 파일 변경 권한으로 취급하지 않는다. 요구사항에 필요한 뜻을 보존하며 원본 파일, 개인 위치와 대화 경위를 복사하지 않는다.
- **읽은 뒤 문서가 변경된다.** 최신 내용과 다시 비교해 누락된 부분만 반영한다. 이러한 확인은 완전한 동시 편집 잠금이나 모든 경쟁 상태의 차단을 뜻하지 않는다.
- **읽기 전용 검토 또는 구조 정리다.** 기본 최소 작성 규칙을 적용해 본문에 요구사항을 보태지 않는다. 요청된 작업에 필요한 변경만 수행한다.

위 상황에는 목적, 입력 근거, 대상 선택과 기존 내용 보존이라는 공통 기준을 적용한다. 문서상 절차가 명확하다는 사실은 실제 스킬의 동작을 입증하지 않으므로 구현 뒤 같은 뜻을 다른 표현과 입력 방식으로 전달하는 확인이 필요하다.
