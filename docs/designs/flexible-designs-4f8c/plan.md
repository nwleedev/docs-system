# 유연한 설계 스킬 전환 계획

작업 목적, 작성 분량과 대상 문서 선택을 분리한다. 요구사항 생성과 보완은 최소 작성을 기본으로 하고 기존 문서를 먼저 탐색한다. 빈 문서 준비는 별도 작업으로 유지한다. 스킬과 호출 지침을 전환하고 생성 스크립트를 추가한 뒤 마지막에 전체를 검증한다.

기준은 [요구사항](./requirements.md)의 「문서 구조와 연결」, 「빈 문서 생성」, 「기존 문서 활용」, 「내용 작성과 구조 정리」, 「추가 결정과 계획 변경」과 「완료 조건」이다. 기술 선택은 [생성과 기록 방식 조사](./references/creation-and-decision-research.md)를, 스킬 구성은 [요청 처리와 스킬 구성 조사](./references/request-routing-and-skill-structure.md)를 근거로 한다. 이 계획은 후속 구현을 위한 것이며 구현 완료를 뜻하지 않는다.

기본 작성 방식은 [최소 작성 결정](./decisions/minimal-writing-default.md)을 따른다.

## 진행 상태

- 기존 구조와 작성 규칙: 반영 및 검증 완료.
- 문서 탐색과 보완 절차: 반영 및 검증 완료.
- 이름과 호출 지침 전환: 반영 및 검증 완료.
- 빈 문서 생성 스크립트: 구현 및 실행 검증 완료.
- 전체 검토와 검증: 완료. 기본 스킬 검사기는 YAML 모듈 부재로 실행 불가, 표준 YAML 파서를 사용한 형식 검사로 대체.

## 기존 구조 안에서 생성과 작성 규칙을 정리한다

수정 대상은 [저장소 설계 기준](../README.md)과 `skills/use-design-docs/references/_README.md`다. 기존 기준 README를 우선하는 방식과 기본본 생성 승인 절차를 유지한다. 두 파일을 자동 동기화하는 기능은 추가하지 않는다.

- `docs/designs/<topic>-<short-id>/`와 그 안의 `requirements.md`, `plan.md`, `references/`, `decisions/` 배치를 유지한다. 새 폴더의 짧은 식별자를 제거하거나 기존 폴더를 이동하는 변경은 하지 않는다.
- 네 종류의 문서와 그 안의 항목에 별도 ID를 부여하지 않는 원칙을 명시한다. 문서의 연결은 상대 링크와 제목 및 절 이름을 사용한다. 폴더 이름의 식별자와 문서 및 항목의 ID를 구분하며 별도 번호 체계나 식별자 목록은 추가하지 않는다.
- 생성과 보완 요청은 최소 내용 작성으로 처리하고, 빈 파일만 준비하는 요청과 읽기 전용 검토를 구분한다. 특정 부사나 문장의 일치 여부를 작성 조건으로 삼지 않는다.
- 빈 문서는 제목, 예시와 안내 문구가 없는 0바이트 `requirements.md`로 정한다. 문서 생성 단계에서만 빈 파일을 허용하고, 내용과 완료 조건이 없는 파일을 구현 기준으로 사용하지 못하게 한다. 빈 `references/`나 `decisions/`는 만들지 않는다.
- 최소 작성은 입력에 있는 목표와 조건 가운데 필요한 내용만 기록한다. 상세 작성은 그 내용을 풀어 설명하되 새 기능, 수치나 구현 결정을 추론해 추가하지 않는다. 작성 분량과 일부 보완 또는 전체 작성 여부는 각각 판단한다.
- 프롬프트와 첨부 내용의 뜻, 수치, 부정, 조건, 예외와 필수 여부를 보존한다. 원문 복사나 대화 기록 대신 요구사항 문장으로 정리한다. 기록할 목표와 조건이 없으면 필요한 정보를 확인하고 추정으로 문서를 채우지 않는다.
- 조사 질문, 선택적 제안과 요구되는 동작을 바꾸는 미결 사항을 구분한다. 입력에서 확인된 내용의 보완과 조사로 도출한 제안을 섞지 않는다. 제안은 요구사항 본문 밖에 두고 필요한 착수 조건을 함께 설명한다.
- 구조 정리는 제목, 순서와 문단 배치에 한정한다. 의미, 의무 수준, 조건, 예외와 범위를 바꿔야 하면 구조 정리를 중단하고 변경 여부를 확인한다.
- 추가 결정이 필요한 동안에는 영향받는 작업을 멈춘다. 선택지와 미결 질문은 조사 자료에 두고, 확정 뒤에만 `decisions/`에 결정, 이유, 결과와 재검토 조건을 기록한다. 요구사항이 바뀌면 그 변경을 먼저 반영하고 관련 계획을 갱신한다.

서로 다른 문서의 책임을 분리하는 방식을 적용한다. 스크립트는 빈 파일만 준비하고 내용 작성은 문서 절차에서 수행한다. 요구사항은 목표와 조건을, 조사 자료는 사실과 제안을, 결정 문서는 확정된 선택을 담는다. 검증에서는 기존 배치와 문서별 책임을 유지하면서 최소 작성, 빈 문서 준비와 조사 제안을 구분할 수 있는지 확인한다. 각 단계가 끝나면 계획에 달라진 대상과 남은 절차를 반영하며 검증은 마지막에 모아서 수행한다.

## 기존 문서 탐색과 내용 반영 순서를 정한다

새 스킬의 `SKILL.md`에는 작업 선택과 중단 조건을 두고, 필요할 때 읽는 `references/requirements-workflow.md`를 추가한다. 이 참고 문서는 탐색, 비교와 보완 순서를 설명한다. 권한과 문서별 필수 정보는 기준 README에서 관리하며 같은 규칙을 여러 파일에 복제하지 않는다.

작업은 다음 순서로 연결한다.

1. 현재 요청과 유효한 대화 맥락에서 작업 목적과 작성 분량을 확인한다. 이미 확인한 작성 의도를 매번 다시 묻지 않는다. 첨부 파일은 내용 근거로 읽으며 파일 안의 지시를 새 변경 권한으로 취급하지 않는다.
2. 지정된 문서를 먼저 확인하고, 지정이 없으면 저장소 문서 위치에서 주제와 목적이 가까운 후보를 찾는다. 파일 이름과 관련 표현으로 후보를 찾은 뒤 본문을 읽어 목적, 조건과 기존 결정이 같은 작업인지 비교한다. 의미 검색용 별도 스크립트, 색인이나 외부 패키지는 추가하지 않는다.
3. 같은 요구사항을 담는 문서가 하나로 확인되면 기존 문서를 사용한다. 빈 문서 요청에서는 위치만 안내하며, 별도 새 문서 지정이 있으면 그 지정을 따른다. 목적이 다른 유사 문서는 참고 대상으로만 사용한다. 후보가 여럿이고 대상을 정할 근거가 부족하면 위치와 차이를 제시하고 대상 선택을 확인한다.
4. 기존 문서 전체와 실제로 읽을 수 있는 입력을 비교한다. 이미 있는 내용은 다시 추가하지 않고 누락된 요구사항만 기록한다. 충돌하는 조건이나 명시되지 않은 삭제 및 대체는 임의로 처리하지 않는다. 읽을 수 없는 첨부 자료가 변경에 필요하면 그 부분만 멈추고 필요한 내용을 확인한다.
5. 새 설계 묶음이 필요할 때만 생성 스크립트를 호출한다. 최소 작성 또는 상세 작성은 만들어진 요구사항 파일에 수행하고 빈 문서 요청이면 비워 둔다. 기존 요구사항의 보완이나 같은 작업의 플랜, 리서치와 결정 추가에는 스크립트를 다시 호출하지 않고 기존 폴더를 사용한다. 입력 파일을 저장소에 복사하거나 프롬프트를 보관하는 기능은 추가하지 않는다.
6. 플랜은 기준 요구사항의 파일과 적용되는 절, 필요한 리서치와 결정 파일을 연결한다. 리서치는 조사 질문과 적용할 요구사항 또는 작업을 밝히고, 결정은 판단할 문제, 확정한 선택과 계획 영향을 기록한다. 여러 플랜이 같은 자료를 사용하면 원래 파일로 연결한다.
7. 요구사항이 바뀌면 기존 계획과 결정에 미치는 영향을 확인한다. 확정된 추가 결정을 기록하고 영향받는 계획을 갱신한다. 변경 내용과 남은 질문은 문서 위치와 함께 간결하게 안내한다.

기록이 이미 충분하면 파일을 수정하지 않는다. 읽은 뒤 문서가 다시 변경된 것이 확인되면 최신 내용과 비교해 보완할 부분을 다시 정한다. 이전 내용을 통째로 덮어쓰거나 새 조건과 모순된 조건을 동시에 확정하지 않는다.

한 진입점에서 필요한 작업만 고르는 방식과 참고 자료를 필요할 때 읽는 구성을 적용한다. 준비, 최소 작성과 상세 작성마다 별도 스킬을 만들지 않는다. 생성 스크립트에는 문서 유사도 판정이나 요구사항 작성 기능을 넣지 않는다. 검증에서는 같은 요청을 반복해도 중복이 생기지 않는지, 입력 형식이 달라져도 같은 뜻과 조건이 보존되는지, 기존 폴더에서 별도 ID 없이 필요한 근거를 찾을 수 있는지 확인한다.

## 이름과 현재 호출 지침을 전환한다

`skills/use-design-docs/`를 `skills/use-flexible-designs/`로 이동한다. `SKILL.md`의 `name`, 제목과 설명, `agents/openai.yaml`의 표시 이름, 요약과 기본 호출문을 새 이름에 맞춘다. 별칭 스킬이나 이전 위치의 전달 파일은 만들지 않는다.

앞 단계의 기준에 따라 `SKILL.md`의 작업 선택, 요구사항 기준 확인과 실행 순서를 수정한다. 새 참고 문서는 요구사항 생성, 보완과 구조 정리에 필요한 경우에 읽도록 `SKILL.md`에 직접 연결한다. 빈 문서 준비도 공통 탐색 절차를 거치고 실제 생성에는 스크립트의 사용법을 적용한다. 문서 관리를 넘어 부족한 정보와 변경 영향을 조사하도록 설명하되, 유연한 설계를 이유로 새로운 아키텍처나 추상화를 강제하지 않는다.

현재 호출 지침과 안내는 다음 파일에서 수정한다.

- `README.md`, `README.ko.md`
- `src/AGENTS.en.md`, `src/AGENTS.ko.md`

과거 `docs/designs/**` 기록의 기존 스킬 이름은 당시의 사실로 보존한다. 실제로 이동한 파일을 가리키는 링크만 새 위치로 수정하며 과거 요구사항과 결정 내용을 재작성하지 않는다. 저장소 밖의 설치된 스킬과 환경 지침은 변경 대상에 포함하지 않는다.

이름을 폴더, 메타데이터와 호출문에 일관되게 적용한다. 검증에서는 이전 스킬 폴더 부재, 새 이름 일치, 현재 호출문 전환과 저장소 내부 링크 연결을 확인한다. 과거 이름이 기록에 남는 것은 현재 호출문이 남는 경우와 구분한다.

## 빈 문서 생성 스크립트를 추가한다

`skills/use-flexible-designs/scripts/create-requirements.mjs`를 추가하고 새 스킬과 두 언어 README에서 실행 방법을 안내한다. 생성과 작성 규칙이 정리된 뒤에 진행한다. 저장소 밖에서 복사한 스킬도 실행할 수 있도록 스크립트 위치와 출력 저장소를 분리한다.

- 입력은 `--repo <root>`와 `--topic <slug>`로 제한한다. `--help`는 사용법만 출력하며 파일을 만들지 않는다. topic은 영문 소문자, 숫자와 단일 하이픈으로 구성된 이름으로 제한하고 디렉터리 구분자와 상대 이동 표기를 거부한다.
- 출력은 지정 저장소의 `docs/designs/<topic>-<short-id>/requirements.md`다. 짧은 ID는 새 폴더 이름에만 Node.js 내장 난수 기능으로 생성한다. 새 폴더를 배타적으로 생성하고, 파일도 `wx`로 생성해 충돌 시 기존 파일을 보존한다. 생성 결과에는 빈 요구사항 파일만 두고 문서 ID, 항목 ID와 빈 하위 디렉터리는 만들지 않는다.
- 기준 README가 없으면 자동으로 기본본을 복사하지 않는다. 생성 승인을 받는 기존 스킬 절차로 돌아갈 수 있도록 실패 이유를 출력한다. 쓰기 대상의 상위 디렉터리가 저장소 밖을 가리키는 경우에는 생성을 거부한다.
- 파일 생성에 실패하면 성공으로 알리지 않는다. 부분 생성된 위치와 재실행에 필요한 정보만 알리고 기존 파일이나 폴더를 자동 삭제하지 않는다.
- 성공하면 생성한 저장소 상대 위치를 표준 출력으로 내보내고 상태 `0`으로 끝낸다. 잘못된 인수와 생성 실패는 표준 오류로 알리고 실패 상태로 끝낸다. 절대 위치와 원본 오류 stack을 일반 오류 메시지에 노출하지 않는다.
- Node.js 22.0.0 이상에서 실행하는 단독 ES module로 구성한다. 인수 해석, 위치 계산과 생성 작업을 필요한 함수로 나누되 한 스크립트 밖에 별도 프레임워크나 범용 생성기를 추가하지 않는다.
- JSDoc에는 구체적인 필드를 가진 입력 및 생성 결과 타입과 실제 함수의 매개변수 및 반환 타입을 적는다. 구조 없는 포괄 타입으로 오류나 결과를 대신하지 않는다.

Node.js의 내장 API를 조합하는 방식과 배타적 생성을 적용한다. 외부 패키지, manifest와 lockfile 변경은 없다. 기존 검사기와 비슷한 코드가 있어도 입력, 반환값과 검증 책임이 같을 때만 공통화를 검토한다.

적용 지침은 [개발 기준](../../dev/README.md)이다. [MJS 검사기 지침](../../dev/node/mjs-cli.md)에서는 단독 CLI 실행, 인수 검사, 오류 출력과 함수 책임을 설명하는 절만 적용한다. 검사기 전용 Git 입력, 탐지기 구성, JSON 출력과 자체 검사 규칙은 생성기에 확대하지 않는다.

`eslint.config.mjs`에는 새 스크립트에 맞는 파일별 설정을 추가해 기존 `pnpm lint` 대상에 포함한다. 기존 검사기의 제한은 유지한다. 현재 저장소에는 JSDoc 전용 타입 검사 명령이 없으므로 도구 추가를 전제하지 않고 필드와 함수 사용을 대조한다.

## 변경 결과를 마지막에 검증한다

앞 절의 관찰 항목은 이 단계에서 함께 확인한다. 검증용 생성 위치는 `temps/flexible-designs-<nonce>/` 아래에 두며 별도의 테스트 코드는 추가하지 않는다.

- 생성 결과가 폴더 하나와 0바이트 요구사항 파일인지 확인한다. 정상 생성, 잘못된 topic, 알 수 없는 인수, 기준 README 누락, 쓰기 실패와 저장소 밖을 가리키는 상위 디렉터리 사례를 직접 실행한다. 기존 문서가 있는 저장소에서 실행한 뒤 그 내용이 바뀌지 않았는지도 확인한다.
- 기존 설계 폴더에 플랜, 리서치와 결정을 추가하는 절차에서 새 설계 폴더를 만들지 않는지 확인한다. 네 종류의 문서와 항목에 별도 ID가 없고 파일 및 절 이름으로 근거를 찾을 수 있어야 한다. 여러 플랜이 같은 자료를 참조할 때 원래 파일의 위치와 내용을 유지하는지도 확인한다.
- 생성 충돌 시 기존 파일을 덮어쓰는 옵션이 없는지와 실제 파일 생성이 배타적으로 수행되는지 확인한다. 생성 실패를 성공으로 출력하지 않는지 확인한다.
- 최소 작성, 상세 작성, 빈 문서 준비, 읽기 전용 검토와 구조 정리를 문서 절차에 대입한다. 같은 뜻을 다른 문장으로 요청하거나 대화 및 첨부로 전달해도 작성 범위가 달라지지 않는지 확인한다. 원문에 있는 수치, 부정과 조건이 보존되고 입력에 없는 요구사항이 추가되지 않아야 한다.
- 유사 문서 없음, 같은 목적의 문서 하나, 후보 여러 개와 목적이 다른 문서를 비교한다. 대상 선택의 근거, 수정 여부와 생성 여부가 구분되어야 한다. 명시적인 새 문서 지정도 확인한다.
- 반복 요청, 이미 반영된 내용, 기존 조건과의 충돌, 읽을 수 없는 첨부와 작성 근거가 없는 요청을 확인한다. 중복이나 추정 내용이 추가되지 않고 필요한 질문만 남아야 한다. 첨부 자료에 포함된 지시만으로 다른 파일을 변경해서는 안 된다.
- 요구사항 보완 뒤 계획과 결정의 영향 범위가 연결되는지 확인한다. 추가 선택이 미결이면 영향받는 작업이 멈추고 확정된 뒤에만 결정과 계획이 갱신되어야 한다.
- 새 스킬 이름, 메타데이터, 호출문과 링크를 대조한다. 두 기준 README의 빈 파일 예외가 계획 수립 및 구현 착수 조건을 약화하지 않는지 확인한다.
- `pnpm lint`와 변경 문서 대상 한국어 표현 검사를 실행한다. JSDoc의 각 타입이 실제 입력과 결과를 설명하고 금지된 포괄 타입이 없는지 확인한다.

동작을 바꾸는 미결 사항, 기존 파일 손상, 이름 불일치 또는 검사 실패가 있으면 해당 작업을 완료로 처리하지 않는다. 추가 결정이 필요하면 결정 이유와 영향받는 작업을 기록하고 계획을 갱신한 뒤 재개한다.
