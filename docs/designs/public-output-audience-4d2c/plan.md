# 역할이 드러나는 공개 문구 적용 계획

## 기준과 범위

이 계획은 `requirements.md`의 `### 역할을 드러내는 표현`을 기준으로 한다. 현재 요구사항은 `skills/use-words-review/`, `AGENTS.md`, `README.md`, `README.ko.md`를 적용 대상으로 열거한다. 이번 작업은 역할 표현 원칙을 저장소에 기록되거나 공유되는 모든 문구와 이름에 적용할 수 있도록 요구사항, 작업 지침, 문서 작성 규칙, `use-words-review`의 검토 절차를 연결한다. 배포용 AGENTS 참고 문서와 설계 문서 및 개발 문서의 작성 규칙도 변경 대상에 포함한다.

다음 세 작업만 수행한다.

1. `requirements.md`에 열거된 특정 파일에만 적용하던 역할 표현 규칙을 저장소에 기록되거나 외부에 공유 또는 배포되는 모든 문구와 이름에도 적용한다.
2. 루트 `AGENTS.md`와 배포용 AGENTS 참고 문서에 역할 확인 원칙을 반영하고, 설계 문서와 개발 문서의 작성 규칙에 각 문서 종류에 맞는 적용 기준을 추가한다.
3. `use-words-review`가 파일명, UI와 접근성 문구, 코드 주석, 커밋 문구를 같은 기준으로 검토하도록 입력과 판정 기준을 보완하고, 판단 난도와 영향도에 맞는 서브에이전트 모델과 추론 강도를 실행할 때 선택하도록 한다.

Git 훅, CI, Vale 규칙, 별도 검사기와 새로운 전용 리뷰 에이전트는 추가하지 않는다. 기존 파일에 있는 `사람`을 일괄 치환하거나 이 계획과 관계없는 문장을 함께 다듬지 않는다.

현재 작업에 적용한 개발 지침은 `docs/dev/README.md`이며, 해당 문서를 검토했다. 이 작업은 저장소 공통 작성 지침과 검토 스킬을 바꾸므로 별도의 `docs/dev/` 문서를 추가하지 않는다.

## 적용 원칙

- `사람`은 금칙어가 아니라 역할이 숨겨졌을 가능성을 알리는 검토 후보다. 일반적인 인간 전체를 뜻하는 문장, 승인된 인용과 목적상 필요한 원문은 문맥을 확인한 뒤 유지할 수 있다.
- 역할을 구분해야 하는 문장은 독자와 행위 주체를 확인한 뒤 `작업 지시자`, `사용자`, `개발자`, `검수자`처럼 저장소 근거로 확인되는 역할을 쓰거나 수행하는 행동을 직접 적는다.
- 역할을 확인할 근거가 없으면 임의로 정하지 않고 `needs human input`으로 보고한다.
- 파일명과 디렉터리명도 저장소 구성원이 읽는 이름이므로 문서 제목과 같은 출처 원칙을 적용한다. 작업 지시 문장, 진행 보고와 개인 식별자를 이름으로 사용하지 않는다.
- 공통 원칙은 루트 `AGENTS.md`가 소유한다. `src/AGENTS.en.md`와 `src/AGENTS.ko.md`에는 같은 판단 기준을 각 문서의 언어와 독자에 맞게 반영하되, 루트 지침을 직역하거나 저장소에만 해당하는 내용을 복사하지 않는다.
- `docs/designs/README.md`와 `docs/dev/README.md`는 각각 설계 문서와 개발 지침에서 역할을 구분해야 하는 경우만 설명한다. 공통 원칙과 점검 목록을 다시 소유하지 않는다.
- 변경분 수집과 판정 절차는 `skills/use-words-review/SKILL.md`가 소유한다. `skills/use-words-review/README.md`에는 다른 저장소의 AGENTS에 합칠 기본 지침만 반영한다.
- 검토할 글의 길이나 파일 수만으로 서브에이전트 설정을 정하지 않는다. 주 에이전트가 이미 수집한 독자, 근거, 문맥의 모호성, 잘못 게시했을 때의 영향을 바탕으로 실행할 때 모델과 추론 강도를 선택한다.
- 모델 이름은 배포 환경마다 달라질 수 있으므로 스킬에는 빠른 검토에 적합한 모델, 일반 검토용 모델, 가장 높은 판단 성능을 제공하는 모델처럼 필요한 성능 수준을 기록한다. 현재 호스트가 제공하는 모델 가운데 해당 수준에 맞는 모델을 사용한다.
- 별도 분류 에이전트나 전용 리뷰 에이전트 파일은 만들지 않는다. 가장 높은 추론 강도를 기본값으로 삼지 않고, 실제 검토 사례에서 품질 개선이 확인될 때만 사용한다.

## 작업 순서

### 1. 요구사항의 적용 대상을 공개 산출물 전체로 정리한다

`docs/designs/public-output-audience-4d2c/requirements.md`의 `### 역할을 드러내는 표현`을 수정한다.

- 기존에 열거한 파일을 예시로 한정하지 않고, 저장소에 기록되거나 공유되는 문구와 이름을 적용 대상으로 명시한다.
- 문서, README, Git 커밋과 협업 문구, 파일명과 디렉터리명, UI와 접근성 문구, 코드 주석을 포함한다.
- 일반적인 인간 전체를 뜻하는 경우와 목적상 필요한 원문은 역할 치환 대상이 아님을 명시한다.
- 특정 역할을 확인할 수 없을 때 임의로 정하지 않는 기존 조건을 유지한다.

완료 여부는 요구사항을 검토하는 개발자나 검수자가 적용 대상, 예외, 확인이 필요한 경우를 구분할 수 있는지 확인해 판단한다.

### 2. 공통 작성 원칙을 배포 지침과 문서 작성 규칙에 연결한다

루트 `AGENTS.md`의 기존 `## Public Outputs`와 `### Pre-publication Check`를 보완한다. 새 절을 만들거나 같은 규칙을 `Writing Natural Korean`에 복사하지 않는다.

- 공개 문구나 이름을 작성하기 전에 독자, 독자가 하려는 일, 문장 속 행위 주체와 검토 또는 승인 주체를 확인하도록 한다.
- 역할을 구분해야 할 때 포괄적인 표현 대신 확인된 역할이나 행동을 직접 쓰도록 한다.
- 바뀐 공개 문구뿐 아니라 파일명과 후보 커밋 메시지도 공유 전 점검 대상에 포함한다.
- 기존 출처, 개인정보, 자연스러운 한국어와 커밋 작성 규칙을 약화하지 않는다.

`src/AGENTS.en.md`와 `src/AGENTS.ko.md`에는 루트 지침과 같은 역할 확인 기준을 반영한다. 두 파일은 다른 저장소에서 참고할 수 있는 배포 문서이므로 각 언어에서 자연스럽게 읽히는 표현을 사용하고, 기존 문장에 있는 `human`이나 `사람`은 역할을 숨기는 경우에만 고친다.

루트 `README.md`와 `README.ko.md`에서는 요구사항 작성자, 제품 결정을 승인하는 결정권자와 자동 검사로 판단할 수 없는 내용을 확인하는 담당 검수자의 책임을 구분한다. 두 파일은 같은 원칙을 각 언어에서 자연스럽게 설명하되 문장을 직역해서 맞추지 않는다.

`docs/designs/README.md`와 `docs/dev/README.md`에는 다음 문서별 기준을 추가한다.

- 설계 문서는 요구사항 작성자, 문서 독자, 결정권자와 검수자가 다를 때 각 역할을 구분한다. 근거만으로 역할을 확인할 수 없으면 `needs human input`으로 보고한다.
- 개발 지침은 규칙 작성자, 지침을 적용할 개발자와 검수자 또는 승인 책임자가 다를 때 각 역할을 구분한다. 확인되지 않은 책임을 현재 규칙으로 만들지 않는다.
- 두 README는 공통 판단 절차를 반복하지 않고 루트 작업 지침과 각 문서 종류에 필요한 기준만 연결한다.

완료 여부는 루트와 배포용 AGENTS 문서가 같은 판단 기준을 전달하고, 두 README가 맡은 문서에서만 필요한 역할 구분을 설명하는지 확인해 판단한다.

### 3. `use-words-review`의 입력, 판정 기준과 실행 설정을 보완한다

`skills/use-words-review/SKILL.md`가 기존의 단일 의미 검토 절차 안에서 역할 표현을 확인하도록 수정한다. 산출물 종류별 리뷰 스킬은 만들지 않는다.

- 검토 범위를 정할 때 변경된 파일명과 디렉터리명, 후보 커밋 메시지를 빠뜨리지 않도록 한다.
- 각 산출물에 대해 독자, 독자가 하려는 일, 문장 속 행위 주체와 검토 또는 승인 주체를 입력으로 기록한다.
- 특정 역할을 가리키는 포괄적인 표현이 남아 있는지, 확인되지 않은 역할을 임의로 붙였는지를 판정 기준에 추가한다.
- 문자열 검색 결과를 자동 실패로 처리하지 않고 주변 문맥과 저장소 근거로 판정한다.
- UI와 접근성 문구는 사용자가 알아야 할 상태와 다음 행동을 기준으로 보고, 코드 설명은 호출자나 유지보수 담당자가 알아야 할 사용 조건과 제약을 기준으로 본다.
- 주 에이전트가 서브에이전트를 호출하기 전에 이미 수집한 검토 정보를 바탕으로 다음 설정 가운데 하나를 고르게 한다.
  - 문서 구조와 근거가 분명하고 정해진 기준을 확인하는 검토에는 빠른 검토에 적합한 모델과 낮은 추론 강도를 사용한다.
  - 문맥에 따른 의미 판단이 필요하지만 책임이나 근거가 분명한 일반 검토에는 일반 검토용 모델과 중간 추론 강도를 사용한다.
  - 짧더라도 지칭 대상이 모호하거나 문서 간 책임이 충돌하는 경우, 또는 개인정보, 보안, 라이선스, 승인 책임처럼 잘못 판단했을 때 영향이 큰 검토에는 가장 높은 판단 성능을 제공하는 모델과 높은 추론 강도를 사용한다.
- Codex에서 현재 확인한 시작 설정은 빠른 검토와 일반 검토에 `gpt-5.6-terra`의 낮은 또는 중간 추론 강도, 영향이 큰 검토에 `gpt-5.6-sol`의 높은 추론 강도다. 이 이름은 필수 설정이 아니라 현재 문서를 기준으로 든 예시이며, 설치한 호스트에서 사용할 수 있는 모델을 실행 전에 확인한다.
- 긴 문서라도 반복적이고 판단 기준이 분명하면 빠른 설정을 사용할 수 있고, 짧은 문구라도 책임이나 공개 여부가 불분명하면 높은 설정을 사용하도록 명시한다.
- `xhigh`, `max`, `ultra`처럼 시간과 토큰 사용량이 큰 설정은 기본 경로에서 제외한다. 대표 검토 사례에서 높은 설정보다 결함 누락이나 오판을 줄인다는 결과가 있을 때만 선택한다.
- 호스트가 실행별 모델 또는 추론 강도 지정을 제공하지 않으면 주 에이전트의 설정을 사용하고, 결과에 해당 제약을 기록한다. 더 높은 설정으로도 확인할 근거가 생기지 않는 항목은 역할을 추정하지 않고 `needs human input`으로 남긴다.

`skills/use-words-review/README.md`의 AGENTS 기본 지침에는 같은 공통 원칙과 검토 입력을 반영한다. 설치 안내에는 성능 수준을 현재 호스트의 모델에 대응시키는 방법과 실행별 설정을 사용할 수 없을 때의 처리만 설명하고, 특정 공급자의 모델 이름을 필수값으로 고정하거나 스킬 내부 절차 전체를 복사하지 않는다.

이 계획의 대표 사례 판정과 기본 경로 변경은 작업 지시자가 승인한다. 범용 설치 안내에서는 저장소마다 요청자와 검수자 또는 승인 책임자가 다를 수 있으므로, 기준 답안은 담당 검수자가 확인하고 기본 설정 변경은 승인 책임자가 결정하도록 역할을 나눈다.

`skills/use-words-review/references/examples.md`에서는 화면 사용자, 문서 독자, 요구사항 작성자, 검수자, 승인 책임자와 배포 담당자를 가리키던 포괄적인 표현을 실제 역할로 바꾼다. 예시의 허용 여부와 원문 보존 기준은 바꾸지 않는다.

완료 여부는 다음 사례로 확인한다.

- 역할을 특정할 수 있는 문장에서 `사람`을 발견하고 `needs revision`으로 판정한다.
- 일반적인 인간 전체를 뜻하는 문장은 단어만으로 실패 처리하지 않는다.
- 근거 없이 역할을 선택한 문장은 `needs human input`으로 판정한다.
- UI 문구, 코드 주석, 파일명과 커밋 초안이 모두 검토 범위에 포함된다.
- 길지만 기준이 분명한 문서와 짧지만 역할이 모호한 문구가 각각 다른 설정으로 분류되어 문서 길이가 선택 기준을 대신하지 않는다.
- 작업 지시자가 승인한 판정과 지적 사항을 대표 사례의 기준 답안으로 사용한다. 각 설정에서 상태 판정이 기준 답안과 모두 일치하고 `needs revision`이나 `needs human input` 사유를 빠뜨리지 않았는지 먼저 확인한 뒤, 조건을 충족한 설정끼리 잘못된 지적, 응답 시간과 토큰 사용량을 비교한다. 더 가벼운 설정을 기본 경로로 바꾸는 결정은 비교 결과와 선택안을 작업 지시자에게 확인받은 뒤 확정한다.

## 검증

작업이 끝나면 다음 증거를 확인한다.

3. 루트와 배포용 AGENTS 문서가 역할을 확인하는 순서와 근거가 없을 때의 처리 방식을 같은 의미로 설명하는지 비교한다.
4. 설계 문서와 개발 지침의 README가 문서별 적용 기준만 추가하고 공통 원칙이나 점검 목록을 중복해서 소유하지 않는지 확인한다.
5. `rg`로 변경 파일의 `사람`을 찾아 각 사용처가 일반적인 인간을 뜻하는지, 특정 역할을 숨기는지 문맥별로 검토한다.
6. 변경된 파일명과 본문, 후보 커밋 메시지를 `use-words-review`로 검토하고 모든 항목이 `pass` 또는 승인된 `not applicable`인지 확인한다.
7. `git diff --check`가 통과하고 변경 파일에 개인 절대 경로, 비공개 식별자, `TODO`, `TBD`, `FIXME`가 없다.
8. Git diff에서 훅, CI, Vale 설정과 별도 검사기가 추가되지 않았음을 확인한다.
9. 짧고 기준이 분명한 커밋 문구, 길고 반복적인 문서, 짧지만 역할이 모호한 문장, 여러 문서의 책임을 함께 판단해야 하는 문장, 개인정보 처리나 대외 공개 방침을 판단해야 하는 문장을 대표 사례로 비교한다.
10. 대표 사례의 설정 선택이 글자 수나 파일 수에 좌우되지 않고 판단 난도와 잘못 판단했을 때의 영향에 따라 달라지는지 확인한다.
11. 호스트가 실행별 설정을 지원하지 않는 경우 주 에이전트 설정 사용과 제약 보고가 동작하고, 지원하는 경우 별도 에이전트 정의 없이 호출 시점의 설정이 적용되는지 확인한다.

## 중단 조건

- 역할을 구분하려면 새로운 직책, 승인 책임이나 저장소 정책을 정해야 하는 경우 작업을 멈추고 작업 지시자에게 결정을 요청한다.
- 요구사항의 적용 범위를 넓히는 과정에서 기존 원문 보존 예외나 개인정보 기준을 바꿔야 하는 경우 요구사항 변경안을 먼저 확인받는다.
- 배포용 AGENTS 참고 문서의 기존 의미를 맞추려면 이번 역할 표현 원칙과 관계없는 정책까지 바꿔야 하는 경우 해당 변경을 중단하고 별도 범위로 보고한다.
- 작성 지침만으로 확인할 수 없는 속성을 자동 차단해야 하는 경우 이번 범위에 검사기를 추가하지 않고 별도 작업으로 남긴다.
- 현재 호스트가 제공하는 모델과 추론 강도를 확인할 수 없으면 모델 이름을 추정해 고정하지 않는다. 상속되는 설정으로 검토하고 확인하지 못한 실행 조건을 결과에 기록한다.
- 대표 사례의 기준 답안이 승인되지 않았거나 낮은 설정의 판정이 기준 답안과 일치하지 않으면 속도를 이유로 기본 설정을 낮추지 않는다.

## 확인한 외부 근거

- [OpenAI: Custom instructions with AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)는 Codex가 저장소 경로에 따라 `AGENTS.md` 지침을 읽고 가까운 지침을 우선하는 방식을 설명한다. 공통 작성 원칙을 루트 `AGENTS.md`에 두는 근거로 사용한다.
- [Anthropic: How Claude remembers your project](https://code.claude.com/docs/en/memory)는 지속 지침을 간결하고 구체적으로 작성하고, 반드시 실행해야 하는 검사는 별도 자동화로 분리하도록 안내한다. 이번 작업은 지침과 의미 검토까지만 다루고 자동 차단은 제외한다.
- [W3C: Labels or Instructions](https://www.w3.org/WAI/WCAG22/Understanding/labels-or-instructions.html)는 사용자가 입력이나 다음 행동을 이해하는 데 필요한 레이블과 안내를 제공하도록 설명한다. UI와 접근성 문구의 독자 판단에 적용한다.
- [Google: API reference code comments](https://developers.google.com/style/api-reference-comments)는 공개 API 설명에서 목적, 인자, 반환값과 예외처럼 호출자가 필요한 정보를 다루도록 안내한다. 코드 설명의 독자와 필요한 정보를 판정하는 데 적용한다.
- [Git: git-commit](https://git-scm.com/docs/git-commit)은 커밋 메시지가 변경 내용을 기록하는 입력임을 설명한다. 후보 커밋 메시지를 다른 공개 산출물과 함께 검토 범위에 포함하는 근거로 사용한다.
- [OpenAI: Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)는 서브에이전트마다 모델과 추론 강도를 지정하거나 주 에이전트의 설정을 물려받을 수 있다고 설명한다. 실행별 설정과 호스트 제약 처리의 근거로 사용한다.
- [OpenAI: Model guidance](https://developers.openai.com/api/docs/guides/latest-model)는 중간 추론 강도를 균형점으로 삼고, 더 높은 강도는 대표 작업에서 품질 개선이 측정될 때 선택하도록 안내한다. 가장 높은 강도를 기본값으로 삼지 않는 근거로 사용한다.
- [OpenAI: Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)는 실제 작업을 반영한 평가와 담당 검수자의 판정을 이용한 보정을 권고한다. 대표 사례에서 판정 품질, 시간과 사용량을 비교하는 근거로 사용한다.
- [Claude Code: Create custom subagents](https://code.claude.com/docs/en/sub-agents)는 서브에이전트의 모델을 호출별로 지정할 수 있지만 확장 사고 설정은 주 대화에서 물려받으며 서브에이전트별로 따로 지정할 수 없다고 설명한다. 모델이나 추론 강도를 호출별로 지정할 수 없는 호스트에서는 주 에이전트 설정을 사용한 사실과 해당 제약을 결과에 기록하는 근거로 사용한다.
- [Anthropic: Effort](https://platform.claude.com/docs/en/build-with-claude/effort)는 단순하거나 응답 시간이 중요한 작업에는 낮은 추론 강도를 사용하고, 작업 난도에 따라 강도를 바꾸며 실제 사례로 검증하도록 안내한다. 검토 크기 대신 판단 난도를 기준으로 삼는 근거로 사용한다.
- [Anthropic: Choosing the right model](https://platform.claude.com/docs/en/about-claude/models/choosing-a-model)는 정확도, 응답 품질, 예외 처리와 비용을 실제 입력으로 비교한 뒤 모델을 바꾸도록 안내한다. 필요한 품질을 충족하는 가장 낮은 성능 수준을 선택하는 근거로 사용한다.
