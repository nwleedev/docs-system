# AI를 프로젝트에 활용할 때 발생하는 문제에 대한 요구사항

## AI가 누구에게 답변을 작성해야 하는지 구분하지 못하는 문제

AI를 여러 애플리케이션 개발 프로젝트, 자료 수집 프로젝트에, 문제에 대한 리서치 프로젝트에 사용하면서 다음과 같은 문제가 발생했습니다.

AI(Codex, Claude Code 등)는 AI 본인이 작성하는 글이 "작업 지시자를 위한 글인지, 애플리케이션을 사용하는 사용자를 위한 글인지, 애플리케이션 개발에 참여하는 개발자를 위한 글인지" 구분하지 못한다. 즉 작업 지시자는 "사용자를 위한 글을 작성해라"라는 프롬프트를 입력해도 AI는 프롬프트를 그대로 받아들여서 작업 지시자를 위한 글을 작성하게 된다. 예를 들어 README.md 파일에 "이 파일을 사용자를 위한 글을 작성하라는 프롬프트에 대해서 작성한 글입니다."라는 내용이 작성된다.

그래서 사용자가 직접 사용해야 하에 웹 페이지 UI가 "마치 작업 지시자에게 어떻게 구현했는지 보고하는 듯한 문구"가 적혀있는 경우가 있다. 개발자들이 보는 README.md 파일에도 "작업 지시자에게 보고하는 듯한 문구"가 적히게 된다.

### 내부 프롬프트를 그대로 문서, 코드, 커밋에 주입하는 문제

AI가 작성하는 코드, 문서, Git 커밋에 "작업 지시자가 입력한 프롬프트"를 그대로 작성하는 문제가 자주 발생합니다.

저는 프롬프트에 대해서 "작업 지시자가 무엇을 의도했는지 파악하고", 그 의도에 맞춰 필요한 작업을 파악하도록 하고 싶습니다.

다시 말해서 "이 기능을 사용하지 않는다."라는 프롬프트를 입력하면 AI는 기본적으로 "기능이 존재하지 않음을 테스트하는 테스트 코드"를 추가적으로 작성합니다. 그게 아니라 해당하는 테스트 코드를 제거해야 하는게 더 좋지 않겠냐는 의견이 존재합니다.

또는 특정 컴포넌트를 제거하라는 프롬프트를 입력하면 "컴포넌트가 존재하지 않음을 테스트하는 테스트 코드를 추가로 작성하는 것"이 아니라, 해당 컴포넌트와 관련된 테스트 코드를 제거해야 한다는 의견이 존재합니다.

## AI가 잘못된 텍스트를 사용하는 문제

AI가 텍스트나 문서를 아무렇게나 작성하도록 하면 막상 사람 입장에서 읽기 어려운 상황이 많이 발생합니다.

한국어 텍스트의 경우 한국인들이 평소에 사용하지 않는 "경계", "범위", "좁히다", "계약", "루브릭" 등의 기계적인 번역, 직역, 번역체가 자주 발생합니다.

그리고 아무런 지침이 없으면 아무런 생각 없이 "AI가 양산형으로 생산한 것 같은 텍스트나 결과"가 발생합니다.

AI가 작성하는 텍스트는 사람이 입력하기 어려운 기호(Symbol)이 작성되어있습니다.

- 대표적으로 `·`, 이모지가 있습니다.

## 요구사항

**절대 예시에 대해서만 문제 범위를 한정짓지 않습니다.**

제가 확인하고 싶은 것은 다음과 같습니다.

1. AI가 번역체, 기계적인 번역을 사용하지 못하게 하는 방법
1. AI가 "작업 지시자가 입력한 프롬프트"를 그대로 문서나 코드, 커밋에 적지 않도록 하는 방법.
1. AI가 텍스트를 작성하기 전에 "이 텍스트가 과연 해당 대상을 위한 텍스트인가" 확인할 수 있도록 하는 방법
1. AI가 폴더 및 파일 경로를 그대로 기록하지 못하게 하는 방법, 개인정보인지를 식별하고 개인정보 그대로 문서화하거나 커밋하지 못하게 하는 방법, 독자에게 필요한 저장소 상대 경로만 기록하도록 하는 방법

### 역할을 드러내는 표현

저장소에 기록되거나 외부에 공유 또는 배포되는 문구와 이름에서는 특정 역할을 `사람`으로 뭉뚱그리지 않습니다. 해당 문장의 주체나 독자에 따라 `지시자`, `작업 지시자`, `사용자`, `개발자`, `검수자`처럼 실제 역할을 알 수 있는 말을 사용합니다.

적용 대상에는 문서와 README, Git 커밋과 협업 문구, 파일명과 디렉터리명, UI와 접근성 문구, 코드 주석이 포함됩니다. `skills/use-words-review/` 아래 파일, 루트 `AGENTS.md`, `src/AGENTS.en.md`, `src/AGENTS.ko.md`, `README.md`, `README.ko.md`도 적용 대상이며, 이 목록에 있는 파일로 범위를 한정하지 않습니다.

`사람`만 적으면 작업을 요청한 쪽, 결과물을 사용하는 쪽, 개발하는 쪽, 결과를 확인하는 쪽 가운데 누구를 뜻하는지 알기 어렵습니다. 실제 개발 과정에서 책임과 승인 주체를 구분하기 어렵고 번역체처럼 읽힌다는 의견이 있었습니다.

문구를 바꿀 때에는 기존 문장이 가리키는 주체와 책임을 먼저 확인합니다. 특정 역할을 저장소에서 확인할 수 없으면 임의로 정하지 않고 확인이 필요한 항목으로 남깁니다.

일반적인 인간 전체를 뜻하는 문장에는 역할 이름을 억지로 붙이지 않습니다. 승인된 인용문이나 요구사항 원문처럼 정확한 문구를 보존해야 하는 경우에도 원문을 유지할 수 있습니다.

작업이 완료되면 다음 결과를 확인할 수 있어야 합니다.

- 적용 대상에서 특정 역할을 가리키는 `사람`이 남아 있지 않습니다.
- 바뀐 문장만 읽어도 작업을 요청하는 쪽, 결과물을 사용하는 쪽, 개발하는 쪽과 결과를 확인하는 쪽을 구분할 수 있습니다.
- 역할을 확인할 근거가 없는 문장은 임의로 바뀌지 않고 별도 확인 대상으로 보고됩니다.

요구사항 문서에 있는 문제에 대해서 실제로 유사한 이슈가 있었는지를 한번 확인해주세요.

그리고 위 문제들을 방지하기 위해서 사람들이 시도한 방법, 실제로 효과가 있었던 사례 등등, 위 문제를 대해서 리서치해주세요.

### 요구사항 문서, 개발 지침 문서 관리

docs/designs/README.md 파일을 참고하여 요구사항에 대한 설계 문서, docs/dev/README.md 파일을 토대로 개발 코드 케이스에 대한 개발 지침 문서를 작성할 수 있습니다.

각 리드미를 참고하여 어떤 파일 및 폴더 구조를 사용하는지 확인하세요.

다름이 아니라 저는 "AI가 설계, 개발 가이드 문서를 작성할 때"에도 입력받은 프롬프트를 그대로 주입하지 않도록 하고 싶습니다. 그리고 각 문서에 대해서도 프롬프트를 그대로 복사하지 않도록 하고 싶습니다.

AI가 프롬프트를 토대로 작업 지시자의 의도를 더 파악하고, 각 문서의 역할을 명확하게 하면서, 중복되는 내용이 없도록 하고 싶습니다. 문서의 역할을 명확하게 함과 동시에 작업할 때에도 하나의 문서만 사용하는 것이 아닌 여러 문서를 유기적으로 활용할 수 있도록 하고 싶습니다.

### 작업 지시 문구가 산출물의 내용과 구조를 대신하면 안 되는 경우

**작업 지시 문구 자체를 보존해야 하는 산출물이 아닌 경우, 다음과 같은 상황을 오류로 취급해야 합니다.**

1. 원문이 문서의 목적과 관계없이 본문에 들어간다.
1. 작업 지시가 제품이나 프로젝트에 관한 사실처럼 쓰인다.
1. UI, README, 코드 주석, 커밋 메시지가 작업 지시자에게 보내는 보고문으로 바뀐다.
1. 민감정보가 있는 원문이 공개 자료나 장기 보관 로그에 남는다.
1. 작업 지시 문구가 문서의 제목, 파일명이나 소제목을 대신한다.
1. 한 프롬프트에 함께 적힌 서로 다른 요구가 하나의 문서나 결정으로 묶인다.
1. 작업 지시가 결정의 근거, 현재 규칙이나 저장소에 관한 사실을 대신한다.
1. 추적하지 않는 작업 메모나 프롬프트의 내용을 추적 문서에서 다시 풀어 쓴다.
1. 내부 명령, 도구 사용 조건, 진행 보고와 실행 기록이 요구사항, 계획, 결정 문서에 섞인다.
1. 사용자에게 보이는 문구나 배포되는 API가 내부 구현 계획과 확인 목록을 전달한다.
1. 개인 계정명이 포함된 절대 경로, 로컬 첨부 위치, 비공개 프로젝트 식별자나 내부 경로가 공개 자료에 남는다.

### 프롬프트, 원문을 그대로 보존해야 하는 경우

**다음의 경우에만 프롬프트 또는 원본 텍스트를 그대로 보존시키도록 하고 싶습니다.**

1. 사람이 문구를 소유하는 요구사항 문서
1. 사람이 승인한 UI 문구나 인용문
1. 프롬프트 처리 자체를 검증하는 평가 데이터
1. 문제를 재현하기 위한 최소 입력
1. 접근 권한과 보존 기간이 정해진 비공개(커밋되지 않는) 실행 기록

### 필요한 작업 및 변경사항

요구사항에 작성된 문제점에 대응하기 위해서 무엇을 해야 하는지 리서치, 검토해주시고 진행해주세요.

우선 저는 다음에 대해서 리서치 및 검토해주세요.

1. skills/use-design-docs/SKILL.md 파일에 변경이 필요할지 파악
1. skills/use-dev-guidance/SKILL.md 파일에 변경이 필요할지 파악
1. docs/designs/README.md 파일에 변경이 필요할지 파악
1. docs/dev/README.md 파일에 변경이 필요할지 파악

그리고 이 문제에 대응하기 위해서 전용 스킬을 하나 더 세팅하는 것에 대해서도 리서치, 검토하세요.

그리고 만약 vale 설정 파일이 필요하다면 다음 위치에 작성하는 것을 검토해주세요.

```
- src
  - vale
    - <directory>/<topic>.<extension>
    - <topic>.<extension>
    - README.md
```

여기는 압축파일까지 커밋하지 않습니다. 대신 README.md 파일에서 **이 설정파일들을 어떻게 세팅할 수 있을지**에 대해서 작성하세요.

### 리뷰 에이전트

다양한 프로젝트에서 작업 사항이 발생합니다. 작업 사항을 검토할 때 범용 서브에이전트를 실행하는 스킬이 필요합니다. 이 스킬은 별도로 이름 붙인 전용 에이전트 파일을 만들지 않고, 실행할 때 범용 서브에이전트에 검토 역할과 기준을 전달해야 합니다.

references 폴더에 파일을 너무 많이 배치하면 각 파일의 정합성이 맞지 않을 수 있습니다.

```
skills/
  use-words-review/
    README.md
    SKILL.md
    references/
      examples.md
```

examples.md 파일은 리뷰 에이전트가 참고할 수 있는 예시 파일을 의미합니다.

- AGENTS.md 파일의 `**Writing Natural Korean**`의 경우 AGENTS.md 대신 examples.md 파일로 옮기는 것에 대해서 검토합니다.

README.md 파일은 "스킬에 대해서 안내", 그리고 "스킬을 AI가 적절한 시기를 파악하고 호출하기 위해서 AGENTS.md 파일에 추가해야 하는 부분 지침"에 대해서 작성합니다.

- 예를 들어 AGENTS.md 파일에 `## Documentation Work` 파트가 어떻게 작성되어있는지 확인해주세요.

### 자연스러운 문장 연결

번역체, AI가 양산한 것 같은 문장 스타일은 이제 체크가 가능한 상황에서 문장이 "그럴 듯해 보여도 막상 문장이 자연스럽게 이어지지 않아서" 이해할 수 없는 상황이 발생합니다.

문장에 번역체가 쓰였는지, AI 양산형 스타일로 작성되었는지만 파악하지 않고, 각 문장이 자연스럽게 연결되는지, 실제 작업자 및 동료가 "AI가 작성한 문장을 이해할 수 있는지" 체크할 수 있어야 합니다.

각 문장은 앞뒤 문장과의 관계뿐 아니라 그 문장만 읽어도 뜻을 이해할 수 있어야 합니다.

자연스러운 어휘와 문법을 사용했더라도 전제, 조건, 판단이나 행동을 한 문장에 여럿 압축해 필요한 설명이 빠지면 이해하기 어려운 문장으로 봅니다.

`skills/use-words-review/` 내 파일에 대해서 각 파일을 어떻게 업데이트해야 할지 리서치해주시고, 필요한 작업을 진행합니다.

### 토큰 비용

각 문장을 검토하느라 서브에이전트를 자주 호출하기 때문에 토큰 사용량이 생각보다 많이 발생합니다.

현재 use-words-review 스킬이 호출하는 서브에이전트의 모델과 추론 강도가 어떻게 되는지 파악해주세요. 그리고 "토큰 사용량을 줄이면서 성능을 최대한 유지하는 방법"을 리서치해주세요.

### 스킬에 README.md 파일 제거

`skills/use-words-review/README.md` 파일은 AGENTS.md 파일에 use-words-review를 사용하려면 어떤 문구를 추가해야 할지에 대해서 작성했습니다.

그런데 막상 README.md 파일에 백틱으로 구성된 코드블럭이 src 폴더에 있는 AGENTS 파일과 겹치는 부분이 있는 것 같다는 의견이 있었습니다.

그래서 스킬 폴더에 README.md 파일을 배치하는 대신, use-design-docs, use-dev-guidance처럼 src/AGENTS.\*.md 파일에 스킬과 관련 지침을 추가하고 싶습니다.

대신 각 스킬마다 주석 등으로 범위를 지정해서, 만약 "특정 스킬을 제거하고 싶으면 해당 주석으로 구성되는 구간의 지침만 제거해라"라는 방식으로 사용자에게 안내해야 할 것 같습니다.

관련 유사 사례가 더 있는지 리서치해주시고, use-words-review 스킬의 README.md 파일을 제거하고 src/AGENTS.\*.md 파일에 스킬 관련 지침을 추가해주세요.

### 문맥에 맞지 않는 `경로`와 `공개` 표현

`skills/use-words-review`는 번역체, AI가 양산한 것처럼 보이는 문체와 뜻이 분명하지 않은 문장을 찾아 검토 결과로 보고합니다. 결과물의 교정은 별도로 승인받은 수정 작업에서 진행합니다.

이번 문제는 `경로`라는 단어의 사용 여부가 아니라 그 단어가 가리키는 뜻을 독자가 문맥만으로 알 수 있는지입니다. 파일이나 디렉터리의 위치, URL의 구성 요소, 네트워크 패킷이 전달되는 구간처럼 정확한 기술 개념을 가리킬 때는 `경로`를 유지합니다. 방법, 절차, 선택지나 진행 순서를 구체적으로 적을 수 있는데도 이를 `경로`로 뭉뚱그리면 검토 대상으로 봅니다.

`테스트 환경 접근 경로 세팅`만으로는 연결 주소를 정한다는 뜻인지, 접속 방법을 안내한다는 뜻인지, 접근 권한을 부여하는 절차를 마련한다는 뜻인지 알 수 없습니다. 저장소 근거만으로 작성 의도를 확인할 수 없으면 임의로 고치지 않고 `needs human input`으로 판정합니다. 의도가 확인되면 실제 행동에 맞춰 `테스트 환경 접속 방법을 안내한다` 또는 `테스트 환경 접근 권한을 부여하는 절차를 마련한다`처럼 다시 씁니다.

이 저장소와 요구사항 소유자가 확인해 제공한 실제 실패 사례를 조사 시작 자료로 사용합니다. 외부 자료는 한국어 문서가 있고 인터넷으로 배포되는 소프트웨어 저장소, 작성자가 AI 사용 사실을 밝혔거나 생성 과정을 확인할 수 있는 자료, 정확한 기술 용례를 확인할 수 있는 공식 문서로 나눠 조사합니다. 조사에 사용한 검색어와 확인 날짜, 자료의 포함 및 제외 기준과 출처 목록을 기록해 다른 검수자가 기록된 조사 범위를 다시 확인할 수 있게 합니다. AI 작성 여부가 확인되지 않은 자료는 AI 문체의 근거로 단정하지 않습니다. 각 후보 표현은 다음 내용을 함께 기록합니다.

- 표현이 쓰인 문맥과 출처
- 독자가 대상, 행동, 조건이나 결과를 알기 어려운 이유
- 같은 표현이 정확한 기술 용어로 쓰인 정상 사례
- 작성 의도를 확인할 수 있을 때 가능한 구체적인 문장
- 조사 자료와 판단 방법의 한계

`공개`도 일괄적으로 금지하지 않습니다. 실제 한국어 공식 문서에서 용례를 조사하고, 암호 기술 용어인 `공개 키`, 법률에 따른 정보 제공을 뜻하는 `정보공개`처럼 고유한 상태, 기술 개념이나 행위를 구분할 때만 `공개`라는 표현을 사용합니다. `공개 저장소`는 제품의 저장소 표시 유형이나 보안 규칙에서 별도의 읽기 권한 없이 누구나 내용을 볼 수 있는 상태를 그 이름으로 구분할 때만 유지합니다. 인터넷에서 배포되는 소프트웨어 저장소를 통칭할 때는 `인터넷으로 배포되는 소프트웨어 저장소`처럼 독자가 확인해야 할 상태를 구체적으로 적습니다.

`공개 API`와 `공개 미리 보기`는 제공 기관의 한국어 문서가 해당 명칭을 사용한다는 이유만으로 허용하지 않습니다. `공개 API`는 호출할 수 있는 대상과 인증 조건을 문서에서 확인할 수 있어야 합니다. `공개 미리 보기`는 참여할 수 있는 대상과 정식 출시 전 적용되는 조건을 문서에서 확인할 수 있어야 합니다.

단순히 인터넷에서 찾을 수 있거나 배포됐다는 뜻이라면 `인터넷으로 배포되는`, `누구나 읽을 수 있는`, `외부에서 호출할 수 있는`처럼 실제 상태를 적습니다. 조사 결과에는 `공개`를 유지할 사례와 바꿔야 할 사례, 판단 근거가 된 한국어 문서의 문맥과 출처를 함께 기록합니다.

단어의 출현 빈도만으로 문제 표현을 정하지 않습니다. 새 자료를 추가로 확인해도 새로운 문제 유형이나 판정 기준이 나오지 않으면 조사를 중단합니다.

조사가 끝나면 요구사항 소유자가 확인한 문제 사례와 정상 사례로 변경 결과를 검증합니다. 문제 사례를 놓치거나 정상 사례를 잘못 지적하거나 작성 의도를 확인할 수 없는 문제 사례를 `needs human input`으로 남기지 못하면 완료로 판정하지 않습니다.

이번 요구사항은 `경로`와 `공개` 표현을 판정하는 기준과 조사 방법에만 적용합니다. 기존 문장 연결 검토 기준, 서브에이전트 모델 선택과 스킬 배포 방식은 변경하지 않습니다.
