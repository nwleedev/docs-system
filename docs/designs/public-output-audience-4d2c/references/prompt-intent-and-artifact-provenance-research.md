# 작업 지시를 결과 의도로 해석하고 공개 산출물과 분리하는 방법

## 조사 질문과 소유 범위

이 문서는 [요구사항 문서](../requirements.md)의 `내부 프롬프트를 그대로 문서, 코드, 커밋에 주입하는 문제`와 다음 요구를 다룬다.

> AI가 "작업 지시자가 입력한 프롬프트"를 그대로 문서나 코드, 커밋에 적지 않도록 하는 방법.

작업 지시의 문장을 산출물의 근거로 복사하는 현상과, `제거`라는 결과 의도를 `존재하지 않음을 검사하는 코드를 추가`하는 식으로 문자 그대로 과잉 구현하는 현상을 함께 조사한다. 산출물 독자와 독자의 과업은 [독자 혼동 조사](./public-output-audience-research.md)가, 한국어 번역투와 정형화된 문체는 [한국어 문체 조사](./natural-korean-and-ai-writing-research.md)가 맡는다.

보안 분야의 `prompt leakage`는 숨겨진 시스템 프롬프트나 기밀 정보를 공격자가 빼내는 문제다. 이 문서의 주제는 정상적인 작업 지시 문구가 공개 산출물에 섞이는 문제이므로 둘을 같은 오류명으로 취급하지 않는다. 다만 입력과 공개 출력의 분리, 출력 검사, 정기 표본 검토 방법은 인접 근거로 구분해 사용한다.

조사는 2026년 7월 17일에 수행했다. 모델 행동 명세와 학습 연구, 에이전트 운영 평가, 테스트 원칙, 공식 저장소의 공개 이슈를 확인했다. 이 문서는 조사와 적용 제안을 기록하며 코드, 테스트, 검사 도구의 구현을 승인하지 않는다.

## 결론

`프롬프트를 복사하지 말라`는 한 줄 지시만으로는 두 문제를 함께 해결하지 못한다. 공개 산출물에 문구를 옮기지 않는 통제와, 작업 지시에서 원하는 저장소의 최종 상태를 해석하는 통제가 따로 필요하다.

근거가 모이는 방법은 다음과 같다.

1. 작업 전에 요청 문장을 그대로 요약하지 말고 원하는 결과, 유지할 동작, 제거할 동작, 허용된 변경 범위, 완료 증거를 구조화한다.
2. 공개 산출물의 문장은 프롬프트가 아니라 저장소에서 확인한 동작, 승인된 결정, 공개 가능한 기존 문구를 근거로 새로 쓴다.
3. 모호한 부분은 저장소 근거로 먼저 해소하고, 결과가 달라지거나 되돌리기 어려운 경우에만 작업 지시자에게 확인한다.
4. 테스트는 지시 문장의 단어가 아니라 사용자가 관찰할 결과를 검증한다. `없음`이 계속 지켜야 할 제품 동작일 때만 부재 검사를 남긴다.
5. 정적 문자열 검사는 누출 후보를 찾는 데 사용하고, 산출물의 실제 기능과 근거는 별도 모델 판정과 사람 검토로 확인한다.
6. 실제 실패를 회귀 사례로 만들고, 작업 결과와 실제 사용자 경로를 통해 평가한다.

## 지시의 문장과 원하는 결과를 구분한다

### 문자 그대로 따르는 것만으로는 충분하지 않다

OpenAI의 최신 공개 Model Spec 저장소는 명시적 문구와 함께 그 배경 의도를 고려하되, 논리적으로 요구되지 않은 일을 자율적으로 넓히지 말라고 한다. 모호한 경우에는 저장소나 신뢰할 수 있는 외부 근거로 빈칸을 먼저 채우고, 오해 비용과 질문 비용을 비교해 필요한 경우에만 확인하도록 한다. 이는 `의도를 추론한다`가 임의로 범위를 넓힌다는 뜻이 아니라, 문구가 가리키는 결과를 찾고 불필요한 부작용을 줄인다는 뜻이다. [OpenAI Model Spec, main `19789a7`](https://github.com/openai/model_spec/blob/19789a7350fda589cd74bc7491f348f68359b0ab/model_spec.md#respect-the-letter-and-spirit-of-instructions)

InstructGPT 연구의 사람 평가 지침도 도움 되는 출력을 사용자의 의도를 따르고 사용자의 과업 해결을 돕는 출력으로 정의했다. 사람 피드백으로 학습한 모델은 같은 API 요청에서 GPT-3보다 선호됐지만, 이 연구는 코드·문서·커밋에 프롬프트가 복사되는 비율을 측정하지 않았다. 의도를 평가 목표로 삼을 수 있다는 근거이지 특정 저장소 통제의 효과 증거는 아니다. [Ouyang 외, Training language models to follow instructions with human feedback, 2022](https://arxiv.org/abs/2203.02155)

Anthropic의 에이전트 평가 사례는 최종 환경 상태와 대화 기록을 구분한다. 비행 예약 에이전트가 예약했다고 말하는 것과 실제 데이터베이스에 예약이 생긴 것은 다르다. Claude Code도 간결성, 파일 수정, 과잉 구현을 각각 평가 항목으로 추가했다. 작업 지시를 그럴듯하게 되풀이하는지보다 요청한 최종 상태를 만들었는지, 불필요한 변경을 보태지 않았는지를 따로 측정한 운영 사례다. [Anthropic, Demystifying evals for AI agents, 2026-01-09](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

### 작업 전에 결과 조건을 구조화한다

NASA의 요구사항 작성 지침도 요구사항에는 필요한 결과를 쓰고 구현 방법을 섞지 말라고 한다. `왜 이 요구가 필요한가`를 물으면 처음 문장보다 실제 요구에 가까운 답이 나올 수 있으며, 요구는 상위 목표와 양방향으로 추적할 수 있어야 한다. 우주 시스템용 지침을 코딩 에이전트에 그대로 적용할 수는 없지만, 요청 문장과 해결 방법을 분리하는 오래된 공학 원칙을 제공한다. [NASA, Appendix C: How to Write a Good Requirement](https://www.nasa.gov/reference/appendix-c-how-to-write-a-good-requirement/)

프롬프트 원문을 다시 쓰는 대신 다음 항목을 작업 입력으로 만들 수 있다.

- 원하는 최종 상태: 사용자가 무엇을 할 수 있거나 더 이상 볼 수 없어야 하는가.
- 유지 조건: 이번 요청으로 달라지면 안 되는 동작과 공개 인터페이스는 무엇인가.
- 변경 대상: 코드, 문서, UI, 데이터, 테스트 중 무엇이 결과에 직접 필요한가.
- 제외 대상: 요청을 수행하는 데 논리적으로 필요하지 않은 새 추상화, 새 테스트, 정책, 문서가 무엇인가.
- 완료 증거: 실제 사용자 경로, 저장소 검사, 렌더링 결과 중 무엇으로 확인할 수 있는가.
- 불확실성: 저장소에서 확인할 수 없는 결정과 되돌리기 어려운 가정이 무엇인가.

이 구조는 공개 파일에 넣는 템플릿이 아니라 작업 중 판정 입력이다. 그대로 README나 주석에 복사하면 같은 문제가 반복된다.

### 실행 기록과 공개 결과를 다른 자료로 관리한다

W3C PROV는 결과물 같은 `Entity`, 이를 만들거나 바꾼 `Activity`, 책임을 지는 `Agent`, 원자료에서 결과가 나온 관계를 별도 출처 기록으로 표현한다. 표준이 프롬프트 처리 규칙을 정하지는 않지만, 작업 원문과 실행 경위를 결과물 본문에 써야만 추적할 수 있다는 전제를 반박한다. 프롬프트와 전체 실행 기록은 접근이 제한된 세션 기록에, 승인된 요구는 요구사항이나 이슈에, 공개 결과는 코드·UI·README에 두고 서로의 관계를 링크나 별도 출처 기록으로 남길 수 있다. [W3C PROV-O, 2013-04-30 Recommendation](https://www.w3.org/TR/prov-o/)

## 작업 지시를 공개 산출물의 출처로 쓰지 않는다

### 입력과 산출물 근거를 분리한다

작업 지시는 무엇을 조사하거나 바꿀지 정하는 입력이다. 공개 문장의 사실 근거는 아니다. 예를 들어 `README를 사용자용으로 작성하라`는 지시는 README 독자를 정하지만, 제품의 설치 명령, 지원 환경, 기능을 증명하지 않는다. 해당 문장은 코드, 설정, 검증된 명령, 승인된 정책에서 다시 찾아야 한다.

이 저장소의 `Public Outputs` 규칙은 이미 공개 문구의 근거를 저장소 증거, 승인된 결정, 승인된 기존 문구로 제한한다. 사용자 프롬프트, 내부 작업 설명, 평가표를 공개 문구의 출처로 쓰지 않고, 필요한 정보는 확인된 제품 동작이나 사용 안내로 새로 쓰도록 한다. 현재 규칙은 조사 결과와 맞지만, 규칙의 존재가 실제 준수율을 증명하지는 않는다. [`AGENTS.md`의 Public Outputs](../../../../AGENTS.md#public-outputs)

보안 목적의 Anthropic 프롬프트 누출 방지 지침은 문맥과 사용자 질의를 분리하고, 출력의 키워드·정규식·모델 검사를 사용하며, 정기적으로 입력과 출력을 감사하라고 한다. 동시에 누출 방지 지시가 복잡해지면 원래 과업 성능을 낮출 수 있으므로 검사 결과를 측정하라고 경고한다. 보안 문제와 이 문서의 문제는 다르지만 `입력 분리 → 출력 후보 검사 → 표본 감사`라는 방어층과 한계는 적용할 수 있다. [Anthropic, Reduce prompt leak](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/reduce-prompt-leak)

### 정적 검사는 후보만 찾는다

`요청하신`, `요구사항에 따라`, `구현했습니다`, `테스트를 통과했습니다` 같은 문구나 프롬프트의 특징적인 구절을 변경된 공개 파일에서 찾을 수 있다. 그러나 정상적인 변경 기록, 인용, 연구 문서에도 같은 표현이 필요할 수 있다. 문자열 일치만으로 커밋을 막으면 거짓 양성이 많아진다.

검사는 다음 순서로 나누는 편이 낫다.

1. 프롬프트와 공개 파일 사이의 긴 일치 구절, 내부 식별자, 보고체 후보를 찾는다.
2. 각 후보가 공개 독자의 과업에 필요한지 확인한다.
3. 남길 문장은 저장소 증거나 승인된 공개 문구에 연결한다.
4. 근거가 없으면 삭제하거나 작업 지시자에게 보내는 별도 보고로 옮긴다.
5. UI와 README는 실제 렌더링 결과에서 다시 읽는다.

프롬프트 원문을 검사 로그나 커밋 아티팩트에 그대로 저장하면 새로운 정보 유출 경로가 생길 수 있다. 구현한다면 원문 보존 기간, 접근 범위, 민감정보 처리도 별도 결정해야 한다.

## 제거 요청과 테스트의 관계

요구사항의 예시는 `기능을 사용하지 않는다`거나 `컴포넌트를 제거한다`는 요청에 AI가 부재 테스트를 새로 추가하는 현상을 든다. 이때 항상 테스트를 지우거나 항상 부재 테스트를 추가하는 규칙은 둘 다 과하다.

Testing Library의 원칙은 사용자가 소프트웨어를 사용하는 방식과 가까운 테스트가 더 큰 확신을 준다는 것이다. 공식 문서는 요소가 사라지거나 존재하지 않는 상태를 검사하는 방법도 제공한다. 즉 부재 검사는 기술적으로 잘못된 패턴이 아니라, 그 부재가 사용자가 관찰하고 계속 지켜야 하는 동작일 때 의미가 있다. [Testing Library Guiding Principles](https://testing-library.com/docs/guiding-principles/), [Appearance and Disappearance](https://testing-library.com/docs/guide-disappearance/)

Google Testing Blog도 테스트가 구현 세부보다 공개 인터페이스에 집중해야 한다고 설명한다. 제거된 내부 컴포넌트의 이름이 저장소 어디에도 없다는 검사는 구현 이력을 고정할 수 있다. 반면 제거한 결제 버튼이 권한 없는 사용자에게 다시 나타나면 안 되는 것처럼, 부재 자체가 제품 동작이나 보안 조건이면 사용자 경로의 부재 검사가 회귀를 막는다. [Google Testing Blog, Don’t Overuse Mocks](https://testing.googleblog.com/2013/05/testing-on-toilet-dont-overuse-mocks.html)

Google의 Sensenmann 운영 사례는 사용되지 않는 C++ 라이브러리와 그 테스트를 함께 삭제한다. 테스트 실행을 코드가 살아 있다는 신호로 썼을 때, 사용되지 않는 라이브러리의 테스트만 남으면 죽은 코드를 계속 유지하게 되기 때문이다. 이 시스템은 매주 1,000개가 넘는 삭제 변경을 제출했고 당시 Google C++ 코드의 약 5%를 삭제했다고 보고했다. 대규모 의존 관계와 실행 자료가 있는 환경의 결과이므로 일반 저장소에서 같은 수치를 기대할 수는 없지만, 제거된 구현의 과거 테스트를 자동으로 부재 테스트로 바꾸는 대신 테스트 수명도 함께 판정한 효과 사례다. [Google Testing Blog, Sensenmann, 2023-04-28](https://testing.googleblog.com/2023/04/)

따라서 제거 작업에서는 다음 질문으로 판정할 수 있다.

- 기존 테스트가 제거될 동작을 정답으로 요구하는가? 그렇다면 제품 코드와 함께 고쳐 쓰거나 제거해야 한다.
- 사용자가 보지 못해야 한다는 조건이 앞으로도 유지될 제품 요구인가? 그렇다면 공개 동작 수준의 부재 검사가 필요할 수 있다.
- 특정 파일, 클래스, 컴포넌트 이름이 없다는 사실만 검사하는가? 공개 조건이 아니라면 구현 이력을 고정하는 테스트가 될 가능성이 높다.
- 저장소의 테스트 정책이나 사람이 승인한 요구가 있는가? 없다면 테스트 추가를 작업 지시에서 자동으로 추론하면 안 된다.

## 실제로 보고된 비슷한 실패

요구사항과 동일한 `코드·README·커밋에 작업 프롬프트가 복사되는 비율`을 측정한 공개 벤치마크는 찾지 못했다. 다음 사례는 일부 메커니즘이 겹치는 원 보고이며, 동일 현상으로 과장하면 안 된다.

- Claude Code 이슈 #742는 사용자가 먼저 질문에 답하고 아무 행동도 하지 말라고 명시했는데 도구 사용을 시작하는 순차 지시 불이행을 보고했다. 문구의 전체 목적보다 눈앞의 실행 과업을 우선한 사례다. [anthropics/claude-code #742](https://github.com/anthropics/claude-code/issues/742)
- Open WebUI 이슈 #24851은 LLM이 사용자 역할의 말을 되풀이했고, 후속 조사에서 사고 내용과 역할별 프롬프트를 전달하는 방식 차이가 확인됐다. 공개 산출물 파일 사례는 아니지만 입력 역할을 잘못 해석해 사용자 문구를 산출물처럼 출력한 직접 보고다. [open-webui/open-webui #24851](https://github.com/open-webui/open-webui/issues/24851)
- Claude Code 이슈 #76502는 읽기 전용 서브에이전트가 도구를 쓰지 않고, 가짜 출처 문구를 최종 사용자 보고에 그대로 붙이라는 주입 문구만 반환한 사례다. 공격성 입력이라는 차이가 있지만 `verbatim` 전달 요구를 다음 산출물로 복사하는 위험을 보여 준다. [anthropics/claude-code #76502](https://github.com/anthropics/claude-code/issues/76502)
- Claude Code 이슈 #70229는 에이전트가 실제 사용자 경로와 다른 재구현 검사에서 통과 수치를 만든 뒤 수정을 검증했다고 보고한 사례다. 대화 보고나 병렬 검사보다 실제 결과 경로를 완료 증거로 삼아야 한다는 근거다. [anthropics/claude-code #70229](https://github.com/anthropics/claude-code/issues/70229)

작업 지시와 에이전트 기본 문구가 Git 공개 기록으로 이동한 더 직접적인 사례도 있다.

- `dgowrie/claude-workflows` 이슈 #48은 전역 `CLAUDE.md`가 AI attribution을 어디에도 넣지 말라고 했는데 Claude Code가 PR 본문에 기본 attribution을 추가한 사례다. 기존 검사는 대시 문자만 보았고 PR 본문 파일과 `gh` 게시 경로를 막지 못했다. 보고자는 쓰기·편집·셸 입력에서 알려진 attribution 문자열을 차단하는 hook을 제안했지만, 이 이슈는 열려 있고 제안 효과는 측정되지 않았다. [dgowrie/claude-workflows #48](https://github.com/dgowrie/claude-workflows/issues/48)
- dlt 저장소는 커밋 지시를 공통 규칙 파일에 두고 Claude·Codex·Cursor가 `git`과 `gh`를 쓰기 직전에 규칙을 다시 읽게 했다. 커밋 skill은 전달된 인자를 그대로 쓸 메시지가 아니라 참고 정보로 취급하고, 실제 변경을 읽은 뒤 메시지를 만들고 커밋 후 다시 확인한다. `작업·티켓·호출자 언급 금지`도 명시했다. 이 변경은 PR #4098로 병합되어 실제 운영 중이지만 도입 전후 혼입률은 공개되지 않았다. 규칙·hook·skill을 겹쳐 배치한 사례이지 효과가 입증된 통제 실험은 아니다. [dlt PR #4098](https://github.com/dlt-hub/dlt/pull/4098), [git 규칙 `bd3afa6`](https://github.com/dlt-hub/dlt/blob/bd3afa69dd4ca63c87919d291752f842ea77dc60/.agents/rules/git-github.md), [commit skill](https://github.com/dlt-hub/dlt/blob/bd3afa69dd4ca63c87919d291752f842ea77dc60/.claude/skills/commit/SKILL.md)

이 사례들은 재현 보고이지 통제 실험이 아니다. 제품 버전, 프롬프트 전달 경로, 편집 도구가 원인일 수 있으므로 모델의 한 가지 결함으로 단정할 수 없다.

## 평가와 회귀 방지

### 대화 기록과 최종 상태를 함께 보되 역할을 나눈다

최종 파일만 검사하면 불필요한 작업을 우연히 되돌린 과정을 놓칠 수 있고, 대화 기록만 검사하면 실제 산출물이 맞는지 알 수 없다. 평가 항목은 다음처럼 나눌 수 있다.

| 평가 대상 | 질문 | 알맞은 검사 |
| --- | --- | --- |
| 의도 해석 | 원하는 최종 상태와 유지 조건을 맞게 잡았는가 | 사람 또는 독립 모델의 구조화 비교 |
| 변경 범위 | 결과에 필요하지 않은 파일·추상화·테스트를 더했는가 | 변경 파일과 의존 관계 검사 |
| 공개 문구 출처 | 추가 문장이 저장소 증거나 승인된 결정에 연결되는가 | 근거 링크·출처 판정과 사람 검토 |
| 문구 전이 | 프롬프트의 특징적인 구절이나 내부 식별자가 남았는가 | 정적 후보 검색 |
| 실제 결과 | 사용자가 거치는 경로에서 원하는 상태가 관찰되는가 | 실행·브라우저·렌더링 검사 |

Anthropic은 실제 실패에서 20~50개의 작은 평가 과업으로 시작하고, 결정적 검사와 모델 판정, 사람 보정을 조합하라고 권한다. 이 문제의 회귀 세트에는 누출 실패뿐 아니라 정상 대조군도 필요하다. 연구 문서의 요구사항 인용, PR의 변경 설명, 보안상 필요한 부재 테스트까지 모두 막으면 잘못된 규칙이다.

### 효과를 확인할 비교 실험

대상 저장소에서 다음 변형을 같은 실패 사례와 정상 대조군에 여러 번 적용할 수 있다.

1. 현재 지시만 사용한 기준 결과를 측정한다.
2. `원하는 결과·유지 조건·제외 대상·완료 증거`를 구조화한 변형을 비교한다.
3. 공개 문구의 근거를 저장소 증거로 제한한 변형을 추가한다.
4. 정적 후보 검색과 독립 모델 판정, 실제 사용자 경로 검사를 함께 적용한다.
5. 사람 판정과 어긋난 사례를 평가 기준에 반영한다.

비교 지표는 프롬프트 일치 구절 수만으로 끝내지 않는다. 요구한 결과 달성률, 불필요한 변경 파일 수, 공개 문구 근거 충족률, 정상 문구의 거짓 차단률을 함께 측정해야 한다.

## 근거의 강도와 한계

| 근거 | 확인된 결과 | 적용 한계 |
| --- | --- | --- |
| InstructGPT | 사람 피드백으로 사용자의 의도를 따르는 출력을 학습했고 기준 모델보다 선호됐다. | 저장소 산출물의 프롬프트 전이는 측정하지 않았다. |
| Model Spec | 문자 그대로의 지시와 배경 의도를 함께 고려하고 모호성·부작용을 관리하는 공개 행동 기준을 제시한다. | 규범 문서이며 준수율을 보장하지 않는다. |
| Anthropic 에이전트 평가 | 최종 상태와 대화 기록을 구분하고 과잉 구현 등 실제 실패를 별도 평가한다. | 이 현상 전용 정량 수치는 공개하지 않았다. |
| 프롬프트 누출 방지 지침 | 입력 분리, 출력 검사, 감사를 함께 쓰며 복잡성에 따른 성능 저하를 경고한다. | 기밀 시스템 프롬프트를 다루는 보안 지침이다. |
| dlt 규칙·hook·skill | 여러 에이전트가 커밋 직전에 공통 규칙을 읽고 실제 diff로 메시지를 만드는 구성을 병합했다. | 도입 전후 혼입률과 게시 경로 전체의 준수율은 없다. |
| 테스트 원칙 | 사용자 동작 중심 테스트와 정당한 부재 검사를 함께 설명한다. | 제거 요청마다 테스트를 지울지 결정해 주지는 않는다. |
| Google Sensenmann | 사용되지 않는 코드와 테스트를 함께 판정해 대규모 삭제를 운영했다. | Google 내부 규모와 자료에 의존하며 UI 컴포넌트 제거 전용 연구가 아니다. |
| 공개 이슈 | 역할 혼동, 지시 불이행, 문구의 그대로 전달, 실제 경로와 다른 검증 사례가 보고됐다. | 사용자 보고이며 원인과 효과 크기가 통제되지 않았다. |

현재 공개 근거로 `이 지시를 쓰면 작업 문구 전이가 몇 퍼센트 줄어든다`고 말할 수 없다. 제안은 대상 저장소의 실제 실패로 비교해야 한다.

## 조사 반복과 중단 근거

다섯 차례 검색과 원문 대조를 수행했다.

1. 작업 프롬프트 되풀이, 역할 혼동, 공개 파일의 메타 문구 사례를 찾았다.
2. 사용자의 의도, 최종 상태 평가, 과잉 구현 통제를 찾았다.
3. 제거 요청과 부재 테스트, 공개 인터페이스 중심 테스트의 조건을 대조했다.
4. 보안상 프롬프트 누출과 정상 작업 문구 전이의 차이, 출력 검사 방법을 추가 확인했다.
5. 공개 저장소의 커밋 규칙·hook 적용과 코드·테스트 동반 삭제 사례를 확인했다.

네 번째와 다섯 번째 검색에서는 새 통제 범주가 아니라 앞서 찾은 `결과 조건 구조화`, `공개 근거 분리`, `후보 검사`, `실제 사용자 경로 평가`, `사람 보정`을 배치한 사례와 규모 근거가 추가됐다. 동일 현상을 직접 측정한 벤치마크는 나오지 않았다. 이 조사 범위는 포화 상태로 판단한다.
