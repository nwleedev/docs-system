# 개인정보와 민감한 원문을 필요한 범위에서만 보존하는 방법

## 조사 질문과 소유 범위

이 문서는 [요구사항 문서](../requirements.md)의 다음 요구와 오류를 조사한다.

> AI가 폴더 및 파일 경로를 그대로 기록하지 못하게 하는 방법, 개인정보인지를 식별하고 개인정보 그대로 문서화하거나 커밋하지 못하게 하는 방법, 독자에게 필요한 저장소 상대 경로만 기록하도록 하는 방법

> 개인 계정명이 포함된 절대 경로, 로컬 첨부 위치, 비공개 프로젝트 식별자나 내부 경로가 공개 자료에 남는다.

또한 요구사항의 `프롬프트, 원문을 그대로 보존해야 하는 경우`에 적힌 다섯 가지 예외가 언제 정당한지 조사한다. 이 문서는 개인정보·비공개 식별자·경로의 분류, 최소 보존, 접근권한, 보존기간, 삭제를 맡는다. 작업 지시와 독자에게 전달할 글과 문구의 출처 분리는 [작업 의도와 산출물 출처 조사](./prompt-intent-and-artifact-provenance-research.md)가, 제목과 결정 단위는 [결정 기록 범위 조사](./decision-record-scope-and-title-research.md)가 맡는다.

조사는 2026년 7월 17일에 수행했다. NIST와 W3C의 개인정보·최소 수집 지침, AI 공급자의 데이터 보존 문서, OpenTelemetry의 생성형 AI 기록 사례, GitHub의 민감정보 제거 지침과 검사 기능, 오픈 소스 개인정보 탐지 도구를 확인했다. 이 문서는 법률 자문이나 보존 정책의 승인 기록이 아니다.

## 결론

절대 경로가 언제나 개인정보인 것은 아니다. 경로에 포함된 계정명이나 프로젝트명이 특정 사람 또는 비공개 조직과 연결되는지, 독자가 그 값을 알아야 하는지, 외부에 알려진 뒤 되돌릴 수 있는지를 함께 봐야 한다. 개인과 연결되지 않는 임의 계정명도 환경 구조를 드러낼 수 있고, 비공개 프로젝트명과 내부 서버 경로는 개인정보가 아니더라도 기밀 정보일 수 있다.

따라서 `절대 경로 금지`만으로 끝내지 않고 다음 순서를 적용해야 한다.

1. 독자에게 전달할 글이나 문구에 그 값이 필요한 목적을 확인한다.
2. 개인 식별 가능성, 조직 기밀성, 자격 증명 여부를 각각 분류한다.
3. 저장소 상대 경로, 자리표시자, 합성 값으로 목적을 달성할 수 있는지 먼저 확인한다.
4. 원문이 꼭 필요하면 접근권한과 보존기간, 삭제 방법, 외부 서비스의 보존 조건을 정한다.
5. 커밋 전 검사와 사람 검토를 거치고, 삭제 뒤에는 복제본과 파생 자료까지 확인한다.

요구사항에 적힌 원문 보존 예외도 자동 허용 목록이 아니다. 각 예외 안에서 정확한 문구가 필요한 이유와 최소 범위를 다시 확인해야 한다.

## 경로와 식별자를 분류하는 기준

NIST SP 800-122는 개인정보를 단독 또는 다른 정보와 결합해 개인의 신원과 연결할 수 있는 정보로 본다. NIST의 디지털 신원 지침 FAQ는 사용자명이 사람을 식별하는 정보와 연결되면 개인정보지만, 임의로 부여되어 사람과 연결되지 않는 사용자명은 그렇지 않을 수 있다고 설명한다. 따라서 경로의 문자열 모양만으로 개인정보 여부를 확정할 수 없다. [NIST SP 800-122](https://csrc.nist.gov/pubs/sp/800/122/final), [NIST SP 800-63 FAQ](https://pages.nist.gov/800-63-FAQ/)

커밋하거나 공유하기 전에는 적어도 다음 범주를 따로 판정해야 한다.

| 값의 종류 | 주된 위험 | 기본 처리 |
| --- | --- | --- |
| 개인 계정명과 연결된 로컬 절대 경로 | 개인 식별과 작업 환경 정보가 드러남 | 저장소 상대 경로나 역할 중심 자리표시자로 바꾼다. |
| 임의 계정명이나 임시 경로 | 환경 구조가 드러나고 위치를 재현할 수 없음 | 독자에게 필요하지 않으면 생략하고 상대 경로를 쓴다. |
| 비공개 프로젝트명·내부 서버·조직 경로 | 조직 기밀과 공격에 활용될 정보가 드러남 | 공유할 자료에서 제거하고 외부 사용을 승인받은 명칭만 쓴다. |
| 공개 저장소의 상대 경로 | 독자가 파일을 찾는 데 필요한 위치 | 현재 구조에서 확인한 경로만 기록한다. |
| 토큰·키·암호·세션 값 | 계정이나 시스템 접근 | 외부에 노출되지 않도록 하고, 이미 노출됐다면 먼저 폐기하거나 교체한다. |

W3C Privacy Principles는 사용자가 원하는 결과에 필요한 데이터만 전달하고, API도 필요한 세분성을 제공해야 한다고 설명한다. 환경과 설정처럼 부수적으로 수집한 정보도 사람을 다시 알아보는 데 쓰일 수 있다고 경고한다. 독자가 파일을 찾는 데 저장소 상대 경로로 충분하다면 로컬 절대 경로를 보존할 이유가 없다. [W3C Privacy Principles](https://www.w3.org/TR/privacy-principles/)

## 원문을 그대로 보존할 수 있는 조건

원문 보존은 다음 질문을 모두 통과해야 한다.

- 목적: 문구를 그대로 보존해야만 확인할 수 있는 결과가 있는가.
- 필요성: 요약, 자리표시자, 합성 입력, 일관된 가명 값으로 같은 목적을 달성할 수 없는가.
- 범위: 실패나 승인을 증명하는 최소 구절만 남겼는가.
- 접근: 원문을 볼 수 있는 사람과 시스템이 정해져 있는가.
- 보존: 만료 시점과 삭제 책임, 백업·파생 자료의 처리가 정해져 있는가.
- 외부 처리: 모델 공급자, 평가 도구, 로그 저장소 같은 제3자의 보존·학습·삭제 조건을 확인했는가.

요구사항에 적힌 예외는 다음처럼 해석할 수 있다.

| 보존 사례 | 원문이 필요한 때 | 제한 |
| --- | --- | --- |
| 사람이 문구를 소유하는 요구사항 | 사람의 의도와 표현 자체가 기준일 때 | 요구사항에 포함된 제3자의 개인정보나 비공개 정보까지 다른 사람과 공유하도록 승인한 것은 아니다. |
| 사람이 승인한 UI 문구나 인용문 | 승인된 표현이나 인용 정확성을 검증할 때 | 승인된 문자열만 보존하며 그 문구를 만들게 한 전체 작업 지시는 제외한다. |
| 프롬프트 처리 평가 데이터 | 정확한 표현 변화가 평가 대상일 때 | 의미가 같은 합성·비식별 입력으로 평가할 수 있으면 원문을 쓰지 않는다. |
| 최소 재현 입력 | 특정 문자나 표현이 실패 원인일 때 | 원인과 관계없는 이름·경로·본문은 자리표시자로 바꾼다. |
| 비공개 실행 기록 | 진단과 감사에 원문이 꼭 필요할 때 | 기본은 내용 미수집이며, 접근통제·암호화·만료·삭제가 정해진 경우에만 켠다. |

가명 처리와 해시는 언제나 익명화를 뜻하지 않는다. NIST SP 800-188은 비식별 처리의 재식별 위험을 평가하고 관리해야 한다고 설명한다. 같은 가명으로 여러 기록을 연결할 수 있거나 원본 후보가 좁으면 다시 개인과 연결될 수 있다. 암호화는 접근 위험을 낮추지만 복호화 가능한 원문을 계속 보존하는 방식이다. [NIST SP 800-188](https://csrc.nist.gov/pubs/sp/800/188/final)

## 실행 기록은 내용 수집을 기본값으로 두지 않는다

OpenTelemetry의 2026년 생성형 AI 관측 사례는 모델명, 토큰 수, 지연 시간 같은 메타데이터를 기본으로 수집하고, 프롬프트·응답·도구 인자는 민감한 내용을 포함할 수 있어 별도 선택을 해야만 수집하는 구성을 보여 준다. 원문이 디버깅에 유용하다는 이유만으로 모든 실행에서 저장하지 않는 실제 설계 사례다. [OpenTelemetry, Inside the LLM Call](https://opentelemetry.io/blog/2026/genai-observability/)

비공개 기록도 서비스 설정에 따라 보존 기간이 달라진다. OpenAI API 데이터 제어 문서는 기본 악용 방지 로그에 프롬프트와 응답이 포함될 수 있고 기본적으로 최대 30일 보존될 수 있으며, 기능별 애플리케이션 상태와 외부 MCP의 정책이 따로 적용된다고 설명한다. Anthropic도 기능과 계약에 따라 보존 기간과 제로 데이터 보존 적용 범위가 다르고, 상태를 보존하는 기능과 제3자 통합은 별도 조건을 갖는다고 밝힌다. 두 문서는 계속 바뀔 수 있으므로 도구 이름만 보고 비공개라고 가정하지 말고 실행 시점의 설정을 확인해야 한다. [OpenAI API data controls](https://platform.openai.com/docs/guides/your-data), [Anthropic data retention](https://privacy.claude.com/en/articles/7996866-how-long-do-you-store-my-organization-s-data)

## 검사 도구가 맡을 수 있는 범위

GitHub secret scanning은 알려진 비밀 형식과 조직이 정의한 사용자 지정 패턴을 찾고, 사용자 지정 패턴을 알림 없이 시험 실행할 수 있다. 그러나 비밀 탐지는 사람 이름, 로컬 경로, 비공개 프로젝트명을 모두 판정하는 개인정보 검사기가 아니다. 정규식은 정상 경로를 잘못 잡거나 변형된 식별자를 놓칠 수 있으므로 후보 탐지로만 써야 한다. [GitHub custom patterns](https://docs.github.com/en/code-security/reference/secret-security/custom-patterns), [GitHub managing custom patterns](https://docs.github.com/en/code-security/how-tos/secure-your-secrets/customize-leak-detection/manage-custom-patterns)

Microsoft Presidio는 이름, 전화번호, 계정 같은 개인정보 후보를 탐지·익명화하는 오픈 소스 도구지만, 공식 저장소도 모든 민감정보를 찾는다고 보장하지 않으며 거짓 양성과 거짓 음성이 있을 수 있다고 밝힌다. 자동 검사는 다음 후보를 표시하고 사람이 문맥을 판정하는 데 적합하다. [Microsoft Presidio `517d13b`](https://github.com/microsoft/presidio/tree/517d13b9b37d4c1b7af0453f99b267b715be1f80)

- 사용자 홈을 포함하는 절대 경로
- 로컬 첨부·임시 저장 위치
- 조직이 정한 비공개 프로젝트와 호스트 이름
- 토큰·키·암호 패턴
- 프롬프트와 커밋하거나 공유할 파일 사이의 긴 일치 구절

커밋하거나 공유하기 전에는 변경 파일과 커밋 메시지를 함께 검사하고, 각 후보가 독자에게 필요한 저장소 상대 경로인지 확인한다. 경로가 상대 형식이라는 이유만으로 안전하다고 단정하지 않는다. 비공개 디렉터리명이나 개인 식별자가 상대 경로 안에도 들어갈 수 있다.

## 민감정보가 외부에 알려진 뒤의 대응

GitHub의 민감정보 제거 지침은 자격 증명이 외부에 노출됐으면 저장소 기록을 지우기 전에 먼저 폐기하거나 교체하라고 한다. 기록 재작성은 커밋 해시, 서명, 브랜치 보호, 풀 리퀘스트와 다른 개발자의 복제본에 영향을 주며, 중앙 저장소에서 지워도 포크·캐시·기존 복제본에 남을 수 있다. 예방 검사가 사후 기록 재작성보다 비용이 낮다는 직접적인 운영 근거다. [GitHub, Removing sensitive data from a repository](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)

개인 경로나 비공개 프로젝트명이 외부에 알려진 경우에는 위험도와 복제 범위를 먼저 확인하고, 파일의 최신 버전만 고칠지 기록 전체를 재작성할지 사람이 결정해야 한다. 기록 재작성은 되돌리기 어렵고 협업자에게 영향을 주므로 자동화된 기본 조치로 삼지 않는다.

## 검토 대상 저장소에서 확인한 위험

검토 대상 저장소의 추적 문서에서 개인 계정과 연결될 수 있는 절대 경로, 로컬 첨부 위치, 작업 중 사용한 비공개 식별자를 확인했다. 다른 추적 문서에는 추적하지 않는 입력 자료의 내용을 다시 풀어 쓴 흔적이 있었다. 이 관찰은 독자에게 전달할 글과 문구에 저장소 상대 경로만 남기고, 원문 보존이 필요한 자료는 접근과 보존기간을 정한 별도 기록으로 분리해야 한다는 요구사항의 실제 사례다.

해당 저장소의 이름, 로컬 경로, 파일명, 원문은 이 문서에 기록하지 않았다. 현재 개정의 관찰이므로 이후 수정 여부는 다시 확인해야 하며, 이 한 저장소의 사례로 발생 빈도를 일반화할 수 없다.

## 적용 제안

후속 설계가 승인된다면 커밋하거나 공유하기 전 검사를 다음 순서로 구성할 수 있다.

1. 변경된 글과 문구, 커밋 메시지를 나열한다.
2. 절대 경로, 로컬 첨부 위치, 내부 호스트·프로젝트명, 비밀 형식, 긴 원문 일치 후보를 찾는다.
3. 각 후보가 독자의 과업에 필요한지와 개인·조직·보안 위험을 따로 판정한다.
4. 필요하지 않으면 삭제하고, 위치 안내가 필요하면 현재 저장소에서 확인한 상대 경로로 바꾼다.
5. 원문이 필요하면 목적·접근·만료·삭제 조건이 있는 비공개 저장소로 분리한다.
6. 렌더링된 문서와 API 응답까지 사람 관점에서 확인한다.

평가 데이터와 재현 자료에는 원문을 무조건 복사하지 않는다. 먼저 자리표시자, 합성 값, 일관된 가명 값 순서로 대체하고, 정확한 원문이 실패 원인일 때만 최소 입력을 제한된 위치에 둔다.

## 한계와 남은 질문

- 개인정보와 기밀정보의 법적 범위는 관할 지역과 조직 정책에 따라 달라진다. 이 문서는 법적 판정을 대신하지 않는다.
- 외부 AI와 로그 서비스의 보존 조건은 계정·기능·계약과 시점에 따라 달라진다. 실행 전에 최신 설정을 다시 확인해야 한다.
- 개인정보 탐지 도구의 거짓 양성과 거짓 음성을 이 문제의 한국어 문서와 경로 표본에서 측정한 자료는 찾지 못했다.
- 원문 보존의 필요성과 독자의 확인 가능성이 충돌할 수 있다. 문서에 실을 인용문이나 실제 사용자 문구는 사람이 승인할 범위를 정해야 한다.
- 검토 대상 저장소의 관찰은 발생 사례이지 예방 통제의 효과 증거가 아니다.

## 조사 반복과 중단 근거

네 차례 검색과 원문 대조를 수행했다.

1. 경로와 사용자명이 개인정보가 되는 조건, 최소 수집 원칙을 확인했다.
2. 평가·재현·요구사항·실행 기록에서 원문 보존이 필요한 조건을 나눴다.
3. AI 공급자와 관측 도구의 내용 수집 기본값, 보존기간, 제3자 처리를 대조했다.
4. 자동 탐지, 커밋 전 검사, 이미 외부에 알려진 뒤의 제거 절차를 확인했다.

마지막 검색에서는 `목적과 필요성`, `최소화`, `접근통제`, `보존기간과 삭제`, `후보 탐지와 사람 판정`, `사후 복제본 대응` 외의 새 통제 범주가 나오지 않았다. 경로 자체를 항상 개인정보로 보는 근거도 찾지 못해 이 조사 범위는 포화 상태로 판단했다.
