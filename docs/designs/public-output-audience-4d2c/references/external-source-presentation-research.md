# 외부 출처를 찾기 쉽게 배치하는 방법

## 조사 질문과 적용 범위

이 문서는 [요구사항 문서](../requirements.md)의 `외부 출처를 찾기 어려운 문제`를 다룬다. 설계 문서에서 하나의 주장을 여러 외부 출처로 뒷받침할 때 링크와 근거의 관계를 어떻게 표시해야 읽기 쉽고 Markdown에서도 안정적으로 보이는지 조사했다.

조사는 2026년 7월 28일에 수행했다. 웹 접근성 기준, 정부와 기술 문서 작성 지침, GitHub의 Markdown 문법과 현재 저장소의 설계 문서를 확인했다. 학술 논문의 인용 형식을 그대로 도입하는 일이나 기존 설계 문서 전체를 한 번에 고치는 일은 이번 조사 범위에 포함하지 않았다.

## 결론

여러 출처가 하나의 주장을 뒷받침할 때는 주장을 상위 항목에 쓰고 출처를 하위 항목에 하나씩 두는 2단계 목록을 기본 형식으로 사용한다. 하나의 주장만 담은 문단 바로 아래에 1단계 출처 목록을 두는 방법도 같은 관계를 나타낼 수 있다. 두 형식 모두 출처마다 별도 항목을 사용하며, 각 항목에는 문서나 페이지를 구분할 수 있는 링크 문구와 그 출처에서 확인한 내용을 함께 적는다.

2단계 목록이 항상 필요한 것은 아니다.

- 출처가 하나뿐이면 주장 문장 끝에 설명이 분명한 링크 하나를 둔다.
- 하나의 주장만 담은 문단과 출처 목록이 바로 이어지면 출처를 1단계 목록으로 나눌 수 있다.
- 출처들이 서로 다른 주장을 뒷받침하면 주제별 소제목이나 문단을 나누고 각 주장 가까이에 해당 출처를 둔다.
- 같은 주장을 뒷받침하는 출처가 여러 개이면 상위 항목에 종합한 내용을 적고 하위 항목에는 출처를 하나씩 두는 방식을 기본으로 사용한다.
- 출처 링크만 모은 목록은 각 출처가 어떤 주장을 뒷받침하는지 알 수 없으므로 사용하지 않는다.

한 링크 항목에는 외부 링크를 하나만 둔다. 링크 문구는 기관명만 쓰거나 `자세히 보기`처럼 적지 않고 문서나 페이지의 고유한 제목을 포함한다. 링크 뒤에는 해당 출처에서 확인한 사실을 한 문장으로 적는다.

## 확인한 근거

- **링크는 따로 읽어도 목적을 알아야 한다.** W3C는 보조 기술이 페이지의 링크만 모아 보여줄 수 있으므로 링크 문구만으로 목적지를 이해할 수 있어야 한다고 설명한다. 대한민국 전자정부 웹사이트 품질진단 기준도 링크의 용도나 목적을 이해할 수 있는 문구를 요구한다. 여러 링크를 한 문장에 이어 붙이는 행위 자체를 금지하는 기준은 아니지만, 각 링크를 다른 목적지와 구분할 수 있는 이름으로 써야 한다는 직접 근거다.
  - [W3C 링크 목적 이해 문서](https://www.w3.org/WAI/WCAG22/Understanding/link-purpose-link-only)는 링크 문구만 따로 읽어도 목적을 알 수 있어야 한다고 설명한다. 2026년 7월 28일 확인했다.
  - [전자정부 웹사이트 품질진단 기준](https://www.law.go.kr/LSW/flDownload.do?bylClsCd=200201&flNm=%5B%EB%B3%84%ED%91%9C%5D+%EC%A0%84%EC%9E%90%EC%A0%95%EB%B6%80+%EC%9B%B9%EC%82%AC%EC%9D%B4%ED%8A%B8+%ED%92%88%EC%A7%88%EC%A7%84%EB%8B%A8+%EA%B8%B0%EC%A4%80%28%EC%A0%9C7%EC%A1%B0+%EC%A0%9C1%ED%95%AD+%EA%B4%80%EB%A0%A8%29&flSeq=139718373)은 적절한 링크 텍스트와 콘텐츠의 논리적인 순서를 별도 항목으로 검사한다. 2026년 7월 28일 확인했다.
- **출처는 주장을 설명하는 위치에 둬야 한다.** Google은 링크가 독자의 판단을 늘리고 본문 이탈을 만들 수 있으므로 가장 관련 있는 페이지를 골라 필요한 문맥 가까이에 두라고 권한다. GOV.UK는 문서 끝의 정리되지 않은 링크 목록을 피하고 링크가 유용한 본문 위치에 두라고 안내한다. 출처를 문서 끝에 한꺼번에 모으기보다 주장 가까이에 연결해야 한다는 근거다.
  - [Google 교차 참조와 링크 지침](https://developers.google.com/style/cross-references)은 링크를 선별하고 페이지 제목이나 목적을 설명하는 고유한 링크 문구를 사용하도록 안내한다. 2026년 7월 28일 확인했다.
  - [GOV.UK 링크 작성 지침](https://guidance.publishing.service.gov.uk/writing-to-gov-uk-standards/writing-guidelines/add-links/)은 링크를 필요한 내용 가까이에 두고 출처와 관계없는 `참고 자료` 목록을 피하도록 안내한다. 2026년 7월 28일 확인했다.
  - [Digital.gov 링크 지침](https://digital.gov/guides/plain-language/design/links)은 링크가 너무 많으면 독자의 단기 기억에 부담을 줄 수 있으므로 필요한 링크만 남기고 목적을 설명하라고 권한다. 2026년 7월 28일 확인했다.
- **목록은 반복되는 항목을 훑어보기 쉽게 만든다.** Google과 Microsoft는 순서가 중요하지 않은 반복 항목을 글머리표 목록으로 제시하고, 비슷한 항목은 같은 문장 구조로 맞추라고 안내한다. GitHub는 Markdown의 중첩 목록을 공식 지원한다. 주장과 출처처럼 소속 관계가 있는 항목을 두 단계로 나타낼 수 있다는 형식 근거다.
  - [Google 목록 작성 지침](https://developers.google.com/style/lists)은 단순한 항목 모음에는 목록을 사용하고 같은 수준의 항목을 병렬 구조로 작성하도록 안내한다. 2025년 5월 16일 갱신본을 2026년 7월 28일 확인했다.
  - [Microsoft 목록 작성 지침](https://learn.microsoft.com/en-us/style-guide/scannable-content/lists)은 복잡한 내용을 훑어보기 쉽게 나누되 각 항목을 짧고 일관된 구조로 작성하도록 안내한다. 2026년 2월 10일 갱신본을 2026년 7월 28일 확인했다.
  - [GitHub Markdown 작성 문서](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax)는 들여쓰기로 상위 항목과 하위 항목의 관계를 나타내는 중첩 목록을 지원한다. 2026년 7월 28일 확인했다.
  - [GitHub Flavored Markdown 명세](https://github.github.com/gfm/)는 목록 항목 안에 다른 목록을 포함하는 구문과 들여쓰기 규칙을 정의한다. 0.29-gfm을 2026년 7월 28일 확인했다.

## 다른 형식과 적용 조건

- **주장 문단과 1단계 출처 목록.** 하나의 주장만 담은 문단 바로 아래에 출처 목록이 이어지면 상위 목록 항목 없이도 근거의 대상을 알 수 있다. 다만 한 출처 항목에 링크를 여러 개 넣으면 링크별 이름과 뒷받침 내용을 구분하기 어려우므로 출처마다 항목을 나눈다.
- **주제별 소제목.** 출처 묶음이 서로 다른 결론을 뒷받침한다면 2단계 목록 하나에 넣지 않고 결론별 소제목이나 문단으로 나눈다. 상위 항목 하나에 여러 주장을 넣으면 링크를 분리해도 근거의 대응 관계는 여전히 모호하다.
- **각주.** GitHub는 Markdown 각주를 지원하지만 각주 위치와 상관없이 문서 아래쪽에 표시하며 위키에서는 지원하지 않는다. 호주 정부 Style Manual도 각주 형식은 게시 방식과 독자의 필요에 맞을 때만 선택하라고 안내한다. 현재 설계 문서는 여러 Markdown 표시 환경에서 읽힐 수 있고 출처와 주장의 관계를 바로 확인해야 하므로 각주를 기본 형식으로 사용하지 않는다.
  - [GitHub Markdown 각주 문서](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax#footnotes)는 각주가 문서 아래쪽에 표시되고 위키에서는 지원되지 않는다고 설명한다. 2026년 7월 28일 확인했다.
  - [호주 정부 출처 표시 지침](https://www.stylemanual.gov.au/referencing-and-attribution)은 각주 방식을 게시 환경과 독자의 필요에 맞을 때만 선택하도록 안내한다. 2026년 7월 28일 확인했다.
- **참조형 링크.** Markdown의 참조형 링크는 원문에서 긴 URL을 분리할 수 있지만 화면에 표시되는 링크 배치는 인라인 링크와 같다. 한 문장에 링크가 여러 개 이어지는 문제를 해결하지 못하므로 URL이 길어 원문을 읽기 어려운 경우에만 사용한다.

## 저장소에서 확인한 상태

변경 전 `docs/designs/`에는 한 줄에 외부 링크가 둘 이상 있는 줄이 48개 있었다. 이 수치는 모든 줄이 읽기 어렵다는 뜻이 아니라 여러 출처를 한 문장이나 목록 항목에 넣는 방식이 반복된다는 탐색 결과다. 현재 계획의 `확인한 외부 근거`에는 한 항목에 최대 여덟 개의 링크가 들어 있어 각 출처를 구분하기 어려웠다.

이번 변경에서는 현재 계획의 외부 출처만 새 형식으로 고친다. 기존 설계 문서 전체를 일괄 변경하면 문장과 근거의 관계를 다시 검토하지 않은 채 모양만 바꿀 수 있으므로, 각 문서를 다음에 수정할 때 해당 주장과 출처를 함께 확인한다.

## 요구사항과 계획에 미치는 영향

`requirements.md`에는 여러 출처를 하나의 주장에 연결하는 기본 형식과 완료 증거가 필요하다. `plan.md`에는 `docs/designs/README.md`의 Presentation과 reference 작성 기준을 보완하고 현재 계획의 외부 출처를 같은 방식으로 고치는 작업 및 검증 방법이 필요하다.

기계 검사는 한 줄에 외부 링크가 여러 개 있는 위치를 후보로 찾을 수 있다. 그러나 링크를 여러 줄로 나누기만 해도 검사를 통과할 수 있으므로 최종 판정은 각 출처가 가까운 주장과 연결되는지 읽어 확인해야 한다.

## 조사 반복과 중단 근거

세 차례 검색과 원문 대조를 수행했다.

1. 링크 문구와 링크 목적을 다룬 국내외 접근성 기준을 확인했다.
2. 목록, 중첩 목록, 본문 링크와 각주를 다룬 기술 문서 작성 지침 및 Markdown 문법을 비교했다.
3. 출처를 주장 가까이에 두는 방식과 각주의 적용 조건을 추가로 검색하고 현재 저장소의 링크 배치를 대조했다.

마지막 검색에서는 설명이 분명한 링크 문구, 주장 가까이에 둔 출처, 반복 항목을 나눈 목록, 게시 환경에 따라 제한적으로 쓰는 각주라는 기존 범주가 다시 확인됐다. 새로운 배치 방식이나 2단계 목록을 배제할 근거가 나오지 않아 조사를 끝냈다.
