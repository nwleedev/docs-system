# Progressive UI 리서치 스킬 개선 계획

이 계획은 후속 스킬 문서 작업자가 요구사항을 구현 순서와 확인 근거로 옮길 때 사용한다. 독자는 아래 작업을 차례로 수행하고 각 단계의 확인 근거를 검토한다.

## 목표

`use-progressive-user-interfaces`가 사용자의 시각 취향만 먼저 비교하지 않고, 서비스 목표와 사용자 작업에 필요한 디자인 질문을 정한 뒤 사례를 찾고, 실제 화면 근거를 확인하고, 서로 다른 해결책을 비교하여 실행 UI에서 검증하도록 개선한다.

이 계획의 기준은 [요구사항](requirements.md)이다. 요구사항의 문구와 적용 대상은 이 계획에서 바꾸지 않는다. 구현 방식으로 제안하는 파일 분리는 계획상 선택이며, 요구사항에 새 조건을 추가하지 않는다.

## 작업 대상

스킬의 안내 문서만 수정한다. 애플리케이션 코드, Browser 도구, 외부 연동, 저장 서비스, 새 의존성이나 조사 스크립트는 변경하지 않는다. 사용자 선택과 응답 대기, 단계별 기록과 기본 탐색 차례를 정의한 `preferences.md`는 수정하지 않고 동작이 계속 연결되는지 확인한다.

필요한 자료는 [실제 UI 리서치 근거](references/research-evidence.md)와 [스킬 지침 및 참고 자료 구성 조사](references/skill-authoring-and-context-research.md)를 사용한다. 첫 문서는 실제 UI 조사와 Browser 사용 근거를 제공하고, 둘째 문서는 스킬 문서 구성 근거를 제공한다.

요구사항은 `sources.md`를 권장 구조에 포함하지만, 출처 지침을 `discovery.md`와 `inspection.md`에서 이해하기 쉽게 유지할 수 있으면 별도 파일을 생략할 수 있다고 명시한다. 기존 UI 조사 근거 문서와 두 절차에 나눠 반영해 새 `sources.md`는 추가하지 않는다.

## 요구사항 기준

다음 요구사항을 후속 문서에 반영한다.

- 리서치가 사용자 취향과 시각적 방향에서 너무 빨리 시작되는 문제
- 후보 탐색이 너무 일찍 끝나는 문제
- 검색과 브라우저를 언제 써야 하는지 구분하지 못하는 문제
- UI를 세부 수준까지 분석하지 못하는 문제
- 사례별 특징이 종합 과정에서 사라지는 문제
- 외부 디자인 자료에 하나의 역할만 부여하는 문제
- 화면에서 본 특징과 제작자가 밝힌 의도를 혼동하는 문제
- UI의 공통점만 남기지 말고 비교할 선택지를 유지해야 한다는 조건
- 일반 디자인 지침과 서비스 고유의 시각 방향을 구분하는 조건
- 기본 화면 밖의 상태 확인, 정확한 수치의 근거, 이슈 및 PR을 조사할 시점
- 외부 디자인 지침을 스킬에 지나치게 복사하지 않는 조건
- 개선 후 전체 작업 순서, 확인 기준과 성공 조건

[현재 유지해야 하는 부분](requirements.md#현재-유지해야-하는-부분)은 보호 조건이다. 실제 UI와 다른 자료의 구분, 사용자 선택과 AI 판단의 분리, 기존 규칙의 재사용, 최신 실행 UI 검증을 약화하지 않는다.

## 작업 순서

### 1. 루트 안내와 후보 탐색을 정리한다

**대상 파일:** `skills/use-progressive-user-interfaces/SKILL.md`, `skills/use-progressive-user-interfaces/references/discovery.md`

서비스 목표, 사용자 작업, 필요한 화면과 상태, 디자인 질문을 탐색 전에 정하도록 루트 안내와 탐색 순서를 맞춘다. 분위기와 좋아하는 서비스는 검색 방향을 돕는 정보로 남긴다. `discovery.md`는 Web Search를 통한 다관점 후보 검색과 후보 탐색 종료 기준을 맡게 하고, 내부 검색 시도와 사용자에게 선택을 묻는 탐색 차례를 구분한다.

**적용할 패턴:** 점진적 공개를 적용해 루트 문서는 사용할 절차를 선택하는 안내자로 유지한다. 공식 스킬 안내는 참고 자료를 언제 읽을지 루트에서 연결하고, 세부 절차를 하위 파일에 둘 것을 권한다. 근거는 [스킬 작성 조사](references/skill-authoring-and-context-research.md)와 [후보 탐색 요구사항](requirements.md#후보-탐색이-너무-일찍-끝나는-문제)이다.

**확인 근거:** 새로운 시나리오에서 디자인 질문이 사용자 작업으로부터 도출되는지, 서로 다른 검색 관점이 사용되는지, 고정 URL 수 없이 탐색 종료를 설명할 수 있는지 확인한다. 내부 검색 횟수가 사용자 탐색 차례에 합산되지 않아야 한다.

### 2. 실제 UI와 상호작용 상태를 확인하는 절차를 둔다

**대상 파일:** `skills/use-progressive-user-interfaces/SKILL.md`, `skills/use-progressive-user-interfaces/references/inspection.md`

새 `inspection.md`에서 Web Search가 후보와 공식 자료를 찾는 일과 Browser가 실제 렌더링, 상호작용, 반응형 변화, 로그인 후 화면, 화면 출처와 로컬 실행 UI를 확인하는 일을 구분한다. 필요한 화면만 현재 환경에서 사용 가능한 Browser로 관찰하게 하고, 데스크톱 내장 Browser와 Cloud Browser의 접근 조건을 혼동하지 않게 한다.

화면, 주요 영역, 구성 요소, 내부 구조, 개별 요소와 상태를 질문에 필요한 수준까지 조사한다. 직접 관찰, 출처가 밝힌 이유, AI 해석과 미확인 항목을 분리한다. 정확한 수치는 공식 토큰, 명세, 코드, Storybook 또는 DOM/CSS에서 근거를 확인한 경우에만 제시하고, 이슈와 PR은 구현 위험을 판단할 이유가 있을 때 조사한다.

**적용할 패턴:** 각 근거를 출처와 적용 대상에 연결해 기록한다. 실제 화면 관찰은 검색 요약이나 디자인 지침으로 대체할 수 없다. 상세 근거는 [실제 UI 리서치 근거](references/research-evidence.md) 및 요구사항의 [검색과 브라우저 선택 기준](requirements.md#검색과-브라우저를-언제-써야-하는지-구분하지-못하는-문제)에 따른다.

**의존성:** 1단계에서 정한 디자인 질문을 입력으로 사용한다.

**확인 근거:** 실제 페이지를 직접 보지 않은 상태를 관찰했다고 쓰지 않는지, 접근하지 못한 상태를 미확인으로 남기는지, 필요한 상태와 화면 크기만 검사하는지 확인한다. 스크린샷만으로 검증되지 않은 픽셀이나 토큰 값을 확정하지 않아야 한다.

### 3. 사례별 분석과 선택지 비교를 분리한다

**대상 파일:** `skills/use-progressive-user-interfaces/SKILL.md`, `skills/use-progressive-user-interfaces/references/rationale.md`

새 `rationale.md`에서 후보 사례를 각각 분석한 뒤 비교하도록 한다. 공통점, 서로 다른 해결 방식, 한 사례에만 있는 특성, 반대되는 선택, 장단점과 이유를 확인하지 못한 차이를 보존한다. 사용자의 현재 작업 조건을 비교 기준으로 삼고, 여러 사례를 평균적인 시각 방향으로 압축하지 않는다.

일반 디자인 지식과 현재 서비스의 시각 방향을 분리한다. 외부 자료 하나에 고정 역할을 부여하지 않고 개별 근거의 종류, 질문, 적용 대상과 조건을 기록한다.

**적용할 패턴:** 사례별 분석 후 비교하는 방식으로 각 근거의 원본을 보존한다. 이 단계는 요구사항의 [사례별 특징 보존](requirements.md#사례별-특징이-종합-과정에서-사라지는-문제), [근거와 해석 구분](requirements.md#화면에서-본-특징과-제작자가-밝힌-의도를-혼동하는-문제), [선택지 비교](requirements.md#ui의-공통점만-남기지-말고-비교할-선택지를-유지해야-한다)에 따른다.

**의존성:** 2단계에서 확인한 화면 관찰 내용을 입력으로 사용한다.

**확인 근거:** 최종 비교에서 각 특성을 어느 사례와 출처에서 확인했는지 거슬러 갈 수 있어야 한다. 사용자에게 제시하는 선택지마다 현재 작업에 어떤 영향을 주는지와 장단점, 불확실성이 드러나야 한다.

### 4. 구현 입력과 실행 UI 검증으로 근거를 전달한다

**대상 파일:** `skills/use-progressive-user-interfaces/SKILL.md`, `skills/use-progressive-user-interfaces/references/implementation.md`, `skills/use-progressive-user-interfaces/references/validation.md`

`implementation.md`는 색과 간격뿐 아니라 정보 위계, 화면 구성, 구성 요소 구조, 동작 위치, 상태 표현과 화면 크기 변화를 필요한 항목에 따라 구현 규칙과 검증 조건으로 전달한다. 검증되지 않은 수치는 잠정 값으로 구분하고, 반복 사용이 확인된 규칙만 토큰으로 구체화한다.

`validation.md`는 실제 실행 중인 최신 화면에서 요구사항에 맞는 특성과 영향을 받은 상태를 확인하도록 `inspection.md`의 근거 원칙과 연결한다. 코드 변경 완료나 생성 이미지가 실제 UI 검증을 대신하지 않게 한다. 기존 `preferences.md`의 사용자 선택과 탐색 차례 의미는 바꾸지 않는다.

**적용할 패턴:** 기존 원칙을 먼저 재사용하고 필요한 규칙만 추가하는 점진적 시스템 확장을 적용한다. 확정 선호, 잠정 구현안과 실행 화면에서 검증한 규칙을 구분한다. 근거는 요구사항의 [기존 규칙 재사용과 실제 UI 검증](requirements.md#현재-유지해야-하는-부분) 및 [스킬 문서 구성 제안](requirements.md#개선안-스킬-문서-구성)이다.

**의존성:** 3단계의 선택지 비교와 기존 사용자 선택 절차를 입력으로 사용한다.

**확인 근거:** 서비스별 규칙이 선택한 근거와 사용 조건을 포함하는지, 검증 화면이 현재 코드 변경을 반영하는지, 확인하지 않은 상태나 화면에 규칙을 확대 적용하지 않는지 확인한다.

## 최종 검토

수정 대상 문서를 미래의 스킬 사용자 관점에서 다시 읽고, 요구사항의 각 문제와 성공 조건이 적어도 한 문서에 연결되는지 확인한다. 직접 관찰, 외부 자료가 밝힌 이유, AI 해석과 미확인 사항이 혼합되지 않는지 사례별로 점검한다. 실제 Browser 확인이 필요한 조건과 사용할 수 없는 환경의 처리도 함께 검토한다.

요구사항의 확인 기준을 이용해 다음 상황을 문서 절차로 따라가 본다: 검색 후보가 유명한 SaaS 한두 개에 치우치는 경우, 실제 페이지 확인이 필요한 경우, 호버나 키보드 초점을 확인해야 하는 경우, 사례별 분석에서 선택지를 비교하는 경우, 스크린샷만 있어 정확한 값을 알 수 없는 경우, 로그인 또는 로컬 UI 접근이 제한된 경우. 이 검토는 문서 내용과 연결 상태를 확인하며, 새 자동 평가기나 실행 코드를 추가하지 않는다.

마지막으로 저장소 문서 배치와 상대 링크를 확인하고, 한국어 문구 검사를 수행한다. 문서 검토는 구현이 요구사항에 맞게 작동함을 증명하지 않으므로, 실행 UI 검증 완료 여부는 실제 화면 근거가 마련된 경우에만 판단한다.

## 개발 지침과 미결정 사항

계획 작성과 후속 문서 변경에는 [`docs/dev/README.md`](../../dev/README.md)를 적용한다. 이번 변경은 스킬 문서에 한정하고 소스 코드, `.mjs` 파일, 외부 의존성이나 개발 도구를 바꾸지 않으므로 [`docs/dev/node/mjs-cli.md`](../../dev/node/mjs-cli.md)는 적용하지 않는다.

계획을 막는 미결정 사항은 없다. 실행 환경에서 Browser를 사용할 수 있는지, 특정 사이트에 접근할 수 있는지, 실제 대상 서비스의 로그인 상태가 필요한지는 실행 시 확인할 조건이다. 환경에서 관찰할 수 없는 화면이나 동작은 미확인으로 남기고, 그 근거가 필수인 결정은 사용자에게 화면 자료를 요청하거나 결정을 보류한다.

## 완료 조건

- 요구사항의 모든 개선 기준이 스킬 본문 또는 그 기준을 설명하는 참고 절차에 반영되거나, 기존에 충족되어 유지하는 부분으로 확인된다.
- Web Search의 후보 탐색과 Browser를 통한 실제 UI 확인 조건이 분리된다.
- 사용자 선택과 기존 단계 재개 동작을 유지한다.
- 사례별 특성과 근거를 비교 후에도 출처까지 추적할 수 있다.
- 화면에서 확인한 값과 별도 자료로 확인한 정확한 값을 구분한다.
- 요구사항에 명시한 작업 대상 밖의 코드, 도구, 저장 시스템이나 외부 의존성을 추가하지 않는다.
- 최종 문서 링크와 한국어 표현을 검사하고 문서 전체를 독자로서 읽어 모순을 확인한다.
