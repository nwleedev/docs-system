# 실제 UI 리서치 절차를 뒷받침하는 자료

현재 스킬은 사용자 선택과 실행 화면 검증을 신중히 처리하지만, 검색으로 후보군을 넓히고 각 후보의 차이를 근거에 따라 비교하는 절차는 별도로 정리할 여지가 있다. 공식 자료를 대조하면 후보 검색 도구와 실제 화면 확인 도구를 나누고, 디자인 근거를 출처 전체가 아니라 개별 정보 단위로 분류하는 방향이 적절하다.

## 조사 질문

이 조사는 `use-progressive-user-interfaces`의 실제 UI 사례 검색, 화면 분석, 근거 구분과 비교 절차를 어떻게 개선할지 확인한다. 2026-09-25에 Codex 공식 문서, ChatGPT Browser 안내, W3C WAI-ARIA Authoring Practices Guide, Apple Human Interface Guidelines와 Carbon Design System의 현재 웹 문서를 살펴봤다. 문서에 고정 버전이 표시되지 않은 자료는 조사일 기준의 현재 문서로 취급했다.

## 저장소에서 확인한 현재 상태

`skills/use-progressive-user-interfaces/SKILL.md`는 현재 목표와 사용자 작업을 확인한 뒤 단계에 맞는 절차 파일을 읽도록 한다. `references/discovery.md`는 검색 관점을 정하고 실제 후보 화면을 살피며, 화면 자료와 출처, 확인한 상태를 단계 기록에 포함하도록 한다. 다만 검색과 시각 확인을 별도 단계로 나누지 않고, 후보군을 모은 뒤 다양성을 확인하거나 검색을 더 해도 새 전략이 나오지 않는 시점을 판단하는 절차도 따로 정하지 않는다.

`references/implementation.md`는 현재 작업에 필요한 규칙을 색, 배경, 글자, 간격, 형태, 테두리와 그림자 중심으로 설명한다. 화면 구조, 정보 배치와 상호작용 상태도 서비스 디자인 규칙으로 전달하도록 구현 입력 항목을 늘릴 수 있다.

`references/preferences.md`는 사용자 선택, 응답 대기, 탐색 횟수와 선택한 요소의 적용 대상을 이미 설명한다. `references/validation.md`는 변경 영향을 받는 상태와 조건, 다른 기존 화면에서의 규칙 재사용, 미확인 상태 처리도 설명한다. 이 절차들은 이번 조사 품질 개선을 위해 다시 만들 필요가 없다.

## 공식 자료에서 확인한 사실

[Codex Web Search 안내](https://developers.openai.com/codex/web-search)는 CLI에서 `--search`로 실시간 검색을 요청할 수 있고, IDE 확장은 연결된 Codex 호스트의 검색 설정을 사용한다고 설명한다. [Codex Browser 안내](https://developers.openai.com/codex/browser)는 Browser가 CLI와 IDE 확장에서 제공되지 않는다고 명시하고, 웹 또는 데스크톱의 ChatGPT에서 사이트를 열어 조사하는 도구로 설명한다. 따라서 폭넓은 후보 검색과 실제 화면을 여는 도구는 서로 다른 능력으로 취급해야 한다. Browser가 모든 스킬 실행 환경에서 제공된다고 가정할 수 없다.

[ChatGPT 데스크톱 내장 Browser 안내](https://help.openai.com/en/articles/20001277-using-the-built-in-browser-in-the-chatgpt-desktop-app)는 macOS와 Windows 앱의 Work와 Codex에서 내장 Browser를 쓸 수 있으며, 여러 탭 이동, 로그인, 로컬 개발 화면 확인과 화면 주석이 가능하다고 설명한다. 이 Browser는 사용자 기기의 Chrome과 별도 상태를 사용한다. [ChatGPT Cloud Browser 안내](https://help.openai.com/en/articles/20001280-using-cloud-browser-in-chatgpt)는 Work에서 위임한 작업에 별도 원격 Browser를 쓰고, 허용된 웹사이트 중 로그인 없이 볼 수 있거나 로그인 후 볼 수 있는 페이지를 읽고 조작할 수 있다고 설명한다. Cloud Browser의 이용 조건은 요금제, 지역, 워크스페이스 권한과 웹사이트에 따라 달라지며, 개인 Browser의 탭과 로그인 상태를 공유하지 않는다. 따라서 두 도구의 작동 환경과 접근 대상을 구분해야 한다.

Cloud Browser로 Web Search 목록에서 찾기 어려운 로그인 후 화면을 확인할 수도 있지만, 공식 안내는 모든 웹사이트와 UI 상태를 확인할 수 있다고 말하지 않는다. 실제로 화면에 표시되거나 조작한 내용만 기록하고, 보지 못한 정보까지 확인했다고 추정해서는 안 된다. 로컬 개발 화면 검증은 데스크톱 내장 Browser의 용도로 안내되어 있으므로, 원격 Cloud Browser가 사용자 컴퓨터의 로컬 주소를 열 수 있다고 가정하지 않는다.

[W3C의 APG 소개](https://www.w3.org/WAI/ARIA/apg/about/introduction/)는 APG가 ARIA 접근성 의미와 상호작용 패턴, 키보드 동작을 안내하는 비규범 자료이며, 예제는 설명용이고 완전한 디자인 시스템이나 배포용 코드가 아니라고 밝힌다. 접근성 또는 키보드 동작에 관한 근거와 실제 서비스 화면의 시각 방향을 정하는 근거는 구분해야 한다.

[Apple HIG의 레이아웃 지침](https://developer.apple.com/design/human-interface-guidelines/layout)은 정보 위계와 화면 배치, 창 크기와 기기, 방향, 글자 크기, 언어에 따른 적응을 함께 설명한다. 하나의 출처가 시각 구성과 플랫폼 조건에 관한 정보를 모두 제공할 수 있으므로, 출처 전체에 한 가지 역할만 부여하면 정보를 잃는다.

[Carbon 타일 사용 지침](https://carbondesignsystem.com/components/tile/usage/)은 기본형, 탐색형, 선택형, 펼침형을 나누고 각 유형의 구성, 상호작용과 상태를 따로 설명한다. 같은 컴포넌트 계열에서도 용도에 따라 구성과 동작이 다를 수 있다. [Carbon 탭 사용 지침](https://carbondesignsystem.com/components/tabs/usage/)은 선택, 비선택, 마우스 올림, 초점과 비활성 상태를 구분한다. 상태의 존재와 표현은 화면 한 장에서 보이는 기본 상태만으로 추정할 수 없다.

## 근거에서 도출한 판단

공식 지침과 디자인 시스템 문서는 사용 목적, 구성, 동작, 플랫폼 조건을 설명하는 데 유용하지만, 그 자료 자체가 출시된 서비스 화면을 관찰한 근거는 아니다. 따라서 실제 외형을 비교하려면 출시된 UI나 출처가 확인된 화면을 직접 살펴보고, 문서에서 얻은 근거는 적용 조건과 함께 별도로 기록해야 한다.

한 자료가 시각 구성, 접근성, 동작과 플랫폼 적응을 동시에 설명할 수 있으므로 자료마다 하나의 역할을 고정하기보다 근거마다 출처 종류, 디자인 질문, 적용 조건과 확인 상태를 연결하는 편이 정확하다. 출처가 명시한 이유, 화면에서 확인한 사실과 AI의 해석도 구분해야 한다.

Codex Web Search 문서는 Codex에서 폭넓게 웹을 검색할 수 있음을 뒷받침하지만, 후보 수나 검색 종료 기준의 최적값을 입증하지 않는다. 공식 자료들은 사례별 분석과 조건별 상태 확인의 필요성을 보여주지만, 여러 검색에서 새 전략이 더 나오지 않는 시점과 디자인 품질 사이의 관계를 정량적으로 입증하지 않는다. 이런 항목은 고정 수치로 정하기보다 실제 사용에서 비교 가능한 완료 증거로 평가해야 한다.

## 요구사항에 미치는 영향과 실행 제안

요구사항은 서비스 목표와 사용자 작업에서 질문을 정하고, Web Search로 후보를 넓힌 뒤, 필요한 후보만 시각적으로 살펴보고, 사례별 차이와 근거를 보존한 상태로 선택지와 장단점을 비교하도록 정했다. Codex Web Search나 시각 확인 도구가 없는 환경에서는 성공한 것처럼 보고하지 않고 미확인 상태와 필요한 근거를 남겨야 한다.

현재 파일 구조를 유지하면서 `discovery.md`를 후보군 검색 중심으로 정리하고, 독립적인 화면 분석과 선택지 비교 절차를 각각 필요할 때 읽도록 분리하는 방안을 제안한다. 검색 관점과 근거 출처에 관한 짧은 지침은 검색 및 화면 분석 절차에서 관리할 수 있으므로 별도의 자료 분류 참고 파일을 반드시 만들 필요는 없다. 기존 `preferences.md`의 사용자 선택 차례 관리, `implementation.md`의 잠정 입력과 `validation.md`의 실제 UI 검증은 유지하고, 구현에 전달할 규칙 종류만 필요한 만큼 늘린다. 별도 파일 구성은 필수 조건이 아니라 조사에서 나온 실행 방안이다.

이 조사만으로 각 디자인 시스템의 내용을 빠짐없이 평가하거나 현재 서비스 목표에 어느 선택지가 가장 잘 맞는지 결정하지 않았다. 화면별 수치와 상호작용 방식은 사용 대상, 플랫폼, 버전과 실제 자료를 확인한 뒤 판단해야 한다.
