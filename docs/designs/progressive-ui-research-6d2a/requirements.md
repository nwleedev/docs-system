# use-progressive-user-interfaces 개선 요구사항

## 문서 목적

이 문서는 현재 `use-progressive-user-interfaces` 스킬의 문제와 개선 후 충족해야 할 조건을 정한다.

개선안을 계획하거나 구현 완료 여부를 판단하는 사람이 이 문서를 기준으로 삼는다.

스킬은 서비스 목표와 사용자 작업에서 출발해 해결할 디자인 문제를 정하고, 디자인 지침과 실제 서비스 UI를 조사하고, 해결 방식을 비교한 뒤, 사용자 선택을 그 서비스에 적용할 규칙으로 정하고 실행 화면에서 검증해야 한다.

---

## 현재 유지해야 하는 부분

현재 스킬에는 개선 후에도 유지해야 할 중요한 원칙이 있다.

### 실제 UI와 다른 자료를 구분한다

실제 출시된 서비스 UI, AI가 생성한 시안, 출처를 확인하지 못한 이미지, 공식 디자인 문서와 검색 목록을 서로 다른 근거로 취급해야 한다.

검색 목록의 설명이나 도움말 페이지를 실제 UI를 직접 관찰한 근거로 사용해서는 안 된다.

### 사용자 선택과 AI 판단을 구분한다

다음 상태를 서로 혼동해서는 안 된다.

- 사용자가 확인한 선호
- 사용자가 확인한 비선호
- 아직 결정하지 않은 항목
- AI가 탐색을 위해 세운 가설
- 검증을 위한 잠정 구현안
- 실제 실행 UI에서 검증된 규칙

사용자가 한 서비스를 선택했다고 해서 그 서비스의 모든 색상, 모서리, 타이포그래피와 구성 요소를 선호한다고 일반화해서는 안 된다.

### 기존 규칙을 먼저 재사용한다

새로운 화면이 필요하다는 이유만으로 항상 새로운 UI 리서치를 시작해서는 안 된다.

기존에 확정한 디자인 원칙과 규칙으로 새로운 화면을 표현할 수 있는지 먼저 확인해야 한다.

### 구현 후 실제 UI를 다시 검증한다

생성 시안, 디자인 명세, 빌드 성공 메시지, 코드 변경 완료는 실제 UI 검증을 대체할 수 없다.

현재 코드가 반영된 실행 화면에서 선택한 특성이 유지되는지 다시 확인해야 한다.

---

## 현재 스킬의 주요 문제

### 리서치가 사용자 취향과 시각적 방향에서 너무 빨리 시작된다

현재 스킬은 사용자의 시각적 선호를 알아보는 데 큰 비중을 둔다.

그러나 같은 사용자가 같은 시각 스타일을 선호하더라도 실제로 수행하는 작업에 따라 필요한 UI는 달라진다.

항목을 빠르게 비교해야 하는 화면과 처음 사용하는 사람을 안내하는 화면에는 같은 취향을 그대로 적용할 수 없다.

따라서 시각적 선호만으로 디자인 탐색을 시작해서는 안 된다.

#### 요구사항

새로운 탐색은 다음 순서를 기본으로 해야 한다.

서비스가 달성하려는 목표

→ 사용자가 수행하려는 작업

→ 현재 판단에 필요한 화면 또는 상태

→ 해결해야 하는 디자인 질문

→ 디자인 문제에 필요한 자료 조사

사용자가 말한 분위기나 좋아하는 서비스는 검색 방향과 비교 기준을 형성하는 하나의 입력으로 취급한다.

사용자의 최초 표현을 완성된 디자인 명세로 간주해서는 안 된다.

---

## 후보 탐색이 너무 일찍 끝나는 문제

현재 `discovery.md`는 검색 관점을 다양하게 만들도록 하지만, 후보를 몇 개 찾은 뒤 상세 분석으로 넘어갈지 판단하는 조건은 충분히 설명하지 않는다.

따라서 첫 검색에서 주제에 맞는 SaaS 한두 개를 찾은 뒤 곧바로 그 서비스 분석으로 넘어갈 수 있다.

이 경우 다음 문제가 발생한다.

- 처음 발견한 서비스의 디자인 방향에 지나치게 영향을 받을 수 있다.
- Linear, Vercel, Notion처럼 이미 널리 알려진 SaaS만 반복해서 찾을 수 있다.
- 서비스 이름은 달라도 실제 시각 표현 방식은 거의 같을 수 있다.
- 같은 문제를 다른 방식으로 해결하는 업종의 사례를 놓칠 수 있다.
- 사용자에게 비교할 만한 디자인 선택지를 충분히 제시하지 못할 수 있다.

#### 요구사항

화면을 자세히 확인하기 전에 폭넓게 후보를 탐색해야 한다.

후보를 탐색할 때는 하나의 검색어만 사용해서는 안 된다.

현재 디자인 질문에 따라 다음 관점을 골라 조합해야 한다.

- 서비스 분야
- 사용자 작업
- 화면 역할
- 상호작용 방식
- 정보 밀도
- 탐색 구조
- 사용자가 피하고 싶은 특성
- 같은 문제를 해결하는 다른 업종
- 서로 다른 시각 방향
- 참고할 공식 디자인 시스템 또는 패턴

고정된 숫자의 URL을 채우는 것을 목표로 삼아서는 안 된다.

검색 종료 여부는 다음 조건을 기준으로 판단해야 한다.

- 현재 디자인 질문에 대해 의미 있게 다른 해결 방법을 여러 개 찾았는가
- 검색 목록이 특정 서비스나 디자인 계열에 편중되지 않았는가
- 사용자가 비교할 가치가 있는 서로 다른 방향을 제시할 수 있는가
- 다른 검색 관점으로 추가 조사했을 때 새로운 방향보다 이미 발견한 방향의 반복이 주로 나타나는가

특별한 이유가 없다면 SaaS 한두 개만 찾고 후보 탐색을 끝내서는 안 된다.

사용자에게 후보를 제시해 의견을 받는 차례와 내부 검색 횟수는 별개로 취급해야 한다.

---

## 검색과 브라우저를 언제 써야 하는지 구분하지 못하는 문제

현재 스킬은 검색하거나 실제 화면을 확인하라고만 하므로 Web Search와 ChatGPT의 Browser가 맡는 일이 분명하지 않다.

이 기준이 없으면 후보를 넓게 찾는 단계부터 Browser로 사이트를 하나씩 열어 후보 탐색이 줄어들 수 있다.

반대로 화면에 실제로 표시되는 UI나 상호작용 상태를 봐야 할 때도 Web Search 목록과 검색 이미지에만 의존할 수 있다.

ChatGPT 데스크톱 앱의 내장 Browser는 Work와 Codex에서 사용할 수 있다. 사용자와 ChatGPT가 같은 페이지를 보며 여러 탭을 이동하고, 로그인하고, 로컬 개발 화면을 확인하거나 화면 영역에 주석을 달 수 있다. 내장 Browser는 사용자 PC의 Browser와 별도의 상태를 사용한다. [데스크톱 내장 Browser 안내](https://help.openai.com/en/articles/20001277-using-the-built-in-browser-in-the-chatgpt-desktop-app)

ChatGPT Work 웹과 모바일의 Cloud Browser는 원격 환경에서 동작하며, 접근이 허용된 사이트 중 이용할 수 있는 곳의 페이지를 읽고 조작할 수 있다. 검색 목록에서 찾기 어려운 로그인 후 UI도 직접 확인할 수 있지만, 이용 가능 여부는 웹사이트마다 다르다. Cloud Browser도 사용자 PC의 Browser와 별도의 로그인 상태를 사용한다. [Cloud Browser 안내](https://help.openai.com/en/articles/20001280-using-cloud-browser-in-chatgpt)

Browser를 쓸 수 있는지와 각 도구에서 할 수 있는 일은 실행 환경, 계정의 요금제와 이용 지역, 워크스페이스 설정, 웹사이트에 따라 달라진다. 스킬은 현재 실행 환경에서 어떤 Browser 동작을 쓸 수 있는지 확인하고, 접근하지 못한 화면이나 상태를 관찰한 것처럼 기록해서는 안 된다.

따라서 두 도구의 선택 조건을 스킬에서 명시해야 한다.

### Web Search를 사용해야 하는 경우

Web Search는 외부 자료를 넓게 발견하고 텍스트 기반 근거를 조사하는 기본 수단으로 사용한다.

다음 상황에서는 Browser보다 Web Search를 먼저 사용해야 한다.

- 새로운 참고 사례를 넓게 찾는다.
- 여러 서비스 분야에서 같은 문제를 해결하는 사례를 찾는다.
- HIG, Material, Carbon, WAI-ARIA 등의 공식 문서를 찾는다.
- 현재 공식 문서의 최신 내용을 확인한다.
- 여러 검색 관점으로 후보군을 구성한다.
- 이미지 검색과 연결된 페이지에서 시각 자료를 찾는다.
- 구성 요소의 공식 명세나 디자인 토큰 자료를 찾는다.
- 원본 코드, Storybook, 이슈와 PR 같은 추가 근거를 찾는다.
- 특정 이슈가 현재 버전에서도 존재하는지 조사한다.
- 실제 페이지를 직접 보지 않아도 답할 수 있는 사실을 검증한다.
- 심층 검토 후보를 정하기 전에 자료의 폭과 다양성을 확보한다.

Web Search에서 적합한 서비스 하나를 발견했다는 이유만으로 즉시 Browser를 열어 자세히 분석해서는 안 된다.

후보 탐색 중이라면 우선 다른 검색 관점에서도 사례를 찾아야 한다.

### 사용할 수 있는 Browser로 실제 화면을 확인해야 하는 경우

실제 화면이나 상호작용에 관한 근거가 필요할 때 Browser를 사용한다.

다음 상황에서는 현재 환경에서 쓸 수 있는 Browser를 우선 검토해야 한다.

#### 실제 화면을 보아야 디자인을 판단할 수 있는 경우

다음 항목을 확인해야 한다면 접근 가능한 페이지를 Browser로 열어 살핀다.

- 화면 전체의 구성
- 탐색 영역과 내용의 실제 공간 관계
- 사이드바, 도구 모음, 패널, 카드의 화면 위계
- 구성 요소 사이의 크기와 배치
- 글자 크기와 강조의 위계
- 테두리와 구분선의 사용 방식
- 모서리의 둥근 정도와 컨테이너 형태
- 그림자와 배경색으로 영역을 나누는 방식
- 조작 요소와 주변 내용 사이의 간격
- 실제 정보 밀도
- 아이콘과 이름표의 관계
- 주요 동작의 위치
- 보조 정보의 위치

검색 미리보기나 홍보용 이미지로 후보를 고르는 데 충분하고 실제 UI 확인이 현재 질문에 필요하지 않다면 Browser를 열지 않아도 된다. 실제 UI를 근거로 판단해야 할 때는 원본 페이지를 확인한다.

#### 상호작용으로 확인해야 하는 상태가 중요한 경우

현재 디자인 질문에 중요한 다음 상태가 정적인 자료에 보이지 않는다면 Browser로 직접 조작해 확인한다.

- 마우스를 올린 상태
- 키보드 초점
- 활성 상태
- 선택 상태
- 펼친 상태
- 접은 상태
- 열린 메뉴
- 열린 팝오버
- 툴팁 표시
- 열린 대화상자
- 로딩 중 변화
- 입력값 검증
- 오류 상태
- 완료 상태
- 알림 토스트
- 스크롤 동작
- 넘치는 내용
- 끌어 놓는 상태

실제로 조작하지 않은 상태를 관찰한 것처럼 기록해서는 안 된다.

확인하지 못한 상태는 명시적으로 미확인 상태로 남긴다.

#### 화면 크기에 따른 변화를 직접 확인해야 하는 경우

화면 크기에 따라 UI가 달라지는 방식이 중요하고 공식 문서나 정적 자료만으로 판단하기 어렵다면 Browser로 확인한다.

예를 들어 다음을 검사할 수 있다.

- 사이드바가 접히는가
- 탐색 구조가 바뀌는가
- 도구 모음의 동작이 더보기 메뉴로 이동하는가
- 표나 목록이 폭이 줄어든 화면에서 어떻게 바뀌는가
- 대화상자가 시트 형태로 바뀌는가
- 정보 밀도가 조절되는가

#### 이미지가 실제 서비스 화면인지 확인해야 하는 경우

검색에서 발견한 자료가 다음 중 무엇인지 분명하지 않다면 Browser에서 원본 페이지를 확인한다.

- 실제 출시 UI
- 홍보용 목업
- 오래된 서비스 화면
- 제삼자가 다시 만든 화면
- 디자인 갤러리에 재게시된 이미지
- AI 생성 이미지

실제 서비스 UI임을 확인하지 못한 이미지를 출시 화면에 대한 직접 관찰 근거로 사용해서는 안 된다.

#### 로그인 후의 실제 서비스 화면이 필요한 경우

로그인하지 않고 볼 수 있는 시작 페이지나 안내 문서만으로 실제 서비스 UI를 알 수 없고, 로그인 후 화면이 현재 디자인 질문에 중요하다면 그 화면을 열 수 있는 Browser를 사용한다.

로그인이 필요하면 계정 정보를 채팅에 쓰지 말고 Browser의 로그인 화면에 직접 입력한다.

내장 Browser와 Cloud Browser는 각각 별도의 로그인 상태를 사용하므로 기존 Chrome의 로그인 정보나 열린 탭을 이용할 수 있다고 가정하지 않는다. 기존 Chrome 환경이 꼭 필요한 작업은 다른 Browser 사용 조건을 확인해야 한다.

#### 로컬에서 실행 중인 UI를 검증해야 하는 경우

구현 후 실제 프로젝트 화면을 확인할 때는 후보 탐색 단계보다 내장 Browser의 우선순위가 높아진다.

현재 코드가 반영된 로컬 개발 화면을 열 수 있다면 데스크톱 내장 Browser에서 다음을 확인한다. 원격 Cloud Browser에서 로컬 주소에 접근할 수 있다고 가정해서는 안 된다.

- 코드 변경이 실제 화면에 반영되었는가
- 선택한 시각적 특성이 유지되는가
- 구성 요소가 주변 화면과 어떻게 연결되는가
- 영향을 받는 상호작용 상태가 의도대로 보이는가
- 화면 크기에 따라 어떻게 바뀌는가
- 여러 화면에서 같은 규칙을 재사용하는가

사용자가 특정 화면 영역을 가리켜야 할 때는 데스크톱 내장 Browser에서 그 영역에 주석을 달 수 있다.

### Web Search에서 Browser로 바꾸는 기준

다음 질문을 기준으로 판단해야 한다.

검색 목록과 공식 문서만으로 현재 판단을 충분히 내릴 수 있는가.

실제 페이지를 보지 않으면 중요한 시각적 차이를 놓치는가.

직접 조작해야 확인할 수 있는 상태가 현재 결정에 중요한가.

검색 목록에서 찾은 이미지가 실제 서비스 UI인지 불확실한가.

앞으로 작성할 주장이 실제 화면을 관찰했다는 근거를 필요로 하는가.

검색 목록과 문서만으로 판단하기 어렵고, 나머지 질문 중 하나라도 그렇다면 현재 환경에서 쓸 수 있는 Browser로 확인해야 한다.

반대로 후보 찾기, 최신 공식 문서 조사, 여러 검색 방향 비교, 이슈 탐색처럼 조사 폭과 문서 근거가 중요하다면 Web Search를 계속 사용해야 한다.

### 도구 사용 순서

실제 서비스 UI를 조사할 때 기본 순서는 다음과 같다.

디자인 질문 정의

→ Web Search로 여러 관점에서 후보 찾기

→ 후보군 구성

→ 중복되거나 비슷한 후보 제외

→ 의미 있게 다른 해결 방법 확인

→ 심층 검토할 후보 선정

→ 각 후보에서 확인할 시각 근거 정의

→ 필요한 후보만 현재 환경에서 쓸 수 있는 Browser로 직접 확인

→ 사례별 독립 분석

→ 사례 간 비교

Browser를 심층 검토할 후보를 정한 뒤에만 사용할 수 있다는 뜻은 아니다.

후보 탐색 중에도 특정 이미지가 실제 서비스 화면인지 확인해야 다음 검색 방향을 정할 수 있다면 Browser를 사용할 수 있다.

이때 Browser는 새 후보를 하나씩 찾는 검색 도구가 아니라 Web Search에서 생긴 불확실성을 확인하는 도구로 사용한다.

## UI를 세부 수준까지 분석하지 못하는 문제

현재 스킬은 분위기, 정보 밀도, 모서리의 둥근 정도, 테두리, 그림자, 글자와 색처럼 화면 전체의 특성을 주로 본다.

이 정보만으로는 서비스마다 실제로 다른 점을 설명하기 어렵다.

여러 서비스를 조사하더라도 마지막에 `compact`, `neutral`, `small radius`, `clear hierarchy`처럼 구체적인 차이를 설명하지 못하는 표현만 남을 수 있다.

조사 근거에 정리한 Carbon의 구성 요소 지침은 사용해야 할 때와 피해야 할 때, 변형, 구조, 동작, 접근성까지 자세히 설명한다.

UI 규칙도 목적, 대안, 구성, 동작, 상태, 키보드와 초점, 화면 크기에 따른 변화 등을 구분해 설명할 수 있어야 한다.

#### 요구사항

심층 검토 대상으로 정한 사례는 현재 문제에 필요한 수준까지 나누어 분석해야 한다.

화면

→ 주요 영역 또는 화면 층

→ 구성 요소

→ 구성 요소의 내부 구조

→ 개별 요소

→ 상태

필요에 따라 다음 특성을 관찰한다.

- 화면 구성
- 탐색 구조의 위계
- 화면 영역의 위계
- 구성 요소 목록
- 구성 요소의 내부 구조
- 개별 요소의 배치
- 요소 안의 배치 방식
- 요소 사이의 간격
- 정보 밀도
- 글자 크기와 강조의 위계
- 보조 정보의 위치
- 주요 동작의 위치
- 보조 동작의 위치
- 아이콘 표현 방식
- 조작 가능성을 나타내는 표현
- 테두리 표현
- 구분선 표현
- 컨테이너 표현
- 형태
- 색으로 강조하는 방식
- 그림자 단계
- 줄바꿈
- 말줄임
- 스크롤
- 넘치는 내용의 처리
- 화면 크기에 따른 변화
- 상호작용 상태
- 일시적으로 나타나는 UI
- 움직임

모든 화면에서 모든 항목을 기계적으로 채우는 것은 목적이 아니다.

현재 디자인 질문에 영향을 주는 부분은 전체 분위기 설명에 그치지 않고 구성 요소와 개별 요소까지 조사해야 한다.

## 사례별 특징이 종합 과정에서 사라지는 문제

현재 구조에서는 여러 서비스를 조사한 뒤 곧바로 공통점을 추출할 수 있다.

그러면 서비스별 고유한 차이는 사라지고 여러 SaaS에서 흔히 보이는 평균적인 특징만 남는다.

#### 요구사항

심층 검토 대상으로 정한 사례는 다른 사례와 비교하기 전에 각각 분석을 마쳐야 한다.

첫 번째 사례 분석

→ 두 번째 사례 분석

→ 세 번째 사례 분석

→ 필요한 다른 사례 분석

→ 사례 간 비교

→ 종합

순서를 지켜야 한다.

개별 분석이 끝나기 전에 여러 사례의 공통점을 정리해서는 안 된다.

사례를 비교할 때 다음 차이를 보존해야 한다.

- 여러 사례에서 공통적으로 나타나는 방식
- 동일한 문제를 서로 다르게 해결하는 방식
- 특정 사례에만 나타나는 특징
- 다른 사례와 반대되는 선택
- 선택에 따른 장단점
- 아직 이유나 효과를 확인할 수 없는 차이

최종 종합 후에도 각 특징이 어느 사례에서 발견되었는지 추적할 수 있어야 한다.

## 외부 디자인 자료에 하나의 역할만 부여하는 문제

디자인 지침을 찾을 때는 자료의 종류에 따라 먼저 살펴볼 항목을 정할 수 있다.

WCAG와 WAI-ARIA APG에서는 접근성 제약, 의미 구조, 키보드 조작과 초점을 주로 확인한다.

Apple HIG에서는 탐색, 모달 동작과 피드백을 포함한 사용자 경험 원칙을 주로 확인한다.

Material에서는 구성 요소 체계, 의미를 담은 토큰 구조와 화면 적응 방식을 주로 확인한다.

Carbon에서는 기업용 UI 구성 요소의 쓰임, 대안, 작업 절차와 상태를 주로 확인한다.

Tailwind에서는 이미 정한 디자인 규칙을 코드로 표현하는 방법을 주로 확인한다.

이 구분은 자료를 고르는 출발점으로 유용하지만, 자료 전체에 하나의 고정 역할을 부여해서는 안 된다.

HIG에도 시각 표현 방식과 구성 요소 배치 지침이 있고, Material에도 구성 요소 선택과 화면 적응에 관한 지식이 있기 때문이다.

#### 요구사항

자료 전체가 아니라 거기서 확인한 개별 근거를 분류해야 한다.

필요한 경우 다음 관점으로 근거를 구분한다.

근거의 종류는 다음과 같다.

- 화면에서 직접 관찰한 내용
- 공식 지침
- 공식 명세
- 공식 구현
- 원본 코드
- 이슈 또는 PR
- AI가 제안한 시안

근거가 답하는 디자인 질문은 다음과 같이 나눌 수 있다.

- 서비스 목표
- 사용자 작업
- 정보 구조
- 화면 탐색
- 상호작용
- 구성 요소 선택
- 내부 구조
- 동작
- 시각 디자인
- 문구와 정보
- 접근성
- 화면 크기에 따른 변화
- 구현

필요하면 근거가 적용되는 대상과 조건도 적는다.

예를 들어 Apple 플랫폼의 규칙인지, 일반 웹에도 적용할 수 있는지, 특정 구성 요소에만 적용되는지 구분해야 한다.

자료마다 정해진 입력 항목을 만들거나 항상 전부 채우도록 요구하지 않는다.

서로 다른 종류의 근거를 하나의 사실처럼 합치지 않아야 한다.

## 화면에서 본 특징과 제작자가 밝힌 의도를 혼동하는 문제

실제 UI를 직접 보고 구분선이 있거나 부가 정보가 제목 아래에 놓였다는 사실은 관찰할 수 있다.

하지만 제작자가 그 배치가 빠른 훑어보기를 위한 것이라고 설명하지 않았다면, 그 이유는 AI의 해석일 수 있다.

#### 요구사항

다음 세 종류를 구분해야 한다.

### 직접 관찰한 내용

실제 UI, 이미지, 코드 또는 동작에서 직접 확인한 사실.

### 자료에 명시된 이유

공식 문서, 공식 디자인 글이나 제작자의 설명에서 확인한 디자인 목적과 이유.

### AI의 해석

화면에서 관찰한 특징과 출처가 뒷받침하는 사실을 바탕으로 AI가 추론한 가능성.

AI의 해석을 제작자가 밝힌 의도처럼 표현해서는 안 된다.

공식 설명이 없는 사례도 시각 비교 자료로 사용할 수 있지만, 제작 의도를 임의로 만들어서는 안 된다.

## UI의 공통점만 남기지 말고 비교할 선택지를 유지해야 한다

현재 구조에서는 여러 사례를 조사한 뒤 하나의 공통 원칙으로 합치기 쉽다.

그러나 서로 다른 사례는 같은 문제를 해결하는 여러 선택지일 수 있다.

#### 요구사항

조사 내용을 먼저 디자인 질문과 여러 해결 선택지로 정리해야 한다.

예를 들어 복잡하고 반복되는 정보를 찾아보는 방법에는 다음과 같은 선택지가 있을 수 있다.

- 조밀하게 이어지는 목록
- 구획을 나눈 카드 묶음
- 목록과 세부 내용을 나란히 보는 화면
- 필요한 정보를 단계별로 펼쳐 보이는 방식

그다음 현재 서비스의 조건을 기준으로 비교한다.

기준에는 필요에 따라 다음 내용을 포함할 수 있다.

- 반복 사용 빈도
- 항목 간 비교 필요성
- 한 화면의 정보량
- 사용 가능한 화면 폭
- 사용자의 숙련도
- 동작 빈도
- 현재 맥락을 유지할 필요
- 실수했을 때 발생하는 비용

스킬은 여러 선택지를 평균적인 하나의 형태로 합치기 전에 각 선택의 장단점을 보존해야 한다.

최종 시각 방향은 사용자의 선택과 현재 서비스의 목적을 바탕으로 정해야 한다.

## 일반 디자인 지침과 서비스 고유의 시각 방향이 섞이는 문제

Material과 Carbon 같은 디자인 시스템은 상호작용과 구성 요소 구조뿐 아니라 뚜렷한 시각 표현 방식도 제시한다.

따라서 이런 시스템의 시각 표현을 일반 UI 원칙처럼 그대로 적용하면, 서비스가 Material 또는 IBM의 시각적 특징을 그대로 닮을 수 있다.

디자인 지침을 참고할 때는 HIG에서 구성 요소를 선택하는 이유와 맥락 처리 방식을, Material에서 시스템 구조와 구성 요소 분류, 화면 적응 방식을 살펴볼 수 있다.

#### 요구사항

다음 두 종류의 지식을 구분해야 한다.

### 일반 디자인 지식

- 언제 사용하는지
- 언제 사용하지 않는지
- 대안
- 동작
- 접근성
- 화면 적응 방식
- 구성 요소의 내부 구조
- 상호작용 관례

### 서비스 고유의 시각 방향

- 글자 표현
- 정보 밀도
- 간격
- 형태
- 모서리 둥글기
- 테두리
- 화면 영역의 위계
- 색 사용 방식
- 아이콘 표현 방식
- 움직임의 특성
- 구성 요소의 시각적 변형

서비스 고유의 시각 방향은 실제 서비스 UI 조사, 서비스 목표와 제약, 사용자가 확인한 선택을 바탕으로 정한다.

Material, Carbon, HIG의 기본 외형을 현재 서비스의 기본값으로 자동 적용해서는 안 된다.

## 처음 보이는 UI 상태만 조사하는 문제

AI는 처음 보이는 UI를 먼저 분석하고 조작 뒤에 나타나는 UI를 빠뜨리기 쉽다.

예를 들어 마우스를 올린 상태, 키보드 초점, 활성 또는 선택 상태, 펼치거나 비활성화된 상태, 로딩, 빈 화면, 오류와 완료, 알림 토스트, 대화상자, 팝오버, 메뉴, 툴팁, 입력값 검증과 넘치는 내용이 누락될 수 있다.
- 화면 크기별 변화
- 테마별 변화

#### 요구사항

현재 디자인 질문에 영향을 주는 상태가 있다면 사례를 자세히 살펴보는 과정에서 확인해야 한다.

확인한 상태와 확인하지 못한 상태를 구분한다.

정지 화면 한 장만 확보했다면 화면에 나타나지 않은 상호작용까지 확인한 것으로 취급하지 않는다.

구현 단계에서도 현재 디자인 결정에 영향을 받는 상태를 검증 조건에 포함해야 한다.

## 스크린샷에서 정확한 디자인 값을 추정하는 문제

스크린샷을 통해 상대적인 특징을 관찰할 수는 있다.

예를 들어 가로 여백이 세로 여백보다 크거나 모서리가 덜 둥글어 보인다는 점은 화면에서 관찰한 내용으로 기록할 수 있다.

그러나 정지 화면만으로 여백, 모서리 둥글기, 글자 크기와 색의 정확한 값을 확정해서는 안 된다.

#### 요구사항

정확한 수치가 디자인 결정에 필요하면 다음과 같은 추가 근거를 찾아야 한다.

- 공식 디자인 명세
- 공식 디자인 토큰
- 공식 구성 요소 코드
- 공식 Storybook
- 실제 DOM 또는 CSS

검증 가능한 자료를 찾지 못하면 서로 비교할 수 있는 시각적 특징만 기록한다.

관찰한 값을 자동으로 서비스의 디자인 토큰으로 정해서는 안 된다.

반복해서 사용할 필요가 확인된 서비스별 결정만 적절한 단계에서 토큰으로 구체화한다.

---

## 이슈와 PR을 언제 조사할지 정하지 않은 문제

공식 디자인 문서는 의도된 동작을 설명하지만, 실제 구현에서 생기는 예외 상황까지 모두 보여주지는 않는다.

초점 이동, 스크롤, 포털, 중첩 오버레이, 고대비, 오른쪽에서 왼쪽으로 쓰는 언어, 화면 크기별 회귀 문제는 이슈와 PR에서 더 잘 드러날 수 있다.

그러나 모든 사례에서 이슈 추적기까지 조사하면 조사 비용이 지나치게 커진다.

#### 요구사항

다음 상황에서는 공식 이슈와 PR 조사를 검토해야 한다.

- 특정 구성 요소 라이브러리를 실제 프로젝트에 사용할 예정이다.
- 상호작용하는 구성 요소 여러 개를 함께 사용한다.
- 초점 이동이나 키보드 조작이 중요하다.
- 접근성이 중요한 판단 기준이다.
- 고대비, 테마, 오른쪽에서 왼쪽으로 쓰는 언어 같은 조건이 중요하다.
- 공식 문서와 실제 동작이 다르게 보인다.
- 현재 버전에서 알려진 문제가 해결되었는지 판단해야 한다.

이슈를 근거로 삼을 때에는 가능한 경우 다음을 함께 확인한다.

- 현재 상태
- 영향을 받는 버전
- 재현 조건
- 프로젝트 유지관리자의 판단
- 수정에 연결된 PR 또는 커밋
- 수정된 버전
- 현재 구현 대상과 조건이 같은지 여부

이슈와 PR은 구현 실패와 예외 상황을 보여주는 근거로 취급한다.

---

## 외부 디자인 지침을 스킬에 지나치게 복사하는 문제

HIG, Material, Carbon 등의 디자인 자료는 계속 변경된다.

현재 내용을 스킬에 대량으로 복사하면 시간이 지나면서 공식 문서와 달라지고, 스킬을 읽는 데 필요한 문맥도 불필요하게 늘어난다.

#### 요구사항

스킬은 외부 디자인 지침의 복사본이 아니라 필요한 지침을 찾아 확인하는 조사 절차를 설명해야 한다.

스킬에는 주로 다음을 정의한다.

- 어떤 디자인 질문에서 어떤 자료를 찾는가
- 각 자료에서 어떤 근거를 확인하는가
- 플랫폼별 지침을 어떻게 구분하는가
- 언제 실제 화면을 확인하는가
- 언제 원본 코드나 Storybook까지 살펴보는가
- 언제 이슈와 PR을 조사하는가
- 어떤 조건에서 추가 조사를 멈추는가

HIG, Material, Carbon의 현재 내용은 작업할 때 공식 자료에서 확인한다.

참고 문서는 필요한 단계에서만 읽어 불필요하게 읽을 분량을 줄여야 한다.

## 개선안: 스킬 문서 구성

현재 `discovery`, `preferences`, `implementation`, `validation`에 있는 후반 절차는 상당 부분 유지할 수 있다.

후보 검색, 화면 확인, 근거 분류와 선택지 비교는 각기 다른 책임으로 나누어야 한다.

다음 파일 구조는 책임을 나누는 한 가지 권장안이다. 별도 파일을 추가하는 일 자체를 필수 조건으로 삼지는 않는다.

```text
skills/use-progressive-user-interfaces/
├── SKILL.md
└── references/
    ├── sources.md
    ├── discovery.md
    ├── inspection.md
    ├── rationale.md
    ├── preferences.md
    ├── implementation.md
    └── validation.md
```

### SKILL.md

전체 작업 순서와 반드시 지킬 원칙을 정의한다.

각 단계에서 읽을 참고 문서를 안내한다.

Web Search와 사용할 수 있는 Browser의 선택 원칙도 이 파일에서 늘 적용되는 조건으로 요약한다.

### sources.md

HIG, Material, Carbon, WAI-ARIA, 실제 서비스 UI, 구현 코드, 이슈와 PR을 언제 조사할지 정의한다.

자료 전체에 고정 역할을 부여하지 않고, 개별 근거의 종류와 적용 조건을 구분하는 방법을 정의한다.

이 지침을 `discovery.md`와 `inspection.md`에서 이해하기 쉽게 유지할 수 있다면 별도 `sources.md`는 만들지 않아도 된다.

### discovery.md

Web Search를 중심으로 후보를 폭넓게 찾는다.

다음 순서로 진행한다.

검색 관점 결정

→ 여러 검색어 조사

→ 후보군 구성

→ 중복 후보와 비슷한 해결 방식 제외

→ 해결 방향의 다양성 확인

→ 추가 검색으로 얻을 내용 확인

→ 심층 검토 대상 선정

이 단계에서는 각 UI의 세부 시각 표현을 분석하지 않는다.

### inspection.md

심층 검토 대상으로 정한 사례를 자세히 살핀다.

화면에서 상태까지 필요한 수준으로 나누어 시각적 특징을 관찰한다.

실제 화면이나 상호작용을 확인해야 할 때는 현재 실행 환경에서 사용할 수 있는 Browser를 이용한다. 데스크톱 내장 Browser와 Cloud Browser의 접근 조건이 다르다는 점을 설명한다.

직접 관찰한 내용, 자료에 명시된 이유, AI의 해석과 확인하지 못한 내용을 구분한다.

### rationale.md

각 사례의 특징을 평균화하지 않고 디자인 질문, 선택지, 비교 기준과 장단점으로 정리한다.

각 선택지를 뒷받침하는 근거와 불확실성을 남긴다.

### preferences.md

사용자의 선택과 비선호, 적용 대상과 미결정 사항을 기록한다.

현재 구조의 주요 원칙을 유지한다.

### implementation.md

확정된 디자인 판단을 서비스에 적용할 원칙과 규칙으로 정리한다.

색상, 글자, 간격 외에도 다음 규칙을 포함할 수 있어야 한다.

- 정보 위계
- 구성 요소의 내부 구조
- 화면 영역의 구성
- 동작의 위치
- 보조 정보의 위치
- 정보 밀도
- 상태 표현
- 화면 크기에 따른 변화
- 상호작용에 따른 시각 표현

반복 사용이 필요하다고 확인된 규칙만 의미를 드러내는 토큰으로 구체화한다.

### validation.md

실행 중인 UI를 검증한다.

현재 구조를 유지하면서 필요한 경우 화면 크기, 상호작용 상태, 테마, 키보드 초점, 넘치는 내용, 언어를 확인한다.

실행 중인 로컬 UI를 열 수 있다면 데스크톱 내장 Browser를 우선적인 시각 검증 수단으로 고려한다. 원격 Cloud Browser에서도 로컬 주소를 열 수 있다고 가정하지 않는다.

## 개선 후 전체 작업 순서

새 디자인 질문이 생기면 다음 순서를 기본으로 한다.

서비스 목표 파악

→ 사용자 작업 파악

→ 살펴볼 화면과 상태 결정

→ 디자인 질문 정의

→ 필요한 자료 종류 결정

→ Web Search를 이용한 후보 탐색

→ 후보군 구성

→ 서로 다른 해결 선택지 확인

→ 심층 검토 대상 선정

→ 필요한 후보를 Browser로 직접 확인

→ 각 사례 독립 분석

→ 직접 관찰, 자료에 명시된 이유와 AI 해석 구분

→ 사례 간 차이 비교

→ 선택지, 비교 기준과 장단점 정리

→ 사용자 선택 확인

→ 서비스별 디자인 규칙 작성

→ 구현 입력 제공

→ 실행 중인 UI 검증

→ 재사용할 규칙 확정

기존 규칙으로 해결할 수 있는 화면에서는 이 작업을 처음부터 다시 하지 않는다.

새 디자인 질문이 생겼을 때 필요한 단계부터 다시 수행한다.

## 개선 후 확인 기준

개선된 스킬은 기존 버전과 같은 UI 과제를 수행해 달라진 점을 확인해야 한다.

### 자료 탐색의 폭

유명한 SaaS 한두 개만 찾고 조사를 끝내지 않는지 확인한다.

### 해결 방향의 다양성

서로 다른 서비스 이름을 찾는 데 그치지 않고 실제 해결 방식의 차이를 발견하는지 확인한다.

### 분석의 구체성

`clean`, `compact`, `neutral` 같은 넓은 표현에 그치지 않고 필요한 경우 구성 요소의 내부 구조와 상태까지 설명하는지 확인한다.

### 사례별 특징의 보존

최종 종합 후에도 각 사례의 독특한 디자인 선택을 출처까지 거슬러 확인할 수 있는지 확인한다.

### 근거 구분

직접 관찰한 사실, 공식 자료가 밝힌 이유와 AI의 해석이 서로 섞이지 않는지 확인한다.

### 적절한 도구 선택

후보를 넓게 찾거나 공식 자료를 조사할 때 Web Search를 사용하는지 확인한다.

실제 화면, 상호작용 상태, 로그인 후 화면을 확인할 때 현재 환경에서 제공되는 Browser를 사용하는지 확인한다. 로컬 UI를 검증할 때는 데스크톱 내장 Browser를 사용할 수 있는지 확인한다.

Browser를 단순 검색 도구로 반복 사용하지 않는지 확인한다.

반대로 실제 화면 근거가 필요한데 Web Search 목록만으로 관찰을 마쳤다고 주장하지 않는지 확인한다.

### 상태 확인

현재 디자인 결정에 중요한 일시적 UI와 상호작용 상태를 확인했거나, 확인하지 못했다고 명시하는지 확인한다.

### 정확한 수치의 근거

스크린샷만 보고 검증되지 않은 픽셀(px), 색상, 모서리 둥글기와 토큰 값을 만들어내지 않는지 확인한다.

### 서비스에 적용하는 이유

사례의 특징을 보기 좋다는 이유만으로 가져오지 않고 현재 서비스의 목표, 사용자 작업, 조건과 장단점을 근거로 설명하는지 확인한다.

### 조사 효율

모든 후보를 Browser로 열거나 모든 디자인 시스템 문서를 한꺼번에 읽지 않는지 확인한다.

후보를 폭넓게 찾는 단계와 화면을 자세히 분석하는 단계를 실제로 구분하는지 확인한다.

## 성공 조건

개선된 `use-progressive-user-interfaces`로 디자인 작업을 마친 뒤 다음 사항을 설명할 수 있어야 한다.

현재 해결한 디자인 질문이 무엇인지 설명할 수 있어야 한다.

왜 그 질문이 서비스와 사용자 작업에 중요한지 설명할 수 있어야 한다.

어떤 디자인 지침과 실제 서비스 UI를 조사했는지 설명할 수 있어야 한다.

실제 서비스들이 같은 문제를 어떤 서로 다른 방식으로 해결하는지 설명할 수 있어야 한다.

필요하면 그 차이를 화면, 영역, 구성 요소, 내부 구조, 개별 요소와 상태로 나누어 설명할 수 있어야 한다.

직접 관찰한 사실, 공식 자료가 설명한 이유와 AI가 추론한 내용을 구분할 수 있어야 한다.

사용자가 선택할 수 있는 디자인 선택지와 각각의 장단점을 보존할 수 있어야 한다.

사용자가 무엇을 선택하고 피하기로 했는지 적용 대상을 함께 설명할 수 있어야 한다.

선택한 내용을 서비스별 디자인 원칙과 규칙으로 정리할 수 있어야 한다.

구현된 실제 UI에서 정한 규칙이 의도한 특징을 유지하는지 검증할 수 있어야 한다.

여러 사례를 조사한 뒤에도 모든 SaaS에서 흔히 보이는 평균적인 디자인으로 압축되지 않아야 한다.

각 사례의 서로 다른 해결 방식과 세부적인 시각적 특징을 보존하면서 현재 서비스에 필요한 디자인을 선택할 수 있어야 한다.
