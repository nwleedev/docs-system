# 점진적 UI 선호 탐색 스킬 정비 계획

현재 이슈를 해결하기 위해 기존 자료의 역할을 잘못 해석하는 동작과 사용자 응답을 기다리는 단계가 이어지지 않는 동작만 고친다. 스킬에는 실제 UI 탐색, 시각적 비교, 사용자 선택, 규칙 정리와 실제 화면 검증만 남긴다. 저장 위치, 특정 입력 UI, 실행 환경과 다른 스킬은 필수 조건으로 두지 않는다.

이 계획은 스킬 작성자와 검토자가 기존 다섯 Markdown 파일을 정비하고 동작 사례로 확인하기 위한 문서다. 기준은 [요구사항](requirements.md)의 [프로젝트에 맞는 검색](requirements.md#프로젝트에-맞는-검색), [사용자 선택과 단계 결과](requirements.md#사용자-선택과-단계-결과), [단계 결과와 작업 재개](requirements.md#단계-결과와-작업-재개), [코드 수정과 시각적 검증의 역할](requirements.md#코드-수정과-시각적-검증의-역할), [스킬 제공 조건](requirements.md#스킬-제공-조건)이다. 근거와 한계는 [UI 탐색 대상과 응답 대기 상태 조사](references/scope-and-turn-continuity.md)를 따른다.

## 변경 범위

다음 파일만 수정한다.

- `skills/use-progressive-user-interfaces/SKILL.md`
- `skills/use-progressive-user-interfaces/references/discovery.md`
- `skills/use-progressive-user-interfaces/references/preferences.md`
- `skills/use-progressive-user-interfaces/references/implementation.md`
- `skills/use-progressive-user-interfaces/references/validation.md`

새 스크립트, 설정 파일, 외부 패키지, 상태 저장소와 고정된 결과 형식은 추가하지 않는다. 입력 UI의 표시 시간, 작업 상태 전환과 대화 보존 기능은 변경 범위에 포함하지 않는다. 애플리케이션 코드도 수정하지 않는다.

## 구현 순서

### 1. 스킬이 받을 정보와 반환할 정보를 정한다

`SKILL.md`에서 필수 절차를 다음 순서로 정의한다.

1. 현재 UI 판단에 필요한 목표, 사용자 작업과 화면을 정한다.
2. 기존 구현, 문서, 프로토타입과 생성 산출물의 역할을 구분한다.
3. 실제 UI를 관찰하고 시각적으로 구별되는 후보를 비교한다.
4. 사용자가 선택한 특성과 적용 범위를 확인한다.
5. 확인된 선호를 구현에 사용할 규칙과 검증 조건으로 정리한다.
6. 최신 실행 화면이 제공되면 규칙을 검증한다.

스킬 설명에는 새 탐색뿐 아니라 진행 중인 후보 비교에 대한 짧은 답변과 이전 단계 결과를 이용한 재개도 사용 시점으로 포함한다. 프로젝트 기록 위치를 먼저 정하는 절차, `main session` 같은 실행 주체, 특정 도구와 특정 입력 방식에 대한 문구는 제거한다.

확인은 스킬 본문만 읽어도 각 참고 문서를 언제 사용하는지, 어떤 입력을 받을 수 있는지, 각 단계가 무엇을 반환하는지 판단할 수 있는지로 한다.

### 2. 기존 자료에서 탐색 범위를 정하는 기준을 추가한다

`discovery.md`에서 예시 화면을 찾기 전에 이번에 판단할 사용자 작업과 시각적 질문을 정하도록 한다. 자료는 항목별로 다음 역할을 구분한다.

- 명시된 목표와 승인된 요구사항 또는 결정
- 보존 대상으로 확인된 기존 동작과 제약
- 기존 UI와 코드가 보여 주는 현재 상태
- 프로토타입, 생성 산출물과 초안이 제안하는 해결안
- 탐색을 위해 세운 가설
- 출처나 승인 상태를 확인하지 못한 항목

기존 구현에 없는 작업을 자동으로 제외하거나, 초안과 생성 산출물에 있는 동작을 자동으로 추가하지 않는다. 불명확한 항목이 이번 후보나 비교 질문을 바꿀 때만 사용자에게 확인한다. 실제 UI, 생성 시안과 출처 미확인 이미지를 구분하는 기존 규칙은 유지한다.

확인은 일부 화면만 구현된 HTML과 승인되지 않은 보조 기능이 들어 있는 생성 산출물을 각각 입력으로 삼아, 같은 자료가 현재 상태 또는 해결안 후보로만 사용되는지 살펴본다.

### 3. 기록 절차를 단계 결과와 응답 처리로 바꾼다

`preferences.md`는 저장 위치를 정하는 절차를 제거하고, 다음 단계에서 필요한 정보를 반환하는 절차로 바꾼다.

- 현재 탐색 주제와 단계
- 후보와 다시 확인할 수 있는 시각 자료
- 비교할 특성과 정확한 질문
- 확인된 선호와 비선호 및 적용 범위
- 미결정 사항, 임시 제안과 검증 상태
- 완료한 탐색 횟수와 응답 대기 중인 차례
- 다음 작업과 필요한 사용자 입력

별도 스키마를 만들지 않는다. 호출자가 이전 단계 결과를 제공하면 이를 사용하고, 없으면 이전 상태를 추정하지 않는다. 이미 확인한 사실을 다시 묻지 않되, 하나의 대기 질문을 식별할 수 없으면 필요한 부분만 확인한다.

구조화된 입력 기능이 있고 응답이 올 때까지 질문을 유지할 수 있으면 이를 사용할 수 있다. 그런 기능이 없으면 후보와 질문을 대화 응답으로 제시한다. 수락은 선택으로 반영하고, 명시적 거절은 제시한 선택지를 원하지 않는 것으로 처리하며, 취소나 무응답은 미결정 상태로 유지한다. 응답 전에 탐색 횟수를 늘리거나 다음 단계로 진행하지 않는다.

확인은 구조화된 입력 기능이 없는 경우, 사용자가 질문을 닫은 경우, 후보를 본 뒤 짧은 번호만 답한 경우와 이전 단계 결과가 없는 경우를 비교한다. 스킬 이름을 다시 요구하거나 취소를 선택으로 처리하면 실패다.

### 4. 구현 입력에서 실행 환경 가정을 제거한다

`implementation.md`는 선택한 특성을 구현 가능한 규칙과 검증 조건으로 바꾸는 일만 담당하게 한다. 구현 주체나 개발 절차를 특정하지 않고 다음 정보를 반환한다.

- 대상 화면과 사용자 작업
- 유지할 시각적 특성과 선택 근거
- 재사용할 원칙과 허용된 예외
- 검증 전 임시 값과 미결정 사항
- 피해야 할 특성
- 검증할 화면, 상태와 사용 조건

이미지 생성 기능은 사용할 수 있을 때만 시안 제작에 활용한다. 기능이 없거나 실패하면 실제 UI 근거만으로 결정할 수 있는지 확인하고, 필요한 시각적 판단은 미결정으로 남긴다. 이미지 생성 기능을 직접 구현하거나 특정 도구를 요구하지 않는다.

확인은 이미지 생성 기능이 없는 경우에도 이미 확보한 실제 UI를 이용한 규칙 정리가 가능한지, 생성 시안을 실제 서비스 근거나 검증된 규칙으로 바꾸지 않는지로 한다.

### 5. 검증 입력과 결과를 독립적으로 정의한다

`validation.md`는 제공된 사용자 선택, 구현 입력과 최신 실행 화면을 기준으로 검증한다. 프로젝트 기록이나 특정 실행 주체가 있어야 시작할 수 있다는 전제는 제거한다.

최신 화면과 현재 변경의 관계를 확인할 수 없으면 검증을 보류한다. 확인한 화면, 상태와 조건에 한해서만 규칙을 확정하고, 다른 화면에 재사용한 근거가 없으면 적용 범위를 넓히지 않는다. 구현 차이는 구현 입력으로, 선호 충돌은 사용자 선택으로 되돌려야 한다는 기존 분기는 유지한다.

확인은 생성 시안만 있는 경우, 빌드 결과만 있는 경우, 변경 전 화면만 있는 경우, 재사용 대상이 없는 경우와 다른 화면에서 차이가 발견된 경우로 한다.

## 전체 동작 확인

다섯 파일을 모두 수정한 뒤 아래 사례를 처음부터 끝까지 한 번씩 추적한다. 자동 검사 스크립트는 새로 만들지 않는다.

### 문서 체계와 구조화된 입력 기능이 없는 경우

사용자 목표와 제공된 화면만으로 후보를 비교하고 질문을 대화 응답으로 남길 수 있어야 한다. 저장 위치를 묻거나 탐색을 중단하면 실패다.

### 기존 구현이 불완전한 경우

명시된 목표에 필요한 작업이 기존 HTML에 없어도 탐색 대상에서 빠지지 않아야 한다. 기존 구현은 현재 상태의 근거로만 사용한다.

### 초안 산출물에 기능이 많은 경우

승인되지 않은 화면과 동작을 모두 현재 요구사항으로 승격하지 않아야 한다. 이번 시각적 판단에 필요한 항목만 후보 선정에 사용한다.

### 질문이 취소되거나 응답 전에 사라지는 경우

그 탐색 차례는 응답 대기 상태로 남아야 한다. 이전 단계 결과가 제공되면 같은 질문부터 이어 가고, 제공되지 않은 상태를 복원했다고 보고하지 않아야 한다.

### 사용자가 스킬 이름 없이 답하는 경우

하나의 대기 질문을 확인할 수 있으면 짧은 답변을 그 질문에 연결하고 다음 단계로 진행해야 한다. 여러 질문 중 어느 것인지 알 수 없을 때만 어느 질문에 대한 답인지 확인한다.

### 수정 후 화면을 검증하는 경우

새 레퍼런스 탐색부터 반복하지 않고 제공된 선택과 검증 조건을 최신 화면에 적용해야 한다. 구현 성공 메시지만으로 시각적 검증을 완료하면 실패다.

## 보류할 항목

질문 식별자, 단계 결과의 버전, 중복 응답 방지와 만료 규칙은 현재 문제를 해결하는 데 필수적이지 않으므로 추가하지 않는다. 오래된 질문의 답이 새 질문에 연결되거나 같은 답이 두 번 반영되는 사례가 확인될 때 검토한다.

입력 UI가 계속 표시되는지, 응답 대기 상태가 비종료 작업으로 유지되는지와 다음 사용자 메시지에서 스킬이 자동으로 선택되는지는 실행 환경에서 확인할 문제다. 스킬 설명과 단계 결과는 이 실패의 영향을 줄일 수 있지만 해결을 보장하지 않는다.

## 완료 조건

- 기존 구현과 생성 산출물의 존재만으로 탐색 범위를 추가하거나 제외하지 않는다.
- 실제 UI 탐색부터 사용자 선택, 구현 입력과 최신 화면 검증까지 필수 절차가 유지된다.
- 저장 위치, 다른 스킬, 특정 입력 UI, 실행 모드와 구현 주체가 필수 조건으로 남지 않는다.
- 응답 대기 상태는 후보, 질문과 다음 작업을 포함한 단계 결과로 전달된다.
- 구조화된 입력 기능의 유무와 관계없이 같은 사용자 선택 의미를 유지한다.
- 취소와 무응답은 선택이나 탐색 완료로 처리되지 않는다.
- 검증하지 않은 선호와 생성 시안이 확정 규칙으로 바뀌지 않는다.
- 파일 간 용어와 링크를 확인하고 한국어 표현 검사를 마친 뒤 최종 리뷰를 한 번만 수행한다.
