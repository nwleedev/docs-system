# 점진적 UI 디자인 스킬 구현 계획

연구용 스킬 `use-progressive-user-interfaces`를 하나의 `SKILL.md`와 네 참고 문서로 구성한다. 먼저 프로젝트 문서에서 진행 상태를 복원하고, 실제 UI 탐색, 사용자 선택, 잠정 시각화와 구현 입력, 수정 후 검증을 연결한다. 애플리케이션 코드 수정은 메인 세션에 맡긴다.

이 계획은 스킬 작성자와 검토자가 승인된 요구사항을 지침으로 구현하고 실제 사용에서 확인하기 위한 문서다. 기준은 같은 묶음의 [요구사항](requirements.md)이며, 작업별 적용 절은 아래에 연결한다. 역할 판단은 [코드 수정과 시각적 검증 결정](decisions/code-editing-and-visual-validation.md), 예외 처리는 [탐색, 기록과 검증 결정](decisions/workflow.md)을 따른다.

## 작성할 파일과 제외할 작업

저장소의 `skills/`는 연구 자료를 두는 곳이므로, 첫 구현도 다른 프로젝트에서 조정해 사용할 수 있는 Markdown 지침으로 작성한다. 설치나 배포를 완료한 스킬로 표현하지 않는다. [스킬 제공 조건](requirements.md#스킬-제공-조건)에 따라 다음 파일을 작성한다.

- `skills/use-progressive-user-interfaces/SKILL.md`
- `skills/use-progressive-user-interfaces/references/discovery.md`
- `skills/use-progressive-user-interfaces/references/preferences.md`
- `skills/use-progressive-user-interfaces/references/implementation.md`
- `skills/use-progressive-user-interfaces/references/validation.md`

첫 구현에는 실행 스크립트, 외부 패키지, 별도 서버나 자료 저장 서비스를 추가하지 않는다. 브라우저와 이미지 생성은 현재 실행 환경에서 제공하는 도구를 사용하며 별도로 구현하지 않는다. Excalidraw와 tldraw는 [관찰 예시](requirements.md#예시와-구현-요구사항의-구분)로만 취급하고 스킬의 기본 후보나 구현 대상으로 고정하지 않는다.

[개발 지침](../../dev/README.md)은 후속 변경의 기술 지침을 선택할 기준이다. 현재 계획은 Markdown 지침 작성이므로 MJS 스캐너의 개발 규칙을 스킬 구현에 적용하지 않는다. 실행 코드나 의존성이 필요해지면 이 계획 밖에서 추가하지 말고 필요한 변경과 적용 지침을 먼저 검토한다.

## 작성 순서와 확인 방법

### 진행 단계와 필수 중단 조건

`SKILL.md`에 사용 시점, 프로젝트 맥락 확인, 기존 기록 읽기와 단계 선택을 작성한다. [사용자 선택의 확인과 기록](requirements.md#사용자-선택의-확인과-기록), [규칙 축적과 재탐색](requirements.md#규칙-축적과-재탐색), [현재 목표에 포함하지 않는 일](requirements.md#현재-목표에-포함하지-않는-일)을 기준으로 필요한 참고 문서만 직접 읽도록 연결한다.

새 작업은 프로젝트 용도와 현재 필요한 화면부터 확인한다. 재개한 작업은 기록된 선택, 남은 판단과 다음 작업부터 읽는다. 수정 후 실행 화면을 받은 작업은 탐색을 다시 시작하지 않고 검증 단계로 이동한다. 충돌이나 검증 실패가 있으면 원인에 따라 사용자 선택 또는 구현 입력 단계로 돌아가게 한다.

확인은 신규 요청, 기록이 있는 요청, 수정 후 검증 요청을 각각 읽고 어떤 문서로 이동하는지 추적하는 방식으로 한다. 코드 변경을 직접 수행하거나 사용자 선택 없이 규칙을 확정하는 지시가 없는지도 확인한다.

### 실제 UI 탐색과 후보 제시

`discovery.md`에 [프로젝트에 맞는 검색](requirements.md#프로젝트에-맞는-검색), [레퍼런스로 사용할 자료](requirements.md#레퍼런스로-사용할-자료), [접근 실패 처리](requirements.md#실제-ui에-접근하지-못했을-때), [비교 후보의 차이](requirements.md#비교-후보의-차이)와 [시각 자료의 역할](requirements.md#시각-자료의-역할)을 구현한다.

검색 관점을 나누고 후보의 실제 화면을 관찰한 뒤, 사용자에게 확인할 차이를 골라 비교한다. 서비스와 화면의 이름, 원본 위치, 관찰한 이미지와 상태를 연결해 관찰 근거를 남기는 방법을 설명한다. 필요하면 화면 크기와 확인 날짜를 함께 적되, 모든 프로젝트에 새로운 고정 문서 형식을 만들지는 않는다.

실제 UI에 접근하지 못하면 다른 실제 UI를 더 다양한 관점에서 탐색한다. 서비스 분야, 화면과 상호작용 방식, 정보 밀도 등 [프로젝트에 맞는 검색](requirements.md#프로젝트에-맞는-검색)의 관점을 바꾸어 후보를 다시 찾는 절차를 작성한다. 탐색 횟수와 종료 판단은 [탐색을 끝낼 조건](requirements.md#탐색을-끝낼-조건)을 유지한다.

확인은 도움말만 검색된 경우, 한 서비스에 접근할 수 없는 경우, 반드시 관찰할 서비스가 막힌 경우와 출처가 불명확한 사용자 이미지를 받은 경우를 비교한다. 접근 실패 사례에서는 어떤 검색 관점을 바꾸었고 어떤 다른 실제 UI를 찾았는지 확인한다. 실제 UI, 생성 시안과 출처 미확인 자료가 같은 근거로 제시되지 않아야 한다. 정상 사례에서는 일반적으로 3~5개인 후보가 서로 다른 시각적 판단을 돕는지 확인한다.

### 사용자 선택, 탐색 횟수와 기록 재개

`preferences.md`에 [사용자 선택의 확인과 기록](requirements.md#사용자-선택의-확인과-기록), [기록 위치와 작업 재개](requirements.md#기록-위치와-작업-재개), [탐색을 끝낼 조건](requirements.md#탐색을-끝낼-조건)을 구현한다. 실제 선호는 스킬 파일이 아닌 참여 프로젝트의 문서에 기록하도록 한다.

선택한 속성과 적용 대상을 구분하고, 미결정, AI 가설과 임시 구현값이 확인된 선호와 섞이지 않게 한다. 충돌하는 선택은 기존 규칙 변경, 예외, 특정 대상에 한정하거나 미결정으로 남기는 방안을 사용자에게 설명한다. 기록할 위치가 없으면 최초 사용 시 정하고, 기존 확정 지침은 중복 생성하지 않는다.

후보 제시 후 피드백까지 한 차례로 계산한다. 피드백 대기, 전부 거절, 판단 보류와 접근 실패를 각각 설명하고, 기본 3회 이후에는 사용자가 선택한 행동만 수행하게 한다. 종료에 필요한 원칙 3~7개와 비선호, 재사용할 제약을 정리하되 모든 속성의 확정을 기다리지 않는다.

확인은 한 후보에서 버튼 모양만 선택한 사례, 기존 원칙과 충돌한 사례, 두 차례 탐색 후 재개한 사례와 세 차례 모두 판단을 보류한 사례로 한다. 원래 선택과 횟수가 유지되고, 자동 연장이나 새로운 주제 탐색이 시작되지 않아야 한다.

### 잠정 시각화와 메인 세션에 전달할 구현 입력

`implementation.md`에 [시각적 방향과 필요한 디자인 규칙](requirements.md#시각적-방향과-필요한-디자인-규칙), [새로운 조합의 시각화와 실제 UI 검증](requirements.md#새로운-조합의-시각화와-실제-ui-검증), [코딩 에이전트용 산출물](requirements.md#코딩-에이전트용-산출물)을 구현한다. 이 문서에서는 메인 세션이 승인된 변경을 구현할 때 사용할 디자인 판단과 확인 조건을 정하며, 디자인 스킬에 코드 수정 책임을 부여하지 않는다.

이미지 생성 도구를 사용해 서로 다른 레퍼런스에서 고른 특징을 프로젝트 화면에 조합하는 절차를 작성한다. 생성 이미지는 시안으로 표시하고, 실제 UI 근거와 섞지 않는다. 도구를 사용할 수 없으면 가능하다고 보고하지 않고, 이미 확보한 실제 화면으로 판단할 수 있는지 확인하거나 필요한 시각화를 보류한다.

메인 세션에 전달할 내용에는 대상 화면, 유지할 특성, 사용자 선택의 근거, 기존 규칙, 허용된 예외, 임시 값, 피해야 할 스타일과 검증할 조건을 포함한다. 검증용 임시 변경안과 재사용할 확정 지침을 구분해, 아직 검증하지 않은 값도 임시 상태로 구현할 수 있게 한다. 디자인 스킬은 `tokens.css`, 테마 설정이나 컴포넌트 파일을 직접 변경하지 않는다.

확인은 이미지에서 선택한 특징이 구현 입력에 유지되는지, 임시 값이 확정 명세로 전달되지 않는지, 서비스 이름만으로 스타일을 설명하지 않는지로 한다. 새로운 속성이 필요하지 않은데 전체 토큰이나 컴포넌트 체계를 만들도록 요구하는 내용도 없어야 한다.

### 수정 후 실제 UI 검증과 규칙 확정

`validation.md`에 [변경 영향에 따른 검증과 규칙 확정](requirements.md#변경-영향에-따른-검증과-규칙-확정), [코드 수정과 시각적 검증의 역할](requirements.md#코드-수정과-시각적-검증의-역할), [규칙 축적과 재탐색](requirements.md#규칙-축적과-재탐색), [초기 디자인 시스템의 완료 조건](requirements.md#초기-디자인-시스템의-완료-조건)을 구현한다.

메인 세션이 수정한 코드로 실행한 최신 화면을 받아 합의한 조건과 비교한다. 화면에서 유지된 특징, 차이, 예외와 확인하지 못한 조건을 사용자에게 제시한다. 차이를 고치려면 구현 입력 단계로 돌아가고, 선호나 공통 규칙을 바꿔야 하면 사용자 선택을 다시 확인한다. 새로운 시각적 의문이 없으면 레퍼런스를 다시 찾지 않는다.

공통 규칙은 다른 기존 화면이나 컴포넌트에서 재사용한 모습까지 확인한다. 적용할 다른 대상이 없으면 확인한 대상에 한정해 기록한다. 검증된 규칙과 적용 조건만 기존 확정 지침에 반영하고, 한 화면의 검증 완료와 초기 디자인 시스템의 완료를 따로 판단한다.

확인은 생성 이미지만 있는 경우, 빌드 성공 메시지만 있는 경우, 변경 전 스크린샷이 전달된 경우, 다른 대상에서 재사용 차이가 발견된 경우와 재사용 대상이 없는 경우로 한다. 앞의 세 경우에는 실제 UI 검증이 끝났다고 판단하지 않아야 한다. 재사용 차이는 미해결로 남기고, 검증 대상을 만들기 위해 새 애플리케이션을 작성하지 않아야 한다.

## 문서 연결과 실제 사용 확인

네 문서의 초안이 갖춰지면 `SKILL.md`에서 각 문서를 직접 찾을 수 있는지, 동일한 규칙을 여러 문서에서 다르게 정의하지 않았는지 검토한다. 링크, 파일명, 비어 있는 파일, 미완성 표시와 한국어 표현을 검사한다. 자동 검사가 없다는 이유로 검사 스크립트를 새로 추가하지 않는다.

그다음 사용자가 제공하거나 사용을 승인한 프로젝트에서 실제 UI 관찰부터 선택 기록과 재개까지 확인한다. 구현 후 검증은 메인 세션이 승인된 코드 수정을 마쳤고, 최신 실행 화면을 확인할 수 있을 때 진행한다. 스킬 작성 작업 자체가 참여 프로젝트의 코드 변경을 승인하지는 않는다.

작성자는 어떤 입력에서 어떤 문서를 읽고, 무엇을 보여 주고 기록하며, 어디서 사용자 판단을 기다렸는지 확인할 근거를 남긴다. 검토자는 실제 UI 관찰 여부, 임시 결정의 유지, 코드 수정 책임과 검증 후 규칙 확정을 확인한다. 사용자의 선호와 규칙 변경 승인은 사용자가 직접 판단한다.

[사용 과정에서 확인할 성과](requirements.md#사용-과정에서-확인할-성과)는 사용 후 관찰할 항목으로 유지한다. 비교 작업과 집계 방법이 없는 상태에서 시간, 토큰이나 수정 횟수 감소를 입증했다고 보고하지 않는다. 스킬 지침 작성 완료와 실제 사용 검증 완료를 구분한다.

## 멈추거나 다시 확인할 조건

스킬 지침 작성을 막는 운영 방식의 미결정 사항은 없다. 다만 참여 프로젝트의 기록 위치, 이번에 검증할 화면과 상태는 스킬 실행 시 사용자와 정할 값이다.

실제 사용 확인에 필요한 프로젝트, 화면이나 접근 도구가 없으면 그 확인을 미완료로 남긴다. 사용자 피드백이 없으면 같은 탐색 차례에서 기다리고, 기본 탐색 제한 이후의 행동이나 기존 규칙 변경을 임의로 결정하지 않는다. 최신 실행 화면이 없으면 확정 규칙 갱신을 보류한다.

스킬에 애플리케이션 코드 수정, 외부 패키지나 새 저장 서비스를 맡겨야 한다는 판단이 생기면 영향을 받는 작업을 멈추고 요구사항 작성자에게 확인한다. 요구사항이 바뀌면 이 계획의 적용 절과 검증 방법을 다시 검토한다.
