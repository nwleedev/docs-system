# UI 탐색 대상과 응답 대기 상태 조사

현재 스킬은 시각 자료의 출처와 사용자 선호의 승인 상태는 구분하지만, 프로젝트 자료만으로 구현할 화면과 동작을 결정해도 되는지 판별하지 않는다. 또한 사용자 응답을 기다리라고 지시하면서도 후보와 질문을 먼저 저장하는 순서를 정하지 않는다. 요구사항에는 프로젝트 자료의 승인 상태를 판별하고 질문 전에 복원 가능한 상태를 기록하며, 후속 응답에서 스킬 이름을 다시 요구하지 않는 동작을 추가했다. 스킬 설계자와 검토자는 이 세 동작을 함께 구현해야 한다.

이 문서는 [프로젝트에 맞는 검색](../requirements.md#프로젝트에-맞는-검색), [기록 위치와 작업 재개](../requirements.md#기록-위치와-작업-재개), [스킬 제공 조건](../requirements.md#스킬-제공-조건)을 검토하기 위한 조사 자료다. 요구사항에 반영한 동작과 아직 구현하지 않은 변경 제안을 구분한다. 저장소와 외부 자료는 2026-09-10에 확인했다.

## 조사 질문

- 기존 React, HTML, 요구사항 문서와 Claude Artifact에서 어떤 화면과 동작을 현재 탐색 대상으로 삼아야 하는가?
- 후보를 제시한 직후 실행이 끝나거나 사용자가 입력 UI를 닫아도 선택과 탐색 상태를 어떻게 이어 가야 하는가?
- `SKILL.md`로 고칠 수 있는 부분과 실행 환경의 책임은 무엇인가?

## 현재 구현과 변경 이력

따라서 확인된 문제를 최근 스킬 수정에서 생긴 회귀로 볼 근거는 없다. 최초 절차에서 규정하지 않은 사례가 실제 사용에서 드러났다고 보는 편이 현재 이력에 맞는다.

### 구현하거나 탐색할 화면과 동작을 정하는 근거가 없다

[스킬 본문](../../../../skills/use-progressive-user-interfaces/SKILL.md)은 프로젝트 목적, 현재 필요한 화면이나 컴포넌트, 기존 디자인 지침과 진행 기록을 먼저 파악하도록 한다. 그러나 “현재 필요”를 누가 승인했는지, 기존 구현과 문서가 요구사항인지 관찰 자료인지 판별하는 절차는 없다.

[탐색 절차](../../../../skills/use-progressive-user-interfaces/references/discovery.md)는 실제 UI, 생성 시안과 출처를 확인하지 못한 이미지를 구분한다. 이 구분은 시각 자료를 어디까지 근거로 쓸 수 있는지 정하지만 프로젝트 입력의 권한은 정하지 않는다. 기존 React나 HTML, 초안 문서와 Artifact가 각각 승인된 요구사항, 잠정 해결안 또는 오래된 구현 중 무엇인지 알 수 없다.

[선택 기록 절차](../../../../skills/use-progressive-user-interfaces/references/preferences.md)는 프로젝트, 대상 화면, 탐색 주제와 시각적 선택을 기록한다. 화면과 동작 후보의 출처, 승인 상태, 현재 탐색에 포함하거나 제외한 이유는 기록 대상이 아니다. 이 때문에 같은 모호성에서 상반된 판단이 나올 수 있다.

- 기존 구현에 있는 화면만 필요하다고 보아 명시된 목표에 필요한 사용자 작업을 누락한다.
- 초안 요구사항이나 생성된 Artifact에 나타난 화면과 동작을 모두 현재 디자인 탐색에 포함한다.

### 응답 대기 전에 복원 지점을 만들라는 지시가 없다

[탐색 절차](../../../../skills/use-progressive-user-interfaces/references/discovery.md)는 후보와 질문을 제시한 다음 피드백을 기다리라고 한다. [스킬 본문](../../../../skills/use-progressive-user-interfaces/SKILL.md)은 단계가 끝날 때 기록을 갱신하라고 한다. 후보 제시와 응답 사이에 실행이 끝나는 경우, 어느 지시가 먼저 적용되어야 하는지 명확하지 않다.

[선택 기록 절차](../../../../skills/use-progressive-user-interfaces/references/preferences.md)는 응답을 기다리는 차례와 다음 행동을 기록 대상으로 정했다. 그러나 후보를 보여 주기 전에 이 정보를 저장해야 한다는 순서, 저장 실패 시 후보 제시를 중단하는 조건, 입력 UI가 취소된 경우의 재개 방식은 없다. 기존 구현은 대화가 정상적으로 이어진 뒤 기록을 갱신하는 경우에는 작동할 수 있지만, 응답 대기 자체가 실행 중단점이 되는 환경에서도 작동한다고 확신할 수 없다.

## 외부 근거

### 프로토타입과 Artifact의 화면을 모두 구현 대상으로 볼 수 없다

[GOV.UK의 프로토타입 지침](https://www.gov.uk/service-manual/design/making-prototypes)은 프로토타입을 구현에 착수하기 전에 여러 디자인을 탐색하고 시험하는 수단으로 설명하며, 시험에서 좋지 않은 평가를 받은 프로토타입은 버릴 수 있다고 밝힌다. 코드 프로토타입도 운영 코드와 같은 기준을 충족하지 않으며 그대로 복사하지 말라고 한다. [GOV.UK의 alpha 지침](https://www.gov.uk/service-manual/agile-delivery/how-the-alpha-phase-works)은 전체 사용자 여정을 모두 만들 필요 없이 위험한 가정을 시험하는 데 필요한 만큼만 구현하라고 한다.

[Anthropic의 Artifact 안내](https://support.anthropic.com/en/articles/9487310-what-are-artifacts-and-how-do-i-use-them)는 Artifact를 대화와 분리된 창에서 편집하고 반복하거나 나중에 재사용할 수 있는 독립 산출물로 설명한다. 문서, 코드, 웹사이트와 React 컴포넌트가 모두 같은 형식에 들어갈 수 있다. 따라서 Artifact라는 형식만으로 그 안의 화면과 동작이 승인된 요구사항인지 판별할 수 없다는 결론은 이 설명과 일치한다. 이 결론은 Anthropic이 요구사항 관리 규칙을 명시했다는 뜻이 아니라, 여러 성격의 산출물이 같은 형식을 사용한다는 사실에서 도출한 것이다.

[GOV.UK의 사용자 요구 조사 지침](https://www.gov.uk/service-manual/user-research/start-by-learning-user-needs)은 사용자에게서 나오지 않은 의견과 제안을 검증할 가정으로 분류하고, 요구는 해결안보다 사용자가 해결하려는 문제에 초점을 맞추라고 한다. [NIST의 인간 중심 디자인 개요](https://www.nist.gov/itl/iad/human-centered-technologies/human-factors-human-centered-design)도 사용 맥락 파악, 사용자 요구사항 명시, 디자인 해결안 작성과 평가를 서로 다른 활동으로 둔다.

이 자료를 함께 보면 파일 종류나 구현 완성도가 아니라 출처와 승인 상태로 구현하거나 탐색할 화면과 동작을 판별해야 한다. 승인된 요구사항과 결정은 현재 목표의 근거가 될 수 있다. 기존 구현, 프로토타입, 생성된 Artifact와 초안 문서는 현재 상태나 해결안 후보를 보여 주지만, 별도 근거 없이 화면이나 동작을 추가하거나 제외하는 권한은 갖지 않는다.

또한 서비스가 제공할 모든 동작과 이번 시각 탐색에서 확인할 사용자 작업은 같지 않다. 승인된 동작이어도 현재 디자인 질문을 판단하는 데 필요하지 않으면 이번 후보 탐색에서 구현하거나 비교할 이유가 없다. 반대로 기존 구현에 없어도 현재 디자인 질문을 판단하는 대표 사용자 작업이라면 요구사항 근거를 확인한 뒤 탐색 대상에 포함할 수 있다.

### 사람의 응답을 기다리는 실행은 먼저 상태를 보존해야 한다

[OpenAI의 스킬 작성 지침](https://developers.openai.com/codex/skills)은 스킬을 명시적으로 호출하거나 설명과 맞는 작업에서 자동으로 불러오며, 명령형 단계가 받을 자료와 남길 자료를 명확히 적고 실제 프롬프트로 동작을 시험하라고 한다. 이 문서는 한 차례 명시적으로 부른 스킬이 다음 사용자 메시지에서도 자동으로 활성화된다고 명시하지 않는다. 따라서 짧은 선택 응답만으로 스킬이 다시 선택될 것이라고 전제해서는 안 된다는 판단은 문서의 활성화 방식에서 도출한 것이다.

[OpenAI 모델 지침](https://developers.openai.com/api/docs/guides/latest-model)은 불명확하거나 충돌하는 스킬 지침이 모델을 일찍 멈추게 할 수 있으므로 스킬과 다른 지침을 점검하라고 한다. 또한 사용자 판단이 필요할 때 이미 할 수 있는 일을 먼저 마쳐 사용자가 검토할 안을 구체화하도록 권한다. 현재 스킬의 기록 시점과 응답 대기 순서를 명확히 해야 한다는 근거가 된다.

[OpenAI Agents SDK의 사람 승인 절차](https://openai.github.io/openai-agents-python/human_in_the_loop/)는 실행을 멈출 때 `RunState`를 직렬화하고, 판단을 받은 뒤 원래 실행을 그 상태로 재개한다. [MCP 2025-11-25의 사용자 입력 요청 명세](https://modelcontextprotocol.io/specification/2025-11-25/client/elicitation)는 응답을 수락, 거절과 취소로 구분하며, 취소를 명시적 거절과 다르게 처리하도록 한다. 같은 버전의 [작업 명세](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/tasks)는 `input_required`를 완료나 실패가 아닌 진행 중 상태로 정의한다.

세 자료의 구현 방식은 다르지만 공통 조건은 같다. 질문을 제시한 상태는 작업 완료가 아니며, 실행을 재개할 식별 정보와 상태가 질문보다 먼저 보존되어야 한다. 사용자가 입력 UI를 닫거나 클라이언트가 표시를 중단한 경우도 선택이나 거절로 기록하면 안 된다.

## 검토한 수정 의견

### “예시 화면에 의존하지 않는다”만 추가하는 방안은 문제를 충분히 설명하지 못한다

현재 스킬은 실제 서비스 UI를 직접 관찰해 사용자의 시각적 선호를 찾는 일을 목적으로 한다. 따라서 예시 화면에 의존하지 말라는 지시는 실제 UI를 판단 근거로 사용하는 정상 동작까지 제한할 수 있다. 또한 `SKILL.md`에는 Excalidraw와 tldraw를 기본 후보나 구현 대상으로 삼지 말라는 지시가 이미 있다.

실제 누락은 화면이 예시인지 여부가 아니라, 프로젝트 자료가 승인된 요구사항인지 현재 상태의 증거인지 잠정 해결안인지 판별하는 절차다. 기존 React와 HTML을 무시하지 않고 현재 상태와 보존할 동작을 확인하는 데 사용하되, 그 구현에 없는 작업을 곧바로 불필요하다고 판단해서는 안 된다. 초안 요구사항과 Artifact도 탐색 가설로 사용할 수 있지만, 그 안의 모든 화면과 동작을 승인된 요구사항으로 취급해서는 안 된다.

### “스킬을 계속 호출하라”는 안내는 복구 절차로 채택하지 않는다

재호출 안내는 사용자가 매번 스킬 선택과 작업 상태 복원을 책임지게 한다. 안내 문구는 후보 선택 UI의 표시 시간을 늘리거나, 질문을 받은 작업을 응답 대기 상태로 바꾸거나, 다음 메시지에 이전 상태를 연결하지 못한다.

공식 스킬 작성 지침에 따르면 스킬은 현재 프롬프트에서 명시적으로 호출되거나 요청이 스킬 설명과 일치할 때 선택된다. 따라서 `SKILL.md`의 설명에는 진행 중인 UI 비교에 답하거나 기록된 탐색을 재개하는 요청도 사용 조건에 포함해야 한다. 다만 자동 선택 여부는 실행 환경이 정하므로, 설명 변경과 별도로 질문 전 기록과 복원 절차가 필요하다.

사용자에게는 스킬을 다시 호출하라고 요구하는 대신 선택 방법을 분명하게 안내한다. 입력 도구를 사용할 수 없으면 후보와 질문을 대화의 마지막 응답으로 남기고, 다음 메시지에서는 기록된 응답 대기 상태부터 계속한다. 입력 UI가 사라진 경우에도 응답이 없었다는 상태를 유지한다.

## 변경 제안

### 프로젝트 자료의 역할부터 분류한다

스킬은 시각 탐색 전에 구현하거나 탐색할 화면과 동작을 새로 추측하지 말고, 이번 판단에 필요한 입력을 아래 상태로 분류할 수 있어야 한다.

- 현재 목표와 승인된 요구사항 또는 결정
- 보존이 확인된 기존 동작과 기술 제약
- 기존 UI와 코드가 보여 주는 현재 상태
- 프로토타입, Artifact, 초안 문서가 제안하는 해결안이나 화면과 동작에 관한 가설
- AI가 탐색을 위해 세운 가설
- 출처나 승인 상태를 확인하지 못한 항목

같은 파일 안에서도 항목별 상태가 다를 수 있다. 문서 제목이 `requirements`라는 이유로 모든 내용을 승인된 요구사항으로 처리하거나, 구현에 없다는 이유로 목표에서 제외하지 않는다. 상태가 불명확한 항목 중 이번 디자인 질문의 선택을 바꾸는 항목만 사용자에게 확인한다.

시각 탐색에는 서비스의 모든 화면과 동작을 넣지 않고, 현재 시각적 결정을 검증할 대표 작업과 상태만 넣는다. 무엇을 포함하고 제외했는지, 그 판단이 승인된 요구사항인지 조사 제안인지 프로젝트 기록에서 찾을 수 있어야 한다.

### 후보를 보여 주기 전에 응답 대기 상태를 기록한다

후보 비교를 한 차례의 실행으로 끝내려 하지 말고, 아래 순서를 명시할 필요가 있다.

1. 각 후보의 식별 정보, 화면 근거, 비교할 특성과 표시 가능한 자료 위치를 기록한다.
2. 사용자에게 물을 질문, 허용되는 응답, 현재 차례가 `feedback pending`이라는 상태와 응답 후 다음 행동을 기록한다.
3. 기록을 다시 읽어 후보와 질문을 복원할 수 있는지 확인한다.
4. 실행 환경이 응답을 기다릴 수 있는 입력 도구를 제공하면 한 번 호출하고 응답이 올 때까지 다른 단계나 완료 답변을 만들지 않는다.
5. 그런 도구가 없으면 후보와 질문을 대화의 최종 응답으로 제시하고 실행을 끝낸다. 다음 메시지에서는 기록된 `feedback pending` 상태부터 재개한다.
6. 입력 UI가 취소되거나 응답 없이 사라지면 차례를 완료로 세지 않고 같은 후보와 질문을 기록에서 복원한다.

기록에 후보 이름만 남겨서는 시각 비교를 복원할 수 없다. 사용자가 다시 볼 수 있는 이미지나 실행 화면의 위치, 관찰 상태, 비교 질문을 함께 남겨야 한다. 저장할 수 없는 일시적인 화면만 있는 경우에는 복원 가능하다고 보고하지 않고, 다시 확보해야 할 자료를 다음 행동으로 기록한다.

스킬 설명에는 진행 중인 UI 후보 비교에 답하는 후속 메시지에도 이 스킬을 적용한다는 뜻을 넣는 방안을 검토할 수 있다. 다만 자동 활성화와 입력 UI 수명은 실행 환경이 정하므로, 이 문구만으로 작업이 재개된다고 판단하면 안 된다.

### 실행 환경에서 별도로 확인할 사항

`SKILL.md`는 기록 순서와 재개 절차를 정할 수 있지만, 입력 UI를 계속 표시하거나 같은 실행을 재개시키지는 못한다. 다음 현상은 실행 환경의 로그와 UI 상태로 별도 확인해야 한다.

- 후보를 제시한 뒤 모델이 완료 응답을 생성해 입력 UI가 닫혔는가?
- 입력 요청이 완료되지 않았는데 작업 상태가 `completed`로 바뀌었는가?
- 사용자의 클릭 전에 클라이언트가 요청을 취소했는가?
- 다음 사용자 메시지가 기존 작업과 기록 위치에 연결되었는가?
- 후속 메시지에서 스킬이 다시 선택되지 않아도 주 대화가 기록된 다음 행동을 실행할 수 있는가?

실행 환경이 응답 대기 상태와 재개 가능한 실행을 제공하지 않으면, 스킬 변경만으로 선택지가 계속 보이게 만들 수 없다. 이 경우 대화에 남는 최종 질문과 프로젝트 기록을 복구 수단으로 사용하면서 호스트 문제를 따로 고쳐야 한다.

## 확인 사례 제안

### 기존 구현 때문에 필요한 작업을 빠뜨리는 사례

프로젝트 목표에는 주요 작업이 명시되어 있지만 기존 HTML에는 일부 화면만 있다. 스킬은 HTML을 현재 상태로 기록하고, 목표와 승인된 요구사항에서 이번 디자인 질문에 필요한 대표 사용자 작업을 정해야 한다. 구현에 없다는 이유만으로 그 작업을 제외하면 실패다.

### 초안 산출물 때문에 불필요한 작업을 넣는 사례

Claude Artifact나 초안 요구사항에 승인되지 않은 보조 화면이나 동작이 포함되어 있다. 스킬은 이를 해결안 가설로 남기고, 현재 시각 판단에 필요하거나 승인된 화면과 동작만 조사 대상으로 삼아야 한다. 파일에 있다는 이유만으로 모든 화면을 후보 탐색이나 시안에 넣으면 실패다.

### 후보 제시 직후 실행이 끝나는 사례

후보를 보여 준 직후 실행이 끝나도 기록에는 후보 근거, 비교 질문, 미완료 차례와 다음 행동이 이미 있어야 한다. 후속 메시지에서 같은 후보를 복원하고, 이전 차례를 완료로 중복 계산하지 않아야 한다.

### 입력 UI가 취소되는 사례

사용자가 선택하지 않은 채 입력 UI를 닫거나 클라이언트가 요청을 취소한다. 스킬은 취소를 선호, 비선호나 거절로 기록하지 않고 `feedback pending`을 유지해야 한다. 다음 실행에서 같은 질문을 복원할 수 있어야 한다.

## 한계와 필요한 판단

현재 자료만으로 실제 중단이 모델의 완료 응답, 입력 도구 사용 순서 또는 클라이언트 결함 중 어디에서 시작됐는지 확정할 수 없다. 재현 시점의 대화 내용, 입력 요청 상태와 작업 상태 변화가 필요하다.

[요구사항](../requirements.md)은 프로젝트 자료의 승인 상태, 대표 작업과 화면의 선정 근거, 질문 전 기록, 취소 후 복원과 스킬 재호출이 필요 없는 후속 응답을 규정한다. 현재 `SKILL.md`와 참고 문서는 아직 이 요구사항을 구현하지 않았다. 실행 환경의 입력 UI와 작업 상태 변경은 이 저장소의 스킬 문서와 별도 책임으로 남는다.
