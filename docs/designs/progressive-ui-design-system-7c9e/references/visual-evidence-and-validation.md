# 실제 UI 근거와 디자인 규칙 검증 기준

실제 화면을 비교하고 선택을 점진적으로 규칙에 반영하는 방향은 유지할 수 있다. 다만 실제 UI의 출처와 관찰 상태, 자료를 구하지 못했을 때의 처리, 규칙 확정에 필요한 검증 수준이 정해져야 같은 요구사항으로 작업하는 에이전트들이 다른 결론을 내리지 않는다.

이 자료는 스킬의 요구사항을 검토하는 사람을 위한 조사 자료다. [실제 UI 탐색과 시각적 비교](../requirements.md#실제-ui-탐색과-시각적-비교), [새로운 조합의 시각화와 실제 UI 검증](../requirements.md#새로운-조합의-시각화와-실제-ui-검증), [초기 디자인 시스템의 완료 조건](../requirements.md#초기-디자인-시스템의-완료-조건)을 구체화할 때 참고한다. 아래 보완 문구는 제안이며 요구사항으로 확정되지 않았다.

외부 자료와 실제 화면은 2026-09-05에 확인했다. 공식 문서는 자료 접근 방법과 디자인 시스템 운영 원칙을 확인하는 근거로 사용했으며, 문서 사이트의 외형을 UI 레퍼런스로 사용하지 않았다.

## 실제 UI에서 확인할 수 있는 내용

실행된 화면은 같은 분야의 서비스에서도 다른 디자인 선택을 보여준다. 브라우저 MCP로 두 화이트보드 서비스의 로그인 전 초기 편집 화면을 열고, 1200 × 1200 화면 크기의 스크린샷을 직접 비교했다. 두 서비스는 탐색 방법의 확인 사례이며, 참여 프로젝트의 디자인 후보로 선정한 것이 아니다.

### Excalidraw

[Excalidraw의 실제 편집 화면](https://excalidraw.com/)에는 상단 중앙의 가로 도구 모음, 왼쪽 아래의 확대와 축소 조작, 흰 캔버스가 보였다. 선택한 도구에는 연보라색 배경을 사용했고, 초기 안내에는 손글씨 형태의 글자를 사용했다.

이 관찰은 초기 화면의 도구 배치와 선택 강조 방식에 한정된다. 모든 컴포넌트, 편집 상태나 다른 화면 크기에서도 같은 원칙을 사용하는지는 확인하지 않았다.

### tldraw

[tldraw의 실제 편집 화면](https://www.tldraw.com/)에는 하단 중앙의 도구 모음과 오른쪽 위의 색, 선과 크기 속성 패널이 보였다. 캔버스는 밝은 회색이었고, 선택한 도구와 로그인 버튼에는 파란색을 사용했다.

이 관찰도 로그인 전 초기 편집 상태에 한정된다. 협업 상태, 도형 선택 후의 변화나 전체 디자인 토큰을 확인한 근거로 사용할 수 없다.

### 비교로 확인한 한계

두 화면 모두 그리기 도구를 제공하지만 도구 모음의 위치, 속성 패널의 표시와 선택 강조색은 다르다. “화이트보드”라는 분야 이름만으로 시각적 특징을 정할 수 없으며, 한 장의 화면으로 서비스 전체의 규칙을 일반화할 수도 없다.

초안의 “시각적 특징을 파악한다”는 조건에는 어느 화면에서 무엇을 봤는지 확인할 증거가 필요하다. 다음 문구를 보완안으로 제안한다.

> 비교 후보에는 서비스와 화면의 이름, 원본 위치, 확인 날짜, 화면 크기와 상태, 직접 본 이미지나 실행 화면을 함께 제시한다. 관찰한 특징과 AI의 해석을 구분하고, 프로젝트의 어떤 화면이나 작업에 참고할 수 있는지 설명한다.

이 제안은 관찰 항목을 정하는 데 쓰며, 특정 파일 형식이나 저장 도구를 정하지 않는다. 반드시 기록할 항목과 “충분히 파악했다”는 판단 기준은 아직 확정되지 않았다.

## 실제 UI 자료에 접근하지 못했을 때

UI 자료 모음이 있어도 현재 환경에서 자동으로 접근할 수 있다고 가정할 수 없다. [Mobbin의 공식 MCP와 API 안내](https://docs.mobbin.com/overview)는 자료 모음에 접근하는 MCP와 REST API를 구분하고, 인증과 이용 가능한 요금제를 명시한다. 이 사실은 외부 자료의 존재와 실제 사용 가능 여부가 다르다는 근거다. 이번 조사에서 Mobbin의 인증된 자료나 개별 화면을 조회한 것은 아니다.

현재 요구사항은 도움말을 UI 레퍼런스로 사용하는 일을 금지하지만, 로그인이나 유료 접근 때문에 실제 화면을 구하지 못한 경우의 다음 행동은 정하지 않았다. 도움말 페이지를 임의로 대신 사용해서는 안 된다는 점은 분명하다.

처리 방안으로는 접근 가능한 다른 실제 서비스 탐색, 사용자가 제공한 화면 활용, 필요한 자료를 확보할 때까지 비교 보류가 있다. 어떤 방안을 기본으로 삼을지와 출처를 확인하지 못한 스크린샷을 허용할지는 사용자의 판단이 필요하다. 특정 외부 서비스의 연동이나 구독을 요구사항으로 추가할 근거는 없다.

## 탐색 제한과 미결정 상태

최대 3회라는 탐색 제한은 종료 시점을 정하지만, 제한에 도달해도 디자인 방향을 정하지 못한 경우의 처리는 설명하지 않는다. [탐색을 끝낼 조건](../requirements.md#탐색을-끝낼-조건)의 제한과 정보 확보 조건을 모두 만족하지 못하는 경우가 남아 있다.

“한 차례”가 후보 검색부터 사용자 피드백까지인지, 검색 도구 호출 횟수인지도 구분해야 한다. 후보가 모두 부적합하거나 사용자가 선택을 보류했을 때 한 차례로 계산하는지도 정해져 있지 않다.

보완 문구로 다음을 제안한다.

> 탐색 한 차례는 비교 후보를 제시하고 사용자 피드백을 확인하는 과정으로 센다. 제한에 도달해도 선호가 정해지지 않았으면 미결정으로 남기며, 잠정 시각화, 탐색 연장 또는 보류 중 다음 행동을 사용자와 정한다.

탐색 연장은 현재의 기본 제한에 예외를 추가하므로 승인 없이 적용할 수 없다. 한 차례에 3~5개 후보, 원칙 3~7개, 탐색 최대 3회라는 수치는 초안의 운영 기준이다. 아래 공식 자료들로 최적의 수치라고 입증되지는 않았다.

## 시각적 선호와 규칙 확정의 차이

생성 이미지에 대한 선호만으로 실제 UI 동작까지 검증했다고 볼 수는 없다. [GOV.UK Design System의 기여 기준](https://design-system.service.gov.uk/community/contribution-criteria/)은 새로운 컴포넌트의 유용성과 중복 여부를 살피고, 배포 전에는 사용자 조사, 기존 스타일 재사용과 여러 환경에서의 동작을 확인한다. 확인한 사용 조건을 명확히 밝히는 일도 요구한다.

[W3C의 Focus Visible 해설](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html)은 키보드로 조작할 때 현재 초점이 어디 있는지 보여주는 상태를 설명한다. 생성 이미지 한 장은 애플리케이션을 조작하며 초점이 이동하는 동작을 증명하지 못한다. 이는 외형 확인과 실행 중 상태 확인을 구분해야 한다는 판단 근거다.

현재 요구사항의 “가능한 경우” 시각화와 “충분히 검증된” 규칙은 서로 다른 해석을 허용한다. 스킬이 이미지로 확인한 방향을 어디까지 확정할지, 실제 UI 검증이 끝나지 않은 값은 어떻게 다룰지 정해야 한다. 보완 문구로 다음을 제안한다.

> 생성 이미지로 확인한 선택은 시각적 방향에 대한 사용자 선호로 기록한다. 실제 UI에서 값이나 동작을 확인하지 않았다면 임시 결정으로 구분하며, 검증한 화면과 상태를 넘어 일반화하지 않는다.

이 제안은 이미지 생성의 역할을 유지하면서 검증 근거를 구분하는 안이다. 특정 접근성 준수 수준이나 모든 상태의 검사를 자동으로 요구하지 않는다. 현재 프로젝트의 접근성, 반응형 화면, 언어, 밝은 테마와 어두운 테마를 어느 수준까지 확인할지도 별도 판단이 필요하다.

## 규칙을 점진적으로 축적하는 방향

원칙부터 시작해 필요한 규칙과 코드로 구체화하는 방식은 이미 운영되는 디자인 시스템에서도 확인할 수 있다. [USWDS 성숙도 모델](https://designsystem.digital.gov/maturity-model/)은 “You don’t need to adopt the design system all at once.”라고 설명하며, 원칙, 사용자 경험 지침과 코드의 순서로 도입을 나눈다.

[GOV.UK의 기여 기준](https://design-system.service.gov.uk/community/contribution-criteria/)은 기존 컴포넌트와 중복되는지, 기존 스타일을 재사용하는지 확인한다. 두 자료를 비교하면 한 번에 모든 컴포넌트를 만들지 않고 기존 규칙을 먼저 사용하는 방향에는 운영 사례가 있다. 다만 이는 개인의 취향을 발견하는 이번 스킬의 성과를 직접 입증하지 않는다.

[Design Tokens Format Module 2025.10](https://www.designtokens.org/tr/2025.10/format/)은 토큰을 사람이 읽을 수 있는 이름과 값에 연결된 정보로 정의하고, 도구 사이에서 이를 교환하는 형식을 설명한다. 2025-10-28의 안정된 Community Group 보고서이며 W3C 표준은 아니다. 이 명세는 값을 전달하는 형식의 근거가 될 수 있지만, 사용자가 그 값을 선호하거나 사용을 승인했다는 증거를 대신하지 않는다.

따라서 시각적 원칙, 사용자의 선택과 토큰의 실제 값을 구분하는 초안의 방향은 유지할 수 있다. DTCG 형식 채택, 특정 프레임워크 테마와 파일 구조는 이번 요구사항에서 확정하지 않는다. 초안에 있던 참고 파일 구조 역시 예상안이므로 필수 파일 구성으로 취급하지 않는다.

## 역할과 완료 증거에서 남은 판단

대표 화면의 코드 수정 책임은 [실제 UI 검증 요구사항](../requirements.md#새로운-조합의-시각화와-실제-ui-검증)에 미결정으로 남아 있다. 스킬이 코드까지 수정하는 방식과 코딩 에이전트에 맡기는 방식은 필요한 작업 권한과 산출물이 다르므로, 이를 정하기 전에는 구현 절차를 확정하기 어렵다.

[초기 디자인 시스템의 완료 조건](../requirements.md#초기-디자인-시스템의-완료-조건)은 주요 실제 UI에서의 일관성과 새 화면에서의 재사용을 요구한다. 그러나 어떤 화면을 대표로 고르고 누가 어떤 자료로 완료를 판단하는지까지는 정하지 않았다. 다음 보완안을 검토할 수 있다.

> 검증할 대표 화면과 확인할 상태를 사용자와 정한다. 초기 규칙을 만든 화면과 그 규칙을 재사용한 다른 화면을 비교하고, 사용자가 확인한 일관성과 남은 예외를 기록한다.

반복 요청과 수정 작업이 얼마나 줄어야 성공인지 임의로 정할 근거도 없다. [사용 과정에서 확인할 성과](../requirements.md#사용-과정에서-확인할-성과)를 평가하려면 기존 방식과 비교할 작업, 반복 요청과 직접 수정의 집계 방법, 기록 담당자를 정해야 한다. 비교 조건이 정해지기 전까지 비용 감소와 일관성 향상은 검증할 가설로 유지한다.

상태 기록의 저장 위치, 이전 작업을 재개할 때 확인할 자료와 확정 지침의 갱신 방식도 후속 설계에서 정할 사항이다. 선호의 종류가 나뉘어 있다는 것만으로 세션 사이에 이전 선택이 보존된다고 볼 수는 없다.
