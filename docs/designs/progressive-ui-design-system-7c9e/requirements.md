# 점진적 UI 디자인 시스템 구축 스킬 요구사항

이 스킬은 참여하는 프로젝트와 유사한 서비스의 실제 UI를 찾아 시각적 특징을 파악하고, 사용자와 비교하면서 확인한 선호를 프로젝트에 맞는 디자인 규칙으로 축적한다. 현재 필요한 UI부터 검증하고, 새로운 화면에서도 재사용할 수 있는 초기 디자인 시스템과 코딩 에이전트용 지침을 제공한다.

이 요구사항 초안은 스킬 설계자와 검토자가 필요한 동작과 완료 조건을 확인하기 위한 문서다. 스킬 사용자는 시각 자료를 보고 선호와 규칙 변경을 판단하며, 스킬은 탐색과 비교를 돕고 확인된 선택을 정리한다.

## 해결하려는 문제

사용자가 원하는 UI를 언어로 정확하게 설명하지 못해도, 실제 화면을 비교하면서 선호를 구체화할 수 있어야 한다. 최초 요청은 취향을 알아보기 위한 출발점으로 취급하며, 곧바로 완성된 UI 명세나 CSS로 해석하지 않는다.

이 과정은 레퍼런스 검색, 스크린샷 전달, 반복 요청과 직접 CSS 수정에 드는 부담을 줄이는 데 목적이 있다. 화면과 컴포넌트를 추가해도 디자인의 일관성을 유지하고, 사용자가 처음부터 모든 디자인 토큰과 컴포넌트를 결정하지 않아도 필요한 규칙을 갖춰 나갈 수 있어야 한다.

## 실제 UI 탐색과 시각적 비교

### 프로젝트에 맞는 검색

참여 프로젝트의 용도와 현재 필요한 화면을 고려해 유사한 서비스의 UI를 찾는다. 추상적인 요청 전체를 검색어 하나로 사용하지 않고, 필요한 검색 관점으로 나누어 탐색한다.

검색 관점에는 서비스 분야, 화면이나 상호작용 방식, 분위기, 정보 밀도, 형태와 모서리 반경, 배경 영역의 구분과 입체감, 테두리, 타이포그래피, 색과 강조색, 사용자가 피하려는 특성이 포함될 수 있다.

### 레퍼런스로 사용할 자료

실제로 출시된 서비스의 UI와 UI 사례를 모아 제공하는 자료를 우선한다. 도움말, 문서, 블로그와 검색 유입을 목적으로 만든 페이지를 실제 UI 레퍼런스로 사용하지 않는다. 스킬은 실제 화면을 시각적으로 살펴보고 프로젝트의 디자인 판단에 사용할 특징을 파악해야 한다.

가능하면 자료의 출처와 실제 서비스에서 사용되는 화면인지 확인한다. 제안용 디자인과 AI 생성 이미지는 실제 운영 중인 서비스의 UI와 같은 근거로 취급하지 않는다.

### 실제 UI에 접근하지 못했을 때

실제 UI에 접근하지 못하면 다른 실제 UI를 더 다양한 관점에서 탐색한다.

[프로젝트에 맞는 검색](#프로젝트에-맞는-검색)의 관점을 바꾸어 프로젝트에 적합한 후보를 찾는다. 적합한 대안도 없으면 사용자에게 화면 제공을 요청하거나 비교를 보류한다. 사용자가 특정 서비스를 반드시 관찰하도록 지정했다면 임의로 대체하지 않고 다음 행동을 확인한다.

사용자가 제공한 이미지의 출처를 확인하지 못해도 취향을 묻는 자료로 사용할 수 있다. 다만 실제 출시된 서비스의 UI라는 근거로 확정하지 않는다. 도움말이나 생성 이미지로 실제 UI 근거를 대신하지 않는다.

### 예시와 구현 요구사항의 구분

Excalidraw와 tldraw는 실제 UI를 관찰하고 비교하는 방법을 설명하기 위한 예시다. 두 서비스를 본떠 스킬 또는 서비스를 구현하라는 요구사항이 아니다. 실제 레퍼런스는 참여 프로젝트의 목적과 필요한 화면에 맞춰 선정한다.

### 비교 후보의 차이

비교 후보는 초기 요구에 맞으면서도 시각적으로 구별되는 특성을 가져야 한다. 거의 같은 화면을 여러 개 나열하지 않으며, 일반적으로 한 차례에 3~5개의 후보를 제시한다. 후보 수를 채우는 것보다 사용자가 아직 판단하지 못한 취향을 알아보는 데 도움이 되는지를 우선한다.

유명 서비스 하나를 일찍 정해 복제하는 방향으로 진행하지 않는다. 사용자는 한 후보의 정보 밀도, 다른 후보의 타이포그래피와 또 다른 후보의 배경 구분 방식을 각각 선택할 수 있어야 한다.

### 시각 자료의 역할

외형의 차이는 실제 UI 레퍼런스, 실행된 UI 또는 생성 이미지로 비교한다. ASCII 아트, 문자로 그린 와이어프레임이나 긴 Markdown 설명으로 화면 외형을 대신하지 않는다. 텍스트는 사용자가 시각 자료에서 살펴볼 차이를 설명하는 데 사용한다.

## 사용자 선택의 확인과 기록

확인된 선호, 확인된 비선호, 판단하지 못한 요소, AI의 탐색 가설과 구현을 위한 임시 결정을 구분한다. AI가 추상적인 표현에서 추론한 특성을 사용자의 확정된 취향으로 기록하지 않는다.

사용자가 특정 화면을 골랐다는 이유로 그 화면의 모든 속성을 선호한다고 판단하지 않는다. 가능한 경우 유지할 부분, 제거할 부분, 다른 후보에서 가져올 부분과 아직 판단하기 어려운 부분을 확인한다.

선택은 확인한 대상과 근거에 맞게 적용한다. 예를 들어 버튼 하나의 모서리를 선택한 것만으로 애플리케이션 전체의 모서리 반경을 확정하지 않는다.

새 선택이 기존 디자인 원칙이나 규칙과 충돌하면 자동으로 덮어쓰지 않는다. 스킬은 충돌하는 내용을 사용자에게 보여주고, 기존 규칙 수정, 예외 추가, 특정 컴포넌트에만 적용하는 규칙 또는 미결정 중 어떻게 처리할지 확인한다.

### 기록 위치와 작업 재개

선호와 진행 상태는 참여 프로젝트의 기존 디자인 문서 체계에 기록한다. 적절한 위치가 없으면 최초 실행에서 사용자와 저장 위치를 정하고 이후에도 같은 위치를 사용한다. 기존 확정 지침이 있으면 같은 내용을 다른 문서에 중복 저장하지 않는다.

기록에는 확인한 선호와 비선호, 미결정 사항, 탐색 주제와 진행 횟수, 임시 구현안과 검증된 규칙, 관찰 근거, 검증한 화면과 다음 작업을 구분한다. 작업을 재개할 때에는 이 기록을 먼저 읽는다.

스킬의 참고 문서는 기록 절차를 설명하며, 개별 프로젝트의 선호와 진행 상태를 저장하는 용도로 사용하지 않는다.

## 탐색을 끝낼 조건

하나의 디자인 주제는 기본적으로 최대 3회의 탐색으로 제한한다. 3회를 모두 진행할 필요는 없으며, 추가 검색보다 UI를 만들어 확인하는 편이 판단에 도움이 되면 탐색을 마친다.

후보를 제시하고 사용자 피드백을 확인하면 탐색 한 차례로 센다. 후보를 모두 거절하거나 판단하기 어렵다고 답한 경우도 한 차례에 포함한다. 피드백을 기다리는 동안은 같은 차례가 진행 중인 상태로 유지한다. 내부 검색과 도구 호출은 따로 세지 않는다. 접근 실패로 비교 자료를 제시하지 못했다면 횟수에 포함하지 않고 [실제 UI에 접근하지 못했을 때](#실제-ui에-접근하지-못했을-때)의 절차를 따른다.

3회가 끝나도 방향을 정하지 못하면 자동 검색을 멈추고 미결정으로 남긴다. 사용자가 불확실성을 표시한 잠정 시각화, 추가 횟수를 정한 탐색 연장 또는 주제 보류 중 다음 행동을 선택한다. 잠정 시각화를 선택해도 임시 결정을 확정 규칙으로 바꾸지 않는다.

다음 UI를 설계할 수 있을 정도로 아래 내용이 확보되면 초기 탐색을 마친다.

- 서로 구별할 수 있는 시각적 방향
- 디자인 방향을 설명하는 원칙 3~7개
- 사용자가 피하려는 특성
- 다음 UI에도 적용할 수 있는 디자인 제약

모든 디자인 속성이 확정될 때까지 검색하지 않으며, 탐색을 마친 뒤 새로운 디자인 주제를 자동으로 시작하지 않는다.

## 시각적 방향과 필요한 디자인 규칙

최종 디자인 규칙은 서비스 이름이 아니라 사용자가 선택한 시각적 특성으로 표현한다. “Linear 스타일”이나 “Vercel처럼”이라는 말만으로 규칙을 남기지 않는다.

현재 UI를 구현하고 검증하는 데 필요한 공통 규칙만 정의한다. 색과 배경 영역, 타이포그래피, 간격, 형태와 모서리 반경, 테두리, 그림자와 높이 표현을 필요에 따라 정하며, 처음부터 전체 토큰 계층이나 모든 컴포넌트를 만들지 않는다.

가능하면 CSS 값보다 디자인 원칙과 사용 의미를 먼저 유지한다. 예를 들어 “배경 영역은 주로 테두리로 구분한다”는 원칙을 정하고, 실제 값이 필요해졌을 때 테두리 토큰으로 구체화할 수 있어야 한다.

## 새로운 조합의 시각화와 실제 UI 검증

실제 서비스의 UI는 취향을 발견하는 근거로 사용한다. 생성 이미지는 발견한 특성을 참여 프로젝트의 화면에 조합해 살펴보는 시안으로 사용하며, 실제 서비스 사례로 제시하지 않는다.

새로운 디자인 원칙의 조합을 규칙으로 확정하기 전에 가능한 경우 실행된 UI 또는 생성 이미지로 확인한다. 서로 다른 방향을 비교할 때에는 후보마다 의미 있는 차이를 두고, 가능하면 독립된 이미지나 화면으로 제시한다. 같은 화면의 미세한 변형만 늘려 후보 수를 채우지 않는다.

실제 UI 검증은 현재 프로젝트에서 새로운 디자인 판단을 확인하기에 적합한 대표 화면이나 컴포넌트부터 시작한다. 모든 컴포넌트를 한꺼번에 만들지 않는다. 사용자는 적용된 화면을 보고 다음을 판단할 수 있어야 한다.

- 선택한 시각적 특징이 유지되는가
- 컴포넌트들의 외형이 같은 디자인 원칙을 따르는가
- 레퍼런스에서는 좋았지만 현재 애플리케이션에서는 어색한 선택이 있는가
- 추가로 정해야 할 속성이 있는가

### 변경 영향에 따른 검증과 규칙 확정

구현 전에 이번 디자인 판단을 확인할 대표 화면, 상태와 사용 조건을 사용자와 정한다. 대표 화면에서 선택한 특징을 확인하고, 변경의 영향을 받는 선택, 오류, 비활성, 키보드 초점 등의 상태를 살펴본다. 프로젝트가 지원하는 화면 크기, 테마와 언어 중 변경의 영향을 받는 조건도 확인한다.

공통 규칙으로 확정하려면 적용 가능한 다른 기존 화면이나 컴포넌트에서 재사용한 모습을 확인한다. 다른 적용 대상이 아직 없으면 검증을 위해 화면을 억지로 만들지 않고, 확인한 대상에 한정된 규칙으로 남긴다. 생성 이미지에 대한 선호와 실제 UI에서 검증한 규칙을 구분하며, 검증하지 않은 대상까지 일반화하지 않는다.

한 화면의 검증 완료와 [초기 디자인 시스템의 완료](#초기-디자인-시스템의-완료-조건)를 구분한다. 사용자가 판단할 수 있도록 검증한 화면과 조건, 남은 차이와 예외를 기록한다.

### 코드 수정과 시각적 검증의 역할

애플리케이션 코드 수정은 메인 세션이 담당하고, 디자인 스킬은 디자인 판단과 시각적 검증을 담당한다. 메인 세션은 참여 프로젝트의 작업을 진행하는 주 대화의 코딩 에이전트를 뜻한다. 이는 디자인 스킬을 사용하는 단계와 프로젝트 개발 단계의 역할 구분이며, 별도 에이전트 실행이나 권한 분리를 전제로 하지 않는다.

디자인 스킬은 레퍼런스 관찰 근거, 사용자 선택, 적용 조건과 시각적 검증 기준을 정리하며, 애플리케이션 소스 코드를 직접 변경하지 않는다. 메인 세션은 승인된 변경을 프로젝트의 개발 지침에 따라 구현하고 기존 동작을 검사한다. `tokens.css`, 프레임워크 테마 설정과 컴포넌트 파일의 수정도 애플리케이션 코드 변경에 포함한다.

메인 세션은 코드 수정 후 디자인 스킬의 시각적 검증 절차를 다시 적용한다. 수정한 코드로 실행된 최신 화면을 디자인 기준과 비교하고, 사용자가 유지된 특징과 남은 차이를 판단할 수 있도록 제시한다. 명세 전달이나 빌드 성공만으로 시각적 검증을 마치지 않는다.

## 규칙 축적과 재탐색

사용자 피드백을 받을 때마다 화면 한 곳의 스타일만 고치지 않고, 다른 UI에도 적용할 수 있는지 판단한다. 재사용할 수 있는 선택은 디자인 원칙, 공통 속성이나 용도에 따른 규칙, 디자인 토큰 중 적합한 수준으로 정리한다. 특정 컴포넌트에만 필요한 선택은 그 컴포넌트에 한정한다.

새 화면이나 컴포넌트에는 기존 규칙과 토큰을 먼저 적용한다. 기존 규칙으로 표현할 수 없는 실제 요구가 생겼을 때만 시스템을 확장하며, 컴포넌트가 추가됐다는 이유만으로 토큰을 늘리지 않는다. 시스템의 성과는 규칙과 컴포넌트의 수보다 현재 UI를 일관되게 표현하는지로 판단한다.

후속 작업은 필요한 UI에 기존 규칙을 적용하고 시각화한 뒤 사용자에게 확인받는 순서로 진행한다. 기존 규칙과 현재 화면만으로 해결하기 어려운 새로운 시각적 의문이 생겼을 때만 레퍼런스를 다시 찾는다. 규칙을 수정하거나 추가하면 UI에 적용해 다시 확인한다.

## 코딩 에이전트용 산출물

충분히 검증된 규칙만 코딩 에이전트가 따를 확정 명세로 제공한다. 아직 검증하지 않은 선호나 임시 값을 최종 규칙으로 고정하지 않는다.

현재 프로젝트에 필요한 형태로 디자인 원칙, 디자인 토큰, CSS 변수, 프레임워크 테마, 컴포넌트 사용 규칙, 금지할 시각적 패턴을 제공할 수 있어야 한다. `DESIGN.md` 또는 같은 역할을 하는 에이전트 지침도 산출물에 포함될 수 있다.

스킬이 제공하는 명세와 이를 애플리케이션 코드에 반영하는 작업은 구분한다. 실제 적용은 [코드 수정과 시각적 검증의 역할](#코드-수정과-시각적-검증의-역할)을 따른다.

산출물은 스타일 값뿐 아니라 규칙의 사용 조건과 제약을 설명해야 한다. 코딩 에이전트가 어떤 규칙을 언제 적용하고, 어떤 임의의 스타일 생성을 피해야 하는지 알 수 있어야 한다.

## 스킬 제공 조건

스킬 이름은 `use-progressive-user-interfaces`로 정한다. 이 작업 방식은 Codex에서 재사용할 수 있는 스킬로 제공할 수 있어야 한다. 프로젝트 전체의 `AGENTS.md`에 긴 지침을 복제하는 방식에 의존하지 않는다.

스킬은 현재 진행 단계를 판단하고, 레퍼런스 탐색과 시각화 계획, 사용자 선호 확인, 디자인 규칙 확정과 충돌 검토, 종료 조건 적용과 코딩 에이전트용 산출물 생성을 담당한다.

`SKILL.md`에는 전체 진행 방식과 필수 금지사항을 두고, 상세 절차는 필요할 때 읽는 아래 참고 문서로 분리한다. 스킬 본문을 불필요하게 늘리지 않는다.

- `references/discovery.md`: 프로젝트에 맞는 실제 UI 탐색, 관찰과 후보 비교
- `references/preferences.md`: 사용자 선택의 확인, 충돌 처리와 프로젝트별 기록 절차
- `references/implementation.md`: 잠정 시각화와 메인 세션에 전달할 구현 입력
- `references/validation.md`: 수정 후 실제 UI 검증, 규칙 재사용과 완료 판단

`implementation.md`는 디자인 스킬에 코드 수정 책임을 부여하는 문서가 아니다. 코드 수정 책임은 [코드 수정과 시각적 검증의 역할](#코드-수정과-시각적-검증의-역할)을 따른다.

시안을 살펴보는 과정에서 이미지 생성을 사용할 수 있어야 한다. 사용 가능한 공식 이미지 생성 스킬이나 동등한 도구가 있으면 이를 사용하며, 이미지 생성 자체를 중복 구현하지 않는다. 발견한 방향을 프로젝트 화면으로 표현하거나, 여러 방향을 비교하거나, 다른 레퍼런스에서 선택한 특성을 조합하거나, 텍스트로 판단하기 어려운 속성을 확인할 때 활용한다.

## 초기 디자인 시스템의 완료 조건

현재 프로젝트에서 아래 조건을 만족하면 초기 디자인 시스템 구축을 마친다.

- 디자인을 구별 짓는 시각적 특징을 설명할 수 있다.
- 주요 실제 UI에서 선택한 시각적 특징이 일관되게 나타난다.
- 반복 사용하는 공통 속성과 용도에 따른 규칙이 정의되어 있다.
- 현재 필요한 주요 UI를 기존 규칙으로 표현할 수 있다.
- 코딩 에이전트가 따라야 할 규칙과 금지사항을 명시할 수 있다.
- 새 화면을 추가할 때 디자인 방향을 처음부터 다시 정할 필요가 없다.

모든 컴포넌트와 토큰을 만드는 것을 완료 조건으로 삼지 않는다. 완료 후에도 실제 요구가 없으면 시스템을 계속 확장하지 않는다.

## 사용 과정에서 확인할 성과

성과는 보기 좋은 화면의 생성 여부만으로 판단하지 않는다. 실제 사용에서 아래 변화를 확인하고, 그 관찰을 바탕으로 작업 방식과 스킬을 수정한다.

- 사용자가 처음에는 설명하지 못했던 선호를 발견했는가
- 실제 UI 레퍼런스가 디자인 판단에 도움이 되었는가
- 시각적 비교를 통해 불필요한 반복 요청이 줄었는가
- 확정된 규칙을 새로운 화면에서도 재사용하는가
- 화면 간 디자인 불일치를 수정하는 작업이 줄었는가
- 기존 방식보다 레퍼런스 검색과 직접 CSS 수정에 드는 작업이 줄었는가

### 아직 검증하지 않은 가설

아래 가설은 실제 사용을 통해 확인할 대상으로, 이미 입증된 성과가 아니다.

- 추상적인 요청을 검색 관점으로 나누면 일반적인 웹 검색보다 취향 발견에 도움이 되는 UI 사례를 찾을 수 있다.
- 요청에 맞는지를 기준으로만 고른 후보보다 시각적 차이도 고려한 후보가 선호 확인에 더 도움이 된다.
- 사용자는 CSS나 토큰 값을 직접 고르는 것보다 실제 UI를 비교할 때 선호와 비선호를 더 쉽게 표현할 수 있다.
- 레퍼런스에서 선호를 찾고 생성 이미지로 조합해 검증하면 스크린샷 전달, 반복 요청과 직접 CSS 수정의 부담이 줄어든다.
- 확인된 선택을 용도에 따른 규칙과 토큰으로 축적하면 코딩 에이전트가 새 화면의 디자인 일관성을 유지하기 쉬워진다.

## 현재 목표에 포함하지 않는 일

- 모든 사용자에게 적용되는 보편적인 좋은 디자인 판단
- 디자인 시스템의 완전 자동 생성
- 사용자 선택 없이 취향을 확정하거나 검증하지 않은 규칙을 자동 확정하는 일
- 유명 서비스의 UI 복제
- 처음부터 모든 컴포넌트와 토큰을 생성하는 일
- UI 레퍼런스 자료 모음 자체의 구축
- 특정 벡터 데이터베이스나 임베딩 구조의 선정
- 디자인 시스템 규모를 늘리거나 레퍼런스를 무한히 탐색하는 일
