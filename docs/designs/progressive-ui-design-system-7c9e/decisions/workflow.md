# 실제 UI 탐색, 기록과 검증의 운영 방식

접근 가능한 실제 UI를 먼저 찾고, 사용자 피드백을 기준으로 탐색 횟수를 계산하며, 참여 프로젝트에 기록을 남기고, 변경 영향에 따라 검증하는 방식을 채택한다. 이 결정은 스킬 설계자와 검토자가 기본 동작과 예외를 구현할 때 사용한다.

## 접근 실패 시 대체 탐색

[실제 UI에 접근하지 못했을 때](../requirements.md#실제-ui에-접근하지-못했을-때)는 다른 실제 UI를 더 다양한 관점에서 탐색하는 방식을 따른다. 접근할 때마다 사용자에게 먼저 확인하는 방식과 비교했으며, 특정 서비스의 접근 문제 때문에 전체 탐색이 반복해서 멈추는 일을 줄이는 쪽을 선택했다.

사용자가 반드시 관찰하도록 지정한 서비스는 임의로 대체하지 않는다. 대안을 찾지 못하면 화면 제공을 요청하거나 비교를 보류한다. 특정 서비스의 연동이나 구독은 이 결정의 전제가 아니다.

## 탐색 횟수와 연장

[탐색을 끝낼 조건](../requirements.md#탐색을-끝낼-조건)은 후보 제시와 사용자 피드백을 한 차례로 세고, 기본 3회 이후에는 다음 행동을 사용자에게 확인하는 방식으로 정했다. 3회를 예외 없는 상한으로 적용하는 방식도 비교했지만, 근거를 더 찾을 가치가 있을 때 사용자가 추가 횟수를 정할 수 있도록 했다.

도구 호출 횟수는 사용자가 디자인 방향을 판단한 횟수와 다르다. 탐색 횟수만으로 실행 비용이 제한되는 것은 아니므로 접근 실패는 대체 탐색 절차로 처리하고, 같은 실패를 새 후보 비교로 계산하지 않는다.

## 프로젝트별 기록 위치

[기록 위치와 작업 재개](../requirements.md#기록-위치와-작업-재개)는 프로젝트의 기존 문서 체계를 따르도록 정했다. 모든 프로젝트에 동일한 전용 폴더를 만드는 방식보다 기존 디자인 지침과 중복되지 않는 방식을 선택했다.

위치가 없을 때에는 최초 사용 시 사용자 판단이 필요하다. 스킬의 참고 문서와 프로젝트의 실제 기록을 분리하고, 재개 시 같은 기록을 읽는 절차를 구현해야 한다.

## 변경 영향에 따른 검증

[변경 영향에 따른 검증과 규칙 확정](../requirements.md#변경-영향에-따른-검증과-규칙-확정)은 대표 화면에서 시작하되, 변경이 영향을 주는 상태와 사용 조건을 확인하는 방식으로 정했다. 대표 화면에만 한정하면 공통 규칙의 재사용 근거가 부족하고, 모든 주요 화면을 한 번에 확인하면 초기 탐색의 작업량이 커진다.

공통 규칙은 적용 가능한 다른 기존 대상에서 재사용한 모습을 확인해야 한다. 다른 대상이 아직 없으면 새 화면을 만들도록 요구하지 않고, 확인한 대상에 한정해 기록한다. [코드 수정 책임](code-editing-and-visual-validation.md)은 메인 세션에 유지한다.

## 계획에 미치는 영향과 재검토 조건

탐색과 접근 실패는 `discovery.md`, 사용자 선택과 재개는 `preferences.md`, 잠정 시각화와 구현 입력은 `implementation.md`, 수정 후 검증과 규칙 확정은 `validation.md`에서 구체화한다. 각 절차를 별도로 만들더라도 탐색 횟수와 승인 상태가 다음 단계로 전달되는지 함께 확인해야 한다.

대체 후보가 프로젝트에 맞지 않거나, 연장 요청이 반복되거나, 기록 위치가 달라 재개에 실패하거나, 공통 규칙을 재사용할 때 놓친 차이가 반복되면 운영 방식을 재검토한다. 횟수, 기록 위치의 기본 방식이나 검증 조건을 바꾸려면 요구사항 작성자의 승인을 받아 변경하려는 요구사항을 먼저 갱신한다.
