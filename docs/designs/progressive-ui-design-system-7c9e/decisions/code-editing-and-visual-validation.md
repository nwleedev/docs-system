# 구현 절차의 코드 수정과 디자인 스킬의 시각적 재검증

애플리케이션 코드 수정은 디자인 스킬 밖의 구현 절차에서 수행하고, 수정 후에는 디자인 스킬의 시각적 검증 절차를 다시 적용하는 방식을 채택한다. 구체적인 책임과 완료 조건은 [코드 수정과 시각적 검증의 역할](../requirements.md#코드-수정과-시각적-검증의-역할)을 따른다.

이 결정 기록은 스킬 설계자와 검토자가 코드 수정 책임을 나눈 이유와 남은 위험을 이해하고, 이후 역할 변경이 필요한지 판단할 때 사용한다.

## 비교한 방식과 선택 이유

코드 수정을 별도 구현 절차에 맡기면 프로젝트의 개발 방식을 유지하면서 디자인 스킬을 레퍼런스 탐색, 사용자 선택과 시각적 검증에 집중시킬 수 있다. 프로젝트마다 다른 구현과 검사 방법을 디자인 스킬에 중복 정의하지 않는 데에도 적합하다. 다만 디자인 판단을 구현에 전달하고 수정 후 화면을 다시 확인하는 절차가 빠지지 않아야 한다.

디자인 스킬에 코드 수정까지 포함하는 방식도 비교했다. 시각적 판단을 곧바로 화면에 적용할 수 있지만, 탐색 중인 선택이 코드에 확정되거나 대표 화면을 위한 수정이 공통 컴포넌트와 다른 화면으로 번질 위험이 있다. 이 방식은 채택하지 않는다.

## 결정의 영향과 남은 위험

명세와 코드 수정 단계를 구분해도 선택의 근거, 적용 조건이나 미결정 사항이 구현 과정에서 누락될 수 있다. 시각적 차이와 기존 동작의 이상 여부도 서로 다른 검사 대상이다. 역할 분담 자체를 구현 품질이나 검증 완료의 증거로 취급하지 않는다.

이 결정은 작업 절차의 역할을 정한다. 별도 에이전트 실행, 병렬 코드 수정이나 쓰기 권한 설정은 결정하지 않는다. 전체 디자인 시스템의 완료 판단에 필요한 화면과 증거 등은 [남은 판단](../references/visual-evidence-and-validation.md#역할-분담-결정과-완료-증거에서-남은-판단)에 구분한다.

## 재검토 조건

실제 사용에서 디자인 의도 누락이나 수정 후 재검증 누락이 반복되면, 명세와 개발 절차의 연결을 보완할지 코드 수정 책임을 바꿀지 비교한다. 코드 수정 책임을 바꾸려면 요구사항 작성자가 역할 변경을 승인하고 요구사항을 갱신해야 한다.
