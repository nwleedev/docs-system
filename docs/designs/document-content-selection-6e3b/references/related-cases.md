# 작성 지시와 과정 설명이 문서에 섞인 실제 사례

문서 본문에 편집 안내와 조사 상황 설명이 들어간 사례가 실제 변경 이력에 남아 있다. 이 문제를 방지하려면 특정 표현을 바꾸기 전에 편집 안내와 조사 상황 설명을 문서에 포함하라는 명시적 지시가 있는지 판정해야 한다.

이 자료는 [요구사항의 사례 조사](../requirements.md)를 위해 문서 작성 기준을 관리하는 개발자가 실패 유형과 대응 방식을 비교할 수 있게 한다. 기준일은 2026-09-30이다. 본문과 변경 이력에서 직접 확인되는 문구, 이슈 보고자의 관찰과 저장소에 적용된 규칙을 각각 구분한다.

## 문서에 편집자 안내가 들어간 사례

### Foshan 문서의 편집 안내

2025-03-13 수정본에는 문서 주제 설명 뒤에 편집자에게 중립적인 문체와 출처 사용을 지시하는 문장이 추가됐다. 짧은 원문은 “If you plan to add this information”이다. 해당 문장이 추가된 사실은 [Foshan 변경 이력 1280200320](https://en.wikipedia.org/w/index.php?diff=1280200320)에서 직접 확인할 수 있다.

이 문장은 편집자에게 작성 방법을 지시한다. 이 저장소의 문서에도 같은 문제가 나타나면, 본문 내용으로 요청한 안내인지를 확인하고 지시가 없으면 제외하는 방식이 요구사항에 맞는다.

### Gurmukh Singh Jeet 초안의 제출 지침

2026-04-12 초안의 `Notes for upload` 절에는 제출 전에 이 절을 지우고 인용 형식을 바꾸라는 지침이 들어 있다. 짧은 원문은 “Delete this section before submission.”이다. [초안 변경 이력 1348412352](https://en.wikipedia.org/w/index.php?diff=1348412352)에서 그 절을 확인할 수 있다.

완성 문서에 작업 지침을 넣은 뒤 나중에 지우라고 쓰는 방식은 최종 독자에게 불필요한 지시가 남을 가능성을 만든다. 초안에도 본문과 작성 지시를 구분하고, 명시적으로 요청한 편집 지침이 아니면 본문에 추가하지 않는 방식이 적합하다.

## 조사 상황과 추측이 함께 들어간 사례

Studniční hora의 2025-03-13 수정본은 제공된 검색 결과에서 동물상 정보가 부족하다는 설명 뒤에 해당 산에 있을 것으로 추측하는 동물을 나열한다. 짧은 원문은 “limited in the provided search results”이다. [수정본 1280231958](https://en.wikipedia.org/w/index.php?title=Studni%C4%8Dn%C3%AD_hora&oldid=1280231958)의 `Fauna` 절에서 확인할 수 있다.

여기에는 검색 결과에 관한 작성 상황과 대상에 관한 추측이 섞여 있다. 검색 상황을 설명하는 문구만 지우면 추측을 사실처럼 읽게 할 수 있다. 본문에서 확인할 사실을 남기려면 각 주장의 근거를 다시 확인하고, 뒷받침하지 못하는 주장은 제외하는 방식이 필요하다.

위키백과 편집자들은 이러한 유형을 대화 상대를 위한 설명과 자료 사용에 관한 면책 문구로 분류한다. [AI 작성 징후 자료의 고정 수정본 1377445939](https://en.wikipedia.org/w/index.php?title=Wikipedia:Signs_of_AI_writing&oldid=1377445939#Communication_intended_for_the_user)은 실제 본문과 초안의 사례를 연결한다. 이 자료는 편집자의 관찰을 모은 안내다. 변경 이력은 본문에 쓰인 문구를 보여 주지만, 작성 도구나 원래 프롬프트는 제시하지 않는다. 따라서 이 사례에서 확인할 대상은 문구가 문서의 주제에 맞는지 여부다.

## 작업 언급을 명시적 요청에 한정한 운영 사례

dlt는 커밋에 작업, 티켓과 호출자에 관한 언급을 사용자가 요청한 경우에만 넣도록 한다. 짧은 원문은 “No references to the task/ticket/caller”이다. [dlt의 Git 규칙 고정본](https://github.com/dlt-hub/dlt/blob/270004efd860470411869de44055ec43549ec58d/.agents/rules/git-github.md)은 실제 변경을 설명하는 글과 대화의 작업 경위를 구분하는 운영 사례다.

[dlt PR #4098](https://github.com/dlt-hub/dlt/pull/4098)은 2026-06-23 병합됐으며, 커밋 메시지 규칙, 실행 직전 규칙을 전달하는 hook과 커밋 스킬을 함께 도입한다. 본문은 AI가 붙인 과도한 설명과 작성 도구 표시가 합쳐진 커밋에 누적되는 문제를 변경 이유로 든다.

[dlt의 커밋 스킬 고정본](https://github.com/dlt-hub/dlt/blob/270004efd860470411869de44055ec43549ec58d/.claude/skills/commit/SKILL.md)은 전달받은 문구를 그대로 쓸 메시지가 아닌 참고 정보로 취급하고, 실제 변경을 읽어 메시지를 작성하도록 한다. 해당 파일은 2026-06-23 수정본이다.

이 저장소에 적용할 수 있는 부분은 명시적 요청을 확인하는 조건과 결과물 작성 직전에 내용을 고르는 순서다. PR과 규칙 파일에서 규칙의 적용 사실을 확인할 수 있다. PR에는 도입 전후 혼입률 값이 제시되어 있지 않다.

## 사용자 문구를 되풀이한 인접 사례

[Open WebUI #24851](https://github.com/open-webui/open-webui/issues/24851)은 2026-05-17, 버전 0.9.5에서 역할극 응답이 사용자 발언을 되풀이한다는 보고다. 짧은 원문은 “It parrots the user.”이다. 문서 파일의 사례는 아니지만 사용자 발언이 응답에 반복되는 문제를 비교할 수 있다.

보고자는 다른 도구와 요청을 대조한 뒤 사고 내용의 재전달 여부가 다르다고 설명했다. [2026-07-27 유지보수자 답변](https://github.com/open-webui/open-webui/issues/24851#issuecomment-5089612867)은 사고 블록 전달이 의도된 동작이며 필터 로직을 확인해야 한다고 말한다. 기준일의 이슈 상태는 `CLOSED`지만, 수정 버전이나 문제가 해소됐는지를 설명하는 답변은 없다.

이 사례가 보여 주는 조사 대상은 모델뿐 아니라 입력 조립과 대화 재전달 방식이다. [내용 선정 절차](./content-selection-research.md#작성-전에-적용할-내용-판정-제안)를 비교할 때에도 문서 본문에 과정 설명이 들어간 사례와 사용자 발언이 응답에 반복된 사례를 구분해야 한다.
