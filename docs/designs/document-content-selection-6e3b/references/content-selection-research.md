# 문서에 실릴 내용을 먼저 고르는 작성 기준

`use-better-terms`에 문장 표현을 고치기 전, 해당 내용이 문서에 포함되어도 되는지 판단하는 절차를 추가하는 방안을 우선 제안한다. 작업 설명을 자연스러운 문장으로 바꾸기만 하면 불필요한 내용은 그대로 남는다. 별도 스킬은 내용 선정만 독립적으로 반복할 필요가 확인될 때 비교할 수 있다.

이 자료는 [요구사항의 내용 포함 조건과 해결 방안](../requirements.md)을 기준으로, 문서 작성 기준을 관리하는 개발자가 두 방안을 비교할 수 있게 한다. 외부 자료는 2026-09-30 기준이며, 고정 버전이 없는 지침은 그날의 문서를 기준으로 한다.

## 현재 저장소에서 빠진 판정

현재 규칙은 작업 입력을 본문에 옮기지 않도록 하지만, 주의사항과 과정 설명을 포함하라는 명시적 요청을 어떻게 구분할지는 정하지 않는다.

[`docs/designs/README.md`](../../README.md)의 모든 문서에 적용하는 규칙은 프롬프트, 에이전트 지시, 도구 조건과 진행 보고를 작업 입력으로 취급한다. 참고 자료에 작업 문구나 진행 보고를 조사 결과처럼 기록하는 것도 금지한다. 문서 종류별 작성 권한은 이 README에 있으므로, 새 내용 판정이 기존 권한을 바꾸게 해서는 안 된다.

[`use-better-terms`](../../../../skills/use-better-terms/SKILL.md)는 독자, 독자의 다음 행동, 확인된 사실과 승인된 결정을 모은 뒤 뜻을 보존하는 대안을 적용한다. 근거가 있는 문장이어도 해당 문서에서 요청한 내용인지 먼저 판정하는 단계는 명시하지 않는다. 근거 부족을 기록하거나 판정 조건을 독자가 찾을 수 있게 하라는 지침도 기록 위치가 불명확하면 부가 설명을 본문에 넣는 근거로 오해할 수 있다.

기존 [작업 의도와 산출물 조사](../../public-output-audience-4d2c/references/prompt-intent-and-artifact-provenance-research.md#입력과-산출물-근거를-분리한다)는 입력과 사실 근거를 구분한다. 이 자료는 그 구분에 더해, 사실인 내용과 요청한 문서에 실을 내용도 다를 수 있다는 점을 다룬다.

## 외부 지침에서 확인되는 원칙

내용을 선별하려면 독자의 목적과 문서 종류를 먼저 정하고, 작업 지시를 본문 자료와 구분해야 한다. 다음 지침은 각각 이 판단의 다른 부분을 뒷받침한다.

### 불필요한 도입과 부가 설명을 줄인다

Google은 문서의 목적을 필요한 정보를 전달하는 데 두며, `please note` 같은 상투적 도입과 장황한 문장을 피하도록 한다. 짧은 원문은 “Placeholder phrases like please note and at this time.”이다. [Google의 문체 지침](https://developers.google.com/style/tone)은 2026-05-27 갱신본이다.

Google은 주의 문구의 남용을 줄이고, 독자가 작업에 성공하는 데 필요한 정보는 별도 주석이나 알림으로 돌리지 말라고 한다. 따라서 주의 문구를 줄이는 것과 필요한 조건을 없애는 것은 다른 선택이다. [Google의 주의 문구 작성 지침](https://developers.google.com/style/notices)은 2025-09-08 갱신본이다.

### 문서 종류에 맞춰 설명을 고른다

Diátaxis는 사용 방법 문서에서 독자의 목표를 중심에 두고, 목표 달성에 필요하지 않은 설명이나 참고 정보를 빼거나 다른 자료로 연결하도록 한다. [Diátaxis의 사용 방법 문서 지침](https://diataxis.fr/how-to-guides/)은 독자가 해야 할 행동과 도구의 기능 나열을 구분한다.

설명 문서에는 설계 이유, 기술적 제약과 대안을 포함할 수 있지만, 다른 문서에 속할 지시나 세부 기술 설명까지 흡수하지 않도록 한다. [Diátaxis의 설명 문서 지침](https://diataxis.fr/explanation/)을 대조하면, 설명이라는 형식만으로 에이전트가 수행한 모든 과정을 포함할 근거가 생기지는 않는다.

### 지시, 참고 자료와 출력 예시를 분리한다

OpenAI는 프롬프트에서 지시, 예시와 문맥 자료를 구분하고, Markdown 제목이나 XML 태그로 각 자료가 시작하고 끝나는 부분을 표시하도록 안내한다. [OpenAI의 프롬프트 작성 지침](https://developers.openai.com/api/docs/guides/prompt-engineering#message-formatting-with-markdown-and-xml)은 입력과 출력 예시를 별도로 제시한다.

문서 작업에는 이 구조를 적용해 작성 지시, 본문에 사용할 사실 자료와 포함이 허용된 인용을 따로 읽게 하는 방안을 제안한다. 자료를 구분하는 표시는 에이전트의 입력에 쓰고, 완성 문서에는 그 주제에 필요한 내용을 작성한다.

출력 형식을 제한해도 내용 판정은 남는다. [OpenAI의 Structured Outputs 지침](https://developers.openai.com/api/docs/guides/structured-outputs#handling-mistakes)은 스키마를 따르는 출력에도 오류가 있을 수 있다고 설명한다. 고정된 문서 틀이나 허용한 항목 이름만으로 과정 설명의 혼입을 막았다고 판정할 수는 없다.

## 작성 전에 적용할 내용 판정 제안

문서의 주제, 독자의 행동과 명시적으로 포함하라고 한 내용부터 정한다. 이를 위한 판단 메모를 완성 문서에 복사하지 않는다.

1. 문서 종류와 독자가 확인할 결과를 정한다. 요구사항에는 필요한 결과와 조건을, 계획에는 앞으로 수행할 일과 확인 방법을, 보고서에는 요청한 조사 결과나 관찰 결과를 담는다.
2. 작성 지시와 본문 자료를 구분한다. 조사하라는 지시는 조사 수행을 허용한다. 수행한 명령, 검색 순서나 작성 중 판단을 본문에 나열하라는 뜻으로 확대하지 않는다.
3. 주의사항, 파일을 읽을 때 적용할 지침, 작업 상황과 수행 과정에 관한 내용은 해당 문서에 포함하라는 명시적 지시가 있는지 확인한다. 지시가 없으면 본문 후보에서 제외한다.
4. 남은 문장은 확인된 사실이나 승인된 결정으로 작성한다. 프롬프트를 문서에 관한 사실처럼 쓰거나, 대화 경위를 변경 이유로 바꾸지 않는다.
5. 문장을 제거할 때 필요한 조건까지 사라지는지 확인한다. 조건이 사라지면 확인된 사실을 직접 설명하도록 다시 쓰거나, 해당 주장을 제외한다. 판단에 필요한 뜻이나 포함 권한이 없으면 문서 밖에서 확인한다.

명시적 지시는 내용, 대상 문서와 필요한 정도를 함께 확인하는 방식이 적합하다. 부록에 수행 명령을 남기라는 지시는 그 부록에 한정한다. 보고서를 요청했다는 이유만으로 작성 과정까지 허용한 것으로 보지 않는다. 구현 계획의 예정된 작업과, 실제 구현을 수행한 경위를 회고하는 글도 구분한다.

## 사실의 뜻을 바꾸지 않는 방법

불필요한 주의 문구를 제외한 뒤에는 남은 주장도 그 근거가 확인하는 내용만 말해야 한다.

자료가 어떤 기능의 존재만 보여 준다면 그 기능이 권장된다고 쓰지 않는다. 실행 결과가 특정 입력에서 성공했음을 보여 준다면 모든 입력에서 성공한다고 확대하지 않는다. 이 경우 문서에는 확인된 기능이나 관찰 결과를 직접 쓸 수 있다. 추가적인 면책 문단을 넣는 것으로 근거 없는 확대를 정당화하지 않는다.

반대로 문구를 지우면 근거가 없는 권장이나 성공 주장이 남는 경우, 주장까지 고치거나 제외해야 한다. 의미를 유지할 사실이 부족하면 질문이나 작업상 제약을 대화에서 알린다. 이를 문서의 주의사항으로 자동 추가하지 않는다.

현재 [`docs/designs/README.md`의 참고 자료 규칙](../../README.md#referencesmd)은 한계와 불확실성, 그 영향을 기록하도록 한다. 새 요구사항을 적용할 때에는 이 규칙이 요구하는 사실의 적용 조건과, 요청하지 않은 부가 주의 문구를 구분해야 한다. 어떤 내용을 연구 문서의 필수 정보로 계속 둘지, 어떤 내용을 명시적 요청이 있을 때만 둘지는 후속 변경에서 정할 사항이다.

## 스킬 구성 방안

### `use-better-terms`에 내용 판정을 추가한다

기존 호출과 검토 단위를 그대로 사용하면서, 표현 대안을 만들기 전에 포함 여부를 판정할 수 있다. 근거가 있는 작업 설명을 더 자연스럽게 다듬어 본문에 남기는 문제를 같은 절차에서 잡을 수 있다는 점이 장점이다.

루트 `SKILL.md`에는 내용 선정이 표현 수정에 앞선다는 순서와 호출 조건을 적고, 상세한 문서 종류와 사례는 필요할 때 읽는 참고 자료로 분리하는 구성이 적합하다. [Agent Skills 명세의 자료 로딩 방식](https://agentskills.io/specification#progressive-disclosure)은 메타데이터, 활성화한 스킬 본문과 필요한 참고 자료를 구분한다. 명세가 기존 스킬과 새 스킬 중 하나를 선택해 주는 것은 아니며, 분리 위치는 현재 호출 방식에 따른 판단이다.

기존 스킬은 근거와 의미를 보존하는 검토를 맡으므로, 포함 여부를 이유로 요구사항 작성 권한이나 승인 상태를 새로 정하면 안 된다. 내용 판정에는 언어와 무관한 기준을 두고, 한국어 참고 자료에는 문장 표현의 차이만 남기는 편이 중복을 줄인다.

### 내용 선정 전용 스킬을 만든다

문구 수정 없이 문서에 실을 내용만 검토하는 일이 반복되거나, 여러 작성 스킬이 같은 판정을 먼저 사용할 때 비교할 수 있다. 작성 전 판정과 표현 검토를 따로 호출할 수 있다는 점이 장점이다.

현재 저장소에서는 `use-design-docs`가 문서 작성 권한과 종류별 절차를 연결하고, `use-better-terms`가 저장 전 글을 검토한다. 전용 스킬을 추가하면 독자와 근거 수집을 반복하거나 같은 기준을 두 곳에서 유지할 수 있다. 문서 종류별 규칙은 저장소 README에 두고, 스킬이 그 내용을 다시 정의하지 않는 구성이 필요하다.

따라서 기존 스킬 확장을 먼저 비교 대상으로 삼는 편이 현재 구조에 맞는다. 내용 선정만 수행할 독립적인 호출 수요가 확인되면 전용 스킬을 다시 비교한다.

## 방안의 효과를 확인할 비교 사례

실패 문구와 정상 문구를 함께 비교해야 한다. 다음 상황을 후속 방안 비교에 사용하는 방법을 제안한다.

- 조사 보고서에 검색 순서가 들어가지만 과정 설명은 요청하지 않은 경우: 검색 순서를 제외하고 조사 결과와 출처를 남기는지 확인한다.
- 같은 보고서의 부록에 검색 방법을 쓰라고 명시한 경우: 부록에 필요한 방법을 남기고 다른 문서에 전파하지 않는지 확인한다.
- 계획에서 앞으로 수행할 작업을 설명하는 경우: 작업 설명이라는 이유로 계획의 실행 순서까지 삭제하지 않는지 확인한다.
- 작업 입력에 문서의 독자와 작성 형식이 지정된 경우: 그 지시를 본문의 사실이나 작성 경위로 옮기지 않는지 확인한다.
- 관찰된 결과의 조건이 필요한 경우: 부가 주의 문구를 없애면서 결과를 더 넓게 주장하지 않는지 확인한다.
- 같은 내용을 다른 말로 쓴 경우: 특정 문자열의 일치 여부와 무관하게 포함할 내용을 동일하게 판정하는지 확인한다.

현재 절차와 제안한 절차에 같은 상황을 적용해 불필요한 설명의 잔존, 필요한 조건의 삭제, 승인되지 않은 내용 추가와 판정에 드는 작업량을 함께 비교할 수 있다. 비교에 사용할 오류 유형과 대응 방법은 [실제 사례 자료](./related-cases.md)에 정리되어 있다.
