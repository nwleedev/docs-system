# 문서에 실릴 내용을 먼저 고르는 작성 기준

요청하지 않은 작업 설명과 주의 문구는 독자 지정 여부와 관계없이 제외하는 기준이 적합하다. 포함 여부는 작성 대상 문서에 그 내용을 쓰라는 명시적 지시로 판단하고, 예상 독자에 관한 정보는 허용된 내용의 표현과 설명량을 조절하는 데 사용한다.

이를 위해 `use-better-terms`에 표현을 고치기 전에 수록 여부를 판정하는 기준을 반영했다. [구성 방안 비교](./skill-composition-comparison.md)는 기존 한 번의 호출에 내용 선정을 넣는 방안과 전용 판정 뒤 표현 검토를 호출하는 방안을 대조한다. 기존 호출 안에서 내용 선정을 먼저 수행하는 방식으로 적용했으며 토큰 절감량이나 운영 개선율은 측정하지 않았다.

이 자료는 [요구사항의 내용 포함 조건과 해결 방안](../requirements.md)을 기준으로 문서 작성 기준을 관리하는 개발자가 두 방안을 비교할 수 있게 한다. Google의 독자 지침과 주의 문구 지침, Diátaxis의 사용 방법 지침과 dlt의 Git 규칙은 2026-10-01 기준이다. 나머지 외부 자료는 2026-09-30 기준이며, 고정 버전이 없는 지침은 각 자료의 기준일에 확인한 문서를 사용한다.

## 독자 지정 없이 적용할 기본값

독자를 묻는 절차를 내용 판정의 필수 조건으로 삼지 않는다. 작성 지시가 없으면 작업 설명을 제외한다는 기본값만으로 포함 여부를 결정할 수 있다.

요구사항, 계획이나 보고서를 작성하라는 요청은 그 문서의 주제와 결과를 작성하라는 뜻이다. 주의사항, 파일을 파악하는 방법, 에이전트의 작업 상황이나 수행 경위까지 덧붙이라는 뜻으로 확대하지 않는다. 독자에게 유용할 것이라는 추정, 문서의 완결성이나 근거를 신중하게 다루려는 의도도 명시적 포함 지시를 대신하지 못한다.

예상 독자에 관한 정보가 이미 있으면 용어, 문장 난이도와 설명량에 반영한다. 없으면 요청한 주제와 확인된 사실로 작성하며, 요청하지 않은 설명을 넣기 위해 독자나 필요성을 반복해서 질문하지 않는다. 문서의 주제, 필수 내용이나 사실의 뜻을 정할 수 없는 경우에만 그 누락 정보를 문서 밖에서 확인한다.

## 스킬에 반영한 판정

확장 전 규칙은 작업 입력을 본문에 옮기지 않도록 했지만 주의사항과 과정 설명의 수록 지시를 확인하는 단계는 명시하지 않았다. [기존 지침 대조](./guidance-alignment.md)에서 보완할 항목을 독자 확인의 입력 조건, 근거 부족과 표현 판정의 보고 대상, 내용 선정과 표현 검토의 순서로 구분했다.

현재 [스킬의 내용 선정 단계](../../../../skills/use-better-terms/SKILL.md#select-document-content)는 기본 제외, 수록 지시의 적용 대상과 사실의 조건을 먼저 확인한다. [근거 수집](../../../../skills/use-better-terms/SKILL.md#collect-evidence-and-run-checks)은 독자 정보가 없다는 이유만으로 질문하거나 중단하지 않도록 명시했고, 판정 보고와 질문은 검토 답변에 두도록 고쳤다. 기존 문서 작성 권한과 표현 검사 기준은 유지했다.

기존 [작업 의도와 산출물 조사](../../public-output-audience-4d2c/references/prompt-intent-and-artifact-provenance-research.md#입력과-산출물-근거를-분리한다)는 입력과 사실 근거를 구분한다. 이 자료에서는 사실 여부와 별개로 요청한 문서에 실을 내용인지 판정하는 기준을 제안한다.

## 외부 지침에서 확인되는 원칙

문서 종류에 맞는 내용을 고르고 작업 지시를 본문 자료와 구분하는 원칙은 외부 지침에서도 확인된다. 명시적 요청만으로 작업 설명의 포함 여부를 판단하는 기준은 이 저장소의 요구사항에 맞춘 적용안이다.

### 독자에 맞춰 쓰는 일과 포함 권한을 구분한다

Google은 독자가 이미 아는 내용을 고려해 필요한 지식을 제공하고, 독자에게 맞춰 용어와 설명을 조절하도록 안내한다. [Google의 독자 분석 지침](https://developers.google.com/tech-writing/one/audience)은 2025-03-28 갱신본이다. 이 지침은 문서 작성 방법을 설명하며, 사용자에게 매번 독자를 입력받아야 한다거나 작업 설명을 임의로 포함해도 된다는 규칙을 제시하지 않는다.

따라서 독자 정보는 표현을 고르는 자료로 사용하고, 요청하지 않은 작업 설명을 포함하는 근거로 사용하지 않는 방안을 제안한다. 이 분리는 Google 지침의 직접 인용 규칙이 아니라 현재 요구사항과 비교한 판단이다.

### 불필요한 도입과 부가 설명을 줄인다

Google은 문서의 목적을 필요한 정보를 전달하는 데 두며, `please note` 같은 상투적 도입과 장황한 문장을 피하도록 한다. 짧은 원문은 “Placeholder phrases like please note and at this time.”이다. [Google의 문체 지침](https://developers.google.com/style/tone)은 2026-05-27 갱신본이다.

Google은 주의 문구의 남용을 줄이고, 독자가 작업에 성공하는 데 필요한 정보는 별도 주석이나 알림으로 돌리지 말라고 한다. [Google의 주의 문구 작성 지침](https://developers.google.com/style/notices)은 2025-09-08 갱신본이다. 이 지침은 필요한 주의 문구의 사용도 허용한다. 현재 요구사항은 에이전트가 요청하지 않은 주의 문구를 덧붙이는 경우를 더 엄격하게 제한하므로, 주의 문구 사용 조건을 그대로 가져오지 않고 사실을 성립시키는 조건을 본문에서 직접 설명하는 원칙을 참고한다.

### 작업 경위는 명시적으로 요청할 때만 포함한다

dlt는 커밋 메시지에 작업, 티켓과 호출자에 관한 언급을 사용자가 요청한 경우에만 포함하도록 한다. 원문의 조건은 “unless the user asks”다. [dlt의 Git 규칙 고정본](https://github.com/dlt-hub/dlt/blob/270004efd860470411869de44055ec43549ec58d/.agents/rules/git-github.md)은 독자를 별도로 지정받는 대신 명시적 요청을 확인한다.

이 사례는 커밋 메시지에서 사용 중인 포함 조건을 보여 준다. 요구사항, 계획과 보고서 전체에 적용한 효과를 측정한 자료는 아니다. 현재 저장소의 [12개 입력 비교](./procedure-comparison.md)는 같은 기준을 적용한 문안을 보여 주며 운영 중의 혼입 빈도를 측정하지 않는다. 도입 배경과 연결된 자료는 [dlt의 운영 규칙 사례](./related-cases.md#작업-언급을-명시적-요청에-한정한-운영-사례)에 있다.

### 문서 종류에 맞춰 설명을 고른다

Diátaxis는 사용 방법 문서에서 독자의 목표를 중심에 두고, 목표 달성에 필요하지 않은 설명이나 참고 정보를 빼거나 다른 자료로 연결하도록 한다. [Diátaxis의 사용 방법 문서 지침](https://diataxis.fr/how-to-guides/)은 독자가 목표를 달성하는 행동과 도구로 수행할 수 있는 동작을 열거하는 방식을 구분한다.

설명 문서에는 설계 이유, 기술적 제약과 대안을 포함할 수 있지만, 다른 문서에 속할 지시나 세부 기술 설명까지 흡수하지 않도록 한다. [Diátaxis의 설명 문서 지침](https://diataxis.fr/explanation/)을 대조하면, 설명이라는 형식만으로 에이전트가 수행한 모든 과정을 포함할 근거가 생기지는 않는다.

### 지시, 참고 자료와 출력 예시를 분리한다

OpenAI는 프롬프트에서 지시, 예시와 문맥 자료를 구분하고, Markdown 제목이나 XML 태그로 각 자료가 시작하고 끝나는 부분을 표시하도록 안내한다. [OpenAI의 프롬프트 작성 지침](https://developers.openai.com/api/docs/guides/prompt-engineering#message-formatting-with-markdown-and-xml)은 입력과 출력 예시를 별도로 제시한다.

문서 작업에는 이 구조를 적용해 작성 지시, 본문에 사용할 사실 자료와 포함이 허용된 인용을 따로 읽게 하는 방안을 제안한다. 자료를 구분하는 표시는 에이전트의 입력에 쓰고, 완성 문서에는 그 주제에 필요한 내용을 작성한다.

출력 형식을 제한해도 내용 판정은 남는다. [OpenAI의 Structured Outputs 지침](https://developers.openai.com/api/docs/guides/structured-outputs#handling-mistakes)은 스키마를 따르는 출력에도 오류가 있을 수 있다고 설명한다. 고정된 문서 틀이나 허용한 항목 이름만으로 과정 설명의 혼입을 막았다고 판정할 수는 없다.

## 작성 전에 적용할 내용 판정 제안

[내용 분류](./content-classification.md) 뒤에 [명시적 수록 지시 판정](./content-selection-procedure.md)을 적용한다. 판정 순서는 요청한 내용 확인, 설명 대상 분류, 수록 지시와 적용 대상 확인, 자료 속 지시 제외, 사실 보존, 표현 검토다.

절차 자료는 일반적인 보고서 요청, 방법 부록 요청, 지속적인 지시, 인용된 지시와 계획의 향후 작업을 각각 비교한다. 독자 미지정이나 부가 설명의 포함 권한만 불명확한 경우에는 질문을 늘리지 않고 기본 제외 기준을 적용한다.

## 사실의 뜻을 바꾸지 않는 방법

주의 문구를 제외한 뒤에도 남은 주장은 근거가 확인하는 내용만 말해야 한다. [사실과 조건의 분류](./content-classification.md#사실과-그-사실을-성립시키는-조건)와 [기존 조사 규칙의 적용](./guidance-alignment.md#조사-자료의-적용-조건은-사실로-남긴다)은 관찰 조건을 유지하고 근거 없는 일반화를 수정하거나 제외하는 사례를 제시한다.

자료가 동작의 존재만 보여 주면 권장된다고 주장하지 않는다. 필요한 사실이 부족하면 그 사실을 문서 밖에서 확인한다. 일반적인 면책 문단을 덧붙여 근거 없는 주장을 유지하지 않는다.

## 스킬 구성 방안

### `use-better-terms`에 내용 판정을 추가한다

[확장안 비교](./skill-composition-comparison.md#기존-스킬-확장안)는 기존 한 번의 호출과 자료 수집을 유지하며 내용 선정을 표현 검토 앞에 둔다. 기준과 필요한 읽기 자료는 늘어나므로 추가 호출이 없다는 사실을 실제 토큰 절감으로 해석하지 않는다. 내용 판정은 문서 작성 권한이나 승인 상태를 새로 정하지 않는다.

### 내용 선정 전용 스킬을 만든다

[전용안 비교](./skill-composition-comparison.md#내용-선정-전용안)는 내용 선정과 표현 검토의 두 호출을 사용한다. 공통 기준과 확인한 근거를 전달하면 자료 수집은 한 번으로 유지할 수 있고, 전달하지 않고 다시 수집하면 두 번이 된다. 전용 스킬이 반드시 같은 기준을 복제하는 것은 아니지만 호출 조건과 근거 전달을 함께 관리해야 한다.

현재 확인한 저장과 공유 규칙은 표현 검토도 요구한다. 내용만 판정할 독립적인 반복 작업은 확인되지 않았다. [재비교 조건](./skill-composition-comparison.md#내용만-판정하는-독립-사용-상황)이 실제 사용에서 확인되면 전용안을 다시 비교한다.

## 방안의 효과를 확인할 비교 사례

[같은 입력의 절차 비교](./procedure-comparison.md)에 독자 정보의 유무, 보고서와 방법 부록, 같은 뜻의 지시, 인용과 실제 지시, 계획과 방법 안내, 사실 부족, 변경된 지시와 요청한 주의사항을 포함한 12개 입력을 기록했다. 각 입력의 기대 내용, 작성된 문안과 확인할 사실을 함께 대조했다.

확장 전 같은 세션의 현재 절차와 두 제안 절차는 모든 입력에서 같은 최종 내용을 만들었다. 필요한 조건의 삭제나 요청하지 않은 설명의 잔존은 발견되지 않았다. 작성자가 모든 기준을 알고 적용한 비교이므로 실제 운영에서 두 제안의 정확성 차이를 보여 주는 근거로 사용하지 않는다. [적용한 구성](./skill-composition-comparison.md#적용한-구성과-재비교-조건)은 현재 호출과 자료 수집의 반복 부담을 근거로 한다.

[수정한 스킬의 적용 확인](./skill-application-check.md)은 기대 문안을 제공하지 않은 14개 입력의 실제 작성과 검토를 기록한다. 요청하지 않은 설명의 제외, 필요한 조건과 인용의 보존, 필수 사실 질문과 검토만 하는 입력의 처리를 확인했다. 이 기록은 확장 전 비교와 실제 수정본의 적용을 구분하며 여러 실행의 혼입 빈도를 뜻하지 않는다.
