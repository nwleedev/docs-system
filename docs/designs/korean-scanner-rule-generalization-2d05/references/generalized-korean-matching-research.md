# 한국어 표현 검사 일반화 조사

## 결론

NFD는 현재 문제의 해법이 아니라 한글 음절을 자모로 분해하는 내부 표현 가운데 하나다. NFC와 NFD로 저장된 문자열을 같은 것으로 비교할 수는 있지만, 표제어, 품사, 어간, 어미와 문맥을 판정하지 않는다. 현재 스캐너가 네 표제어에만 엄격한 검사를 적용하는 이유는 NFD가 아니라, 네 표제어의 표면형과 어미 그룹을 `morphologyMatchers`에 따로 적고 한 입력 조합을 실행 코드에서 별도 제외했기 때문이다.

가장 작은 적합한 개선 방향은 다음과 같다.

1. 완전 일치 표현은 규칙과 원문을 같은 정규화 형식으로 비교해 정준 동등한 표기를 함께 찾는다. NFC는 일반 문서 문자열에 적합한 기본 형식이지만, 현재 스캐너에는 원문 위치를 보존하는 NFD 대응이 이미 있으므로 현대 한글 범위에서는 이를 일반 표현에 재사용할 수 있다.
2. 용언은 모든 표제어 규칙에 공통으로 적용되는 하나의 형태 판정기를 사용한다. 진단 규칙 목록에는 표제어와 품사 같은 검사 의도만 두고, 활용과 불규칙 규칙은 표현별 실행 분기가 아닌 공통 한국어 규칙 자료로 관리한다.
3. 공통 형태 규칙을 적용할 때만 NFD나 동등한 한글 음절 분해를 내부 계산에 사용한다. NFD를 스캐너 전체의 형태 분석 메커니즘으로 취급하지 않는다.
4. `Intl.Segmenter`와 Unicode 문자 속성은 한글 문자열 구간을 찾는 보조 수단일 뿐 형태 분석을 대신하지 않는다. 현재 실행 환경에서는 포함하는 문자도 기존 코드와 다르므로 단순 치환하지 않는다.
5. 외부 형태 분석기를 실행 중 의존성으로 추가하지 않는다. 처리할 활용형을 늘려야 한다는 측정 근거가 생기면, 출처와 라이선스를 승인한 규칙으로 배포용 자료를 미리 생성하는 방법을 별도 결정한다.

여기서 실행 코드에 직접 열거하지 않는다는 말은 검사 정책 자료까지 없앤다는 뜻이 아니다. 어떤 표현을 검토할지 정하는 진단 규칙 목록은 저장소의 요구사항이므로 반드시 남아야 한다. 없애야 할 것은 특정 표제어만 아는 제어 흐름, 사람이 적은 표면형 조합과 단일 문자열 예외다. 이 조사는 구현 방향을 제안하지만 승인된 결정이나 구현 계획은 아니다.

조사 대상은 한국어 스캐너 구현 담당자와 진단 정책 결정자다. 조사일은 2026년 9월 1일이며, 저장소 기준은 `main`의 `382a7ace55b8e93c4c8b639333ec5efd27be4705`다.

## 현재 코드에서 확인한 문제

[`korean-expressions.mjs`](../../../../skills/use-better-terms/scripts/korean-expressions.mjs)의 `rules`는 모든 진단을 `kind: "literal"`로 만든다. 그중 `buildExpressionIndex()`는 형태 판정 규칙이 참조한 진단만 일반 완전 일치 검색에서 제외한다. 따라서 같은 진단 목록 안에서도 일부 규칙만 다른 검사 의미를 갖는다.

별도 검사 방식의 동작은 다음 자료에 묶여 있다.

- `endingGroups`는 자음 및 모음 뒤 어미, 축약형, 과거형과 관형형을 실행 코드에 배열로 적는다.
- `morphologyMatchers`는 `좁다`, `좁히다`, `박다`, `박히다` 네 표제어와 각각의 표면 변이형을 실행 코드에 적는다.
- `compileMorphologyMatchers()`는 이 네 표제어의 표면형과 어미만 NFD로 바꾼다.
- `collectMorphologyMatches()`는 한글 문자열 구간의 첫머리에서 표면형을 찾고, 남은 NFD 문자열 전체가 matcher가 참조한 어미 집합에 있을 때만 경고한다.
- `isMorphologyTokenCodePoint()`는 허용할 한글 Unicode code point 구간을 직접 적는다.
- `isExcludedMorphologyContext()`는 한 입력 조합만 형태 후보에서 제외한다.

이 구조에서는 새 표제어를 추가할 때 진단 규칙 외에 표면 변이형, 어미 그룹 연결과 예외 코드를 함께 고쳐야 한다. 반대로 형태 판정기에 연결되지 않은 일반 규칙은 NFC와 NFD 입력을 같은 문자열로 보지 않는다. 앞선 [브랜치와 `main` 비교](../../korean-scanner-detection-gaps-8a2f/references/main-mechanism-comparison.md)는 이 차이가 `다룹니다`, `회의를 가집니다`와 NFD로 저장한 일반 표현의 미탐지로 남았음을 실행 결과로 확인했다.

## NFD와 NFC가 처리할 수 있는 문제

[Unicode Standard Annex #15 revision 57](https://www.unicode.org/reports/tr15/tr15-57.html)은 NFD를 “Canonical Decomposition”, NFC를 “Canonical Decomposition, followed by Canonical Composition”으로 정의한다. 같은 문서는 완성형 `가`와 결합 자모 `ᄀ`과 `ᅡ`를 정준 동등한 예로 제시하며, 일반 콘텐츠에는 NFC를 권고한다고 설명한다. 이 규칙에 따르면 양쪽 문자열을 같은 정규화 형식으로 바꾸면 NFC와 NFD 입력의 이진 표현 차이는 제거할 수 있다.

NFC는 일반 문서 저장과 교환의 기본 형식으로 더 적합하다. 보통의 문서 입력은 이미 NFC이고 한글 음절이 한 `code point`로 유지된다. `String.prototype.normalize()`가 제공하는 NFC는 외부 패키지가 필요 없으며 [ECMAScript 2026 명세](https://tc39.es/ecma262/2026/multipage/text-processing.html#sec-string.prototype.normalize)에 정의되어 있다.

그러나 현재 스캐너의 구현 선택은 다르다. 형태 검사 경로가 이미 `buildNfdMapping()`으로 NFD 비교 위치를 원문 UTF-16 위치에 대응시키므로, 현대 한글 고정 표현에도 같은 대응을 적용하는 편이 코드와 위치 복원 책임을 덜 늘린다. NFC와 NFD는 모두 정준 동등성 비교를 제공하므로 이 선택은 의미 판정의 차이가 아니라 기존 내부 자료를 재사용하는 결정이다. 범위를 임의의 Unicode 결합 문자까지 넓히지 않고 현대 한글 음절과 정준 분해 자모로 한정해야 한다.

NFD는 활용 규칙이 종성 자모나 자모 결합을 직접 확인해야 할 때 유용한 내부 형식이다. 현재 코드처럼 NFD에서 찾은 위치를 원문 UTF-16 위치로 돌리는 변환 정보가 필요하며, 정규화한 문자열의 위치를 곧바로 경고의 위치값에 쓰면 안 된다. NFD를 쓴다는 사실만으로 `박혔다`를 `박히다`, `었`, `다`로 분석하거나 `박지`의 문맥상 의미를 확정할 수는 없다.

NFKC와 NFKD는 기본 비교 형식으로 채택하지 않는다. UAX #15는 호환 정규화가 서식 차이뿐 아니라 일부 의미 있는 구분을 없앨 수 있으므로 임의의 텍스트에 무조건 적용해서는 안 된다고 명시한다. 현재 요구사항은 정준 동등성 처리이지 호환 문자 통합이 아니다.

따라서 선택은 NFD와 다른 단일 대안 가운데 하나를 고르는 문제가 아니다. 일반 문자열 저장에는 NFC가 적합하고, 현재 스캐너의 현대 한글 비교와 형태 계산에는 원문 위치 대응을 가진 NFD를 함께 재사용할 수 있다. 어느 형식을 쓰더라도 정규화는 형태 분석을 대신하지 않는다.

## 문자열 구간 분리는 형태 분석이 아니다

[Unicode Standard Annex #29 revision 47](https://www.unicode.org/reports/tr29/tr29-47.html)은 글자, 단어와 문장 분리의 기본 규칙을 정의하고 언어별 조정을 허용한다. 이 단어 분리는 선택과 검색을 위한 문자열 위치를 제공하지만 한국어 표제어와 어미를 정의하지 않는다.

Node.js 표준 기능인 `Intl.Segmenter("ko", { granularity: "word" })`도 같은 한계가 있다. [현재 ECMA-402 명세](https://tc39.es/ecma402/#sec-segmenter-objects)는 “Whether a segment is ‘word-like’ is implementation-dependent”라고 설명한다. 2026년 9월 1일 Node.js 22.18.0, ICU 77.1에서 `값이 박혔다 박지 씨 좁았습니다`를 검사했을 때 `값이`, `박혔다`, `박지`, `씨`, `좁았습니다`가 각각 한 구간으로 나왔다. 어간과 어미는 나뉘지 않았다. ICU의 [Boundary Analysis 문서](https://unicode-org.github.io/icu/userguide/boundaryanalysis/)도 단어 위치 탐색과 사전 기반 분리를 설명할 뿐 한국어 형태 분석을 제공하지 않는다.

Unicode 정규식 속성은 직접 적은 네 문자 범위를 줄일 수 있지만 동작이 같지 않다. [Unicode Technical Standard #18 revision 25](https://www.unicode.org/reports/tr18/tr18-25.html)과 [Unicode Standard Annex #24 revision 39](https://www.unicode.org/reports/tr24/tr24-39.html)은 `Script`와 `Script_Extensions` 속성의 목적과 Unicode 버전에 따른 자료 갱신을 정의한다. 현재 Node.js에서 `\p{Script_Extensions=Hangul}`은 기존 코드가 받는 완성형 음절, 결합 자모와 확장 자모 외에 호환 자모 `ㄱ`과 한글 방점 `〮`도 받았다. 이 문자를 같은 문자열 구간에 포함할지 먼저 정하지 않고 문자 속성으로 바꾸면 검사 입력 범위가 달라진다.

따라서 문자열 구간 판정에는 다음 원칙이 필요하다.

- 형태 판정기의 입력 단위를 찾는 일과 표제어를 판정하는 일을 분리한다.
- 배포한 Node.js와 ICU 버전에 따라 경고 목록이 달라지면 안 되므로 `Intl.Segmenter`가 나눈 구간을 진단의 유일한 근거로 삼지 않는다.
- Unicode 속성을 쓰려면 호환 자모, 옛한글과 방점 포함 여부를 규칙 자료에 명시하고 사용할 Unicode 버전을 검사한다.

## 표현별 실행 분기를 없애는 방법

### 진단 정책과 형태 규칙을 분리한다

진단 규칙 목록은 어떤 표현을 왜 검토할지 기록한다. 완전 일치 표현은 비교할 문자열을, 용언은 표제어와 품사를 기록한다. 스캐너는 목록에 있는 모든 완전 일치 규칙에 같은 정준 동등 비교 방식을 적용하고, 모든 용언 규칙에 같은 형태 판정 방식을 적용한다. 새 용언을 추가할 때 스캐너 함수, 어미 배열이나 예외 조건을 수정해야 한다면 일반화가 완료된 것이 아니다.

한국어 활용 자료는 표제어마다 가능한 표면 문자열을 나열하지 않고 공통 규칙으로 관리한다. 규칙에는 어간 유형, 받침 조건, 규칙 및 불규칙 활용과 어미 연결 조건이 필요하다. 이는 제거할 수 없는 언어 자료지만 실행 코드의 특정 표현 분기와는 성격이 다르다. 자료를 검증하고 한 번 계산한 색인이나 유한 상태 자료로 바꾸면 실행 중에는 모든 표제어에 같은 알고리즘을 적용할 수 있다.

이 구조에서도 `박지`의 문맥상 의미는 형태만으로 확정할 수 없다. 후속 요구사항은 형태상 `박다`와 어미 `지`로 분석되는 후보를 모두 보고하고 단일 문자열 예외를 두지 않는 것으로 이 정책을 정했다. 문맥 분석 없이 입력의 의미를 자동으로 확정한다는 목표는 세우지 않는다.

### 외부 도구를 실행 중에 넣는 방법은 현재 조건과 맞지 않는다

[Kiwi의 2026년 9월 1일 HEAD](https://github.com/bab2min/Kiwi/tree/f06a54db4748e4eb5b8ced127c281fc8fac73ea1)는 표제어와 품사 분석, 경량 언어 모델을 통한 모호성 해소를 제공한다. C++ 코어, 컴파일된 라이브러리와 모델 파일을 요구하므로 외부 패키지 없이 배포하는 현재 스캐너에는 들어갈 수 없다.

[Open Korean Text의 같은 날 HEAD](https://github.com/open-korean-text/open-korean-text/tree/74cc4ae7d3dab232747cd5ddb723e4b73c476e4f)는 Scala 및 Java 환경에서 정규화, 형태소 분석과 어근화를 제공하지만 “완전한 수준의 형태소 분석을 지향하지는 않습니다.”라고 범위를 밝힌다. JVM 의존성도 현재 배포 조건과 맞지 않는다.

[HFST의 같은 날 HEAD](https://github.com/hfst/hfst/tree/fcfb18ec145cf0add9c77f3e2133eb805155ec64)는 언어 규칙을 유한 상태 변환기로 만드는 라이브러리와 도구를 제공한다. [Rouzeta의 고정 HEAD](https://github.com/dsindex/rouzeta/tree/580e2eafc5e4b1bf3f82fa8f867fd9263190878c)는 이 접근을 한국어 형태 분석에 적용하지만 foma, Xerces-C, OpenFST와 별도 분석 자료를 요구한다. 앞선 [한국어 활용형 탐지 구현 조사](../../better-terms-scanner-reliability-5063/references/korean-morphology-rule-practices.md)가 확인한 43 MB 분석 자료도 현재의 작은 배포 스크립트에 비해 크다.

따라서 완성된 외부 분석기를 직접 호출하는 방법은 정확도 비교 기준으로는 유용하지만 이번 구현 후보에서는 제외한다.

### 미리 생성한 자료는 후속 확장 후보다

[hunspell-dict-ko의 고정 HEAD](https://github.com/spellcheck-ko/hunspell-dict-ko/blob/606164264399ca037325bd41750f9c108ed4c290/suffix.py)는 활용 규칙을 `suffixdata.py`에서 읽고, 조건과 어미 연결을 확장한 뒤 배포 자료를 만든다. 내부에서는 NFD를 계산에 사용하고 생성값을 NFC로 되돌린다. 이는 NFD 자체가 분석기가 아니라 자료 주도 규칙을 계산하기 위한 표현임을 보여 주며, 사람이 모든 활용형을 실행 코드에 적지 않는 선례다.

이 저장소도 승인된 한국어 규칙에서 작은 읽기 전용 자료를 미리 생성하고 배포 스크립트에는 실행기만 둘 수 있다. 다만 자료의 출처, 라이선스, 갱신 명령, 결과 크기와 재현성을 먼저 승인해야 한다. hunspell-dict-ko의 완성 사전과 HFST는 현재 저장소에 그대로 가져올 수 있는 무조건적인 허가나 기술 조건을 제공하지 않는다. 이 조사는 외부 자료의 복사 또는 의존성 추가를 승인하지 않는다.

## 권고하는 책임 분리

후속 설계는 다음 순서에서 각 책임을 한 번만 수행해야 한다.

1. 원문은 바꾸지 않고 UTF-16 위치 계산의 기준으로 유지한다.
2. 일반 완전 일치 규칙과 원문의 현대 한글 비교 구간에 기존 NFD 위치 대응을 적용한다.
3. 검사 대상으로 삼을 한글 문자 구간에 따라 형태 판정 후보를 결정한다.
4. 진단 규칙 목록의 모든 용언에 공통 활용 규칙을 적용해 표제어와 품사 후보를 만든다. 필요한 경우 내부에서 NFD를 사용한다.
5. 형태 후보와 진단 정책을 연결해 기존 경고 ID, 표현, 원문 위치와 인용문을 만든다.

구현 후보를 평가할 때에는 다음 조건으로 일반화를 확인한다.

- 새 용언을 추가할 때 진단 규칙 자료만 바뀌고 스캐너 실행 코드는 바뀌지 않는다.
- 모든 용언 규칙이 같은 형태 판정과 같은 모호성 정책을 적용받는다.
- 일반 완전 일치 규칙은 NFC와 NFD로 저장한 정준 동등 입력을 모두 찾는다.
- `warning.expression`, 원문 UTF-16 위치, 인용문과 JSON 구조는 현재 결과와 호환된다.
- 실행 중 외부 패키지, 모델, 네트워크와 JVM 또는 native 실행 파일이 필요하지 않다.
- 현재의 특정 표제어 배열과 `박지 씨` 단일 예외가 실행 코드에 남지 않는다.

가장 먼저 구현할 대상은 기존 NFD 위치 대응을 일반 완전 일치에 적용하는 처리와 공통 형태 규칙을 읽는 판정기다. 전체 한국어 사전이나 대형 유한 상태 자료는 실제 미탐지 및 오탐 측정에서 작은 공통 규칙이 부족하다고 확인될 때만 검토한다.

## 구현 전에 승인할 항목

- 진단 규칙 목록에서 완전 일치 표현과 표제어 규칙을 구분하는 자료 형식
- 지원할 현대 한글, 옛한글, 호환 자모와 방점의 범위
- 형태 분석만으로 문맥상 의미를 확정할 수 없는 후보의 경고 정책
- 불규칙 활용 자료의 출처와 관리 책임
- 외부 자료를 미리 생성해 포함할 경우의 라이선스, 최대 배포 크기와 재생성 절차

이 항목은 요구사항 승인 책임자의 승인 없이 결정으로 기록하지 않는다.

## 한계와 불확실성

- 이번 조사는 구조와 의존성 적합성을 비교했으며, 후보 구현의 정확도와 실행 시간은 측정하지 않았다.
- 현재 네 표제어의 어미 목록이 다루는 활용형을 전수 언어 자료와 대조하지 않았다. 이 목록은 일반 규칙의 근거가 아니라 현재 실행 코드에 직접 적은 항목을 확인하는 증거로만 사용했다.
- `Intl.Segmenter` 실행 결과는 Node.js 22.18.0과 ICU 77.1에서만 확인했다. 명세상 구현 의존 결과이므로 다른 ICU 버전의 동일 결과를 전제하지 않는다.
- 외부 저장소 HEAD는 2026년 9월 1일 `git ls-remote` 결과다. Kiwi `f06a54db4748e4eb5b8ced127c281fc8fac73ea1`, Open Korean Text `74cc4ae7d3dab232747cd5ddb723e4b73c476e4f`, hunspell-dict-ko `606164264399ca037325bd41750f9c108ed4c290`, Rouzeta `580e2eafc5e4b1bf3f82fa8f867fd9263190878c`, HFST `fcfb18ec145cf0add9c77f3e2133eb805155ec64`를 확인했다.
- 정규화와 규칙 기반 분석만으로 문맥 중의성을 완전히 해결할 수 없다. 높은 정밀도가 필수라면 모델을 포함한 형태 분석기의 배포 비용과 현재 무의존성 조건 가운데 하나를 다시 선택해야 한다.
