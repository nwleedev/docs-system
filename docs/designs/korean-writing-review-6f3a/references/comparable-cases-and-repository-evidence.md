# 한국어 문서 검토 실패와 유사 운영 사례

## 조사 질문과 자료 보호

이 문서는 [한국어 문서 검토 재발 방지 요구사항의 적용 조건](../requirements.md#적용-조건)에 따라, 지정된 예시 저장소의 모든 워크트리 브랜치와 커밋에서 반복된 문장 문제를 식별 정보 없이 기록하고 외부의 유사 운영 사례와 비교한다. AGENTS와 스킬의 변경 담당자는 어떤 실패가 한 문장의 우연한 표현인지, 어떤 실패가 작성 및 검토 체계의 누락인지 구분해 이후 변경 범위를 정할 수 있어야 한다.

예시 저장소의 이름, 로컬 위치, 조직명, 개인 자료, 문서 제목과 원문은 기록하지 않는다. 아래 수치는 2026년 8월 1일에 Git 객체와 각 커밋의 변경을 읽어 계산한 집계이며, 문장 내용은 일반화한 실패 유형으로만 설명한다.

원본 저장소를 열람할 수 있는 검증 역할과 집계 기록의 접근 및 보관 방법은 정해지지 않았다. 아래 수치는 현재 조사 결과를 설명하지만 독립 검증을 마친 기준은 아니다. 요구사항 작성자는 갱신한 체계를 적용하고 후속 작업을 계속한 뒤 이 문제를 다시 검토하기로 했다. 이번 설계와 이후 파일 변경을 막는 질문으로 취급하지 않으며, 원본 위치나 식별 정보를 이 문서에 추가해 임시로 해결하지 않는다.

## 예시 저장소에서 확인한 전체 이력

예시 저장소에는 두 워크트리 브랜치가 있었다. 기본 브랜치는 초기 커밋 하나, 문서 작업 브랜치는 기본 브랜치 위의 커밋 여섯 개로 구성됐다. 조사자는 일곱 커밋의 변경 파일, 추가 및 수정 문장과 최종 문서를 모두 확인했다.

초기 커밋은 저장소 지침, 설계 문서 지침, 개발 지침과 무시 파일을 추가했다. 이후 여섯 커밋은 요구사항 작성 및 보정 네 번과 리서치 문서 작성 및 보정 두 번으로 나뉘었다. 기본 브랜치에는 문서 작성과 공유 전 검토 지침이 있었지만, 작업 브랜치의 리서치 문서에는 같은 문장부호와 번역체가 반복됐다.

### 가운뎃점은 긴 리서치 문서를 작성할 때 집중됐다

초기 커밋의 Markdown 추가문에는 가운뎃점이 두 번 있었다. 요구사항만 추가하거나 보정한 세 커밋에는 없었고, 마지막 요구사항 보정에는 한 번 있었다. 반면 첫 리서치 문서 커밋의 추가문에는 301번, 두 번째 리서치 문서 커밋의 추가문에는 116번 나타났다.

최종 리서치 문서 다섯 개에서는 각각 116번, 114번, 107번, 80번과 21번 나타났고 요구사항 문서에는 한 번 나타났다. 병렬 항목, 기술 조건, 지표와 역할을 한 어구에 압축할 때 가운뎃점이 반복됐다. 특정 문장을 고치는 것만으로는 다음 긴 문서에서 재발을 막기 어렵다는 증거다.

### 후보 단어에는 정상 용례와 불분명한 용례가 섞였다

리서치 커밋의 추가문에는 `계약`, `경로`, `공개`가 반복됐다. 일부 `계약`은 실제 법률 또는 업무 계약을 가리켰지만, 일부는 측정 전에 정할 규칙이나 API 입출력 조건을 한 단어로 묶었다. `경로`도 파일 위치가 아니라 경험을 얻는 방법, 회사 업무와 별도 활동 가운데 선택할 방법을 가리키는 데 사용됐다. `공개`는 누구나 읽을 수 있는 저장소, 인터넷에 배포된 제품, 외부에 제시할 수 있는 증거와 오픈소스를 한꺼번에 나타냈다.

이 결과는 단어의 출현만으로 실패를 정하면 실제 법률 계약과 파일 경로까지 잘못 고치게 됨을 보여 준다. 같은 단어가 가리키는 대상, 이용 주체, 권한, 행동과 결과를 문장에서 확인해야 한다.

### 지침의 존재만으로 검토 실행을 증명할 수 없다

기본 브랜치의 지침에는 자연스러운 한국어 작성과 `use-words-review` 실행 조건이 있었다. 그런데 작업 브랜치의 대량 문서 변경에는 가운뎃점과 불분명한 표현이 그대로 남았다. Git 이력에는 독립 검토가 어떤 문장을 판정했는지, 한국어 참조 자료를 읽었는지, 기계 검사를 실행했는지 확인할 결과가 없었다.

따라서 “지침 파일이 복사됐다”와 “한국어 검토가 실행됐다”를 다른 완료 조건으로 다뤄야 한다. 설치 확인은 파일 존재로 끝낼 수 있지만, 동작 확인은 한국어 결과물을 만드는 대표 작업에서 참조 파일 로딩, 기계 검사와 의미 검토 결과를 관찰해야 한다.

## 유사 사례에서 확인한 운영 방식

### Microsoft는 공통 규범과 언어별 판단 자료를 함께 사용한다

Microsoft의 한국어 현지화 스타일 가이드는 국립국어원의 사전과 맞춤법을 규범 자료로 두고, 제품 독자와 상황에 맞는 한국어 선택을 별도 스타일 지침으로 관리한다. 문장과 문단의 의도를 이해한 뒤 한국어 문장을 다시 쓰고, 기술 독자와 일반 독자에게 사용하는 용어를 달리하도록 안내한다. 2024년 9월 5일 수정된 PDF와 2025년 2월 6일에 갱신된 공식 배포 파일을 2026년 8월 1일에 확인했다. [Microsoft 한국어 현지화 스타일 가이드](https://aka.ms/korean-styleguide)

현재 저장소에 적용할 수 있는 점은 맞춤법 규범만으로 문서 품질을 끝내지 않고, 대상 저장소의 독자와 기술 문맥에 맞는 언어별 자료를 함께 읽게 하는 구조다. Microsoft의 개별 추천 번역어를 이 저장소의 공통 용어로 가져오는 것은 조사 범위를 벗어난다.

### Vale는 확실히 판정할 수 있는 항목만 자동화한다

Vale는 문서 형식을 이해하는 검사 도구로, 정규식 기반 존재 검사와 치환, 반복, 일관성, 맞춤법 및 프로젝트 어휘를 조합한다. 규칙마다 적용 범위와 예외를 둘 수 있어 코드 블록과 일반 산문을 구분할 수 있다. 2026년 8월 1일에 공식 저장소와 문서를 확인했다.

- [Vale 공식 저장소](https://github.com/vale-cli/vale)는 문서 형식을 인식하고 프로젝트별 규칙을 확장할 수 있는 문장 검사 도구임을 설명한다.
- [Vale 스타일 문서](https://docs.vale.sh/topics/styles)는 규칙별 적용 범위, 경고 수준과 검사 종류를 정의하는 방법을 설명한다.
- [Vale 프로젝트 어휘 문서](https://docs.vale.sh/keys/vocabularies)는 허용어와 피해야 할 표현을 별도 파일로 관리하면서 정규식 예외를 적용하는 방법을 설명한다.

이 사례는 가운뎃점처럼 정확한 문자 검사는 자동화하고, `경로`와 `계약`처럼 문맥에 따라 뜻이 달라지는 표현은 검토 후보로 남기는 분담을 뒷받침한다. 후보 단어를 모두 거부 목록에 넣으면 정상 전문용례도 오류로 처리될 수 있다.

### AGENTS와 스킬은 항상 필요한 조건과 상세 자료를 나눈다

OpenAI의 Codex 문서는 `AGENTS.md`를 작업 전에 읽고 저장소 루트부터 현재 작업 디렉터리까지 지침을 합친다고 설명한다. Anthropic의 Agent Skills 자료는 스킬 이름과 설명을 먼저 불러오고, 선택된 스킬의 본문과 참조 자료를 필요할 때 읽는 단계적 로딩을 설명한다. OpenAI 문서는 2026년 8월 1일에 현재 내용을 확인했고, Anthropic 자료는 2025년 10월 16일 공개 뒤 2025년 12월 18일에 공개 명세 안내가 추가된 판을 확인했다.

- [OpenAI의 AGENTS.md 지침 로딩 문서](https://developers.openai.com/codex/guides/agents-md)는 저장소 전체에 필요한 시작 조건을 루트 지침에서 전달할 수 있음을 확인한다.
- [Anthropic의 Agent Skills 구조 설명](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)은 상세 자료를 스킬 참조 파일로 분리하면서도 스킬 설명이 올바른 시점에 선택되도록 작성해야 함을 설명한다.

현재 저장소에서는 “커밋하거나 공유할 한국어 글이나 이름을 만들면 `korean.md`를 읽는다”는 짧은 조건을 AGENTS에 두고, 실제 표현 판정은 스킬 참조 파일 한 곳에서 관리하는 방식으로 적용할 수 있다. 파일을 바꾸지 않는 채팅 답변의 조건부 로딩은 [채팅 답변의 한국어 품질 적용 조사](./conversational-korean-output-research.md)가 소유한다. 이는 AGENTS에 긴 단어 목록을 복사하는 방식과 다르다.

### 실제 실패 자료가 평가 묶음의 시작점이 된다

OpenAI와 Anthropic은 실제 사용 사례와 실패에서 평가 과제를 만들고, 확정적으로 검사할 수 있는 항목은 자동화하며, 정답이 하나로 정해지지 않는 품질 판단은 명확한 기준을 사용한 모델 또는 승인받은 기대 판정으로 보정하라고 안내한다. OpenAI 문서는 2026년 8월 1일에 현재 내용을 확인했고, Anthropic 자료는 2026년 1월 9일 공개본을 확인했다.

- [OpenAI의 평가 설계 지침](https://developers.openai.com/api/docs/guides/evaluation-best-practices)은 과제별 평가, 지속적인 사례 추가, 자동 검사와 사람 판단의 보정을 권한다.
- [Anthropic의 에이전트 평가 설계 지침](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)은 실제 실패에서 작은 초기 평가 묶음을 만들고, 가능한 경우 결정적인 검사와 필요한 경우 모델 판정을 결합하도록 안내한다.

예시 저장소의 문장을 그대로 평가 자료로 복사하면 개인 자료와 특정 조직 정보가 남을 수 있다. 조사자는 실패 구조만 보존한 합성 문장과 정확한 전문용례를 짝지어 언어별 판정 자료에 추가하는 방안을 제안한다. 한국어 사례는 `korean.md`가 소유하고, 언어 공통 사례만 `examples.md`에 둔다. 이번 작업의 초기 기대 판정은 [한국어 답변 검토 평가 사례](./korean-review-evaluation-cases.md)에 기록했으며, 갱신한 체계를 적용한 결과로 보정해야 한다.

## 조사자가 제안하는 적용 방향

관찰한 이력은 가운뎃점 문자 검사와 검토 호출을 함께 확인할 필요를 보여 준다. 커밋 이력만으로 실제 검토 호출이 누락됐는지 확정할 수는 없다. 일반 산문에서 U+00B7을 쓰지 않는 규칙이 승인됐으므로, 기계 검사는 정확한 문자 보존 예외를 제외한 모든 변경에서 같은 기준으로 문자를 찾아야 한다.

번역체는 기계 검사만으로 판정할 수 없다. 조사자는 커밋하거나 공유할 한국어 글이나 이름을 만들기 전에 `korean.md`를 읽게 하고, 공유 전 독립 검토에서 문장의 대상, 주체, 행동, 조건과 결과를 판정하는 방안을 제안한다. 정상 전문용례와 실패 문장을 함께 평가하지 않으면 검토가 단어 삭제로 치우칠 수 있다. 채팅 답변에는 별도 조사 문서가 정한 자체 점검과 조건부 로딩을 적용한다.

복사 설치 방식에서는 스킬, AGENTS 호출 구간과 한국어 참조 자료가 함께 갱신됐는지 확인할 필요가 있다. 자동 배포 도구를 새로 만들지는 이번 요구사항에 포함되지 않았으므로, 조사자는 설치 뒤 대표 작업을 실행하는 확인 절차를 문서와 스킬에 연결하는 방법부터 검토할 것을 제안한다.

## 한계와 다시 조사할 조건

- 예시 저장소는 한 곳이며, 문서 종류와 작성 모델이 다른 저장소의 실패 빈도를 대표하지 않는다.
- 커밋 이력만으로 작성 중 어떤 지침이 실제로 로딩됐는지 확인할 수 없다. 관찰한 결과는 호출 누락 가능성을 강하게 보여 주지만 특정 도구 동작을 확정하지 않는다.
- 외부 사례는 구조와 검사 분담의 근거다. 각 조직의 전체 편집 과정이나 품질 개선률을 현재 저장소에 그대로 적용할 수 없다.
- AGENTS 지침, 스킬 탐색 위치나 모델 동작이 바뀌면 설치 및 호출 확인 방법을 다시 조사해야 한다.
- 예시 저장소 집계를 다시 검증할 역할과 기록 보관 방식은 갱신한 체계를 적용한 뒤 후속 작업에서 다시 정해야 한다.
