# 한국어 문서 검토 실패와 유사 운영 사례

## 조사 질문과 자료 보호

이 문서는 [한국어 문서 검토 재발 방지 요구사항의 적용 조건](../requirements.md#적용-조건)에 따라, 지정된 예시 저장소의 모든 워크트리 브랜치와 커밋에서 반복된 문장 문제를 식별 정보 없이 기록하고 외부의 유사 운영 사례와 비교한다. AGENTS와 스킬의 변경 담당자는 어떤 실패가 한 문장의 우연한 표현인지, 어떤 실패가 작성 및 검토 체계의 누락인지 구분해 이후 변경 범위를 정할 수 있어야 한다.

예시 저장소의 이름, 로컬 위치, 조직명, 개인 자료, 문서 제목과 원문은 기록하지 않는다. 초기 이력 수치는 2026년 8월 1일에, 후속 문서 수치는 2026년 8월 2일에 Git 객체와 각 커밋의 변경을 읽어 계산했다. 문장 내용은 일반화한 실패 유형으로만 설명한다.

원본 저장소를 열람할 수 있는 검증 역할과 집계 기록의 접근 및 보관 방법은 정해지지 않았다. 아래 수치는 현재 조사 결과를 설명하지만 독립 검증을 마친 기준은 아니다. 요구사항 작성자는 갱신한 체계를 적용하고 후속 작업을 계속한 뒤 이 문제를 다시 검토하기로 했다. 이번 설계와 이후 파일 변경을 막는 질문으로 취급하지 않으며, 원본 위치나 식별 정보를 이 문서에 추가해 임시로 해결하지 않는다.

## 예시 저장소에서 확인한 전체 이력

예시 저장소에는 초기 설정 이력과 그 뒤의 문서 작업 이력이 있었다. 조사자는 두 이력에서 바뀐 파일, 추가 및 수정 문장과 최종 문서를 모두 확인했다. 공개 문서에는 저장소를 다시 식별할 수 있는 브랜치 구조와 정확한 커밋 수를 남기지 않는다.

초기 설정 이력은 저장소 지침, 설계 문서 지침, 개발 지침과 무시 파일을 추가했다. 후속 이력은 요구사항과 리서치 문서를 작성하고 보정했다. 기준 지침에는 문서 작성과 공유 전 검토 조건이 있었지만, 후속 리서치 문서에는 같은 문장부호와 번역체가 반복됐다.

### 가운뎃점은 긴 리서치 문서를 작성할 때 집중됐다

초기 설정과 요구사항 변경에서는 가운뎃점이 없거나 한 자릿수에 그쳤다. 반면 긴 리서치 문서를 추가한 변경에서는 수백 번 나타났다.

최종 리서치 문서에서는 문서마다 수십 번에서 백 번 이상 나타났지만 요구사항 문서에는 드물었다. 병렬 항목, 기술 조건, 지표와 역할을 한 어구에 압축할 때 가운뎃점이 반복됐다. 특정 문장을 고치는 것만으로는 다음 긴 문서에서 재발을 막기 어렵다는 증거다.

### 후보 단어에는 정상 용례와 불분명한 용례가 섞였다

리서치 커밋의 추가문에는 `계약`, `경로`, `공개`가 반복됐다. 일부 `계약`은 실제 법률 또는 업무 계약을 가리켰지만, 일부는 측정 전에 정할 규칙이나 API 입출력 조건을 한 단어로 묶었다. `경로`도 파일 위치가 아니라 경험을 얻는 방법, 회사 업무와 별도 활동 가운데 선택할 방법을 가리키는 데 사용됐다. `공개`는 누구나 읽을 수 있는 저장소, 인터넷에 배포된 제품, 외부에 제시할 수 있는 증거와 오픈소스를 한꺼번에 나타냈다.

이 결과는 단어의 출현만으로 실패를 정하면 실제 법률 계약과 파일 경로까지 잘못 고치게 됨을 보여 준다. 같은 단어가 가리키는 대상, 이용 주체, 권한, 행동과 결과를 문장에서 확인해야 한다.

### 지침의 존재만으로 검토 실행을 증명할 수 없다

기준 지침에는 자연스러운 한국어 작성과 `use-words-review` 실행 조건이 있었다. 그런데 후속 문서 변경에는 가운뎃점과 불분명한 표현이 그대로 남았다. Git 이력에는 독립 검토가 어떤 문장을 판정했는지, 한국어 참조 자료를 읽었는지, 기계 검사를 실행했는지 확인할 결과가 없었다.

따라서 “지침 파일이 복사됐다”와 “한국어 검토가 실행됐다”를 다른 완료 조건으로 다뤄야 한다. 설치 확인은 파일 존재로 끝낼 수 있지만, 동작 확인은 한국어 결과물을 만드는 대표 작업에서 참조 파일 로딩, 기계 검사와 의미 검토 결과를 관찰해야 한다.

### 후속 문서 작업에서 다른 번역체가 재발했다

갱신된 AGENTS 지침을 적용한 뒤 이루어진 후속 문서 작업도 별도로 확인했다. 여러 Markdown 문서에 수백 줄이 추가됐고, 추가문에서 `포화`와 `경계`는 각각 두 자릿수, `소유`는 그보다 많이, `반증`은 몇 차례 나타났다. 기존 대표 후보인 `계약`, `경로`, `공개`도 여러 번 반복됐다. 출현 횟수는 검토 후보를 찾는 신호이며, 그 자체로 오류 판정은 아니다.

문맥을 확인하자 `포화가 아니었다`와 같은 결론 문구가 여러 절에서 반복됐고, `경계`는 포함 대상과 제외 대상을 직접 쓰는 대신 책임이나 검토 범위를 뭉뚱그렸다. 문서나 기관이 자료와 절차를 `소유한다`는 문장은 실제로 누가 기록하고 운영하며 답변하는지 감췄다. `반증`은 가설을 반박하는 증거가 아니라 실행 가능성을 확인하거나 실패 조건을 점검하는 뜻으로 쓰였다. 일부 `경로`도 파일 위치가 아니라 선택 방법이나 진행 순서를 대신했다.

이 어휘는 새 문서만의 산출물이 아니었다. 기준이 된 기존 설계 자료에도 `포화`, `경계`, `소유`, `경로`가 있었고, 영어 설계 지침에는 `own`, `owner`, `ownership`이 수십 번 있었다. 이 분포는 작성 모델이 기존 문서의 구조와 근거뿐 아니라 표현까지 재사용했을 가능성을 뒷받침한다. 다만 커밋만으로 생성 과정을 관찰할 수 없으므로 인과를 확정하지 않는다.

후속 작업이 사용한 AGENTS 지침은 기본 제한 크기 안에 있었고 자연스러운 한국어 규칙도 포함했다. 반면 실제 수동 Git 워크트리에는 Codex가 저장소 스킬로 탐색하는 위치에 `use-words-review`가 없었다. 다른 체크아웃의 무시된 디렉터리에 같은 스킬 원본이 있어도 현재 작업 디렉터리에서 발견되지 않으면 검토 절차는 시작되지 않는다. 잘못된 설치 위치, 워크트리별 파일 차이, 기존 문서 어휘의 무비판적 재사용과 공유 전 검토 부재는 이 재발과 함께 관찰된 조건이다. 각 조건의 기여도는 현재 자료만으로 확정하지 않는다.

특정 모델이 다른 모델보다 원래 나쁜 한국어를 쓴다는 결론은 이 자료로 입증할 수 없다. 번역체 연구는 LLM이 자연스러운 참조보다 번역문에 가까운 표현을 만들 수 있고 학습 및 미세 조정 자료가 그 경향에 영향을 줄 수 있음을 보이지만, 이번 모델과 비교 모델을 같은 입력, 같은 도구와 같은 평가 조건으로 반복 실행한 자료는 없다. 이번 설계는 모델 이름을 원인으로 고정하지 않고 설치, 문맥, 검토와 평가에서 재현 가능한 조건을 고친다.

### 모델 차이로 느껴진 원인은 분리해서 검증해야 한다

OpenAI는 GPT-5.6을 포함한 최신 모델에서 중복 지침과 긴 도구 설명을 줄이고, 실제 평가에서 확인된 결함을 고치는 예시는 남기라고 안내한다. 대화가 길어질수록 반복된 문맥이 영향을 키울 수 있으므로 시작 시점과 누적 문맥을 함께 보라고도 권한다. Anthropic도 출력의 어조와 구조를 바꾸는 데 구체적이고 다양한 예시가 강하게 작용한다고 설명한다. 두 회사의 자료는 모델이 문체 지침을 처리하는 방식에 차이가 있을 수 있음을 보여 주지만, 어느 모델의 한국어가 더 낫다는 비교 결과는 제공하지 않는다.

- [OpenAI의 GPT-5.6 프롬프트 지침](https://developers.openai.com/api/docs/guides/latest-model#prompting-best-practices)
- [Anthropic의 Claude 프롬프트 지침](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)

언어 연구는 모델이 번역문에서 자주 보이는 어휘와 문장 구조를 재생할 수 있다는 설명을 뒷받침한다. ACL 2025 논문은 번역 작업에서 LLM의 결과에 번역체가 남고 미세 조정 자료의 편향이 영향을 줄 수 있다고 보고했다. 한국어 생성문 연구인 KatFishNet은 조사한 모델 결과에서 사람이 쓴 글보다 품사 연쇄의 다양성이 낮고 반복 구조가 많았다고 보고했다. 두 연구 모두 이번 Codex 실행이나 비교 대상 모델을 직접 시험하지 않았으므로 일반적인 발생 가능성만 설명한다.

- [ACL 2025의 LLM 번역체 연구](https://aclanthology.org/2025.acl-long.630/)
- [KatFishNet의 한국어 AI 생성문 분석](https://arxiv.org/abs/2503.00032)

한국어와 영어, 중국어 생성문의 어휘 다양성을 비교한 연구에서는 GPT-4.1이 Claude 3.5보다 일관되게 낮은 결과를 보이지 않았다. 이 결과도 현재 모델 비교로 옮길 수는 없지만, 공급자 이름만으로 관찰한 문체 차이를 설명하기 어렵다는 반대 근거다. [LLM 생성문의 언어별 어휘 다양성 비교](https://www.kci.go.kr/kciportal/ci/sereArticleSearch/ciSereArtiView.kci?sereArticleSearchBean.artiId=ART003291556)

현재 자료로 구분할 수 있는 원인은 세 층이다. 첫째, 일반적인 학습 및 생성 특성 때문에 번역체와 반복 구조가 나올 수 있다. 둘째, 기존 문서와 긴 지침이 현재 결과의 어휘를 유도할 수 있다. 셋째, 스킬이 발견되지 않으면 저장 전 검토가 실행되지 않는다. 이번 후속 사례는 둘째와 셋째를 직접 확인했지만 첫째의 모델별 차이는 확인하지 못했다. 이후 모델 비교가 필요하면 같은 원문, 같은 AGENTS, 같은 스킬 설치, 같은 도구와 추론 설정으로 여러 번 실행하고 모델 이름을 가린 사람 판정을 사용해야 한다.

## 유사 사례에서 확인한 운영 방식

### Microsoft는 공통 규범과 언어별 판단 자료를 함께 사용한다

Microsoft의 한국어 현지화 스타일 가이드는 국립국어원의 사전과 맞춤법을 규범 자료로 두고, 제품 독자와 상황에 맞는 한국어 선택을 별도 스타일 지침으로 관리한다. 문장과 문단의 의도를 이해한 뒤 한국어 문장을 다시 쓰고, 기술 독자와 일반 독자에게 사용하는 용어를 달리하도록 안내한다. 2024년 9월 5일 수정된 PDF와 2025년 2월 6일에 갱신된 공식 배포 파일을 2026년 8월 1일에 확인했다. [Microsoft 한국어 현지화 스타일 가이드](https://aka.ms/korean-styleguide)

현재 저장소에 적용할 수 있는 점은 맞춤법 규범만으로 문서 품질을 끝내지 않고, 대상 저장소의 독자와 기술 문맥에 맞는 언어별 자료를 함께 읽게 하는 구조다. Microsoft의 개별 추천 번역어를 이 저장소의 공통 용어로 가져오는 것은 조사 범위를 벗어난다.

### Vale는 확실히 판정할 수 있는 항목만 자동화한다

Vale는 문서 형식을 이해하는 검사 도구로, 정규식 기반 존재 검사와 치환, 반복, 일관성, 맞춤법 및 프로젝트 어휘를 조합한다. 규칙마다 적용 범위와 예외를 둘 수 있어 코드 블록과 일반 산문을 구분할 수 있다. 2026년 8월 1일에 공식 저장소와 문서를 확인했다.

- [Vale 공식 저장소](https://github.com/vale-cli/vale)는 문서 형식을 인식하고 프로젝트별 규칙을 확장할 수 있는 문장 검사 도구임을 설명한다.
- [Vale 스타일 문서](https://docs.vale.sh/topics/styles)는 규칙별 적용 범위, 경고 수준과 검사 종류를 정의하는 방법을 설명한다.
- [Vale 프로젝트 어휘 문서](https://docs.vale.sh/keys/vocabularies)는 허용어와 피해야 할 표현을 별도 파일로 관리하면서 정규식 예외를 적용하는 방법을 설명한다.

이 사례는 가운뎃점처럼 정확한 문자 검사는 자동화하고, `경로`와 `계약`처럼 문맥에 따라 뜻이 달라지는 표현은 검토 후보로 남기는 분담을 뒷받침한다. 후보 단어를 모두 거부 목록에 넣으면 정상 전문용례도 오류로 처리될 수 있다.

### AGENTS와 스킬은 항상 필요한 조건과 상세 자료를 나눈다

OpenAI의 Codex 문서는 `AGENTS.md`를 작업 전에 읽고 저장소 루트부터 현재 작업 디렉터리까지 지침을 합친다고 설명한다. Anthropic의 Agent Skills 자료는 스킬 이름과 설명을 먼저 불러오고, 선택된 스킬의 본문과 참조 자료를 필요할 때 읽는 단계적 로딩을 설명한다. OpenAI 문서는 2026년 8월 1일에 현재 내용을 확인했고, Anthropic 자료는 2025년 10월 16일 공개 뒤 2025년 12월 18일에 공개 명세 안내가 추가된 판을 확인했다.

- [OpenAI의 AGENTS.md 지침 로딩 문서](https://developers.openai.com/codex/guides/agents-md)는 저장소 전체에 필요한 시작 조건을 루트 지침에서 전달할 수 있음을 확인한다.
- [Anthropic의 Agent Skills 구조 설명](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)은 상세 자료를 스킬 참조 파일로 분리하면서도 스킬 설명이 올바른 시점에 선택되도록 작성해야 함을 설명한다.

현재 저장소에서는 “커밋하거나 공유할 한국어 글이나 이름을 만들면 `korean.md`를 읽는다”는 짧은 조건을 AGENTS에 두고, 실제 표현 판정은 스킬 참조 파일 한 곳에서 관리하는 방식으로 적용할 수 있다. 일반 채팅에서는 이 파일을 읽지 않는다. 사용자가 특정 문구 검토를 명시적으로 요청하거나 채팅에서 만든 문구를 저장 또는 전달하려는 경우에만 예외로 읽는다. 자세한 구분은 [채팅 답변의 한국어 품질 적용 조사](./conversational-korean-output-research.md)에 기록한다. 이는 AGENTS에 긴 단어 목록을 복사하는 방식과 다르다.

### 실제 실패 자료가 평가 묶음의 시작점이 된다

OpenAI와 Anthropic은 실제 사용 사례와 실패에서 평가 과제를 만들고, 확정적으로 검사할 수 있는 항목은 자동화하며, 정답이 하나로 정해지지 않는 품질 판단은 명확한 기준을 사용한 모델 또는 승인받은 기대 판정으로 보정하라고 안내한다. OpenAI 문서는 2026년 8월 1일에 현재 내용을 확인했고, Anthropic 자료는 2026년 1월 9일 공개본을 확인했다.

- [OpenAI의 평가 설계 지침](https://developers.openai.com/api/docs/guides/evaluation-best-practices)은 과제별 평가, 지속적인 사례 추가, 자동 검사와 사람 판단의 보정을 권한다.
- [Anthropic의 에이전트 평가 설계 지침](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)은 실제 실패에서 작은 초기 평가 묶음을 만들고, 가능한 경우 결정적인 검사와 필요한 경우 모델 판정을 결합하도록 안내한다.

예시 저장소의 문장을 그대로 평가 자료로 복사하면 개인 자료와 특정 조직 정보가 남을 수 있다. 조사자는 실패 구조만 보존한 합성 문장과 정확한 전문용례를 짝지어 언어별 판정 자료에 추가하는 방안을 제안한다. 한국어 사례는 `korean.md`에, 언어 공통 사례는 `examples.md`에 둔다. 이번 작업의 초기 기대 판정은 [한국어 답변 검토 평가 사례](./korean-review-evaluation-cases.md)에 기록했으며, 갱신한 체계를 적용한 결과로 보정해야 한다.

## 조사자가 제안하는 적용 방향

관찰한 이력은 가운뎃점 문자 검사와 검토 호출을 함께 확인할 필요를 보여 준다. 커밋 이력만으로 실제 검토 호출이 누락됐는지 확정할 수는 없다. 일반 산문에서 U+00B7을 쓰지 않는 규칙이 승인됐으므로, 기계 검사는 정확한 문자 보존 예외를 제외한 모든 변경에서 같은 기준으로 문자를 찾아야 한다.

번역체는 기계 검사만으로 판정할 수 없다. 조사자는 커밋하거나 공유할 한국어 글이나 이름을 만들기 전에 `korean.md`를 읽게 하고, 공유 전 독립 검토에서 문장의 대상, 주체, 행동, 조건과 결과를 판정하는 방안을 제안한다. 정상 전문용례와 실패 문장을 함께 평가하지 않으면 검토가 단어 삭제로 치우칠 수 있다. 일반 채팅은 AGENTS 작성 규칙만 적용하고, 명시적인 문구 검토 요청과 저장 예정 문구에만 참조 파일과 스킬을 사용한다.

복사 설치 방식에서는 스킬, AGENTS 호출 구간과 한국어 참조 자료가 함께 갱신됐는지 확인할 필요가 있다. 자동 배포 도구를 새로 만들지는 이번 요구사항에 포함되지 않았으므로, 조사자는 설치 뒤 대표 작업을 실행하는 확인 절차를 문서와 스킬에 연결하는 방법부터 검토할 것을 제안한다.

기존 설계 문서는 사실, 결정과 문서 구조를 확인하는 근거로만 사용해야 한다. 기존 표현이 승인된 문구라는 별도 근거가 없으면 제목, 요약 문장과 반복 어구를 새 문서의 문체 예시로 재사용하지 않는다. 비교 대상마다 같은 속성을 같은 순서로 쓰는 구조는 독자에게 도움이 될 수 있으므로 유지할 수 있다. 금지할 것은 반복 구조 자체가 아니라 근거 없이 되풀이하는 결론 문구와 실제 행동을 감춘 추상 명사다.

## 한계와 다시 조사할 조건

- 예시 저장소는 한 곳이며, 문서 종류와 작성 모델이 다른 저장소의 실패 빈도를 대표하지 않는다.
- 커밋 이력만으로 작성 중 어떤 지침이 실제로 로딩됐는지 확인할 수 없다. 관찰한 결과는 호출 누락 가능성을 강하게 보여 주지만 특정 도구 동작을 확정하지 않는다.
- 외부 사례는 구조와 검사 분담의 근거다. 각 조직의 전체 편집 과정이나 품질 개선률을 현재 저장소에 그대로 적용할 수 없다.
- AGENTS 지침, 스킬 탐색 위치나 모델 동작이 바뀌면 설치 및 호출 확인 방법을 다시 조사해야 한다.
- 특정 모델 사이의 차이는 같은 원문 자료, 같은 지침과 같은 실행 환경에서 여러 번 비교하지 않았다. 관찰한 문체만으로 모델별 원인을 단정할 수 없다.
- 예시 저장소 집계를 다시 검증할 역할과 기록 보관 방식은 갱신한 체계를 적용한 뒤 후속 작업에서 다시 정해야 한다.
