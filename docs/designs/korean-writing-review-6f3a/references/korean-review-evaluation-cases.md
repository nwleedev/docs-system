# 한국어 답변 검토 평가 사례

## 목적과 사용 방법

이 문서는 [한국어 문서 검토 재발 방지 요구사항의 완료 증거](../requirements.md#완료-증거)를 확인할 대표 사례를 한 번 제시한다. `korean.md`, 두 배포용 AGENTS 문서와 `use-words-review`의 변경 담당자는 같은 표현 기준을 파일 작성과 채팅 답변에 적용해 금지 문자를 놓치는지, 문맥이 정확한 용어까지 고치는지 확인할 수 있다. 채팅과 저장 결과물에서는 검토 호출 조건이 다르므로 문장 판정과 실행 범위를 따로 확인한다.

아래 판정은 갱신한 체계를 처음 실행하기 위한 기대값이다. 특정 저장소의 원문을 옮기지 않은 합성 사례이며, 후속 적용에서 발견한 오판에 따라 사례와 기대값을 보정한다.

## 판정 상태

- `pass`: 문장을 그대로 사용할 수 있다.
- `needs revision`: 저장소 근거와 문장 안의 정보만으로 고칠 수 있다.
- `needs human input`: 표현을 하나로 정할 정보나 승인된 결정이 없다.
- `not applicable`: 판정 항목이 해당 입력이나 작업 유형에 적용되지 않는다. 적용되지 않는 이유를 실행 결과에 적으며, 확인하지 못한 항목을 이 상태로 처리하지 않는다.

## 일반 산문의 U+00B7

### 사례 1: 병렬 산문

입력: `설계·구현·검증 결과를 한 문서에 기록한다.`

기대 판정: `needs revision`

지적 위치: 병렬 항목 사이의 U+00B7 두 곳

수정 예: `설계, 구현과 검증 결과를 한 문서에 기록한다.`

### 사례 2: 코드 포인트 설명

입력: `검사기는 U+00B7(·)을 찾는다.`

기대 판정: `pass`

근거: 코드 포인트와 해당 문자를 대응시키는 검증 자료이므로 정확한 문자를 보존한다.

### 사례 3: 승인 여부를 모르는 이름

입력: `화면에는 서비스·관리자라는 이름을 표시한다.`

기대 판정: `needs human input`

근거: 승인된 화면 이름을 정확히 인용한 것인지, 작성자가 새 산문을 만든 것인지 입력만으로 알 수 없다.

## 문맥에 따른 용어

### 사례 4: 규칙을 밝히지 않은 계약

입력: `두 모듈의 계약을 강화한다.`

기대 판정: `needs human input`

근거: 두 모듈이 지켜야 할 입력, 출력, 오류 처리나 호환 조건이 제시되지 않았다.

### 사례 5: 법률 용어

입력: `납품 계약은 양 당사자가 서명한 날부터 효력이 생긴다.`

기대 판정: `pass`

근거: 당사자와 효력 조건을 설명하는 법률 계약이다.

### 사례 6: 파일 위치

입력: `설정 파일 경로는 config/app.yml이다.`

기대 판정: `pass`

근거: 파일의 위치를 식별한다.

### 사례 7: 방법을 경로라고 쓴 문장

입력: `새 도구를 익힐 경로를 제공한다.`

기대 판정: `needs human input`

근거: 교육 과정, 문서, 실습 순서 또는 지원 절차 중 무엇을 제공하는지 알 수 없다.

### 사례 8: 이용 조건이 없는 공개

입력: `결과를 공개 가능한 형태로 바꾼다.`

기대 판정: `needs human input`

근거: 누가 어디에서 어떤 행동을 할 수 있어야 하는지 정해지지 않았다.

### 사례 9: 접근 조건을 밝힌 문장

입력: `개인 식별 정보를 제거한 보고서는 로그인 없이 읽을 수 있는 문서 사이트에 게시한다.`

기대 판정: `pass`

근거: 게시 전 조건, 게시 위치와 독자의 열람 조건이 드러난다.

### 사례 10: 줄일 대상을 밝히지 않은 좁히기

입력: `기능 범위를 좁혀 품질을 보장한다.`

기대 판정: `needs human input`

근거: 제외할 기능과 품질을 판정할 기준 또는 관찰 가능한 결과가 없다.

### 사례 11: 코드에 박는다는 표현

입력: `기본 주소를 코드에 박는다.`

기대 판정: `needs human input`

근거: 리터럴, 상수, 빌드 값 또는 설정 중 어느 방식인지 알 수 없다.

### 사례 12: 다섯 단어 밖의 후보

입력: `새 절차가 다양한 상황을 효과적으로 지원하고 문제를 표면화한다.`

기대 판정: `needs human input`

근거: 허용할 상황, 실행할 행동과 드러나는 문제가 없다. 판정 대상은 `지원하다`와 `표면화하다`이며 특정 다섯 단어로 제한되지 않는다.

### 사례 13: 실제 행동을 밝힌 문장

입력: `검사기는 문서 링크가 끊기면 파일 경로와 오류 원인을 출력한다.`

기대 판정: `pass`

근거: 행동 주체, 조건, 출력 내용이 드러나며 `경로`도 파일 위치라는 뜻으로 쓰였다.

## 번역체와 정형화된 채팅 답변

### 사례 14: 정보가 없는 상투적 답변

입력: `본질적으로 이 접근은 다양한 측면에서 강력하고 원활한 작업을 보장합니다.`

기대 판정: `needs human input`

근거: 평가 대상, 동작 조건과 확인 결과가 없다. 근거 없이 장점을 새로 만들면 안 되므로 문체만 고쳐서 통과시킬 수 없다.

### 사례 15: 확인한 결과를 직접 말하는 답변

입력: `설정 파일을 확인했지만 실행 명령은 정의되어 있지 않습니다. 저장소의 도구 구성을 더 확인한 뒤 실행 방법을 제안하겠습니다.`

기대 판정: `pass`

근거: 확인한 사실, 다음 행동과 순서가 드러난다.

### 사례 16: 형식만 맞춘 반복 구조

입력: `핵심은 세 가지입니다.`라는 도입 뒤에 근거 없이 같은 길이의 항목 세 개를 만들고, 끝에서 같은 내용을 다시 요약한다.

기대 판정: `needs revision`

근거: 실제 내용이 세 부분이라는 근거가 없고 도입과 결론이 정보를 추가하지 않는다.

### 사례 17: 주체가 사라진 수동문

입력: `검토에 의해서 문제가 다루어지고 결과가 공개됩니다.`

기대 판정: `needs human input`

근거: 누가 무엇을 확인하고, 어떤 문제를 어떻게 처리하며, 누가 결과를 볼 수 있는지 알 수 없다.

### 사례 18: 기준 없는 포화

입력: `이번 조사도 포화가 아니었다.`

기대 판정: `needs human input`

근거: 새 정보가 무엇이었는지, 자료 수집을 언제 끝낼지 알 수 없다.

### 사례 19: 정확한 연구 중단 기준

입력: `새 문제가 나오지 않는 인터뷰가 다섯 건 연속되면 자료가 포화됐다고 판정하고 모집을 끝낸다.`

기대 판정: `pass`

근거: 연구 자료의 포화 상태와 자료 수집 중단 기준이 함께 드러난다.

### 사례 20: 책임을 감춘 경계와 소유

입력: `기준 문서가 조사와 실행의 경계를 소유한다.`

기대 판정: `needs human input`

근거: 조사에 포함할 대상, 실행 담당자, 결정 또는 기록 행동이 없다.

### 사례 21: 정확한 보안 경계

입력: `외부 요청은 보안 경계를 통과하기 전에 인증 서비스가 서명을 검증한다.`

기대 판정: `pass`

근거: 경계의 안과 밖, 검사 시점과 행동 주체가 드러난다.

### 사례 22: 가설 없는 반증

입력: `구현 전에 접근법을 반증한다.`

기대 판정: `needs human input`

근거: 시험할 주장, 관찰 방법과 기각 조건이 없다.

### 사례 23: 가설과 기각 조건을 밝힌 반증

입력: `대조군과 실험군의 차이가 사전에 정한 오차 범위 안이면 새 알고리즘이 처리 시간을 줄인다는 가설을 반증한 것으로 판정한다.`

기대 판정: `pass`

근거: 시험할 가설, 관찰 대상과 기각 조건이 드러난다.

### 사례 24: 권리 관계를 밝힌 소유

입력: `임대 계약이 끝나면 장비의 소유권은 임차인에게 이전된다.`

기대 판정: `pass`

근거: 법률상 권리, 이전 시점과 권리를 받는 당사자가 드러난다.

### 사례 25: 필요한 반복 구조

입력: 세 후보를 비용, 예상 기간, 실패 조건의 순서로 각각 비교하고 후보마다 확인한 값과 근거를 적는다.

기대 판정: `pass`

근거: 같은 순서가 독자의 비교를 돕고 각 항목이 서로 다른 정보를 제공한다.

### 사례 26: 기존 문체를 근거로 삼은 새 문장

입력: `이전 설계 문서가 같은 표현을 썼으므로 새 문서에도 포화와 경계를 그대로 쓴다.`

기대 판정: `needs revision`

근거: 기존 문서가 사실과 결정을 뒷받침할 수는 있어도 표현 자체가 승인됐다는 근거는 아니다. 새 문장의 대상, 행동과 조건을 직접 써야 한다.

### 사례 27: 서로 다른 사항을 한 문단에 모은 글

입력: `확인이 필요한 사항은 다음과 같다. 빌드 서버 접근 권한은 현재 권한 목록을 받은 뒤 정하며, 목록을 받기 전에는 서버 설정을 바꾸지 않는다. 오류 로그 보관 기간은 승인된 보안 정책을 확인한 뒤 정하고 현재 문서에는 확정값을 쓰지 않는다. 릴리스 승인자는 배포 절차에서 확인하며, 승인 역할을 확인하기 전에는 배포 시작 조건을 추정하지 않는다. 배포 실패 시 되돌리기 방법은 배포 도구의 복구 절차를 확인한 뒤 기록하고, 복구 절차가 없으면 배포 작업을 시작하지 않는다.`

기대 판정: `needs revision`

근거: 각 사항의 근거와 후속 행동은 확인되지만 하나의 중심 내용으로 이어지지 않는다. 새 결정을 만들지 않고 사항별 플레인 텍스트 문단으로 나눌 수 있다.

### 사례 28: 의미 단위별 문단

입력:

빌드 서버 접근 권한은 현재 권한 목록을 받은 뒤 정한다. 목록을 받기 전에는 서버 설정을 바꾸지 않는다.

오류 로그 보관 기간은 승인된 보안 정책을 확인한 뒤 정한다. 현재 문서는 보관 기간을 확정값으로 표시하지 않는다.

릴리스 승인자는 배포 절차에서 확인한다. 승인 역할을 확인하기 전에는 배포 시작 조건을 추정하지 않는다.

배포 실패 시 되돌리기 방법은 배포 도구의 복구 절차를 확인한 뒤 기록한다. 복구 절차가 없으면 배포 작업을 시작하지 않는다.

기대 판정: `pass`

근거: 각 문단이 하나의 확인 사항을 먼저 밝히고 근거와 후속 행동을 이어서 설명한다. 문단은 빈 줄로 구분되며 목록으로 바꾸지 않아도 각 관계를 확인할 수 있다.

### 사례 29: 길지만 하나의 중심 내용을 설명하는 문단

입력: `변환기는 입력 행의 날짜를 검사한다. 먼저 날짜 값이 비어 있는지 확인한다. 값이 있으면 승인된 날짜 형식과 비교한다. 형식이 맞지 않으면 행 번호와 입력값을 오류 결과에 기록한다. 오류가 하나라도 있으면 출력 파일을 만들지 않는다. 모든 날짜가 유효하면 변환 결과를 저장한다.`

기대 판정: `pass`

스크립트 기대: 긴 문단 경고 없음

근거: 여섯 문장이 날짜 검사라는 하나의 중심 내용을 설명하고 검사 순서, 실패 조건과 결과가 이어진다. 초기 경고 기준에 닿지 않으며 의미 검토에서도 문단을 나눌 이유가 없다.

### 사례 30: 경고가 발생하지만 유지할 수 있는 문단

입력: `변환기는 입력 행의 날짜를 검사한다. 먼저 날짜 값이 비어 있는지 확인한다. 값이 있으면 승인된 날짜 형식과 비교한다. 형식이 맞지 않으면 행 번호와 입력값을 오류 결과에 기록한다. 오류가 하나라도 있으면 출력 파일을 만들지 않는다. 모든 날짜가 유효하면 변환 결과를 저장한다. 저장이 끝나면 처리한 행의 수를 기록한다.`

스크립트 기대: 긴 문단 경고 1개, 정상 종료

기대 판정: `pass`

근거: 일곱 문장에 도달해 의미 검토 후보가 되지만 모든 문장이 날짜 검사와 저장 순서를 설명한다. 길이 경고만으로 수정을 요구하지 않는다.

### 사례 31: 경고 뒤 분리가 필요한 문단

입력: `확인이 필요한 사항을 기록한다. 서버 접근 권한은 권한 목록을 받은 뒤 정한다. 목록을 받기 전에는 서버 설정을 바꾸지 않는다. 로그 보관 기간은 보안 지침을 확인한 뒤 정한다. 현재 문서에는 확정되지 않은 기간을 쓰지 않는다. 배포 승인자는 배포 절차에서 확인한다. 승인 역할을 확인하기 전에는 배포 시작 조건을 추정하지 않는다.`

스크립트 기대: 긴 문단 경고 1개, 정상 종료

기대 판정: `needs revision`

근거: 일곱 문장에 도달한 사실은 검토를 시작하게 할 뿐이다. 의미 검토에서는 접근 권한, 로그 보관 기간과 배포 승인자가 서로 다른 중심 내용이므로 문단을 나눌 수 있다.

### 사례 32: 기술 수식어만 있는 전달 경로

입력: `릴리스 전달 경로는 패키지 이름과 버전을 구분한다.`

기대 판정: `needs human input`

근거: `릴리스`와 `전달`은 경로의 분야만 좁힐 뿐 레지스트리 URL, 산출물 디렉터리, 배포 대상 또는 패키지 표기 형식 중 무엇을 뜻하는지 정하지 않는다.

### 사례 33: 근거로 제거 대상을 확인할 수 있는 코드 경로

입력: `운영 빌드에서 로그인 토큰 설정 코드 경로를 제거한다.`

제공 근거: 승인된 요구사항과 소스 코드가 운영 빌드의 `setLoginToken` import와 호출을 제거 대상으로 정한다.

기대 판정: `needs revision`

근거: `코드 경로`는 파일 위치, import 관계, 실행 흐름 또는 관련 코드 전체를 뜻할 수 있다. 제공 근거로 새 결정을 하지 않고 제거 대상을 `setLoginToken` import와 호출로 바꿔 쓸 수 있다.

### 사례 34: 실제 URL을 경로라고 쓴 문장

입력: `릴리스 전달 경로는 https://packages.example.invalid/v1/team/app이다.`

제공 근거: 패키지 게시 문서가 이 URL을 릴리스 업로드 대상으로 정한다.

기대 판정: `needs revision`

근거: URL과 게시 문서로 대상을 확인할 수 있으므로 새 결정 없이 `릴리스 업로드 URL은 https://packages.example.invalid/v1/team/app이다.`로 고칠 수 있다. URL을 직접 쓸 수 있는 문장에서 `경로`를 유지하지 않는다.

## 실행과 판정 방법

U+00B7 검사는 일반 산문과 정확한 문자 보존 구간을 구분한 뒤 문자 존재를 결정적으로 확인한다. 의미 사례는 지적 위치, 근거와 기대 상태를 함께 비교한다. 실패 표현을 없앤 비율만 세지 않고 정상 전문용례를 그대로 둔 비율도 확인한다.

### 일반 채팅

진행 알림, 짧은 확인, 설명과 긴 조사 답변을 각각 실행한다. 모든 경우 `korean.md` 읽기, `use-words-review` 실행과 검토용 서브에이전트 호출이 없어야 한다. 중간 메시지와 최종 답변은 사례 1과 사례 4부터 17의 표현 기준을 지켜야 한다. 실행 기록으로 AGENTS 규칙을 적용한 내부 과정을 추정하지 않고, 사용자에게 보인 문장만 판정한다.

### 저장 결과물

한국어 문서를 새로 만들거나 고친 뒤 저장 또는 공유하는 작업을 실행한다. 같은 공유 단위에서는 `korean.md`를 읽고 `use-words-review`를 한 번 실행해야 한다. 일반 산문의 U+00B7 검색과 의미 검토가 모두 포함됐는지 실행 기록과 검토 결과로 확인한다.

후속 재발을 재현할 때에는 뜻이 모호한 추상 명사와 반복 결론이 섞인 기존 설계 자료를 제공하고, 그 자료의 사실과 결정만 사용해 새 문서를 작성하게 한다. 새 결과물에 후보 단어가 없기만 하면 통과시키지 않는다. 요구사항 누락 여부, 주체와 행동의 명확성, 정확한 전문용례 보존과 필요한 비교 구조 유지도 함께 판정한다.

스킬 설치 조건은 네 가지로 나누어 실행한다. 사용자 위치와 저장소의 `.agents/skills`에서 발견되는 경우에는 검토가 실행돼야 한다. Codex가 관리하는 워크트리에 무시 파일을 포함하도록 설정한 경우에는 복사 결과를 확인한다. 수동 Git 워크트리에서 로컬 스킬이 전달되지 않은 경우에는 한국어 문서 완료를 주장하지 않고 설치 누락을 보고해야 한다.

### 명시적인 채팅 문구 검토 요청

파일을 바꾸지 않은 상태에서 사용자가 특정 한국어 문구의 검토를 요청한다. 이 경우에는 일반 채팅의 예외로 `use-words-review`를 실행해야 한다. 검토 결과에는 적용한 판정, 지적 위치와 이유가 있어야 하며, 독립 검토 수단이 없으면 그 제한을 밝혀야 한다.

### 채팅에서 작성한 저장 예정 문구

채팅에서 초안을 작성하는 동안에는 스킬을 실행하지 않는다. 사용자가 그 문구를 문서에 저장하거나 외부에 전달하도록 요청하면 저장 또는 전달 직전에 한 번 실행한다. 이 사례로 채팅 채널 자체가 아니라 결과물의 쓰임에 따라 검토 범위가 바뀌는지 확인한다.

각 실행에서 호스트가 제공하는 스킬 호출 수, 서브에이전트 호출 수와 경과 시간을 기록한다. 일반 채팅에서 검토 호출이 0회인지와 저장 결과물 또는 명시적인 검토 요청에서 검토가 1회인지가 호출 범위의 통과 조건이다. 경과 시간은 환경에 따라 달라지므로 처음 실행에서는 값을 기록하고, 반복 실행 자료가 생긴 뒤 허용 기준을 정한다.

설치 조건과 작업 유형의 조합마다 변경 전후를 각각 세 번 실행하고 결과를 문장 단위의 `pass`, `needs revision`, `needs human input`, `not applicable`로 비교한다. 후보 단어 출현 수는 검토 대상을 찾는 보조 지표로만 사용한다. 사람 검토자는 모델 이름과 설정을 가린 상태에서 두 결과를 쌍대 비교하고, 문체보다 요구사항 충족과 사실 정확성을 먼저 판정한다. 필수 항목의 자동 판정과 사람 판정이 어긋나거나, 같은 입력에서 기대 판정과 다른 상태가 나오거나, 세 실행에 둘 이상의 상태가 나오면 사례를 보강하고 세 번 다시 실행한다. 두 번째 보정 뒤에도 어긋나면 `needs human input`으로 보고한다.

OpenAI는 평가 자료에 일반 사례, 예외 사례와 적대적 사례를 함께 넣고 실제 사용자가 입력하는 여러 형식과 긴 대화 문맥을 고려하라고 안내한다. 또한 사람 판정으로 평가 기준을 보정하도록 권한다. 2026년 8월 1일에 현재 지침을 확인했다. [OpenAI의 평가 설계 지침](https://developers.openai.com/api/docs/guides/evaluation-best-practices)

## 후속 구현의 반복 판정 결과

2026년 8월 2일에 사례 18부터 22, 사례 24부터 26, 경계만 언급한 문장, 최소 실행 예제와 영어 보통명사 사례를 한 입력으로 묶어 변경 전후에 각각 세 번 검토했다. 검토 입력에는 기존 표현이 승인된 문체가 아니라는 조건과 영어 역할명의 한국어 정의를 함께 제공했다. 각 실행은 해당 체크아웃의 `SKILL.md`, `korean.md`와 `examples.md`를 읽었으며 파일을 바꾸지 않았다.

갱신본은 세 실행에서 같은 판정을 냈다. 판정 기준이나 중단 조건이 없는 `포화`, 뜻과 담당자가 드러나지 않는 `경계`와 `소유`, 시험할 주장과 기각 조건이 없는 `반증`은 모두 `needs human input`이었다. 조사 중단 조건, 보안 검사 지점, 법률상 소유권, 최소 실행 예제와 필요한 비교 구조는 모두 `pass`였다. 기존 문체를 그대로 쓰겠다는 문장과 이미 정의한 한국어 역할명 대신 영어 보통명사를 섞은 문장은 모두 `needs revision`이었다. 정상 전문용례와 필요한 반복 구조를 잘못 고친 실행은 없었다.

변경 전 기준선은 열한 항목 가운데 열 항목에서 세 실행의 상태가 같았다. 기존 문체를 그대로 쓰겠다는 문장은 두 실행에서 `needs human input`, 한 실행에서 `needs revision`으로 갈렸다. 갱신본은 이 문장을 세 번 모두 `needs revision`으로 판정했다. `korean.md`에 기존 문서 표현의 재사용 기준과 직접 대조 사례를 둔 변경이 판정 차이를 줄였다고 볼 수 있다. 다만 실행 수가 적고 실행 환경이 모델과 설정을 모두 제공하지 않았으므로 모델 일반 성능의 변화로 해석하지 않는다.

세 갱신본 실행은 모두 `use-words-review` 적용 1회와 `korean.md` 전체 읽기를 보고했다. 한 실행은 별도 검수자 호출 1회를 완료했고, 두 실행은 동시 실행 한도 때문에 스킬이 정한 주 에이전트 대체 절차를 사용했다. 세 기준선 실행도 같은 한도 때문에 대체 절차를 사용했다. 따라서 이번 결과는 의미 판정의 반복성을 확인하지만 독립 검수 가용성은 입증하지 않는다.

갱신본 한 실행은 모델과 추론 설정을 보고했지만 나머지 실행에서는 같은 정보를 확인할 수 없었다. 호스트는 여섯 실행의 호출별 토큰 수와 경과 시간을 제공하지 않았다. 이 값은 추정하지 않았으며 성능과 비용 비교도 하지 않았다. 모델 이름과 설정을 가린 사람의 쌍대 비교도 이번 실행에서는 수행하지 않았다. 변경 전후 체크아웃을 아는 상태에서 문장별 판정만 대조했으므로, 위 결과는 문장 판정의 반복 여부만 뒷받침한다.

두 배포용 AGENTS의 일반 채팅 제외, 저장 또는 공유 직전 검토, 명시적인 문구 검토 예외와 참조 누락 시 중단 조건은 문장별로 대조했다. 현재 구현 범위에는 루트 README 변경과 대상 저장소 설치가 없어서, 일반 채팅 0회와 저장 결과물 및 명시적 검토 1회라는 호스트 호출 수는 실제 설치 환경에서 관찰하지 못했다. 사용자 위치와 저장소 위치, Codex 관리 워크트리와 수동 Git 워크트리의 설치 검증은 README 설치 작업을 승인하고 대상 저장소에 다시 적용할 때 수행한다. 그 전에는 정적 지침 대조를 실제 호출 보장의 근거로 사용하지 않는다.

## 한계

이 묶음은 초기 대표 사례이지 한국어 표현의 전체 목록이 아니다. 후속 적용에서 발견한 압축 표현과 정상 전문용례를 계속 추가해야 한다. 한 저장소의 결과만으로 모델별 한국어 품질 차이를 판정하지 않는다. 예시 저장소 집계를 다시 검증할 역할과 원본 자료의 보관 방식은 이번 평가 묶음에서 정하지 않는다.
