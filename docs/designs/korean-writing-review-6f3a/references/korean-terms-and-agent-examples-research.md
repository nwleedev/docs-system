# 한국어 용어 제한과 AGENTS 예시 배치 조사

## 조사 목적과 독자

이 문서는 [한국어 문서 검토 재발 방지 요구사항의 목표](../requirements.md#목표)에 따라 `references/korean.md`에 어떤 문제 사례를 추가하고, 문맥에 따라 뜻이 달라지는 표현의 허용 조건을 어떻게 좁힐지 조사한다. 이후 `korean.md`, 두 배포용 AGENTS 문서와 `use-words-review`를 바꿀 담당자가 규칙을 기록할 파일과 검증 사례를 정할 때 사용한다.

일반 산문의 U+00B7 금지와 용어 수를 고정하지 않는 문맥별 판정은 [일반 산문 문장부호와 문맥별 용어 판정](../decisions/general-prose-and-contextual-wording.md)에서 승인됐다. 이 문서는 그 결정을 `korean.md`와 평가 사례에 적용하는 방법을 조사한다. 대표 사례의 기대 상태는 구현 전 검증을 위한 초기 제안이며, 후속 적용 결과에 따라 보정해야 한다.

## 단어 목록보다 문맥별 허용 조건이 적합하다

표준국어대사전은 `계약`을 관계자 사이에서 지킬 의무를 정한 약속으로 풀이하고, `공개`를 사실이나 내용을 여러 사람에게 터놓는 행위로 풀이한다. `경로`에는 지나가는 길이라는 뜻이 있고, `좁히다`와 `박다`에도 물리적인 기본 뜻이 있다. 이 단어들은 실제 대상을 정확히 가리킬 수 있으므로 출현만으로 오류를 확정할 수 없다. 2026년 8월 1일에 표제어와 뜻풀이를 확인했다.

- [표준국어대사전의 `계약` 검색 결과](https://stdict.korean.go.kr/search/searchResult.do?pageSize=10&searchKeyword=%EA%B3%84%EC%95%BD)는 당사자와 의무가 있는 약속이라는 기본 뜻을 확인한다.
- [표준국어대사전의 `경로` 검색 결과](https://stdict.korean.go.kr/search/searchResult.do?pageSize=10&searchKeyword=%EA%B2%BD%EB%A1%9C)는 길이나 지나가는 구간이라는 기본 뜻을 확인한다.
- [표준국어대사전의 `공개` 검색 결과](https://stdict.korean.go.kr/search/searchResult.do?pageSize=10&searchKeyword=%EA%B3%B5%EA%B0%9C)는 여러 사람에게 터놓는 행위라는 기본 뜻을 확인한다.
- [표준국어대사전의 `좁히다` 검색 결과](https://stdict.korean.go.kr/search/searchResult.do?pageSize=10&searchKeyword=%EC%A2%81%ED%9E%88%EB%8B%A4)는 면적을 작게 하는 기본 뜻을 확인한다.
- [표준국어대사전의 `박다` 검색 결과](https://stdict.korean.go.kr/search/searchResult.do?pageSize=10&searchKeyword=%EB%B0%95%EB%8B%A4)는 물체를 두들겨 꽂는 기본 뜻을 확인한다.

Google 개발자 문서 지침은 모호하거나 여러 뜻으로 쓰이는 용어를 문맥 없이 거부하지 않는다. 독자와 제품 분야에서 통용되면 유지할 수 있고, 그 밖의 경우에는 더 구체적인 표현으로 바꾸거나 처음 나올 때 뜻을 설명하도록 한다. 2026년 8월 1일에 현재 지침을 확인했다.

- [Google 개발자 문서의 용어 목록](https://developers.google.com/style/word-list)은 `사용 주의`와 `사용하지 않음`을 구분하고, 독자와 제품 분야에 따라 용어를 판단하도록 설명한다.
- [Google 개발자 문서의 전문용어 지침](https://developers.google.com/style/jargon)은 통용되는 전문용어는 유지할 수 있지만, 모호한 용어는 더 구체적으로 쓰거나 처음 나올 때 설명하도록 안내한다.

W3C의 명료한 언어 지침도 낯선 용어와 전문용어를 없애거나 설명하되, 새 뜻을 임의로 부여하지 말라고 안내한다. 이 근거는 정확한 전문용례를 보존하면서 추상적인 대체어만 제한하는 방향을 지지한다. 2026년 8월 1일에 현재 지침을 확인했다. [W3C의 명료한 단어 사용 지침](https://www.w3.org/WAI/WCAG2/supplemental/patterns/o3p01-clear-words/)

## `korean.md`에는 최소 대조 사례를 추가해야 한다

문제 사례는 실제 실패의 문장 구조를 재현하되 특정 저장소의 원문, 직무, 조직이나 수치를 옮기지 않아야 한다. 한 사례에는 주된 결함 하나만 두고, 같은 단어의 정상 용례를 바로 뒤에 배치해야 한다. 그래야 검토자가 단어를 삭제하는 대신 대상, 행동, 조건과 결과를 확인한다.

각 사례에는 다음 정보가 필요하다.

- **판정:** `pass`, `needs revision` 또는 `needs human input` 가운데 하나
- **위치:** 판정 대상이 되는 짧은 어구
- **근거:** 유지할 전문용례인지, 저장소 근거로 고칠 수 있는지, 새 결정이 필요한지
- **독자 영향:** 그대로 두면 독자가 무엇을 결정하거나 실행할 수 없는지
- **대조 사례:** 같은 표현을 정확히 쓴 문장 또는 필요한 정보를 드러내 다시 쓴 문장

OpenAI의 프롬프트 지침은 원하는 출력과 다양한 입력의 예를 함께 주면 모델이 패턴을 적용할 수 있다고 설명한다. 2026년 8월 1일에 현재 지침을 확인했다. [OpenAI의 예시 기반 프롬프트 지침](https://developers.openai.com/api/docs/guides/prompt-engineering#few-shot-learning)

이 조사에서는 해당 원칙을 현재 용어 문제에 적용해 실패 사례와 통과 사례를 함께 두는 방안을 제안한다. 실패 사례만 두면 `계약`이나 `경로`의 출현 자체를 실패 신호로 오해해 정상 전문용례까지 고칠 위험이 있다. 이 과잉 수정 위험은 공식 문서의 직접 주장이 아니라 현재 사례 구조에서 도출한 분석이다.

## 모든 후보 용어에 같은 판정 질문을 적용해야 한다

다음 내용은 `korean.md`에 추가할 판정 기준 제안이다. 다섯 단어는 현재 실패에서 찾은 대표 사례일 뿐 닫힌 목록이 아니다. `보장하다`, `지원하다`, `다루다`, `노출하다`, `포착하다`, `정렬하다`, `표면화하다`처럼 영어 표현을 한 단어로 옮겼거나 실제 동작을 감출 수 있는 다른 표현도 다음 질문으로 판정해야 한다.

- 해당 분야의 승인된 자료에서 같은 뜻으로 쓰는 확립된 용어인가?
- 문장이 가리키는 대상과 행동 주체가 드러나는가?
- 독자가 행동, 조건과 결과를 하나로 이해할 수 있는가?
- 앞의 조건을 충족하지 못한다면 저장소 근거로 실제 동작을 확인해 더 구체적으로 쓸 수 있는가?

처음 세 조건을 모두 충족하면 용어를 유지하고 `pass`로 판정한다. 하나라도 충족하지 못했지만 마지막 질문의 근거가 있으면 실제 행동을 적어 `needs revision`으로 판정한다. 뜻을 하나로 정할 근거가 없으면 단어를 임의로 바꾸지 않고 `needs human input`으로 판정한다.

현재 문서 구조를 유지하려면 `경로`와 `공개`는 같은 이름의 기존 절을 보강한다. `계약`은 여러 전문용어를 함께 설명하는 절에서 분리해 허용 조건과 대조 사례를 찾기 쉽게 만든다. `좁히다`와 `박다`는 각각 새 절을 만들고, 직역과 번역체 절에서는 해당 절로 연결한다. 가운뎃점은 단어 판정과 성격이 다르므로 별도의 문장부호 절에 둔다. 한 사례를 여러 절에 복사하지 않는다.

### `계약`은 의무나 합의한 규칙이 식별될 때만 유지한다

법률 계약, 근로계약, 거래 계약처럼 당사자와 의무가 있는 경우에는 유지한다. 소프트웨어 문서에서는 저장소가 `계약 기반 설계`, 인터페이스 계약 또는 이벤트 계약을 승인된 용어로 사용하고, 문장이 입력, 출력, 위반 조건이나 호환 조건을 구체적으로 밝힐 때만 유지한다.

`API 계약`, `측정 계약`, `모듈 간 계약`처럼 무엇을 지켜야 하는지 적지 않은 표현은 검토 후보가 된다. 저장소 근거에서 실제 규칙을 찾을 수 있으면 `입출력 규칙`, `호출 조건`, `필드와 자료형`, `측정 전에 합의한 기준`처럼 다시 써서 `needs revision`으로 판정한다. 근거가 없으면 `needs human input`이다.

문제 사례:

> 두 모듈의 계약을 좁혀 결과를 보장한다.

이 문장은 합의한 값, 줄일 대상과 확인할 결과를 밝히지 않으므로 `needs human input`이다.

조건을 밝힌 대조 사례:

> 주문 모듈은 주문 번호와 결제 상태를 문자열로 전달한다. 필드가 없으면 수신 모듈이 요청을 거부한다.

### `경로`는 위치나 실제 이동 구간을 가리킬 때만 유지한다

파일과 디렉터리 위치, URL 경로, 네트워크 전달 구간, 그래프 탐색 경로처럼 출발점과 도착점 또는 위치가 식별되면 유지한다. 프로젝트의 진행 방법, 경력 선택, 학습 절차, 승인 방법을 뜻하는 `경로`는 실제 행동을 적어야 한다.

문제 사례:

> 새 기술을 익힐 경로를 정리한다.

교육 과정, 실습 순서, 참고 자료 또는 승인 절차 가운데 무엇을 정하는지 알 수 없으므로 `needs human input`이다.

정확한 전문용례:

> 설정 파일 경로는 `config/app.yml`이다.

### `공개`는 독자와 허용되는 행동이 드러날 때만 유지한다

법률상 정보공개, 공개 키, 제품이 정의한 공개 저장소처럼 상태나 행위가 확립된 경우에는 유지한다. 다만 문서의 독자가 그 용어만으로 열람 대상과 권한을 알 수 없으면 로그인 필요 여부, 읽기와 수정 권한, 게시 위치나 배포 상태를 함께 적어야 한다.

`공개 자료`, `공개 가능한 결과`, `외부 공개`처럼 대상과 이용 조건이 없는 표현은 검토 후보가 된다. 확인 가능한 조건이 있으면 `로그인 없이 읽을 수 있다`, `웹사이트에 게시한다`, `패키지 저장소에서 내려받을 수 있다`처럼 다시 쓴다.

문제 사례:

> 조사 결과를 공개 가능한 형태로 만든다.

누가 어디에서 무엇을 볼 수 있어야 하는지 정해지지 않았으므로 `needs human input`이다.

조건을 밝힌 대조 사례:

> 조사 결과에서 개인 식별 정보를 제거한 뒤 인터넷 사용자가 로그인 없이 읽을 수 있는 문서 사이트에 게시한다.

### `좁히다`는 줄이는 대상과 결과가 확인될 때만 유지한다

폭이나 면적을 줄이는 기본 뜻, 후보 수나 기간처럼 전후 범위를 비교할 수 있는 경우에는 유지한다. 저장소가 `타입 좁히기`처럼 분야의 용어를 채택했다면 그 정의와 판정 대상이 드러나는 문장에서도 유지할 수 있다.

`범위를 좁힌다`, `계약을 좁힌다`, `문제를 좁힌다`처럼 무엇을 어떤 기준으로 얼마나 줄이는지 알 수 없는 표현은 더 구체적으로 써야 한다.

문제 사례:

> 기능 범위를 좁혀 품질을 높인다.

제외할 기능과 품질을 판단할 기준이 없으므로 `needs human input`이다.

조건을 밝힌 대조 사례:

> 첫 배포에서는 파일 업로드와 검색만 제공하고, 공유와 알림은 다음 배포에서 검토한다.

### `박다`는 공개 기술 문서에서 원칙적으로 다른 동작으로 풀어 쓴다

물체를 두드려 꽂는 실제 동작, 승인된 인용문, 제품이나 명령의 정확한 이름에는 원문을 유지할 수 있다. 기술 문서에서 `값을 박다`, `규칙을 박다`, `문구를 박다`는 구어적이며 실제 동작이 서로 다르므로 기본적으로 검토 후보로 삼는다.

저장소 근거에 따라 `리터럴로 하드코딩한다`, `상수로 고정한다`, `설정 파일에 명시한다`, `화면에 표시한다`처럼 구체적인 동사로 바꾼다. 무엇을 뜻하는지 확인할 수 없으면 `needs human input`이다.

문제 사례:

> 기본 주소를 코드에 박는다.

주소를 리터럴로 저장할지, 상수로 선언할지, 설정값으로 제공할지 알 수 없으므로 `needs human input`이다.

행동을 밝힌 대조 사례:

> 기본 주소는 배포 환경의 `SERVICE_URL` 환경 변수에서 읽는다.

### 연구 자료의 `포화`는 판단 방법과 중단 기준이 있을 때 유지한다

흡수, 용액, 색상, 시장과 자원 사용량처럼 해당 분야에서 포화 상태가 정의되고 측정 기준을 밝힌 경우에는 유지한다. 조사 문서에서 `자료가 포화됐다`, `인터뷰가 포화됐다`고 쓸 때에는 새 자료가 더 이상 새로운 주제나 범주를 만들지 않는다는 연구 방법과 중단 기준이 제시돼야 한다.

`포화가 아니었다`라는 결론만 반복하면 무엇을 더 조사해야 하는지 알 수 없다. 확인한 새 정보, 남은 질문과 다음 수집 조건을 직접 쓴다.

문제 사례:

> 이번 조사도 포화가 아니었다.

근거와 중단 기준이 없어 `needs human input`이다.

조건을 밝힌 대조 사례:

> 새 문제가 나오지 않는 인터뷰가 다섯 건 연속되면 자료가 포화됐다고 판정하고 모집을 끝낸다.

### `경계`는 구분 기준이나 실제 접점이 식별될 때만 유지한다

수학의 경계, 보안 경계, 시스템 사이의 명시된 인터페이스처럼 분야에서 뜻이 정해지고 안과 밖 또는 책임이 바뀌는 지점을 설명할 때에는 유지한다. 단순히 검토 범위, 제외 대상, 역할 분담이나 연결 지점을 묶어 `경계`라고 쓰면 실제 조건을 직접 적는다.

문제 사례:

> 이 문서는 조사와 실행의 경계를 다룬다.

무엇을 조사에 포함하고 누가 언제 실행하는지 알 수 없어 `needs human input`이다.

정확한 전문용례:

> 인증 서비스 밖에서 받은 요청은 보안 경계를 통과하기 전에 서명을 검증한다.

### `소유`는 권리나 명시된 책임 관계가 있을 때만 유지한다

재산권, 지식재산권, 제품이 정의한 코드 소유권이나 저장소의 승인된 역할 이름처럼 권리와 책임이 정해진 경우에는 유지한다. 문서, 기관 또는 절차가 항목을 `소유한다`는 문장은 실제 주체와 행동을 감출 수 있다. 문서라면 `기록한다`, 조직이라면 `운영한다` 또는 `답변한다`, 사용자가 자료를 다룬다면 `보관한다`나 `제출한다`처럼 확인한 행동을 쓴다.

문제 사례:

> 기준 문서가 모든 결정을 소유한다.

문서가 결정을 내리는지, 승인된 결정을 기록하는지 알 수 없어 `needs human input`이다.

행동을 밝힌 대조 사례:

> 승인 담당자가 결정한 내용은 기준 문서에 기록한다.

정확한 권리 용례:

> 임대 계약이 끝나면 장비의 소유권은 임차인에게 이전된다.

### `반증`은 가설을 틀렸다고 판정할 증거가 있을 때만 유지한다

과학적 가설이나 명시된 주장과 그 주장을 기각할 관찰 조건이 있을 때에는 유지한다. 실행 가능성 확인, 자료 대조, 실패 조건 점검과 반대 사례 탐색을 모두 `반증`으로 부르지 않는다.

문제 사례:

> 구현 전에 접근법을 반증한다.

어떤 주장과 실패 기준을 시험하는지 알 수 없어 `needs human input`이다.

행동을 밝힌 대조 사례:

> 최소 예제를 실행해 필수 API가 현재 버전에서 동작하는지 확인한다. 호출이 실패하면 이 접근을 채택하지 않는다.

정확한 연구 용례:

> 대조군과 실험군의 차이가 사전에 정한 오차 범위 안이면 새 알고리즘이 처리 시간을 줄인다는 가설을 반증한 것으로 판정한다.

### 영어 보통명사와 반복 결론도 별도로 확인한다

제품명, API 식별자, 명령, 코드와 저장소가 승인한 전문용어는 원문을 유지한다. 일반적인 역할, 단계, 상태와 판단을 영어로 병기하거나 문장 속에 섞으면 한국어만으로 뜻이 분명한지 먼저 확인한다. 번역어를 괄호로 반복해도 의미가 더 구체적이지 않다면 한 언어로 다시 쓴다.

비교 대상마다 같은 속성을 같은 순서로 설명하는 구조는 독자가 대조하기 쉬우므로 `pass`가 될 수 있다. 반면 각 절의 끝에 근거 없이 같은 결론을 붙이거나, 실제로 달라진 내용을 말하지 않는 요약을 반복하면 `needs revision`이다. 판정 기준은 반복 횟수가 아니라 각 문장이 새 사실, 결정, 행동 또는 조건을 더하는지 여부다.

## 일반 산문의 U+00B7과 정형화된 표현도 대조 사례가 필요하다

국립국어원의 문장 부호 규정은 일부 병렬 어구에 가운뎃점을 쓸 수 있고, 같은 용례에서 쉼표를 쓰거나 부호를 생략할 수도 있다고 설명한다. Apple은 macOS에서 특수 문자를 넣을 때 문자 보기를 열어 검색한 뒤 선택하도록 안내한다. Microsoft도 Windows와 Office에서 문자표 또는 유니코드 코드 입력을 안내한다. 이 자료는 모든 키보드에서 U+00B7 입력이 어렵다고 증명하지는 않지만, 일반 문자와 달리 별도 입력 절차가 필요할 수 있음을 보여 준다. 현재 작성 환경에서 직접 입력하기 어렵다는 요구사항 작성자의 판단을 근거로 [일반 산문 문장부호와 문맥별 용어 판정](../decisions/general-prose-and-contextual-wording.md)은 일반 산문에서 이 문자를 쓰지 않기로 정했다. 2026년 8월 1일에 자료를 확인했다.

- [국립국어원 한글 맞춤법의 문장 부호 규정](https://korean.go.kr/kornorms/regltn/regltnView.do?regltn_code=0001)은 해당 병렬 용례에서 쉼표를 쓰거나 부호를 생략할 수 있다고 설명한다.
- [Apple의 macOS 특수 문자 입력 안내](https://support.apple.com/guide/pages/accents-and-special-characters-tanec2c2fdfd/11.1/mac/1.0)는 문자 보기를 열고 이름이나 코드로 문자를 찾아 넣는 절차를 설명한다.
- [Microsoft의 유니코드 문자 입력 안내](https://support.microsoft.com/en-US/Word/insert-ascii-or-unicode-latin-based-symbols-and-characters)는 문자표 또는 문자 코드와 단축키를 사용하는 절차를 설명한다.
- [Unicode 16.0의 문장부호 설명](https://www.unicode.org/versions/Unicode16.0.0/core-spec/chapter-6/)은 U+00B7을 여러 의미를 가진 별도 문자로 설명한다.

`korean.md`에는 다음 사례 묶음을 추가하는 방안이 적합하다.

- 일반 산문에서 병렬 항목을 U+00B7로 이은 실패 사례와 쉼표, 조사 또는 문장 분리로 고친 사례
- 인용문, 승인된 화면 문구, 제품명, 수식, 표준 표기, 코드, 정규식, 코드 포인트와 평가 입력에서 정확한 문자를 보존한 통과 사례
- `본질적으로`, `다양한 측면에서`, `강력한`, `원활한`처럼 사실을 더하지 않는 표현만 있는 실패 사례와 실제 조건 및 동작을 적은 대조 사례
- 소제목마다 같은 문단 길이와 같은 수의 목록을 반복한 구조적 실패 사례와 내용에 따라 길이와 형식을 달리한 대조 사례
- `포화`, `경계`, `소유`, `반증`이 대상과 조건을 감춘 실패 사례와 정확한 연구, 보안, 권리 관계의 통과 사례
- 기존 문서의 같은 표현을 이어받은 실패 사례와 사실 및 결정만 사용해 새 문장으로 쓴 통과 사례
- 반복되는 비교 구조는 유지하되 정보가 없는 결론 문구만 제거하는 과잉 수정 방지 사례

## AGENTS에는 전체 사례가 아니라 짧은 검토 신호를 둬야 한다

OpenAI는 개발자 지침에 규칙과 예시를 함께 둘 수 있고, 여러 입력 유형을 보여 주는 소수 예시가 출력 패턴을 유도한다고 설명한다. 반면 Codex Skills는 스킬 설명, `SKILL.md`, 필요한 참조 자료를 단계적으로 읽어 문맥 사용량을 줄인다. 두 원칙을 함께 적용하면 AGENTS에는 놓치기 쉬운 검토 신호만 두고 전체 판정 사례는 `korean.md` 한 곳에서 관리하는 편이 적합하다.

- [OpenAI의 프롬프트 구성 지침](https://developers.openai.com/api/docs/guides/prompt-engineering)은 개발자 메시지에 지침, 예시와 필요한 문맥을 구분해 둘 수 있다고 설명한다.
- [OpenAI의 스킬 작성 지침](https://developers.openai.com/codex/skills)은 스킬 본문과 참조 자료를 필요할 때 읽는 단계적 로딩을 설명한다.
- [Anthropic의 Agent Skills 구조 설명](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)은 상세 자료를 보조 파일에 두고 스킬 본문에서 적용 시점을 명시하는 구성을 설명한다.

두 배포용 AGENTS 문서에는 같은 의미의 짧은 예시를 넣는 방안을 제안한다.

- `설계·구현·검증`처럼 가운뎃점으로 산문을 압축하지 말고 문장 관계를 밝힌다.
- `계약`, `경로`, `공개`, `포화`, `경계`, `소유` 같은 후보를 발견하면 단어만 바꾸지 말고 대상, 행동, 조건과 결과가 드러나는지 `korean.md`로 판정한다. 이 목록은 예시이며 `좁히다`, `박다`, `반증`과 새 후보에도 같은 질문을 적용한다.
- `본질적으로`, `다양한 측면에서`, `강력한`, `원활한`처럼 사실을 더하지 않는 표현을 사용하지 않는다.
- 기존 문서는 사실과 결정의 근거이지 승인된 문체 예시가 아니다. 기존 추상 명사와 반복 결론을 새 문서에 그대로 옮기지 않는다.

AGENTS에는 용어별 허용 조건, 상태별 판정과 전체 대조문을 복사하지 않는다. 같은 규칙을 두 언어의 AGENTS와 `korean.md`에 중복하면 한 파일만 갱신됐을 때 판정이 달라진다. 두 AGENTS 문서는 커밋하거나 공유할 한국어 글이나 이름이 있을 때 설치된 `use-words-review`의 `references/korean.md`를 읽도록 명시하고, 상세 사례는 `korean.md`에 유지해야 한다. 채팅 답변의 로딩 조건은 [채팅 답변의 한국어 품질 적용 조사](./conversational-korean-output-research.md)를 따른다.

영어 배포본도 한국어 결과물에 적용할 신호는 한국어 원형을 그대로 보여 주고 설명만 영어로 쓴다. 문제 표현을 영어로 번역하면 검토할 실제 문자열이 사라지고, 두 배포본이 서로 다른 한국어 패턴을 가리킬 수 있다.

## 구현에 반영할 사항

- 일반 산문의 U+00B7 금지와 정확한 문자 보존 예외를 `korean.md`의 문장부호 절에서 구분한다.
- 다섯 단어의 허용 조건을 대표 사례로 싣되, 같은 판정 질문이 새 후보에도 적용된다고 명시한다.
- 후속 사례에서 확인한 `포화`, `경계`, `소유`, `반증`, 영어 보통명사 혼용과 반복 결론을 대조 사례로 추가한다.
- 기존 문서의 사실과 문체를 구분하는 언어 공통 사례는 `examples.md`에 두고, 한국어 고쳐 쓰기는 `korean.md`에 둔다.
- 대표 사례의 초기 기대 상태는 [한국어 답변 검토 평가 사례](./korean-review-evaluation-cases.md)에 한 번만 기록하고 후속 실행으로 보정한다.
- AGENTS에 넣을 검토 신호는 두 배포본에서 같은 동작을 지시하는지 함께 확인한다.

## 한계와 다시 확인할 조건

- 사전 뜻풀이는 단어의 일반적인 뜻을 확인하지만 특정 소프트웨어 분야의 승인 용어를 대신하지 않는다. 대상 저장소의 공식 문서와 용어집이 다른 뜻을 명시하면 그 근거를 함께 확인해야 한다.
- 소수 예시는 모델이 따라야 할 패턴을 보여 주지만 모든 문맥의 판정을 증명하지 않는다. 정상 용례와 실패 용례를 함께 실행해 과잉 수정을 확인해야 한다.
- AGENTS에 예시를 추가해도 에이전트가 참조 파일을 실제로 읽었거나 검토를 수행했다는 증거가 되지 않는다. 설치 뒤 대표 작업의 실행 기록을 확인해야 한다.
