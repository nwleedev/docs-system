# 한국어 문서 검토 재발 방지 요구사항

## 목표

여러 애플리케이션 저장소에 복사해 사용하는 문서 체계에서 한국어 문서의 가운뎃점, 뜻을 바로 알기 어려운 번역체와 정형화된 AI 문체를 작성 단계와 공유 전 검토 단계에서 찾아낼 수 있도록 개선 방향을 조사한다.

현재 `use-words-review` 관련 파일과 배포용 AGENTS 문서를 기준으로, 한국어 판정 자료가 실제 작업에서 빠지지 않도록 연결하는 방법을 조사한다. AGENTS 문서에서 `references/korean.md`를 직접 가리키는 방법도 검토한다.

같은 문제가 발생한 사례와 다른 문서 작성 시스템의 대응 방법을 조사하고, 이후 변경 작업에서 사용할 수 있는 근거를 설계 패키지에 남긴다.

실제 실패를 일반화한 문자열 검색 후보의 문제 사례와 정상 대조 사례는 검사 스크립트의 내장 규칙에 두고, `references/korean.md`에는 문자열 검색으로 찾을 수 없는 의미 검토 사례를 남기는 방법을 조사한다. `계약`, `경로`, `공개`, `좁히다`, `박다`처럼 문맥에 따라 뜻이 달라지는 표현은 허용 조건을 구체화하고 제한을 강화할 수 있는지 검토한다.

배포용 한국어와 영어 AGENTS 문서가 `references/korean.md`와 `use-words-review`를 명시적으로 가리키게 하는 방법을 조사한다. AGENTS 문서에 가운뎃점, 번역체와 정형화된 AI 문체의 문제 사례를 직접 넣는 방안도 상세 기준의 중복 관리 위험과 함께 비교한다.

저장소 파일을 만들거나 바꾸는 작업뿐 아니라 사용자와 주고받는 채팅 답변에도 같은 한국어 기준을 적용하는 방법을 조사한다.

`use-words-review`는 AI가 만들거나 고친 한국어 문서와 저장, 커밋, 게시 또는 전달할 한국어 문구를 우선 검토한다. 일반 채팅, 진행 알림과 설명 답변에는 이 스킬을 실행하지 않고, 두 배포용 AGENTS 문서에 직접 적은 한국어 작성 규칙을 적용한다.

사용자가 채팅에서 특정 문구의 검토를 명시적으로 요청하면 일반 채팅의 예외로 `use-words-review`를 실행한다. 채팅에서 작성한 문구를 그대로 저장, 게시 또는 전달할 예정인 경우에도 저장할 결과물의 검토 조건을 적용한다.

일반 산문에서는 U+00B7을 사용하지 않는다. 이 문자를 직접 입력하기 어렵다는 현재 작성 환경을 고려해 쉼표, 조사, 문장 분리처럼 일반 키보드로 입력할 수 있는 표현을 쓴다. 인용문, 승인된 이름, 코드, 정규식, 문자 처리 검증, 코드 포인트 설명과 평가 입력처럼 정확한 문자를 보존해야 하는 경우는 일반 산문과 구분한다.

문맥별 허용 조건은 `계약`, `경로`, `공개`, `좁히다`, `박다`에만 적용하지 않는다. 번역어 또는 뜻을 압축한 표현을 발견하면 해당 분야에서 확립된 용어인지, 문장이 대상, 행동, 조건과 결과를 충분히 밝히는지 확인하고 같은 기준으로 판정한다.

작성하거나 검토할 문단이 길어질 때에는 글자 수나 문장 수만으로 문제를 확정하지 않는다. 서로 다른 중심 내용, 근거, 조건, 결정 상태 또는 후속 행동을 한 문단에 함께 담아 독자가 관계를 다시 구성해야 한다면 의미 단위마다 문단을 나눈다. 각 문단은 중심 내용을 먼저 밝히고, 분리된 문단 사이에 적용 순서나 의존 관계가 있으면 그 관계를 함께 설명한다.

Markdown 산문은 빈 줄로 구분한 플레인 텍스트 문단으로 나눈다. 단순 줄바꿈은 별도 문단으로 간주하지 않는다. 근거와 판단의 관계를 문장으로 설명해야 하는 내용은 읽기 쉬워 보이게 하려는 목적으로 목록으로 바꾸지 않는다. 서로 대등한 항목을 열거하거나 실행 순서를 나타낼 때에는 목록을 유지할 수 있다.

채팅 답변을 서브에이전트가 검토할 수 없는 환경에서도 번역체와 정형화된 AI 문체를 줄일 방법을 조사한다. 일반 채팅을 처음부터 작성할 때 적용할 AGENTS 기준, 저장 결과물과 명시적인 문구 검토 요청에서 상세 한국어 자료를 읽는 시점, 실행 여부를 평가할 방법과 보장할 수 없는 범위를 구분한다.

이후 변경에서 바로 사용할 대표 평가 사례를 한 묶음 제안한다. 예시는 일반 산문의 U+00B7, 정확한 문자 보존, 문맥에 따른 용어 판정, 번역체와 정형화된 채팅 답변을 함께 다룬다.

후속 사례와 변경 계획을 기준으로 기존 `src`, `skills`, `docs` 파일에 필요한 개선을 적용한다. 검사기 개발을 시작하기 전에 Node.js `.mjs` 명령줄 스크립트의 실패 사례, 권장 코드와 피해야 할 코드를 개발 지침에 기록하고, 정확히 찾을 수 있는 코드 형태는 ESLint 규칙으로 검사한다. 이 준비 작업은 `docs/dev/README.md`, `docs/dev/node/mjs-cli.md`, `eslint.config.mjs`, `package.json`과 `pnpm-lock.yaml`을 만들거나 갱신할 수 있다. 후속 구현에서 새로 만들 수 있는 실행 파일은 `skills/use-words-review/scripts/scan-korean-expressions.mjs` 하나다.

"한국어가 제대로 작성되었는지 검사"하기 위해서는 지금 현재는 references/korean.md 파일에 추가 지침 형태로 작성하고 있다. 만약 한국어 텍스트 검사를 스크립트 기반으로 하도록 할 때 korean.md 파일을 유지할지 아니면 스크립트에 모든 한국어 검사 기준을 포함시키도록 할지에 대해서 교차검증 및 비교한다.

한국어 검사 스크립트는 현재 references/korean.md 파일에 있는 "문제 표현"에 대해서 문제 표현이 작성된 내용을 전부 찾은 다음 AI에게 "경고"하는 방식으로 작동하는 건에 대해서 검토한다. 검토 결과를 바탕으로 스크립트를 어떻게 설계할지를 리서치한다.

**스킬의 폴더 구조, 스크립트가 생성하는 데이터에 대한 구조는 임의로 작성하지 않는다.**

## 적용 조건

- 이 저장소는 애플리케이션을 구현하지 않고, 여러 애플리케이션 저장소에서 AI가 작업하는 방법을 연구한다.
- 조사 대상은 `skills/use-words-review/SKILL.md`, `skills/use-words-review/references/korean.md`, `skills/use-words-review/references/examples.md`, `AGENTS.md`, `src/AGENTS.ko.md`와 `src/AGENTS.en.md`다.
- 대상 저장소에는 `docs/designs/README.md`, `docs/dev/README.md`, 필요한 스킬과 배포용 AGENTS 문서를 복사해 적용하는 현재 방식을 고려한다.
- 지정된 예시 저장소의 모든 워크트리 브랜치와 각 커밋의 변경을 조사하되, 저장소 이름, 로컬 위치, 조직명, 개인 자료와 원문 내용을 추적 문서에 옮기지 않는다.
- 기존 [번역투와 정형화된 AI 문체 조사](../public-output-audience-4d2c/references/natural-korean-and-ai-writing-research.md)가 소유하는 일반 판정 원칙은 새 문서에 복제하지 않는다.
- 초기 조사 작업은 요구사항, 조사 자료, 승인된 결정과 초기 평가 사례를 설계 패키지에 기록하는 데까지였다. 개발 준비 작업은 Node.js `.mjs` 개발 지침, ESLint 설정과 개발 의존성 manifest 및 lock 파일을 대상으로 한다. 후속 구현은 변경 계획이 지정한 기존 `src`, `skills`, `docs` 파일과 `skills/use-words-review/scripts/scan-korean-expressions.mjs`를 대상으로 한다. 루트 README와 루트 AGENTS 문서는 이번 구현 범위에 포함하지 않는다.
- 문제 사례에는 특정 저장소나 사용자 문장을 그대로 옮기지 않고, 실패 구조만 남긴 합성 사례와 정상 대조 사례를 사용한다.
- 예시 저장소 집계를 다시 검증할 역할과 원본 자료의 안전한 기록 보관 방식은 이번 작업에서 정하지 않는다. 갱신한 체계를 적용한 뒤 후속 작업을 계속할 때 다시 검토한다.

## 완료 증거

- 현재 파일 구성에서 한국어 작성 기준과 공유 전 검토가 빠질 수 있는 지점이 저장소 근거와 함께 설명되어 있다.
- 가운뎃점을 기계적으로 찾을 수 있는 항목과 문맥을 읽어야 판정할 수 있는 항목이 구분되어 있다.
- 뜻이 불분명한 번역체와 정형화된 AI 문체를 단어 목록만으로 판정하지 않는 개선 방향이 공식 자료와 실제 실패 사례에 연결되어 있다.
- AGENTS 문서에서 `references/korean.md`를 직접 가리키는 방안의 효과, 적용 위치와 중복 관리 위험이 설명되어 있다.
- 다른 문서 작성 시스템과 AI 에이전트 운영 사례가 현재 복사 설치 방식에 미치는 영향과 함께 정리되어 있다.
- 예시 저장소의 모든 워크트리 브랜치와 커밋을 확인한 결과가 원문이나 식별 정보를 드러내지 않는 형태로 기록되어 있다.
- 검사 스크립트에 넣을 문자열 검색 후보의 문제 사례와 정상 대조 사례 선택 기준 및 `korean.md`에 남길 의미 검토 기준이 제안되어 있다.
- `계약`, `경로`, `공개`, `좁히다`, `박다`를 유지할 조건과 고칠 조건이 문맥별로 설명되어 있다.
- 두 배포용 AGENTS 문서가 `korean.md`를 직접 가리키는 방안과 문제 사례를 직접 싣는 방안의 차이, 중복 관리 위험과 권장 범위가 설명되어 있다.
- 채팅 답변에 한국어 기준을 적용할 위치, 실행 시점, 비용과 실제 동작을 확인할 방법이 설명되어 있다.
- 일반 채팅에서는 별도 검토를 호출하지 않고 AGENTS의 작성 규칙을 적용하며, 저장할 결과물과 사용자가 명시적으로 검토를 요청한 문구에만 `use-words-review`를 실행하는 구분이 설명되어 있다.
- 중간 진행 알림과 최종 답변에 적용할 AGENTS 작성 규칙, 별도 검토를 수행하지 않는 데 따른 한계와 실제 동작을 확인할 방법이 설명되어 있다.
- 일반 산문의 U+00B7 금지와 정확한 문자 보존 예외가 구분되어 있다.
- 다섯 가지 예시 밖의 용어에도 같은 문맥별 허용 조건을 적용할 수 있는 판정 절차가 설명되어 있다.
- 서로 다른 미확정 사항과 후속 행동을 한 문단에 모은 실패 사례, 의미 단위별 플레인 텍스트 문단으로 나눈 정상 사례와 길지만 하나의 중심 내용 및 관계가 분명한 정상 사례가 대표 평가에 포함되어 있다.
- 대표 평가 사례가 실패 사례, 정상 사례, 초기 기대 판정과 함께 한 번 제시되어 있다.
- `skills/use-words-review`의 검사 스크립트에는 후속 용어 사례가, 기존 파일에는 기존 문서에서 이어받은 표현의 검사와 검토 중단 조건이 반영되어 있다.
- 두 배포용 AGENTS 문서가 같은 한국어 작성 조건, 스킬 호출 조건과 설치 누락 처리 방식을 설명한다.
- `docs/designs/README.md`가 기존 자료의 사실과 결정은 활용하되 승인되지 않은 문체를 그대로 옮기지 않는 기준을 설명한다.
- `skills/use-words-review/scripts/scan-korean-expressions.mjs`가 존재하며 Node.js 표준 기능만으로 실행된다.
- 검사 스크립트는 외부에서 규칙이나 표현을 선택하는 입력을 받지 않고 내장 `rules` 전체를 항상 순회한다. 출력의 `catalog`는 실제로 순회한 전체 `rules`에서 생성된다. 스크립트는 발견한 모든 출현을 세고, 승인된 출력 한도 안의 상세 경고와 생략한 경고 수 및 판정에 필요한 문제 사례와 정상 사례를 AI에 제공한다.
- 후보가 있거나 없는 정상 실행은 종료 상태 `0`, 인수, Git 또는 입력 처리 실패는 종료 상태 `2`로 구분된다. 외부 패키지와 네트워크 없이 실행할 수 있으며, 같은 파일의 self-test로 핵심 탐색 동작을 확인할 수 있다.
- 현재 구현과 대표 실행은 macOS에서 확인한다. Linux와 Windows 동작은 이번 완료 증거에 포함하지 않는다.
- 개발 지침이 현재 검사기에서 발생할 수 있는 `.mjs` 실패 사례마다 적용 조건, 관찰 결과, 권장 코드, 피해야 할 코드와 검증 방법을 설명한다.
- ESLint가 정확히 찾을 수 있는 코드 형태는 정상 및 오류 사례로 확인된 규칙으로 검사한다. Git 상태, 파일 위치, 인코딩, 문자열 위치와 출력 완료처럼 코드를 실행해야 확인할 수 있는 조건은 후속 검사기의 self-test 또는 실행 검사가 맡는다.
