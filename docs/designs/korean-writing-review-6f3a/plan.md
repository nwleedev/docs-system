# 한국어 문서의 번역체 재발 방지 변경 계획

## 기준과 이번 작업의 범위

이 계획은 [한국어 문서 검토 재발 방지 요구사항](./requirements.md)의 `목표`, `적용 조건`과 `완료 증거`를 기준으로 한다. 일반 산문의 문자와 문맥별 용어 판정은 [일반 산문 문장부호와 문맥별 용어 판정](./decisions/general-prose-and-contextual-wording.md), 채팅과 저장 결과물의 검토 구분은 [한국어 채팅과 저장 결과물의 검토 구분](./decisions/chat-and-stored-output-review-boundary.md)을 따른다.

후속 사례에서는 지침을 적용한 뒤에도 `포화`, `경계`, `소유`, `반증`과 반복 결론이 한국어 문서에 남았다. [후속 사례 조사](./references/comparable-cases-and-repository-evidence.md)는 기존 문서와 새 문서의 어휘 중복, 현재 워크트리에서 발견되지 않은 스킬과 공유 전 검토를 확인할 증거가 없었다는 사실을 함께 확인했다. 이 계획은 특정 단어를 금지하거나 특정 모델을 교체하는 대신, 현재 저장소에서 배포하는 `src`, `skills`, 설치 문서와 설계 문서의 책임을 맞춘다.

요구사항 소유자는 검사기 구현 전에 Node.js `.mjs` 명령줄 스크립트 개발 지침과 ESLint 검사를 준비하고, 후속 작업에서 기존 `src`, `skills`, `docs` 파일을 갱신하도록 요청했다. 준비 작업은 `docs/dev/README.md`, `docs/dev/node/mjs-cli.md`, `eslint.config.mjs`, `package.json`과 `pnpm-lock.yaml`을 만들거나 갱신할 수 있다. 후속 구현에서는 `skills/use-words-review/scripts/scan.mjs`, `korean-expressions.mjs`와 `long-paragraphs.mjs`를 같은 배포 단위로 만들며, 루트 `README.md`, `README.ko.md`와 루트 `AGENTS.md`는 이번 구현에 포함하지 않는다.

[후보 검사기 소스 조사](./references/korean-candidate-expression-linter-research.md#실행-진입점과-탐지-모듈-분리-검토)는 현재 표현 검사와 긴 문단 검사의 탐지 단위가 다르다는 점을 확인했다. [한국어 검사기의 모듈과 출력 상한](./decisions/scanner-modules-and-output-limits.md)에 따라 `scan.mjs`가 두 탐지 모듈을 정적 import하고, 각 검사가 독립된 상세 경고 및 byte 상한과 집계를 제공한다.

[지침 중복 감사](./references/instruction-duplication-audit.md)에 따른 AGENTS 감축 작업은 `src/AGENTS.ko.md`와 `src/AGENTS.en.md`만 바꾼다. 이어지는 스킬 변경은 `skills/use-words-review/SKILL.md`, `references/korean.md`, `references/examples.md`와 `scripts/scan.mjs`, `korean-expressions.mjs` 및 `long-paragraphs.mjs`만 바꾼다. 두 작업을 분리하고, 이미 반영된 용어 판정, 검토 범위와 중단 동작은 바꾸지 않는다. 두 문서 지침은 각 문서 작업의 독립된 기준을 맡으므로 두 감축 작업에서 수정하지 않는다.

## 변경 원칙

- AGENTS는 일반 채팅에 항상 적용할 짧은 작성 행동과 저장 결과물의 스킬 호출 조건을 맡는다.
- `SKILL.md`는 저장하거나 공유할 한국어 결과물의 검토 순서와 보고 방법을 맡는다.
- `korean-expressions.mjs`의 `rules`는 literal 후보의 탐지 조건, 경고 설명, 판정 질문과 한국어 대조 사례를 맡고, `long-paragraphs.mjs`의 `policy`는 긴 문단 후보의 기준과 대조 사례를 맡는다.
- `references/korean.md`는 literal 검색으로 찾을 수 없는 한국어 문장 및 문단의 의미 검토를 맡고, `references/examples.md`는 언어 공통 사례만 맡는다.
- 설치 문서는 배포 원본과 Codex가 실제로 탐색하는 위치를 구분하고 워크트리별 확인 방법을 설명한다.
- 설계 지침은 기존 문서에서 사실, 결정과 구조를 확인하되 표현을 자동으로 재사용하지 않게 한다.
- 후보 단어는 검사 신호이지 거부 목록이 아니다. 정확한 전문용례와 필요한 비교 구조를 보존한다.
- 같은 지침과 사례를 여러 파일에 복사하지 않는다. AGENTS는 짧게 유지하고 문자열 후보의 상세 사례는 검사 스크립트, 목록 밖 의미 검토 사례는 `korean.md`에 한 번만 둔다.

## 작업 단위와 순서

### 1. 평가 입력과 확인할 설치 조건을 먼저 고정한다

변경 전 기준으로 [한국어 답변 검토 평가 사례](./references/korean-review-evaluation-cases.md)의 문장 사례를 실행한다. 뜻이 모호한 기존 설계 자료가 입력에 섞인 저장 문서 작업, 일반 채팅, 명시적인 문구 검토와 설치 누락은 설치 후 호스트에서 실행할 별도 과제로 정의한다.

사용자 설치, 저장소의 `.agents/skills`, Codex가 관리하는 워크트리와 수동 Git 워크트리를 구분한다. 후속 설치 검증에서는 각 환경의 AGENTS 로딩 여부, 스킬 발견 여부, `korean.md` 읽기와 검토 호출 횟수를 기록한다. 현재 조사에서 확인한 수동 워크트리의 설치 누락은 실패 조건의 근거로 사용하되, 다른 설치 방식의 실제 동작을 확인한 것으로 간주하지 않는다.

**현재 변경의 완료 증거.** 문장 사례의 입력, 변경 전 판정과 설치 후 실행할 과제별 관찰 항목이 남아야 한다. 현재 기대 판정과 어긋난 사례는 구현 전에 `needs human input`으로 분리한다. 대상 저장소의 식별 정보와 원문은 평가 자료에 넣지 않는다. 설치 방식별 호출 결과는 후속 설치 작업을 마친 뒤 별도 검증 결과로 기록한다.

### 2. 검사기 구현에 필요한 값을 확정한다

요구사항 소유자가 승인한 후보 검사기 동작과 [후보 검사기 소스 조사](./references/korean-candidate-expression-linter-research.md)에서 선택한 구현값은 다음과 같다.

- 현재 `korean.md`에서 literal로 찾을 수 있는 후보를 모두 내장 `rules`에 넣는다. 의미 단위 `id` 하나에 확인된 활용형을 `expressions`로 명시하며, 다른 단어에 흔히 들어가는 짧은 어간은 사용하지 않는다.
- Markdown 플레인 텍스트 문단이 일곱 문장 이상이면 긴 문단 후보 하나를 경고한다. 이 기준은 의미 오류나 수정 명령이 아니며 후보가 있어도 종료 상태 `0`을 유지한다.
- `--changed`는 staged, unstaged와 untracked 일반 파일을 합쳐 각 파일의 현재 작업 트리 원문 전체를 검사한다. 삭제 파일과 submodule은 제외하고 rename은 새 위치의 현재 파일을 검사한다.
- `--changed`와 현재 디렉터리 안의 상대 위치 파일은 정규화한 상대 위치를 `sourceId`와 `path`에 사용한다. 절대 위치 또는 현재 디렉터리 밖의 `--file` 입력은 `file:1` 형식의 순번 ID를 사용하고 `path`를 생략한다. 표준 입력은 `--source-name`만 식별자로 사용한다.
- 한 실행은 source 512개, 파일 하나 2 MiB와 전체 입력 32 MiB까지 받는다. 상세 경고는 검사마다 최대 20,000개, `quote`는 최대 480 UTF-16 code unit, 직렬화한 검사 결과는 각각 최대 32 MiB다.
- JSON은 공통 `sources`와 검사별 결과 배열인 `checks`를 사용한다. 각 검사 결과는 `id`, `catalog`, `rules`, `warnings`와 `summary`를 가진다. literal 위치는 1부터 시작하는 `line`과 `startUtf16`, 일치 뒤 첫 열인 `endUtf16`으로 나타낸다. 문단 경고는 `count`와 문단 시작의 `line` 및 `startUtf16`을 사용한다. 객체 속성 순서가 아니라 배열의 결정적 순서를 규약으로 사용한다.
- 상세 경고가 해당 검사의 개수나 byte 한도에 닿아도 검사를 끝까지 수행한다. 각 `summary`의 `total`, `shown`과 `omitted`에 전체, 표시 및 생략 수를 기록하고, AI는 생략된 경고가 있으면 검토 결과 마지막에 검사 종류와 `... 그 외 <N>개의 경고가 더 발견됨`을 표시한다.
- 출력은 단일 JSON 객체로 유지한다. JSONL은 단일 JSON의 메모리 사용량이나 첫 출력 지연이 실제로 문제가 되거나 완료 전 record 소비자가 생겼을 때 다시 검토한다.
- 현재 구현과 대표 실행은 macOS에서 확인한다. Linux와 Windows 동작은 이번 완료 증거에 포함하지 않는다.

**완료 증거.** 승인된 값이 요구사항, 조사 자료와 이 계획에서 같은 동작을 설명하고, 문서 검사가 충돌이나 미정 값을 보고하지 않아야 한다. 4단계의 실행 검사에서 세 입력 방식, 공통 `sources`, 고정된 두 `checks`와 종료 상태를 확인한다. 각 검사의 경고 수와 byte 상한을 넘는 입력에서도 해당 검사의 전체 출현 수, 표시 수와 생략 수가 맞고 온전한 JSON 한 건만 출력돼야 한다.

5단계에 명시한 literal 후보는 `korean-expressions.mjs`의 단일 `rules` 상수에 있어야 하고, 12단계의 긴 문단 기준은 `long-paragraphs.mjs`의 `policy`가 맡는다. 각 규칙과 정책은 `id`, `kind`, `message`, `queries`, 문제 사례와 정상 사례를 가진다. literal 규칙은 `expressions`, paragraph 정책은 최소 문장 수인 `min`을 가진다. 자체 검사는 필수 값, 중복 ID, `kind`별 탐지 조건, 전체 표현 규칙 순회와 긴 문단 정책 적용을 확인한다. 이후 AI 작업에서 새 후보를 발견하면 같은 구조의 규칙을 추가하거나 기존 규칙 및 정책의 조건과 사례를 조정할 수 있어야 하며, 변경한 전체 기준은 같은 자체 검사를 통과해야 한다.

### 3. `.mjs` 개발 지침과 ESLint 검사를 먼저 준비한다

검사기 코드를 작성하기 전에 `docs/dev/node/mjs-cli.md`를 현재 개발 지침으로 추가한다. 이 문서는 Node.js 22.0.0에서 실행하는 `.mjs` 검사기를 대상으로 하며, CLI 인수, byte 제한, 엄격한 UTF-8, 파일과 Git 입력, literal 탐색, Markdown 플레인 텍스트 문단 구분, `Intl.Segmenter`의 한국어 문장 분리, UTF-16 위치, 결정적 정렬, JSON 출력과 종료 상태를 설명한다. 후속 `scan.mjs`에 둘 self-test 사례와 가장 작은 검증 방법도 각 실패 조건, 적용 범위, 관찰 결과, 권장 코드 및 피해야 할 코드에 연결한다.

ESLint는 개발 환경에서만 사용하는 의존성이며 배포할 스킬 파일에는 포함하지 않는다. 개발 환경은 ESLint 10.8.0이 요구하는 Node.js `^20.19.0 || ^22.13.0 || >=24`를 사용하고, 검사기 자체는 Node.js 22.0.0 이상에서 실행하는 조건을 유지한다. `eslint.config.mjs`는 ESLint core와 `@eslint/js`만 사용하고 검사기 및 설정 파일에 범위를 제한한다. 기존 import 제한은 유지하되 `scan.mjs`의 정확한 위치에서 두 탐지 모듈의 정적 import만 허용한다. `eslint-plugin-n`, `eslint-plugin-security`와 custom rule은 추가하지 않는다. 정적 규칙은 정상 및 오류 사례를 각각 실행해 의도한 코드만 거부하는지 확인한다.

Git 상태, symlink, 실제 byte 수, UTF-8 해석, 겹치는 문자열, 위치 계산, 출력 상한과 stream 완료는 ESLint가 코드를 실행하지 않고 판정할 수 없다. 이 조건은 4단계의 self-test 및 대표 실행에 연결하고, 정적 규칙이 증명하는 범위로 설명하지 않는다.

**완료 증거.** `pnpm install --frozen-lockfile`, `pnpm lint`와 규칙별 정상 및 오류 사례 검사가 실행 가능해야 한다. 개발 지침의 각 사례는 ESLint, self-test, 대표 실행 또는 요구사항 소유자가 지정한 검수 가운데 하나와 연결돼야 한다. 여러 실행 방식, 입력, Git 및 파일 처리, 탐색, 출력과 오류 처리 관점에서 다시 조사했을 때 새 사례, 기존 사례에 추가할 조건, 코드 예시 또는 정적 규칙이 한 차례 연속으로 나오지 않아야 한다.

### 4. 실행 진입점과 두 탐지 모듈을 작성하고 검사한다

`skills/use-words-review/scripts/scan.mjs`, `korean-expressions.mjs`와 `long-paragraphs.mjs`를 같은 배포 단위로 만든다. Node.js 표준 라이브러리만 사용하고 외부 패키지 설치, 실행 중 인터넷 요청, 별도 규칙 파일, 클래스, 팩터리와 의존성 주입 프레임워크를 추가하지 않는다. `scan.mjs`만 두 탐지 모듈을 정적 import하고 모든 정상 실행에서 함께 호출한다. 규칙 ID, 표현, `catalog`, 검사 종류와 필터를 입력받지 않는다.

- `--changed <repo>`, 반복 가능한 `--file <path>`, `--stdin --source-name <name>` 가운데 정확히 하나를 받는다. `--self-test`는 이 세 입력 방식과 함께 사용할 수 없는 별도 실행 방식이다.
- 세 입력 처리 함수는 같은 `scanSources({ provideSources })` 함수에 `Source`를 제공한다. source 제공 함수만 I/O 경계로 전달하고 두 탐지 함수는 주입하지 않는다. `--changed`는 staged, unstaged와 untracked 일반 파일의 현재 작업 트리 원문 전체를 검사하고, 변경 파일이 없으면 빈 `source` 결과를 낸다. `--file`은 호출 순서를 유지하며 같은 정규화 위치의 중복을 거부한다. 저장소 전체 순회, glob, `--text`와 변경 hunk parser는 넣지 않는다.
- 크기가 0인 파일과 빈 표준 입력은 유효한 source다. 이 경우에도 표현 규칙과 긴 문단 정책으로 만든 두 `catalog`와 source를 출력하고 각 `rules` 및 경고 배열은 비우며 두 `summary`의 집계값을 0으로 반환한다.
- `korean-expressions.mjs`는 모든 source와 모든 내장 표현의 겹치는 literal 출현까지 찾는다. 각 출현에는 1부터 시작하는 `line`, UTF-16 code unit 기준 `startUtf16`과 `endUtf16` 및 최대 480 code unit의 `quote`를 넣는다. source 512개, 파일 하나 2 MiB와 전체 입력 32 MiB를 넘으면 진입점이 입력 실패로 처리한다.
- `long-paragraphs.mjs`는 빈 줄로 구분한 최상위 플레인 텍스트 문단을 `Intl.Segmenter("ko", { granularity: "sentence" })`로 센다. 제목, 표, 목록, 인용문, HTML, front matter, fenced 및 들여쓴 코드는 문단 후보에서 제외한다. 일곱 문장 이상인 문단마다 경고 하나를 만들고 `count`, 문단 시작의 `line`과 `startUtf16` 및 최대 480 UTF-16 code unit의 `quote`를 넣는다. 중첩 구조를 위해 완전한 Markdown parser나 외부 package를 추가하지 않는다.
- 표준 출력의 JSON은 공통 `sources`와 표현 및 문단 순서로 고정한 `checks`를 담는다. 각 검사 결과에는 실제 순회한 규칙 또는 정책으로 만든 `catalog`, 발견된 규칙의 설명과 사례를 한 번씩 담은 `rules`, 결정적 순서의 상세 `warnings`와 `summary`를 둔다. 후보 유무와 상세 경고 생략은 실행 실패가 아니며 결과 파일을 만들지 않는다.
- 각 검사는 상세 경고 20,000개와 직렬화 결과 32 MiB 중 먼저 닿는 한도에서 경고를 자른다. 한도에 닿은 뒤에도 해당 검사의 모든 출현을 끝까지 세며, 각 `summary.total`, `summary.shown`과 `summary.omitted`를 정확히 계산한다. 생략된 출현에서만 발견된 규칙도 해당 `rules`에 포함한다.
- 인수, Git, 파일, 인코딩, 입력 상한과 직렬화 실패만 진입점에서 한 번 처리해 원문과 개인 위치가 없는 표준 오류를 쓰고 종료 상태 `2`를 반환한다. 상세 경고를 모두 빼도 검사 결과 하나가 32 MiB를 넘으면 부분 JSON을 쓰지 않고 실패한다.

`scan.mjs --self-test`는 두 탐지 모듈의 실제 exported function과 운영 조립 함수를 사용한다. 표현 규칙과 문단 정책의 필수 필드 및 ID 중복, 전체 표현 규칙 순회, 겹치는 literal 출현, 여섯 문장과 일곱 문장의 경계, Markdown 제외 block, 줄과 UTF-16 열, 빈 입력, 검사별 상세 경고 축약, 독립된 `summary`, 온전한 JSON 및 실패 상태를 확인한다. 단일 주제와 여러 주제인 일곱 문장 문단에서 같은 경고가 나오는지도 확인해 의미 판정이 탐색 함수에 들어가지 않게 한다. 구현 담당자는 `node skills/use-words-review/scripts/scan.mjs --self-test`를 실행하며 성공은 `0`, 검사 실패는 `2`로 판정한다. 같은 원문을 `--file`과 `--stdin`으로 실행했을 때 `source` 식별 정보 이외의 검사 결과와 집계가 같아야 한다.

Node.js 22.0.0 이상과 Git 2.18.0 이상을 먼저 확인하고 macOS 구현 환경에서 자체 검사와 대표 입력을 실행한다.

**완료 증거.** 세 스크립트가 존재하고 세 입력 방식, 전체 표현 규칙 순회, 긴 문단 정책 적용, 모든 literal 및 긴 문단 후보의 독립 집계, 빈 입력, 검사별 `catalog`, 상세 경고의 결정적 축약, 정확한 두 `summary`, 종료 상태 `0`과 `2`, 입력 및 출력 상한과 자체 검사를 승인된 값으로 구현해야 한다. import graph는 `scan.mjs`에서 두 탐지 모듈로만 향해야 한다. macOS에서 직접 실행한 자체 검사가 통과해야 한다. SARIF, reviewdog, JSONL, pre-commit, CI, Codex hook와 MCP는 현재 소비자가 없으므로 추가하지 않는다.

### 5. 후보 표현 자료와 의미 검토 자료를 나눈다

`skills/use-words-review/scripts/korean-expressions.mjs`의 단일 `rules` 상수에 현재 `korean.md`에서 literal로 찾을 수 있는 후보를 모두 옮긴다. 각 규칙은 실패 문장과 정상 전문용례를 함께 제공한다.

- 일반 산문의 U+00B7을 검사하되 정확한 문자 보존 사례를 함께 제공한다.
- 번역체 형태는 `에 대해서`, `에 의해서`, `에 있어서`, `와의`, `하지 않으면 안 된다`, `회의를 가지다`와 `사용자-facing`을 포함한다.
- 문맥을 확인할 용어는 `범위`, `경계`, `계약`, `루브릭`, `유효성`, `정합성`, `가시성`, `경로`, `공개`, `제품`, `포화`, `소유`와 `반증`을 포함한다.
- 행동을 감출 수 있는 표현은 `지원`, `보장`, `대응`, `다루다`, `노출`, `포착`, `정렬`과 `표면화`를 포함한다.
- 정보를 더하지 않을 수 있는 표현은 `핵심`, `효과적`, `원활`, `강력`, `견고`, `포괄적`, `다양한`과 `본질적`을 포함한다.
- 지칭 대상을 확인할 표현은 `해당`, `관련`, `이 내용`, `결과`, `출력`, `데이터`와 `기능`을 포함한다.
- `좁히`와 `좁혀`처럼 의미 판정 기준은 같지만 글자가 달라지는 활용형은 같은 규칙의 `expressions`에 명시한다. `박`처럼 다른 단어에도 흔히 들어가는 짧은 어간은 사용하지 않고 `박다`, `박아`, `박은`, `박힌`, `박혀`처럼 검토 가치가 확인된 형태만 둔다.

- `포화`는 물리 및 기술 상태라면 해당 분야의 정의, 측정 대상과 판정 조건이 있을 때 유지한다. 연구 자료라면 새 범주가 나오지 않는다는 판단 방법과 자료 수집 중단 기준도 밝혀야 한다.
- `경계`는 수학, 보안, 시스템 접점처럼 안과 밖 또는 책임이 바뀌는 기준이 드러날 때만 유지한다.
- `소유`는 재산권이나 승인된 책임 관계가 실제로 있을 때 사용한다. 그런 관계가 아닌 문서와 기관에는 실제 행동인 `기록한다`, `운영한다`, `답변한다` 등을 근거에 맞게 쓴다.
- `반증`은 명시된 가설과 기각 조건이 있을 때만 유지한다. 실행 가능성 확인, 대조와 실패 조건 점검은 해당 행동을 직접 쓴다.
- `경로`는 파일 위치, URL, 네트워크 구간과 그래프 탐색처럼 위치나 이동 구간이 식별되는지 다시 확인한다.
- 제품명, API 이름과 승인된 전문용어가 아닌 영어 보통명사는 한국어 문장에 그대로 섞지 않는다.
- 기존 문서의 표현은 승인된 문체 예시가 아니다. 기존 자료의 사실과 결정을 사용하되 새 독자에게 필요한 주체, 행동, 조건과 결과를 다시 쓴다.
- 같은 속성을 같은 순서로 비교하는 구조는 유지할 수 있다. 새 정보가 없는 반복 결론만 고친다.

일반 산문의 U+00B7 금지, 정확한 문자 보존 예외와 literal로 판정할 후보는 같은 `rules` 상수에서 관리한다. 용어 수를 닫힌 목록으로 제한하거나 후보 출현만으로 실패시키지 않는다. `references/korean.md`에는 영어식 무생물 주어, 행동 주체가 빠진 피동문, 명사 나열, 지칭 대상 변화와 문단 관계처럼 literal 검색으로 찾을 수 없는 의미 검토 기준만 남긴다.

**완료 증거.** 각 후보 규칙에 실패 사례와 통과 사례가 있고, 스크립트는 내장 `rules` 전체를 순회해 모든 출현을 세고 출력 한도 안의 상세 경고와 생략 수를 알린다. `korean.md`는 목록 밖 표현과 문장 구조를 계속 판정해야 한다. 사례에는 특정 저장소의 문장, 조직, 직무와 수치를 넣지 않는다. 정확한 연구 용어, 보안 경계, 소유권, 법률 계약과 파일 경로가 통과해야 한다.

`skills/use-words-review/references/examples.md`에는 언어 공통 사례 한 쌍만 추가한다. 기존 문서의 확인된 사실과 결정은 새 결과물에 사용할 수 있지만, 기존 제목과 표현은 승인된 공개 문구라는 근거가 없으면 문체 예시로 복사하지 않는다는 사례다. `포화`, `경계` 같은 한국어 문자열과 언어별 고쳐 쓰기는 넣지 않는다.

**공통 사례 완료 증거.** 기존 자료의 사실을 빠뜨리지 않으면서 문장을 새 독자와 용도에 맞게 다시 쓰는 통과 사례와, 기존 문구라는 이유만으로 그대로 옮기는 실패 사례가 함께 있어야 한다. `examples.md`가 한국어 용어 판정을 중복해서는 안 된다.

### 6. `skills/use-words-review/SKILL.md`의 검토 입력과 중단 조건을 보강한다

스킬 범위는 AI가 만들거나 고친 한국어 문서와 저장하거나 공유할 문구 및 이름으로 유지한다. 일반 채팅에는 실행하지 않고, 사용자가 채팅 문구 검토를 명시적으로 요청한 경우만 예외로 남긴다.

검토자는 입력 종류에 맞춰 `scan.mjs`를 먼저 실행하고 공통 `sources`와 두 `checks`의 `catalog`, 상세 경고 및 `summary`를 확인한 뒤 `korean.md`를 반드시 읽는다. 긴 문단 경고는 파일이나 표준 입력의 문단 전체를 다시 읽고 중심 내용, 중요한 정보의 위치와 문장 사이의 관계를 판정한다. 검사별 `summary.omitted`가 0보다 크면 검토 결과 마지막에 검사 종류와 `... 그 외 <N>개의 경고가 더 발견됨`을 표시하고, 상세 판정이 필요한 원문은 파일별로 나눠 다시 실행한다. 결과물뿐 아니라 작성에 사용한 기존 문서도 입력으로 받고, 기존 자료의 추상 명사, 영어 보통명사와 반복 결론을 새 결과물이 근거 없이 이어받았는지 확인한다. 독립 검토자는 각 후보의 실제 용례와 문장별 주체, 행동, 조건, 결과 및 필요한 반복 구조를 판정한다.

스킬 본문에는 새 용어별 설명을 복사하지 않는다. 한국어 결과물이 있는데 `korean.md`를 읽지 못하면 통과를 보고하지 않는다. 독립 검토자를 사용할 수 없으면 주 에이전트가 같은 기준으로 읽기 전용 검토를 수행하고 독립 검토가 아니었다는 제한을 보고한다. 스킬 자체가 발견되지 않는 상황은 실행 전에 생기는 문제이므로 AGENTS와 설치 문서가 맡는다.

**완료 증거.** 일반 채팅 제외와 명시적인 문구 검토 예외가 유지돼야 한다. 저장 결과물 검토에는 스크립트의 전체 규칙 실행, 참조 자료, 기존 문서 오염 검사, 의미 검토와 판정 보고가 모두 있어야 한다. Agent Skills 명세 검사도 통과해야 한다.

### 7. `src/AGENTS.ko.md`와 `src/AGENTS.en.md`를 같은 동작으로 맞춘다

두 배포본의 `USE WORDS REVIEW` 표시 구간을 함께 바꾼다. 영어 배포본에서도 한국어로 작성할 때의 실행 조건과 한국어 후보 문자열은 같은 의미를 유지한다.

- 일반 채팅, 진행 알림과 설명 답변에는 스킬을 실행하지 않는다. 중간 메시지와 최종 답변 모두 처음부터 대상, 주체, 행동, 조건과 결과가 드러나게 쓴다.
- AGENTS에는 `포화`, `경계`, `소유`처럼 실제 행동을 감추기 쉬운 소수 신호와 `설계·구현·검증` 같은 U+00B7 예시만 둔다. 목록이 금칙어가 아니며 새 후보에도 같은 질문을 적용한다고 적는다.
- 기존 문서는 사실과 결정을 확인하는 자료이지 승인된 문체 예시가 아니라고 명시한다. 표현을 재사용하기 전에 실제 행동과 조건을 다시 쓴다.
- AI가 만들거나 고친 한국어 문서, 저장하거나 공유할 문구와 이름은 작성 전에 설치된 스킬의 `references/korean.md`를 읽고 공유 전에 스킬로 검토한다. 스킬은 `scan.mjs`를 실행해 표현 규칙과 긴 문단 정책을 모두 적용한다.
- 사용자가 특정 채팅 문구의 검토를 명시적으로 요청하면 예외로 스킬을 실행한다. 채팅 초안을 저장하거나 전달할 때에는 실제 저장 또는 전달 직전에 한 번 실행한다.
- 스킬이 필요한데 현재 실행에서 찾을 수 없으면 완료를 주장하지 않고 설치 누락을 보고한다.

상세 용어 조건과 전체 대조문은 AGENTS에 넣지 않는다. 이번 구현 범위는 `src`, `skills`, README와 `docs`이므로 루트 `AGENTS.md`는 바꾸지 않는다. 배포 원본을 실제 저장소에 다시 적용할 때 루트 지침과 맞는지는 설치 검증에서 확인한다.

`src/AGENTS.en.md`의 `own`, `owner`, `ownership`도 문맥별로 확인한다. 문서나 절이 정보를 `own`한다고 쓴 곳은 `records`, `defines`, `maintains` 또는 `authoritative source`처럼 실제 관계를 나타내는 표현으로 바꾼다. 요구사항 승인자나 결정 승인자처럼 권한을 가진 역할 이름은 그 권한이 현재 문서에 정의돼 있을 때만 유지한다. 한국어 배포본도 같은 역할과 행동을 나타내는지 함께 대조한다.

**완료 증거.** 두 배포본의 실행 조건과 중단 동작이 같아야 한다. 일반 채팅의 스킬 호출은 없어야 하며 저장 결과물과 명시적인 검토 요청은 누락되면 안 된다. AGENTS 전체 크기와 중복 지침을 비교해 새 예시가 기존 규칙을 되풀이하지 않는지 확인한다.

### 후속 설치 작업

루트 `README.md`와 `README.ko.md`는 현재 구현 범위에 포함되지 않는다. 아래 변경은 설치 문서까지 갱신하는 후속 작업에서 적용한다.

`README.md`와 `README.ko.md`에 Codex가 현재 탐색하는 저장소, 사용자와 관리자 위치를 적고, 이 저장소의 `skills/use-words-review/`는 복사할 배포 원본이라고 설명한다. 대상 저장소에 스킬을 커밋하는 방식만 강제하지 않는다.

- 저장소에 작업 절차를 함께 버전 관리해야 하면 `.agents/skills`에 둔다.
- 한 사용자가 여러 저장소에 같은 스킬을 적용하면 사용자 위치 또는 탐색 위치의 심볼릭 링크를 사용할 수 있다.
- 공통 실행 환경은 관리자 위치를 사용할 수 있다.
- 설치와 갱신을 묶어 배포하려면 플러그인을 검토한다.
- Codex 관리 워크트리의 `.worktreeinclude`는 수동 Git 워크트리에 적용되지 않는다고 구분한다.
- 설치 뒤 현재 실행의 스킬 목록, `korean.md` 존재와 대표 한국어 저장 문서 작업을 확인한다. 스킬 목록이 갱신되지 않으면 실행을 다시 시작한다.

**완료 증거.** 두 README가 같은 설치 선택지와 워크트리 제한을 설명해야 한다. 문서의 위치가 Codex 공식 탐색 위치와 일치하고, 대상 저장소에 커밋하지 않아도 되는 선택지가 분명해야 한다.

### 8. `docs/designs/README.md`에 기존 문서의 재사용 기준을 추가한다

파생 설계 문서는 기존 자료에서 요구사항, 결정, 저장소 증거와 필요한 비교 구조를 가져올 수 있다. 기존 제목, 추상 명사와 결론 문구는 승인된 공개 문구라는 근거가 있을 때만 그대로 사용한다. 그렇지 않으면 현재 독자, 행동 주체, 조건과 결과에 맞춰 다시 쓴다.

이 규칙은 반복 구조를 금지하지 않는다. 여러 대상을 같은 속성과 순서로 비교해야 하면 같은 구조를 사용할 수 있다. 각 절이 새 사실이나 판단 근거를 제공하지 않고 같은 결론만 반복할 때 고친다. 한국어 literal 용례는 검사 스크립트가 맡으므로 설계 지침에는 특정 후보 단어 목록을 복사하지 않는다.

현재 파일의 `own`, `owner`, `owning`, `ownership`도 전부 문맥별로 검토한다. 문서나 절의 배치 책임을 설명하는 `owning document`와 `section owns`는 `authoritative document`, `record in` 또는 `maintain in`처럼 문서의 실제 역할을 밝히는 표현으로 바꾼다. 요구사항 문구를 승인하는 역할과 결정을 내리는 역할은 단순 문서 배치와 다르므로, 권한을 뜻하는 역할명은 임의로 바꾸지 않는다. 역할명을 유지한다면 첫 정의에서 그 사람이 승인하거나 결정하는 내용을 직접 설명하고, 문서가 판단하는 것처럼 쓰지 않는다.

**완료 증거.** 기존 문서가 증거와 문체 예시로 혼동되지 않아야 하고, 필요한 비교 구조의 허용 조건도 함께 있어야 한다. 문서를 주체로 삼은 `own` 계열 표현이 남았다면 그 문맥과 유지 근거를 검토 결과에 적는다. `docs/dev/README.md`는 애플리케이션 변경 지침이며 이번 실패의 기준 문서가 아니므로 바꾸지 않는다.

### 9. 두 AGENTS 배포본에서 다른 파일이 맡은 절차를 줄인다

[한국어 문서 검토 재발 방지 요구사항](./requirements.md)의 `목표`와 `완료 증거`에 따라 두 배포본이 같은 한국어 작성 조건과 스킬 호출 조건을 계속 설명하게 한다. 이번 작업은 [지침 중복 감사](./references/instruction-duplication-audit.md)가 다른 파일의 책임이라고 판정한 설명만 줄이며, `skills/use-words-review`, `docs/designs/README.md`와 `docs/dev/README.md`는 바꾸지 않는다.

`한국어 채팅 작성`과 `Writing Korean Chat Responses`에서는 각 파일의 일반 글쓰기 원칙을 다시 설명하는 문장을 줄인다. 일반 채팅에서 스킬을 실행하지 않는 조건, U+00B7 보존 예외와 문맥에 따라 후보 용어를 판정하는 짧은 규칙은 남긴다. 상세 용어 사례는 검사 스크립트가 맡으므로 AGENTS에 추가하거나 옮기지 않는다.

`저장하거나 전달할 글과 문구 검토`와 `Reviewing Text That Will Be Stored or Delivered`에서는 스킬 실행 조건, 사용자가 채팅 문구 검토를 명시적으로 요청한 경우의 예외와 설치 누락 시 중단 조건만 남긴다. 검토 입력 구성, 서브에이전트와 주 에이전트 대체 절차, 판정 상태와 결과 취합 방법은 `skills/use-words-review/SKILL.md`가 맡으므로 AGENTS에서 제거한다.

`설계 문서`와 `Design Documents`는 `docs/designs/README.md`를 읽어야 하는 시점, 기존 `requirements.md` 확인과 완료 후 검증만 남기고 문서 생성 조건과 상세 검사 방법은 해당 README로 연결한다. 파생 문서가 요구사항 원문을 인용하게 하는 현재 문장은 요구사항 파일과 설명적인 소제목을 연결하도록 고쳐 `docs/designs/README.md`와 맞춘다.

`개발 지침`과 `Development Guidance`는 `docs/dev/README.md`를 읽어야 하는 시점, 현재 작업에 필요한 지침 선택과 완료 후 대조만 남긴다. 계획 기준 커밋, 지침 문서 형식과 기계 검사에 관한 상세 절차는 해당 README가 맡게 한다. 공통 검사 원칙은 AGENTS에서 항상 적용할 최소 규칙만 유지하고, 두 README가 독립적으로 제공해야 하는 문서별 검증 규칙은 옮기지 않는다.

두 언어 파일은 같은 변경 단위에서 대조한다. 일반 채팅, 저장 결과물과 명시적으로 요청된 채팅 문구 검토에서 스킬 실행 조건과 중단 동작이 같아야 한다. 이번 감축 대상 밖에 있는 두 파일의 기존 동작 차이는 함께 고치지 않는다. 어느 동작을 유지할지 승인 근거가 없는 차이를 발견하면 해당 부분을 `needs human input`으로 남긴다.

**완료 증거.** 변경 파일은 `src/AGENTS.ko.md`와 `src/AGENTS.en.md`뿐이어야 한다. 두 파일에서 README와 스킬의 상세 절차를 되풀이한 문장이 제거되고, 남은 안내로 각 기준 파일을 찾을 수 있어야 한다. 일반 채팅은 스킬을 실행하지 않고, 저장하거나 전달할 한국어 결과물과 사용자가 검토를 명시적으로 요청한 문구는 스킬 검토 대상이어야 한다. 스킬 또는 `references/korean.md`를 읽을 수 없을 때 완료를 주장하지 않는 조건도 유지해야 한다. 두 언어 파일의 해당 절을 문장별로 대조하고, 감축 대상 밖의 차이가 바뀌지 않았는지 diff로 확인한다.

필수 호출 조건, 누락 시 중단 조건 또는 문서 작업의 권한 규칙을 지워야만 중복을 줄일 수 있다면 작업을 멈춘다. 어느 파일이 해당 규칙을 맡는지 확인한 뒤 AGENTS에 짧은 안내를 남기거나 요구사항 소유자에게 판단을 요청한다.

### 10. `use-words-review`의 파일별 내부 반복을 줄인다

[한국어 문서 검토 재발 방지 요구사항](./requirements.md)의 `목표`, `적용 조건`과 `완료 증거`에 따라 검토 범위, 한국어 판정과 정상 전문용례를 유지하면서 같은 절차나 사례를 다시 설명하는 부분을 줄인다. literal 후보 자료는 `korean-expressions.mjs`, 긴 문단 기준은 `long-paragraphs.mjs`, 목록 밖 의미 검토는 `references/korean.md`, 언어 공통 사례는 `references/examples.md`, 실행 절차는 `SKILL.md`에 한 번씩 둔다. 스크립트는 승인된 `scan.mjs`, `korean-expressions.mjs`와 `long-paragraphs.mjs`만 둔다.

작업 전에 현재 description의 문자 수, 각 파일의 줄 수와 바이트 수를 기록한다. 수치는 감축 결과를 확인하는 보조 자료로만 사용한다. 문장이 줄었더라도 검토 범위나 판정 조건이 사라지면 통과로 판단하지 않는다. 먼저 두 참고 자료의 작은 중복을 줄이고, 그 결과를 기준으로 `SKILL.md`의 실행 절차를 재구성한다. 호출 조건을 담는 description은 본문 정리가 끝난 뒤 마지막에 줄인다.

**검토 문맥 준비.** `SKILL.md`의 `Establish the review scope`, `Collect publishable evidence`와 `Prepare the independent review`에 나뉜 문맥 준비 절차를 한곳으로 모은다. 결과물, 작성에 사용한 기존 문서, 독자와 독자가 해야 할 일, 역할, 저장소 규칙과 검사 결과를 하나의 검토 묶음으로 준비한다. 변경 문단, 절과 전체 파일 가운데 판단에 필요한 가장 작은 단위를 고르는 조건도 이 절에서만 설명한다. 원문 비교가 필요할 때만 최소화한 원문을 제공하고, 개인 경로, 자격 증명, 사적인 URL과 식별자를 지우는 조건을 같은 절에 둔다. 범위 설정 절에는 검토 대상과 공유 단위만 남기고, 검토 요청 구성 절에는 이미 준비한 묶음을 전달한다는 지시만 남긴다.

**현재 검토의 모델 선택.** `Choose the model and reasoning effort`에는 현재 결과물의 독자, 근거, 역할의 명확성, 잘못된 문구가 미칠 영향을 기준으로 낮음, 중간과 높음 가운데 하나를 고르는 규칙만 둔다. 호스트가 지원하는 모델 대응, 요청마다 설정을 바꿀 수 없을 때의 대체 동작과 근거 충돌 또는 누락된 판정 때문에 한 번 더 강한 검토가 필요한 조건도 이 소제목에서 한 번만 설명한다. 문서 길이만으로 모델을 고르지 않는 조건과 최고 추론 수준을 기본값으로 사용하지 않는 조건은 유지한다.

**새 모델 설정의 채택 평가.** 현재 검토에서 모델을 고르는 절차와 다른 소제목으로 분리한다. 기존보다 가볍거나 다른 설정을 계속 사용하려면 담당 검수자가 대표 사례의 기대 판정과 발견 항목을 승인해야 한다. 의미가 불분명한 문장, 문장 사이에서 역할이나 승인 상태가 끊긴 사례, 근거가 없어 `needs human input`이어야 하는 사례와 길지만 뜻이 분명한 통과 사례를 모두 사용한다. 한 결함을 놓치거나 없는 결함을 만들면 설정을 채택하지 않는다. 통과한 설정끼리만 누락, 잘못된 지적, 입력과 출력 토큰 및 걸린 시간을 비교하고, 호스트가 값을 제공하지 않으면 추정하지 않는다. 같은 채택 조건을 현재 모델 선택이나 위임 절에서 다시 설명하지 않는다.

**읽기 전용 검토와 판정 상태.** 수정 금지 지시는 주 에이전트가 따를 전체 원칙, 서브에이전트에게 전달할 읽기 전용 조건과 주 에이전트 대체 절차에만 둔다. 범위 설정, 검토 결과 요구와 마지막 문장에서 같은 지시를 되풀이하지 않는다. `pass`, `needs revision`, `needs human input`, `not applicable`의 정의는 검토 결과 형식에서 한 번만 설명한다. 저장소 근거로 고칠 내용을 확인할 수 있으면 `needs revision`, 필요한 정보가 없거나 충돌하면 `needs human input`이라는 구분도 해당 정의에 합친다. 결과 취합과 보고 절에서는 상태 이름을 사용하되 다시 정의하지 않는다.

**description.** 현재 파일 종류와 문구 종류를 길게 나열한 설명을 줄인다. 설명에는 저장, 커밋, 게시 또는 대화 밖 공유 전에 글과 이름을 검토하는 기능, 사용자가 특정 문구 검토를 요청한 경우의 실행 조건, 한국어가 있으면 한국어 판정 자료를 적용하는 조건과 일반 채팅 제외를 남긴다. 본문이 맡는 검토 입력, 모델 선택과 보고 절차는 description에 넣지 않는다. 수정 전보다 짧아야 하고 Agent Skills 명세의 길이와 형식 제한을 통과해야 한다. 저장 결과물, 명시적인 문구 검토, 일반 채팅과 한국어 포함 여부를 달리한 호출 사례로 필요한 핵심어가 빠지지 않았는지 확인한다.

**한국어 공통 판정.** `references/korean.md`의 첫 문단에는 한국어 부분에만 적용한다는 범위와 후보 표현을 금칙어로 보지 않는다는 원칙만 남긴다. 목록 밖 표현과 문장 구조를 판정할 때 확립된 전문용어인지, 지칭 대상과 행동 주체가 드러나는지, 행동, 조건과 결과를 이해할 수 있는지, 저장소 근거로 빠진 내용을 확인할 수 있는지를 순서대로 묻는다. `pass`, `needs revision`과 `needs human input`으로 나누는 조건도 이 절에서만 설명한다. literal 후보별 질문과 대조 사례는 스크립트의 `rules`로 옮긴다.

**평가 수식어 사례.** `references/korean.md`의 `직역과 번역체`에 있는 `다양한 측면`, `강력한`, `효과적`과 `원활한` 복합 사례를 제거한다. 같은 결함과 정상 대조문을 판정 상태, 빠진 정보와 유지 근거까지 포함해 설명하는 `정보를 더하지 않는 평가 표현` 절은 유지한다. `계약`, `경계`, `좁히다`, `지원`과 `보장`처럼 literal로 찾을 표현의 개별 실패 사례와 정상 전문용례는 스크립트의 규칙으로 옮긴다. 여러 고정 번역이 한 문장에서 행동을 감추는 구조처럼 단어 하나의 출현으로 찾을 수 없는 사례만 `korean.md`에 남긴다.

**기호 사례.** `references/examples.md`의 `Unnecessary symbols and required notation`에는 정확한 수식, 상표, 승인된 화면 이름과 접근성 안내를 보존한다는 언어 공통 원칙을 남긴다. U+00B7의 한국어 실패 사례와 보존 사례는 스크립트의 규칙으로 옮긴다. 장식 목적으로 기호를 이어 붙인 실패 사례, 일반 문장으로 고친 사례와 언어별 문장부호 규칙은 해당 언어 자료가 정한다는 조건은 유지한다.

**정적 검증.** `SKILL.md`, `references/korean.md`, `references/examples.md`와 `scripts/scan.mjs`, `scripts/korean-expressions.mjs`, `scripts/long-paragraphs.mjs` 이외의 파일은 이 작업 단위에서 바꾸지 않는다. description의 문자 수가 수정 전보다 줄고 1,024자를 넘지 않는지 확인한다. Markdown 제목 단계, 목차 링크와 스킬의 상대 링크가 실제 위치를 가리키는지 검사한다. `skills-ref`가 현재 실행 환경에 있으면 스킬 디렉터리를 검증하고, 없으면 이름, description과 YAML 머리말을 Agent Skills 명세에 직접 대조한 뒤 명세 검사기를 실행하지 못했다고 기록한다.

검토 동작은 다음 사례를 문장별로 추적한다. 일반 채팅은 검토 대상에서 빠지고, 저장하거나 대화 밖으로 전달할 문구와 사용자가 명시적으로 검토를 요청한 문구는 공유 단위마다 한 번 검토해야 한다. 한국어가 포함되면 스크립트의 내장 규칙 전체를 실행하고 `korean.md`를 전부 읽으며, 포함되지 않으면 두 절차를 실행하지 않아야 한다. 필수 스크립트나 참고 자료를 읽을 수 없으면 `pass`를 보고하지 않아야 한다. 서브에이전트를 사용할 수 없으면 주 에이전트가 읽기 전용 검토를 수행하고 제한을 밝혀야 한다. 네 판정 상태, 현재 모델 선택, 새 설정의 채택 평가와 근거 충돌 시 재검토 조건도 감축 전과 같은 결과를 내야 한다.

**완료 증거.** diff에서 계획한 반복 문장과 앞쪽 평가 수식어 사례만 사라지고, 네 파일의 다른 사례와 검토 조건이 유지돼야 한다. 수정 전후의 description 문자 수와 파일별 줄 수 및 바이트 수를 함께 기록하되, 크기 감소만으로 완료를 주장하지 않는다. 정적 검사 결과, 호출 사례별 예상 동작 대조와 한국어 문서 검토 결과를 남긴다. 실제 호스트의 스킬 호출 여부와 모델별 판정 품질은 후속 설치 작업의 검증 전까지 확인한 것으로 기록하지 않는다.

검토 대상, 일반 채팅 예외, 원문 최소화, 민감한 정보 제거, 필수 참고 자료, 읽기 전용 대체 절차, 판정 상태 또는 모델 설정 채택 조건 가운데 하나라도 감축 전과 같은 뜻으로 연결되지 않으면 작업을 멈춘다. 짧은 description이 호출 사례를 구분하지 못하면 필요한 핵심어를 복원한 뒤 다시 확인한다. 제거하려는 사례가 특정 판정의 유일한 대조 사례라면 제거하지 않고 `needs human input`으로 보고한다.

### 11. 모든 변경 뒤 대표 작업을 반복하고 결과를 비교한다

1단계와 같은 합성 입력을 변경 전후에 각각 세 번 실행하고 문장별 판정 상태가 반복되는지 확인한다. 먼저 요구사항과 사실을 대조한 뒤 문장별 자연스러움을 판정한다. U+00B7과 후보 표현의 출현 수는 검토 대상을 찾는 보조 자료로만 쓴다.

통과하려면 4단계의 직접 실행과 자체 검사, 5단계의 후보 및 정상 사례, 6단계의 스킬 실행 순서, 7단계와 9단계의 두 AGENTS 호출 조건, 8단계의 설계 문서 기준과 10단계의 파일별 책임이 최종 diff에서 함께 확인돼야 한다. 일반 채팅에서는 스킬을 실행하지 않고, 저장 결과물과 명시적인 문구 검토에서는 공유 단위마다 한 번 실행해야 한다. 스킬 또는 필수 참고 자료가 없으면 완료를 주장하지 않아야 한다. 뜻이 불분명한 후보와 영어 보통명사 및 반복 결론은 고치되 정확한 전문용례, 사실, 요구사항과 필요한 비교 구조는 보존해야 한다. 변경 문서에는 대상 저장소의 식별 정보와 개인 정보가 없어야 한다.

필수 판정이 자동 판정과 사람 판정 사이에서 어긋나거나 세 실행에서 다른 상태가 나오면 사례를 보강한 뒤 같은 조합을 다시 세 번 실행한다. 두 차례 보정 뒤에도 엇갈리면 `needs human input`으로 보고하고 배포를 멈춘다. 새 사례가 기존 판정 질문으로 처리되고 파일별 책임, 실행 순서, 중단 조건과 완료 증거에 누락이 없을 때 현재 저장소 변경 검토를 마친다.

검수자는 모든 규칙 자료와 스킬 연결이 반영된 같은 커밋 및 입력으로 macOS에서 자체 검사와 대표 실행을 수행한다. 검사한 커밋의 식별자, macOS, Node 및 Git 버전, 명령, 종료 상태와 JSON 결과를 Pull Request 검토 기록이나 요구사항 소유자에게 전달하는 검증 보고에 남긴다. 검증 보고를 남기기 위해 검사한 커밋을 수정하지 않는다. 이 기록이 없으면 macOS 검증이나 현재 구현 완료를 주장하지 않는다. Linux와 Windows 동작은 이번 완료 증거에 포함하지 않는다.

후속 설치 작업의 호스트 호출 횟수, 설치 위치별 동작과 가림 쌍대 비교는 루트 README 및 대상 저장소 설치가 승인되고 끝난 뒤 검증한다. 현재 구현에서는 직접 스크립트 실행, 자체 검사, `SKILL.md`의 정적 연결과 macOS 검토 기록만 완료 증거로 사용하며 설치된 호스트의 동작을 확인했다고 주장하지 않는다.

### 12. 긴 문단을 경고하고 의미 단위별 분리 여부를 판정한다

[한국어 문서 검토 재발 방지 요구사항](./requirements.md)의 `목표`와 `완료 증거`에 따라 문단 길이를 검토 신호로 사용하되 글자 수나 문장 수만으로 실패를 확정하지 않는다. 한 문단에 서로 다른 중심 내용, 근거, 조건, 결정 상태 또는 후속 행동이 들어 있어 독자가 관계를 다시 구성해야 하면 각 의미 단위를 플레인 텍스트 문단으로 나눈다. 각 문단은 중심 내용을 먼저 밝히고 문단 사이의 적용 순서와 의존 관계를 유지한다.

긴 문단 탐지는 `long-paragraphs.mjs`가 맡고, `scan.mjs`가 `korean-expressions.mjs`와 이 모듈을 정적 import해 모든 정상 실행에서 함께 호출한다. 표현 검사와 긴 문단 검사는 공통 `sources`를 사용하되 각자 `id`, `catalog`, `rules`, `warnings`와 `summary`를 제공한다.

구현 전에 `docs/dev/node/mjs-cli.md`의 조건부 모듈 분리 지침을 승인된 파일명과 검사별 출력 상한에 맞추고 `eslint.config.mjs`도 함께 갱신한다. 기존 import 제한은 저장소의 다른 파일에 그대로 적용하고, `scan.mjs`의 정확한 위치에만 별도 설정을 둬 `./korean-expressions.mjs`와 `./long-paragraphs.mjs`의 정적 import를 허용한다. `scripts/**/*.mjs`처럼 이후 파일까지 포함하는 pattern으로 예외를 넓히지 않는다. 외부 package import와 동적 import 제한은 세 스크립트에서도 유지한다.

ESLint 정상 사례는 승인된 스크립트에서 허용한 상대 위치를 정적으로 가져와야 한다. 오류 사례는 같은 import를 대상 밖의 `.mjs` 파일에서 사용하거나 승인되지 않은 상대 위치, 외부 package 또는 동적 import를 사용해야 한다. 각 사례의 통과와 거부를 확인하기 전에는 import 제한 변경을 완료로 판단하지 않는다. 적용 기준은 [Node.js MJS 명령줄 검사기](../../dev/node/mjs-cli.md#고정된-두-탐지-모듈을-정적으로-가져온다)를 따른다.

`long-paragraphs.mjs`의 단일 `policy`에 문단 후보 기준을 둔다. Markdown 플레인 텍스트 문단이 일곱 문장 이상이면 문단 시작 위치, 관찰한 문장 수와 제한된 원문 일부를 경고로 출력한다. 이 값은 장문 기술 문서 지침에서 선택했지만 검사 대상인 모든 Markdown 산문 문단에 적용하는 초기 기준이며 오류 기준이 아니다. 한국어 글자 수나 영어 단어 수 기준은 추가하지 않는다. 후보가 있어도 종료 상태는 `0`이고, 출력에 같은 뜻의 `severity`나 `requiresReview` 필드를 반복하지 않는다.

문단은 빈 줄로 구분하고 단순 줄바꿈은 같은 문단으로 센다. 제목, 표, 목록, 인용문, HTML, front matter, fenced 및 들여쓴 코드처럼 플레인 텍스트 산문이 아닌 Markdown 블록은 문장 수 계산에서 제외한다. 외부 parser를 추가하지 않고 현재 구분할 블록을 결정적인 줄 검사와 fence 상태로 식별한다. 중첩된 Markdown 구조를 정확히 해석해야만 판정할 수 있는 입력은 후보를 만들지 않으며 의미 검토에서 계속 확인한다.

`src/AGENTS.ko.md`와 `src/AGENTS.en.md`의 일반 작성 규칙에는 의미 단위별 문단 분리와 길이 경고가 확정 판정이 아니라는 조건을 같은 뜻으로 추가한다. `skills/use-words-review/SKILL.md`는 스크립트가 알린 긴 문단의 전체 문맥을 읽은 뒤 중심 내용, 중요한 정보의 위치와 문단 사이의 관계를 판정하게 한다. `skills/use-words-review/references/korean.md`에는 여러 주제를 한 문단에 모은 실패 사례, 의미 단위별 플레인 텍스트 문단으로 나눈 정상 사례와 경고가 발생하지만 하나의 중심 내용을 설명하는 정상 사례를 둔다.

Markdown 결과물에서는 빈 줄로 구분된 문단인지 확인한다. 단순 줄바꿈은 통과 근거로 사용하지 않는다. 서로 대등한 항목을 열거하거나 실행 순서를 나타내는 경우에는 목록을 유지할 수 있지만, 근거와 판단 및 후속 행동의 관계를 설명해야 하는 산문을 목록으로 바꾸는 것만으로 통과시키지 않는다.

**완료 증거.** [한국어 답변 검토 평가 사례](./references/korean-review-evaluation-cases.md)의 사례 27부터 31까지를 실행한다. 여섯 문장인 사례 29에는 긴 문단 경고가 없어야 한다. 일곱 문장인 사례 30과 31에는 각각 경고 하나가 발생하고 스크립트는 `0`으로 끝나야 한다. AI는 같은 종류의 경고를 받은 사례 30을 `pass`, 사례 31을 `needs revision`으로 판정해야 한다. 여러 중심 내용을 한 문단에 모은 사례 27은 길이 경고 유무와 관계없이 `needs revision`, 의미 단위별로 분리한 사례 28은 `pass`여야 한다. 두 배포용 AGENTS의 작성 조건, `SKILL.md`의 검토 기준과 `korean.md`의 사례를 문장별로 대조하고, 문단 분리를 위해 사실, 근거, 결정 상태 또는 후속 행동을 삭제하지 않았는지 확인한다.

문단을 나누려면 새로운 역할, 결정, 순서나 인과 관계를 추정해야 하는 경우에는 `needs human input`으로 남긴다. 긴 문단 경고를 자동 수정이나 확정 오류로 승격하지 않으며 새로운 외부 의존성은 추가하지 않는다.

## 중단 조건과 사람의 판단이 필요한 항목

- 한국어 저장 결과물 작업에서 스킬을 찾을 수 없으면 설치 방법을 바로 추정해 바꾸지 않고 현재 설치 상태를 보고한다.
- 후보 표현이 정확한 전문용어인지 저장소 근거로 정할 수 없으면 단어를 임의로 바꾸지 않고 `needs human input`으로 남긴다.
- 기존 문구가 승인된 공개 표현인지 알 수 없으면 재사용하지 않고 승인 근거를 요청한다.
- `scan.mjs`에 허용할 두 정적 import만 정확히 구분하지 못하고 기존 import 제한을 더 넓혀야 한다면 구현을 멈추고 정적 검사 방식을 다시 검토한다.
- 모델이나 추론 설정을 바꾸려면 같은 평가 묶음의 비교 결과와 선택 권한이 필요하다. 이번 계획은 모델 교체를 승인하지 않는다.
- 원본 사례 집계를 다시 검증할 역할과 안전한 보관 방식은 이번 계획에서 정하지 않는다. 갱신한 체계를 적용한 뒤 후속 작업에서 다시 검토한다.

## 커밋 단위

변경은 실행 가능한 의존 순서로 나눈다.

1. 승인된 구현 기준을 담은 요구사항, 조사 자료와 이 계획
2. `skills/use-words-review/SKILL.md`, `references/korean.md`, `references/examples.md`, `scripts/scan.mjs`, `scripts/korean-expressions.mjs`와 `scripts/long-paragraphs.mjs`의 책임 재배치, 검사기 실행 연결과 자체 검사
3. `src/AGENTS.ko.md`, `src/AGENTS.en.md`의 중복 감축과 두 배포본 대조 결과
4. 현재 요구사항을 충족하는 데 실제 변경이 필요할 때만 `docs/designs/README.md`
5. 긴 문단 경고, 의미 단위별 문단 분리 기준과 대표 평가 사례
6. 전체 대표 실행에서 발견한 누락 보정과 최종 검증 결과

루트 `README.md`와 `README.ko.md`의 설치 안내는 후속 설치 작업을 승인받은 뒤 별도 커밋한다.

각 커밋 전에 변경된 공개 문구, 출처, U+00B7, 개인 경로, 비공개 식별자와 임시 표시를 확인한다. 한국어 문서는 `use-words-review`로 검토하고, 변경 단위가 통과하지 않으면 다음 단위로 넘어가지 않는다.
