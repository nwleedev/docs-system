# 한국어 글과 문구 판정 기준

한국어가 포함된 결과물에서만 이 자료를 사용하고, 여러 언어가 섞였으면 한국어 부분에만 적용한다. 검사 스크립트가 알린 후보는 금칙어가 아니다. 이 자료는 문자열 출현만으로 찾을 수 없는 문장과 문단의 뜻을 판정한다.

## 문맥을 판정하는 순서

문제처럼 보이는 표현과 목록에 없는 표현을 다음 순서로 판정한다.

1. 해당 분야에서 뜻이 정해진 전문용어, 제품명, API 이름 또는 코드 식별자인지 확인한다.
2. 문장이 가리키는 대상과 행동 주체를 한 가지로 식별할 수 있는지 확인한다.
3. 독자가 행동, 적용 조건과 그 결과를 이해할 수 있는지 확인한다.
4. 빠진 정보를 저장소 근거, 승인된 결정 또는 승인된 문구에서 확인할 수 있는지 확인한다.

근거가 문장을 그대로 뒷받침하면 `pass`다. 근거에서 정확한 대상, 주체 또는 행동을 확인해 새 판단 없이 고칠 수 있으면 `needs revision`이다. 필요한 뜻이나 책임 관계가 없거나 근거끼리 충돌하면 가능한 내용을 추측하지 않고 `needs human input`으로 판정한다.

## 낱말은 자연스럽지만 뜻이 번역체인 문장

한국어 낱말만 썼더라도 영어 문장의 주어와 명사 배열을 그대로 옮기면 행동과 관계가 사라질 수 있다. 무생물인 문서나 기능이 스스로 판단하거나 책임지는 것처럼 쓰지 않고, 실제로 값을 읽고 결정하고 기록하는 주체를 밝힌다. 여러 명사를 이어 붙인 표현은 명사 사이의 관계를 동사와 조사로 풀어 쓴다.

문제가 있는 문장:

> 이 문서는 입력 품질 향상과 오류 처리 개선을 수행한다.

- **판정:** `needs human input`
- **빠진 정보:** 누가 어떤 입력을 검사하는지, 오류가 나면 무엇을 바꾸는지 알 수 없다.
- **독자에게 생기는 영향:** 구현 담당자는 필요한 행동과 완료 조건을 정할 수 없다.

관계를 드러낸 문장:

> 변환기는 각 행의 날짜를 검사한다. 날짜 형식이 맞지 않으면 행 번호와 입력값을 오류 메시지에 기록하고 변환을 중단한다.

- **판정:** `pass`
- **확인 근거:** 행동 주체, 검사 대상, 실패 조건과 처리 결과가 차례로 드러난다.

평가만 더하는 수식어도 같은 방식으로 살핀다. 그 말을 빼면 사실, 조건이나 독자가 해야 할 일이 달라지지 않는다면 저장소 근거에서 실제 동작이나 측정값을 찾아 쓴다. 근거가 없으면 긍정적으로 들리는 표현만 남기거나 임의의 동작을 만들지 않는다.

## 행동 주체를 감추는 문장

피동문 자체를 일괄해서 고치지 않는다. 행위자를 밝힐 필요가 없는 상태 설명은 유지할 수 있다. 검토, 승인, 변경, 배포처럼 책임과 순서가 중요한 행동에서 주체가 빠지면 누가 무엇을 언제 해야 하는지 확인한다.

문제가 있는 문장:

> 검토가 끝나면 변경이 승인되고 배포가 진행된다.

- **판정:** `needs human input`
- **빠진 정보:** 검토 결과를 확인할 역할, 승인할 역할과 배포를 시작할 역할이 없다.
- **독자에게 생기는 영향:** 각 담당자는 자신의 행동과 작업을 시작할 조건을 알 수 없다.

주체와 순서를 드러낸 문장:

> 검수자가 변경 내용을 확인한다. 승인 책임자가 배포를 승인하면 배포 담당자가 배포를 시작한다.

- **판정:** `pass`
- **확인 근거:** 역할별 행동과 다음 행동을 시작할 조건이 이어진다.

## 한국어 문장에 섞인 영어 보통명사

서비스명, 애플리케이션 이름, API 이름, 명령, 코드 식별자와 저장소가 승인한 전문용어는 정확한 이름을 유지한다. 일반적인 역할, 단계, 상태나 판단을 영어로 병기하거나 한국어 문장에 섞을 때에는 영어가 뜻을 더 정확하게 만드는지 확인한다. 같은 뜻을 괄호로 반복하거나 영어 보통명사가 행동을 감추면 한국어로 다시 쓴다.

문제가 있는 문장:

> reviewer가 findings를 확인하고 approval owner에게 전달한다.

- **판정:** `needs revision`
- **고칠 근거:** 문서가 같은 역할과 산출물을 `검수자`, `승인 책임자`와 `검토 결과`로 정의한다.
- **독자에게 생기는 영향:** 영어 역할명이 기존 역할과 같은지 다른지 다시 추측해야 한다.

승인된 식별자를 유지한 문장:

> `Response.create` API가 오류를 반환하면 호출자는 응답의 오류 코드를 기록한다.

- **판정:** `pass`
- **유지 근거:** API 이름은 정확히 보존하고, 행동 주체와 실패했을 때의 동작은 한국어로 밝혔다.

## 기존 문서에서 이어받은 표현

작성에 사용한 기존 문서는 확인된 사실, 승인된 결정과 필요한 비교 구조를 제공할 수 있다. 기존 제목, 추상 명사, 영어 보통명사와 반복 결론은 그 문서에 있었다는 이유만으로 승인된 문체가 되지 않는다. 새 결과물의 독자, 행동 주체, 조건과 결과에 맞게 다시 쓴다.

문제가 있는 처리:

> 이전 문서가 사용한 제목과 결론을 새 문서에도 그대로 옮긴다.

- **판정:** `needs revision`
- **고칠 근거:** 기존 문서가 제공한 사실과 승인된 결정은 확인할 수 있지만, 문구의 재사용 승인은 없다.
- **독자에게 생기는 영향:** 새 문서의 독자가 알아야 할 행동과 조건보다 이전 문서의 짜임이 앞선다.

확인한 내용을 새 독자에게 맞춘 사례:

> 이전 조사에서 로그인 없이 읽을 수 있는 문서만 비교 대상으로 정했다. 새 조사도 같은 조건을 적용하고, 조사자가 문서 주소와 확인 내용을 기록한다.

- **판정:** `pass`
- **확인 근거:** 기존 자료의 비교 조건을 유지하면서 새 결과물의 행동 주체와 기록할 내용을 밝혔다.

## 내용과 무관하게 반복하는 글의 짜임

도입, 소제목 수, 목록 수, 문단 길이와 결론을 실제 내용에 따라 정한다. 다음 형태가 반복되면 독자가 새 정보를 얻는지 확인한다.

- 뒤의 내용을 예고할 뿐인 도입
- 실제 관계와 무관하게 만든 같은 수의 항목
- 소제목마다 같은 길이로 반복하는 문단
- 앞의 답을 다시 말할 뿐인 결론과 요약
- 문단마다 되풀이하는 같은 연결 표현

비교 대상마다 같은 속성을 같은 순서로 제시하면 독자가 차이를 확인할 수 있으므로 유지한다. 반대로 각 항목이 새 근거나 값을 제공하지 않으면 문단 수와 길이를 맞추지 않고 중복된 문장을 지운다.

필요한 비교 구조:

> 세 후보를 비용, 예상 기간과 실패 조건 순서로 비교하고 후보마다 확인한 값과 근거를 적는다.

- **판정:** `pass`
- **유지 근거:** 같은 순서가 비교를 돕고 각 후보가 서로 다른 값과 근거를 제공한다.

## 문장과 문단 사이에서 바뀌는 대상

문장 하나가 자연스러워도 지칭 대상, 역할, 가정 또는 결정 상태가 다음 문장에서 바뀔 수 있다. 다음 관계를 문단과 문서 전체에서 다시 확인한다.

- 대명사와 요약 표현이 가까운 문장에서 한 대상을 가리키는지
- 같은 역할 이름이 문서 전체에서 같은 책임을 맡는지
- 서로 다른 역할 이름의 관계가 근거로 확인되는지
- 제안, 검토 중인 선택과 승인된 결정이 구분되는지
- 앞 단계의 결과가 다음 단계를 시작할 조건으로 이어지는지
- 예외와 가정이 그것을 사용하는 행동보다 먼저 설명되는지

관계가 끊긴 문장:

> 검수자가 수정안을 제안한다. 담당자는 승인된 내용을 배포한다.

- **판정:** `needs human input`
- **빠진 정보:** 담당자가 누구인지, 누가 언제 수정안을 승인했는지, 승인된 내용이 수정안 전체인지 알 수 없다.
- **독자에게 생기는 영향:** 배포할 문구와 배포를 시작할 시점을 정할 수 없다.

관계를 드러낸 문장:

> 검수자가 수정안을 제안한다. 승인 책임자가 수정안을 승인하면 배포 담당자가 승인된 문구를 배포한다.

- **판정:** `pass`
- **확인 근거:** 제안과 승인을 구분하고, 승인 결과가 다음 행동의 조건으로 이어진다.
