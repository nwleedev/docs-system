# 수정 후 실제 UI 검증과 규칙 확정

수정한 코드로 실행한 최신 화면에서 사용자 선택과 합의한 조건을 확인한 뒤, 검증한 대상에 적용할 규칙만 확정한다. 생성 시안에 대한 선호와 실제 UI에서 검증한 규칙을 구분한다.

## 검증 시작에 필요한 자료

프로젝트 기록과 구현 입력에서 선택 근거, 유지할 특성, 기존 규칙, 임시 값과 예외, 합의한 대표 화면과 확인 조건을 읽는다. 이번 변경의 확인 조건이 정해져 있지 않으면 먼저 사용자와 정한다.

메인 세션이 수정한 코드로 실행한 화면인지 확인한다. 실행 주소나 화면 자료와 함께 어떤 변경을 반영한 화면인지 확인할 근거를 받는다. 현재 작업과 화면의 관계가 불명확하면 메인 세션에 재실행이나 최신 화면 제공을 요청한다.

생성 이미지, 빌드 성공 메시지, 명세 전달만 있거나 변경 전 스크린샷만 있으면 실제 UI 검증은 미완료다. 최신 화면을 직접 시각적으로 볼 수 없으면 확정 규칙 갱신을 보류한다. 확인 자료를 만들기 위해 이 스킬이 애플리케이션 코드를 수정하지 않는다.

## 변경한 화면에서 비교

대표 화면이나 컴포넌트를 직접 보고 선택한 특징이 유지되는지 확인한다. 정보 밀도, 타이포그래피, 간격, 형태, 색, 배경 구분 등 이번 변경에서 판단한 속성을 선택 근거와 비교한다. 외형이 같은 원칙을 따르는지, 레퍼런스에서 좋았던 선택이 프로젝트에서는 어색한지, 추가 판단이 필요한 속성이 있는지 사용자에게 보여준다.

변경의 영향을 받는 선택, 오류, 비활성, 키보드 초점 등의 상태를 살펴본다. 프로젝트가 사용하는 화면 크기, 테마와 언어 중 영향을 받는 조건도 합의한 기준에 따라 확인한다. 상태 전환을 확인해야 한다면 실행 UI를 조작하거나 그 전환을 확인할 수 있는 자료를 받는다. 정지 이미지 한 장으로 조작이나 모든 상태를 확인했다고 말하지 않는다.

화면이나 이미지와 함께 유지된 특징, 선택과 다른 부분, 확인하지 못한 조건을 짧게 설명한다. 사용자에게 시각적 판단을 확인받고 기록한다. 빌드와 기존 동작 검사는 메인 세션의 개발 절차에서 수행하며, 시각적 확인만으로 동작이나 접근성 전체를 검증했다고 보고하지 않는다.

## 재사용 확인과 차이 처리

공통 규칙으로 확정하려면 다른 기존 화면이나 컴포넌트에 같은 규칙을 적용한 모습을 확인한다. 규칙의 의미와 선택한 특징이 재사용 대상에서도 유지되는지 비교한다. 확인하지 않은 대상까지 적용된다고 일반화하지 않는다.

다른 대상이 아직 없으면 새 화면을 만들지 않고 확인한 대상에 한정된 규칙으로 남긴다. 재사용한 화면에서 차이가 발견되면 공통 규칙의 검증을 미완료로 남기고 차이를 기록한다. 대표 화면이 좋아 보인다는 이유로 공통 규칙까지 완료로 판단하지 않는다.

차이의 원인에 따라 다음 절차를 선택한다.

- 합의한 특성이 구현되지 않았다면 구현 입력으로 돌아가 메인 세션에 수정할 대상과 확인 조건을 전달한다. 수정 뒤 최신 UI로 다시 검증한다.
- 선호나 기존 원칙을 바꿔야 한다면 사용자 선택과 기록 절차로 돌아가 규칙 변경, 예외, 특정 대상 한정 또는 미결정을 확인한다. 기존 규칙을 임의로 약화하지 않는다.
- 필요한 상태나 화면을 볼 수 없다면 확인한 부분과 미확인 부분을 나누고 자료를 요청한다. 미확인 조건을 통과로 처리하지 않는다.

기존 규칙과 현재 화면으로 해결할 수 있으면 레퍼런스를 다시 찾지 않는다. 해결되지 않는 새로운 시각적 의문이 있을 때만 탐색 여부를 사용자와 확인한다.

## 검증한 규칙 기록

사용자가 확인한 시각적 판단과 실제 UI 검증 근거를 연결해 프로젝트 기록을 갱신한다. 규칙마다 사용 의미, 적용 대상과 조건, 검증한 화면과 상태, 선택 근거, 예외와 남은 차이를 읽을 수 있게 남긴다. 기록 방법은 `SKILL.md`의 사용자 선택과 기록 절차를 따른다.

확정 지침에는 검증을 마친 규칙과 그 적용 조건만 반영한다. 미결정, 임시 구현값, 확인하지 못한 상태와 재사용 차이는 따로 남긴다. 사용자 선호 확인만 끝난 값을 검증된 토큰으로 바꾸거나, 확인하지 않은 조건을 지워 완료된 것처럼 만들지 않는다.

사용 조건에 따라 디자인 원칙, 공통 속성, 용도별 규칙이나 토큰 중 필요한 수준으로 정리한다. 컴포넌트가 늘었다는 이유만으로 토큰을 추가하지 않는다. 규칙을 바꾸거나 추가하면 적용된 UI를 다시 확인하며, 실제 코드 반영은 메인 세션에 맡긴다.

## 화면 검증과 초기 디자인 시스템의 완료

한 화면의 검증 완료는 그 화면에서 합의한 조건을 확인했다는 뜻이다. 초기 디자인 시스템 전체의 완료로 확대하지 않는다.

초기 디자인 시스템은 현재 프로젝트에서 다음 근거가 확보되었을 때 완료로 판단한다.

- 다른 방향과 구별되는 시각적 특징을 설명할 수 있다.
- 현재 주요 실제 UI에서 선택한 특징이 일관되게 나타난다.
- 반복 사용하는 공통 속성과 용도별 규칙이 정리되어 있다.
- 현재 필요한 주요 UI를 기존 규칙으로 표현할 수 있다.
- 코딩 에이전트가 사용할 규칙, 적용 조건과 피할 스타일이 명시되어 있다.
- 새 화면에서도 기존 방향과 규칙을 재사용한 근거가 있어 처음부터 다시 정할 필요가 없다.

부족한 근거가 있으면 완료한 화면과 남은 확인을 분리해 보고한다. 모든 컴포넌트와 토큰을 만들거나 검증용 애플리케이션을 새로 만드는 일을 완료 조건으로 삼지 않는다. 완료 후에도 실제 요구가 없으면 시스템을 더 확장하지 않는다.

탐색 시간, 토큰 사용량이나 수정 횟수의 감소는 비교할 실제 작업과 기록이 있을 때만 평가한다. 지침이나 화면을 작성했다는 사실만으로 이런 성과를 입증했다고 말하지 않는다.
