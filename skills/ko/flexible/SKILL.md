# 요구사항 검토와 실행 플랜 작성

- **검토**만 요청받으면 요청된 판단과 근거를 제시한다. 판단을 내릴 근거가 부족하면 확인한 사실과 결론에 필요한 정보를 명시한다. 검토 결과는 답변으로 제공한다.
- **요구사항 작성 또는 보완**을 요청받으면 확인된 요구사항과 제약을 문서에 반영한다.
- **플랜 작성 또는 실행**을 요청받으면 아래 기준에 따라 플랜을 작성하거나 기존 플랜을 검토한다. 실행 요청을 받은 경우에만 확정된 단계 중 선행 조건을 충족한 단계를 수행한다.

파일 생성과 수정은 그 작업이 요청 범위에 포함될 때 수행한다.

## 현재 상태와 기존 결정 확인

저장소 최상위부터 요구사항, 설계, 플랜을 관리하는 문서와 규칙을 검색한다. 기존 규칙에서 정한 위치와 작성 방식을 준수한다. 요청에 요구사항, 결정 또는 플랜의 지속적인 기록이 포함되고 저장소에 문서 관리 규칙이 없으면 `docs/designs/README.md` 생성을 제안할 수 있다. 생성에 대한 동의가 확인되면 [설계 문서 안내](references/_README.md) 전문을 `docs/designs/README.md`에 복사한다. 첨부 파일과 프롬프트는 조회 자료로 사용하고 저장소에 복사하지 않는다.

요청, 요구사항 문서와 승인된 결정에서 원하는 결과와 제약을 식별한다. 코드, 테스트, Git 이력, 프로젝트 README, 인수인계 문서와 설계 기록에서 검토 대상이 현재 어떻게 작동하며 무엇이 바뀌었는지 확인한다. 저장소 자료로 해결할 수 없는 기술적 질문에 답할 때는 적용 버전과 실행 조건에 맞는 외부 자료를 조사한다.

확인한 실행 결과나 산출물을 완료 기준과 대조해 요구사항을 충족하는지 판단한다. 원인이나 수정 완료에 관한 주장을 검토할 때는 관찰 결과, 원인 추정, 수정 제안, 실행 후 검증 결과를 구분한다. 각 자료로 무엇을 확인했는지 명시한다.

## 요구사항 구체화와 실행 단계 확정 조건

실행 단계의 확정 여부는 다음 세 항목을 기준으로 판단한다. 각 항목의 근거가 되는 요청, 문서 항목 또는 승인된 결정을 식별한다.

1. **원하는 결과.** 어떤 사용 상황과 입력에서 무엇이 실행되어야 하고 어떤 결과나 산출물이 필요한지 명시한다.
2. **변경 대상과 제약.** 변경할 기능, 기능이 실행되는 조건이나 결과 또는 문서를 명시한다. 적용 대상에 따라 결과가 달라지면 포함하거나 제외할 서비스 사용자, 데이터 또는 사용 상황을 명시한다. 유지해야 할 기존 기능과 사용 방식, 준수할 제약을 기록한다.
3. **완료 기준.** 관찰할 실행 결과나 확인할 산출물과 검증 통과 조건을 명시한다. 정상 실행, 기존 기능과의 호환성 또는 실패 시 결과에 대한 요구사항이 있으면 각각의 기준을 명시한다.

세 항목의 근거를 확인하고 구현 방법을 선택하는 데 필요한 조사를 마친 단계만 확정한다. 외부에서 이용할 수 있는 기능이나 확인할 수 있는 결과를 추가하거나 변경 또는 제거하려면 각 변경이 기준 요구사항이나 승인된 결정에 근거하는지 확인한다. 기능의 실행 조건, 실패 시 결과, 화면에서 선택할 수 있는 기능도 확인한다. 근거가 없는 변경은 확정된 플랜에 넣지 않고 수행하지 않는다.

- **결정이 필요한 사항.** 결과, 변경 대상, 제약 또는 완료 기준이 불분명하거나 서로 충돌하면 기존 요구사항과 승인된 결정을 대조한다. 대조한 뒤에도 요구사항의 뜻을 확정할 수 없거나 기술적 제약으로 요구사항을 그대로 충족할 수 없으면 문제가 생기는 조건과 요청한 결과에 미치는 영향을 답변에서 직접 설명한다. 선택이 필요하면 선택지별로 무엇이 달라지는지 설명하고 질문한다. 답변에 의존하는 단계는 미확정으로 표시하고 필요한 결정을 명시한다. 답변에 의존하지 않는 단계는 별도로 계획할 수 있다.
- **조사로 확인할 사항.** 요구사항이 확정됐고 기술적 사실이나 구현 방법이 정해지지 않았다면, 변경 판단에 필요한 코드, 인터페이스 또는 실제 실행 결과를 조사한다. 구현 단계가 조사 결과에 의존하면 조사에서 확인할 사실과 확인 방법을 먼저 명시하고, 결과를 확인한 뒤 구현 단계를 확정한다. 같은 요구를 충족하는 방법이 여럿이면 확인한 근거와 제약에 맞춰 선택한다.
- **이미 충족한 요구사항.** 현재 기능의 실행 결과나 산출물을 완료 기준과 대조한다. 충족이 확인된 항목은 검증 근거를 제시하고 변경 대상에서 제외한다.

### 예시

- **내보낼 항목을 결정해야 하는 경우.** “책 검색 결과를 파일로 내려받고 싶어요.” 현재 페이지에는 10권이 표시되고 전체 검색 결과는 12권이다. “파일에는 현재 페이지의 10권을 포함할까요, 전체 검색 결과 12권을 포함할까요?”라고 묻는다. 기존 내보내기 기능이 파일에 어떤 항목을 담는지는 먼저 확인할 수 있다. 내보내기 범위의 구현 단계와 완료 기준은 답변 후 확정한다.
- **가상의 공방 예약 확인증.** 예약이 확정되면 확인증 인쇄에 실패해도 예약 번호를 표시하라는 요구사항이 있다면, 인쇄 성공을 번호 표시의 조건으로 삼지 않는다. 인쇄 실패 시 번호를 표시해야 하는지 요구사항과 승인된 결정에서 확인할 수 없다면 답변에서 “인쇄에 실패해도 예약 번호를 표시해야 하나요?”라고 묻는다. 확인증을 이메일로 보내는 기능을 추가할 근거가 없다면 플랜에 넣지 않고 구현하지 않는다.
- **저장소를 조사하면 계획할 수 있는 경우.** “Windows와 macOS 설치 안내를 한 문서로 모아 주세요.” 두 안내의 준비 절차와 설치 명령을 대조한다. 일치하는 절차는 한 번만 설명하고 서로 다른 명령은 운영체제별로 안내하도록 계획한다.
- **변경 없이 충족하는 경우.** 검색된 책 12권 전체를 내보내 달라는 요청이 있으면 기존 기능으로 생성한 파일을 연다. 두 페이지의 책 제목을 파일과 대조해 12권이 모두 포함된 것으로 확인되면, 파일 생성 방법과 대조 결과를 제시한다.

## 실행 플랜 작성

1. 플랜에 원하는 결과와 유지할 제약을 명시한다. 각 단계에 변경 대상, 수행할 작업과 그 근거가 되는 요구사항 또는 결정을 명시한다. 한 단계에서 외부에서 이용할 수 있는 기능이나 확인할 수 있는 결과를 여러 가지 바꾼다면 각 변경의 근거를 기록한다. 근거 문서가 있으면 그 문서의 항목을 링크한다.
2. 선행 단계의 어떤 산출물이나 검증 결과가 필요한지 명시하고 실행 순서를 정한다. 미확정 단계에는 남은 질문 또는 조사 항목과 확정 조건을 기재한다.
3. 각 단계에 예상 산출물, 검증 방법과 통과 조건을 명시한다. 최종 검증에는 요청 범위에 포함된 요구사항과 유지할 제약 각각의 확인 방법을 포함한다. 외부에서 이용할 수 있는 기능과 확인할 수 있는 결과를 변경 전후로 비교한다. 실제 변경 사항마다 기준 요구사항이나 승인된 결정에서 근거를 확인한다.

### 예시

- **두 운영체제의 설치 안내를 한 문서로 통합하는 플랜.** 두 README를 살펴보니 준비 절차는 같고 설치 명령은 서로 다르다. 기존 명령과 실행 순서를 유지하고 두 README 어디서든 통합 설치 안내를 찾을 수 있어야 한다는 조건이 정해졌다. 이때 제시할 플랜은 다음과 같다.
  1. 신규 설치 문서에 공통 준비 절차를 한 번만 설명하고, 설치 명령은 Windows용과 macOS용으로 나누어 안내한다. 원본과 대조해 각 운영체제에서 실행할 명령과 그 순서가 모두 보존됐는지 확인한다.
  2. 신규 설치 문서를 작성한 뒤, 각 README의 중복 설명을 해당 운영체제의 설치 안내로 바로 연결되는 링크로 바꾼다. 각 README의 링크를 열었을 때 해당 운영체제의 설치 명령이 표시되는지 확인한다.

## 플랜에 따라 실행하고 갱신하기

실행을 시작하거나 재개할 때 기준 요구사항, 기존 결정과 최신 플랜을 참조한다. 기록된 진행 상태를 실제 산출물 또는 검증 기록과 대조하고 선행 조건을 충족한 확정 단계부터 진행한다.

단계별 검증을 마치거나 실행이 중단될 때 완료 여부, 실제 검증 결과와 근거, 남은 작업과 재개 조건을 갱신한다. 플랜 문서에 기록하거나, 대화에서 플랜을 제공한 경우에는 대화에서 변경된 진행 상태를 보고한다. 단계별 통과 조건을 충족한 단계만 완료로 표시한다. 전체 완료는 최종 검증으로 판정한다.

- **구현 방법 변경.** 확정된 요구사항 안에서 방법을 변경할 때는 새로 확인한 사실과 변경 이유를 기록한다. 영향을 받는 단계, 선행 조건과 검증 항목을 갱신한다.
- **요구사항 변경.** 결과, 변경 대상, 제약 또는 완료 기준을 변경해야 하면 변경 내용, 영향을 받는 단계와 검증 항목을 명시한다. 변경 사항이 요청에 명시되어 있으면 그 요청을 근거로 사용한다. 결정이 필요하면 [실행 단계 확정 조건](#요구사항-구체화와-실행-단계-확정-조건)의 결정 확인 절차를 적용하고 영향을 받는 단계만 보류한다. 변경이 확정되면 수정 권한이 있는 요구사항 문서에 먼저 반영하고 플랜을 갱신한다. 요구사항 문서가 없거나 수정할 수 없으면 확정된 변경 사항을 대화에 기록하고 그 결정을 플랜에 반영한다.

구현 방법이나 요구사항의 변경으로 효력을 잃은 검증은 다시 수행한다.

### 예시

- **실행 중 링크가 끊긴 경우.** 설치 안내를 옮긴 뒤 설정 예제 링크를 열었더니 파일을 찾을 수 없다. 예제 파일은 그대로 있고 문서 위치가 바뀌어 상대 주소가 달라졌다면, 플랜에 링크를 고치는 절차를 추가한다. 기존 README의 링크를 따라 설치 안내를 연다. 안내에 있는 설정 예제 링크를 선택했을 때 원래 예제 파일이 열리는지 확인한다.
- **실행 중 원하는 결과가 바뀐 경우.** “설치 방법은 두 문서에 그대로 두고, 저장소 첫 화면에서 둘 다 찾을 수 있게 해 주세요”로 요청이 바뀌면 본문을 합치는 절차를 중단한다. 이미 옮긴 내용이 있는지 확인한다. 각 README에 해당 운영체제의 설치 방법을 유지하고 저장소 첫 화면에 두 README의 링크를 표시하도록 플랜을 수정한다. 첫 화면의 각 링크가 해당 README를 여는지, 기존 설치 절차가 모두 남아 있는지 확인한다.

## 요구사항 문서를 작성하거나 보완할 때

같은 주제의 요구사항 문서가 있는지 먼저 확인한다. 문서가 없거나 별도 문서 작성 요청이 명시되어 있으면 새 파일을 생성한다. 그 밖의 경우에는 기존 문서에서 요청받은 부분만 수정한다.

새 파일이 필요하고 저장소가 `docs/designs/README.md`의 문서 구성을 사용하면 아래 스크립트로 주제 폴더와 빈 `requirements.md`를 생성할 수 있다. 스킬 디렉터리에서 Node.js 22.0.0 이상으로 실행한다. 내용 작성도 요청받았으면 생성 후 작성한다.

```sh
node scripts/requirements/create.mjs --repo <repository-root> --topic <topic-slug>
```

`--help`를 단독으로 지정하면 필수 인자와 실행 실패 시 확인할 사항이 표시된다. 기존 문서를 갱신할 때는 스크립트를 다시 실행하지 않는다. 조사와 결정 기록용 디렉터리는 보관할 문서가 생길 때 생성한다.
