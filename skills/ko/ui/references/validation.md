# 실행 중인 UI 검증과 적용 범위별 규칙 확정

최신 실행 화면의 목표 달성, 일관성, 완성도와 구별되는 특징을 확인한다. 확정된 범위 안에서 직접 확인한 규칙만 확정한다.

## 근거와 범위 확인

현재 구현에 넘길 자료의 시나리오, 보존할 기능, 방향, 규칙, 제안, 예외와 대상을 사용한다. 확인 조건이 없으면 [검증 조건](implementation.md#검증-조건-정의)을 읽는다.

실행 중인 UI나 제공된 화면 근거가 평가할 변경을 반영하는지 확인한다. 실행 중인 HTML 시안과 운영 애플리케이션을 구분한다. 모의 구현으로 백엔드 동작을 입증할 수는 없다. 불분명하면 현재 근거를 요청하거나 그 검사를 미룬다. 규칙 확정 전에 [화면 검사](#화면의-네-측면-검사)와 [차이와 재사용](#차이-해결과-재사용-검증)을 따른다.

## 화면의 네 측면 검사

### 목표 달성과 행동 순서

대표 시나리오를 성과에 도달할 때까지 따라간다. 주 행동을 찾기 쉬운지, 정보가 제때 제공되는지, 상태와 다음 행동을 알려 주는지, 반복 행동과 위험 행동에 확인이나 복구 수단이 있는지 확인한다. 상호작용이나 시연 근거로 전환을 검증하고 관찰한 어려움과 조건을 기록한다. 시각 확인만으로는 전체 동작의 정확성이나 측정된 사용성 개선을 입증할 수 없다.

지정된 상호작용 자체를 확인한다. 접근성 대안은 필수 드래그를 보완할 수 있지만 대신하지 않는다. XPath 수정에서는 일치한 대상에 요청이 반영됐고 새로고침 뒤에도 영향을 받는 다른 행동이 작동하는지 확인한다. XPath와 의도한 대상이 다르면 추정한 대체 대상을 검증하지 말고 수정을 보류한다.

### 시각적 일관성

영역과 필요한 상태를 글자, 간격, 정렬, 밀도, 배경과 패널 표현, 행동 강조와 컴포넌트 표현에 비춰 비교한다. 차이에는 시나리오나 상태에 따른 이유가 있어야 한다. 라이브러리 기본 스타일은 허용된다. 선택한 방향과의 불일치가 결함이다.

### 완성도

전체 구성, 읽을 수 있는 해당 분야의 내용, 실제 정보량, 긴 글, 영향받는 상태와 필요한 크기, 테마와 언어를 확인한다. 잘림, 빠진 상태, 임시 내용, 설명 없는 간격과 미완성 영역을 조건별로 기록한다. 뷰포트 하나로 반응형 동작을 추정하지 않는다.

[서비스 내용 규칙](implementation.md#서비스-내용에-집중한-화면)을 적용한다. HTML은 의도한 서비스로 읽혀야 한다. 숨겨진 검토 모드를 포함해 시안 소개, 검토 도구나 작성 과정 설명이 없어야 한다.

문구를 일괄 제거하지 말고 의미와 유용성으로 판단한다. 필요한 도움말, 상태, 오류와 접근성 정보는 보존한다. 중복 면책 문구, 보고, 설계 이유와 불분명한 표현은 고친다. 미해결 구현 한계는 대화에서 설명한다.

키보드 조작, 의미 구조에 따른 접근성이나 기준 준수를 주장하려면 상호작용 또는 필요한 독립 검사를 확보한다. 시각 확인만으로는 충분하지 않다.

### 구별되는 특징

설계 논지와 해당 분야의 제약으로 구조, 계층과 강조를 설명한다. 장식 이상의 구별되는 선택과 그 근거를 밝힌다. 목록, 카드와 사이드바도 시나리오로 정당화되면 사용할 수 있다. 이 판단만으로 모든 서비스와의 차별성이나 측정된 사용성 개선을 입증할 수는 없다.

화면을 확정된 테마 특징과 피할 표현에 대조한다. 명시적 요구 없이 SaaS 디자인이 들어오지 않았는지 확인한다. 관계와 행동이 모두 텍스트와 버튼으로 축소되지 않고 적합한 시각 형식을 사용하는지 살핀다. 다양성을 늘리려고 임의의 이미지를 추가하지 않는다.

## 차이 해결과 재사용 검증

현재 시각 자료와 함께 보존한 특징, 차이와 미검증 조건을 제시한다. 방향이나 선호 확인이 필요하면 [비교](decisions.md#선택-요청과-답변-해석)를 통해 범위를 정한 시각 판단을 받는다.

- 필수 특징 누락: 결함, 대상과 조건을 구현에 넘길 자료로 돌려보내고 수정한 현재 화면을 다시 확인한다.
- 설계 논지로 구조나 시나리오를 설명할 수 없음: 영향을 받는 근거와 그 안의 미해결 근거 질문만 다시 검토한다.
- 기존 규칙과 충돌: [충돌 처리](decisions.md#질문-필요-여부-판단)를 사용한다.
- 상태, 화면이나 상호작용 누락: 검증한 부분과 미검증 부분을 나누고 근거를 요청한다.

기존 규칙과 화면으로 차이를 해결할 수 있으면 사용한다. 공통 규칙을 확정하기 전에 적용할 수 있는 다른 기존 대상을 확인한다. 없으면 해당 대상에만 적용한다. 재사용 시 차이가 미해결이면 공통 검증은 미완료로 유지한다.

현재 근거, 확정된 판단, 확인한 대상과 상태, 이유, 예외와 남은 차이를 규칙과 함께 반환한다. 최종 지침에는 검증한 규칙과 조건만 넣는다. 제안, 추정, 미해결 선택과 재사용 시 차이는 구분해 둔다. 원칙, 공통 특징, 시나리오별 규칙이나 토큰 중 필요한 방식으로 표현한다. 규칙이 바뀌면 영향받는 적용 부분을 다시 확인한다.

## 화면 검증과 초기 시스템 완료 구분

디자인 시스템 완료를 평가할 때만 이 절을 읽는다. 화면 하나로는 충분하지 않다. 현재 주요 화면들이 설명 가능한 일관된 방향을 표현해야 한다. 반복되는 규칙과 시나리오별 규칙이 주요 화면에 적용돼야 한다. 구현 조건과 피할 특징이 명시돼야 한다. 새 화면에서도 매번 모든 결정을 처음부터 하지 않고 그 방향을 재사용할 수 있어야 한다.

근거가 없으면 검증한 화면과 남은 시스템 조건을 따로 보고한다.
