# 테마 조사와 근거 확인

본격 서비스 시안을 만들기 전에 시나리오에 맞으면서 눈에 보이는 차이가 있는 테마 방향을 찾고 근거를 확인해 비교할 수 있게 한다.

## 조사 필요 여부 판단

새 UI 방향에서는 첫 본격 시안 전에 테마를 검색하고 비교한다. 기존에 검증한 규칙, 표준과 플랫폼 관례는 검색의 제약 조건이며 요청한 테마 비교를 대신하지 않는다. 방향이 확정됐거나 수정 대상이 한정됐으면 새로 생긴 미해결 질문만 조사한다. 표준이 불확실하면 공식 지침이 필요하며 서비스 사례를 반드시 더 찾아야 하는 것은 아니다.

탐색 전에 확인할 수 있는 보류 피드백과 차수를 살핀다. 피드백이 보류됐으면 [이어가기](decisions.md#현재-문맥에서-이어가기)를 읽는다. 추가 비교를 찾기 전에는 [차수 한도](decisions.md#차수-계산과-탐색-종료)를 읽는다.

조사가 필요하면 [전략 탐색](#적합한-전략-탐색)으로 이어서 근거를 확인하고 분석한다. 새 방향이면 [테마 비교](#테마-비교-제시)를 제시한다.

## 적합한 전략 탐색

탐색 전에 [조사 시작 조건](#조사-필요-여부-판단)으로 보류 피드백과 남은 차수를 확인한다.

시나리오, 원하는 인상, 정보 관계, 밀도, 분야와 입력 또는 뷰포트 조건으로 서비스 화면과 디자인 사례를 모두 검색한다. 거의 같은 서비스 화면만 찾지 말고 필요한 편집 디자인, 그래픽, 타이포그래피, 사진이나 일러스트 사례로 넓힌다. 가능한 검색 방향이지 채울 할당량은 아니다. 결과가 같은 배치나 표현을 반복하면 색만 바꾸지 말고 디자인 분야나 구성 전략을 바꾼다.

테마는 계층, 글자, 이미지, 구성과 분위기가 일관된 방향이다. 이 시나리오에 어떻게 적합할지 비교한다. 완성된 서비스 템플릿으로 취급하거나 무관한 시각 속성을 절충하지 않는다. 후보를 고를 때 스킬 본문의 SaaS 제외 조건을 적용한다. 익숙한 목록, 버튼이나 사이드바를 모두 SaaS 테마로 분류하지 않는다.

검색으로 사례와 최신 1차 자료를 찾는다. 공식 지침, 코드, Storybook, 명세나 필요한 이슈가 여기에 포함된다. 검색 결과는 단서다. 플랫폼별 지침은 적용 가능 여부를 확인한 뒤 채택한다.

의미 있는 대안을 근거로 구분할 수 있거나, 후보가 같은 전략을 반복하거나, 더 검색해도 쓸 수 있는 근거를 얻지 못하면 멈춘다. 후보 수를 고정하지 않는다. 필수 미답변 질문은 미해결로 유지한다. 외관을 주장하기 전에 [화면 확인](#실제-화면-확인)을, 전략 비교 전에 [분석](#분석-비교와-적용)을 읽는다.

## 테마 비교 제시

볼 수 있는 원자료에 출처 링크와 실제 관찰한 특징을 함께 제시한다. 중요한 차이, 각 방향이 시나리오에 맞거나 충돌하는 지점과 지금 필요한 구체적인 선택을 설명한다. "minimal"이나 "editorial" 같은 이름, 색상 목록이나 긴 설명으로 시각 자료를 대신하지 않는다.

전문 용어를 요구하지 않고 관찰한 특징 중 유지하거나 피할 것을 묻는다. 비교는 서비스 HTML 밖에서 한다. [답변 해석](decisions.md#선택-요청과-답변-해석)을 따르고 답변을 기다린 뒤에만 방향을 확정된 것으로 취급한다. 어느 방향도 수락되지 않았으면 승인된 것처럼 화면을 만들지 말고 미해결 선택과 남은 차수를 보존한다.

## 실제 화면 확인

사용 가능한 Browser 또는 MCP 시각 기능으로 렌더링된 외관, 상호작용, 반응형 변화와 로그인 상태를 확인한다. 접근 가능한지 확인한다. 데스크톱과 원격 환경은 인증, 로컬 접근과 상호작용이 다르다. 디자인 작품은 시각 표현의 근거가 될 수 있지만 출시한 서비스의 동작 근거는 아니다. 한 비교에 함께 나오더라도 이 차이를 유지한다.

전체 화면을 먼저 보고 필요한 영역, 컴포넌트, 구조, 요소와 상태를 질문에 필요한 깊이까지만 확인한다. 서비스와 화면, 출처 위치, 볼 수 있는 근거, 관찰 조건과 갤러리 자료의 출처를 보존한다. 정지 이미지로 숨은 상태나 전환을 입증할 수 없다.

로그인은 로그인 화면에서 진행한다. 채팅에서 자격 증명을 요구하지 않는다. 실패하면 확인하지 못한 화면이나 상태, 필요한 기능과 관찰한 실패를 밝힌다. 허용됐을 때만 대체 수단을 시도한다. 지정한 서비스를 말없이 바꾸지 않는다. 필수 근거를 계속 얻을 수 없으면 현재 스크린샷, 녹화, 지원되는 접근 방법이나 확인 연기를 요청한다.

## 분석, 비교와 적용

각 사례의 문제, 정보 관계, 행동 배치와 반복, 상태, 밀도 및 필요한 시각 선택을 근거와 조건으로 분석한 뒤 비교한다. 설계 논지에 비춰 중요한 장단점을 비교한다. 사례를 절충하는 대신 대안과 불확실성을 보존한다.

각 전략에 채택인 `adopt`, 수정해 적용하는 `adapt`, 제외인 `reject`, 미해결인 `unresolved` 중 하나를 반환하고 이유, 근거와 대상을 적는다. 설계 논지의 잘못된 가정은 고친다. 승인과 충돌하면 [질문 분류](decisions.md#질문-필요-여부-판단)를 따른다. 새 방향이면 [테마 비교](#테마-비교-제시)를 제시한다. 그 밖의 의미 있는 대안에는 [비교 절차](decisions.md#선택-요청과-답변-해석)를 사용한다. 방향이 정해지면 요청한 시안이나 구현에 넘길 자료로 이어간다.

보고된 동작, 위험이나 문서와의 불일치 때문에 필요할 때만 공식 이슈나 변경 이력을 조사한다.
