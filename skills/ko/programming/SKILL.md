# 구현 방법 조사와 설계 판단

요청한 결과를 어떤 코드와 구조로 구현할지 제안하고, 그 선택이 프로젝트의 제약을 충족하는 이유를 설명한다. 기본 범위는 조사와 조언이다. 소스 코드, 테스트, 설정 또는 도구의 변경에는 명시적인 구현 또는 개발 요청이 필요하다.

## 요구사항과 기존 동작 확인

1. 실제 사용 상황에서 기대하는 결과와 유지해야 할 조건을 확인한다. 이미 확인한 요구사항과 답변을 활용한다. 프로젝트 이름이나 비교 대상에서 추론한 기능은 조사할 질문으로 취급한다. 저장소에 `docs/dev/README.md`가 있으면 현재 요청에 적용할 개발 지침을 확인한다. 조사 착수에 별도 README, 스킬, 플랜 또는 정해진 문서 구조를 요구하지 않는다.
2. **기존 구현이 있으면** 요청 한 건을 기준으로 호출자가 전달하는 입력, 실행되는 함수, 저장값이나 반환값, 실패 시 응답을 추적한다. 관련 파일, 타입, 버전과 실행 조건을 식별하고 조사 범위와 선정 이유를 설명한다. 문서, 테스트와 호출자가 의존하는 동작을 대조해 호환 조건을 확인한다. 기존 테스트가 내부 호출 순서를 재현한다는 사실만으로 그 순서를 유지할 의무가 생기지는 않는다.
3. **구현 전이면** 예상 입력, 필요한 결과, 실패 시에도 지켜야 할 조건에서 설계 질문을 도출한다. 제안한 구조와 실제로 확인한 구현을 구분한다. 저장소에서 확인할 수 있는 사항은 먼저 조사한다. 선호가 정해지지 않았거나 선택에 따라 사용자에게 제공할 동작이 달라지면 선택지별 영향과 권장안을 제시하고 의사를 확인한다.

## 구현 방법을 결정하는 기준

구현 선택에 영향을 주는 항목을 조사한다. 조사할 질문에 답하는 명세, 공식 문서, 연구 논문, 소스 코드 또는 실패 기록을 선택한다. 자료에서 설명한 조건을 프로젝트의 버전과 실행 환경에 대조한다.

- **코드와 모듈.** 요구사항별로 어떤 함수가 입력을 검증하고 어느 모듈이 값을 저장하거나 반환하는지 설명한다. 변경할 파일, 함수, 타입과 재사용할 부분을 구분하고 그 이유를 제시한다. 예를 들어 파일과 표준 입력에 같은 검사 규칙을 적용한다면 입력을 수집하는 함수는 각각 지정하고, 수집한 텍스트의 검사는 같은 함수에 위임할 수 있다. 입력 방식이 추가될 때 어느 파일을 수정해야 하는지 확인한다.
- **디자인 패턴.** 반복되는 구현이나 독립적으로 변경되어야 할 부분을 식별한다. 기존 함수를 활용하는 방법과 패턴을 적용하는 방법을 비교한다. 다음 요구사항이 추가되면 각 방법에서 어떤 코드가 변경되는지, 호출 관계와 유지보수 비용은 어떻게 달라지는지 설명한다. 패턴의 명칭만으로 도입 효과를 단정하지 않는다.
- **서비스 코드의 가독성.** 설명 주석이 필요해 보이면 이름을 구체화하는 방법과 함수나 데이터 구조를 변경하는 방법을 비교한다. 기존 동작을 유지하면서 이름과 구조만으로 호출 순서와 가능한 상태를 이해할 수 있는 설계를 선택한다. 예를 들어 업로드 중과 완료가 동시에 성립할 수 없다면 두 불리언 값의 조합을 주석으로 제한하기보다 하나의 업로드 상태로 표현하는 방법을 검토한다.
- **서비스 코드의 주석.** 실행이나 프로젝트 도구의 작동에 필요한 주석만 작성한다. JSDoc은 프로젝트에서 사용하는 도구가 해당 표기를 읽고, 생략하면 필요한 타입 검사나 산출물이 달라지는 경우에만 작성한다. 함수 이름이나 구현 순서를 반복하는 설명은 생략한다.
- **시스템 아키텍처.** 변경이 프로세스, 서비스 또는 저장소 사이의 통신에 영향을 주면 요청 한 건을 기준으로 어느 구성 요소가 무엇을 전송하고 어디에서 상태를 갱신하는지 설명한다. 예를 들어 접수와 실행을 별도 프로세스가 담당한다면 접수 직후 실행이 중단됐을 때 요청이 보존되는지, 재시도 시 같은 요청을 두 번 실행할 수 있는지 확인한다. 모듈 내부 변경으로 해결할 수 있으면 시스템 재설계를 전제하지 않는다.
- **컴퓨터과학 원리.** 데이터 표현, 동시성, 중복 연산, 접근 권한 또는 자원 사용량이 판단에 영향을 주는 조건을 조사한다. 예를 들어 UTF-8 문자 하나의 바이트가 서로 다른 입력 조각에 포함될 수 있다. 각 조각을 독립적으로 해석하는 방식과 디코더 상태를 유지하는 방식이 같은 문자열을 반환하는지 비교한다. 어떤 입력에서 차이가 발생하고 어떤 관찰로 설명을 검증하거나 반박할 수 있는지 제시한다.

조사 초기부터 문제 발생 지점의 코드만 수정하는 방법과 원인이 되는 저장, 조회, 연산 순서 또는 통신 방식을 변경하는 방법을 함께 검토한다. 필수 동작과 오류 응답을 보존할 수 있는지 먼저 확인하고, 선택에 영향을 주는 실행 시간, 메모리 사용량, 디스크 접근 횟수나 전송량, 저장 공간, 기존 방식에서 제안한 방식으로 전환할 때의 위험을 비교한다. 수정할 파일 수나 대안 수를 선택 기준으로 삼지 않는다.

원리의 배경은 해당 원리가 어떤 문제를 해결하며 왜 이 프로젝트에 적용되는지 이해하는 데 필요한 만큼 설명한다. 프로젝트의 실제 도입 이유는 설계 문서, 이슈와 버전 이력에서 별도로 확인한다. 확인할 수 없는 과거 결정이나 승인 사유는 추정하지 않는다.

## 권장안과 검증 방법 제시

조사 후 첫 답변에서 권장하는 구현 방법과 이유를 제시한다. 현재 착수할 수 있는 단계와 각 단계의 어떤 선행 조건이 충족됐는지 설명한다. 보류할 단계가 있으면 먼저 확인할 정보나 결정할 사항을 명시한다. 착수 조건과 전체 요구사항의 완료 기준은 별도로 명시한다.

- **구현 예시.** 프로젝트의 버전, 타입, 호출 관계와 개발 규칙에 맞는 간결한 코드 예시로 실행 순서와 선택 이유를 설명한다. 호출자에게 필요한 반환값, 저장할 값, 실패 시 응답을 포함한다. 코드 변경이 필요하지 않다면 요구사항과 기존 구현을 대조해 그 이유를 설명한다. 같은 판단을 설명할 수 있으면 무관한 객체, 테스트 데이터, 스크립트나 애플리케이션을 추가하지 않는다.
- **코드 스타일 문서의 예제.** 사용자 요청이나 해당 문서의 작성 지침에서 예제 주석을 명시적으로 허용한 경우에만 작성한다. 허용된 주석은 독자가 예제의 동작을 이해하는 데 필요한 부분에 한정한다. 그 밖의 설명은 코드 블록 밖의 본문에 작성한다.
- **검증.** 어떤 입력에서 어떤 결과를 확인하면 요구사항이 충족되는지 설명한다. 테스트가 필요하면 적합한 테스트 종류와 작성 방법을 조사하고, 단언문으로 실제 검증 대상의 결과를 확인하는 예시를 제시한다. 테스트가 불필요하면 이유를 설명한다. 공식 문서 및 소스 코드와 대조한 내용, 모의 응답, 실제 실행 결과를 구분한다. 실행하지 않은 코드 예시에는 ‘미실행’이라고 표시한다. 예시를 제시했다는 이유로 파일 생성이나 검사 실행을 요구하지 않는다.
- **비용과 위험.** 중요한 위험이 발생할 조건과 영향을 받는 동작을 설명한다. 그 위험을 판단할 때 확인한 사실과 아직 검증하지 않은 가정을 구분하고, 위험을 완화할 방법을 제시한다. 측정값, 가정에 따른 추정치와 아직 측정하지 않은 효과를 구분한다. 이 스킬의 호출만으로 측정 실행이 허용되지는 않는다. 기한과 자원 한도가 제시된 경우에만 그 조건을 완료 예상에 반영한다.

답변의 분량과 표현 방식은 요청에 맞춘다. 단순한 변경에 무관한 조사를 추가하지 않는다. 구성 요소의 관계를 그림으로 설명할 필요가 있으면 사용 가능한 도구와 편집기에서의 가독성을 확인한다. 마지막에는 확인한 동작, 전체 완료에 필요한 후속 절차와 미결정 사항을 명시한다.

## 근거가 부족하거나 조건이 변경된 경우

- 대안을 제외할 때는 어떤 제약을 충족하지 못하는지, 무엇을 확인해 그렇게 판단했는지 명시한다. 호환 여부나 효과를 확인하지 못했으면 어떤 사실이 확인될 때 추천이 달라지는지 설명한다. 요청된 조사 범위에서 어떤 대안을 권장할지와 그 이유를 설명할 수 있거나, 결정을 위해 추가로 확인할 정보를 특정하면 조사를 마친다. 불확실성을 변경 권한으로 해석하지 않는다.
- 조사에서 확인한 기술적 제약 때문에 저장소 규칙을 적용할 수 없거나, 조사에서 권장하는 방법이 저장소 규칙과 다르면 해당 결정을 보류한다. 충돌하는 조건과 필요한 선택을 설명하고 독립적인 조사는 계속한다. 제안과 승인된 결정을 구분한다.
- 추가로 확인한 내용이 기존 결함, 불분명했던 요구사항, 기술적 제약, 기능 추가 제안 중 어디에 해당하는지 구분한다. 그 내용이 기존 구현안에 어떤 영향을 주는지 설명한다. 요구사항 추가를 제안한다면 기존 요구 중 어느 결과를 달성할 수 없는지 설명하고 같은 결과를 달성할 다른 방법도 비교한다. 필수 절차를 생략하거나 위험을 근거로 기능을 임의로 추가하지 않는다.
- 요구사항이 같더라도 가정이 달라지면 구현 가능성, 남은 단계와 소요 자원, 선행 조건과 완료 예상을 재검토한다. 저장소의 변경 절차가 있으면 따른다. 별도 절차가 없으면 대화나 지정된 문서에서 영향을 설명한다. 영향을 받지 않은 검증 결과는 유지한다. 합의한 결과나 제약을 변경해야 하면 동의를 구한다.

## 문서 기록과 조사 재개

기술 판단은 대화에서 설명할 수 있다. 문서 기록이 필요하면 지정된 파일과 저장소의 문서 관리 규칙을 확인한다. 파일 지정이 없으면 적합한 위치와 이유를 제안한다. 지정된 파일이 없거나 수정할 수 없으면 대화에서 초안과 위치 후보를 제시하고 허용된 조사를 계속한다. 대화에 제시한 초안과 저장된 문서를 구분한다.

지정된 문서에만 그 목적에 맞춰 기록한다. 요구사항 문서에는 의도한 동작과 제약을, 플랜에는 절차와 검증 방법을, 참고 문서에는 원리와 출처 및 적용 조건을 기록한다. 기존 설명을 참조할 수 있으면 해당 위치를 안내한다. 기술 제안을 승인된 요구사항으로 기록하지 않는다. 자료 보관에도 파일 지정 조건을 적용하며, 별도 조사 파일이나 임시 파일을 임의로 생성하지 않는다.

조사를 시작하거나 재개할 때, 다음 설계 결정을 검토하기 전에는 지정된 기록에서 목적, 유지할 조건, 비교한 대안, 선택 이유, 가정, 예시와 미해결 질문을 확인한다. 이전 결정의 가정이 지금도 성립하는지 확인한 후 후속 판단에 적용한다. 대화 기록의 압축 여부와 관계없이 이 기준을 적용한다. 기록 위치가 지정되지 않았으면 조사 재개용 파일을 생성하지 않는다.
