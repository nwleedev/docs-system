# 설계 문서

이 디렉터리는 한 대화나 pull request가 끝난 뒤에도 이해할 수 있어야 하는 요구사항, 근거, 결정과 플랜을 보관한다. `requirements.md`는 요구사항 책임자가 관리한다. AI는 검토, 조사, 승인된 결정 기록, 계획과 검증을 할 수 있지만 요청한 성과를 만들어내거나 말없이 고쳐서는 안 된다.

## 묶음과 문서 구성

```text
docs/designs/
  README.md
  <topic>-<short-id>/
    requirements.md
    references/
      <research-topic>.md
    decisions/
      <decision-topic>.md
    plan.md
```

세션, 기여자나 pull request가 달라져도 문맥이 유지돼야 할 때만 묶음을 만든다. 모든 묶음에는 `requirements.md`가 있다. 새 묶음 준비 단계에서는 빈 파일이어도 된다. 필수 정보가 갖춰지기 전에는 구현 기준이 아니다.

참고, 결정과 플랜 파일은 아래의 생성 조건을 충족할 때만 만든다. 빈 디렉터리나 임시 내용을 만들지 않는다. 폴더에는 주제를 설명하는 이름과 충돌을 피할 수 있는 짧은 ID를 사용한다. 같은 목적의 확장에는 그 폴더를 재사용한다.

문서는 산문 중심이며 고정 템플릿이 없다. 필수 정보를 보존하고 금지 내용을 제외하며 필요한 검사를 통과하면 제목과 순서를 달리 정할 수 있다.

## 모든 문서의 규칙

- 작성 전에 문서 종류, 대상 독자와 독자가 내려야 할 결정 또는 행동을 확인한다. 요구사항, 결정, 검토와 실행의 책임이 다르면 역할을 구분해 밝힌다. 근거에서 책임 역할을 확인할 수 없으면 임의 배정하지 말고 `needs human input`으로 보고한다.
- 요구사항, 출처가 있는 사실, 분석, 제안, 승인된 결정과 미해결 질문을 분명히 구분한다. 한 요청에서 나왔더라도 무관한 주제는 각각을 관리하는 문서에 둔다.
- 독자에게 전달할 주장은 확인된 저장소 근거, 출처가 있는 조사, 승인된 결정이나 승인된 문구를 사용한다. 프롬프트, 에이전트 지침, 진행 메모, 요청한 형식, 도구 조건, 진행 보고와 추적하지 않는 메모는 진행을 위한 입력이며 게시할 근거로 보지 않는다.
- 요구사항 책임자가 관리하는 요구사항, 승인된 화면 문구, 인용, 프롬프트 처리 평가 자료, 최소 재현 입력이나 접근을 제한한 미추적 로그처럼 정확한 원문이 필요한 경우에만 보존한다. 필요한 부분만 남긴다.
- 내용을 설명하는 제목 하나와 논리적인 제목 계층을 사용한다. 각 절에서 배경보다 결론이나 결정을 먼저 쓰고 한 주제에 집중한다.
- 표를 쓰지 않는다. 순서 없는 항목은 글머리표를, 순서나 우선순위만 숫자를 사용한다. 반복 항목을 비교할 때는 항목마다 하위 절을 두고 해당 속성을 같은 순서로 제시한다. 빈 항목이나 반복 결론은 쓰지 않는다.
- 외부 링크는 내용을 설명하는 이름으로 뒷받침하는 주장 옆에 둔다. 여러 출처가 한 주장을 뒷받침하면 비교한 결론과 출처별 확인 사실을 적는다. 다른 주장을 뒷받침하는 출처는 구분한다. 끝에 무관한 링크 목록을 남기지 않는다.
- 기준이 되는 요구사항, 결정, 근거나 지침은 여러 파일에 복사하지 말고 연결한다. 상대 파일 링크와 내용을 설명하는 제목으로 요구사항, 플랜, 참고와 결정을 연결한다. 별도의 문서나 항목 ID를 부여하지 않는다. 공통 근거는 원래 파일에 둔다. 실제 도구나 검토 절차가 사용할 때만 메타데이터를 추가한다.
- 대상 독자에게 자연스러운 언어를 사용한다. 독자나 승인된 형식이 정확한 형태를 요구하지 않으면 직역, 근거 없는 칭찬, 장식 기호와 낯선 표기를 제거한다.
- 자격 증명, 개인 위치, 비공개 URL, 비공개 프로젝트 식별자와 가공하지 않은 민감 로그를 추적 문서에 넣지 않는다. 저장소 상대 위치와 안정적인 공개 URL을 우선한다. 안전하지 않은 요구사항 문구는 말없이 고치지 말고 요구사항 책임자에게 알린다.

## `requirements.md`

### 권한과 생성

요구사항 생성이나 보완 요청은 명시된 성과와 조건을 최소한으로 작성할 권한을 준다. 적절하면 같은 목적의 기존 문서를 재사용한다. 빈 문서를 명시적으로 요청하면 파일만 준비한다. 검토만 요청했으면 수정할 수 없다. 상세 작성은 제공한 요구사항의 설명을 넓히며 요청 범위를 넓히지 않는다.

의미, 수량, 조건, 예외와 의무 수준을 보존한다. 프롬프트나 대화 이력을 복사하지 말고 요구사항을 쓴다. 명시된 성과, 유지돼야 할 조건, 관찰 가능한 완료 근거와 명시된 미해결 질문만 포함한다. 빠진 요구사항을 추론하거나 조사와 제안을 승인으로 취급하지 않는다. 영향을 받는 내용을 바꾸기 전에 충돌이나 빠진 뜻을 보고한다.

요청한 구조 편집은 의미를 바꾸지 않고 제목, 문단과 순서를 재구성할 수 있다. 근거 없는 절은 빈 제목이나 임시 내용으로 만들지 말고 생략한다. 준비한 빈 파일은 완성된 요구사항 문서가 아니다. 정보가 없으면 그 정보에 의존하는 진행만 막힌다. 요청이 충분한 기준을 제공하면 영향 없는 일은 계속할 수 있다.

### 필수 정보

- 의도한 성과
- 반드시 성립해야 하는 조건
- 완료를 보여 줄 관찰 가능한 근거
- 요청한 동작을 바꿀 미해결 질문이 있으면 그 질문

### 금지 내용

- AI가 추론했지만 요구사항 책임자가 승인한 것처럼 제시한 요구사항
- 관찰 가능한 근거 없는 완료 표현
- 요구사항 책임자의 승인 없이 필수 성과로 제시한 구현 선택
- 기존 구현을 준수하는 것처럼 보이게 하려고 추가한 지시

### 검토

파일 전체를 읽고 모호함, 모순, 빠진 완료 근거, 검증할 수 없는 표현과 동작을 바꾸는 미답변 질문을 확인한다. 진행을 막는 질문, 선택적 제안, 사실 조사 질문과 결정 책임자의 판단이 필요한 결정을 구분한다. 요구사항 책임자의 의도를 대신 확정하거나 평가하면서 말없이 수정하지 않는다.

## `references/*.md`

현재 대화 뒤에도 사실 조사나 저장소 근거를 재사용할 때 참고 문서를 만든다. 지속적으로 넘길 문맥이 필요하지 않은 간단한 사실 확인은 대화에 둔다.

### 필수 정보

- 조사 질문과 그 조사가 필요해진 요구사항 영역 또는 명시적 맥락
- 출처와 확인한 날짜 또는 리비전
- 각 사실 옆에 둔 내용을 설명하는 출처 링크
- 출처가 직접 뒷받침하는 사실
- 근거 비교로 도출한 결론
- 한계, 충돌, 미해결 불확실성과 요구사항, 결정이나 계획에 미치는 영향

중요한 주장에는 최신 공식 문서, 표준과 소스 저장소를 우선하고 독립된 1차 자료와 교차 확인한다. 외부 지침과 저장소가 다르면 어느 한쪽이 자동으로 옳다고 하지 말고 차이를 설명한다.

### 금지 내용

- 출처 있는 사실처럼 제시한 근거 없는 주장
- 승인된 결정처럼 제시한 분석
- 승인받지 않은 새 요구사항
- 어떤 주장을 뒷받침하는지 알 수 없는 출처
- 조사 결과처럼 제시한 요청 문구, 진행 보고, 검토 지시나 비공개 환경 정보

## `decisions/*.md`

진행에 중요한 영향을 주고 나중에도 이해할 수 있어야 하는 승인된 선택에만 결정 기록을 만든다. AI는 선택지를 준비할 수 있고 결정 책임자가 결과를 승인한다. 선택이 요청한 성과를 바꾸면 영향을 받는 진행을 재개하기 전에 요구사항 책임자가 `requirements.md`를 갱신한다.

### 필수 정보

- 결정이 필요한 질문
- 결정이 충족해야 할 요구사항 영역과 성과
- 실제로 검토한 중요한 선택지
- 승인된 결정과 그 이유
- 예상 영향, 플랜에 미치는 영향과 재검토 조건

### 금지 내용

- 승인처럼 제시한 AI 권고
- 만들어낸 승인 근거
- 승인 문구보다 넓거나 좁은 결정
- `requirements.md`를 말없이 덮어쓰는 결정
- 결정 질문, 이유나 결과처럼 제시한 요청 문구 또는 구현 보고

## `plan.md`

실행 계획이 필요하고 동작을 바꾸는 모호함과 필수 결정이 해결됐을 때만 `plan.md`를 만든다. 조사만 하는 소규모 묶음에는 플랜이 필요하지 않다.

### 필수 정보

- 기준 `requirements.md`의 위치와 적용할 제목
- 진행 단위에 연결한 요구사항 영역과 성과
- 의존 관계와 실행 순서 및 각 선행 조건 없이는 후속 단계가 무엇을 하거나 확인할 수 없는지에 대한 설명
- 단위별 관찰 가능한 검증과 전체 성과를 달성하는 데 남은 연결
- 미해결 차단 요인과 명확한 중단 조건
- 이후 변경이 실행에 영향을 줄 수 있는 `docs/dev/`의 적용 파일

플랜의 첫 커밋 전에는 검토한 파일을 잠정 기준으로 삼는다. 이후에는 `plan.md`를 마지막으로 바꾼 커밋의 버전을 기준으로 삼는다. Git 객체 ID나 타임스탬프를 기준 식별자로 기록하지 않는다. 플랜을 바꾸고 커밋하면 요구사항과 나열한 개발 지침을 다시 검토했다는 뜻이다.

플랜에서 구현 절차를 고를 수는 있다. 모든 필수 성과와 보존할 동작은 진행 및 검증에 연결하거나 차단됐다고 밝혀야 한다.

시작 선행 조건과 최종 수용 기준을 구분한다. 미해결 선택은 그 선택에 의존하는 진행만 막는다. 일상적인 구현 선택을 위해 모든 프로젝트 세부 사항을 미리 확정할 필요는 없다. 완료 예상을 판단할 때는 명시된 기한과 자원 한도를 고려한다. 추정의 근거와 불확실성을 설명한다. 근거가 부족하면 날짜를 만들어내지 않는다.

### 금지 내용

- 구현 절차로 위장한 새 요구사항
- 해결된 사실처럼 제시한 가정
- 관찰 가능한 근거를 밝히지 않은 모호한 검사
- 구현 근거 대신 문서만으로 한 완료 주장
- 플랜 내용으로 사용한 요청 문구, 도구 지시, 진행 설명, 검토 형식이나 비공개 환경 정보

## 검증

각 속성을 신뢰성 있게 판단할 수 있는 검사 중 비용이 가장 적은 것을 사용한다.

- 해당 검사가 있으면 저장소 도구로 배치, 필수 파일, 빈 파일이나 디렉터리, 미해결 임시 표시와 저장소 상대 링크를 확인한다.
- AI는 필수 정보, 모호함, 모순, 근거의 뒷받침, 요구사항 반영 여부와 가독성을 확인한다.
- 요구사항 책임자는 요구사항을 확인하고 동작을 바꾸는 질문에 답한다. 결정 책임자는 결정을 승인한다. 담당 검토자는 도구로 판단할 수 없는 의도한 동작과 장단점을 판단한다.

적용할 기준마다 `pass`, `needs revision`, `needs human input`, `not applicable` 중 하나로 보고하고 짧은 인용이나 파일 위치를 근거로 제시한다. 근거가 없으면 추론하지 말고 없다고 밝힌다. 검토와 재작성은 별도 행위다.

추가하거나 변경한 참고 문서, 결정과 플랜은 대상 독자의 관점에서도 최종본을 읽는다. 각 사실 주장과 결정 이유를 허용된 출처와 대조한다. 비공개 정보를 검사한다. 제목과 구조가 문서를 만든 요청이 아니라 주제를 설명하는지 확인한다.

문서는 의도와 근거를 기록하며 구현 준수를 입증하지 않는다. 구현 근거에는 적용할 lint, 타입 또는 스키마 검사, 테스트, 실행 중 검사와 담당 검토자의 판단을 사용한다.

## 진행 중 요구사항 변경

허용된 요구사항이 바뀌거나 새 근거로 구현 가능성, 노력, 의존 관계나 완료에 대한 플랜의 가정이 무효가 되면 이 절차를 사용한다. 먼저 관찰한 사실과 추론을 구분한다. 이슈가 결함, 불분명한 의도, 기술 제약 또는 능력 추가 제안 중 무엇인지 확인한다. 이는 조사를 위한 구분이며 필수 분류명이나 자동 요구사항 추가 규칙이 아니다.

1. 허용된 동작이나 제약 변경을 `requirements.md`에 기록한다. 채팅에만 남은 서술은 지속적으로 쓸 갱신이 아니다. 요구사항이 같으면 보존하고 새 근거와 영향을 기존 플랜이나 적합한 보충 기록에 쓴다.
2. 현재 요구사항과 새 근거를 `plan.md`를 마지막으로 바꾼 커밋의 기준과 비교한다.
3. 영향받는 참고, 결정, 진행 단위와 검증 방법 및 영향받지 않는 것과 여전히 유효한 완료 근거를 확인한다. 명시된 기한이나 자원 한도에 비춰 남은 노력, 순서와 전체 완료 예상을 다시 판단한다.
4. 영향받는 진행은 멈춘다. 영향 없는 진행은 여전히 요구사항을 충족할 때만 계속한다. 요청한 성과나 제약을 바꾸는 선택은 그 책임자와 해결한다. 이전 추정을 유지하려고 필수 동작을 말없이 제거하지 않는다.
5. 영향을 받는 파생 문서를 갱신하고 검토한 플랜을 커밋한 뒤 해당 진행을 재개한다. 새 근거가 플랜을 바꾸지 않으면 일을 만들어내지 말고 수정이 필요 없는 이유를 설명한다.

모든 진행을 자동으로 처음부터 다시 하거나 완료된 내용에 맞춰 요구사항을 고쳐 쓰지 않는다.

## 필요할 때만 구조 추가

- 참조가 불안정해지기 전에 모호한 제목이나 책임을 분명히 한다.
- 디렉터리를 훑어보기 어려워질 때만 참고 자료나 결정 색인을 추가한다.
- 실제로 사용하는 도구가 있을 때만 기계가 읽는 메타데이터를 추가한다.
- `plan.md`와 실제 변경을 함께 검토하기 어려울 때만 반영 여부나 완료 여부를 확인할 별도 기록을 추가한다.

묶음의 내용을 복사하지 말고 이슈와 pull request에서 연결한다. 요구사항, 출처, 결정, 의존성이나 구현 근거가 바뀌면 문서를 다시 확인한다.
