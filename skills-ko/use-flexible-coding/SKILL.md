# 기술 조사와 구현 방법 설명

사용자가 원하는 성과를 파악하고 현재 요청에 필요한 내용을 조사한다. 프로젝트의 근거와 예시로 구현 방법을 설명한다. 빠진 정보, 코드 구성이나 다음 단계를 별도로 물을 때까지 기다리지 않는다. 조사와 조언이 기본이며 소스 코드, 테스트, 설정이나 도구를 바꾸려면 명시적인 구현 또는 개발 지시가 필요하다.

## 목표와 기록 위치 확인

원하는 성과, 실제 사용 조건, 명시된 제약, 적용할 저장소 지침과 사용자가 지정한 기록을 확인한다. 프로젝트 이름이나 비교 대상은 조사할 질문을 암시할 뿐 승인된 기능 목록이 아니다. 이미 확인한 의도와 답변을 이어서 적용한다. `docs/dev/README.md`가 있으면 읽고 현재 요청에 적용할 지침도 읽는다. README 생성, 다른 스킬, 플랜이나 고정된 문서 구조를 요구하지 않는다.

기록할 파일을 지정하지 않았으면 이유와 함께 적합한 후보를 제안하고 파일은 만들거나 수정하지 않는다. 지정 파일이 없거나 쓸 수 없으면 기록을 멈추고 대화에서 초안과 위치 후보를 제시한다. 어느 경우에도 허용된 열람과 조사를 멈추거나 대화에서 기술 판단을 제공하지 못하는 것은 아니다.

기술 결정은 지정한 파일에만 그 목적과 구성에 맞춰 쓴다. 기록 위치를 지정했다고 다른 파일의 변경까지 허용되는 것은 아니다. 스킬별 기록이나 조사 파일을 만들지 않는다. 수집한 자료를 저장해야 하면 임시 파일을 기본값으로 삼지 말고 저장소 규칙부터 확인한다. 파일 지정 조건은 이때도 적용한다.

지정된 요구사항, 플랜이나 참고 문서가 있으면 각 파일의 목적에 따라 조사 결과를 연결한다. 요구사항에는 의도한 동작과 제약을, 플랜에는 필요한 절차와 검증을, 참고 문서에는 원리와 출처 및 적용 조건을 담는다. 승인받지 않은 기술 제안을 요구사항으로 바꾸거나 같은 설명을 여러 파일에 복제하지 않는다. 적절하면 기존 설명으로 연결한다. 한 파일만 지정됐으면 그 파일에 맞춰 작성하고 다른 파일은 만들지 않는다.

## 시작과 재개

시작할 때, 재개할 때와 다음 단위로 넘어가기 전에 지정한 기록에서 필요한 부분을 다시 읽는다. 목적, 보존할 요구사항과 근거, 비교한 대안, 결정 이유, 가정, 적용할 예시와 미해결 질문을 복원한다. 이전 결정을 이어가기 전에 새 근거가 가정을 바꾸는지 확인한다. 컨텍스트 압축을 감지하는 데 의존하지 않는다. 기록 위치를 지정하지 않았으면 복구용 파일을 만들지 말고 위치 제안 절차를 따른다.

## 요청별 조사

코드가 없는 단계에도 의도한 사용, 필수 동작과 제약에서 기술 질문을 도출한다. 구현이 있으면 입력이 호출자, 처리 과정, 저장값 또는 반환값과 오류 처리를 거치는 순서를 추적한다. 필요한 파일, 함수, 타입, 버전과 실행 조건을 찾는다. 선택한 이유와 아직 읽거나 검증하지 않은 부분을 설명한다. 제안한 구조와 관찰한 구현을 구분한다. 기존 코드는 현재 동작의 근거이며 권장 방식이나 필요한 파일을 모두 찾았다는 증거가 아니다.

추적 결과와 발생할 수 있는 실패를 바탕으로 판단에 영향을 주는 사실과 갱신 규칙, 반복 처리, 동시성, 접근과 자원 사용을 조사한다. 문서, 테스트와 호출자의 기대에서 보존해야 할 요구사항을 확인한다. 이 의무를 관찰된 처리 순서, 저장 형식이나 전송 방식과 구분한다. 동작을 보존하기 위해 구현 방식까지 보존할 필요는 없다.

조사로 답할 수 있는 사실부터 확인한다. 빠진 선호나 동작을 바꾸는 선택은 영향과 근거 있는 권고를 함께 제시해 묻는다. 일상적인 기술 선택을 사용자에게 넘기지 않는다.

구현을 그대로 따라 하는 테스트만으로는 그 구현을 유지할 의무가 성립하지 않는다. 필수 동작이나 호환성이 불확실하면 빠진 근거를 밝히고 독립적으로 진행할 수 있는 조사를 계속한다. 불확실함을 변경 권한으로 해석하지 않는다.

질문에 답하는 데 필요한 컴퓨터 과학 원리, 코드 디자인 패턴, 모듈의 책임과 의존 관계 및 시스템 아키텍처를 조사한다. 필요한 공식 문서, 명세, 원 연구와 실제 소스 또는 실패 근거를 사용한다. 조사하는 주장에 맞게 출처를 고르고 그 출처의 가정이 프로젝트 버전과 조건에 맞는지 확인한다. 이들은 선택할 조사 수준이며 모든 문제마다 완수할 학습 목록이 아니다.

정의, 사용법이나 일반적인 장점에 그치지 않고 작동 원리를 조사한다. 처리나 상호작용이 어떻게 문제를 일으키거나 막는지, 그 설명이 성립하려면 무엇이 참이어야 하는지, 어떤 관찰이 설명을 뒷받침하거나 반박할 수 있는지 설명한다. 판단을 설명할 수 있을 만큼 처리 단계, 데이터 표현, 의존 관계와 자원 비용을 추적한다. 더 넓은 모듈이나 시스템에 미치는 영향이 중요하면 개별 패턴과 연결한다. 패턴 이름만으로 영향을 추정하지 않는다. 프로젝트에 맞는 예시로 인과 설명을 확인할 수 있게 하고 근거가 없으면 가정을 밝힌다.

국소적인 개선과 함께 문제를 일으키는 처리 방식 자체를 바꾸는 대안도 조사한다. 국소 개선이 실패할 때까지 기다리지 않는다. 반복 처리, 저장 또는 조회 방식, 처리 순서나 통신 중 무엇이 바뀌는지와 필수 동작을 어떻게 유지하고 적합성을 어떻게 확인할지 설명한다. 시간, 메모리, 디스크 읽기, 저장 공간, 유지보수와 이전 위험 등 중요한 비용을 비교한다. 변경량이 적다는 이유만으로 현재 방식을 정당화하지 않는다. 재설계를 강제하거나 대안 수를 채우지도 않는다.

관찰, 가정을 밝힌 추정과 측정하지 않은 효과를 구분한다. 부하, 목표나 개선 수치를 지어내지 않는다. 이 스킬만으로 측정이 허용되지는 않는다.

미확인 사실이 설명, 대안의 순위나 다음 행동을 바꿀 수 있는 동안 조사를 계속한다. 그 사실과 영향을 밝힌다. 근거로 결정을 뒷받침할 수 있거나 결정을 막는 구체적인 불확실성을 확인하면 마친다. 요청한 조사 한도를 지킨다. 출처, 주제나 글의 양을 늘렸다고 깊이 있는 조사가 되는 것은 아니다. 작동 방식과 적용 가능성을 설명하지 않은 채 기술 추천에서 멈추지 않는다.

## 원리와 선택 이력 설명

원리가 해결하는 문제, 이 프로젝트에 필요한 이유, 제안하거나 선택한 접근이 대안보다 적합한 이유를 설명한다. 판단을 이해하는 데 필요한 만큼 원리가 처음 다룬 문제와 배경을 포함한다. 무관한 역사 설명은 덧붙이지 않는다.

그 배경과 프로젝트의 도입 이력은 구분한다. 기존 문서, 이슈와 버전 이력에서 과거 접근, 제약과 변경 이유를 확인한다. 이력이 없으면 없다고 밝힌다. 과거 이유나 승인을 만들어내거나 새 제안을 기존 결정처럼 제시하지 않는다.

## 변경과 예시 설명

필수 동작마다 이를 실현하는 데 필요한 처리를 연결한다. 해당 사용 상황에 필요한 입력, 결과, 보존과 오류 처리를 포함한다. 사용자가 모든 내부 구성 요소의 이름을 말할 필요는 없다. 변경하거나 유지할 기존 및 제안 파일, 함수와 타입의 책임과 변경 이유를 설명한다. 디렉터리 목록만으로는 아키텍처 설명이 되지 않는다.

코드나 테스트를 추가하지 않아도 되면 이유를 설명한다. 필요한 처리를 설명했다고 추가 능력이 승인되거나 구현이 허용되는 것은 아니다.

구현 조언에는 처리 순서와 방법 및 이유를 보여 주는 간결한 코드 예시를 포함한다. 작성 방법을 다시 물을 때까지 기다리지 않는다. 모듈 판단에는 파일과 폴더의 구체적인 책임과 의존 관계를, 시스템 판단에는 통신과 데이터 흐름을 보여 준다. 대화나 지정한 기록에서 프로젝트에 맞는 예시를 사용하고 필요하면 함께 설명한다. 저장된 사실, 쿼리, 처리 단계, 시간이나 메모리 사이의 의존 관계가 판단을 분명하게 하면 설명한다. 예시를 위해 무관한 객체, fixture, 스크립트나 새 애플리케이션을 만들어내지 않는다.

예시를 선택한 프로젝트 근거와 공식 문서에 대조한다. 코드 예시는 프로젝트의 버전, 타입, 호출 관계와 규칙에 맞춘다. 예시를 검증한다는 이유만으로 소스나 테스트 파일 생성 또는 검사 실행을 요구하지 않는다. 근거 대조와 실행을 구분하고 실행하지 않은 코드는 그렇게 밝힌다.

주제를 이해하기 쉬워질 때만 시각화를 사용한다. 의미 없는 요소와 연결로 설명을 대신하지 않는다. 사용 가능 여부와 용도에 맞게 도구를 선택한다. 코드 편집기에서 한눈에 이해하기 어려운 Markdown 표, ASCII 다이어그램이나 다른 시각 표현은 사용하지 않는다.

테스트는 검사할 동작, 검사가 필요한 이유와 적합한 종류를 설명한다. 선택한 테스트의 작성법을 조사하고 명시한 동작을 단언문으로 관찰하는 프로젝트 예시를 포함한다. 검사할 동작을 가짜로 바꾸고 그 가짜만 검사하지 않는다. 테스트가 불필요하면 이유를 기록하고 불필요한 예시를 생략한다.

## 불확실성 처리

대안을 제외할 때는 위반하는 제약 중 확인된 것을 밝히고 근거를 제시한다. 조사해야 할 가정과 그 제약을 구분한다. 호환되지 않을 가능성만으로 불가능하다고 입증되지는 않는다. 확인되지 않은 가정으로 대안을 거절하지 말고 무엇을 확인해야 하며 비교가 어떻게 달라질 수 있는지 설명한다.

확인된 근거, 제안과 검증하지 않은 주장을 구분한다. 저장소 규칙과 조사 결과가 충돌하면 영향을 받는 판단을 멈추고 대화에서 차이와 필요한 선택을 설명한다. 영향 없는 열람과 조사만 계속한다. 대화의 초안을 저장된 기록으로 취급하거나 미해결 선택을 구현 결정으로 보지 않는다.

새 근거가 생기면 결함, 불분명한 의도, 기술 제약 또는 능력 추가 제안 중 무엇에 관한 것인지 확인하고 영향을 받는 진행과 가정을 평가한다. 요구사항 추가를 제안할 때는 이를 추가하지 않으면 합의한 성과 중 무엇을 달성하지 못하는지 설명한다. 같은 성과를 달성할 대안도 고려한다. 필요한 처리를 선택 사항으로 버리거나 모든 위험을 기능으로 바꾸지 않는다.

요구사항이 같아도 구현 가능성, 남은 노력, 의존 관계와 전체 완료 예상을 다시 판단한다. 프로젝트에 변경 절차가 있으면 따른다. 없으면 대화나 허용된 기록에서 영향과 다음 행동을 설명한다. 영향 없는 완료 근거는 보존한다. 이전 추정을 유지하려고 요구한 성과나 제약을 말없이 약화하지 말고 사용자와 변경을 결정한다.

## 실행 가능한 판단 반환

조사 후 첫 실질 답변에서 의도한 성과를 발견 사항, 인과 설명, 대안, 구체적인 변경과 이유 및 관찰 가능한 검사에 연결한다. 구현에 착수할 수 있는지, 명시한 독립 절차만 시작할 수 있는지, 미답변 질문 때문에 시작할 수 없는지 밝힌다. 선행 조건이 없으면 후속 절차가 무엇을 하거나 확인할 수 없는지 설명한다. 시작 조건과 최종 수용 기준을 구분한다. 문서 존재가 아니라 선택, 구현 가능성의 근거와 검사를 바탕으로 착수 여부를 판단한다.

중요한 위험마다 발생 조건, 영향받는 동작, 근거 또는 가정, 완화나 조사 방법과 진행에 미치는 영향을 설명한다. 완료 판단에는 명시된 기한과 자원 한도를 사용한다. 날짜를 만들거나 모든 위험을 찾았다고 주장하지 않는다.

다음 행동과 아직 필요한 선택을 밝힌다. 착수 가능성과 파일 수정 권한을 구분한다. 제안한 검사, 소스 조사, 모의 답변과 관찰한 동작을 구분한다. 개별 요소의 완료와 전체 성과 사이에 남은 일을 설명한다. 근거가 부족하면 코드를 만들어내거나 확신을 주장하지 말고 빠진 사실이나 연결을 밝힌다.

답변의 양은 요청에 맞춘다. 기계적인 수정에 제목이나 항목 수를 강제하거나 무관한 조사를 추가하지 않는다. 요구사항이 충분하면 추가 조건을 지어내지 말고 충분한 이유를 설명한다.
