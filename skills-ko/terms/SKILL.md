# 다양한 종류의 텍스트에서 모호한 표현 교정

파일을 작성할 때 파일의 예상 독자를 먼저 확인하고 독자 입장에서 이해할 수 있는 글을 작성하는 것이다.

파일 작성 후 파일의 목적, 의도, 내용을 보존하면서 텍스트 작성에 사용된 용어 및 표현을 더 적절한 표현으로 교체한다.

## 검토 대상

리뷰 대상을 특정 문서로 제한하지 않는다.

텍스트 작성에 사용된 용어 & 표현을 리뷰해야 하는 대상은 다음과 같다.

- 프로젝트에서 관리되는 파일
- 프로젝트에서 특정 작업을 위해 임시로 생성되는 파일
- 커밋 메시지 및 커밋 상세

## 작성 전 확인

글을 작성하기 전 다음을 확인한다.

- 프로젝트 상세 정보, 제약 조건, 현재 상황을 파악한다.
- 글을 작성하는 목적, 글의 역할
- 예상 독자, AI를 포함하지 않음.

## 표현 검토 기준

글을 작성할 때에는 다음과 같은 원칙을 준수한다.

### 반복과 추상적인 표현

- 구체적인 내용이 없는 예고를 사용하지 않는다.
- 상투적인 연결 표현을 사용하지 않는다.
- 같은 결론을 반복하지 않는다.
- 항목의 개수를 고정시키지 않는다.
- 추상 명사, 추상 수식어를 사용하는 대신 구체적인 표현을 사용한다.

### 문장과 문단 구성

- 한 문장에는 하나의 역할을 하도록 한다.
- 접속사로 계속 연결시키지 않는다. 독립적인 지시로 분할한다. 조건과 예외 사항을 모두 보존한다.
- 한 문단에 너무 많은 내용을 작성하지 않는다.

### 문장부호와 기호

- 쉼표를 자제한다.
- 세미콜론을 사용하지 않는다.
- 키보드로 입력이 어려운 기호를 사용하지 않는다.
- 다음과 같은 기호를 사용하지 않는다.
  - 가운뎃점
  - 엠 대시 (—)
- 코드 문법 또는 정확한 원본 내 인용에 필요한 문장부호를 유지한다.

### 사실을 보고할 때

- 보고에는 확인된 사실만 기록한다. `읽다`, `보다`를 아무 상황에서나 사용하지 않는다.

- `보고서를 읽었다.`: 보고서에 대해서 무엇을 했는지 파악할 수 없다.

### 한국어 표현

한국어를 작성할 때에는 다음과 같은 규칙을 준수한다.

#### 주어와 행동

- 동사와 조사를 사용해 주어와 행동을 분명하게 한다.
- 문서와 기능이 무언가를 판단하거나 책임지는 것처럼 작성하지 않는다.
- 모든 문장을 능동 표현으로 작성하지 않는다. 모든 문장을 수동, 피동 표현으로 작성하지 않는다.

- `이 문서는 입력 품질 향상과 오류 처리 개선을 수행한다.`: 누가 어떤 입력을 검사하고 오류 뒤에 무엇이 변경되는지 파악할 수 없다.
- `업무를 안정적으로 처리하고 업무를 관리한다.`: 업무, 작업, 과업이라는 표현으로는 각각 무엇을 담당하는지 파악할 수 없다.

#### 명칭과 전문 용어

- 정확한 서비스명, API 이름, 명령어, 식별자, 기술 용어는 유지한다.
- 외국어로 된 명칭은 통용되는 한글 표기를 사용한다. 고유명사는 공식적으로 사용하는 한글 명칭을 사용한다. 일상적으로 사용되는 외래어의 경우 한글로 표기한다. 개발 관련 전문 용어는 영어 표현을 유지할 수 있다.
  - `reviewer`: 리뷰어
  - `OpenAI`: `오픈에이아이(OpenAI)`
  - `finding`: 리뷰 결과

#### 반복되는 문장 표현

- 반복되는 문장 표현이 있는지 확인한다. 되도록 `A부터 B까지의 C`, `A와 B를 C로 연결`와 같은 AI 상투적인 표현은 사용하지 않는다.
  - 다음과 같이 특정 범위가 정의되어 있는 경우에는 사용 가능하다.
    - `신청 기간은 3월 1일부터 3월 10일까지다.`

## 한국어 텍스트 검사

파일에 대해서 스크립트를 통해서 우리가 작성한 파일에 대해서 잘못된 표현이 있을지 검사할 수 있다.

### 검사 전 확인

스크립트를 사용할 때에는 다음을 주의한다.

- 비공개 식별자, 개인 위치가 출력되지 않도록 한다.
- 민감정보, 개인정보가 보이지 않도록 한다.
- 자격 증명과 비공개 URL을 확인한다.
- HTML 주석과 미해결 표시도 확인.

### 스크립트 실행

한국어 글은 이 `SKILL.md`를 기준으로 `scripts/scan.mjs`를 실행한다. 다음 입력 방식 중 하나를 사용한다.

- `--changed <repo>`: 스테이징된 변경, 스테이징되지 않은 변경과 추적하지 않는 파일을 포함한다.
- `--file <path>`: 정확한 대상 파일을 지정하며 여러 번 사용할 수 있다.
- `--stdin --source-name <name>`: 제공한 텍스트를 표준 입력으로 받을 수 있다.

### 스크립트 실행 결과 확인

JSON 전체를 확인한다. 다음을 더 구체적으로 확인한다.

- `sources`와 표현 및 긴 문단에 대한 `checks`.
- 각 `catalog`와 일치한 모든 `rules`를 확인
- 모든 경고와 각 `summary`

경고가 보이지 않으면 무시하지 않고 입력 데이터의 사이즈를 줄여서 다시 시도할 수 있다.

### 문구를 수정하는 경우

경고를 확인했으면 현재 텍스트의 내용적 의미, 의도, 목적을 유지하면서 자연스러운 대안으로 수정한다. 단어 하나만 바꿨다고 수정 완료라고 취급하지 않는다.

수정이 완료되면 추가적인 결함이 있을지에 대해서 한번 더 리뷰한다.
