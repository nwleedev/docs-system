# 요구사항 검토와 실행 플랜 작성

검토만 요청받으면 현재 요구사항으로 어디까지 계획할 수 있는지, 더 확인할 사항이 있다면 무엇인지 설명한다. 작성이나 보완을 요청받으면 확인된 요구와 조건을 문서에 반영한다. 플랜을 요청받으면 실행 순서와 확인 방법을 제시하고, 실행까지 요청받으면 그 순서에 따라 진행한다.

## 현재 상태와 기존 결정 확인

저장소 최상위부터 요구사항, 설계, 플랜을 관리하는 문서와 규칙을 찾는다. 기존 규칙에서 정한 위치와 작성 방식을 따른다. 규칙이 없고 설계 문서를 계속 관리할 기준이 필요하면 `docs/designs/README.md` 생성을 제안할 수 있다. 생성에 동의하면 [설계 문서 안내](references/_README.md) 전체를 읽고 그 내용을 복사한다. 첨부 파일이나 프롬프트를 저장소에 복사하지 않는다.

요청과 기존 요구사항에서 무엇이 달라져야 하고 어떤 조건은 유지해야 하는지 확인한다. 사용자가 무엇을 보고 완료를 판단할지도 살핀다. 코드와 Git 이력, 프로젝트 README, 인수인계 문서와 설계 기록에서 현재 상태와 이미 정한 내용을 찾는다. 외부 자료는 남은 질문에 답하는 데 필요할 때 조사한다.

## 플랜을 시작할 수 있는 조건

- **원하는 결과가 해석에 따라 달라지면** 기존 기록을 먼저 확인한다. 그래도 뜻이 분명하지 않으면 각 선택에 따라 무엇이 달라지는지 설명하고 어느 쪽을 원하는지 묻는다. 선택에 따라 필요한 절차도 달라지면 그 차이를 조사한다. 답이 필요한 단계만 보류한다.
- **원하는 결과는 분명하고 실현 방법을 모르면** 계획을 좌우하는 사실부터 조사한다. 무엇을 확인하면 다음 단계를 정할 수 있는지 밝힌다. 같은 요구를 충족하는 방법이 여럿이면 확인한 근거와 제약에 맞춰 고른다.
- **무엇을 바꾸고 어떻게 완료를 확인할지 분명하면** 플랜을 작성한다. 이미 요구사항을 충족한다면 그 근거를 제시하고 마친다.

### 예시

- **사용자에게 물어야 하는 경우.** “책 검색 결과를 파일로 내려받고 싶어요.” 첫 화면에는 10권이 보이고 검색된 책은 총 12권이다. “파일에는 현재 페이지의 10권을 담을까요, 검색된 12권을 모두 담을까요?”라고 묻는다. 답에 따라 파일에 넣을 책과 완료를 확인할 기준이 달라진다.
- **저장소를 조사하면 계획할 수 있는 경우.** “Windows와 macOS 설치 안내를 한 문서로 모아 주세요.” 두 안내에서 공통으로 사용하는 명령과 운영체제마다 다른 명령을 대조한다. 그래야 어느 설명을 한 번만 쓰고 어느 설명을 따로 유지할지 정할 수 있다.
- **변경이 필요 없는 경우.** 답이 “이번 검색에서 찾은 책 12권을 모두 내려받고 싶어요”라면 먼저 기존 기능으로 받은 파일을 연다. 두 페이지의 책 제목을 파일과 하나씩 대조해 12권이 모두 들어 있다면, 내려받는 방법과 확인 결과를 알려 준다.

## 실행 플랜 작성

1. 기준이 되는 요구사항과 결정을 확인한 뒤, 변경할 대상과 이유만 플랜에 명시한다.
2. 다음 단계에서 앞 단계의 어떤 결과가 필요한지 밝히고 순서를 정한다. 아직 시작할 수 없는 단계에는 무엇이 확인돼야 시작할 수 있는지 명시한다.
3. 단계별 완료 기준을 정한다. 마지막에는 실제 사용 상황에서 처음의 요구와 유지해야 할 조건을 함께 확인할 방법을 제시한다.

### 예시

- **두 운영체제의 설치 안내를 한 문서로 통합하는 플랜.** 두 README를 살펴보니 준비 절차는 같고 설치 명령은 서로 다르다. 기존 명령과 실행 순서를 유지하고 두 README 어디서든 새 안내를 찾을 수 있어야 한다는 조건이 정해졌다. 이때 제시할 플랜은 다음과 같다.
  1. 신규 설치 문서에 공통 준비 절차를 한 번만 설명하고, 설치 명령은 Windows용과 macOS용으로 나누어 안내한다. 원본과 대조해 각 운영체제에서 실행할 명령과 그 순서가 모두 보존됐는지 확인한다.
  2. 신규 설치 문서를 작성한 뒤, 각 README의 중복 설명을 해당 운영체제의 설치 안내로 바로 연결되는 링크로 바꾼다. 두 README에서 각각 링크를 열어 올바른 설치 명령까지 찾을 수 있는지 확인한다.

## 플랜에 따라 실행하고 갱신하기

실행을 요청받으면 선행 조건이 충족된 단계부터 진행한다. 각 단계에서 실제로 확인한 내용과 남은 절차를 구분하고, 마지막에 사용자가 기대한 결과를 확인한다.

새로 확인한 사실 때문에 방법만 달라지면 영향을 받는 단계와 확인 방법을 갱신한다. 약속한 결과나 제약까지 바꿔야 하면 무엇이 달라지는지 설명하고 결정을 구한다. 변경의 영향을 받는 단계는 결정될 때까지 보류하고, 영향을 받지 않는 작업은 계속한다.

### 예시

- **실행 중 링크가 끊긴 경우.** 설치 안내를 옮긴 뒤 설정 예제 링크를 열었더니 파일을 찾을 수 없다. 예제 파일은 그대로 있고 문서 위치가 바뀌어 상대 주소가 달라졌다면, 플랜에 링크를 고치는 절차를 추가한다. 기존 README에서 새 설치 안내를 거쳐 원래 예제 파일까지 열어 보고 완료 여부를 판단한다.
- **실행 중 원하는 결과가 바뀐 경우.** “설치 방법은 두 문서에 그대로 두고, 저장소 첫 화면에서 둘 다 찾을 수 있게 해 주세요”로 요청이 바뀌면 본문을 합치는 절차를 중단한다. 이미 옮긴 내용이 있는지 확인하고, 두 README에 설치 방법을 두고 첫 화면에 링크를 모으도록 플랜을 바꾼다. 첫 화면의 각 링크에서 운영체제별 설치 절차를 끝까지 읽을 수 있으면 완료다.

## 새 요구사항 문서를 만들 때

새 문서 생성을 요청받았고 저장소가 `docs/designs/README.md`의 문서 구성을 사용하면 아래 스크립트로 주제 폴더와 빈 `requirements.md`를 만들 수 있다. 스킬 디렉터리에서 Node.js 22.0.0 이상으로 실행한다. 내용 작성도 요청받았으면 생성 후 작성한다.

```sh
node scripts/requirements/create.mjs --repo <repository-root> --topic <topic-slug>
```

`--help`로 필요한 인자와 실패 시 확인할 사항을 볼 수 있다. 기존 문서를 갱신할 때는 스크립트를 다시 실행하지 않는다. 다른 문서 관리 방식을 쓰는 저장소에서는 그 규칙과 위치를 따른다. 조사와 결정 기록용 디렉터리는 보관할 문서가 생길 때 만든다.
