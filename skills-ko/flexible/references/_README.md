# 설계 문서

이 디렉터리에 주제별 요구사항, 조사 근거, 승인된 결정과 실행 플랜을 보관한다. AI는 요청받은 범위에서 검토, 조사, 계획과 검증을 진행하고 승인된 결정을 기록한다. 요청하지 않은 문서를 만들거나 기존 문서를 알리지 않고 수정하지 않는다.

## 묶음과 문서 구성

```text
docs/designs/
  README.md
  <topic>-<nonce>/
    requirements.md
    references/
      <reference>.md
    decisions/
      <decision>.md
    plan.md
```

주제마다 `requirements.md`를 둔다. 같은 주제를 이어서 다룰 때는 기존 폴더를 사용한다. 참고 자료, 결정과 플랜은 아래 조건에 따라 필요한 파일만 추가한다. 빈 디렉터리나 임시 내용을 미리 만들지 않는다.

## `requirements.md` — 원하는 결과와 유지할 조건

검토만 요청받으면 기존 문서를 읽고 어떤 내용이 빠졌거나 서로 다르게 해석되는지 설명한다. 작성이나 보완을 요청받으면 같은 주제의 요구사항 문서를 찾아 요청받은 부분을 고친다. 새 문서를 만들라는 명시적인 지시가 있을 때 새 파일을 만든다. 빈 문서를 요청받으면 내용은 비워 둔다.

사용자가 어떤 상황에서 어떤 결과를 얻어야 하는지와 그대로 유지해야 할 조건을 설명한다. 무엇을 보고 요구사항이 충족됐다고 판단할지도 밝힌다. 답에 따라 결과가 달라지는 내용은 질문으로 남긴다.

### 기록 예시

- **댓글 끄기의 완료 조건.** 관리자가 댓글을 끄고 기존 게시물을 열면 댓글 영역에 비활성 안내가 표시된다. 이미 달린 댓글은 그 화면에 보이지 않는다.
- **침수 수리 서비스의 미결정 질문.** 집이 침수됐을 때 여러 업체의 견적을 비교할 수 있으면 충분한가? 견적을 기다리지 않고 바로 출동을 요청할 수도 있어야 하는가?

## `references/*.md` — 다시 사용할 조사 근거

조사 결과를 이후 계획이나 검토에서 다시 참고해야 할 때 만든다. 조사한 질문과 출처, 각 자료에서 확인한 사실을 기록한다. 이를 근거로 방법을 제안할 때는 그 이유와 자료만으로 판단할 수 없는 점도 설명한다.

### 기록 예시

- **레고 건축물 세트의 시험 판매.** 시카고의 일부 매장에서는 블록 수가 같은 다른 세트보다 높은 가격에도 건축물 세트가 팔렸다. 이 시험 판매만으로는 다른 지역의 고객도 같은 가격에 구매할지 알 수 없다.

## `decisions/*.md` — 승인된 선택과 이유

이후 작업에 영향을 주는 선택이 승인됐고 그 이유를 남길 필요가 있을 때 만든다. 무엇을 결정해야 했는지 밝히고, 실제로 검토한 선택지 중 무엇을 왜 채택했는지 기록한다. 그 선택에 따라 달라지는 단계도 명시한다. 승인 전에는 선택지를 조사 자료나 미결정 질문으로 남긴다.

### 기록 예시

- **오리건 도로 관제 시스템의 홈 화면 개편.** 기존에는 홈 화면만 바꾸어도 시스템 전체를 테스트하고 배포해야 해 지역 관제센터들이 필요한 변경을 오래 기다렸다. 오리건주 교통부와 오리건주립대 개발팀은 시스템을 개별 배포할 수 있는 서비스로 나누기로 하고 홈 화면부터 개편했다.

## `plan.md` — 실행 순서와 완료 기준

원하는 결과가 정해졌고 실행 순서를 이후 작업에서 다시 참조해야 할 때 만든다. 기준이 되는 `requirements.md`의 절을 연결한다. 단계별로 무엇을 바꿔 어떤 결과를 얻을지 정한다. 다음 단계에 필요한 결과가 있으면 그 이유를 밝히고 순서를 정한다. 각 단계가 끝났는지, 마지막에 전체 요구사항을 충족했는지 확인할 방법도 제시한다.

구현 방법을 모르면 무엇을 알아내야 다음 단계를 정할 수 있는지 밝힌다. 선택이 필요한 단계에는 결정할 사항을 남기고, 그 결정에 영향을 받지 않는 절차는 먼저 계획한다. 실행을 요청받아 진행한 뒤에는 실제로 확인한 결과와 남은 절차를 기록한다.

요구사항이 바뀌거나 새 근거 때문에 계획대로 진행할 수 없으면 영향을 받는 단계를 멈춘다. 원하는 결과가 달라졌으면 변경이 확정되고 요구사항 수정이 허용된 뒤 `requirements.md`와 플랜에 차례로 반영한다. 방법만 달라졌으면 근거와 함께 해당 단계의 순서와 확인 방법을 갱신한다. 영향을 받지 않는 단계는 요청 범위 안에서 계속 진행할 수 있다.

### 기록 예시

- **시안 검토와 도구 선정이 끝나면 화면 구현을 시작한다.** 사용자가 시안을 직접 사용해 본 뒤 반영할 수정 사항을 정한다. 구현 도구는 시안 검토와 별도로 선정할 수 있다. 두 단계가 끝나면 화면을 구현하고 합의한 수정 사항이 반영됐는지 확인한다.
