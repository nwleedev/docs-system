# 저장소 개발 지침 적용

현재 저장소의 `docs/dev/README.md`를 지속적으로 사용할 개발 지침, 뒷받침 근거와 검증의 기준으로 삼는다. 이 스킬은 필요한 절차와 순서를 정한다. README를 대신하거나 코드, 의존성, 설정, 도구 또는 문서 변경을 허용하지 않는다.

## 기준 문서 확인

1. 저장소 최상위를 확인하고 `<repo-root>/docs/dev/README.md`가 있는지 확인한다.
2. 있으면 전부 읽는다. 이 스킬의 `references/_README.md`와 비교하거나 동기화하지 않는다.
3. 없으면 요청에 저장소별로 유지할 개발 규칙이 필요한지 판단한다. 스킬을 호출했다는 이유만으로 README를 만들지 않는다.
4. 유지할 규칙이 필요하면 동봉된 `references/_README.md`와 정확한 대상 위치를 확인하고 저장소 README를 만들지 사용자에게 묻는다.
5. 승인받으면 첫 줄의 유지보수 주석을 제외한 내용을 복사하고 만든 README를 전부 읽는다. 기존 README는 덮어쓰지 않는다.
6. 생성을 거절하면 저장소 지침, 기존 문서 위치와 디렉터리 구성을 조사한다. 허용된 작성 요청에는 이 근거로 정할 수 있는 위치를 사용한다. 정할 수 없으면 묻는다. 읽기 전용 요청에서는 수정하지 않는다.
7. 사용자 요청과 적용할 저장소 지침을 따른다. 저장소 README와 중요한 충돌이 있으면 말없이 선택하지 않고 보고한다.

## 필요한 절차 선택

읽기 전용 선행 조사와 마지막 검증을 포함해 요청한 성과에 필요한 절차를 모두 선택한다. 무관한 일은 제외한다. 의존하는 절차는 순서대로 진행한다. 이후에는 새 근거 때문에 원래 범위 안에서 필요해진 절차만 추가한다.

- **현황 파악:** 기술 구성, 정확한 버전, 현재 동작, 기존 지침, 검사와 저장소 근거를 확인한다.
- **조사:** 적용할 패턴, 안티패턴, 의존성, 위험과 검증 방법을 조사한다.
- **지침 작성과 검토:** README의 수록 조건에 따라 유지할 저장소 지침을 만들거나 고치거나 검토한다.
- **검사 도구 검토:** 정적 분석, 타입 또는 스키마 검사, 테스트, 훅, CI, 실행 중 검사 또는 책임 있는 검토를 비교하거나 제안한다.
- **변경 적용:** 명시적으로 요청한 코드, 의존성, 설정이나 도구를 변경한다.
- **검증:** 현재 근거로 지침, 검사 또는 구현을 검증한다.

읽기 전용 조사로는 변경 권한이 생기지 않는다. 선택지에 따라 저장소 전체 정책, 비용, 호환성, 데이터나 동작이 크게 달라지면 사람의 판단을 기다린다.

## 저장소와 외부 근거 조사

1. 필요한 매니페스트, lockfile, 설정, 스크립트, CI, 테스트, 생성물, 코드, 결정과 `docs/dev` 파일만 조사한다. 기존 코드와 글은 낡을 수 있는 근거이며 올바른 패턴의 증거로 보지 않는다.
2. 외부 지침이 버전에 따라 달라지면 정확한 기술과 의존성 버전을 기록한다. 최신 공식 문서, 표준과 소스 저장소를 우선하고 저장소 근거와의 충돌을 적는다.
3. 패턴 사례를 조사할 때는 고정된 리비전의 공개 오픈 소스 애플리케이션과 확인된 실패 또는 변경 이유를 함께 사용한다. 현재 애플리케이션 코드는 안티패턴이나 권장 예시의 출처로 쓰지 않는다. 현재 기술 구성, 동작과 연결 지점을 확인하는 데만 사용한다.
4. 저장소 README가 정한 안티패턴 필수 항목을 적용한다. 코드 모양만으로 분류하거나 가능한 모든 안티패턴을 열거하려 하지 않는다.
5. 동작을 바꾸기 전에 관찰할 수 있는 동작, 외부 API, 저장 데이터, 오류 처리, 영향을 받는 호출자와 연결 지점 중 요청에서 변경을 허용하지 않은 것을 확인한다.

## 신뢰할 수 있는 검사 중 비용이 가장 적은 방법 선택

1. 의존성이나 맞춤 규칙을 추가하기 전에 기존 컴파일러, 포매터, 린터, 타입 또는 스키마 검사기, 테스트, 훅과 CI를 재사용한다.
2. 의도한 실패를 허용 가능한 정확도와 비용으로 찾을 때만 기계적 검사를 사용한다. 새 정적 규칙은 위반 사례와 정상 사례 또는 이에 상응하는 실행 근거로 확인한다.
3. 정적 분석으로 판단할 수 없는 속성은 실패를 관찰할 수 있는 테스트, 실행 중 검사, 브라우저 검사 또는 담당 검토자가 판단하는 방법을 사용한다.
4. 저장소에서 정한 명령을 사용한다. 없으면 추정한 명령을 제안으로 제시하고 실행 전에 승인받는다. 검증 뒤 이번에 시작한 프로세스를 종료한다.
5. 필수 검사가 실패하거나 미해결 결과에 아직 승인받지 않은 결정이 필요하면 그 검사에 의존하는 변경을 진행하지 않는다.

## 의존성과 허용된 변경 처리

1. 외부 의존성을 고르거나 바꾸기 전에 해석된 직접 및 전이 의존성 그래프, 선택한 버전의 공식 연동 방식, 적용할 패턴, 호환성, 유지보수, 보안, 라이선스, 설치된 대안, 플랫폼 기능과 내부 구현을 조사한다.
2. 조사만으로 의존성, 설정, 검사, 지침이나 코드 변경이 허용되지 않는다. 명시적으로 요청한 범위의 변경만 적용하고 무관한 동작과 사용자의 변경을 보존한다.
3. 허용된 의존성 변경 뒤에는 실제 매니페스트, lockfile과 해석된 그래프의 변경을 살핀다. 예상하지 못한 전이 의존성 갱신을 조사한다.
4. README의 수록 조건을 충족하고 문서 변경이 허용됐을 때만 유지할 지침을 추가한다. 각 규칙을 관리하는 문서는 하나로 정한다.

## 마무리

절차를 모두 마친 뒤 적용할 README와 저장소 검사를 한 번 실행한다. 조사한 근거와 버전, 출처, 변경 파일, 명령과 결과, 남은 불확실성과 사람의 판단이 필요한 질문을 보고한다. 글로 쓴 지침이나 진행 보고를 구현 증거로 제시하지 않는다.
