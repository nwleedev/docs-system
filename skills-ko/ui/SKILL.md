# UI 설계

대화, 시각 비교와 직접 확인할 수 있는 HTML로 사용자가 의도한 서비스 경험을 구체화한다. 구체화하는 동안 요청한 동작과 확정한 선택을 보존한다. 디자인을 고르는 사람과 서비스를 사용할 사람은 필요한 정보가 다를 수 있다. 디자인 논의는 서비스 화면 밖에서 한다.

## 설계 근거 마련

새 방향에서는 원하는 성과, 대표 시나리오, 필수 행동과 상태, 제약, 기존 지침, 원하는 인상과 피할 특징을 확인한다. 있는 문맥부터 사용한다. 중요한 미확인 사항은 일찍 논의한다. 디자인 용어와 CSS 값을 요구하지 않는다. 답이 이미 있으면 설문을 요구하지 않는다.

명시된 요구사항과 확정된 선호를 기존 구현, 초안과 가정에서 구분한다. 사람들이 무엇을 보고 판단하고 실행하는지 설명한다. 반복과 실수의 비용도 포함한다. 기능 목록만으로는 시나리오가 되지 않는다. 지정된 상호작용을 더 쉬운 대안으로 바꾸거나 침묵을 승인으로 해석하지 않는다.

조사 전에 정보 우선순위, 행동 배치, 밀도와 해당 분야의 정보 관계를 잠정적으로 설명한다. 이후 디자인 테마와 서비스 UI를 검색하고 눈으로 확인할 수 있는 차이를 제시한다. 첫 본격 UI 시안 전에 피드백으로 방향을 정한다. 테마 선택은 논의한 특징에만 적용되는 승인이다. 보류한 선택이나 수정은 탐색을 반복하지 말고 현재 단계에서 재개한다.

## 공통 규칙

모든 절차에 적용하는 규칙은 여기에 두고 참고 문서에 반복하지 않는다.

- 각 주장을 **직접 관찰**인 `Observed`, **출처에 명시**된 사실인 `Source-stated`, **시나리오에 따른 해석**인 `Interpretation`, **근거 미확인**인 `Unknown`으로 구분한다. 출처, 화면, 상태와 필요한 뷰포트 또는 날짜를 보존한다. 주장의 범위는 근거를 넘을 수 없다. 검색 요약, 텍스트나 DOM만의 조사와 열지 않은 링크로는 외관을 입증할 수 없다. 생성했거나 확인하지 않은 이미지로 출시된 UI를 관찰했다고 할 수 없다. 정확한 CSS 값, 토큰과 breakpoint에는 명세, 코드, Storybook 또는 조사한 DOM/CSS가 필요하다. 스크린샷 추정값은 잠정값으로 남긴다.
- **확정된 선호와 기피**는 명시적 선택과 그 범위를 포함한다. 이를 **미해결 선택**, **가설**, **잠정 기본값 또는 구현 제안**, **검증된 규칙**과 구분한다. 검증된 규칙에는 현재 실행 중인 UI 근거, 확인한 조건, 확정된 시각 판단과 적용 범위가 있어야 한다. 빌드, 인수인계 자료, 과거 스크린샷이나 마음에 든 시안만으로 실행 중인 UI, 동작, 접근성이나 구현값을 검증할 수 없다. 승인된 선택을 기본값으로 바꾸지 않는다. 침묵은 승인도 거절도 아니다.
- 외관은 볼 수 있는 이미지나 실행 중인 화면으로 보여 준다. ASCII나 텍스트 와이어프레임을 쓰지 않는다. 근거가 없으면 그 근거가 필요한 결론만 미완료로 남긴다. 시안 확인, 구현에 넘길 자료, 실행 중인 UI 검증과 공통 규칙 검증을 구분해 보고한다. 개선은 측정값과 비교 기준이 있을 때만 주장한다.
- 익숙한 상호작용과 접근성 관례를 보존하면서 시나리오와 해당 분야의 내용에서 구별되는 구성을 도출한다. 참고 사례는 전략을 얻는 자료다. 색상, 글꼴, 모서리와 그림자를 모아 조합하는 재료로 취급하지 않는다. 최종 규칙은 서비스 이름에 기대지 않고 설명한다.
- 명시적 요청이 없으면 테마 후보와 시안 방향에서 SaaS 디자인을 제외한다. 구독 모델이나 기업 대상이라는 사실은 그런 요청이 아니다. SaaS 서비스도 사용한다는 이유로 일반적인 조작 요소를 금지하지 않는다.
- 현재 화면에 필요한 기본 규칙을 정하고 실제 시나리오가 있을 때만 확장한다. 전체 토큰 계층, 모든 컴포넌트 변형, 참고 자료 저장 서비스나 추가 검증 화면을 미리 만들지 않는다. 개선할 때 필수 기능을 보존한다.
- 요청한 위치와 권한 안에서 독립 HTML 시안 파일을 만들고 수정한다. 운영 애플리케이션 파일, 토큰, 테마, 컴포넌트와 테스트는 바꾸지 않는다. 피드백 서버, 에이전트 연결 도구, 브라우저 확장이나 시안 내부 검토 도구를 추가하지 않는다. 서비스 조작 요소와 필요한 사용자 도움말은 서비스에 남긴다.

## 선택적 디자인 에이전트

명시적으로 요청한 경우에만 디자인 에이전트를 만든다. 수를 지정하지 않았으면 실행 환경의 한도 안에서 하나를 사용한다. 시나리오, 확정된 선택, 피할 특징과 한정된 디자인 책임을 전달한다. 제안만으로 방향이 승인되거나 운영 코드 수정이 허용되지는 않는다. 위임할 수 없으면 에이전트를 만들었다고 하지 말고 그 제한을 보고한다.

## 필요한 절만 읽기

공통 규칙과 선택한 절을 하위 절까지 전부 읽는다. 연결한 절은 명시한 조건에 해당할 때만 따라간다. 참고 파일 전체를 기본으로 불러오지 않는다. 탐색을 다시 시작하지 말고 현재 확인할 수 있는 다음 행동에서 이어간다.

- 새 방향이나 방향 변경: 위의 설계 근거를 마련하고 [테마 조사와 비교](references/research.md#조사-필요-여부-판단), [답변이-필요한-질문](references/decisions.md#질문-필요-여부-판단)을 읽는다.
- 외부 사례: [전략 탐색](references/research.md#적합한-전략-탐색), [실제 화면 확인](references/research.md#실제-화면-확인), [전략 분석](references/research.md#분석-비교와-적용)을 순서대로 읽는다. 직접 확인만 필요하면 화면 확인 절만 읽는다.
- 짧은 답변이나 비교 재개: [이어가기](references/decisions.md#현재-문맥에서-이어가기), [답변 해석](references/decisions.md#선택-요청과-답변-해석), [차수 계산](references/decisions.md#차수-계산과-탐색-종료)을 읽는다.
- HTML 시안: [현재 기본 규칙](references/implementation.md#현재-화면의-기본-규칙-정리), [생성과 직접 확인](references/implementation.md#시안-생성과-확인)을 읽는다.
- 요소 선택 안내: [화면 밖에서 선택하고 복사하기](references/implementation.md#시안-밖에서-요소-선택)를 읽는다.
- 복사한 XPath와 수정 요청: [요청 해석](references/decisions.md#xpath-수정-요청-해석), [대상 확인과 수정](references/implementation.md#복사한-전체-xpath로-수정)을 순서대로 읽는다. 선택과 복사는 서비스 HTML 밖에서 한다.
- 구현에 넘길 자료: [검증 조건](references/implementation.md#검증-조건-정의), [자료 준비](references/implementation.md#구현에-넘길-자료-준비)를 읽는다. 현재 규칙이 없거나 바뀔 때만 기본 규칙을 읽는다.
- 변경 후 UI 확인: [현재 근거와 범위](references/validation.md#근거와-범위-확인), [화면 검사](references/validation.md#화면의-네-측면-검사), [차이와 재사용](references/validation.md#차이-해결과-재사용-검증)을 읽는다. 디자인 시스템을 평가할 때만 [시스템 완료](references/validation.md#화면-검증과-초기-시스템-완료-구분)를 읽는다.

## 이어가는 데 필요한 문맥 반환

바뀐 결정이나 근거, 영향을 받는 범위, 미해결 조건, 보류한 정확한 질문과 허용 답변, 다음 행동과 필요한 입력을 반환한다. 확인할 수 있는 이전 결과가 바뀌지 않았으면 반복하지 않는다. 필요하면 후보 식별자와 볼 수 있는 자료, 선택 상태와 명시된 이유, 완료 또는 보류한 차수와 승인된 연장도 유지한다.

이전 문맥이 없거나 압축됐으면 다음 행동에 필요한 목표, 시나리오, 설계 논지, 제약, 전략과 근거, 확정된 선택, 제안, 충돌, 확인한 대상과 조건 및 차수 상태를 확인 가능한 자료에서 재구성한다. 빠진 정보만 요청한다. 확인할 수 없는 문맥을 복원했다고 주장하지 않는다. 고정된 스키마나 저장 요건은 아니다. 프로젝트별 선택을 이 스킬에 저장하거나 저장하지 않은 문맥이 계속 보존된다고 주장하지 않는다.
